## 1. The merchant chat on Managed Agents loses replies after a network blip, shows messages as "sending" forever, and fails to archive finished sessions

**基于 Managed Agents 的商家聊天在网络抖动后丢失回复、消息一直显示“发送中”，而且无法归档已结束的会话** · `Agent Loop` · `Hard`

### Question · 题目

A merchant-facing chat runs on Claude Managed Agents. The web backend sends the merchant's message with `events.send`, then opens the event stream and relays events to the browser. Support reports four problems: sometimes the first reply never appears; after a mobile network drop, part of an answer is missing; some messages show "sending" forever; and the cleanup job that archives sessions right after they go idle intermittently gets a 400 saying the session is still running.

> 一个面向商家的聊天功能运行在 Claude Managed Agents 上。Web 后端用 `events.send` 发送商家的消息，然后打开事件流，把事件转发给浏览器。客服反馈了四个问题：有时第一条回复根本不出现；手机网络断开后，某个回答缺了一部分；有些消息一直显示“发送中”；而在会话进入空闲后立即归档会话的清理任务，偶尔会收到 400，提示会话仍在运行。

Explain each problem and fix the client.

> 解释每个问题，并修复这个客户端。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The event stream is a live feed, not a log: it delivers what happens while you are listening and does not replay the past. A reliable client opens the stream before acting, recovers missed history from the events API, tracks what the server has actually processed, and does not trust the first idle signal for state changes.

> **核心思路。** 事件流是实时推送，而不是日志：它只投递你在监听期间发生的事情，不会重放过去的内容。一个可靠的客户端会在行动之前先打开流，从事件 API 中补回错过的历史，跟踪服务端实际处理了什么，并且不会因为第一次收到空闲信号就去改变状态。

**Four problems, four patterns.**

> **四个问题，对应四种模式。**

- **Missing first reply: stream first, then send.** If you send before the stream is open, the agent may process the message and emit its first events before your consumer is attached. Open the stream, which starts buffering immediately, then send.
  > **第一条回复缺失：先开流，再发送。** 如果在流打开之前就发送，Agent 可能会在你的消费者接上之前就处理完消息并发出最初的事件。先打开流（它会立即开始缓冲），再发送。
- **Gaps after a drop: lossless reconnect.** SSE has no replay, so a naive reconnect starts from "now". On reconnect, open the stream, read the full history with `events.list()`, then tail the live stream, handling each event ID once. Terminal checks must still run for events you already handled, or a terminal event that was in the history is skipped and the loop never ends.
  > **断线后出现缺口：无损重连。** SSE 不支持重放，所以简单的重连会从“现在”开始。重连时，先打开流，用 `events.list()` 读取完整的历史，再继续读取实时流，并对每个事件 ID 只处理一次。对于已经处理过的事件，仍然必须执行终止检查，否则历史中的终止事件会被跳过，循环永远不会结束。
- **"Sending" forever: read `processed_at`.** A message you send appears on the stream with `processed_at` null while it is queued and again with a timestamp once processed. But `user.tool_result`, `user.custom_tool_result` and `user.define_outcome` are processed on receipt and arrive already stamped, so a UI that waits for a null first never clears them.
  > **一直“发送中”：读取 `processed_at`。** 你发送的消息在排队期间会以 `processed_at` 为 null 出现在流上，处理完之后会带着时间戳再出现一次。但 `user.tool_result`、`user.custom_tool_result` 和 `user.define_outcome` 在收到时就被处理，到达时已经带有时间戳，所以一个等待“第一次出现时为 null”的界面永远不会把它们标记为已完成。
- **400 on archive: the post-idle race.** The stream emits `session.status_idle` slightly before the session's queryable status reflects it. Poll the session briefly until it is no longer running before archiving, and leave it if it is still running after a short wait.
  > **归档时返回 400：空闲之后的竞态。** 流发出 `session.status_idle` 的时间，略早于会话的可查询状态反映这一变化的时间。在归档之前，短暂地轮询会话，直到它不再处于运行状态；如果短暂等待后仍在运行，就先不要动它。

```go
// Replay feeds history first, then the live stream, to handle exactly once per
// event ID. It returns true when a terminal event was seen, even one already
// handled, so the caller can stop.
func Replay(history, live []Event, handle func(Event)) bool {
	seen := map[string]bool{}
	for _, batch := range [][]Event{history, live} {
		for _, e := range batch {
			if !seen[e.ID] {
				seen[e.ID] = true
				handle(e)
			}
			if e.Type == "session.status_terminated" {
				return true
			}
		}
	}
	return false
}
```

**Do not end on idle alone.** A session also goes idle while waiting for a tool confirmation or a custom tool result. Keep the stream open when the idle stop reason is `requires_action`, and handle the pending request.

> **不要只因为空闲就结束。** 会话在等待工具确认或自定义工具结果时也会进入空闲状态。当空闲的停止原因是 `requires_action` 时，要保持流处于打开状态，并处理待处理的请求。

**Trade-offs.** Replaying history on every reconnect costs extra reads on long sessions; you can start from the last event ID you processed if you store it. Polling before archive adds a second or two to cleanup, which is far cheaper than intermittent failures. Webhooks can replace long-lived streams for background sessions, but an interactive chat still needs the stream for live text.

> **取舍。** 每次重连都重放历史，会在长会话上带来额外的读取；如果你保存了最后处理的事件 ID，就可以从那里开始。归档前轮询会让清理多花一两秒，但这远比间歇性的失败便宜。对于后台会话，可以用 webhook 代替长连接的流，但交互式聊天仍然需要用流来实时输出文本。

</details>

## 2. The nightly feed audit did not run for three nights, and nothing alerted

**夜间 feed 审计连续三晚没有运行，却没有任何告警** · `Production` · `Hard`

### Question · 题目

A Managed Agents scheduled deployment runs a feed audit every night at 2:00 in `America/New_York`. Merchants noticed missing audit emails for three nights. Investigation finds a mix of causes: one night the run hit a rate limit, another night the deployment had been paused during an incident and was unpaused the next day, and one night's session sat idle waiting for a tool approval. The team's dashboard only watched for failed sessions.

> 一个 Managed Agents 的定时部署每晚在 `America/New_York` 时区的 2:00 运行 feed 审计。商家注意到连续三晚都没有收到审计邮件。调查发现原因各不相同：一晚运行碰到了限流；另一晚由于事故期间部署被暂停，第二天才恢复；还有一晚的会话一直处于空闲状态，在等待一次工具审批。而团队的看板只监控失败的会话。

Explain each failure and design monitoring that catches all of them.

> 解释每一种失败，并设计能够发现所有这些失败的监控。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A schedule can fail without any session failing: a run may never create a session, a paused schedule does not fire, and a session can wait forever. Monitor the thing you actually need, a successful audit each night, rather than only the errors you expect.

> **核心思路。** 定时任务可能在没有任何会话失败的情况下就失败了：一次运行可能根本没有创建会话，被暂停的定时任务不会触发，而会话也可能永远等待下去。要监控你真正需要的东西，即每晚一次成功的审计，而不仅仅是你预料中的那些错误。

**What the platform does in each case.**

> **在每种情况下，平台会怎么做。**

- **Rate limited.** The run is recorded immediately as `session_rate_limited` with no retry; the schedule simply tries again at the next occurrence. No session exists, so a session-based dashboard sees nothing.
  > **被限流。** 这次运行会立即被记录为 `session_rate_limited`，并且不会重试；定时任务只会在下一次触发时间再试。由于根本没有会话，基于会话的看板什么也看不到。
- **Paused.** Pausing suppresses scheduled triggers; unpausing resumes from the next occurrence, and missed triggers are not backfilled.
  > **被暂停。** 暂停会抑制定时触发；恢复后从下一次触发时间开始，错过的触发不会被补跑。
- **Waiting for approval.** No client is attached when a run fires, so a call that pauses for approval, under `always_ask` (the MCP default) or `auto` with no determination, waits indefinitely unless a `session.status_idled` webhook handler answers it.
  > **等待审批。** 运行触发时没有客户端连接，所以一个因审批而暂停的调用，无论是在 `always_ask`（MCP 的默认策略）下，还是在 `auto` 下没有得出结论时，都会无限期地等待，除非有一个处理 `session.status_idled` webhook 的程序来作答。
- **Also possible: DST and archived agents.** Wall-clock times that do not exist on the spring-forward day, such as 2:00 AM, are skipped, and fall-back times fire twice. If the agent is archived, the deployment is archived too, and no run is recorded at all.
  > **另外还可能：夏令时和被归档的 Agent。** 在夏令时开始那天并不存在的本地时间（例如凌晨 2:00）会被跳过，而在夏令时结束那天重复出现的时间会触发两次。如果 Agent 被归档，部署也会随之被归档，并且根本不会留下任何运行记录。

**Monitoring.** Subscribe to the `deployment_run.*` webhook events and list runs with `has_error` to see failures such as `session_rate_limited`, `vault_not_found` or `environment_archived`. Handle `session.status_idled` to answer or deny pending approvals by rule. Most importantly, alert on absence: if no successful audit has completed within a day plus a grace period, page someone, which also catches paused or archived deployments that record nothing.

> **监控。** 订阅 `deployment_run.*` webhook 事件，并用 `has_error` 列出运行记录，以发现 `session_rate_limited`、`vault_not_found` 或 `environment_archived` 等失败。处理 `session.status_idled`，按规则对待处理的审批作答或拒绝。最重要的是，对“缺失”进行告警：如果在一天加上一段宽限期内都没有完成一次成功的审计，就通知相关人员，这同样能发现那些不留下任何记录的、被暂停或被归档的部署。

```go
// overdue reports a deployment whose last successful run is older than the
// schedule allows, which also catches deployments that stopped recording runs.
func overdue(lastSuccess, now time.Time, every, grace time.Duration) bool {
	return now.Sub(lastSuccess) > every+grace
}
```

**Fixes.** Move the schedule out of the 1 to 3 AM local window or use UTC. After an incident pause, trigger a manual run, which works even while paused, to catch up deliberately. Give unattended agents tools that do not need approval, or a webhook handler that decides. Keep a deployment budget, which is copied onto each fired session.

> **修复方法。** 把定时时间移出本地时间凌晨 1 点到 3 点的区间，或者改用 UTC。在因事故暂停之后，手动触发一次运行（即使在暂停期间也可以），有意识地把落下的补上。给无人值守的 Agent 配置不需要审批的工具，或者提供一个负责做决定的 webhook 处理程序。保留部署预算，它会被复制到每一个被触发的会话上。

**Trade-offs.** Absence alerts need a clear definition of success, such as the report written and emailed, not just a session ended. Manual catch-up runs cost money and can overlap with the next scheduled run, so make the audit idempotent per night. Removing approvals for unattended runs trades human oversight for reliability, so restrict those agents to safe, reversible actions.

> **取舍。** 缺失告警需要对“成功”有清晰的定义，例如报告已生成并已发送邮件，而不仅仅是某个会话结束了。手动补跑要花钱，而且可能与下一次定时运行重叠，所以要让审计按“每晚”保持幂等。为无人值守的运行去掉审批，是用人工监督换取可靠性，所以要把这些 Agent 限制在安全、可撤销的操作范围内。

</details>

## 3. The competitor-price agent fetches 40 product pages per run, and the context fills with menus and cookie banners

**竞品价格 Agent 每次运行要抓取 40 个商品页面，上下文被导航菜单和 cookie 横幅塞满** · `RAG` · `Medium`

### Question · 题目

A price-intelligence agent on Claude Opus 5.5 searches for each of a merchant's products on competitor sites and fetches the product pages to read prices and stock. It uses `web_search_20250305` and a client-side scraping tool the team wrote. Runs are slow and expensive, prices are sometimes read from "related products" widgets, and the agent occasionally fetches pages no one asked for after reading a page full of links.

> 一个运行在 Claude Opus 5.5 上的价格情报 Agent，会在竞品网站上搜索商家的每个商品，并抓取商品页面来读取价格和库存。它使用 `web_search_20250305` 以及团队自己写的一个客户端抓取工具。运行又慢又贵，价格有时是从“相关商品”小组件里读出来的，而且 Agent 在读到一个满是链接的页面后，偶尔会去抓取没人要求的页面。

How would you redesign the retrieval?

> 你会如何重新设计这个检索过程？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Raw web pages are mostly noise: navigation, scripts, recommendations. The less of that reaches the model's context, the cheaper and more accurate each answer. Use the newer server-side web tools, which filter content before it reaches the context, and constrain where they can go.

> **核心思路。** 原始网页大部分是噪音：导航、脚本、推荐内容。进入模型上下文的噪音越少，每个回答就越便宜、越准确。使用较新的服务端网络工具，它们会在内容进入上下文之前进行过滤，并限制它们可以访问的范围。

**Mechanism.** `web_search_20260209` and `web_fetch_20260209` support dynamic filtering on current models, including Claude Opus 5.5: the model writes and runs code to filter results before they reach the context window. It is built into these versions and activates automatically, with no beta header and no separate code execution tool. Declaring a standalone `code_execution` tool alongside them creates a second execution environment that can confuse the model.

> **机制。** `web_search_20260209` 和 `web_fetch_20260209` 在包括 Claude Opus 5.5 在内的当前模型上支持动态过滤：模型会编写并运行代码，在结果进入上下文窗口之前对其进行过滤。这一功能内置在这些版本中并自动启用，不需要 beta 请求头，也不需要单独的代码执行工具。在它们旁边再单独声明一个 `code_execution` 工具，会创建第二个执行环境，可能让模型感到困惑。

**Redesign.**

> **重新设计。**

- **Switch tool versions** to `web_search_20260209` and `web_fetch_20260209`, and retire the custom scraper for pages the server tools can read.
  > **切换工具版本**为 `web_search_20260209` 和 `web_fetch_20260209`，对于服务端工具能读取的页面，停用自定义抓取工具。
- **Constrain the tools.** Use `allowed_domains` with the competitor sites you track, `max_uses` to cap fetches per run, and `max_content_tokens` on web fetch to bound each page.
  > **约束这些工具。** 用 `allowed_domains` 限定为你们跟踪的竞品网站，用 `max_uses` 限制每次运行的抓取次数，并在网页抓取上用 `max_content_tokens` 限制每个页面的大小。
- **Ask for exactly what you need.** Tell the agent to return price, currency, stock and the URL for the main product, not recommendations, and turn on web fetch's `citations` option so each price can point to its source text.
  > **只要你真正需要的东西。** 告诉 Agent 只返回主商品的价格、币种、库存和 URL，不要推荐商品，并开启网页抓取的 `citations` 选项，让每个价格都能指向它的来源文本。
- **Handle tool errors.** Web search and web fetch errors return a normal response whose result content is an error object, such as `max_uses_exceeded`, not an exception. Check for it and record "unknown", never "no competitor".
  > **处理工具错误。** 网页搜索和网页抓取出错时返回的是正常响应，其结果内容是一个错误对象，比如 `max_uses_exceeded`，而不是抛出异常。检查这种情况并记录为“未知”，绝不能记录为“没有竞品”。

```json
{"tools": [
  {"type": "web_search_20260209", "name": "web_search",
   "allowed_domains": ["amazon.com", "ebay.com"], "max_uses": 10},
  {"type": "web_fetch_20260209", "name": "web_fetch",
   "allowed_domains": ["amazon.com", "ebay.com"], "max_uses": 40,
   "max_content_tokens": 20000}
]}
```

**About unrequested fetches.** Web fetch only fetches URLs already present in the conversation, but a fetched page puts many URLs there, which is how the agent wandered. Domain allow-lists and `max_uses` bound that, and the instruction to stay on the product's own page keeps the task focused.

> **关于没人要求的抓取。** 网页抓取只会抓取对话中已经出现过的 URL，但一个被抓取的页面会把很多 URL 带进对话，这就是 Agent 到处乱逛的原因。域名白名单和 `max_uses` 可以限制这一点，而“只看商品自身页面”的指令能让任务保持专注。

**Platform note.** Check availability before relying on these tools everywhere: on Vertex AI only the basic `web_search_20250305` is available and web fetch is not, so a multi-cloud deployment needs a fallback path there.

> **平台说明。** 在到处依赖这些工具之前，先确认可用性：在 Vertex AI 上只有基础版的 `web_search_20250305`，并且没有网页抓取，所以多云部署需要在那里准备一条降级路径。

**Trade-offs.** Server-side tools are simpler and filter better, but some sites block automated fetching, so keep the custom scraper as a fallback for those, behind your own rate limits. Tight content limits save tokens but can cut off the price on long pages; measure on real pages before choosing a number.

> **取舍。** 服务端工具更简单，过滤效果也更好，但有些网站会阻止自动抓取，所以对这些网站要保留自定义抓取工具作为降级方案，并配合你们自己的限流。严格的内容上限能节省 token，但可能在很长的页面上把价格截掉；在确定具体数值之前，先在真实页面上测量。

</details>

## 4. Sessions on the self-hosted sandbox sit in a queue, and traces show nothing about tool calls

**自托管沙箱上的会话一直在队列中等待，而追踪中看不到任何工具调用的信息** · `Evals & Observability` · `Medium`

### Question · 题目

For an enterprise merchant, the team runs Managed Agents with a self-hosted environment: workers in the merchant's VPC claim work and run the tools. After a deploy, merchants report that the agent "thinks forever". The OpenTelemetry traces in the team's backend show model requests but no tool calls at all, so nobody can tell where time goes. The workers are woken by a webhook handler that runs the work loop inside the HTTP request.

> 为了一个企业商家，团队使用自托管环境运行 Managed Agents：位于商家 VPC 中的 worker 领取工作并运行工具。一次部署之后，商家反馈 Agent“一直在思考”。团队后端中的 OpenTelemetry 追踪能看到模型请求，却完全看不到工具调用，所以没人能说清时间花在了哪里。worker 由一个 webhook 处理程序唤醒，而这个处理程序在 HTTP 请求内部运行工作循环。

How would you diagnose and fix this, and what would you monitor?

> 你会如何诊断并修复这个问题？你会监控什么？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** In a self-hosted environment the work happens in two places: the agent loop on Anthropic's side and the tools in your workers. Observability must cover both, and the queue between them is the first place to look when nothing happens.

> **核心思路。** 在自托管环境中，工作发生在两个地方：Anthropic 一侧的 Agent 循环，以及你们 worker 中的工具。可观测性必须同时覆盖这两者，而当什么都没发生时，首先要看的就是两者之间的队列。

**Check the queue first.** The work stats endpoint returns `depth`, `pending`, `oldest_queued_at` and `workers_polling`. Work queued with no worker polling means the workers are down or misconfigured; workers polling but old items waiting means they cannot keep up or are stuck on items. Call these control-plane endpoints from outside the worker host, because putting an organization-scoped API key on the worker host exposes it to the agent's tool calls.

> **先检查队列。** 工作统计接口会返回 `depth`、`pending`、`oldest_queued_at` 和 `workers_polling`。有工作在排队却没有 worker 在轮询，说明 worker 挂了或配置有误；有 worker 在轮询但有旧的工作项还在等待，说明它们跟不上，或者卡在了某些工作项上。要在 worker 主机之外调用这些控制面接口，因为把组织级别的 API key 放到 worker 主机上，会让它暴露给 Agent 的工具调用。

```go
// stalled says why work is not being picked up, or "" if the queue looks healthy.
func stalled(s QueueStats, now time.Time, maxWait time.Duration) string {
	switch {
	case s.Depth > 0 && s.WorkersPolling == 0:
		return "work queued but no worker is polling"
	case s.Depth > 0 && now.Sub(s.OldestQueuedAt) > maxWait:
		return "oldest work item has waited too long"
	default:
		return ""
	}
}
```

**The webhook handler bug.** With webhook-driven wake, the handler must verify the delivery, acknowledge it, and run the drain in the background. A session run outlives the webhook delivery timeout, so draining inside the HTTP handler gets cut off and work stays queued.

> **webhook 处理程序的 bug。** 使用 webhook 唤醒时，处理程序必须先校验这次投递并确认它，然后在后台执行排空队列的操作。一次会话运行的时间会超过 webhook 的投递超时，所以在 HTTP 处理程序内部排空队列会被中途切断，工作就一直留在队列里。

**Why traces show no tools.** In a self-hosted sandbox the API emits no tool spans, because it does not run the tools. The SDK environment worker (Python, TypeScript or Go) emits them in its own process, under one `anthropic.environment.work` span per work item, but only if a tracer provider is registered in the process that runs the worker and the sandbox can reach the tracing backend or collector.

> **为什么追踪中看不到工具。** 在自托管沙箱中，API 不会发出工具 span，因为工具不是它运行的。SDK 的环境 worker（Python、TypeScript 或 Go）会在它自己的进程中发出这些 span，每个工作项对应一个 `anthropic.environment.work` span，但前提是在运行 worker 的进程中注册了 tracer provider，并且沙箱能够访问追踪后端或采集器。

- Alert on queue depth, the age of the oldest item and workers polling equal to zero.
  > 对队列深度、最旧工作项的等待时长，以及轮询 worker 数为零的情况设置告警。
- Register tracing in the worker process and allow egress from the sandbox to the collector only.
  > 在 worker 进程中注册追踪，并且只允许从沙箱到采集器的出站流量。
- Track tool duration and errors per tool, so a slow merchant system shows up as a slow span, not as the agent thinking.
  > 按工具跟踪耗时和错误，这样一个缓慢的商家系统就会表现为一个缓慢的 span，而不是被误认为 Agent 在思考。

**Link the traces.** The API reads the `traceparent` header on the worker's Sessions API requests, so each SDK span contains the API span of its request. With tracing set up in the worker, one trace then shows the queue wait, the model's turn and each tool call in order.

> **把追踪串起来。** API 会读取 worker 发出的 Sessions API 请求中的 `traceparent` 请求头，所以每个 SDK span 都包含其对应请求的 API span。在 worker 中配置好追踪之后，一条追踪就能按顺序显示排队等待、模型的回合以及每一次工具调用。

**Trade-offs.** Webhook-driven wake saves running idle workers but adds a moving part; always-on pollers are simpler and react faster at the cost of idle capacity. Sending tool spans to your own backend keeps data inside the merchant's boundary, which is often a requirement for self-hosting in the first place, but means you run that backend.

> **取舍。** 用 webhook 唤醒可以省下空闲 worker 的运行成本，但会多一个可能出问题的环节；一直在线的轮询器更简单、响应更快，代价是闲置的资源。把工具 span 发送到你们自己的后端，可以让数据留在商家的边界之内，而这往往正是采用自托管的原因，但也意味着你们要自己运维这个后端。

</details>

## 5. Security review of a self-hosted agent sandbox: what Anthropic still sees, and what you now own

**自托管 Agent 沙箱的安全评审：Anthropic 仍然能看到什么，而你们现在要负责什么** · `Safety & Security` · `Senior`

### Question · 题目

An enterprise merchant agreed to the catalog agent only if tools run inside their own infrastructure, so the team moved it to a self-hosted environment. A security review before launch finds: the worker image runs as root with full network egress; the environment key is baked into the image; the same environment serves several merchants; web search and web fetch are still enabled; and the merchant's Shopify token was planned to go into a vault credential.

> 一个企业商家只有在工具运行于他们自己的基础设施内时才同意使用商品目录 Agent，于是团队把它迁移到了自托管环境。上线前的一次安全评审发现：worker 镜像以 root 身份运行，并且拥有完全的出站网络访问；环境 key 被打包进了镜像；同一个环境为多个商家提供服务；网页搜索和网页抓取仍然处于开启状态；而商家的 Shopify token 原计划放进 vault 凭证中。

Walk through the review: what moves to you, what does not, and how you fix each finding.

> 梳理这次评审：哪些责任转移给了你们，哪些没有，以及如何修复每一项发现。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Self-hosting moves tool execution, and therefore the blast radius of a compromised tool, into infrastructure you control. It does not move the agent loop, and it does not make the setup secure by itself: hardening, egress, keys and isolation become your job.

> **核心思路。** 自托管把工具的执行，以及一个被攻破的工具可能造成的影响范围，转移到了你们控制的基础设施中。它并没有转移 Agent 循环，也不会让这套部署自动变得安全：加固、出站控制、密钥和隔离，都变成了你们的工作。

**What stays and what moves.** The agent loop stays on Anthropic's orchestration layer, and tool inputs and outputs still flow to Anthropic's control plane so the model can see results. Bash, file operations and code run in your container, so filesystem contents and the sandbox's network egress stay in your environment. Web search and web fetch are the exception: they run on Anthropic's servers in both environment types.

> **哪些留下，哪些转移。** Agent 循环仍然留在 Anthropic 的编排层上，工具的输入和输出也仍然会流向 Anthropic 的控制面，这样模型才能看到结果。Bash、文件操作和代码运行在你们的容器中，所以文件系统中的内容和沙箱的出站网络流量都留在你们的环境内。网页搜索和网页抓取是例外：无论哪种环境类型，它们都运行在 Anthropic 的服务器上。

**The findings.**

> **评审发现。**

- **Root and open egress.** You own container hardening: run as non-root with a read-only root filesystem and dropped capabilities, and restrict egress to what the tools need, because there is no default restriction.
  > **root 用户与开放的出站网络。** 容器加固由你们负责：以非 root 用户运行，使用只读的根文件系统并移除多余的能力（capabilities），并把出站流量限制在工具真正需要的范围内，因为默认没有任何限制。
- **Environment key in the image.** The environment key gives access to one environment's work queue. Keep it in a secrets manager and rotate it on exposure; Anthropic cannot fast-revoke a leaked environment key for you. The per-session work secret goes only into the sandbox serving that session, never into images, shared volumes or logs.
  > **环境 key 被打包进镜像。** 环境 key 可以访问某一个环境的工作队列。把它保存在密钥管理系统中，并在暴露时轮换；Anthropic 无法替你们快速吊销一个泄漏的环境 key。每个会话的 work secret 只能放进服务于该会话的沙箱中，绝不能放进镜像、共享卷或日志里。
- **One environment for several merchants.** Use one workspace and environment per trust boundary when running untrusted code, so one merchant's session cannot reach another's files or credentials.
  > **多个商家共用一个环境。** 运行不可信代码时，每个信任边界使用一个工作区和一个环境，这样一个商家的会话就无法触及另一个商家的文件或凭证。
- **Web tools still on.** They bypass your egress controls entirely; disable them, or restrict them per tool with `allowed_domains` or `blocked_domains` in the agent toolset.
  > **网络工具仍然开启。** 它们会完全绕过你们的出站控制；要么关闭它们，要么在 Agent 工具集中按工具用 `allowed_domains` 或 `blocked_domains` 进行限制。
- **Shopify token in a vault.** Vault environment-variable credentials are not yet supported for self-hosted environments, because egress is yours and there is nowhere to substitute the secret. Use MCP credentials or a host-side custom tool that holds the token outside the sandbox.
  > **把 Shopify token 放进 vault。** 自托管环境目前还不支持 vault 的环境变量凭证，因为出站流量由你们控制，没有地方可以替换这个机密。改用 MCP 凭证，或者使用一个在沙箱之外持有 token 的主机端自定义工具。

**What Anthropic cannot do for you.** It cannot verify your image or supply chain, sandbox tool execution inside your container, or enforce retention once tool output reaches your infrastructure. So add image scanning and signing, least privilege for the tool process, and log retention and redaction policies of your own. Also tell the merchant plainly that tool inputs and outputs still pass through Anthropic's control plane: self-hosting keeps their files and network inside, not every byte the model reads.

> **Anthropic 无法替你们做的事。** 它无法验证你们的镜像或供应链，无法在你们的容器内部对工具执行进行沙箱隔离，也无法在工具输出进入你们的基础设施之后强制执行保留策略。所以要加上镜像扫描和签名、为工具进程设置最小权限，并制定你们自己的日志保留和脱敏策略。还要坦率地告诉商家，工具的输入和输出仍然会经过 Anthropic 的控制面：自托管让他们的文件和网络留在内部，但并不是模型读到的每一个字节都留在内部。

**Trade-offs.** Self-hosting satisfies data-location requirements for files and network access, at the cost of owning a security surface that the cloud sandbox handled for you. Per-merchant environments improve isolation but multiply workers and keys to manage. Be precise in promises to the merchant: overstating what stays inside is a bigger risk than the technical gaps.

> **取舍。** 自托管满足了文件和网络访问的数据位置要求，代价是你们要负责一块原本由云端沙箱替你们处理的安全面。按商家划分环境能提高隔离性，但会让需要管理的 worker 和密钥成倍增加。对商家的承诺要精确：夸大哪些东西留在内部，比技术上的缺口风险更大。

</details>
