## 1. A tagging pipeline forced its tool with tool_choice, and on the new model every request returns 400

**一个打标签流水线用 tool_choice 强制调用工具，换到新模型后每个请求都返回 400** · `Agent Loop` · `Hard`

### Question · 题目

A nightly job tags 200,000 products with Google product categories. Each request defines one tool, `tag_product`, and sets `tool_choice: {"type": "tool", "name": "tag_product"}` so the model always answers through the tool. A support agent uses `tool_choice: {"type": "any"}` on its first turn to make sure it looks up the order before replying. After switching both to Claude Opus 5.5, every request fails with `tool_choice: type "tool" and "any" are not supported for this model.` The token-counting step and the batch job fail too.

> 一个夜间任务为 200,000 个商品打上 Google 商品类目标签。每个请求只定义一个工具 `tag_product`，并设置 `tool_choice: {"type": "tool", "name": "tag_product"}`，让模型总是通过这个工具来回答。一个客服 Agent 在第一轮使用 `tool_choice: {"type": "any"}`，确保它在回复之前先查询订单。把两者都切换到 Claude Opus 5.5 之后，每个请求都以 `tool_choice: type "tool" and "any" are not supported for this model.` 失败。token 计数这一步和批处理任务也都失败了。

Explain the change and migrate both routes without losing what forcing gave you.

> 解释这项变化，并在不丢失“强制调用”所带来的保证的前提下迁移这两条路由。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Forcing a tool was always a way to get one of three things: structured data, schema-valid arguments, or a guaranteed action before the reply. On the newest models the forcing switch is gone, so you ask for each of those things directly instead.

> **核心思路。** 强制调用工具一直是为了得到以下三样东西之一：结构化数据、符合 schema 的参数，或者在回复之前一定会执行的动作。在最新的模型上，强制调用这个开关没有了，所以你要直接去争取这三样东西中的每一样。

**What changed.** On Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1, `tool_choice` of type `any` or `tool` returns a 400 `invalid_request_error`, on the Messages API, the Message Batches API and the token-counting endpoint alike. That is why all three steps broke at once. `{"type": "auto"}` (the default) and `{"type": "none"}` are unchanged. `disable_parallel_tool_use: true` still works with `auto`, but it now means at most one call, not exactly one.

> **发生了什么变化。** 在 Claude Opus 5.5、Claude Sonnet 5.5、Claude Fable 5.1 和 Claude Mythos 5.1 上，类型为 `any` 或 `tool` 的 `tool_choice` 会返回 400 `invalid_request_error`，Messages API、Message Batches API 和 token 计数接口都是如此。这就是三个步骤同时出错的原因。`{"type": "auto"}`（默认值）和 `{"type": "none"}` 没有变化。`disable_parallel_tool_use: true` 仍然可以和 `auto` 一起使用，但它现在的意思是“最多调用一次”，而不是“恰好调用一次”。

**Migrate by intent.**

> **按意图迁移。**

- **The tagging job only wanted JSON.** Replace the tool with structured outputs: `output_config.format` with a JSON schema. The answer comes back as text that matches the schema, with no tool round trip.
  > **打标签任务只是想要 JSON。** 用结构化输出替换这个工具：在 `output_config.format` 中提供一个 JSON schema。答案会以符合 schema 的文本形式返回，不需要经过一次工具调用的往返。
- **A tool must get valid arguments.** Keep `tool_choice` on `auto`, set `strict: true` on the tool definition with `additionalProperties: false` in its schema, and say in the prompt when the tool applies.
  > **工具必须拿到合法的参数。** 让 `tool_choice` 保持 `auto`，在工具定义上设置 `strict: true`，并在其 schema 中加上 `additionalProperties: false`，同时在提示中说明什么时候应该使用这个工具。
- **The application requires a call on this turn.** For the support agent, append a `role: "system"` message after the latest user turn that names `lookup_order`, says the call is required for this turn and tells the model to start its response with it. Keep that message in the history on later requests.
  > **应用要求本轮必须调用。** 对于客服 Agent，在最新的 user 轮次之后追加一条 `role: "system"` 消息，点名 `lookup_order`，说明本轮必须调用它，并让模型以这次调用开始它的回复。在后续请求中把这条消息保留在历史里。

```json
{"model": "claude-opus-5-5", "max_tokens": 16000,
 "output_config": {"format": {"type": "json_schema", "schema": {
   "type": "object", "additionalProperties": false,
   "required": ["product_id", "category"],
   "properties": {"product_id": {"type": "string"}, "category": {"type": "string"}}}}},
 "messages": [{"role": "user", "content": "Tag this product: ..."}]}
```

**Make the loop check, not assume.** Without forcing, a turn can end without the call you expected. Check `stop_reason` before reading content: on `refusal` do not run any tool from that turn, and on `max_tokens` retry with more room. If the support agent replies without calling `lookup_order`, your code notices the missing `tool_use` block, logs it as a policy miss and either asks again with the reminder or routes the conversation to a human. Measure how often this happens on real traffic; it should be rare once the prompt names the tool, but it must never be silent.

> **让循环去检查，而不是去假设。** 没有了强制调用，一轮对话可能在没有发生你预期的调用时就结束了。在读取内容之前先检查 `stop_reason`：如果是 `refusal`，就不要执行该轮中的任何工具；如果是 `max_tokens`，就给更多空间后重试。如果客服 Agent 没有调用 `lookup_order` 就回复了，你们的代码要发现缺少 `tool_use` 块，把它记录为一次违反规则，然后要么带着提醒再问一次，要么把对话转给人工。在真实流量上测量这种情况出现的频率；当提示里点名了工具之后，它应该很少见，但绝不能悄无声息。

**Test the batch path too.** Batches and token counting reject the same field, so a migration that only fixes the interactive path still fails at night. Search the codebase for every `tool_choice` with `any` or `tool`, including test fixtures and the request builder shared by the batch job, and fix them in one change.

> **也要测试批处理路径。** 批处理和 token 计数会拒绝同样的字段，所以只修复交互式路径的迁移，到了晚上仍然会失败。在代码库中搜索每一个类型为 `any` 或 `tool` 的 `tool_choice`，包括测试数据和批处理任务共用的请求构造器，并在一次改动中全部修复。

**Trade-offs.** Structured outputs are the cleanest fix for extraction, but a document with citations cannot use them in the same request, since the two are incompatible. Prompted tool use lets the model think first, which usually improves the arguments, but it moves the guarantee from the API into your loop, so you own the check. Keeping old routes on a model that still accepts forcing buys time, but the newest models are where this is going.

> **取舍。** 结构化输出是解决抽取问题最干净的方案，但带引用（citations）的文档不能在同一个请求中使用它，因为两者不兼容。通过提示引导的工具调用让模型可以先思考，这通常会改善参数质量，但它把保证从 API 挪到了你们的循环里，所以检查要由你们负责。把旧路由留在仍然接受强制调用的模型上可以争取时间，但最新的模型代表着方向。

</details>

## 2. The feed-writing tool streams faster now, but a cut-off CSV was written to a merchant's catalog

**写商品 feed 的工具现在流式输出更快了，但一份被截断的 CSV 被写进了商家的商品目录** · `Tools & MCP` · `Hard`

### Question · 题目

A catalog agent writes whole product feeds through a client tool `write_feed(path, contents)`, often tens of thousands of tokens. The chat UI used to sit silent for minutes while the model generated `contents`, so the team set `eager_input_streaming: true` on the tool. The UI now shows progress immediately. A week later a merchant's feed lost its last 3,000 rows: the tool ran with a `contents` value that stopped mid-line, and no error was logged.

> 一个商品目录 Agent 通过客户端工具 `write_feed(path, contents)` 写入完整的商品 feed，内容常常有几万个 token。以前在模型生成 `contents` 的那几分钟里，聊天界面一直没有动静，所以团队在这个工具上设置了 `eager_input_streaming: true`。现在界面会立即显示进度。一周后，某个商家的 feed 丢掉了最后 3,000 行：这个工具在 `contents` 停在某一行中间的情况下执行了，而且没有记录任何错误。

Explain what eager streaming changed and how to make the tool safe.

> 解释 eager 流式输出改变了什么，以及如何让这个工具变得安全。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** By default the API waits until each tool parameter is complete and valid before streaming it, which is safe but slow for large inputs. Eager streaming sends the parameter as it is written, which is fast, but it also hands you the job of checking that what arrived is complete and valid. The team took the speed and forgot the job.

> **核心思路。** 默认情况下，API 会等到每个工具参数完整且合法之后才把它流式发出，这样很安全，但对于大的输入来说很慢。eager 流式输出会边写边发送参数，这样很快，但同时也把“检查收到的内容是否完整且合法”这件事交给了你。团队拿到了速度，却忘了这份责任。

**Mechanism.** With buffering, a 20K-token parameter is a silent gap of minutes on the stream. With `eager_input_streaming: true`, fragments arrive as they are generated, and the API no longer validates or coerces the parameter. The accumulated JSON can be cut off at `max_tokens` in the middle of a parameter, or simply be invalid. The SDKs accumulate it with a tolerant partial-JSON parser, so a broken input often comes back as a silently truncated object rather than an exception. A truncated `contents` string parses fine; it is just shorter.

> **机制。** 在有缓冲的情况下，一个 20K token 的参数在流上就是几分钟的空白。设置 `eager_input_streaming: true` 后，片段会在生成时立即到达，而 API 不再校验或强制转换这个参数。累积起来的 JSON 可能在某个参数中途因为 `max_tokens` 而被截断，也可能本身就不合法。SDK 使用一个宽容的部分 JSON 解析器来累积它，所以有问题的输入经常会以一个被悄悄截断的对象返回，而不是抛出异常。被截断的 `contents` 字符串可以正常解析，只是变短了。

**The fix: check before you run.**

> **修复方法：执行之前先检查。**

- **Check `stop_reason` first.** If it is `max_tokens` and the turn has a `tool_use` block, the input is probably truncated: do not run the tool, retry with a higher `max_tokens`. If it is `refusal`, a tool input may be cut off too, so run none of that turn's tools.
  > **先检查 `stop_reason`。** 如果它是 `max_tokens` 且这一轮有 `tool_use` 块，输入很可能被截断了：不要执行工具，而是用更大的 `max_tokens` 重试。如果它是 `refusal`，工具输入也可能被截断，所以该轮的工具一个都不要执行。
- **Validate against the schema.** Parse strictly, reject unknown fields and check required ones. A typed tool helper does this for you; a raw JSON-schema tool or a manual loop must do it itself.
  > **按 schema 校验。** 严格地解析，拒绝未知字段并检查必填字段。带类型的工具辅助函数会替你完成这件事；原始 JSON schema 工具或手写循环则必须自己完成。
- **Return failures to the model.** If validation fails and you hold the `tool_use` block, do not run the tool; send a `tool_result` with `is_error: true` containing the bad input, built with a JSON library, so the model can try again.
  > **把失败返回给模型。** 如果校验失败而你手上有这个 `tool_use` 块，就不要执行工具；发送一个 `is_error: true` 的 `tool_result`，其中包含有问题的输入（用 JSON 库构造），让模型可以重试。

```go
// FeedInput is the schema of the write_feed tool.
type FeedInput struct {
	Path     string `json:"path"`
	Contents string `json:"contents"`
}

// parseFeedInput rejects input that is invalid, has unknown fields or misses required ones.
func parseFeedInput(raw []byte) (FeedInput, error) {
	var in FeedInput
	dec := json.NewDecoder(bytes.NewReader(raw))
	dec.DisallowUnknownFields()
	if err := dec.Decode(&in); err != nil {
		return in, err
	}
	if in.Path == "" || in.Contents == "" {
		return in, errors.New("path and contents are required")
	}
	return in, nil
}
```

**Validate the content, not only the JSON.** A schema check proves the JSON is well formed, not that the feed is complete. For a write that replaces merchant data, add domain checks: the CSV parses, every row has the expected columns, and the row count is within a sane range of the current feed. Write to a temporary file and swap it in only when the checks pass, so a bad write never reaches the live catalog.

> **不仅要校验 JSON，还要校验内容。** schema 检查只能证明 JSON 格式正确，不能证明 feed 是完整的。对于会替换商家数据的写操作，要加上业务层面的检查：CSV 能够解析，每一行都有预期的列，行数与当前 feed 相比处在合理的范围内。先写入一个临时文件，只有在检查通过后才替换上去，这样一次错误的写入永远不会进入线上的商品目录。

**Where to leave it off.** Eager streaming is only meaningful on streamed requests with client tools. It is not a valid field on server tools such as web search, code execution or an MCP toolset, it is ignored on non-streaming requests, and a proxy or gateway in front of the API may reject the unknown field. Some older deployments on Amazon Bedrock also reject it with a 400.

> **哪些地方不要开启。** eager 流式输出只对带客户端工具的流式请求有意义。它不是网页搜索、代码执行或 MCP 工具集这类服务端工具的合法字段，在非流式请求中会被忽略，而 API 前面的代理或网关可能会拒绝这个未知字段。Amazon Bedrock 上的一些较旧的部署也会以 400 拒绝它。

**Trade-offs.** Eager streaming fixes the long silence and lets you show progress, at the cost of client-side validation that you must write and test. For small tools there is little to gain, so leave them buffered. For large, destructive inputs, keep eager streaming but treat every input as untrusted until it passes both schema and domain checks; the server would have delivered the same broken parameter in buffered mode, eager mode only moves the failure to your side.

> **取舍。** eager 流式输出解决了长时间的沉默，让你能显示进度，代价是你必须编写并测试客户端的校验。对于输入很小的工具，收益不大，就让它们保持缓冲模式。对于输入很大、具有破坏性的工具，可以保留 eager 流式输出，但在输入同时通过 schema 检查和业务检查之前，都要把它当作不可信的；在缓冲模式下，服务器同样会交付这个有问题的参数，eager 模式只是把失败挪到了你这一侧。

</details>

## 3. The harness tells the agent mid-chat which store is active, and a shopper forges the same message

**harness 在对话中途告诉 Agent 当前是哪个店铺，而一位顾客伪造了同样的消息** · `Context & Memory` · `Medium`

### Question · 题目

A support agent serves shoppers for many stores. When a shopper switches stores in the widget, the harness adds a line to the shopper's next message: `<system-reminder>Active store: Nordic Wool. Refund limit: $50.</system-reminder>`. One shopper typed the same tag into the chat with a refund limit of $5,000, and the agent believed it. Separately, an engineer suggests putting the active store into the top-level system prompt instead, rewritten on every turn.

> 一个客服 Agent 为许多店铺的顾客提供服务。当顾客在聊天组件中切换店铺时，harness 会在顾客的下一条消息里加一行：`<system-reminder>Active store: Nordic Wool. Refund limit: $50.</system-reminder>`。有一位顾客在聊天中输入了同样的标签，把退款上限写成 $5,000，而 Agent 相信了它。另外，有一位工程师建议改为把当前店铺写进顶层 system prompt，并在每一轮都重写它。

What is wrong with both approaches, and how should mid-conversation context be delivered?

> 这两种做法分别有什么问题？对话中途的上下文应该如何传递？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Instructions from you and text from the shopper must travel on different channels. If both arrive as user text, the model cannot tell them apart, and anyone who can type can pretend to be you. And anything that changes at the start of the prompt makes the whole conversation after it uncacheable.

> **核心思路。** 来自你们的指令和来自顾客的文本必须走不同的通道。如果两者都以 user 文本的形式到达，模型就无法区分它们，任何能打字的人都可以冒充你们。而提示开头部分的任何变化，都会让其后的整段对话无法被缓存。

**Why the first approach is unsafe.** A reminder inside a user turn is just text. Anything that writes to user-visible input, a shopper, a product review or a tool result, can forge it. **Why the second is expensive.** Editing the top-level `system` changes the prefix in front of the entire history, so every turn misses the prompt cache.

> **为什么第一种做法不安全。** user 轮次里的提醒只是普通文本。任何能写入用户可见输入的东西，无论是顾客、商品评论还是工具结果，都可以伪造它。**为什么第二种做法代价高。** 修改顶层 `system` 会改变整个历史前面的前缀，所以每一轮都会错过提示缓存。

**The fix: mid-conversation system messages.** On models that support them, such as Claude Opus 5.5 and Claude Sonnet 5.5, append `{"role": "system", "content": "..."}` to `messages` when the store changes. The top-level system prompt stays byte-identical, so the cached prefix survives, and `role: "system"` is a channel the shopper cannot forge.

> **修复方法：对话中途的 system 消息。** 在支持它的模型上，例如 Claude Opus 5.5 和 Claude Sonnet 5.5，当店铺发生变化时，向 `messages` 追加 `{"role": "system", "content": "..."}`。顶层 system prompt 保持逐字节不变，所以缓存的前缀得以保留，而 `role: "system"` 是顾客无法伪造的通道。

```json
"messages": [
  ...history,
  {"role": "user", "content": "I'd like to return my sweater."},
  {"role": "system", "content": "Active store: Nordic Wool. Refund limit: $50."}
]
```

- **Placement rules.** It must follow a user message (or an assistant message ending in server-tool use), and be the last entry or be followed by an assistant turn. It cannot be the first message, and its content is text only.
  > **位置规则。** 它必须跟在一条 user 消息之后（或一条以服务端工具调用结束的 assistant 消息之后），并且要么是最后一条，要么后面紧跟一个 assistant 轮次。它不能是第一条消息，内容只能是文本。
- **Per-turn reminders.** For something true for one turn only, give the message `clear_at: "next_user_message"` (a beta). It renders for one turn and then stays in the history cleared, costing no input tokens.
  > **只在一轮内有效的提醒。** 对于只在一轮内成立的内容，给这条消息加上 `clear_at: "next_user_message"`（beta 功能）。它会生效一轮，然后以已清除的状态留在历史中，不消耗输入 token。
- **Never delete earlier copies.** Removing a reminder you sent before is a history edit: the cache misses from that point, and on the newest models every later thinking block is invalidated. Keep old messages and append new ones.
  > **绝不删除之前的副本。** 删除你之前发送过的提醒属于修改历史：缓存会从那个位置开始失效，而且在最新的模型上，之后的每一个思考块都会失效。保留旧消息，追加新消息。
- **Fallback.** On a model without support, the request returns a 400 saying the system role is not supported; catch it and fall back to the user-turn reminder, with the extra defences below.
  > **降级方案。** 在不支持它的模型上，请求会返回 400，提示不支持 system 角色；捕获这个错误，退回到 user 轮次中的提醒，并配合下面的额外防线。

**Do not rely on the prompt for limits.** A refund limit is a business rule, so the refund tool enforces it on the server with the real store's configuration, whatever the conversation says. Strip or escape anything resembling your reminder tags from shopper input, and log attempts, which are a useful abuse signal.

> **不要依赖提示来执行限额。** 退款上限是业务规则，所以无论对话里说了什么，退款工具都要在服务端根据真实店铺的配置来执行它。从顾客输入中去掉或转义任何类似你们提醒标签的内容，并记录这些尝试，它们是很有用的滥用信号。

**Trade-offs.** Mid-conversation system messages keep the cache and the trust boundary, but not every model supports them, so the harness needs a tested fallback. Appending messages makes the history longer than rewriting it, but the cost of an extra line is small compared with re-processing the whole conversation every turn.

> **取舍。** 对话中途的 system 消息既保留了缓存，也守住了信任边界，但并不是每个模型都支持它，所以 harness 需要一个经过测试的降级方案。追加消息会让历史比重写时更长，但与每一轮都重新处理整段对话相比，多一行的成本很小。

</details>

## 4. After an SDK upgrade, the answer-checking step of the policy assistant fails with a 400

**SDK 升级之后，政策助手的答案校验步骤以 400 失败** · `RAG` · `Medium`

### Question · 题目

A policy assistant answers merchants from ad-policy documents with citations enabled. A second step then asks the model to check the answer: the code copies the first response's content blocks into a new user message, "Check this answer against the sources". After upgrading the SDK to a release that sends API version `2026-10-21`, the checking step fails with a 400, while the answering step still works.

> 一个政策助手在开启引用（citations）的情况下，根据广告政策文档回答商家的问题。随后的第二步会让模型检查这个答案：代码把第一次响应的内容块复制到一条新的 user 消息中，“请根据来源检查这个答案”。把 SDK 升级到发送 API 版本 `2026-10-21` 的版本之后，检查步骤以 400 失败，而回答步骤仍然正常。

What broke, and how should the pipeline pass cited answers between steps?

> 什么出了问题？流水线应该如何在步骤之间传递带引用的答案？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Citations are the model's claims about where its words came from, so they belong to the assistant side of a conversation. On the new API version you may not hand them back to the model as if the user had written them. Keep the text, keep the citation data in your own system, and pass the sources explicitly.

> **核心思路。** 引用是模型对“自己的话出自哪里”的声明，所以它们属于对话中 assistant 的一侧。在新的 API 版本上，你不能把它们当作用户写的内容交还给模型。保留文本，把引用数据保存在你们自己的系统里，并显式地传递来源。

**What broke.** On API version `2026-10-21`, a request containing a `text` block with a non-empty `citations` array in a `user` message returns a 400. This applies whether the block sits directly in the message or inside a `search_result` block, including one inside a `tool_result`, and also to token counting and Message Batches. Copying the answer blocks into a user turn is exactly that. The answering step still works because citations on assistant messages sent back unchanged, and the `"citations": {"enabled": true}` setting on `document` and `search_result` blocks, are still accepted.

> **什么出了问题。** 在 API 版本 `2026-10-21` 上，如果请求的 `user` 消息中包含一个带有非空 `citations` 数组的 `text` 块，就会返回 400。无论这个块直接位于消息中，还是位于 `search_result` 块中（包括 `tool_result` 里的 `search_result`），都是如此，token 计数和 Message Batches 也一样。把答案块复制到 user 轮次里恰好就是这种情况。回答步骤仍然正常，是因为原样回传的 assistant 消息中的引用，以及 `document` 和 `search_result` 块上的 `"citations": {"enabled": true}` 设置，仍然是被接受的。

**The fix.**

> **修复方法。**

- **Send text, not cited blocks.** Before putting an answer into a user turn, remove `citations` from its text blocks and keep the text.
  > **发送文本，而不是带引用的块。** 在把答案放进 user 轮次之前，从它的文本块中删除 `citations`，保留文本。
- **Give the checker the evidence explicitly.** Store each citation's `cited_text` and document index in your own records, and give the checker the answer text plus the source passages as documents, so it checks claims against sources rather than trusting the answer's own references.
  > **显式地把证据交给检查器。** 把每条引用的 `cited_text` 和文档索引保存在你们自己的记录中，然后把答案文本连同来源段落（以文档形式）一起交给检查器，这样它是对照来源去核对声明，而不是相信答案自带的引用。
- **Fix it at the source.** Find every place that copies response content into a user message, including `search_result` and `tool_result` builders, and route them through one helper.
  > **从源头修复。** 找出所有把响应内容复制进 user 消息的地方，包括构造 `search_result` 和 `tool_result` 的代码，让它们都经过同一个辅助函数。

```go
// stripCitations removes citations from text blocks before Claude's answer is
// placed in a user turn; the text is kept.
func stripCitations(blocks []map[string]any) []map[string]any {
	out := make([]map[string]any, 0, len(blocks))
	for _, b := range blocks {
		c := make(map[string]any, len(b))
		for k, v := range b {
			if k != "citations" {
				c[k] = v
			}
		}
		out = append(out, c)
	}
	return out
}
```

**Ship it safely.** This fix also works on the old version `2023-06-01`, so deploy it before the SDK upgrade. The same version also removes sampling parameters and rejects a `document` block directly in an assistant message, so search for those in the same change and run the pipeline's tests against the new version before switching.

> **安全地上线。** 这个修复在旧版本 `2023-06-01` 上同样有效，所以要在 SDK 升级之前部署它。同一个版本还移除了采样参数，并拒绝直接放在 assistant 消息中的 `document` 块，所以要在同一次改动中把这些也搜索出来，并在切换之前用新版本跑一遍流水线的测试。

**Trade-offs.** Stripping citations loses the inline link between a sentence and its source in the checker's input, which is why you store the citation data yourself and pass the sources as documents. That costs a few more input tokens per check, but the checker then works from evidence rather than from the answer's own claims about its evidence, which is what a check should do anyway.

> **取舍。** 去掉引用后，检查器的输入中就失去了句子与其来源之间的内联关联，所以你要自己保存引用数据，并把来源作为文档传入。这会让每次检查多消耗一些输入 token，但检查器从此依据的是证据本身，而不是答案对其证据的自我声明，这本来就是检查应该做的事。

</details>

## 5. The nightly policy audit says "all clear" for 1,200 merchants, but 300 of them were never checked

**夜间政策审计对 1,200 个商家报告“全部合规”，但其中 300 个从未被检查过** · `Multi-agent` · `Senior`

### Question · 题目

Every night a lead agent on Claude Managed Agents audits merchants' ad copy for policy problems. It starts a dynamic workflow run that gives each merchant to an agent and combines the findings. The morning report said "no violations found" for 1,200 merchants. A spot check showed that about 300 merchants had no audit at all: some agents failed, some never started, and the summary treated missing results as clean.

> 每天夜里，Claude Managed Agents 上的一个主 Agent 都会审计商家的广告文案是否存在政策问题。它启动一个动态工作流运行（workflow run），把每个商家分配给一个 Agent，再汇总结果。早上的报告对 1,200 个商家都写着“未发现违规”。抽查发现，大约 300 个商家根本没有被审计：有些 Agent 失败了，有些从未启动，而汇总把缺失的结果当成了合规。

Redesign the audit so that "clean" means checked, and explain the limits you must design around.

> 重新设计这次审计，让“合规”真正意味着“已检查”，并说明你在设计时必须考虑的限制。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** In a fan-out, silence is not success. An audit must know the full list of items before it starts, account for every item at the end, and report three states: checked and clean, checked with findings, and not covered. A run that finished is not a run that passed.

> **核心思路。** 在扇出（fan-out）中，沉默并不等于成功。审计必须在开始之前就知道完整的条目清单，在结束时对每一个条目都有交代，并报告三种状态：已检查且合规、已检查且有问题、未覆盖。一次运行结束了，并不代表它通过了。

**Why it happened.** A workflow run's `result.type` of `completed` means the workflow finished, not that the work passed. One agent failing can fail the whole run unless the workflow is told otherwise, and the server has limits: about 64 threads working at once in a run today, around 1,000 threads over a run's life (a run that goes over ends with `thread_limit_error`), a run lifetime of 24 hours by default, and 10 open runs per session by default. A design that starts one agent per merchant, plus a reviewer each, can hit the thread limit, and anything the summary does not explicitly count disappears.

> **为什么会这样。** 工作流运行的 `result.type` 为 `completed`，表示工作流跑完了，而不是工作通过了。除非工作流另有安排，否则一个 Agent 失败就可能让整次运行失败；而且服务端有限制：目前一次运行中同时工作的线程大约是 64 个，一次运行的整个生命周期内大约 1,000 个线程（超出的运行会以 `thread_limit_error` 结束），运行的生命周期默认是 24 小时，每个会话默认最多同时打开 10 个运行。一个“每个商家一个 Agent、再各配一个审核者”的设计可能会触及线程上限，而汇总中没有被明确计数的东西就会消失。

**Redesign.**

> **重新设计。**

- **The list comes first.** The lead agent receives the merchant list from your system and must return a status for every ID on it. Your code, not the model, compares that list with the results.
  > **先有清单。** 主 Agent 从你们的系统接收商家清单，并且必须为清单上的每一个 ID 返回状态。由你们的代码而不是模型，把这份清单与结果进行比对。
- **Prompt the workflow for failure and review.** In the agent's system prompt: one agent failing must not fail the run, and a merchant whose agent failed is listed as not covered; a second agent reviews every merchant, not only the flagged ones; give the run a time limit a few times longer than the work should take.
  > **在提示中要求工作流处理失败和复核。** 在 Agent 的 system prompt 中写明：一个 Agent 失败不能导致整次运行失败，其 Agent 失败的商家要列为未覆盖；由第二个 Agent 复核每一个商家，而不仅仅是被标记的那些；为运行设定一个比预期工作时长长几倍的时间限制。
- **Batch items to fit the limits.** With a reviewer per item, each agent should take several merchants, so the run stays well under the thread limit.
  > **把条目分批以适应限制。** 每个条目都有一个复核者时，每个 Agent 应该负责多个商家，这样运行就能远低于线程上限。
- **Handle run outcomes.** Switch on `result.type` first; on `error`, read `result.error.type`, and re-queue every merchant without a result for the next run rather than marking it clean.
  > **处理运行结果。** 首先根据 `result.type` 分支；如果是 `error`，就读取 `result.error.type`，并把所有没有结果的商家重新排入下一次运行，而不是把它们标记为合规。
- **Cap the spend.** Every agent in a run uses tokens, so give the session a budget. A session at its budget pauses with `stop_reason: budget_reached` instead of terminating, and raising the budget resumes it.
  > **限制花费。** 运行中的每个 Agent 都会消耗 token，所以要给会话设定预算。达到预算的会话会以 `stop_reason: budget_reached` 暂停，而不是终止，提高预算后它会继续运行。

```go
// Status is what the audit records for one merchant.
type Status string

const (
	Checked    Status = "checked"
	Failed     Status = "failed"
	NotCovered Status = "not_covered"
)

// coverage compares the merchants that should have been audited with the
// results that came back; anything without a result is not covered.
func coverage(expected []string, results map[string]Status) map[Status][]string {
	out := map[Status][]string{}
	for _, m := range expected {
		s, ok := results[m]
		if !ok {
			s = NotCovered
		}
		out[s] = append(out[s], m)
	}
	return out
}
```

**Report honestly.** The morning report leads with coverage, for example "900 checked, 12 with findings, 300 not covered and re-queued", and alerts when coverage drops below a threshold. Not covered merchants keep their previous status with its date, never a fresh "clean". Track coverage and review disagreement rates over time: a reviewer that never disagrees is probably not reviewing.

> **如实报告。** 早上的报告首先给出覆盖情况，例如“900 个已检查，12 个有问题，300 个未覆盖并已重新排队”，并在覆盖率低于阈值时告警。未覆盖的商家保留它们之前的状态及其日期，绝不能给出一个新的“合规”。持续跟踪覆盖率和复核分歧率：一个从不提出异议的复核者，很可能根本没在复核。

**Trade-offs.** Reviewing every merchant adds about one more agent per item, roughly doubling the cost of the audit, and batching several merchants per agent makes one failure affect more merchants. For a policy audit, where a miss can get a merchant's ads disapproved, that cost is usually justified; for a cheap, low-stakes scan, skip the second look and say so in the report.

> **取舍。** 复核每一个商家，相当于每个条目大约多出一个 Agent，审计成本大约翻倍；而让每个 Agent 负责多个商家，会让一次失败影响更多商家。对于政策审计来说，一次遗漏就可能导致商家的广告被拒登，这样的成本通常是值得的；而对于便宜、低风险的扫描，可以省去第二次复核，并在报告中注明这一点。

</details>
