## 1. The help-center assistant's eval stayed at 91% for a week while its retrieval was broken

**帮助中心助手的检索坏了整整一周，评测分数却一直停在 91%** · `RAG` · `Medium`

### Question · 题目

A RAG assistant answers merchants' questions about the platform, such as shipping rules, payout schedules and how to link an ad account, from help-center articles. A 200-case eval runs on every change. A configuration bug disconnected the retrieval tool for a week. The eval still scored 91%, and nobody noticed until merchants complained that the assistant quoted old payout dates.

> 一个 RAG 助手根据帮助中心的文章回答商家关于平台的问题，比如配送规则、结算周期，以及如何绑定广告账号。每次改动都会跑一遍 200 个用例的评测。一次配置错误让检索工具断开了整整一周。评测分数仍然是 91%，直到商家投诉助手报出了过时的结算日期，才有人发现。

How can an eval miss this? Redesign it.

> 评测怎么会漏掉这种问题？请重新设计它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** An eval for a retrieval system must fail when retrieval fails. If it does not, it is measuring what the model already knows, not whether the system finds and uses the right document.

> **核心思想。** 检索系统的评测，必须在检索失效时失败。如果它没有失败，那它衡量的是模型本来就知道的东西，而不是系统能否找到并使用正确的文档。

**Why the score did not move.** Many cases were answerable from memory: general questions such as what a chargeback is, or facts that are public anyway. The model answered them without any document. The grader made it worse by checking whether the answer looked right, not whether it rested on a retrieved article. And the gold answers for payout dates were never re-checked after the articles changed, so stale answers still matched stale keys.

> **为什么分数没有变化。** 很多用例靠记忆就能回答：比如什么是拒付这类通用问题，或者本来就公开的事实。模型不需要任何文档就能答出来。评分器又让情况更糟：它只检查答案看起来对不对，而不检查答案是否基于检索到的文章。而且结算日期的标准答案在文章更新之后从未重新核对过，所以过时的答案仍然能对上过时的答案键。

**Prove the mechanism is wired.** Run the eval once with retrieval switched off. The score must drop sharply. Report the drop as the retrieval lift, and list the cases that are still correct without retrieval: rewrite them or tag them as general knowledge.

> **证明检索机制确实接上了。** 关闭检索再跑一遍评测，分数必须明显下降。把这个下降幅度作为检索带来的提升报告出来，并列出关闭检索后仍然答对的用例：要么重写它们，要么把它们标记为通用知识。

```go
type Result struct {
	Correct  bool
	Grounded bool // the cited article supports the answer
}

// Run every case twice: retrieval on, and retrieval switched off.
// Cases still correct without retrieval are measuring memory, not RAG.
func retrievalLift(on, off map[string]Result) (lift float64, fromMemory []string) {
	var onOK, offOK int
	for id, r := range on {
		if r.Correct && r.Grounded {
			onOK++
		}
		if off[id].Correct {
			offOK++
			fromMemory = append(fromMemory, id)
		}
	}
	n := float64(len(on))
	return float64(onOK)/n - float64(offOK)/n, fromMemory
}
```

**Cases that need the documents.** Ask about values only your help center holds, such as your own fee tiers, cut-off times and recently changed articles. Tie each gold answer to the article version it came from, and re-verify it when that article changes.

> **需要文档才能回答的用例。** 问那些只有你们帮助中心才有的值，比如你们自己的费率档位、截止时间，以及最近改过的文章。把每个标准答案和它所依据的文章版本绑定，文章一变就重新核对。

**Test both directions.** Add questions the help center does not answer. The right behavior is to say so, not to invent an answer; without these cases, a system that always answers scores perfectly. Keep "no answer" separate from a real negative answer: "the help center does not cover this" is an answer, while an empty, crashed or cut-off response is an error, not a score.

> **从两个方向测试。** 加入帮助中心无法回答的问题。正确的行为是如实说明，而不是编造答案；没有这些用例，一个永远都给出答案的系统也能拿满分。把「没有答案」和真正的否定回答区分开：「帮助中心没有涉及这个问题」是一个回答，而空响应、崩溃或被截断的响应是错误，不应计入分数。

**Grade grounding.** Require the answer to cite the article it used, and check that the cited passage supports the claim. A correct-looking answer with no supporting source fails.

> **对依据进行评分。** 要求答案引用它所使用的文章，并检查被引用的段落是否支撑这个说法。看起来正确却没有支撑来源的答案判为失败。

**Watch production as well.** Count retrieval calls per conversation and alert when they fall to zero. That alert would have caught this bug on day one, eval or not.

> **同时监控生产环境。** 统计每个对话中的检索调用次数，降到零时就告警。不管有没有评测，这个告警都能在第一天就发现这个 bug。

**Trade-offs.** The retrieval-off run doubles eval cost, so run it on each release rather than on every commit. Platform-specific and synthetic cases are less like real traffic, so keep a slice sampled from real questions next to them.

> **权衡。** 关闭检索的那次运行会让评测成本翻倍，所以在每次发布时跑一次，而不是每次提交都跑。平台特有的用例和合成用例不太像真实流量，所以旁边还要保留一部分从真实问题中抽样的用例。

</details>

## 2. Auditors want the ad-review agent to show its reasoning, and after the move to Claude Opus 5.5 some reviews come back as refusals

**审计人员希望广告审核 agent 展示它的推理过程，而在迁移到 Claude Opus 5.5 之后，部分审核以拒答告终** · `Safety & Security` · `Medium`

### Question · 题目

Before ads go to the platforms, a review step checks the merchant's ad copy against the ad policies. For the audit trail, the prompt says "Before your decision, write out your complete step-by-step reasoning", and the JSON output has a `reasoning` field. After the move to Claude Opus 5.5, some requests return HTTP 200 with `stop_reason: "refusal"` and `stop_details.category: "reasoning_extraction"`. The code reads the first content block and crashes. Server-side fallbacks are enabled, but they do not help.

> 广告提交到各平台之前，有一个审核步骤会依据广告政策检查商家的广告文案。为了留下审计记录，提示词写着「在给出结论之前，写出你完整的逐步推理过程」，而 JSON 输出里有一个 `reasoning` 字段。迁移到 Claude Opus 5.5 之后，一部分请求返回 HTTP 200，`stop_reason: "refusal"`，`stop_details.category: "reasoning_extraction"`。代码读取第一个内容块时就崩溃了。服务端回退已经开启，却没有帮上忙。

Explain what happens and redesign the audit trail.

> 解释发生了什么，并重新设计审计记录。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** On newer models the model's reasoning lives in thinking blocks. A prompt that asks it to reproduce that internal reasoning in the answer text may be declined. Read the reasoning from summarized thinking blocks, and ask the answer only for a short explanation.

> **核心思想。** 在较新的模型上，模型的推理存在于思考块里。要求模型在答案文本中复现其内部推理的提示，可能会被拒绝。应当从摘要形式的思考块中读取推理，而在答案里只要求一段简短的解释。

**What happens.** Claude Opus 5.5, like Claude Opus 5, the Claude Fable models and Claude Sonnet 5.5, runs a classifier for reasoning extraction. A decline is a normal HTTP 200 with `stop_reason: "refusal"` and a `stop_details` category, so check `stop_reason` before reading `content`. Fallbacks do not help here: a category with no recommended fallback, such as `reasoning_extraction`, comes back as a refusal. A refusal before any output still counts against your rate limits.

> **发生了什么。** Claude Opus 5.5 和 Claude Opus 5、Claude Fable 系列以及 Claude Sonnet 5.5 一样，会运行一个针对推理提取的分类器。一次拒绝是一个普通的 HTTP 200，带有 `stop_reason: "refusal"` 和一个 `stop_details` 类别，所以在读取 `content` 之前要先检查 `stop_reason`。回退在这里帮不上忙：没有推荐回退模型的类别（比如 `reasoning_extraction`）会直接以拒绝返回。在产生任何输出之前的拒绝，仍然会计入你的速率限制。

**The redesign.**

> **重新设计。**

- Remove the "write out your complete reasoning" line and the `reasoning` field from the output format. Both are written-for-older-models patterns that a prompt audit should catch.
  > 删掉「写出你完整的推理过程」那句话，以及输出格式中的 `reasoning` 字段。两者都是为旧模型写的模式，提示词审计应当把它们找出来。
- Ask for the decision plus a short explanation that names the policy clause and the words in the ad that trigger it. A short explanation of the answer is still allowed.
  > 要求给出结论，外加一段简短的解释，说明所依据的政策条款以及广告中触发它的词语。对答案作简短解释仍然是允许的。
- Set `display: "summarized"` on adaptive thinking and store the summary with each decision for the auditors. The raw chain of thought is never returned on any model; `display` controls only what you see, and thinking is billed the same either way.
  > 在自适应思考上设置 `display: "summarized"`，并把摘要和每个结论一起保存下来供审计人员查看。任何模型都不会返回原始的思维链；`display` 只控制你能看到什么，无论怎样设置，思考的计费都一样。
- Treat a refusal as its own outcome: send the ad to a human review queue, and never auto-approve it.
  > 把拒绝当作一种独立的结果：把这条广告送进人工审核队列，绝不能自动通过。

```go
type Review struct {
	Status   string // "decided" or "refused"
	Category string
	Answer   string // decision plus a short explanation
	Summary  string // summarized thinking, stored for auditors
}

func reviewAd(ctx context.Context, client anthropic.Client, ad string) (Review, error) {
	adaptive := anthropic.ThinkingConfigAdaptiveParam{Display: anthropic.ThinkingConfigAdaptiveDisplaySummarized}
	resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
		Model:     "claude-opus-5-5",
		MaxTokens: 4096,
		Thinking:  anthropic.ThinkingConfigParamUnion{OfAdaptive: &adaptive},
		System: []anthropic.TextBlockParam{{Text: "Decide whether the ad meets the policy. " +
			"Give the decision and a one- or two-sentence explanation naming the policy clause."}},
		Messages: []anthropic.MessageParam{anthropic.NewUserMessage(anthropic.NewTextBlock(ad))},
	})
	if err != nil {
		return Review{}, err
	}
	if resp.StopReason == anthropic.StopReasonRefusal { // check before reading content
		return Review{Status: "refused", Category: string(resp.StopDetails.Category)}, nil
	}
	r := Review{Status: "decided"}
	for _, b := range resp.Content {
		switch v := b.AsAny().(type) {
		case anthropic.ThinkingBlock:
			r.Summary += v.Thinking
		case anthropic.TextBlock:
			r.Answer += v.Text
		}
	}
	return r, nil
}
```

**Trade-offs.** A summary is not the full reasoning, so tell the auditors what they are reading. The short explanation in the answer is what a merchant can see, and the summary is what the audit keeps. Both may contain merchant data, so give them the same retention rules as the ads themselves.

> **权衡。** 摘要并不是完整的推理，所以要告诉审计人员他们看到的是什么。答案里的简短解释是商家能看到的内容，而摘要是审计保留的内容。两者都可能包含商家数据，所以要对它们应用和广告本身相同的保留规则。

</details>

## 3. On Managed Agents, one MCP server suddenly runs unauthenticated, and another stops working an hour into each session

**在 Managed Agents 上，一个 MCP 服务器突然在未认证状态下运行，另一个则在每个会话进行到一小时左右时失效** · `Tools & MCP` · `Hard`

### Question · 题目

A campaign agent on Managed Agents connects to two MCP servers: the company's own catalog server and a partner's ads server that uses OAuth. Credentials live in vaults, one vault per merchant. Recent incidents:

> Managed Agents 上的一个广告投放 agent 连接两个 MCP 服务器：公司自己的商品目录服务器，以及一个使用 OAuth 的合作方广告服务器。凭据存放在 vault 中，每个商家一个 vault。最近发生了这些事故：

- The catalog team moved its server from `https://mcp.catalog.example.com/mcp` to `.../mcp/v2`. Since then the catalog tools fail with authentication errors, although the vault credential is still there.
  > 商品目录团队把服务器从 `https://mcp.catalog.example.com/mcp` 迁到了 `.../mcp/v2`。从那以后，目录工具都以认证错误失败，尽管 vault 里的凭据还在。
- Long sessions lose the ads server about an hour in.
  > 长会话在进行到一小时左右时，就会失去广告服务器的连接。
- Adding a second credential for the catalog server to a merchant's vault returns 409.
  > 往某个商家的 vault 里为目录服务器再添加一个凭据，返回 409。
- Someone proposes putting the catalog bearer token in the system prompt "just for now".
  > 有人提议「暂时」把目录服务器的 bearer token 放进系统提示词里。

Explain each problem and design the credential setup.

> 解释每个问题，并设计凭据的配置方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** On Managed Agents, MCP servers are authenticated only through vault credentials, and a credential is matched by the server's URL. The match decides whether a token is sent at all; the refresh settings decide how long it keeps working.

> **核心思想。** 在 Managed Agents 上，MCP 服务器只能通过 vault 凭据认证，而凭据是按服务器 URL 匹配的。是否匹配决定了到底会不会发送令牌；刷新设置决定了令牌能用多久。

**Why the catalog runs unauthenticated.** MCP credentials are keyed by `mcp_server_url`. The match is normalized, not byte-exact: scheme and host are lowercased, and default ports and trailing slashes are stripped. A different path, subdomain or non-default port does not match, and when nothing matches the connection is attempted without authentication. That is why you see the server's own auth error, not a vault error. The `/mcp/v2` move changed the path. Keys are immutable, so archive the old credential and create a new one for the new URL; archiving purges the secret and frees the key.

> **为什么目录服务器在未认证状态下运行。** MCP 凭据以 `mcp_server_url` 为键。匹配是规范化后的，而不是逐字节比较：scheme 和 host 会转成小写，默认端口和末尾的斜杠会被去掉。不同的路径、子域名或非默认端口都无法匹配，而在没有任何匹配时，连接会在没有认证的情况下尝试建立。这就是为什么你看到的是服务器自己的认证错误，而不是 vault 错误。迁到 `/mcp/v2` 改变了路径。键是不可变的，所以要归档旧凭据，再为新 URL 创建一个新凭据；归档会清除密钥并释放这个键。

**Why the ads server dies after an hour.** An `mcp_oauth` credential is refreshed automatically through the OAuth `refresh_token` grant, but only when it has a `refresh` block with the `token_endpoint`, `client_id` and `token_endpoint_auth`. Without that block the access token works until it expires, and then the agent loses access. Use `none` for a public client, and `client_secret_basic` or `client_secret_post` for a confidential one, as the partner's token endpoint expects.

> **为什么广告服务器一小时后就失效。** `mcp_oauth` 凭据会通过 OAuth 的 `refresh_token` 授权自动刷新，但前提是它带有一个包含 `token_endpoint`、`client_id` 和 `token_endpoint_auth` 的 `refresh` 块。没有这个块，访问令牌只能用到过期为止，之后 agent 就失去了访问权限。对公开客户端使用 `none`，对机密客户端则按合作方令牌端点的要求，使用 `client_secret_basic` 或 `client_secret_post`。

**Why 409.** `mcp_server_url` must be unique among the active credentials in a vault, and a vault holds at most 20 credentials. One vault per merchant is the right shape; `vault_ids` can be set only when a session is created.

> **为什么返回 409。** 在一个 vault 的有效凭据中，`mcp_server_url` 必须是唯一的，而且一个 vault 最多容纳 20 个凭据。每个商家一个 vault 是正确的结构；`vault_ids` 只能在创建会话时设置。

**Why not the system prompt.** Keys in a system prompt or user message persist in the session's event history. Vault secret fields are write-only and never returned.

> **为什么不能放进系统提示词。** 系统提示词或用户消息里的密钥会持久保存在会话的事件历史中。而 vault 的密钥字段是只写的，永远不会被返回。

**Catch it before merchants do.** Credentials are not validated until runtime, so a wrong one surfaces as an authentication error during the session, which keeps running. Add a CI check that every MCP server URL on the agent has a matching credential, and a short smoke session per release.

> **在商家发现之前抓住问题。** 凭据要到运行时才会被校验，所以错误的凭据会在会话期间以认证错误的形式出现，而会话仍会继续运行。加一个 CI 检查，确保 agent 上每个 MCP 服务器的 URL 都有匹配的凭据，并在每次发布时跑一个简短的冒烟测试会话。

```go
// Mirrors the documented match: scheme and host lowercased,
// default port and trailing slash dropped; path, subdomain and other ports must match.
func vaultKey(raw string) (string, error) {
	u, err := url.Parse(raw)
	if err != nil {
		return "", err
	}
	scheme, host, port := strings.ToLower(u.Scheme), strings.ToLower(u.Hostname()), u.Port()
	if (scheme == "https" && port == "443") || (scheme == "http" && port == "80") {
		port = ""
	}
	if port != "" {
		host = net.JoinHostPort(host, port)
	}
	return scheme + "://" + host + strings.TrimRight(u.EscapedPath(), "/"), nil
}

// CI check: every MCP server on the agent must have a credential in the merchant vault.
func unauthenticated(servers, vaultURLs []string) []string {
	have := map[string]bool{}
	for _, v := range vaultURLs {
		if k, err := vaultKey(v); err == nil {
			have[k] = true
		}
	}
	var missing []string
	for _, s := range servers {
		if k, err := vaultKey(s); err != nil || !have[k] {
			missing = append(missing, s)
		}
	}
	return missing
}
```

**Trade-offs.** One vault per merchant isolates tokens but multiplies rotation work when a server moves. The CI check only mirrors the documented rule; the platform decides, so keep the smoke session.

> **权衡。** 每个商家一个 vault 能隔离令牌，但服务器一迁移，轮换工作量就成倍增加。CI 检查只是模仿了文档中的规则；真正的判定在平台，所以冒烟测试会话不能省。

</details>

## 4. The migration eval says Claude Haiku 5.5 is 12 points worse at product descriptions, and the gold answers were written by Claude Haiku 4.5

**迁移评测显示 Claude Haiku 5.5 写商品描述的得分低了 12 分，而标准答案是由 Claude Haiku 4.5 写的** · `Evals & Observability` · `Hard`

### Question · 题目

The product-description pipeline runs on Claude Haiku 4.5. To decide on Claude Haiku 5.5, the team built an eval: 300 products, with last month's Claude Haiku 4.5 descriptions as the gold answers, reviewed by nobody. The score is embedding similarity to the gold text, with a pass threshold, and each case runs once. The result: Claude Haiku 4.5 passes 94%, Claude Haiku 5.5 passes 82%.

> 商品描述流水线运行在 Claude Haiku 4.5 上。为了决定是否换成 Claude Haiku 5.5，团队搭了一个评测：300 个商品，以上个月 Claude Haiku 4.5 生成的描述作为标准答案，没有任何人审核过。评分方式是与标准文本的 embedding 相似度，超过阈值即算通过，每个用例只跑一次。结果：Claude Haiku 4.5 的通过率是 94%，Claude Haiku 5.5 是 82%。

Reading the failures, you find Claude Haiku 5.5 rows with empty text, rows that are cut off mid-sentence, and a few refusals, all scored as 0. Explain what is wrong and design an eval that can decide.

> 翻看失败的用例，你发现 Claude Haiku 5.5 有一些行文本为空，一些行在句子中间被截断，还有少数拒答，全都被记为 0 分。解释问题出在哪里，并设计一个能够做出判断的评测。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** This eval rewards imitating the incumbent model, and it mixes plumbing failures into the model's score. Both push the result toward "keep the old model".

> **核心思想。** 这个评测奖励的是模仿现有模型，而且把管道层面的故障混进了模型的得分。两者都会把结果推向「继续用旧模型」。

**Gold from the incumbent.** Never use model A's outputs as gold when the question is A versus B. Similarity to Claude Haiku 4.5's text punishes every stylistic difference and gives Claude Haiku 4.5 a near-perfect score by construction.

> **标准答案来自现有模型。** 当问题是 A 和 B 相比哪个更好时，绝不能用模型 A 的输出作为标准答案。与 Claude Haiku 4.5 文本的相似度会惩罚每一处风格差异，并且从设计上就让 Claude Haiku 4.5 拿到接近满分。

**Plumbing counted as quality.**

> **管道问题被算成了质量问题。**

- **Empty text.** Claude Haiku 5.5 thinks by default, so a response can begin with `thinking` blocks, whose text is omitted by default. Code that reads the first block as the answer gets an empty string. Read blocks by `type`.
  > **空文本。** Claude Haiku 5.5 默认会思考，所以响应可能以 `thinking` 块开头，而思考块的文本默认是省略的。把第一个块当作答案的代码拿到的是空字符串。应按 `type` 读取内容块。
- **Cut-off rows.** Thinking counts toward `max_tokens`, and the newer tokenizer counts the same text as about 30% more tokens. A limit tuned for Claude Haiku 4.5 clips answers. Mark those rows truncated, and raise the limit.
  > **被截断的行。** 思考会计入 `max_tokens`，而且新的分词器对同样的文本大约多算 30% 的 token。为 Claude Haiku 4.5 调好的上限会截断答案。把这些行标记为被截断，并提高上限。
- **Refusals.** Score them as their own metric. Claude Haiku 5.5 has no server-side fallback, so the pipeline needs its own handling for them anyway.
  > **拒答。** 把它们作为单独的指标统计。Claude Haiku 5.5 没有服务端回退，所以流水线本来就需要自己处理拒答。

```go
type Row struct {
	Err         error
	ServedModel string // read from the response, not the request
	StopReason  string
	Text        string // text blocks only, collected by type
}

// Only "graded" rows reach the grader; the rest are counted separately.
func status(r Row, want string) string {
	switch {
	case r.Err != nil, r.ServedModel != want:
		return "error" // errors file, never a zero
	case r.StopReason == "refusal":
		return "refused" // its own metric
	case r.StopReason == "max_tokens":
		return "truncated"
	case strings.TrimSpace(r.Text) == "":
		return "no_answer"
	}
	return "graded"
}

// Rough 95% half-width for a pass-rate difference: about 1/sqrt(cases*reps).
func noiseFloor(cases, reps int) float64 { return 1 / math.Sqrt(float64(cases*reps)) }
```

**A design that can decide.** Grade atomic properties instead of similarity: every fact matches the product's attributes, nothing is invented, length and format rules hold, banned claims are absent. Use checks in code where possible and a judge only for tone. For the judge, randomize the order in pairwise comparisons, do not say which answer is the old one, tell it not to reward length, avoid using a model under test as its own judge, and calibrate it against a few dozen human labels. Run an oracle and a null baseline through the whole pipeline first, and assert the served model on every row.

> **一个能做出判断的设计。** 用原子化的属性来评分，而不是相似度：每条事实都与商品属性一致、没有编造内容、符合长度和格式规则、没有违禁说法。能用代码检查的就用代码，只在语气这类方面使用评审模型。对于评审模型：在成对比较中随机打乱顺序，不要告诉它哪个是旧答案，要求它不要因为篇幅长而加分，避免让被测模型给自己评分，并用几十条人工标注对它进行校准。先让一个理想答案（oracle）基线和一个空（null）基线完整跑通整条流水线，并在每一行上断言实际服务的模型。

**Enough signal.** With 300 cases and one rep, the noise floor is about 6 points. Use two or three reps and a paired comparison, and set effort explicitly on Claude Haiku 5.5 (its default is `medium`), trying two or three levels.

> **足够的信号。** 300 个用例、每个只跑一次，噪声下限大约是 6 分。每个用例跑两到三次并做配对比较，同时在 Claude Haiku 5.5 上显式设置 effort（它的默认值是 `medium`），尝试两到三个等级。

**Trade-offs.** A rubric costs more to build than a similarity score, and a judge adds its own cost and variance. Both are cheaper than switching, or not switching, on a number that measured the wrong thing.

> **权衡。** 构建评分细则比算相似度成本更高，评审模型也会带来自身的成本和波动。但和依据一个衡量错了东西的数字去决定换或不换模型相比，这两者都更便宜。

</details>

## 5. After moving the catalog agent to a self-hosted sandbox, its memory notes go missing, a read-only playbook gets edited, and some sessions never start

**把商品目录 agent 迁到自托管沙箱之后，它的记忆笔记会丢失、只读的操作手册被改动，还有些会话根本启动不了** · `Context & Memory` · `Senior`

### Question · 题目

A catalog agent on Managed Agents uses two memory stores: a read-only "Merchant playbook" and a read-write "Notes" store per merchant. The team moved it to a self-hosted environment on its own Kubernetes cluster, running the Go SDK worker. Since then:

> Managed Agents 上的一个商品目录 agent 使用两个记忆库：一个只读的「商家操作手册」，以及每个商家各自一个可读写的「笔记」库。团队把它迁到了自己 Kubernetes 集群上的自托管环境，运行 Go SDK 的 worker。从那以后：

- notes written near the end of a session are lost after deploys;
  > 在会话快结束时写下的笔记，在发布之后丢失了；
- a note an agent just wrote is silently replaced by an older version;
  > agent 刚写下的一条笔记，被一个更旧的版本悄无声息地替换了；
- an agent changed a playbook file with `sed` through `bash`, acted as if the change had stuck, and the next session never saw it;
  > 一个 agent 通过 `bash` 用 `sed` 修改了操作手册里的一个文件，并以为修改已经生效，而下一个会话却根本看不到这个修改；
- after a node crash, new sessions for that merchant sit idle with `requires_action` and no error event;
  > 一个节点崩溃之后，该商家的新会话一直处于空闲状态，停在 `requires_action`，也没有任何错误事件；
- an engineer disabled memory sync "to save API calls", and the agent now looks for notes it was told exist and finds nothing.
  > 一位工程师为了「节省 API 调用」禁用了记忆同步，结果 agent 去找那些被告知存在的笔记时，什么也找不到。

Explain each symptom and design the worker setup.

> 解释每个现象，并设计 worker 的部署方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** On a self-hosted environment, memory is a local copy that the SDK worker downloads and syncs, not a live mount. The store on Anthropic's side remains the source of truth. Every symptom comes from treating the copy as if it were the store.

> **核心思想。** 在自托管环境中，记忆是由 SDK worker 下载并同步的本地副本，而不是实时挂载。Anthropic 那边的记忆库仍然是唯一可信的数据源。每一个现象都源于把副本当成了记忆库本身。

**Lost on deploy.** The worker installs no signal handlers. A killed worker runs no teardown at all; a cancelled one skips the final sync but still uploads changed files. Wire SIGTERM to cancellation, and give the pod at least 30 seconds before a hard kill, because the final flush can take that long.

> **发布时丢失。** worker 不会安装任何信号处理器。被强制杀掉的 worker 完全不会执行清理；被取消的 worker 会跳过最后一次同步，但仍会上传改动过的文件。把 SIGTERM 接到取消逻辑上，并在强制杀掉之前给 Pod 至少 30 秒，因为最后一次刷写可能需要这么久。

```go
func main() {
	// SIGTERM cancels the context, so the worker still uploads changed notes.
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	// No API key on this host: the worker authenticates with the
	// environment key and the work item's secret from ANTHROPIC_* variables.
	client := anthropic.NewClient()
	w := environments.NewEnvironmentWorker(client, environments.EnvironmentWorkerOptions{
		Workdir:             "/workspace",
		MemorySyncInterval:  10 * time.Second,                       // 0 = default 15 s; negative disables memory
		MemorySyncDeletions: environments.MemorySyncDeletionsLogOnly, // audit deletes first
	})
	if err := w.HandleItem(ctx, environments.HandleItemOptions{}); err != nil {
		log.Printf("work item failed: %v", err) // mount errors show up here, not in the session
		os.Exit(1)
	}
}
```

**Replaced by an older version.** Conflicts resolve in favor of the store. If a file changed remotely since the last sync, the worker keeps the store's version and overwrites the local file with only a logged warning; the agent's write still succeeded and it sees no error. Avoid two writers on one file: one note file per topic or session, or host-side updates with a `content_sha256` precondition.

> **被旧版本替换。** 冲突会以记忆库为准来解决。如果某个文件在上次同步之后在远端被改过，worker 会保留记忆库里的版本并覆盖本地文件，只在日志里记一条警告；agent 的写入仍然显示成功，它也看不到任何错误。避免多个写入方写同一个文件：每个主题或每个会话一个笔记文件，或者在宿主机侧用带 `content_sha256` 前置条件的更新。

**The edited playbook.** For read-only stores the worker's `write` and `edit` tools refuse changes, but `bash` edits are not blocked locally. They never sync, and the next remote change overwrites them. Tell the agent in the store's instructions that the playbook is read-only, and remove `bash` if the agent does not need it.

> **被修改的操作手册。** 对于只读记忆库，worker 的 `write` 和 `edit` 工具会拒绝修改，但通过 `bash` 的修改在本地不会被拦截。这些修改永远不会同步，下一次远端变更就会覆盖它们。在记忆库的说明里告诉 agent 操作手册是只读的；如果 agent 用不到 `bash`，就把它去掉。

**Idle with no error.** A killed worker left the store's directory behind. The worker refuses a work item when something already exists at the store's path, and mount failures are logged, not reported to the session. Remove the leftover directory (its unsynced edits are lost), then send `user.interrupt` to re-queue the work. The same rule means two sessions cannot mount one store on one host, so run one sandbox per session; a discarded sandbox leaves nothing behind.

> **空闲且没有错误。** 被杀掉的 worker 留下了记忆库的目录。当记忆库路径上已经存在东西时，worker 会拒绝这个工作项，而挂载失败只会写进日志，不会报告给会话。删除残留的目录（其中未同步的修改会丢失），然后发送 `user.interrupt` 让工作重新排队。同样的规则意味着两个会话不能在同一台主机上挂载同一个记忆库，所以要每个会话一个沙箱；丢弃的沙箱不会留下任何残留。

**Disabled sync.** A negative interval disables memory entirely: stores are neither downloaded nor synced, yet the session's system prompt still describes them. Keep the default 15 seconds or set no lower than 5. A shorter interval narrows the window in which another running session sees stale notes, at the cost of more requests.

> **禁用同步。** 负数的同步间隔会完全禁用记忆：记忆库既不会被下载也不会被同步，但会话的系统提示里仍然会描述它们。保持默认的 15 秒，或者设置为不低于 5 秒。更短的间隔能缩小其他正在运行的会话看到过时笔记的时间窗口，代价是更多的请求。

**Trade-offs.** One sandbox per session costs startup time but removes leftover directories and shared paths. Logging deletes before enabling them protects notes but lets stale files pile up. Ship worker logs to your alerting, since that is where memory failures appear.

> **权衡。** 每个会话一个沙箱会增加启动时间，但能消除残留目录和共享路径的问题。在启用删除之前先只记录删除操作能保护笔记，但会让过时的文件越积越多。把 worker 的日志接入告警系统，因为记忆相关的故障只会出现在那里。

</details>
