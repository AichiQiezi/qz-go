## 1. "Do you ship to Brazil?" The help assistant answers a confident yes, although no document in the store's help center says so

**「你们发货到巴西吗？」帮助助手自信地回答「可以」，可店铺帮助中心里没有任何文档这么说** · `RAG` · `Medium`

### Question · 题目

A store's help assistant retrieves passages from the merchant's help center and answers shoppers. A shopper asked whether the store ships to Brazil. The shipping page says the store ships only to the United States, Canada and Mexico, and the assistant still answered "Yes, we ship to Brazil, delivery takes 10 to 15 days." In a review of 200 conversations, the team found that most wrong answers came from questions the help center does not cover at all: the assistant fills the gap with what sounds like a typical store policy.

> 一家店铺的帮助助手从商家的帮助中心检索段落来回答顾客的问题。有位顾客问店铺是否发货到巴西。发货页面写的是只发往美国、加拿大和墨西哥，助手却依然回答「可以，我们发货到巴西，配送需要 10 到 15 天」。团队复查了 200 段对话，发现大多数错误回答都来自帮助中心根本没有覆盖的问题：助手会用听起来像是典型店铺政策的内容去填补空白。

How do you make the assistant say "I don't know" when it should, without making it refuse questions it can answer?

> 你要如何让助手在该说「我不知道」的时候这么说，同时又不让它拒答那些本来能回答的问题？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Retrieval always returns something, and a model asked to be helpful will answer from general knowledge when the passages are thin. Answering from the documents has to be a checked property of the answer, not a hope expressed in the prompt. Give the model an explicit way out, require evidence for every answer, and verify that evidence in code before the shopper sees it.

> **核心思想。** 检索总会返回点什么；而一个被要求提供帮助的模型，在段落内容单薄时会凭通用知识作答。「依据文档作答」必须是答案上一个经过检查的属性，而不是提示词里表达的一种期望。给模型一条明确的退路，要求每个答案都有证据，并在顾客看到之前用代码核验这些证据。

**Why it happened here.** The shipping passage was retrieved, but nothing told the model that silence on Brazil means no. Shoppers' questions about other countries look like questions the store answers, so the model completed the pattern. Two gaps: the prompt never made "not covered" an acceptable outcome, and nothing checked the answer against the passages.

> **这里为什么会出错。** 发货段落确实被检索到了，但没有任何东西告诉模型：对巴西只字未提，意味着不发。顾客关于其他国家的问题，看起来就像店铺会回答的那类问题，于是模型顺着模式补全了答案。有两个缺口：提示词从未把「未覆盖」当作一个可接受的结果，也没有任何东西拿段落去核对答案。

**Make abstaining a first-class answer.**

> **让放弃作答成为一等公民的答案。**

- Ask for a structured reply with a field such as `answerable`, the answer, and citations that name a passage ID and quote it word for word. Say in the prompt that answers must come only from the passages, that a policy the passages do not state is not covered, and that a list of countries is a complete list.
  > 要求模型给出结构化回复，包含 `answerable` 这样的字段、答案本身，以及标明段落 ID 并逐字引用原文的引证。在提示词里写明：答案只能来自这些段落；段落里没有写明的政策就是未覆盖；一份国家列表就是完整的列表。
- Give the fallback a real destination: a handoff to the support team or a link to contact the store, so abstaining still helps the shopper.
  > 给兜底回复一个真正的去处：转交给客服团队，或者给出联系店铺的方式，这样即使放弃作答也依然在帮顾客。

**Verify in code.** The Managed Agents guidance on multi-agent setups is explicit that a check in your own code that calls no model, such as confirming each cited quote appears word for word in the source, is fine, and that sending a failing answer back to the same session a few times at most is fine too:

> **用代码核验。** Managed Agents 关于多 Agent 配置的指南明确说过：在你自己的代码里做一个不调用模型的检查，比如确认每条引文都逐字出现在原文里，是可以的；把未通过检查的答案退回同一个会话、最多重试几次，也是可以的：

```go
// Draft is the model's structured answer: it must point at passages and quote them.
type Draft struct {
	Answerable bool
	Answer     string
	Citations  []Citation
}

type Citation struct {
	PassageID string
	Quote     string
}

const fallback = "I couldn't find this in the store's policies, so I've passed your question to the support team."

// gate decides what the shopper sees. It calls no model: it only checks that the
// answer rests on passages that were actually retrieved and quoted word for word.
func gate(d Draft, retrieved []Passage, minScore float64) (string, string) {
	if !d.Answerable {
		return fallback, "model said not answerable"
	}
	if len(d.Citations) == 0 {
		return fallback, "no citations"
	}
	byID := map[string]Passage{}
	for _, p := range retrieved {
		byID[p.ID] = p
	}
	for _, c := range d.Citations {
		p, ok := byID[c.PassageID]
		if !ok {
			return fallback, "cites a passage that was not retrieved: " + c.PassageID
		}
		if p.Score < minScore {
			return fallback, fmt.Sprintf("cited passage %s scored %.2f, below %.2f", p.ID, p.Score, minScore)
		}
		if c.Quote == "" || !strings.Contains(norm(p.Text), norm(c.Quote)) {
			return fallback, "quote not found in " + p.ID
		}
	}
	return d.Answer, "ok"
}
```

- In a local run, the uncited "yes" and the "yes" that quoted a sentence the page does not contain both fell back to the handoff; the cited "no" passed.
  > 在一次本地运行中，没有引证的「可以」，以及引用了页面上并不存在的句子的「可以」，都被兜底转交给客服；带引证的「不发货」则通过了检查。
- The score threshold is per embedding model and per corpus. Pick it from labeled questions, not by intuition.
  > 分数阈值取决于具体的嵌入模型和语料。要用带标注的问题来确定它，而不是凭直觉。
- If you use the API's built-in citations on document blocks instead, note that citations cannot be combined with `output_config.format`; that request returns a 400.
  > 如果改用 API 在文档块上内置的 citations 功能，要注意 citations 不能和 `output_config.format` 一起用；这样的请求会返回 400。

**Measure both directions.** Build an eval with three kinds of questions: answerable, unanswerable but on-topic (Brazil), and answerable only by combining two passages. Track wrong answers and wrong refusals separately. A gate that only lowers wrong answers can quietly raise refusals on questions the help center does cover.

> **两个方向都要度量。** 建一套包含三类问题的评测：能回答的、话题相关但无法回答的（比如巴西）、需要结合两个段落才能回答的。把错误回答和错误拒答分开统计。一道只降低错误回答的闸门，可能会悄悄抬高帮助中心明明覆盖了的问题的拒答率。

**Trade-offs.** Quote checks reject paraphrased but correct answers, so normalize whitespace and case and allow short quotes. Each fallback costs a support ticket; log every gated answer with its reason, and turn frequent "not covered" questions into a list for the merchant: the cheapest fix is often a new help article.

> **权衡。** 引文检查会拒掉那些转述了原文但内容正确的答案，所以要统一空白和大小写，并允许较短的引文。每一次兜底都要花费一张客服工单；把每个被拦下的答案连同原因一起记录下来，并把高频的「未覆盖」问题整理成清单交给商家：最便宜的修复往往是补一篇新的帮助文章。

</details>

## 2. The merchant presses Stop halfway through a bulk price change: the next message fails, the agent does not know what was changed, and one edit kept running

**商家在批量改价进行到一半时按下「停止」：下一条消息报错，Agent 不知道改了什么，还有一个修改仍在继续执行** · `Agent Loop` · `Hard`

### Question · 题目

The catalog assistant runs on a hand-written tool loop over the Messages API. A merchant asked it to raise prices on winter items, watched it start, and pressed Stop. Three things went wrong. The next message the merchant sent failed with a 400 from the API. The bulk price tool kept running in the background and finished all 200 products. When the conversation was repaired, the assistant told the merchant "no prices were changed", because it had never seen the results.

> 目录助手运行在一个基于 Messages API 手写的工具循环上。商家让它给冬季商品涨价，看着它开始执行后按下了「停止」。结果出了三个问题：商家接下来发的消息被 API 以 400 拒绝；批量改价工具在后台继续运行，把 200 个商品全部改完了；对话被修复之后，助手告诉商家「没有改动任何价格」，因为它从未看到过工具结果。

Explain each failure and design what Stop should do.

> 解释每个故障，并设计「停止」应有的行为。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Stop is not "forget the turn". It ends work at a known point and then tells the model exactly what happened. The history must stay valid, the tools must actually stop, and the model must see the truth about partial work.

> **核心思想。** 「停止」不等于「忘掉这一轮」。它要在一个确定的位置结束工作，然后把发生了什么准确地告诉模型。历史必须保持合法，工具必须真正停下来，模型必须看到部分完成的工作的真实情况。

**Failure one: the 400.** The last assistant message in the history held `tool_use` blocks, and the next request sent the merchant's text with no `tool_result` for them. Every tool call needs a result in the next user message, and all results for one turn go in a single user message. A call that failed or never ran still gets a result, with `is_error: true`; you never drop it.

> **故障一：400。** 历史里最后一条 assistant 消息包含 `tool_use` 块，而下一次请求只发送了商家的文字，没有对应的 `tool_result`。每一个工具调用都需要在下一条 user 消息里给出结果，并且同一轮的所有结果要放在同一条 user 消息里。失败的或从未执行的调用也要有结果，标上 `is_error: true`；绝不能把它丢掉。

**Failure two: the edit kept running.** The UI cancelled the HTTP request, but the tool ran in its own goroutine with a background context. Cancelling a request to the model does not cancel your tools. Pass the turn's context into every tool and have long tools check it between batches, so they stop at a boundary they can describe.

> **故障二：修改仍在继续。** 界面取消了 HTTP 请求，但工具运行在自己的 goroutine 里，用的是一个后台 context。取消对模型的请求，并不会取消你自己的工具。要把这一轮的 context 传进每个工具，并让耗时长的工具在批次之间检查它，这样它们就会停在一个可以描述清楚的边界上。

**Failure three: the wrong summary.** The repair deleted the tool calls instead of answering them, so the model never learned that prices had changed. Write results that say what happened:

> **故障三：错误的总结。** 那次修复把工具调用删掉了，而不是给它们回填结果，所以模型从未得知价格已经改了。要写出说明实际情况的结果：

```go
// runStep executes one assistant turn's tool calls in order. Whatever happens,
// it returns exactly one tool_result per tool_use, so the history stays valid.
func runStep(ctx context.Context, calls []ToolUse) []ToolResult {
	results := make([]ToolResult, 0, len(calls))
	for _, c := range calls {
		if ctx.Err() != nil {
			results = append(results, ToolResult{c.ID,
				"Not run: the merchant pressed Stop before this call started.", true})
			continue
		}
		done, err := bulkEdit(ctx, c.Items)
		switch {
		case err == nil:
			results = append(results, ToolResult{c.ID, fmt.Sprintf("Updated %d of %d products.", done, c.Items), false})
		case errors.Is(err, context.Canceled):
			results = append(results, ToolResult{c.ID, fmt.Sprintf(
				"Stopped by the merchant after updating %d of %d products. The rest were not changed.", done, c.Items), true})
		default:
			results = append(results, ToolResult{c.ID, "Failed: " + err.Error(), true})
		}
	}
	return results
}
```

- In a local run with Stop pressed during the second call, the first result said 30 of 30 updated, the second said it stopped after 80 of 200, and the third said it never started. That is what the model needs to give an honest summary and offer to finish or undo.
  > 在一次本地运行中，在第二个调用执行期间按下「停止」：第一个结果说 30 个中的 30 个已更新，第二个说在 200 个中改完 80 个后停止，第三个说根本没有开始。模型正需要这些信息，才能给出如实的总结，并提出继续完成或撤销。
- A tool that cannot stop midway, such as a single external API call, should be awaited, and its real outcome reported. If the outcome is unknown, say so and tell the model to check state before retrying.
  > 无法中途停下的工具，比如单次外部 API 调用，应当等待它结束，并报告真实结果。如果结果未知，就如实说明，并告诉模型在重试之前先检查状态。

**Where the merchant's next words go.** Send them as a text block after the last `tool_result` in that same user message, never inside a `tool_result`; the migration guide warns that user text placed inside or directly after a tool result can be read as a prompt injection. If Stop arrives while the model is still generating, abort the stream and do not append the partial response: run tools only once a response has ended, and the history holds only complete turns.

> **商家接下来说的话放在哪里。** 把它们作为一个文本块，放在同一条 user 消息里最后一个 `tool_result` 之后，绝不要放进 `tool_result` 里；迁移指南提醒过，放在工具结果内部或紧跟其后的用户文字，可能会被当成提示词注入。如果按下「停止」时模型仍在生成，就中止流式响应，不要把不完整的回复追加进历史：只在一次响应结束后才运行工具，这样历史里就只有完整的轮次。

**Trade-offs.** Stopping between batches leaves a half-applied change, which is often worse than finishing. For bulk edits, consider a preview then apply design where Stop before apply changes nothing, and record a change set so "undo what you did" is a tool rather than a guess.

> **权衡。** 在批次之间停下，会留下一个只应用了一半的修改，这往往比做完更糟。对于批量修改，可以考虑「先预览、再应用」的设计，在应用之前按「停止」就什么都不会改变；同时记录一份变更集，让「撤销你刚才做的」成为一个工具，而不是一次猜测。

</details>

## 3. "How did yesterday go?" The sales assistant reports the wrong day for merchants in California, and putting the current time in the system prompt broke caching

**「昨天卖得怎么样？」销售助手给加州商家报的是错误的那一天，而把当前时间写进系统提示词又让缓存失效了** · `Context & Memory` · `Medium`

### Question · 题目

The sales assistant answers questions like "how did yesterday go?" and "compare this week with last week". Merchants in California report that "yesterday" is often the wrong day. Early on, the model sometimes guessed a date from its training data. The team fixed that by adding `Current date: <UTC date>` to the top of the system prompt, and the cache hit rate fell to near zero. The reporting tool takes a date and the server converts it with UTC boundaries.

> 销售助手回答「昨天卖得怎么样？」「这周和上周比一比」这类问题。加州的商家反映，「昨天」经常是错误的那一天。早先，模型有时会根据训练数据去猜一个日期。团队的修复办法是在系统提示词顶部加上 `Current date: <UTC 日期>`，结果缓存命中率跌到接近零。报表工具接收一个日期，服务器按 UTC 的日界线去换算它。

Explain what is wrong and how the agent should handle time.

> 解释问题出在哪里，以及 Agent 应当如何处理时间。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The model does not know the current date or the merchant's time zone unless you tell it, and "yesterday" is a local concept. Give it the store's local time as volatile context placed after the cached prefix, and let tools, not the model, turn local days into timestamp ranges.

> **核心思想。** 除非你告诉它，模型并不知道当前日期，也不知道商家所在的时区；而「昨天」是一个本地概念。把店铺的本地时间作为易变的上下文，放在缓存前缀之后提供给模型；把本地日期换算成时间戳范围的工作交给工具，而不是交给模型。

**Three bugs in one feature.**

> **一个功能里的三个 bug。**

- **The wrong date.** The note gave the UTC date. At 07:30 UTC on November 2 it is still Sunday evening, November 1, in Los Angeles, so the store's yesterday is October 31, not November 1.
  > **错误的日期。** 那条说明给的是 UTC 日期。在 UTC 时间 11 月 2 日 07:30，洛杉矶仍是 11 月 1 日周日晚上，所以店铺的「昨天」是 10 月 31 日，而不是 11 月 1 日。
- **The wrong day boundaries.** Even with the right date, the server cut the day at UTC midnight, so a California "day" included the previous evening's orders and missed the last hours of the day.
  > **错误的日界线。** 即使日期对了，服务器也是按 UTC 零点来切分一天的，所以加州的「一天」包含了前一天晚上的订单，又漏掉了这一天最后的几个小时。
- **The cache.** Prompt caching is a prefix match: any byte change invalidates everything after it, and the render order is tools, then system, then messages. A date at the top of the system prompt changes the prefix every day, or every request if it includes the time. The caching guide calls this out directly: keep the system prompt frozen and inject dynamic context such as the current date later in `messages`.
  > **缓存。** 提示词缓存是前缀匹配：任何一个字节的变化，都会让它之后的一切失效；而渲染顺序是先 tools、再 system、再 messages。系统提示词顶部的日期每天都会改变前缀，如果还带着时刻，就是每次请求都在变。缓存指南直接点明了这一点：保持系统提示词不变，把当前日期这类动态上下文放到后面的 `messages` 里。

**The fix.** Store each merchant's IANA time zone. Each turn, add a short clock note in the new part of the conversation, either in the user turn or as a mid-conversation system message on models that support it; such a message must follow a user message and cannot be `messages[0]`. Then give the reporting tool local dates and let it compute the range:

> **修复方案。** 为每个商家保存其 IANA 时区。每一轮在对话新增的部分加一条简短的时间说明，可以放在 user 轮次里，也可以在支持的模型上用对话中途的 system 消息；这种消息必须跟在 user 消息之后，而且不能是 `messages[0]`。然后让报表工具接收本地日期，由它来计算时间范围：

```go
// clockNote is the volatile context for one turn. It goes into messages
// (after the cached prefix), never into the frozen system prompt.
func clockNote(now time.Time, storeTZ string) (string, error) {
	loc, err := time.LoadLocation(storeTZ)
	if err != nil {
		return "", err
	}
	t := now.In(loc)
	return fmt.Sprintf("Store local time: %s (%s, %s). Interpret relative dates in this time zone.",
		t.Format("Monday 2006-01-02 15:04"), storeTZ, t.Format("UTC-07:00")), nil
}

// dayRange turns a calendar day in the store's zone into a UTC half-open range
// for the reporting API. The tool does the date math, not the model.
func dayRange(day string, storeTZ string) (time.Time, time.Time, error) {
	loc, err := time.LoadLocation(storeTZ)
	if err != nil {
		return time.Time{}, time.Time{}, err
	}
	start, err := time.ParseInLocation("2006-01-02", day, loc)
	if err != nil {
		return time.Time{}, time.Time{}, err
	}
	end := start.AddDate(0, 0, 1) // next local midnight, not start+24h
	return start.UTC(), end.UTC(), nil
}

// yesterday is computed from the store's local date, not the server's.
func yesterday(now time.Time, storeTZ string) string {
	loc, _ := time.LoadLocation(storeTZ)
	return now.In(loc).AddDate(0, 0, -1).Format("2006-01-02")
}
```

- In a local run at 07:30 UTC on November 2, 2026, the server's yesterday was November 1 and the store's yesterday was October 31.
  > 在一次本地运行中，在 2026 年 11 月 2 日 UTC 07:30，服务器的「昨天」是 11 月 1 日，而店铺的「昨天」是 10 月 31 日。
- November 1, 2026 in Los Angeles is the day daylight saving time ends, and the range came out as 25 hours. Adding a calendar day, not 24 hours, is what gets this right.
  > 2026 年 11 月 1 日是洛杉矶夏令时结束的日子，算出来的范围是 25 小时。正是因为加的是一个日历日而不是 24 小时，结果才是对的。
- Let the tool echo the resolved range in its result, such as "Oct 31, 00:00 to 24:00 Pacific", so the model can state it and the merchant can catch a misunderstanding.
  > 让工具在结果里回显它解析出的范围，比如「太平洋时间 10 月 31 日 00:00 至 24:00」，这样模型可以把它说出来，商家也能及时发现误解。

**Trade-offs.** A clock note on every turn adds a few tokens and a little text the model must read; adding it only when the conversation is new or the date has changed is enough for most stores. Week boundaries differ by locale, so make "this week" a store setting rather than letting the model choose Monday or Sunday.

> **权衡。** 每一轮都附上时间说明，会多出几个 token，也让模型多读一点文字；对大多数店铺来说，只在对话刚开始或日期变化时加上就够了。周的起止因地区而异，所以要把「本周」做成店铺设置，而不是让模型自己决定从周一还是周日算起。

</details>

## 4. A prompt change lifted the support eval from 84% to 87%, and rerunning the old prompt scored 86%: is the win real?

**一次提示词修改把客服评测从 84% 提到了 87%，可重跑旧提示词也得了 86%：这个提升是真的吗？** · `Evals & Observability` · `Hard`

### Question · 题目

The support team keeps an eval of 120 real tickets, each run once and graded pass or fail by an LLM judge. A prompt change scored 87% against the old prompt's 84%, and the change was about to ship. Someone reran the old prompt as a sanity check and got 86%. Last month two other "wins" of 2 to 4 points were shipped and later showed no change in the escalation rate.

> 客服团队维护着一套由 120 张真实工单组成的评测，每个用例只跑一次，由一个 LLM 评审打通过或不通过。一次提示词修改得到了 87%，旧提示词是 84%，这个修改眼看就要上线。有人出于稳妥重跑了一遍旧提示词，得到了 86%。上个月，另外两个 2 到 4 个点的「提升」上线后，转人工率并没有任何变化。

What is going on, and how should the team decide whether a change is a win?

> 这是怎么回事？团队应当如何判断一次修改是否真的带来了提升？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A single run of an eval is a point estimate with no error bar. Model outputs vary from run to run, and the judge can vary too, so every score has a noise floor. A difference smaller than that floor is not evidence, and the team has been shipping noise.

> **核心思想。** 评测只跑一次，得到的是一个没有误差范围的点估计。模型的输出每次运行都会不同，评审也可能不同，所以每个分数都有一个噪声下限。小于这个下限的差异算不上证据，而团队一直在上线噪声。

**How big the noise is.** The eval-audit checklist gives a rule of thumb for a pass rate: the half-width of the paired-difference 95% interval is roughly one over the square root of cases times reps. With 120 cases and one rep, that is about plus or minus 9 points, so a 3-point gain says nothing. The old prompt's 84 then 86 is the same noise seen directly.

> **噪声有多大。** 评测审计清单给出了通过率的一条经验法则：配对差值 95% 区间的半宽，大约是用例数乘以重复次数之后开平方再取倒数。120 个用例、每个跑一次，大约是正负 9 个点，所以 3 个点的提升什么也说明不了。旧提示词先 84 后 86，就是直接看到的同一种噪声。

**Measure it instead of arguing.** Run each case several times for both prompts, compare per case, and resample cases to get an interval:

> **去度量，而不是去争论。** 两个提示词都把每个用例跑上几次，逐个用例做比较，再对用例重采样，得到一个区间：

```go
// pairedDelta returns the mean per-case difference (new - old) and a 95%
// bootstrap interval that resamples cases, keeping each case's pair together.
func pairedDelta(old, new Run, iters int, seed int64) (float64, float64, float64) {
	a, b := caseMeans(old), caseMeans(new)
	d := make([]float64, len(a))
	mean := 0.0
	for i := range a {
		d[i] = b[i] - a[i]
		mean += d[i]
	}
	mean /= float64(len(d))
	rng := rand.New(rand.NewSource(seed))
	boot := make([]float64, iters)
	for k := range boot {
		s := 0.0
		for range d {
			s += d[rng.Intn(len(d))]
		}
		boot[k] = s / float64(len(d))
	}
	sort.Float64s(boot)
	return mean, boot[iters*25/1000], boot[iters*975/1000]
}
```

- A simulation with two identical prompts and an 84% average pass rate showed how often noise alone looks like a win. With one rep, the identical prompt gained 3 points or more in about 27% of runs; with five reps, about 6%.
  > 用两个完全相同、平均通过率为 84% 的提示词做模拟，可以看出单靠噪声有多常看起来像一次提升。每个用例跑一次时，相同的提示词在约 27% 的运行中提升了 3 个点或更多；跑五次时，约为 6%。
- The paired design matters: the same case under both prompts is compared with itself, so hard and easy cases do not add noise to the difference.
  > 配对设计很关键：同一个用例在两个提示词下是和自己比较的，因此难的用例和容易的用例不会给差值增加噪声。
- Report "k of N reps passed" per case, and look at which cases flipped. A real improvement moves specific cases for a reason you can name.
  > 按用例报告「N 次中通过了 k 次」，并查看哪些用例发生了翻转。真正的改进，会让具体的用例因为你说得出的原因而变化。

**Remove noise you added yourself.** Run the judge twice on the same outputs; if verdicts change, that is grader variance on top of model variance. Pin seeds and sort anything whose order reaches the model or the judge. Do not try to fix it with `temperature`: from API version `2026-10-21`, sending `temperature`, `top_p` or `top_k` returns a 400 on every model.

> **消除你自己引入的噪声。** 让评审对同一批输出跑两次；如果判定变了，那就是叠加在模型方差之上的评审方差。固定随机种子，对任何顺序会影响模型或评审的内容进行排序。不要指望用 `temperature` 来解决：从 API 版本 `2026-10-21` 起，在任何模型上发送 `temperature`、`top_p` 或 `top_k` 都会返回 400。

**A decision rule.** Before testing, write down the smallest gain worth shipping and check that the noise floor is below it; if not, add reps (cheapest) or cases first. Ship when the paired interval excludes zero and the gain holds on a held-out set, and confirm it later in a production metric such as the escalation rate.

> **一条决策规则。** 测试之前，先写下值得上线的最小提升，并确认噪声下限低于它；如果不低于，就先增加重复次数（最便宜）或用例。当配对区间不包含零、并且提升在留出集上依然成立时再上线，之后再用转人工率这类线上指标加以确认。

**Trade-offs.** Five reps cost five times as much per run. Spend reps on the cases that flip and keep the stable ones at one rep while iterating, then confirm the final choice on the full set.

> **权衡。** 跑五次，每次评测的成本就是原来的五倍。迭代时把重复次数花在会翻转的用例上，稳定的用例只跑一次；最后再在全集上确认最终的选择。

</details>

## 5. Thirty worker agents translate a 5,000-product catalog into German, and the same product term comes out four different ways

**三十个 worker Agent 把 5,000 个商品的目录翻译成德语，同一个商品术语却出现了四种译法** · `Multi-agent` · `Senior`

### Question · 题目

A merchant expanding into Germany needs titles, descriptions and size notes for 5,000 products translated. The team built a coordinator that splits the catalog into batches and hands them to thirty parallel workers. The pilot came back fast, and a German reviewer found "puffer jacket" as Steppjacke, Pufferjacke and Daunenjacke, "free shipping" in three forms, and size notes that mixed EU and US sizes. Each worker's output on its own reads well.

> 一个拓展德国市场的商家，需要翻译 5,000 个商品的标题、描述和尺码说明。团队搭了一个协调者，把目录切分成批次，交给三十个并行的 worker。试点很快完成，可一位德语审校发现：「puffer jacket」被译成了 Steppjacke、Pufferjacke 和 Daunenjacke，「free shipping」有三种写法，尺码说明里欧码和美码混在一起。每个 worker 的输出单独看都很通顺。

Design the system so that the catalog reads as if one translator wrote it.

> 设计这个系统，让整份目录读起来就像出自同一位译者之手。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Parallel workers do not share memory, so every decision a worker makes alone, it makes differently. Consistency has to be decided once, before fan-out, and then enforced after it: a frozen glossary and style sheet that every worker receives, and a check that every output must pass.

> **核心思想。** 并行的 worker 之间不共享记忆，所以每个 worker 独自做的决定，都会做得各不相同。一致性必须在分发之前一次性定下来，并在分发之后强制执行：一份每个 worker 都会收到的、冻结的术语表和风格规范，以及一道所有输出都必须通过的检查。

**Phase one: decide before fanning out.**

> **第一阶段：分发之前先做决定。**

- Extract candidate terms from the whole catalog first: product types, materials, recurring phrases such as shipping and returns lines, and size conventions. One agent proposes renderings; the merchant's German reviewer approves them. This is the step that needs judgment, and it happens once.
  > 先从整份目录里抽取候选术语：商品类型、材质、反复出现的短语（比如发货和退货说明），以及尺码惯例。由一个 Agent 提出译法，商家的德语审校来批准。这是需要判断力的一步，而且只发生一次。
- Freeze the result as a glossary with required renderings and known bad variants, plus a style sheet: formal or informal address, how sizes are shown, units, and brand names left untranslated.
  > 把结果冻结成一份术语表，写明必须使用的译法和已知的错误变体，再加一份风格规范：用敬称还是非敬称、尺码怎样标注、计量单位，以及品牌名不翻译。

**Phase two: fan out with the same context.** Every worker gets the same system prompt with the glossary and style sheet in the same byte order, followed by its batch. Prompt caching is a prefix match, so identical shared content first and the batch last lets workers read the cached prefix instead of paying for it thirty times; check `usage.cache_read_input_tokens` to confirm. Overnight work suits Message Batches, which run asynchronously at 50% cost; results arrive in any order, so key them by `custom_id`, never by position.

> **第二阶段：用相同的上下文分发。** 每个 worker 都拿到相同的系统提示词，其中术语表和风格规范的字节顺序完全一致，后面才是它负责的批次。提示词缓存是前缀匹配，所以把相同的共享内容放在前面、批次放在最后，worker 就能读取缓存的前缀，而不用为它付三十次费用；用 `usage.cache_read_input_tokens` 来确认。隔夜完成的工作适合用 Message Batches，它异步运行，成本减半；结果的返回顺序不固定，所以要用 `custom_id` 来对应，绝不能按位置对应。

**Phase three: check every batch in code.**

> **第三阶段：用代码检查每一个批次。**

```go
// Term is one frozen glossary entry, agreed before any worker starts.
type Term struct {
	Source string   // English term, matched as a whole word
	Target string   // required German rendering
	Avoid  []string // renderings workers drifted to in the pilot
}

type Item struct {
	SKU, Worker, Source, Target string
}

type Violation struct {
	SKU, Worker, Term, Problem string
}

// check runs after every worker batch. It calls no model; failures go back to
// the same worker with the exact term to fix. German compounds ("Wintermantel")
// mean the target check is a case-insensitive substring match, not a word match.
func check(items []Item, glossary []Term) []Violation {
	var out []Violation
	for _, g := range glossary {
		re := regexp.MustCompile(`(?i)\b` + regexp.QuoteMeta(g.Source) + `\b`)
		for _, it := range items {
			if !re.MatchString(it.Source) {
				continue
			}
			tgt := strings.ToLower(it.Target)
			if !strings.Contains(tgt, strings.ToLower(g.Target)) {
				out = append(out, Violation{it.SKU, it.Worker, g.Source, "missing \"" + g.Target + "\""})
			}
			for _, a := range g.Avoid {
				if strings.Contains(tgt, strings.ToLower(a)) {
					out = append(out, Violation{it.SKU, it.Worker, g.Source, "uses \"" + a + "\""})
				}
			}
		}
	}
	sort.Slice(out, func(i, j int) bool { return out[i].SKU < out[j].SKU })
	return out
}
```

- In a local run, the checker flagged both of one worker's drifted items and let "Kinder-Steppjacke" pass, because German compounds mean the target check is a substring match.
  > 在一次本地运行中，检查器标出了某个 worker 偏离术语表的两个条目，而放过了「Kinder-Steppjacke」，因为德语有复合词，所以对译文的检查用的是子串匹配。
- Send a failing item back to the worker that produced it with the exact term to fix, a few times at most, then to a human. Never let a second model silently rewrite it.
  > 把未通过的条目连同需要修正的具体术语，退回给生成它的那个 worker，最多重试几次，之后交给人工。绝不要让另一个模型悄悄地重写它。

**Phase four: sample for what code cannot see.** A German reviewer reads a stratified sample per worker and per product type. Anything they correct that is a pattern becomes a glossary entry, and only affected items are redone.

> **第四阶段：抽样检查代码看不到的东西。** 由德语审校按 worker 和商品类型分层抽样阅读。他们修正的内容只要构成规律，就加进术语表，并且只重做受影响的条目。

**Trade-offs.** German inflects adjectives, so "kostenloser Versand" becomes "kostenlosen Versand" in some sentences, and a naive checker flags correct text; store allowed forms per entry. A glossary change mid-run means a new prefix and a rerun of affected items, so version the glossary and record which version each item used. Thirty workers finish faster, but consistency comes from the shared decisions, not from the number of workers.

> **权衡。** 德语的形容词会变格，所以「kostenloser Versand」在有些句子里会变成「kostenlosen Versand」，朴素的检查器会把正确的文本标为错误；要为每个词条保存允许的词形。运行中途修改术语表，意味着前缀变了、受影响的条目要重跑，所以要给术语表加版本号，并记录每个条目用的是哪个版本。三十个 worker 确实完成得更快，但一致性来自共享的决定，而不是 worker 的数量。

</details>
