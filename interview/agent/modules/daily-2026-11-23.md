## 1. The migration agent writes a 40-step plan up front and keeps following it after step 6 fails, because the plan says so

**迁移 Agent 一开始就写好了 40 步的计划，第 6 步失败后仍然照着计划往下走，因为计划上就是这么写的** · `Agent Loop` · `Medium`

### Question · 题目

A store-migration agent starts each job by writing a detailed plan: export products, map attributes, import, set up redirects, and so on. The harness then feeds the plan back each turn and asks the agent to do the next step. On one job, the attribute mapping failed for 37 products, and the agent went on to import everything anyway, followed later steps that assumed the mapping had worked, and reported the migration as complete.

> 一个店铺迁移 Agent 在每个任务开始时都会写一份详细计划：导出商品、映射属性、导入、设置重定向等等。之后框架每一轮都把计划喂回去，让 Agent 执行下一步。在某个任务中，有 37 个商品的属性映射失败了，而 Agent 依然把所有商品都导入了，接着执行后面那些假设映射已经成功的步骤，最后报告迁移完成。

What is wrong with how the loop uses the plan, and how would you fix it?

> 这个循环使用计划的方式有什么问题？你会如何修复？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A plan is a guess made before the agent has seen any results. It is useful as a map, but every observation can prove part of it wrong. The loop here treated the plan as orders: it asked "what is the next step?" instead of "given what just happened, is the next step still right?"

> **核心思想。** 计划是 Agent 在看到任何结果之前做出的猜测。它作为一张地图是有用的，但每一次观察都可能证明其中一部分是错的。这里的循环把计划当成了命令：它问的是「下一步是什么？」，而不是「鉴于刚刚发生的事，下一步还对吗？」

**Why the agent kept going.** The harness put the full plan at the top of every turn with "do the next step", so the strongest signal in the context was the plan, not the failed result. A failure written as a line of text in a long tool result is easy to read past, and nothing in the loop forced a decision about it.

> **为什么 Agent 一直往下走。** 框架在每一轮的开头都放上完整计划，再加一句「执行下一步」，所以上下文里最强的信号是计划，而不是那个失败的结果。在一份很长的工具结果里，一行失败信息很容易被略过，而循环里也没有任何机制强迫它对此作出决定。

**The fix: keep the plan as state, with dependencies and outcomes.**

> **修复方法：把计划作为带依赖关系和结果的状态来维护。**

```go
type Step struct {
	ID        int
	Goal      string
	DependsOn []int
	Status    string // "pending", "done", "failed", "skipped"
	Note      string
}

// nextAction decides what the harness asks the model to do after each step.
// A failed step never lets dependent steps run on a stale plan.
func nextAction(plan []Step) string {
	failed := map[int]bool{}
	for _, s := range plan {
		if s.Status == "failed" {
			failed[s.ID] = true
		}
	}
	for _, s := range plan {
		if s.Status != "pending" {
			continue
		}
		for _, d := range s.DependsOn {
			if failed[d] {
				return fmt.Sprintf("replan: step %d depends on failed step %d", s.ID, d)
			}
		}
		return fmt.Sprintf("run step %d: %s", s.ID, s.Goal)
	}
	return "verify the result against the original request, then report"
}
```

- Record each step's outcome in the plan, written by the harness from the tool result rather than by the model's summary.
  > 把每一步的结果记录在计划里，由框架根据工具结果写入，而不是根据模型的总结。
- When a step fails, stop dependent steps and ask the model to re-plan from the current state: fix the 37 products, skip them with a note, or ask the merchant. Independent steps, such as redirects that only need the export, can continue.
  > 当某一步失败时，暂停依赖它的步骤，让模型根据当前状态重新规划：修好这 37 个商品、带说明地跳过它们，或者询问商家。互不依赖的步骤（比如只需要导出结果的重定向）可以继续。
- Show the model the outcomes next to the plan, so a failure is as visible as the next step.
  > 把结果和计划并排展示给模型，让失败和下一步一样显眼。

**Verify at the end against the request, not the plan.** "All steps done" is not the goal; "all products are in the new store with correct sizes and every old URL redirects" is. A final check that counts products and samples redirects catches a plan that was followed perfectly and still missed the goal.

> **最后要对照请求来验证，而不是对照计划。** 「所有步骤都完成了」不是目标；「所有商品都已进入新店铺、尺码正确、每个旧 URL 都能重定向」才是。最后做一次检查，清点商品数量并抽查重定向，就能发现那种完美执行了计划、却依然没达成目标的情况。

**Trade-offs.** Planning up front helps the merchant see what will happen and lets you approve risky steps in advance. Re-planning after every step costs tokens and can make the agent wander. A middle path works well: plan coarsely, execute a step, check its outcome, and re-plan only when an outcome differs from what the plan expected.

> **权衡。** 事先规划能让商家看清将要发生什么，也让你可以提前审批有风险的步骤。每一步之后都重新规划会消耗 token，还可能让 Agent 越走越偏。一个效果不错的折中做法是：粗略地规划，执行一步，检查结果，只有当结果与计划预期不同时才重新规划。

</details>

## 2. The help assistant still quotes a return policy that was changed last week, and one that was deleted entirely

**帮助助手仍在引用上周已经修改过的退货政策，甚至还有一条已被彻底删除的政策** · `RAG` · `Medium`

### Question · 题目

Merchant help articles are chunked and embedded into a vector index by a sync job. Last week the support team changed the return window from 14 to 30 days and deleted an outdated article about restocking fees. The assistant now gives both answers depending on the question, and still mentions the restocking fee. The sync job logs "indexed 1 article" for the edit.

> 商家帮助文章由一个同步任务切块、向量化后写入向量索引。上周，客服团队把退货期限从 14 天改成了 30 天，并删除了一篇关于补货费的过时文章。现在助手会根据提问方式给出两种不同的答案，而且仍然会提到补货费。同步任务针对那次修改记录的是「indexed 1 article」。

Explain how the index got into this state and redesign the sync.

> 解释索引是如何变成这样的，并重新设计同步流程。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** An index is a copy of your documents, and a copy is only as good as the process that keeps it in step. Adding new chunks is the easy half. Removing the old ones, on every edit and every delete, is the half that usually goes missing, and the model will quote whatever the index returns.

> **核心思想。** 索引是文档的一份副本，而副本的质量取决于让它保持同步的流程。添加新块是容易的那一半。在每次修改和每次删除时把旧块移除，才是通常被遗漏的那一半；而模型会引用索引返回的任何内容。

**What went wrong.**

> **问题出在哪里。**

- The edit was indexed as new chunks with new IDs. The old chunks saying "14 days" were never removed, so both versions now compete in search.
  > 那次修改被当作新块、用新 ID 写入了索引。写着「14 天」的旧块从来没有被删除，所以两个版本现在在搜索中相互竞争。
- The sync only listened for "article published" events. Deleting an article produced nothing the job acted on, so its chunks stayed forever.
  > 同步任务只监听「文章发布」事件。删除文章不会产生任何该任务会处理的事件，所以它的块永远留在了索引里。
- Events can arrive late or twice, so even a correct handler could re-apply an old version after a new one.
  > 事件可能延迟到达或重复到达，所以即使处理逻辑正确，也可能在新版本之后又应用一次旧版本。

**The fix: treat each article as a unit with a version.**

> **修复方法：把每篇文章作为一个带版本号的整体来处理。**

```go
// apply replaces every chunk of an article, or removes them all.
// Events can arrive late or twice, so older versions are ignored.
func apply(ix Index, seen map[string]int64, e ArticleEvent, chunk func(string) []string) error {
	if e.Version <= seen[e.DocID] {
		return nil // stale or duplicate event
	}
	if err := ix.DeleteByDoc(e.DocID); err != nil {
		return err
	}
	if !e.Deleted && e.Published {
		var cs []Chunk
		for _, t := range chunk(e.Body) {
			cs = append(cs, Chunk{DocID: e.DocID, Version: e.Version, Text: t})
		}
		if err := ix.Upsert(cs); err != nil {
			return err
		}
	}
	seen[e.DocID] = e.Version
	return nil
}
```

- Every chunk carries its article ID and version. An update deletes all chunks of the article and writes the new ones; a delete or unpublish removes them all.
  > 每个块都带有所属文章的 ID 和版本号。更新时删除这篇文章的所有块并写入新块；删除或取消发布时则把它们全部移除。
- Ignore events whose version is not newer than the one already applied, so late and duplicate events are harmless. In a local run, a late version 1 arriving after version 2 changed nothing.
  > 忽略版本号不比已应用版本更新的事件，这样延迟和重复的事件就不会造成影响。在本地运行中，版本 1 在版本 2 之后迟到，没有改变任何东西。
- Run a nightly reconciliation that compares the set of article IDs and versions in the source with the index, and fixes any difference. Events get lost; a full comparison catches what they miss.
  > 每晚运行一次对账，比较源系统和索引中的文章 ID 与版本集合，并修复任何差异。事件会丢失；全量比对能找回它们漏掉的东西。

**At query time, too.** Filter by status and region when searching, and pass the article's last-updated date with each retrieved chunk, so the model can say "as of November 18" and prefer the newer source when two disagree.

> **查询时也要处理。** 搜索时按状态和地区过滤，并在每个检索到的块上附带文章的最后更新日期，这样模型可以说「截至 11 月 18 日」，并在两个来源冲突时优先采用较新的那个。

**Trade-offs.** Re-chunking a whole article on every small edit costs more embedding calls than diffing chunks, but it is simple and always correct. Hard deletes lose history; if you need to answer "what was the policy in October?", keep old versions in a separate archive that the assistant does not search by default.

> **权衡。** 每次小改动都对整篇文章重新切块，比逐块对比需要更多的向量化调用，但它简单，而且总是正确的。硬删除会丢失历史；如果你需要回答「10 月份的政策是什么？」，就把旧版本放在一个助手默认不会搜索的单独归档里。

</details>

## 3. Three overlapping catalog tools, search_products, list_products and get_catalog, give the agent different answers to the same question

**三个功能重叠的商品工具 search_products、list_products 和 get_catalog，让 Agent 对同一个问题给出不同的答案** · `Tools & MCP` · `Hard`

### Question · 题目

The catalog agent's tools were added by three teams over a year. `search_products` does keyword search but only over active products. `list_products` pages through everything, 50 at a time, including drafts. `get_catalog` returns the whole catalog as one large JSON blob. Asked "how many products are out of stock?", the agent sometimes uses one tool and sometimes another, and the answers differ. On large stores, `get_catalog` fills the context and the turn fails.

> 商品 Agent 的工具是三个团队在一年里陆续加上的。`search_products` 做关键词搜索，但只覆盖在售商品。`list_products` 每次 50 个地翻页遍历所有商品，包括草稿。`get_catalog` 把整个商品目录作为一个巨大的 JSON 一次性返回。当被问到「有多少商品缺货？」时，Agent 有时用这个工具、有时用那个，答案也各不相同。在大店铺上，`get_catalog` 会塞满上下文，导致这一轮失败。

Redesign the tool surface.

> 重新设计这组工具。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The model chooses tools by reading their names and descriptions. Three tools that seem to do the same thing, but quietly differ in scope, turn every question into a guess, and each guess gives a different, confidently stated answer. Design tools around the questions the agent must answer, with one obvious tool per kind of question.

> **核心思想。** 模型是通过阅读名称和描述来选择工具的。三个看起来功能相同、实际范围却悄悄不同的工具，会把每个问题都变成一次猜测，而每次猜测都会给出一个不同的、语气笃定的答案。要围绕 Agent 必须回答的问题来设计工具，每类问题对应一个显而易见的工具。

**What is wrong.**

> **问题在哪里。**

- Hidden differences: "active only" and "includes drafts" are not in the names, so the model cannot know the results are not comparable.
  > 隐藏的差异：「只含在售」和「包含草稿」并没有体现在名称里，所以模型无法知道结果彼此不可比。
- A data-dump tool: `get_catalog` puts the work of filtering into the context window. Narrow accessors with filters and limits are the better shape for agents.
  > 一个倾倒数据的工具：`get_catalog` 把过滤的工作推给了上下文窗口。带过滤条件和数量上限的窄接口，才是更适合 Agent 的形式。
- A counting question answered by reading pages. The agent should not count 40,000 products in its head.
  > 一个计数问题却要靠逐页阅读来回答。Agent 不应该在脑子里数 4 万个商品。

**The redesign: one search tool with explicit filters, plus an aggregate tool.**

> **重新设计：一个带显式过滤条件的搜索工具，外加一个聚合工具。**

```json
{
  "name": "search_products",
  "description": "Find products in the merchant's catalog. Use this for any question about which products exist, their stock, price or status. Filter with the fields below instead of fetching everything. Returns at most `limit` products with product_id, title, status, price and total_count. Not for orders or ads.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query":      {"type": "string", "description": "Words to match in title, SKU or tags; empty means all"},
      "status":     {"type": "string", "enum": ["active", "draft", "archived", "any"]},
      "collection": {"type": "string", "description": "Collection ID, if the merchant named one"},
      "limit":      {"type": "integer", "description": "1 to 100"},
      "cursor":     {"type": "string", "description": "From the previous result, for the next page"}
    },
    "required": ["query", "status"],
    "additionalProperties": false
  }
}
```

- Make scope a parameter, not a property of the tool name. `status` is required, so the model must say whether it means active products or all of them.
  > 把范围做成参数，而不是工具名的隐含属性。`status` 是必填项，所以模型必须说明它指的是在售商品还是全部商品。
- Return `total_count` with every page, and add `count_products(filters)` for questions that only need a number. Counting belongs in the database.
  > 每一页都返回 `total_count`，并为只需要一个数字的问题增加 `count_products(filters)`。计数应该在数据库里完成。
- Write descriptions that say when to use the tool and when not to, and turn on strict tool use so the inputs always match the schema.
  > 在描述里写清什么时候用这个工具、什么时候不用，并开启严格工具调用，确保输入始终符合 schema。
- Retire the old tools rather than keeping them "for compatibility". Every extra tool is another wrong choice the model can make.
  > 下线旧工具，而不是「为了兼容」继续保留。每多一个工具，模型就多一个可能做错的选择。

**Measure tool choice.** Build a small eval of real questions with the expected tool and filters, and run it whenever a tool is added or renamed. When the tool set grows large, tool search loads only the relevant schemas instead of all of them.

> **度量工具选择。** 用真实问题建一个小型评测，标注期望使用的工具和过滤条件；每次新增或重命名工具时都运行一遍。当工具集变得很大时，可以用工具搜索只加载相关的 schema，而不是全部加载。

**Trade-offs.** One general tool with many parameters can be harder for the model to fill in than two specific ones, so keep parameters few and well described, and split tools when their questions are truly different, such as products versus orders. Changing tools also changes the cached prompt prefix, so roll the new set out to new conversations.

> **权衡。** 一个参数很多的通用工具，可能比两个专用工具更难让模型正确填写，所以要让参数少而清楚；当两类问题确实不同时（比如商品和订单），就拆成不同的工具。修改工具也会改变缓存的提示词前缀，所以要把新工具集只推给新对话。

</details>

## 4. During a Claude API outage, the team flips the merchant assistant to Amazon Bedrock, and web search, file uploads and nightly batches stop working

**Claude API 故障期间，团队把商家助手切换到了 Amazon Bedrock，结果网页搜索、文件上传和夜间批处理都不能用了** · `Production` · `Hard`

### Question · 题目

The merchant assistant runs on the Claude API. After an incident, leadership asked for a backup, so the team added Amazon Bedrock and a switch that sends all traffic there. The first real failover went badly: the research feature failed because web search was missing, uploaded spreadsheets could not be read, the nightly product-description batch did not run, and many requests failed immediately because of the model name.

> 商家助手运行在 Claude API 上。一次事故之后，管理层要求准备备用方案，于是团队接入了 Amazon Bedrock，并做了一个能把所有流量切过去的开关。第一次真正的故障切换很不顺利：调研功能因为没有网页搜索而失败，上传的表格读不了，夜间的商品描述批处理没有运行，还有很多请求因为模型名称问题直接失败。

Design a failover that works.

> 设计一个真正可用的故障切换方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Two platforms that serve the same models are not the same product. Features, endpoints, model naming and client setup differ, so failover is a per-feature decision, not one switch. Plan what each feature does on the backup before you need it, and test it regularly.

> **核心思想。** 两个提供相同模型的平台并不是同一个产品。功能、接口、模型命名和客户端配置都有差异，所以故障切换是一个逐功能的决定，而不是一个开关。在需要之前就规划好每个功能在备用平台上怎么运作，并定期测试。

**Why it broke, per the platform availability table:**

> **按照平台功能对照表，为什么会坏掉：**

- Web search, web fetch, code execution, the Files API, Message Batches, the MCP connector, server-side refusal fallbacks and Managed Agents are not available on Bedrock.
  > 网页搜索、网页抓取、代码执行、Files API、Message Batches、MCP 连接器、服务端拒答回退以及 Managed Agents，在 Bedrock 上都不可用。
- Bedrock model IDs take an `anthropic.` prefix, such as `anthropic.claude-opus-5-5`, and the client needs a region. Sending the first-party ID fails at once.
  > Bedrock 的模型 ID 要加 `anthropic.` 前缀，比如 `anthropic.claude-opus-5-5`，客户端还需要指定区域。直接发送第一方 ID 会立刻失败。
- Use the platform's own client, the Mantle client in the SDKs, not the first-party client with a different base URL.
  > 要使用该平台自己的客户端（SDK 里的 Mantle 客户端），而不是换了 base URL 的第一方客户端。

**The design: route by capability, and degrade on purpose.**

> **设计：按能力路由，并有意识地降级。**

```go
type Platform struct {
	Name     string
	Model    string          // model ID as this platform spells it
	Features map[string]bool // from the platform availability table, reviewed on every change
}

var claudeAPI = Platform{"claude-api", "claude-opus-5-5", map[string]bool{
	"web_search": true, "code_execution": true, "files_api": true, "batches": true, "fallbacks": true}}
var bedrock = Platform{"bedrock", "anthropic.claude-opus-5-5", map[string]bool{
	"web_search": false, "code_execution": false, "files_api": false, "batches": false, "fallbacks": false}}

// route picks a platform for a request that needs the given features.
// A request is only failed over when the backup can serve all of them.
func route(primaryUp bool, needs []string) (Platform, error) {
	if primaryUp {
		return claudeAPI, nil
	}
	for _, f := range needs {
		if !bedrock.Features[f] {
			return Platform{}, fmt.Errorf("cannot fail over: %s is not available on %s", f, bedrock.Name)
		}
	}
	return bedrock, nil
}
```

- Classify each feature: fails over fully (plain chat and client tools), degrades (research answers without web search, with a visible note), or waits (batches and uploads queue until the primary is back).
  > 给每个功能分类：完全切换（普通对话和客户端工具）、降级运行（调研功能不带网页搜索作答，并给出明显提示），或者等待（批处理和上传排队，直到主平台恢复）。
- Keep the feature table in code and review it against the availability table on every change, since it moves faster than your memory of it.
  > 把功能对照表放在代码里，每次变更时都对照官方的功能表复核，因为它的变化比你的记忆更快。
- Expect a cold cache and different rate limits on the backup, and possibly thinking blocks that the other platform's model cannot read; the API drops those, so long conversations continue with less context of earlier reasoning.
  > 预计备用平台上缓存是冷的、速率限制不同，而且之前的 thinking 块可能无法被另一个平台上的模型读取；API 会丢弃这些块，所以长对话会在缺少早期推理上下文的情况下继续。

**Make it real.** Decide who flips the switch and on what signal, keep credentials and quotas for the backup ready, and run a game day every quarter that sends a slice of real traffic through the backup. A failover path that is never exercised is broken in ways nobody knows yet.

> **让它真正可用。** 确定由谁、根据什么信号来切换；备用平台的凭据和配额要时刻就绪；每个季度做一次演练，把一部分真实流量导到备用平台。一条从未被走过的切换路径，一定存在大家还不知道的问题。

**Alternatives and trade-offs.** Claude Platform on AWS is Anthropic-operated with same-day API parity, so feature gaps are smaller there, but check whether it is an independent failure domain for the outage you are planning for rather than assuming. A second platform also means a second contract, monitoring and data-processing review, so size the backup to the features that must survive an outage.

> **替代方案与权衡。** Claude Platform on AWS 由 Anthropic 运营，API 当天同步上线，所以功能差距更小；但要核实它对于你所防范的故障来说是否是一个独立的故障域，而不是想当然。第二个平台还意味着第二份合同、第二套监控和数据处理评审，所以备用方案的规模应当只覆盖那些在故障期间必须保住的功能。

</details>

## 5. A four-agent ad-creative pipeline lets one stage's bad output flow silently downstream: designing contracts between agents

**一个由四个 Agent 组成的广告创意流水线，让某一环节的错误输出悄无声息地流向下游：设计 Agent 之间的契约** · `Multi-agent` · `Senior`

### Question · 题目

Ad creatives are produced by a pipeline of agents: a researcher reads the product page and supplier sites, a copywriter writes headlines and body text, a compliance agent checks claims, and an uploader pushes ads to Meta. Each stage passes free text to the next. Last month, ads went live claiming "eco-friendly", which no source supported, and one creative contained a sentence copied from a supplier page that told the copywriter to mention a competitor. Nobody could say which stage was at fault.

> 广告创意由一条 Agent 流水线生成：调研员读取商品页和供应商网站，文案撰写标题和正文，合规 Agent 检查宣传用语，上传员把广告推送到 Meta。每个环节都把自由文本传给下一个环节。上个月，有广告在上线时宣称「环保」，而这没有任何来源支持；还有一条创意里包含一句从供应商页面复制来的话，那句话要求文案提到一个竞争对手。没有人能说清是哪个环节出了错。

Redesign how the agents hand work to each other.

> 重新设计这些 Agent 之间交接工作的方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** In a pipeline of agents, each handoff is an interface, and free text is an interface with no contract. Errors compound, injected text rides along as if it were instructions, and when something goes wrong there is no record of what each stage claimed. Treat every handoff like an API between services: a schema, validation in code, and provenance.

> **核心思想。** 在 Agent 流水线里，每一次交接都是一个接口，而自由文本是一个没有契约的接口。错误会层层累积，被注入的文本会像指令一样一路传下去；出问题时，也没有任何记录说明每个环节声称了什么。要把每次交接都当作服务之间的 API 来对待：有 schema，有代码层面的校验，有来源追溯。

**Give each handoff a schema and validate it in code.** Ask each stage for structured output and check it before the next stage starts:

> **给每次交接一个 schema，并在代码里校验。** 要求每个环节输出结构化结果，并在下一个环节开始之前进行检查：

```go
// CopyDraft is the contract between the copywriter and the compliance stage.
type CopyDraft struct {
	ProductID  string   `json:"product_id"`
	Headline   string   `json:"headline"`
	Body       string   `json:"body"`
	ClaimsUsed []string `json:"claims_used"` // must come from the approved claims list
	SourceURLs []string `json:"source_urls"`
}

func (d CopyDraft) Validate(approved map[string]bool, maxHeadline int) error {
	var errs []error
	if d.ProductID == "" {
		errs = append(errs, errors.New("missing product_id"))
	}
	if n := len([]rune(d.Headline)); n == 0 || n > maxHeadline {
		errs = append(errs, fmt.Errorf("headline length %d outside 1..%d", n, maxHeadline))
	}
	for _, c := range d.ClaimsUsed {
		if !approved[c] {
			errs = append(errs, fmt.Errorf("claim %q is not on the approved list", c))
		}
	}
	for _, u := range d.SourceURLs {
		if p, err := url.Parse(u); err != nil || p.Scheme != "https" {
			errs = append(errs, fmt.Errorf("bad source url %q", u))
		}
	}
	return errors.Join(errs...)
}
```

- Claims must come from an approved list built from verified product data, so "eco-friendly" fails validation instead of reaching compliance as a suggestion. In a local run, that draft was rejected with exactly that reason.
  > 宣传用语必须来自基于已核实商品数据建立的白名单，这样「环保」会在校验时被拒，而不是作为一个建议流到合规环节。在本地运行中，那份草稿正是因为这个原因被拒绝的。
- Structured outputs guarantee the shape, not the truth. A refusal or a response cut off at `max_tokens` may not match the schema, so check the stop reason as well as the fields.
  > 结构化输出保证的是格式，而不是内容的真实性。拒答或在 `max_tokens` 处被截断的响应可能不符合 schema，所以除了检查字段，还要检查停止原因。
- A validation failure retries that stage with the specific errors, a bounded number of times, and then stops the item for a human. It never passes a broken draft along.
  > 校验失败时，带上具体错误重试这个环节，次数有上限，之后就把这一项交给人工处理。绝不把有问题的草稿往下传。

**Treat upstream text as data, not instructions.** The researcher read supplier pages, so its output may contain text written by strangers. Pass source material in clearly marked fields, tell each stage that those fields are untrusted content, and give the copywriter only the facts it needs rather than raw page text. The compliance stage must check against the product data and the source URLs, not against the copywriter's own explanation.

> **把上游文本当作数据，而不是指令。** 调研员读过供应商页面，所以它的输出里可能包含陌生人写的文字。用明确标注的字段传递来源材料，告诉每个环节这些字段是不可信内容，并且只给文案提供它需要的事实，而不是原始页面文本。合规环节必须对照商品数据和来源 URL 来检查，而不是对照文案自己的解释。

**Keep provenance end to end.** Store each stage's input, output, model and version with the creative ID. Then "which stage introduced this claim?" is a query, and you can evaluate stages separately: the researcher on factual accuracy, the copywriter on staying within approved claims, compliance on catching planted violations.

> **端到端保留来源记录。** 把每个环节的输入、输出、模型和版本，与创意 ID 一起保存。这样「是哪个环节引入了这条宣传语？」就只需要一次查询，你也可以分别评估各个环节：调研员看事实准确性，文案看是否守在白名单之内，合规看能否抓住事先埋入的违规内容。

**Trade-offs.** Schemas make stages less flexible and add code to maintain, and too many stages add latency and cost without adding quality. Ask whether each stage earns its place: research and copywriting might be one agent with a validator after it, while compliance should stay separate, with deterministic checks first and a model only for judgment calls. Keep the final upload behind a code-enforced gate, never behind another agent's say-so.

> **权衡。** schema 会让各环节变得不那么灵活，也多了需要维护的代码；环节过多会增加延迟和成本，却未必提升质量。要问每个环节是否值得存在：调研和文案也许可以合并成一个 Agent，后面接一个校验器；而合规应当保持独立，先做确定性检查，只在需要判断的地方才用模型。最后的上传要放在由代码强制执行的关卡后面，绝不能只凭另一个 Agent 的一句话就放行。

</details>
