## 1. The copywriting assistant keeps using the formal German "Sie" a merchant asked for in April, ignores today's request for casual copy, and then overwrites the saved preference with a guess

**文案助手一直沿用商家 4 月要求的德语敬称「Sie」，无视今天要用随意语气的要求，后来又用一个猜测覆盖了已保存的偏好** · `Context & Memory` · `Medium`

### Question · 题目

The ad-copy assistant has long-term memory. In April a merchant said "always address German customers formally", and the assistant saved it. Today the merchant asked for casual copy for a TikTok campaign aimed at students; the assistant still wrote formal copy, citing the saved rule. After the merchant complained twice, the assistant updated memory to "merchant prefers casual German", and next week's formal newsletter came out casual.

> 广告文案助手有长期记忆。4 月时，一位商家说「对德国顾客一律使用敬称」，助手把它保存了下来。今天，这位商家为一个面向学生的 TikTok 广告系列要求写随意风格的文案；助手却依然写成了正式语气，理由是那条已保存的规则。商家抱怨了两次之后，助手把记忆改成了「商家偏好随意的德语」，结果下周正式的新闻邮件也变成了随意风格。

What is wrong with how this memory works, and how would you fix it?

> 这套记忆机制哪里出了问题？你会怎样修复？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A memory is an old instruction with a scope. The merchant's words in this conversation are the newest and most specific instruction, so they win for this task. Memory should fill gaps, not overrule the person who is talking to you, and changing a standing preference is a decision the merchant makes, not one the agent infers.

> **核心思想。** 一条记忆，就是一条带有适用范围的旧指令。商家在当前对话里说的话，是最新、也最具体的指令，所以在这个任务上应当以它为准。记忆应当用来填补空白，而不是推翻正在和你说话的人；修改一条长期偏好，是商家做的决定，而不是 Agent 推断出来的结论。

**Two bugs.**

> **两个 bug。**

- **Wrong precedence.** The memory was injected as a rule ("always"), with no date and no scope, and the prompt never said what to do when the merchant contradicts it. The model treated it as a standing order.
  > **优先级错误。** 那条记忆是以规则的形式（「一律」）注入的，没有日期也没有适用范围，提示词也从未说明商家与之矛盾时该怎么办。模型于是把它当成了一道长期命令。
- **Wrong write.** One campaign's request was generalized into a permanent preference, replacing the old one. A task-level instruction overwrote an account-level rule, and nobody confirmed it.
  > **写入错误。** 一个广告系列的要求被泛化成了永久偏好，并替换了旧的那条。一个任务级的指令覆盖了账户级的规则，而且没有任何人确认过。

**Store memories with scope and source, and resolve them in code:**

> **保存记忆时带上适用范围和来源，并在代码里解析它们：**

```go
// resolve picks the value for key: an instruction in this conversation wins,
// then task-scoped notes, then standing merchant preferences, then guesses.
// It also says where the value came from, so the reply can mention it.
func resolve(key string, prefs []Pref, thisChat map[string]string) (string, string) {
	if v, ok := thisChat[key]; ok {
		return v, "this conversation"
	}
	rank := map[string]int{"task": 0, "always": 1, "inferred": 2}
	var c []Pref
	for _, p := range prefs {
		if p.Key == key {
			c = append(c, p)
		}
	}
	if len(c) == 0 {
		return "", "none"
	}
	sort.Slice(c, func(i, j int) bool {
		if rank[c[i].Scope] != rank[c[j].Scope] {
			return rank[c[i].Scope] < rank[c[j].Scope]
		}
		return c[i].SetAt.After(c[j].SetAt) // newer first within a scope
	})
	p := c[0]
	return p.Value, fmt.Sprintf("%s preference saved %s", p.Scope, p.SetAt.Format("2006-01-02"))
}
```

- In a local run, the saved formal preference applied by default, today's casual request won in this conversation, and an agent's guess was used only when nothing else existed.
  > 在一次本地运行中，默认情况下使用已保存的正式偏好；在当前对话里，今天的随意语气要求优先；只有在没有其他依据时，才会使用 Agent 的猜测。
- Pass the resolved value to the model with its source, such as "formal German (saved April 2)", so it can say why it chose it and the merchant can correct it.
  > 把解析出的值连同来源一起交给模型，比如「正式德语（4 月 2 日保存）」，这样模型能说明为什么这么选，商家也能纠正。

**Writes need rules too.** Save task-scoped notes freely, but change an "always" preference only when the merchant states one, and confirm it in plain words: "Should I use casual German for all campaigns from now on, or just this one?" Keep the old value with its date instead of deleting it, so a mistake can be undone.

> **写入也需要规则。** 任务级的笔记可以随意保存，但只有商家明确表达时，才修改「一律」类的偏好，并且要用平实的话确认：「以后所有广告系列都用随意的德语，还是只有这一个？」保留旧值及其日期，而不是直接删除，这样出错时可以撤销。

**Trade-offs.** Asking for confirmation adds a turn, so ask only when a standing preference would change. Scopes such as campaign or channel make resolution more precise but harder to explain; start with three and show merchants a page where they can see and edit what the assistant remembers.

> **权衡。** 请求确认会多一轮对话，所以只在长期偏好要发生变化时才询问。按广告系列、渠道这样细分的范围，能让解析更精确，但也更难解释；先从三种范围开始，并给商家一个页面，让他们能查看和编辑助手记住的内容。

</details>

## 2. AI-written product descriptions are published as HTML, and one copied an image tag with an onerror script from a supplier's page onto the storefront

**AI 撰写的商品描述以 HTML 形式发布，其中一条把供应商页面上带 onerror 脚本的图片标签照搬到了店铺前台** · `Safety & Security` · `Hard`

### Question · 题目

The catalog agent reads a supplier's product page and writes a description for the merchant's storefront. To keep formatting, the team asks the model for HTML and inserts it into the product page as is. A security researcher reported that one jacket's description contained `<img src=x onerror=...>` that sent shoppers' cookies to another domain. The text came from the supplier's page; the model copied it into a feature list.

> 目录 Agent 读取供应商的商品页面，并为商家的店铺前台撰写描述。为了保留格式，团队让模型输出 HTML，并原样插入商品页面。一位安全研究员报告说，有一件夹克的描述里包含 `<img src=x onerror=...>`，会把顾客的 cookie 发送到另一个域名。这段文字来自供应商的页面；模型把它抄进了一个功能列表里。

Explain the vulnerability and design the fix.

> 解释这个漏洞，并设计修复方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Model output is untrusted input, exactly like text from a form. The model read attacker-controlled content, so anything it writes may contain attacker-controlled content. The bug is not that the model copied a tag; it is that the storefront executed whatever the model produced.

> **核心思想。** 模型的输出是不可信的输入，和表单里提交的文字完全一样。模型读取了攻击者控制的内容，所以它写出的任何东西都可能包含攻击者控制的内容。bug 并不在于模型抄了一个标签，而在于店铺前台会执行模型产出的任何东西。

**Why prompts cannot fix it.** "Never output scripts" lowers the rate but cannot guarantee zero, and an attacker can hide payloads that look harmless to a reader, such as event handlers or `javascript:` links. This is a classic stored cross-site scripting bug with a new source. A second model that screens the output has the same weakness: a probabilistic filter in front of a page that executes whatever reaches it.

> **为什么提示词修不好它。** 「绝不输出脚本」能降低发生的频率，却无法保证为零；而且攻击者可以把载荷藏在读者看来无害的地方，比如事件处理属性或 `javascript:` 链接。这是一个经典的存储型跨站脚本漏洞，只是来源换了。再加一个模型来审查输出，也有同样的弱点：它是一个概率性的过滤器，挡在一个会执行一切到达内容的页面前面。

**Fix one: never let the model write markup.** Ask for structured text with structured outputs (`output_config.format`) and let your template produce the HTML. Go's `html/template` escapes text by context:

> **修复一：绝不让模型编写标记。** 通过结构化输出（`output_config.format`）要求模型给出结构化的文本，再由你自己的模板生成 HTML。Go 的 `html/template` 会根据上下文对文本做转义：

```go
// Description is what the model returns (via structured outputs): text only,
// no HTML. The storefront decides the markup, and the template escapes text.
type Description struct {
	Intro    string   `json:"intro"`
	Features []string `json:"features"`
	Care     string   `json:"care"`
}

var page = template.Must(template.New("d").Parse(
	`<p>{{.Intro}}</p>
<ul>{{range .Features}}<li>{{.}}</li>{{end}}</ul>
<p class="care">{{.Care}}</p>
`))
```

In a local run, the copied tag was rendered as visible text, `&lt;img src=x onerror=...&gt;`, and `&` in the care line became `&amp;`. Nothing the model writes can become a tag.

> 在一次本地运行中，被抄进来的标签以可见文字的形式渲染成 `&lt;img src=x onerror=...&gt;`，护理说明里的 `&` 也变成了 `&amp;`。模型写的任何东西都无法变成标签。

**Fix two: layers for what must stay rich.** If merchants need bold text or links, accept a small markup subset and convert it with an allowlist sanitizer on the server: a few tags, no attributes except checked `href` values with `https` only. Add a Content Security Policy on the storefront that forbids inline scripts, so a missed payload still does not run.

> **修复二：对必须保留富文本的部分做多层防护。** 如果商家需要粗体或链接，就只接受一个很小的标记子集，并在服务端用白名单净化器转换：只允许少数几个标签，除了经过检查、且只允许 `https` 的 `href` 之外不允许任何属性。再在店铺前台加上禁止内联脚本的内容安全策略（CSP），这样即使有漏网的载荷也不会执行。

**Clean up and detect.**

> **清理与检测。**

- Scan every stored description for tags and `javascript:` URLs, re-render them through the new path, and check which shoppers loaded the affected pages.
  > 扫描所有已存储的描述，查找标签和 `javascript:` URL，用新链路重新渲染它们，并排查哪些顾客加载过受影响的页面。
- Treat the supplier page as hostile input to the agent too: it is also a prompt-injection channel, and text there may try to change what the agent does, not just what it writes.
  > 也要把供应商页面视为对 Agent 有敌意的输入：它同样是一个提示词注入的渠道，那里的文字可能试图改变 Agent 的行为，而不仅仅是它写出的内容。
- Add eval cases with poisoned supplier pages and assert that rendered output contains no executable markup.
  > 加入带有恶意内容的供应商页面作为评测用例，并断言渲染后的输出不包含任何可执行的标记。

**Trade-offs.** Structured fields limit layout freedom; most product pages need only paragraphs and bullet lists. A strict CSP can break third-party widgets on the storefront, so roll it out in report-only mode first.

> **权衡。** 结构化字段限制了排版的自由度；不过大多数商品页面只需要段落和项目列表。严格的 CSP 可能会破坏店铺前台上的第三方组件，所以先以仅报告模式上线。

</details>

## 3. The catalog-export tool takes eight minutes, the tool call times out after 60 seconds, and the agent starts the same export three more times

**目录导出工具需要 8 分钟，工具调用在 60 秒后超时，于是 Agent 又把同一个导出任务启动了三次** · `Tools & MCP` · `Medium`

### Question · 题目

Merchants ask the assistant to "export my catalog for Google". The `export_catalog` tool calls an internal API that builds the feed file and returns its URL. For large stores that takes about eight minutes, but the tool handler waits only 60 seconds and then returns "Error: timeout". The model, seeing an error, calls the tool again. The export service never stopped the first job, so the largest merchants got four exports running at once and the feed service slowed for everyone.

> 商家会让助手「把我的商品目录导出给 Google」。`export_catalog` 工具会调用一个内部 API，由它生成 feed 文件并返回文件的 URL。对于大店铺，这大约需要 8 分钟，可工具的处理程序只等 60 秒，然后就返回「Error: timeout」。模型看到报错，就再次调用工具。导出服务从未停掉第一个任务，于是最大的那些商家同时有四个导出在跑，feed 服务对所有人都变慢了。

Redesign the tool.

> 重新设计这个工具。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A tool call should return quickly. Long work becomes a job: one tool starts it and returns a job ID at once, another reports its status. Starting must be idempotent, so a repeated call finds the running job instead of creating a second one.

> **核心思想。** 一次工具调用应当很快返回。耗时的工作要变成一个任务：一个工具负责启动它，并立即返回任务 ID；另一个工具负责报告它的状态。启动必须是幂等的，这样重复调用时会找到正在运行的那个任务，而不是再创建一个。

**What went wrong.**

> **出了什么问题。**

- The timeout was reported as a failure. It was not: the outcome was unknown, and the work was still running. The model reasonably retried a call that looked failed.
  > 超时被当作失败报告了出去。可它并不是失败：结果是未知的，工作仍在进行。模型合情合理地重试了一个看起来失败了的调用。
- Nothing tied the second call to the first, so every retry started new work on the server.
  > 没有任何东西把第二次调用和第一次关联起来，所以每次重试都会在服务端启动新的工作。
- The tool description never said that exports take minutes, so the model had no reason to expect a wait or to tell the merchant about one.
  > 工具描述从未提到导出需要几分钟，所以模型没有理由预料到要等待，也就不会告诉商家。

**The redesign: two tools and a job key.**

> **重新设计：两个工具，外加一个任务键。**

```go
// StartExport returns at once. The job ID is derived from the merchant and the
// export parameters, so calling it again while a job runs returns the same job
// instead of starting a duplicate.
func (j *Jobs) StartExport(merchant, format string, now time.Time) string {
	sum := sha256.Sum256([]byte(merchant + "|" + format))
	id := "exp_" + hex.EncodeToString(sum[:6])
	j.mu.Lock()
	defer j.mu.Unlock()
	if job, ok := j.byID[id]; ok && job.Status == "running" {
		return result(job, "An export with these settings is already running. Do not start another; check its status.")
	}
	job := &Job{ID: id, Status: "running", Total: 48000, StartedAt: now}
	j.byID[id] = job
	return result(job, "Started. Exports of this size usually take several minutes. Tell the merchant it is running; check status before your final answer.")
}
```

- In a local run, two calls two minutes apart returned the same job ID, and the second told the model not to start another.
  > 在一次本地运行中，相隔两分钟的两次调用返回了同一个任务 ID，第二次还告诉模型不要再启动新的任务。
- `get_export_status` returns progress, such as 12,000 of 48,000 products, and the file URL when done. Describe in the tool description that exports take minutes, so the model tells the merchant instead of polling in a tight loop.
  > `get_export_status` 返回进度，比如 48,000 个商品中已完成 12,000 个，完成后再返回文件 URL。在工具描述里写明导出需要几分钟，这样模型会告知商家，而不是在一个紧凑的循环里反复轮询。
- Send real failures as `is_error: true` with a reason the model can act on. An unknown outcome is not a failure; say so in the result.
  > 真正的失败要以 `is_error: true` 返回，并附上模型可以据此采取行动的原因。结果未知不等于失败；要在结果里如实说明。

**Finishing the conversation.** For an interactive chat, the agent can end its turn with "your export is running, I will post the link here", and the harness adds a message to the conversation when the job finishes. For an unattended run, let the harness wait on the job and return one result, rather than spending model turns on polling.

> **把对话收尾。** 在交互式聊天中，Agent 可以用「您的导出正在进行，完成后我会把链接发在这里」来结束本轮，任务完成时再由框架往对话里追加一条消息。在无人值守的运行中，让框架去等待任务、最后返回一个结果，而不是把模型的轮次花在轮询上。

**Trade-offs.** The job key decides what counts as "the same export": include the parameters that change the file, and expire the key when the job finishes, so a later export starts fresh. Jobs need storage, cleanup and a way to cancel.

> **权衡。** 任务键决定了什么算作「同一个导出」：要把会改变文件的参数都纳入其中，并在任务结束时让键失效，这样之后的导出会重新开始。任务还需要存储、清理，以及取消的手段。

</details>

## 4. "Does this jacket run small?" The assistant quotes three angry reviews, while 700 of 800 reviewers say the fit is true to size

**「这件夹克偏小吗？」助手引用了三条愤怒的评论，而 800 位评论者中有 700 位说尺码标准** · `RAG` · `Hard`

### Question · 题目

The shopping assistant answers product questions with retrieval over customer reviews: it embeds the question, fetches the five most similar reviews and answers from them. Asked whether a jacket runs small, it said "several customers found it too tight, consider sizing up" and quoted three reviews. Returns for that jacket rose after the assistant launched. A manual check found that about 90% of reviews that mention fit call it true to size.

> 购物助手通过对顾客评论做检索来回答商品问题：它对问题做嵌入，取出最相似的 5 条评论，再据此作答。被问到一件夹克是否偏小时，它说「好几位顾客觉得太紧了，建议选大一码」，并引用了三条评论。助手上线后，这件夹克的退货增加了。人工核查发现，在提到尺码的评论中，约 90% 说尺码标准。

Explain why retrieval failed here and design a better approach.

> 解释这里的检索为什么失败，并设计一个更好的方法。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** "Does it run small?" is a question about a distribution, not about a passage. Top-k retrieval returns the reviews most similar to the question, and reviews that talk about tightness are the most similar to a question about tightness. The answer needs counting across all reviews, so do the counting before the question is asked.

> **核心思想。** 「偏小吗？」问的是一个分布，而不是某一段文字。Top-k 检索返回的是与问题最相似的评论，而谈论「紧」的评论，正是与一个关于「紧」的问题最相似的评论。这个答案需要对所有评论做统计，所以要在问题被提出之前就完成统计。

**Why the answer was skewed.**

> **答案为什么会有偏差。**

- Similarity favors the minority: "too tight in the shoulders" matches "does it run small" better than "fits as expected".
  > 相似度偏向了少数派：「肩部太紧」比「尺码和预期一样」更匹配「偏小吗」这个问题。
- Five reviews out of 800 cannot represent a rate, and the model, seeing only complaints, reasonably concluded the jacket runs small.
  > 800 条中的 5 条代表不了一个比例；而模型只看到了抱怨，得出夹克偏小的结论也就顺理成章。

**Extract once, aggregate on demand.** Run an offline pass that labels each review for the attributes shoppers ask about: fit, size bought, material feel, color accuracy. Use structured outputs so each label is one of a fixed set, plus a quote that justifies it. Message Batches suit this work: it is not urgent, runs asynchronously at 50% cost, and results arrive in any order, so key each one by `custom_id`, such as the review ID. Then answer from the aggregate:

> **一次抽取，按需聚合。** 跑一遍离线流程，为每条评论标注顾客关心的属性：尺码、所买的码数、材质手感、颜色是否准确。用结构化输出，让每个标签都只能取自一个固定集合，并附上一句作为依据的引文。Message Batches 很适合这项工作：它不着急，异步运行，成本减半；结果的返回顺序不固定，所以要用 `custom_id`（比如评论 ID）来对应每一条。然后根据聚合结果作答：

```go
// fitSummary is what the shopper-facing model receives: the full distribution
// and a few quotes per label, not the five most "similar" reviews.
func fitSummary(rs []Extracted, quotesPer int) string {
	count := map[string]int{}
	quotes := map[string][]string{}
	mentioned := 0
	for _, r := range rs {
		count[r.Fit]++
		if r.Fit == "not_mentioned" {
			continue
		}
		mentioned++
		if len(quotes[r.Fit]) < quotesPer {
			quotes[r.Fit] = append(quotes[r.Fit], fmt.Sprintf("%q (%s, size %s)", r.Quote, r.ReviewID, r.Size))
		}
	}
	name := map[string]string{"true": "true to size", "small": "runs small", "large": "runs large"}
	labels := []string{"true", "small", "large"}
	sort.SliceStable(labels, func(i, j int) bool { return count[labels[i]] > count[labels[j]] })
	var b strings.Builder
	fmt.Fprintf(&b, "%d reviews, %d mention fit.\n", len(rs), mentioned)
	for _, l := range labels {
		fmt.Fprintf(&b, "- %s: %d (%.0f%%), e.g. %s\n", name[l], count[l],
			100*float64(count[l])/float64(mentioned), strings.Join(quotes[l], "; "))
	}
	return b.String()
}
```

- In a local example with 800 reviews, the summary showed 89% true to size, 8% small and 3% large, each with an example quote and the size the reviewer bought. The model now writes "most buyers say it fits true to size; a few with broad shoulders found it tight".
  > 在一个包含 800 条评论的本地示例中，汇总显示 89% 尺码标准、8% 偏小、3% 偏大，每一类都附有一条示例引文和评论者所买的码数。现在模型会写出「大多数买家说尺码标准；少数肩宽的买家觉得偏紧」。
- Keep retrieval for questions that really are about a passage, such as "is it machine washable?", and route by question type.
  > 对于真正关于某段文字的问题，比如「能机洗吗？」，仍然使用检索；按问题类型来分流。

**Keep it honest.** Label new reviews incrementally as they arrive, and show the count behind every claim. Check quotes against the review text in code. Audit a sample of labels by hand each month, because a systematic labeling error becomes a confident wrong statistic.

> **保持诚实。** 新评论一到就增量打标签，并为每个结论展示背后的数量。在代码里核对引文与评论原文是否一致。每个月人工抽查一部分标签，因为系统性的标注错误会变成一个自信满满的错误统计。

**Trade-offs.** Extraction covers only the attributes you chose in advance; a new question type needs a new pass. Reviews are not a random sample of buyers: people who return the item write more often, so present numbers as "of reviewers who mentioned fit".

> **权衡。** 抽取只能覆盖你事先选定的属性；出现新类型的问题时，需要再跑一遍。评论也不是买家的随机样本：退货的人更常写评论，所以要把数字表述为「在提到尺码的评论者中」。

</details>

## 5. Black Friday is three weeks away: capacity planning for the shopper chat agent, from token forecasts and rate limits to what to switch off first

**距离黑五还有三周：为顾客聊天 Agent 做容量规划，从 token 预测、速率限制，到先关掉哪些功能** · `Production` · `Senior`

### Question · 题目

Last Black Friday the shopper chat agent hit rate limits for two hours: shoppers saw errors, and the bulk product-description jobs that ran at the same time made it worse. This year traffic is forecast to be higher, the agent now runs on Claude Opus 5.5, and leadership wants a plan that keeps chat working at peak.

> 去年黑五，顾客聊天 Agent 撞上速率限制长达两个小时：顾客看到了报错，同时在跑的批量商品描述任务又让情况雪上加霜。今年的流量预计会更高，Agent 现在运行在 Claude Opus 5.5 上，管理层希望有一个能让聊天在高峰期正常工作的方案。

Walk through how you would plan capacity and degradation.

> 讲讲你会如何规划容量和降级。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Capacity for an LLM product is measured in tokens per minute, not requests. Forecast the tokens each route uses at peak, compare them with the limits that actually apply, remove load that does not need to be live, and decide in advance what to degrade, in what order, when the forecast is wrong.

> **核心思想。** LLM 产品的容量是用每分钟 token 数来衡量的，而不是请求数。预测每条链路在高峰期使用的 token，把它们和实际适用的限制做比较，移除不需要实时处理的负载，并且事先决定预测出错时降级什么、按什么顺序降级。

**Step one: measure the token profile.** From production usage logs, get per-request uncached input, cache reads and output for each route, then multiply by the forecast peak request rate. Read your tier's limits for Claude Opus 5.5 from the Console; they are a separate pool from Claude Opus 5's, so last year's numbers do not carry over. On the Claude API, cache reads do not count toward input-token rate limits on most models, which makes caching a capacity lever, not only a cost lever:

> **第一步：测量 token 画像。** 根据线上的用量日志，得出每条链路每个请求的未缓存输入、缓存读取和输出 token，再乘以预测的峰值请求速率。从 Console 上查看你所在等级下 Claude Opus 5.5 的限额；它和 Claude Opus 5 的是两个独立的池子，所以去年的数字不能照搬。在 Claude API 上，对大多数模型来说，缓存读取不计入输入 token 的速率限制，这让缓存成为了一个容量杠杆，而不只是成本杠杆：

```go
// load returns the tokens per minute that count against the limits. On the
// Claude API, cache reads do not count toward input-token rate limits on most
// models, so only uncached input is added to ITPM.
func load(ps []Profile) (itpm, otpm float64) {
	for _, p := range ps {
		itpm += p.RequestsPerMin * p.UncachedIn
		otpm += p.RequestsPerMin * p.Out
	}
	return
}
```

With example limits, the forecast peak needed 172% of the input limit. Moving bulk descriptions off peak brought it to 112%, and caching the conversation history brought it to 54%. A peak 50% above forecast still pushed output to 118%, which is what the degradation plan is for.

> 在示例限额下，预测峰值需要输入限额的 172%。把批量描述移出高峰期后降到 112%，再缓存对话历史后降到 54%。即便如此，比预测高出 50% 的峰值仍会把输出推到 118%，这正是降级方案要应对的情况。

**Step two: remove load that does not need to be live.** Product descriptions, review labeling and reports go to Message Batches overnight, at 50% cost. Pause nonessential agent features during the peak window.

> **第二步：移除不需要实时处理的负载。** 商品描述、评论打标签和报表，都放到夜间用 Message Batches 处理，成本减半。在高峰时段暂停非必要的 Agent 功能。

**Step three: a degradation ladder, decided now.**

> **第三步：降级阶梯，现在就定好。**

- Lower effort and set a shorter answer length for chat; measure the quality cost on your eval beforehand.
  > 为聊天降低 effort，并设定更短的回答长度；事先在评测上衡量这样做的质量代价。
- Route simple intents, such as order status, to deterministic code or a smaller model.
  > 把简单的意图，比如查询订单状态，分流给确定性的代码或更小的模型。
- Queue with an honest wait message, then hand off to human support, instead of showing errors.
  > 排队时给出如实的等待提示，再转交人工客服，而不是直接显示报错。

**Step four: control retries.** By default the SDK retries 429s, server errors and connection errors twice. Layered on your own retries and the shopper pressing "send" again, that multiplies load exactly when you have none to spare. Set one retry policy, add a circuit breaker that triggers the ladder, and alert on rate-limit responses before shoppers notice.

> **第四步：控制重试。** SDK 默认会对 429、服务端错误和连接错误重试两次。再叠加上你自己的重试，以及顾客再次点击「发送」，就会恰好在你毫无余量的时候成倍放大负载。只保留一套重试策略，加一个触发降级阶梯的熔断器，并在顾客察觉之前就对速率限制响应发出告警。

**Trade-offs.** Higher limits must be requested well before the peak, and Priority Tier is not available for Claude Opus 5.5, so you cannot buy guaranteed capacity there at the last minute. Every rung of the ladder trades quality for availability; rehearse it in a load test with a small share of real traffic, and write down who decides to step down and back up.

> **权衡。** 更高的限额必须在高峰前很早就申请；而 Claude Opus 5.5 不支持 Priority Tier，所以无法在最后时刻为它购买有保障的容量。降级阶梯的每一级，都是在用质量换可用性；要用一小部分真实流量做压测来演练它，并写清楚由谁决定降级、由谁决定恢复。

</details>
