## 1. A support chat turns into a hard investigation halfway through: raising effort without losing the cache

**一段客服对话在中途变成了一次复杂的排查：在不丢失缓存的前提下提高 effort** · `Agent Loop` · `Hard`

### Question · 题目

A merchant-support agent on Claude Opus 5.5 runs at `low` effort, because most turns are simple ("where is my payout?"). Sometimes a conversation turns into a real investigation, such as why a Google Shopping feed lost half its products, and the low-effort answers become shallow. The team tried raising the top-level `effort` to `high` for the rest of the conversation, but cost went up sharply on those conversations and latency jumped on the very next turn, even though the history had not changed.

> 一个运行在 Claude Opus 5.5 上的商家客服 Agent 使用 `low` effort，因为大多数轮次都很简单（“我的回款在哪里？”）。但有时一段对话会变成一次真正的排查，比如为什么某个 Google Shopping feed 丢了一半的商品，这时低 effort 的回答就显得很浅。团队尝试在对话的剩余部分把顶层的 `effort` 提高到 `high`，但这些对话的成本大幅上升，而且下一轮的延迟立刻跳高，尽管历史并没有改变。

Explain what happened and design per-turn effort for this agent.

> 解释发生了什么，并为这个 Agent 设计按轮次调整的 effort。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Effort is the dial between thoroughness and spend, and the right setting changes within one conversation. You want to turn the dial without throwing away the cached history, and you want to turn it back down when the hard part is over.

> **核心思路。** effort 是在“周全”与“花费”之间调节的旋钮，而合适的档位在一段对话内部就会变化。你希望转动这个旋钮时不丢掉已缓存的历史，并在困难部分结束后把它调回去。

**What happened.** Changing the top-level `effort` between requests invalidates the prompt cache, so the first high-effort turn re-processed the whole conversation at full input price, which explains both the cost and the latency jump. On some models a top-level change also steers less reliably, because the model's earlier replies were written at the old level and it tends to stay consistent with them.

> **发生了什么。** 在两次请求之间修改顶层的 `effort` 会让提示缓存失效，所以第一次高 effort 的轮次以完整的输入价格重新处理了整段对话，这同时解释了成本和延迟的跳升。在某些模型上，修改顶层设置的引导效果也不太可靠，因为模型之前的回复是在旧档位下写的，它往往会和这些回复保持一致。

**The fix: per-message effort.** With the beta `mid-conversation-output-config-2026-07-01`, append a `role: "system"` message with empty content and `output_config: {"effort": ...}`. It changes effort for later turns without invalidating the cache. It works on Claude Opus 5.5, Claude Opus 5, Claude Sonnet 5.5, Claude Haiku 5.5, Claude Fable 5.1 and Claude Mythos 5.1 with thinking on, on the Claude API and Google Cloud; an unsupported model returns a 400.

> **修复方法：按消息设置 effort。** 使用 beta `mid-conversation-output-config-2026-07-01`，追加一条内容为空、带有 `output_config: {"effort": ...}` 的 `role: "system"` 消息。它会改变之后轮次的 effort，而不会让缓存失效。它适用于开启思考的 Claude Opus 5.5、Claude Opus 5、Claude Sonnet 5.5、Claude Haiku 5.5、Claude Fable 5.1 和 Claude Mythos 5.1，可在 Claude API 和 Google Cloud 上使用；不支持的模型会返回 400。

```json
{"model": "claude-opus-5-5", "max_tokens": 16000,
 "output_config": {"effort": "low"},
 "messages": [
   ...history,
   {"role": "user", "content": "Half my products disappeared from Google Shopping overnight."},
   {"role": "system", "content": [], "output_config": {"effort": "high"}}
 ]}
```

- **Placement decides timing.** Placed right after a user turn with new input, it sets the level for the reply to that turn; placed elsewhere, it applies from the next user turn with new input. A user turn holding only `tool_result` blocks does not count, so a change inside a tool loop waits.
  > **位置决定生效时机。** 放在一个带有新输入的 user 轮次之后，它会设定对该轮回复的档位；放在其他位置，则从下一个带有新输入的 user 轮次开始生效。只包含 `tool_result` 块的 user 轮次不算新输入，所以在工具循环中途做的修改要等一等才生效。
- **It persists.** The new level holds until another such message changes it, so add a message lowering effort again when the investigation is resolved.
  > **它会一直生效。** 新的档位会一直保持，直到另一条这样的消息修改它，所以在排查结束后要再加一条消息把 effort 调低。
- **Lowering is reliable; raising works best in large jumps**, for example from `low` to `xhigh`.
  > **调低是可靠的；调高则在大幅跳跃时效果最好**，例如从 `low` 直接到 `xhigh`。
- **Keep every effort message in the history.** Removing one later is a history edit that breaks the cache like any other.
  > **把每一条 effort 消息都保留在历史中。** 事后删除其中一条属于修改历史，和其他修改一样会破坏缓存。

**Who decides when to raise it.** Use a cheap signal you control: a classifier on the user message, a tool that returns an error pattern, or the agent's own request to escalate through a tool such as `escalate_investigation`. Log every change with its reason so you can see how often conversations escalate and what they cost.

> **由谁决定何时调高。** 使用一个由你们掌控的低成本信号：对用户消息做分类的分类器、返回特定错误模式的工具，或者让 Agent 通过 `escalate_investigation` 这样的工具自己请求升级。记录每一次修改及其原因，这样就能看到对话升级的频率以及它们的成本。

**Trade-offs.** Per-message effort keeps the cache and lets one conversation be cheap most of the time, but it is a beta with model and platform limits, so keep a fallback such as routing hard investigations to a separate high-effort conversation with a summary. On Claude Sonnet 5.5 with `between_tools`, effort cannot change mid-conversation at all, so a route that may escalate should not use it.

> **取舍。** 按消息设置 effort 能保留缓存，让一段对话在大部分时间里保持低成本，但它是一项有模型和平台限制的 beta 功能，所以要保留一个降级方案，比如把复杂排查转到一段单独的高 effort 对话中，并附上摘要。在使用 `between_tools` 的 Claude Sonnet 5.5 上，对话中途根本无法改变 effort，所以可能需要升级的路由不应使用它。

</details>

## 2. An all-day coordinator agent stops starting helpers in the afternoon

**一个运行一整天的协调者 Agent 到了下午就无法再启动助手了** · `Multi-agent` · `Medium`

### Question · 题目

A merchant-success team runs one long Managed Agents session per day. The coordinator agent hands tasks to roster agents: a feed checker, an ads analyst and a copywriter. Each request from the team spawns one or two helpers. By early afternoon the coordinator can no longer start helpers, and new requests are answered by the coordinator alone, slowly and with less detail. Nothing has crashed, and every helper finished its work hours ago.

> 一个商家成功团队每天运行一个很长的 Managed Agents 会话。协调者 Agent 把任务交给名册中的 Agent：一个 feed 检查员、一个广告分析师和一个文案写手。团队的每个请求都会启动一到两个助手。到了下午早些时候，协调者就无法再启动助手了，新的请求只能由协调者独自回答，又慢又不够详细。没有任何东西崩溃，而且每个助手都在几个小时前就完成了工作。

What limit did the session hit, and how would you design around it?

> 这个会话触到了什么限制？你会如何围绕它进行设计？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Helpers in a session are threads, and finished threads do not disappear on their own. A session has a fixed number of child-thread slots, so a long-lived coordinator must clean up after itself, or use a mechanism that does.

> **核心思路。** 会话中的助手就是线程，而完成工作的线程不会自行消失。一个会话的子线程名额是固定的，所以一个长期运行的协调者必须自己做好清理，或者使用一种会替它清理的机制。

**The limit.** A multiagent session allows at most 25 child threads, and idle threads count. Each helper the coordinator spawned stayed in the session as an idle thread after reporting back, so after enough requests the slots were full. Other limits to know: up to 20 roster entries, and only one level of delegation, since a roster member must not have its own `multiagent` configuration.

> **这个限制。** 一个多 Agent 会话最多允许 25 个子线程，而空闲线程也计算在内。协调者启动的每个助手在汇报之后都作为空闲线程留在会话中，所以在处理了足够多的请求之后，名额就满了。其他需要知道的限制：名册最多 20 个条目，并且只能有一层委派，因为名册成员不能拥有自己的 `multiagent` 配置。

**Fixes.**

> **修复方法。**

- **Archive finished threads.** Your client archives a helper's thread once its report has arrived. Archiving requires the thread to be idle; a thread waiting on `requires_action` counts as idle, and only a running thread must be interrupted first.
  > **归档已完成的线程。** 在助手的报告到达之后，由你们的客户端归档它的线程。归档要求线程处于空闲状态；等待 `requires_action` 的线程也算空闲，只有正在运行的线程才需要先中断。
- **Use dynamic workflows for batches.** When one request means many pieces of work, a workflow run creates its threads as needed and they do not count toward the 25-thread limit; the server archives them by the end of the run.
  > **对批量工作使用动态工作流。** 当一个请求意味着很多份工作时，工作流运行会按需创建线程，这些线程不计入 25 个线程的限制；服务端会在运行结束时把它们归档。
- **Shorter sessions.** One session per merchant case or per shift, rather than per day, keeps thread counts and context small, with handover notes written to a memory store or your own database.
  > **更短的会话。** 每个商家案例或每个班次使用一个会话，而不是每天一个，这样线程数和上下文都能保持较小，交接说明则写入记忆存储或你们自己的数据库。
- **Make the limit visible.** Track the number of non-archived child threads per session and alert well before 25; log when the coordinator answers alone after a spawn failed, so degraded answers are not silent.
  > **让这个限制可见。** 跟踪每个会话中未归档的子线程数量，并在远未达到 25 之前就发出告警；在启动助手失败、协调者只能独自回答时记录日志，这样质量下降就不会悄无声息。

**Briefing helpers well.** Subagents see none of the coordinator's conversation, so each task must carry the merchant ID, the relevant data, the constraints and the expected report format. A coordinator that briefs helpers poorly tends to re-spawn them to ask follow-up questions, which burns slots faster.

> **向助手交代清楚。** 子 Agent 看不到协调者的任何对话，所以每个任务都必须带上商家 ID、相关数据、约束条件以及期望的报告格式。交代不清楚的协调者往往会为了追问而重新启动助手，这会更快地耗尽名额。

**Careful with interrupts.** To stop a running helper before archiving it, send `user.interrupt` with that thread's `session_thread_id`. An interrupt without it stops every non-archived thread in the session, including the coordinator itself. Advisor threads, if the coordinator uses an advisor, are exempt from the 25-thread limit, so they never need this cleanup.

> **中断时要小心。** 要在归档之前停止一个正在运行的助手，就发送带有该线程 `session_thread_id` 的 `user.interrupt`。不带这个字段的中断会停止会话中所有未归档的线程，包括协调者自己。如果协调者使用了顾问（advisor），顾问线程不受 25 个线程的限制，所以永远不需要这种清理。

**Trade-offs.** Archiving threads frees slots but removes the option of sending a follow-up to the same helper, so archive only after the coordinator has used the report. Workflows remove the slot problem for batches but cost tokens for every agent in a run, so they need a session budget. Shorter sessions are simpler to reason about but lose the shared context of a long day unless you write it down.

> **取舍。** 归档线程能释放名额，但也就无法再向同一个助手发送后续消息，所以只有在协调者用完报告之后才归档。工作流解决了批量工作的名额问题，但运行中的每个 Agent 都会消耗 token，所以需要设定会话预算。更短的会话更容易理解，但除非你把内容记录下来，否则会失去漫长一天中积累的共享上下文。

</details>

## 3. Merchants pause for 20 minutes in a planning chat, and every reply after a pause is slow and expensive

**商家在规划对话中停顿 20 分钟，之后的每次回复都又慢又贵** · `Production` · `Medium`

### Question · 题目

A campaign-planning assistant on Claude Opus 5.5 keeps a large cached prefix: the system prompt, the merchant's catalog summary and past results, often well over 100,000 tokens. Merchants work in bursts and often step away for 10 to 40 minutes. The first reply after every pause takes noticeably longer, and the bill shows large cache writes. The prefix is stable, and caching works while merchants are active.

> 一个运行在 Claude Opus 5.5 上的广告活动规划助手维护着一个很大的缓存前缀：system prompt、商家的商品目录摘要和历史结果，经常远超 100,000 个 token。商家的工作是一阵一阵的，经常离开 10 到 40 分钟。每次停顿之后的第一条回复都明显更慢，账单上也显示有大量的缓存写入。前缀是稳定的，而且在商家活跃时缓存工作正常。

Why does this happen, and how would you fix it?

> 为什么会这样？你会如何修复？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A cache entry has a lifetime, and a pause longer than that lifetime means the next request rebuilds the whole prefix. You can pay for a longer lifetime, or keep the entry alive cheaply while the merchant is away.

> **核心思路。** 缓存条目有存活时间，停顿超过这段时间，下一个请求就要重建整个前缀。你可以为更长的存活时间付费，也可以在商家离开期间以很低的成本让条目保持存活。

**Mechanism.** The default cache TTL is 5 minutes, and a read refreshes the timer at no extra cost. The lifetime is measured from the start of the request that wrote or read the entry, so generation time counts against it: a 4-minute generation leaves about one minute before the entry expires. A 20-minute pause therefore always misses, and the next request pays a cache write on the whole prefix, which is both slower and more expensive than a read.

> **机制。** 默认的缓存 TTL 是 5 分钟，而一次读取会免费刷新计时器。存活时间从写入或读取该条目的请求开始时算起，所以生成所用的时间也算在内：一次 4 分钟的生成，只给条目留下大约 1 分钟就会过期。因此 20 分钟的停顿总是会错过缓存，下一个请求要为整个前缀支付一次缓存写入，这比读取更慢也更贵。

**Options, chosen by the gap between requests.**

> **根据请求之间的间隔来选择方案。**

- **Under 5 minutes:** the default 5-minute TTL; every request refreshes it, and it is strictly cheaper.
  > **5 分钟以内：** 使用默认的 5 分钟 TTL；每个请求都会刷新它，这严格来说更便宜。
- **5 to 60 minutes:** either the 1-hour TTL, whose write costs about twice the base input price instead of 1.25 times, or a keep-alive: while the merchant is idle, re-send the previous request with `max_tokens: 0` shortly before the entry expires. It refreshes the timer and bills only a cache read, with no output tokens.
  > **5 到 60 分钟：** 要么使用 1 小时 TTL，它的写入价格约为基础输入价格的 2 倍，而不是 1.25 倍；要么使用保活：在商家空闲时，在条目过期前不久用 `max_tokens: 0` 重发上一个请求。这会刷新计时器，并且只按一次缓存读取计费，不产生输出 token。
- **Over an hour:** neither helps directly; re-warm on a schedule if the next session is predictable, or accept the cold start.
  > **超过 1 小时：** 两者都不能直接起作用；如果下一次会话可以预测，就按计划重新预热，否则就接受冷启动。

```go
// keepAliveAt returns when to send a max_tokens: 0 keep-alive for a cache entry
// written or read by a request that started at start. The TTL counts from the
// start of that request, so generation time is already used up.
func keepAliveAt(start time.Time, ttl, margin time.Duration) time.Time {
	return start.Add(ttl - margin)
}
```

**Details that matter.** On Claude Opus 5.5 a cache read costs 0.05 times the base input price, so a keep-alive is cheap compared with a full rewrite. Send it with streaming off, and without structured outputs, which `max_tokens: 0` does not accept. Stop keep-alives after a sensible idle limit, such as when the merchant closes the tab, so you do not pay to keep abandoned conversations warm. On the Claude API, cache reads also do not count toward input-token rate limits on most models, which helps during busy hours.

> **重要的细节。** 在 Claude Opus 5.5 上，缓存读取的价格是基础输入价格的 0.05 倍，所以与完整重写相比，保活的成本很低。发送保活请求时要关闭流式输出，也不能带结构化输出，因为 `max_tokens: 0` 不接受它。在达到合理的空闲上限后（比如商家关闭页面时）就停止保活，这样就不会为保持被放弃的对话处于预热状态而付费。在 Claude API 上，对大多数模型来说缓存读取也不计入输入 token 的限流额度，这在繁忙时段很有帮助。

**Trade-offs.** The 1-hour TTL is the simplest change but doubles the cost of every write, including for merchants who never pause. Keep-alives need a scheduler and per-conversation state, and they spend money on conversations that may never resume. Measure the distribution of pause lengths and the share of conversations that resume before choosing; a mix, such as keep-alives for the first 30 minutes and then letting the entry expire, is often best.

> **取舍。** 1 小时 TTL 是最简单的改动，但会让每一次写入的成本翻倍，包括那些从不停顿的商家。保活需要调度器和每段对话的状态，而且会在可能永远不会继续的对话上花钱。在做选择之前，先测量停顿时长的分布以及会继续对话的比例；混合方案往往最好，比如在前 30 分钟内保活，之后就让条目过期。

</details>

## 4. "What were my top 10 products by refund rate last quarter?" RAG over the order export gives confident wrong numbers

**“上个季度退款率最高的 10 个商品是哪些？”基于订单导出数据的 RAG 给出了自信却错误的数字** · `RAG` · `Hard`

### Question · 题目

Merchants can ask an assistant questions about their own order export, a CSV of up to a few hundred thousand rows. The team chunked the CSV, embedded it and retrieves the top chunks for each question. Answers to lookup questions are fine, but aggregate questions such as refund rates, totals by country or month-over-month changes are confidently wrong. Someone suggests putting the whole CSV in the prompt instead, since the context window is large.

> 商家可以向助手询问关于自己订单导出数据的问题，这是一个最多几十万行的 CSV。团队把 CSV 切块、向量化，并为每个问题检索最相关的块。查询类问题的回答没有问题，但退款率、按国家汇总、环比变化这类聚合问题的回答却自信而错误。有人建议改为把整个 CSV 放进提示里，因为上下文窗口很大。

Why does RAG fail here, and what would you build instead?

> 为什么 RAG 在这里会失败？你会改为构建什么？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Retrieval finds relevant pieces; aggregation needs all the rows. A question like "refund rate by product" depends on every order, so any method that shows the model a sample will produce a plausible number computed from part of the data. The fix is to let the model write code that runs over the full file, and to put only the result into the conversation.

> **核心思路。** 检索找到的是相关的片段；而聚合需要所有的行。“按商品统计退款率”这样的问题依赖于每一笔订单，所以任何只给模型看一部分样本的方法，都会得出一个根据部分数据算出来、看起来很合理的数字。修复方法是让模型编写在完整文件上运行的代码，并只把结果放进对话中。

**Why both obvious approaches fail.** Top-k retrieval returns a handful of chunks, so totals are computed from a fraction of the rows, and the model has no way to know what is missing. Putting the whole CSV in the prompt is expensive on every turn and still asks the model to do exact arithmetic over hundreds of thousands of rows by reading, which is the wrong tool for the job.

> **为什么两种显而易见的方法都会失败。** top-k 检索只返回少量的块，所以总数是根据一小部分行算出来的，而模型无从知道缺了什么。把整个 CSV 放进提示里每一轮都很昂贵，而且仍然是在要求模型通过阅读，对几十万行数据做精确的计算，这是用错了工具。

**The design: Files API plus code execution.** Upload the export once with the Files API and pass it to the code execution tool as a `container_upload` block. The model writes and runs code in a sandbox that reads the whole file, and only the computed answer enters the context. Generated charts or files come back with file IDs that you download through the Files API.

> **设计：Files API 加代码执行。** 用 Files API 把导出文件上传一次，并以 `container_upload` 块的形式把它交给代码执行工具。模型在沙箱中编写并运行读取整个文件的代码，只有计算出的答案会进入上下文。生成的图表或文件会带着文件 ID 返回，你可以通过 Files API 下载它们。

```json
{"model": "claude-opus-5-5", "max_tokens": 16000,
 "tools": [{"type": "code_execution_20260120", "name": "code_execution"}],
 "messages": [{"role": "user", "content": [
   {"type": "text", "text": "Top 10 products by refund rate last quarter, with order counts."},
   {"type": "container_upload", "file_id": "file_..."}
 ]}]}
```

- **Define the metrics.** Give the model a short data dictionary: what each column means, the timezone of dates, and how your business defines a refund rate, for example refunded orders divided by delivered orders. Most wrong answers come from ambiguous definitions, not from bad code.
  > **定义指标。** 给模型一份简短的数据字典：每一列的含义、日期的时区，以及你们业务中退款率的定义，例如退款订单数除以已送达订单数。大多数错误答案来自含糊的定义，而不是糟糕的代码。
- **Show the work.** Ask the answer to include the number of rows used and any rows excluded, so a merchant can see that the whole file was read.
  > **展示计算过程。** 要求回答中包含所用的行数以及被排除的行，这样商家就能看到整个文件都被读取了。
- **Keep retrieval for text.** Policy and help questions still go to RAG; route numeric questions over the merchant's own data to code execution.
  > **文本问题仍然用检索。** 政策和帮助类问题仍然走 RAG；关于商家自身数据的数值问题则路由到代码执行。
- **Isolate merchants.** Each merchant's file is uploaded and referenced only in that merchant's requests, and files are deleted after their retention period.
  > **隔离商家。** 每个商家的文件只在该商家的请求中上传和引用，并在保留期结束后删除。

**Testing.** Build an eval from questions with known answers computed by your own SQL on the same exports, including edge cases such as empty months, refunds without orders and mixed currencies. Compare the assistant's numbers with the SQL results exactly, not with a judge's opinion.

> **测试。** 用一组已知答案的问题构建评测，这些答案由你们自己的 SQL 在同样的导出数据上计算得出，并包括边界情况，比如没有数据的月份、没有订单的退款以及混合币种。把助手给出的数字与 SQL 结果做精确比较，而不是看评审器的意见。

**Trade-offs.** Code execution adds latency and sandbox container time, which is billed hourly beyond a free allowance, so do not use it for questions with nothing to compute. For the most common reports, a fixed dashboard or a SQL tool over your warehouse is cheaper and more predictable; code execution shines for the long tail of questions nobody built a report for.

> **取舍。** 代码执行会增加延迟和沙箱容器时间，而容器时间在超出免费额度后按小时计费，所以对于没有什么需要计算的问题，不要使用它。对于最常见的报表，固定的看板或者针对数据仓库的 SQL 工具更便宜，也更可预测；代码执行的优势在于那些没人专门做过报表的长尾问题。

</details>

## 5. The prompt was tuned from 71% to 94% on the eval, and production did not improve at all

**提示在评测上从 71% 调到了 94%，而生产环境却毫无改善** · `Evals & Observability` · `Senior`

### Question · 题目

A teammate spent two weeks tuning the support agent's prompt. Each round, a script ran the agent on all 60 eval cases, showed the teammate the failures, and the teammate changed the prompt to fix them. The score climbed from 71% to 94%, and the new prompt shipped. Two weeks later, escalation rates and merchant ratings are unchanged. The final prompt is three times longer and contains phrases copied from specific eval cases.

> 一位同事花了两周时间调优客服 Agent 的提示。每一轮，脚本都在全部 60 个评测用例上运行 Agent，把失败的用例展示给这位同事，然后同事修改提示来修复它们。分数从 71% 爬升到 94%，新提示上线了。两周后，升级人工的比例和商家评分都没有变化。最终的提示长度是原来的三倍，并且包含从具体评测用例中复制过来的语句。

What went wrong, and how should prompt tuning against an eval be run?

> 问题出在哪里？应该如何基于评测来调优提示？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** If the person or model proposing changes can see every case, the score measures how well the prompt memorized those cases, not how well the agent works. You need a wall: cases used to find problems, and different cases used to judge the result.

> **核心思路。** 如果提出修改的人或模型能看到每一个用例，那么分数衡量的是提示把这些用例记得有多好，而不是 Agent 实际工作得有多好。你需要一堵墙：一些用例用来发现问题，另一些用例用来评判结果。

**What went wrong.**

> **问题出在哪里。**

- **No held-out set.** Every case was read and fixed, and the winning round was chosen by the same score, so 94% is an in-sample number.
  > **没有留出集。** 每个用例都被读过、修过，而获胜的那一轮也是用同一个分数选出来的，所以 94% 是一个样本内的数字。
- **Content instead of behaviour.** Copying phrases from failures into the prompt fixes those exact cases and teaches nothing general; a change should describe the behaviour, scaled to how many cases show it.
  > **照搬内容而不是描述行为。** 把失败用例中的语句复制进提示，只能修复那几个具体用例，学不到任何通用的东西；修改应该描述行为，其力度要与表现出该行为的用例数量相称。
- **Noise.** With 60 cases, a few cases flipping by chance move the score by several points, so some "improvements" were noise.
  > **噪声。** 只有 60 个用例时，几个用例偶然翻转就会让分数变动好几个百分点，所以有些“改进”只是噪声。

**How to run it.** Split the cases at random, stratified by category and never by score, into train and test. The proposer reads only train transcripts. Test is scored every round, never opened, picks the winning round and is the number you report. Run each case more than once and know the noise: for a pass rate, the 95% confidence half-width is roughly `1/sqrt(n·reps)`, about ±14 points for 25 test cases at 2 reps and ±10 for 50.

> **应该怎么做。** 把用例随机地划分为训练集和测试集，按类别分层，绝不按分数划分。提出修改的一方只阅读训练集的对话记录。测试集每一轮都要打分，但从不打开查看，由它来选出获胜的那一轮，它也是你对外报告的数字。每个用例运行不止一次，并了解噪声的大小：对于通过率，95% 置信区间的半宽大约是 `1/sqrt(n·reps)`，25 个测试用例各运行 2 次约为 ±14 个百分点，50 个则约为 ±10 个百分点。

```go
// split draws a random train/test split stratified by tag, never by score.
func split(cases []Case, trainShare float64, seed int64) (train, test []Case) {
	byTag := map[string][]Case{}
	for _, c := range cases {
		byTag[c.Tag] = append(byTag[c.Tag], c)
	}
	tags := make([]string, 0, len(byTag))
	for t := range byTag {
		tags = append(tags, t)
	}
	sort.Strings(tags)
	r := rand.New(rand.NewSource(seed))
	for _, t := range tags {
		group := byTag[t]
		r.Shuffle(len(group), func(i, j int) { group[i], group[j] = group[j], group[i] })
		n := int(math.Round(float64(len(group)) * trainShare))
		train = append(train, group[:n]...)
		test = append(test, group[n:]...)
	}
	return train, test
}
```

**More rules that keep the loop honest.** One idea per round, so you know what helped. Keep reference answers out of anything the agent can read, or the loop will eventually find them. Recompute the headline from raw per-case results instead of trusting an aggregate. Treat an implausible jump on a model-graded score as a judge problem until you have checked transcripts by hand. Record refusals and harness errors separately from real failures. And tie every gain to a behaviour you can point to in the traces.

> **让循环保持诚实的更多规则。** 每一轮只尝试一个想法，这样你才知道是什么起了作用。让参考答案远离 Agent 能读取的任何地方，否则循环迟早会找到它们。根据每个用例的原始结果重新计算核心指标，而不是相信某个汇总值。在由模型评分的分数上出现难以置信的跳升时，在亲手检查对话记录之前，都要把它当作评审器的问题。把拒答和测试框架错误与真正的失败分开记录。并且要把每一次提升都对应到对话记录中能指出来的某种行为。

**Close the loop with production.** The eval is a proxy. Before shipping, check that eval categories match real traffic, add recent production failures to the case pool (into train or test at random), and compare production metrics such as escalation rate in an A/B rollout, not just the eval score.

> **与生产环境形成闭环。** 评测只是一个代理指标。在上线之前，检查评测的类别是否与真实流量相符，把近期生产环境中的失败加入用例池（随机分到训练集或测试集），并在 A/B 灰度中比较生产指标，比如升级人工的比例，而不只是看评测分数。

**Trade-offs.** A held-out set means fewer cases to learn from and a noisier headline, so small sets need more reps or more cases. Strict rules slow the loop down, but a fast loop that measures memorization ships prompts that cost more and help nobody, as this one did.

> **取舍。** 留出集意味着可供学习的用例更少、核心指标的噪声更大，所以小规模的用例集需要更多的重复运行或更多的用例。严格的规则会让循环变慢，但一个衡量记忆效果的快速循环，只会产出成本更高却对谁都没有帮助的提示，就像这次一样。

</details>
