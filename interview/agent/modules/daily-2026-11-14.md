## 1. After moving the catalog-audit agent to Claude Fable 5.1, it checks one product per turn and audits take twice as long

**把商品目录审计 agent 迁到 Claude Fable 5.1 之后，它每轮只检查一个商品，审计耗时翻了一倍** · `Agent Loop` · `Medium`

### Question · 题目

A catalog-audit agent has three tools: `get_product`, `get_ad_status` and `get_price_history`. On Claude Fable 5 a turn often requested several lookups at once. On Claude Fable 5.1 the findings are the same, but the agent makes one call per turn, so audits need about twice the round trips and wall-clock time. The team proposes three changes:

> 一个商品目录审计 agent 有三个工具：`get_product`、`get_ad_status` 和 `get_price_history`。在 Claude Fable 5 上，一轮经常会同时请求好几次查询。在 Claude Fable 5.1 上，审计结论相同，但 agent 每轮只发起一次调用，所以审计需要大约两倍的往返次数和实际耗时。团队提出了三项改动：

- add "Always call as many tools in parallel as possible" to the system prompt;
  > 在系统提示里加上「总是尽可能多地并行调用工具」；
- add a reminder after each turn's tool results, and delete the previous turn's reminder so the history stays short;
  > 在每一轮的工具结果后面加一条提醒，并删除上一轮的提醒，让历史记录保持简短；
- send each tool result in its own user message, so the logs are easier to read.
  > 把每个工具结果放在单独的用户消息里发送，这样日志更容易阅读。

Evaluate the three ideas and fix the loop.

> 评估这三个想法，并修复这个循环。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** In long agent loops where the next reads are only implied, Claude Fable 5.1 may issue one call per turn where Claude Fable 5 batched several. The answers are the same; the cost is round trips and time. Measure it, then nudge, and put the nudge in the right place: where it sits matters more than how it is worded.

> **核心思想。** 在长的 agent 循环中，如果接下来要读取的内容只是隐含的，Claude Fable 5.1 可能会每轮只发起一次调用，而 Claude Fable 5 会把几次调用合并在一起。答案是一样的，代价是往返次数和时间。先测量，再提示，并且把提示放在正确的位置：它放在哪里，比它怎么措辞更重要。

**Measure first.** Track the share of assistant turns that contain more than one tool call, and add the nudge only if that share is low. Too much batching shows up as calls issued before the results they depend on, for example a price-history lookup for a SKU the agent has not found yet.

> **先测量。** 统计包含多于一次工具调用的助手轮次所占的比例，只有在这个比例偏低时才加提示。合并过度的表现是：在所依赖的结果出来之前就发出了调用，比如为一个 agent 还没找到的 SKU 去查价格历史。

**The nudge and where it goes.** One sentence near the end of the current request moves the number far more than the same text in the system prompt or a tool description. Each time you send tool results back, append it after them: as a turn-scoped system message (`clear_at: "next_user_message"`, beta `mid-conversation-system-clear-at-2026-08-21`), or without that beta as a text block after the `tool_result` blocks in the same user message. Keep the word "privately": without it the model sometimes answers the reminder ("nothing further is needed") in its final reply.

> **提示语及其位置。** 一句放在当前请求末尾附近的话，对这个比例的影响远大于把同样的文字放在系统提示或工具描述里。每次发回工具结果时，把这句话追加在结果后面：可以作为一条只在本轮生效的系统消息（`clear_at: "next_user_message"`，beta `mid-conversation-system-clear-at-2026-08-21`），没有这个 beta 时，也可以作为同一条用户消息中位于 `tool_result` 块之后的一个文本块。保留「privately」这个词：没有它，模型有时会在最终回复里回应这条提醒（比如「不需要更多信息了」）。

```go
const batchNudge = "First privately list what you need next; then request every item " +
	"that doesn't depend on another's result in this one response."

// Measure first: the share of assistant turns that made more than one tool call.
func multiCallShare(turns []*anthropic.BetaMessage) float64 {
	withTools, multi := 0, 0
	for _, t := range turns {
		n := 0
		for _, b := range t.Content {
			if b.Type == "tool_use" {
				n++
			}
		}
		if n > 0 {
			withTools++
		}
		if n > 1 {
			multi++
		}
	}
	if withTools == 0 {
		return 0
	}
	return float64(multi) / float64(withTools)
}

// All results in one user message, a fresh nudge after them; earlier copies stay as sent.
func toolResultsTurn(results []anthropic.BetaContentBlockParamUnion) anthropic.BetaMessageParam {
	blocks := append(append([]anthropic.BetaContentBlockParamUnion{}, results...), anthropic.NewBetaTextBlock(batchNudge))
	return anthropic.NewBetaUserMessage(blocks...)
}
```

**The three ideas.**

> **那三个想法。**

- **System-prompt line:** the weakest placement, and "as many as possible" invites calls that depend on results not yet available. Use the sentence above, at the end, and measure.
  > **系统提示里的那句话：** 这是效果最弱的位置，而且「尽可能多」会诱发那些依赖尚未拿到的结果的调用。用上面那句话，放在末尾，并进行测量。
- **Deleting old reminders:** append a fresh copy each turn and leave earlier copies in place byte for byte. Rewriting earlier turns restarts the prompt cache and, on this model, invalidates the thinking blocks after the edit.
  > **删除旧的提醒：** 每一轮追加一份新的，并让之前的副本一个字节都不改地留在原处。改写之前的轮次会让提示缓存重新开始，而且在这个模型上，会让修改点之后的思考块失效。
- **One message per result:** return all `tool_result` blocks of a turn in a single user message. Splitting them across messages trains Claude to stop making parallel calls, which is the opposite of the goal. Return a failed call as a `tool_result` with `is_error: true`; never drop it. Log however you like on your side.
  > **每个结果一条消息：** 一轮中所有的 `tool_result` 块都要放在同一条用户消息里返回。把它们拆到多条消息里，会让 Claude 逐渐不再并行调用，恰好与目标相反。失败的调用要作为 `is_error: true` 的 `tool_result` 返回，绝不能丢掉。日志在你自己这边想怎么记都可以。

**Trade-offs.** More parallel calls mean bursts against your own APIs, so check rate limits on the catalog and ad services. The nudge costs a few tokens every turn, and too much batching produces wasted calls; keep watching the multi-call share and the dependency errors together.

> **权衡。** 更多的并行调用意味着对你们自己的 API 形成突发流量，所以要检查商品目录和广告服务的限流。提示语每一轮都会消耗一些 token，而合并过度会产生无用的调用；要同时盯住多调用轮次的比例和依赖错误这两个指标。

</details>

## 2. The model router keeps its own table of context windows and features, and every new model breaks it

**模型路由器自己维护了一张上下文窗口和功能的表，每出一个新模型它就会出问题** · `Production` · `Medium`

### Question · 题目

A SaaS backend routes requests to models by configuration. A hand-kept table says, per model, the context window, the maximum output, whether it uses adaptive thinking or a thinking budget, and which effort levels it accepts. When the team added Claude Haiku 5.5, the table entry was copied from Claude Haiku 4.5. The router then rejected large catalog prompts as "too long" and sent `budget_tokens`, which returned a 400. The router also waited for an SDK release with a typed constant for the new model before anyone could use it.

> 一个 SaaS 后端按配置把请求路由到不同模型。一张人工维护的表记录了每个模型的上下文窗口、最大输出、使用自适应思考还是思考预算，以及接受哪些 effort 等级。团队加入 Claude Haiku 5.5 时，表里的条目是从 Claude Haiku 4.5 复制过来的。结果路由器把大型商品目录提示判定为「太长」而拒绝，还发送了 `budget_tokens`，导致返回 400。而且路由器还要等到 SDK 发布了新模型的类型常量之后，才有人能用上这个模型。

Fix the router so new models stop breaking it.

> 修复这个路由器，让新模型不再把它弄坏。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Ask the API what a model supports instead of keeping your own copy. The Models API returns, for each model, the context window, the output limit and a full capability tree, and it is right on the day a model launches.

> **核心思想。** 向 API 询问模型支持什么，而不是自己维护一份副本。Models API 会针对每个模型返回上下文窗口、输出上限以及完整的能力树，而且在模型发布当天就是准确的。

**What it returns.** `GET /v1/models/{id}` (and the paginated list) has `max_input_tokens` (the context window), `max_tokens` (the output limit) and `capabilities`, a nested tree with a `supported` flag at each leaf: thinking types such as `adaptive`, each effort level, structured outputs, image input, context-management strategies and more. The documented example for Claude Opus 4.8 shows adaptive thinking supported and the budget-based `enabled` type not supported, which is exactly the fact the copied table got wrong.

> **它返回什么。** `GET /v1/models/{id}`（以及分页的列表接口）包含 `max_input_tokens`（上下文窗口）、`max_tokens`（输出上限）和 `capabilities`；后者是一棵嵌套的树，每个叶子节点上都有一个 `supported` 标志：比如 `adaptive` 这样的思考类型、每个 effort 等级、结构化输出、图片输入、上下文管理策略等等。文档中 Claude Opus 4.8 的示例显示：支持自适应思考，不支持基于预算的 `enabled` 类型，而这正是复制过来的那张表搞错的地方。

**The fix.**

> **修复方法。**

- Load model info at startup, refresh it periodically, and keep the last good copy if a refresh fails.
  > 在启动时加载模型信息，定期刷新，刷新失败时保留最近一次成功的副本。
- Validate every route in CI and before sending: thinking type, effort level and sizes, as in the code below.
  > 在 CI 中以及发送请求之前校验每条路由：思考类型、effort 等级和大小限制，如下面的代码所示。
- Build request settings from capabilities: adaptive thinking plus an effort level where adaptive is supported, never a budget copied from an older model.
  > 根据能力来构造请求设置：在支持自适应思考的模型上，使用自适应思考加上一个 effort 等级，绝不使用从旧模型复制过来的预算。
- Count prompt tokens with `count_tokens` against the target model before comparing with `max_input_tokens`, since tokenizers differ between models.
  > 在和 `max_input_tokens` 比较之前，先用 `count_tokens` 针对目标模型计算提示的 token 数，因为不同模型的分词器不一样。
- Pass model IDs as plain strings. Typed SDK constants lag model launches; the string ID works in every SDK version.
  > 用普通字符串传递模型 ID。SDK 的类型常量会滞后于模型发布；字符串 ID 在任何 SDK 版本中都能用。

```go
type Route struct {
	Model  string
	Effort string // "low" ... "max"
}

// Checked against the live Models API, not a hand-kept table.
func checkRoute(ctx context.Context, client anthropic.Client, r Route, promptTokens, maxOut int64) error {
	m, err := client.Models.Get(ctx, r.Model, anthropic.ModelGetParams{})
	if err != nil {
		return err
	}
	c := m.Capabilities
	if !c.Thinking.Types.Adaptive.Supported {
		return fmt.Errorf("%s: no adaptive thinking", m.ID)
	}
	levels := map[string]bool{"low": c.Effort.Low.Supported, "medium": c.Effort.Medium.Supported,
		"high": c.Effort.High.Supported, "xhigh": c.Effort.Xhigh.Supported, "max": c.Effort.Max.Supported}
	if !levels[r.Effort] {
		return fmt.Errorf("%s: effort %q not supported", m.ID, r.Effort)
	}
	if promptTokens > m.MaxInputTokens || maxOut > m.MaxTokens {
		return fmt.Errorf("%s: request does not fit (%d in, %d out)", m.ID, promptTokens, maxOut)
	}
	return nil
}
```

**Where it does not reach.** The Models API is available on the Claude API and Claude Platform on AWS, not on Amazon Bedrock, Google Cloud Vertex AI or Microsoft Foundry; keep a small reviewed table for those routes. It also does not describe prices, rate limits or behavior, such as whether a model has a server-side refusal fallback, so still read the migration notes for each new model.

> **它覆盖不到的地方。** Models API 可以在 Claude API 和 Claude Platform on AWS 上使用，但在 Amazon Bedrock、Google Cloud Vertex AI 和 Microsoft Foundry 上不可用；对于这些路由，要保留一张经过审核的小表。它也不描述价格、速率限制或模型行为（比如某个模型是否有服务端拒答回退），所以每个新模型的迁移说明仍然要读。

**Trade-offs.** A startup dependency on another API needs a cache and a fallback. A `supported` flag says a request will be accepted, not that the model is good for your task; your evals still decide which route uses which model.

> **权衡。** 启动时依赖另一个 API，就需要缓存和兜底。`supported` 标志说明的是请求会被接受，而不是模型适合你的任务；哪条路由用哪个模型，仍然要由你的评测来决定。

</details>

## 3. The advisor tool in production: the advice log is empty, some turns get no advice, and removing the advisor breaks running conversations

**生产环境中的顾问工具：顾问建议日志是空的，有些轮次拿不到建议，而移除顾问会让进行中的对话出错** · `Multi-agent` · `Hard`

### Question · 题目

An ad-campaign planner on the Messages API uses Claude Sonnet 5.5 as the executor with the advisor tool (`advisor_20260301`). It used to run Claude Sonnet 5 with a Claude Opus 4.8 advisor; after the executor moved to Claude Sonnet 5.5, that pairing returned 400, so the advisor became Claude Opus 5.5. Since then:

> 一个基于 Messages API 的广告投放规划器，使用 Claude Sonnet 5.5 作为执行者，并配有顾问工具（`advisor_20260301`）。它以前用的是 Claude Sonnet 5 加 Claude Opus 4.8 顾问；执行者迁到 Claude Sonnet 5.5 之后，这个组合返回 400，于是顾问换成了 Claude Opus 5.5。从那以后：

- the audit log of advice has been empty;
  > 顾问建议的审计日志一直是空的；
- after `max_uses: 2` was added, some long turns contain advisor results with an error instead of advice;
  > 加上 `max_uses: 2` 之后，一些较长的轮次里出现的是带错误的顾问结果，而不是建议；
- a cost flag removes the advisor from ongoing conversations, and some of those requests return 400;
  > 一个控制成本的开关会把顾问从进行中的对话里移除，其中一些请求返回了 400；
- the advisor's input tokens are a large part of the bill.
  > 顾问的输入 token 在账单里占了很大一部分。

Explain each problem and design the advisor setup.

> 解释每个问题，并设计顾问的配置方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** What you can read from an advisor depends on the advisor model, and the advisor's configuration is part of the conversation's prefix. Treat its results as a union you must switch on, and change its configuration only when a new conversation starts.

> **核心思想。** 你能从顾问那里读到什么，取决于顾问模型；而顾问的配置是对话前缀的一部分。要把它的结果当作一个必须分类处理的联合类型，并且只在新对话开始时才修改它的配置。

**Why the log is empty.** A Claude Sonnet 5.5 executor rejects Claude Opus 4.8, 4.7 and 4.6, Claude Sonnet 5 and Sonnet 4.6 advisors with a 400, and every advisor it accepts returns the encrypted `advisor_redacted_result`. The block is always `advisor_tool_result`; its `content` is `advisor_result` with `text` for a plaintext advisor, `advisor_redacted_result` with `encrypted_content`, or `advisor_tool_result_error`. Code that reads `.text` gets nothing. Encrypted advice cannot be read, only replayed. If auditors need readable advice, that is a product decision: this executor cannot pair with a plaintext advisor.

> **为什么日志是空的。** Claude Sonnet 5.5 执行者会以 400 拒绝 Claude Opus 4.8、4.7、4.6，Claude Sonnet 5 和 Sonnet 4.6 这些顾问，而它接受的每一个顾问返回的都是加密的 `advisor_redacted_result`。结果块始终是 `advisor_tool_result`；它的 `content` 可能是带 `text` 的 `advisor_result`（明文顾问）、带 `encrypted_content` 的 `advisor_redacted_result`，或者 `advisor_tool_result_error`。读取 `.text` 的代码什么也拿不到。加密的建议无法读取，只能原样回传。如果审计人员需要可读的建议，那是一个产品层面的决定：这个执行者无法与明文顾问搭配。

```go
// Log every consultation by what actually came back.
func logAdvice(msg *anthropic.BetaMessage) {
	for _, b := range msg.Content {
		r, ok := b.AsAny().(anthropic.BetaAdvisorToolResultBlock)
		if !ok {
			continue
		}
		switch r.Content.Type {
		case "advisor_result": // plaintext advisor, e.g. Opus 4.8
			log.Printf("advice: %s", r.Content.AsResponseAdvisorResultBlock().Text)
		case "advisor_redacted_result": // replay it unchanged; it cannot be read
			log.Printf("advice: redacted, stop_reason=%s", r.Content.StopReason)
		case "advisor_tool_result_error": // max_uses_exceeded, overloaded, ...
			log.Printf("advice failed: %s", r.Content.AsResponseAdvisorToolResultError().ErrorCode)
		}
	}
}
```

**Why advice is missing.** `max_uses` caps consultations per request. Beyond it, the result's content is the error object with `max_uses_exceeded`, and the executor carries on without advice. Count these errors per route before choosing the cap. To bound the size of each consultation instead, use the tool's `max_tokens`: at the cap, the result carries `stop_reason: "max_tokens"` and the executor sees a truncation note.

> **为什么建议缺失了。** `max_uses` 限制的是每个请求的咨询次数。超出之后，结果的内容就是带 `max_uses_exceeded` 的错误对象，执行者会在没有建议的情况下继续。在选定上限之前，先按路由统计这类错误的数量。如果想限制每次咨询的规模，应使用工具的 `max_tokens`：达到上限时，结果会带有 `stop_reason: "max_tokens"`，执行者会看到一条截断说明。

**Why removing it returns 400.** Removing the advisor while history still holds `advisor_tool_result` blocks is allowed if you keep sending the `advisor-tool-2026-03-01` beta header, and the model then cannot call it. But a request without the tool while an advisor call is pending (after `pause_turn`, or `tool_use` in the same turn) is a 400. And removing the tool, or changing its `model` or `caching`, edits `tools`, which invalidates the thinking blocks already in the history. Where the history-editing check is enforced, that request returns 400 unless `thinking.block_binding.prefix_mismatch_behavior` is `"drop_block"` on it and every later request. So change or remove the advisor only in new conversations.

> **为什么移除它会返回 400。** 当历史中仍有 `advisor_tool_result` 块时，只要继续发送 `advisor-tool-2026-03-01` beta 请求头，移除顾问是允许的，之后模型就不能再调用它。但如果在顾问调用尚未完成时（`pause_turn` 之后，或同一轮中出现 `tool_use`）发送不带该工具的请求，就会返回 400。而且移除工具，或者修改它的 `model` 或 `caching`，都属于修改 `tools`，会让历史中已有的思考块失效。在启用了历史编辑检查的地方，这样的请求会返回 400，除非在这个请求以及之后的每个请求上都把 `thinking.block_binding.prefix_mismatch_behavior` 设为 `"drop_block"`。所以只在新对话中修改或移除顾问。

**Why it costs so much.** Without `caching` on the tool, the advisor's own prompt is not cached. Set `"caching": {"type": "ephemeral", "ttl": "5m"}` (or `"1h"`) once, at the start of each conversation, so later consultations read the stable prefix. Append the full `response.content`, advisor results included, on every turn.

> **为什么成本这么高。** 如果工具上没有设置 `caching`，顾问自己的提示就不会被缓存。在每个对话开始时一次性设置 `"caching": {"type": "ephemeral", "ttl": "5m"}`（或 `"1h"`），这样之后的咨询就能读取稳定的前缀。每一轮都要把完整的 `response.content`（包括顾问结果）追加回去。

**Trade-offs.** A tight `max_uses` saves money but leaves hard turns without advice. Encrypted advice protects the advisor's output but gives auditors only the executor's actions. A cost flag that only applies to new conversations takes longer to have an effect, but it never breaks a running one.

> **权衡。** 收紧 `max_uses` 能省钱，但会让困难的轮次拿不到建议。加密的建议保护了顾问的输出，但审计人员只能看到执行者的动作。只对新对话生效的成本开关需要更长时间才能见效，但它绝不会弄坏一个进行中的对话。

</details>

## 4. An enterprise merchant's workspace moves to customer-managed encryption keys, and the Claude Fable 5.2 extractor can no longer use strict tools

**一家企业商家的工作区改用客户自管加密密钥，Claude Fable 5.2 的抽取步骤再也不能使用 strict 工具** · `Tools & MCP` · `Hard`

### Question · 题目

A listing-extraction step on Claude Fable 5.2 reads supplier PDFs and calls a `save_listing` tool defined with `strict: true`. Another route asks for a JSON answer through `output_config.format`. An enterprise merchant requires customer-managed encryption keys (CMEK), and their workspace is moved to an organization that uses them. In a CMEK organization, structured outputs are not available for Claude Fable or Claude Mythos models.

> 一个运行在 Claude Fable 5.2 上的商品信息抽取步骤会读取供应商的 PDF，并调用一个以 `strict: true` 定义的 `save_listing` 工具。另一条路由通过 `output_config.format` 要求返回 JSON 答案。一家企业商家要求使用客户自管加密密钥（CMEK），他们的工作区被迁到了一个使用 CMEK 的组织中。在 CMEK 组织里，Claude Fable 和 Claude Mythos 系列模型不能使用结构化输出。

The team suggests forcing the tool with `tool_choice`, or parsing the model's text with regular expressions. Design the extraction for this organization.

> 团队建议用 `tool_choice` 强制调用工具，或者用正则表达式解析模型的文本。请为这个组织设计抽取方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** In a CMEK organization, structured outputs (strict tool use and JSON outputs) are not available for Claude Fable or Claude Mythos models. The guarantee that inputs match the schema moves from the API into your code, so your code must check everything the schema used to promise.

> **核心思想。** 在 CMEK 组织中，Claude Fable 和 Claude Mythos 系列模型无法使用结构化输出（strict 工具调用和 JSON 输出）。「输入符合 schema」这一保证就从 API 转移到了你的代码里，所以你的代码必须检查 schema 以前承诺的所有东西。

**Why the team's ideas fail.** Claude Fable 5.2 rejects a forced `tool_choice` (`any` or a named tool) with a 400, on `count_tokens` as well. Regular expressions over text break on escaping, which can differ between models: always parse tool inputs as JSON, never match the serialized string.

> **为什么团队的想法行不通。** Claude Fable 5.2 会以 400 拒绝强制的 `tool_choice`（`any` 或指定的工具），在 `count_tokens` 上也一样。在文本上跑正则表达式会在转义上出问题，而不同模型的转义方式可能不同：工具输入一定要按 JSON 解析，绝不能去匹配序列化后的字符串。

**The design.**

> **设计方案。**

- Keep `tool_choice: {"type": "auto"}` with an instruction that names the tool, and leave out `strict` and `output_config.format`.
  > 保留 `tool_choice: {"type": "auto"}`，并加上一条点名该工具的指令；去掉 `strict` 和 `output_config.format`。
- Check `stop_reason` before running any tool: a `max_tokens` turn may hold incomplete input, and a `refusal` turn must not run its calls.
  > 在运行任何工具之前先检查 `stop_reason`：以 `max_tokens` 结束的轮次可能带着不完整的输入，而以 `refusal` 结束的轮次绝不能执行其中的调用。
- Decode the input strictly, reject unknown fields, and check business rules. On failure, return a `tool_result` with `is_error: true` and the exact problems, so the model can correct itself. Cap the retries and never write unvalidated data.
  > 严格地解码输入，拒绝未知字段，并检查业务规则。校验失败时，返回一个 `is_error: true` 的 `tool_result`，写明具体的问题，让模型能够自我纠正。限制重试次数，绝不写入未经校验的数据。
- With eager input streaming on, validate the parsed input before running it, because tolerant parsers can return silently truncated input.
  > 如果开启了 eager input streaming，要在运行之前校验解析后的输入，因为宽容的解析器可能会悄无声息地返回被截断的输入。

```go
type ListingInput struct {
	SKU      string   `json:"sku"`
	Title    string   `json:"title"`
	PriceMin int64    `json:"price_minor"`
	Currency string   `json:"currency"`
	Tags     []string `json:"tags"`
}

// Without strict tool use, the code is the schema check.
func validateListing(raw json.RawMessage) (ListingInput, error) {
	var in ListingInput
	dec := json.NewDecoder(bytes.NewReader(raw))
	dec.DisallowUnknownFields()
	if err := dec.Decode(&in); err != nil {
		return in, fmt.Errorf("input is not valid for this tool: %v", err)
	}
	var problems []string
	if in.SKU == "" {
		problems = append(problems, "sku is required")
	}
	if n := len([]rune(in.Title)); n == 0 || n > 150 {
		problems = append(problems, "title must be 1-150 characters")
	}
	if in.PriceMin <= 0 {
		problems = append(problems, "price_minor must be a positive integer")
	}
	if len(in.Currency) != 3 {
		problems = append(problems, "currency must be a 3-letter ISO code")
	}
	if len(problems) > 0 {
		return in, fmt.Errorf("%s", strings.Join(problems, "; "))
	}
	return in, nil // on error: send it back as an is_error tool_result
}
```

Locally, this check rejected a price sent as a string, an unknown field, and an empty SKU with a wrong currency code, each with a message the model can act on.

> 在本地测试中，这个检查拒绝了以字符串形式发送的价格、一个未知字段，以及一个 SKU 为空且币种代码错误的输入，每一种都附带了模型可以据此修正的说明。

**A routing option.** The restriction applies to Fable and Mythos models only, so strict extraction can move to Claude Opus 5.5 or another model where structured outputs remain available, with Claude Fable 5.2 kept for the hard reasoning steps. Decide with your eval, on this merchant's documents.

> **一个路由上的选择。** 这个限制只针对 Fable 和 Mythos 系列模型，所以 strict 抽取可以转到 Claude Opus 5.5 或其他仍然可以使用结构化输出的模型上，而 Claude Fable 5.2 保留给困难的推理步骤。用你的评测、在这个商家的文档上做决定。

**Trade-offs.** Validation in code costs retries and engineering time, and some invalid inputs will still need a second turn. Moving the step to another model keeps the API guarantee but may change extraction quality. Either way, keep one schema definition that both the tool and the validator use, so they cannot drift apart.

> **权衡。** 在代码里做校验会带来重试成本和工程投入，而且有些无效输入仍然需要再来一轮。把这一步换到另一个模型上可以保留 API 层面的保证，但可能会改变抽取质量。无论哪种方式，都要让工具和校验器共用同一份 schema 定义，这样两者就不会出现偏差。

</details>

## 5. A pull request claims the new prompt cut the checkout assistant's p99 latency from 14 s to 9 s: deciding whether to believe it

**一个 PR 声称新提示词把结账助手的 p99 延迟从 14 秒降到了 9 秒：判断这个结论是否可信** · `Evals & Observability` · `Senior`

### Question · 题目

An engineer rewrote the checkout assistant's prompt and reports that p99 latency fell from 14 seconds to 9 seconds. How it was measured:

> 一位工程师重写了结账助手的提示词，并报告说 p99 延迟从 14 秒降到了 9 秒。测量方式如下：

- the baseline numbers come from yesterday's run, and the new prompt ran this morning;
  > 基线数据来自昨天的运行，而新提示词是今天上午跑的；
- 40 tasks, and the best of three runs was reported;
  > 40 个任务，报告的是三次运行中最好的那一次；
- the client was a laptop on VPN;
  > 客户端是一台连着 VPN 的笔记本电脑；
- times include the SDK's automatic retries;
  > 耗时里包含了 SDK 的自动重试；
- the new prompt ran after a warm-up pass, and the baseline started cold.
  > 新提示词是在一轮预热之后跑的，而基线是冷启动开始的。

Should the team ship it? Design a measurement that can decide.

> 团队应该上线它吗？设计一个能够做出判断的测量方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The same request can take noticeably different times from one hour to the next for reasons that have nothing to do with the change. A latency claim counts only if it beats that noise, measured on the same tasks, in the same run, with the versions interleaved.

> **核心思想。** 同一个请求在不同时段的耗时可能明显不同，原因与这次修改毫无关系。只有当一个延迟结论能够超出这种噪声，并且是在同一批任务上、同一次运行中、两个版本交替执行测得的，它才算数。

**What is wrong with this measurement.**

> **这个测量方式有什么问题。**

- **Another day's baseline.** Service speed drifts, and the drift reads as the change's effect. Time the comparison in the same run.
  > **用另一天的基线。** 服务速度会漂移，而这种漂移会被误读成修改带来的效果。对照组要在同一次运行中计时。
- **Best of three.** The best of several noisy results is partly luck.
  > **三次取最好。** 多个有噪声的结果中最好的那个，部分是运气。
- **p99 from 40 tasks.** A percentile needs roughly ten tasks beyond it: on the order of 100 tasks for p90 and 1,000 for p99. Repeats of the same tasks do not count toward that.
  > **用 40 个任务算 p99。** 一个百分位数大约需要有十个任务落在它之外：p90 大约需要 100 个任务，p99 大约需要 1,000 个。重复运行同样的任务不算在内。
- **Retries inside the seconds.** Whichever version met more transient errors looks slower. Compare final attempts, and report retries separately.
  > **耗时中包含重试。** 哪个版本碰上的瞬时错误更多，哪个就显得更慢。比较最终那一次尝试的耗时，并单独报告重试情况。
- **Warm against cold.** A cache write reads as a regression. Warm each version's cache and drop its first request.
  > **预热对比冷启动。** 一次缓存写入会被误读成性能退化。要分别预热每个版本的缓存，并丢弃各自的第一个请求。
- **The wrong client.** Measure from a client and path production users see, or per-call overhead they never meet inflates every saving.
  > **客户端不对。** 要从生产用户实际使用的客户端和网络路径上测量，否则那些用户根本遇不到的每次调用开销，会夸大每一项节省。

**A measurement that can decide.** Run both prompts on the same tasks, alternating A and B, with the same number of requests in flight and below rate limits. First measure the noise: two runs of the current prompt, side by side. Decide in advance what counts as a difference, for example a 95% bootstrap interval on the ratio that excludes 1, and call anything else "can't tell". Report the ratio at the chosen percentile with its interval.

> **一个能够做出判断的测量方案。** 让两个提示词在同一批任务上运行，A 和 B 交替进行，同时在途的请求数保持一致，并且低于限流阈值。先测量噪声：让当前提示词并排跑两次。事先确定什么才算有差异，比如比值的 95% bootstrap 区间不包含 1，其余情况一律算作「无法判断」。报告在所选百分位上的比值及其区间。

```go
func p90(xs []float64) float64 {
	s := append([]float64(nil), xs...)
	sort.Float64s(s)
	return s[int(0.9*float64(len(s)-1))]
}

// Paired by task: a[i] and b[i] are the same task, run interleaved in one session.
// Returns the p90 ratio b/a with a 95% bootstrap interval over tasks.
func ratioP90(a, b []float64, rounds int) (ratio, lo, hi float64) {
	ratio = p90(b) / p90(a)
	rs := make([]float64, rounds)
	ra, rb := make([]float64, len(a)), make([]float64, len(b))
	for r := range rs {
		for i := range a {
			j := rand.Intn(len(a)) // resample tasks, keeping each pair together
			ra[i], rb[i] = a[j], b[j]
		}
		rs[r] = p90(rb) / p90(ra)
	}
	sort.Float64s(rs)
	return ratio, rs[rounds*25/1000], rs[rounds*975/1000]
}
```

Locally, with 40 simulated tasks and no real change, the interval included 1, so the answer was "can't tell". With 200 tasks and a real 20% cut, the interval was well below 1.

> 在本地用 40 个模拟任务测试、实际没有变化时，区间包含 1，所以结论是「无法判断」。用 200 个任务、实际降低 20% 时，区间明显低于 1。

**Match the change to the percentile.** p50 moves with round trips and output tokens; the tail comes from long tasks, sampling variance or stalls such as cold caches, retries and slow tools. A prompt that shortens replies usually moves p50 first. To claim a p99 win, compare the slowest tasks' profiles before and after, and use production logs if the eval is too small. Timing also says nothing about quality, so run the eval before shipping.

> **让修改与百分位相对应。** p50 随往返次数和输出 token 变化；而长尾来自耗时长的任务、采样波动，或者冷缓存、重试和慢工具这类停顿。一个让回复变短的提示词通常首先影响的是 p50。要宣称 p99 有改善，就要比较修改前后最慢那些任务的剖析数据；如果评测集太小，就用生产日志。计时也完全说明不了质量，所以上线之前还要跑评测。

**Trade-offs.** A proper comparison costs more requests and a day of setup, and often ends in "can't tell". That is still more useful than shipping on a number that drift could have produced.

> **权衡。** 一次严谨的比较需要更多的请求和一天的准备工作，而且结果往往是「无法判断」。但这仍然比依据一个可能完全由漂移造成的数字去上线要有用。

</details>
