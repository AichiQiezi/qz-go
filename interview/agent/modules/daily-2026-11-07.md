## 1. Starting tools before the model finishes its turn: which calls may run early, and what to throw away when the response ends in max_tokens or refusal

**在模型说完之前就开始执行工具：哪些调用可以提前跑，以及响应以 max_tokens 或 refusal 结束时要丢弃什么** · `Agent Loop` · `Hard`

### Question · 题目

A listing-repair agent streams its responses. In a typical turn the model calls three or four tools: `get_listing`, `get_feed_errors`, `get_competitor_price`, and sometimes `update_listing`. Today the loop waits for the whole response, then runs the calls one by one and sends each result in its own user message. A product takes minutes. An engineer proposes starting every tool as soon as its `tool_use` block finishes streaming.

> 一个修复商品信息的 Agent 以流式方式返回响应。在典型的一轮中，模型会调用三到四个工具：`get_listing`、`get_feed_errors`、`get_competitor_price`，有时还有 `update_listing`。目前循环会等整个响应结束，然后逐个执行这些调用，并把每个结果放在单独的用户消息里发回去。处理一个商品要花好几分钟。一位工程师提议：每个 `tool_use` 块一流式输出完毕，就立刻启动对应的工具。

What would you change, what is safe to start early, and what can go wrong?

> 你会改哪些地方？哪些调用可以安全地提前启动？可能出什么问题？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** While the model is still writing the rest of its turn, a tool that only reads data can already be running, so tool time overlaps model time. But anything started early is a bet that the turn will finish normally. Only start work you can throw away.

> **核心思想。** 当模型还在写这一轮剩下的内容时，一个只读数据的工具就已经可以运行了，这样工具耗时就与模型耗时重叠起来。但任何提前启动的工作，都是在赌这一轮会正常结束。只启动那些可以丢弃的工作。

**Where the time goes.** A task's time is roughly the number of calls times the time to first token, plus output tokens divided by output speed, plus everything outside the model: tools, network, retries. The current loop inflates the last term twice: it runs independent calls one after another, and it waits for the whole response before starting any of them.

> **时间花在哪里。** 一个任务的耗时大致等于：调用次数乘以首 token 时间，加上输出 token 数除以输出速度，再加上模型之外的一切：工具、网络、重试。当前的循环把最后一项放大了两次：它把相互独立的调用一个接一个地执行，而且要等整个响应结束才开始执行其中任何一个。

**First fix the easy part.** When the model returns several `tool_use` blocks in one response, run the independent ones concurrently and return all the `tool_result` blocks together in a single user message, before any text. Sending each result in its own message also teaches the model to stop making parallel calls. A failed call still gets a result, with `is_error: true`.

> **先修简单的部分。** 当模型在一个响应里返回多个 `tool_use` 块时，并发执行其中相互独立的调用，并把所有 `tool_result` 块放在同一条用户消息中一起返回，且放在任何文本之前。把每个结果放进单独的消息，还会让模型渐渐不再发起并行调用。失败的调用也要返回结果，并设置 `is_error: true`。

**Then start read-only tools early.** In a streamed response each tool call ends with its own `content_block_stop` event, so the loop can start an independent, read-only tool at that moment. This breaks the usual rule of checking the stop reason before running any tool, which is why it is limited to tools with no side effects.

> **再提前启动只读工具。** 在流式响应中，每个工具调用都以它自己的 `content_block_stop` 事件结束，因此循环可以在那一刻启动一个独立的、只读的工具。这打破了「在运行任何工具之前先检查 stop reason」的常规做法，所以只限于没有副作用的工具。

- **Validate the input first.** With `eager_input_streaming` on, the API does not validate tool input, and the SDK's tolerant parser can return a silently truncated object. Check it against the schema before starting anything.
  > **先校验输入。** 开启 `eager_input_streaming` 时，API 不会校验工具输入，而 SDK 的容错解析器可能悄悄返回一个被截断的对象。在启动任何东西之前，先用 schema 校验它。
- **Discard on `max_tokens` or `refusal`.** A refusal can cut a `tool_use` off mid-input, and a truncated input often still parses. If the turn ends with either stop reason, cancel the early work and use none of its results.
  > **遇到 `max_tokens` 或 `refusal` 时丢弃。** refusal 可能把一个 `tool_use` 截断在输入中途，而被截断的输入往往仍然能被解析。如果这一轮以这两种 stop reason 之一结束，就取消提前启动的工作，并且不使用它的任何结果。
- **Never start writes early.** `update_listing` runs only after the full response has arrived with `stop_reason` equal to `tool_use`.
  > **绝不提前启动写操作。** `update_listing` 只在完整响应到达、且 `stop_reason` 等于 `tool_use` 之后才执行。

```go
type call struct{ ID, Name string; Input json.RawMessage }

type turn struct {
	ctx     context.Context
	cancel  context.CancelFunc
	pending map[string]chan result // started early, keyed by tool_use ID
}

// Called at content_block_stop for each tool_use block.
func (t *turn) onToolDone(c call) {
	if !readOnly[c.Name] || validate(c) != nil {
		return // writes and invalid input wait for the end of the turn
	}
	ch := make(chan result, 1)
	t.pending[c.ID] = ch
	go func() { ch <- run(t.ctx, c) }()
}

// Called once the response is complete.
func (t *turn) finish(stop string, calls []call) ([]result, bool) {
	if stop == "max_tokens" || stop == "refusal" {
		t.cancel() // throw the early work away
		return nil, false
	}
	return collect(t.ctx, t.pending, calls), true // start the rest concurrently, keep call order
}
```

**Prove it.** Time the old and new loop side by side, on the same products, in the same run, because service speed drifts during the day; and run the eval, because a faster loop that changes answers is not a win.

> **证明它有效。** 在同一次运行中、针对同样的商品，把旧循环和新循环并排计时，因为服务速度在一天中会有波动；同时运行评测，因为一个更快但改变了答案的循环并不算成功。

**Trade-offs.** Early starts waste calls whenever a turn is discarded, and those calls count against the merchants' Meta and Google rate limits. The gain is bounded by how much tool time can overlap the rest of the response: if the model writes one short call and stops, there is little to overlap. Tools with side effects or ordering requirements stay sequential.

> **取舍。** 每当某一轮被丢弃，提前启动的调用就白白浪费了，而这些调用会计入商家在 Meta 和 Google 的限流额度。收益的上限取决于工具耗时能与响应剩余部分重叠多少：如果模型只写了一个简短的调用就停下，就几乎没有可以重叠的部分。有副作用或有顺序要求的工具仍然要按顺序执行。

</details>

## 2. The feed-debugging agent got a hand-written tool named "bash": using the Anthropic-defined bash and text editor tools, and what your handler must do

**给 feed 排查 Agent 手写了一个名为 "bash" 的工具：改用 Anthropic 定义的 bash 和文本编辑器工具，以及处理函数必须做些什么** · `Tools & MCP` · `Medium`

### Question · 题目

A support agent helps engineers debug merchants' product feeds. It runs in a worker container that holds the downloaded feed files. The team declared a custom tool `{"name": "bash", "input_schema": {"cmd": "string"}}` and a custom `edit_file` tool, and the handler passes `cmd` straight to `sh -c`. The model sometimes sends inputs the schema did not expect, a stuck command hangs the loop, and a reviewer notices the agent once ran `curl ... | sh` from a feed URL.

> 一个支持 Agent 帮助工程师排查商家的商品 feed。它运行在一个存放已下载 feed 文件的 worker 容器中。团队声明了一个自定义工具 `{"name": "bash", "input_schema": {"cmd": "string"}}` 和一个自定义的 `edit_file` 工具，处理函数把 `cmd` 直接交给 `sh -c` 执行。模型有时会发来 schema 没有预料到的输入，一个卡住的命令会让循环挂起，评审人员还发现 Agent 曾经从一个 feed URL 执行过 `curl ... | sh`。

How should the tools be declared and handled?

> 应该如何声明和处理这些工具？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Claude already knows a built-in bash tool and a built-in text editor. Declare those instead of inventing look-alikes, and spend your effort on the part that is always yours: running the commands safely.

> **核心思想。** Claude 已经熟悉一个内置的 bash 工具和一个内置的文本编辑器。直接声明它们，而不是自己发明外观相似的工具，把精力花在始终由你负责的部分上：安全地执行命令。

**Why the custom tool behaves oddly.** The bash and text editor tools are Anthropic-defined and schema-less: you declare them by `type` and `name` only, and their input schema is built into the model. A custom tool that happens to be called `bash` is just a user-defined tool with your schema, without the built-in behavior.

> **为什么自定义工具表现古怪。** bash 和文本编辑器工具是 Anthropic 定义的、不带 schema 的工具：只需通过 `type` 和 `name` 声明，它们的输入 schema 已内置在模型中。一个恰好名叫 `bash` 的自定义工具，只是一个使用你自己 schema 的用户定义工具，并不具备内置的行为。

```go
Tools: []anthropic.ToolUnionParam{
    {OfBashTool20250124: &anthropic.ToolBash20250124Param{}},
    {OfTextEditor20250728: &anthropic.ToolTextEditor20250728Param{}},
},
```

**What the handler receives.** Both tools are client-executed: Claude returns a `tool_use` block, your code performs the action, and you send back a `tool_result`. The API is stateless, so your application keeps the shell session and files between turns. Bash input is either `{"command": "..."}` or `{"restart": true}`: check `restart` first and reset the session, otherwise run the command and return stdout and stderr together. The text editor sends `view`, `create`, `str_replace` or `insert`; `str_replace` must replace exactly one occurrence and return an error for zero or several matches.

> **处理函数会收到什么。** 这两个工具都由客户端执行：Claude 返回一个 `tool_use` 块，你的代码执行相应操作，然后发回一个 `tool_result`。API 是无状态的，所以由你的应用在各轮之间保留 shell 会话和文件。bash 的输入要么是 `{"command": "..."}`，要么是 `{"restart": true}`：先检查 `restart` 并重置会话，否则执行命令，并把 stdout 和 stderr 合在一起返回。文本编辑器会发送 `view`、`create`、`str_replace` 或 `insert`；`str_replace` 必须恰好替换一处，匹配为零处或多处时要返回错误。

```go
func handleBash(ctx context.Context, sh *Shell, id string, raw string) anthropic.ContentBlockParamUnion {
	var in struct {
		Command string `json:"command"`
		Restart bool   `json:"restart"`
	}
	if err := json.Unmarshal([]byte(raw), &in); err != nil {
		return anthropic.NewToolResultBlock(id, "invalid input: "+err.Error(), true)
	}
	if in.Restart {
		sh.Reset()
		return anthropic.NewToolResultBlock(id, "shell restarted", false)
	}
	if err := allowed(in.Command); err != nil { // allowlist, no shell operators
		return anthropic.NewToolResultBlock(id, err.Error(), true)
	}
	ctx, cancel := context.WithTimeout(ctx, 30*time.Second)
	defer cancel()
	out, err := sh.Run(ctx, in.Command) // stdout and stderr combined
	log.Printf("bash id=%s cmd=%q err=%v", id, in.Command, err)
	return anthropic.NewToolResultBlock(id, out, err != nil)
}
```

- **Commands are untrusted model output.** Run them in an isolated container or VM as a restricted user. Anthropic hosts no sandbox for client-side tools, so the isolation is yours.
  > **命令是不可信的模型输出。** 以受限用户身份在隔离的容器或虚拟机中执行它们。Anthropic 不为客户端工具托管沙箱，所以隔离由你负责。
- **Allowlist executables and reject shell operators** such as `&&`, `|`, `;`, backticks and `$()`. A blocklist is not enough; `curl ... | sh` is exactly what it misses.
  > **对可执行程序使用白名单，并拒绝 shell 操作符**，例如 `&&`、`|`、`;`、反引号和 `$()`。黑名单是不够的；`curl ... | sh` 正是它会漏掉的情况。
- **Set timeouts and resource limits, and log every command,** so one stuck command cannot hang the loop.
  > **设置超时和资源限制，并记录每一条命令**，这样一个卡住的命令就不会让循环挂起。
- **Confine editor paths to one root.** Resolve each path and reject anything that leaves the feed directory.
  > **把编辑器路径限制在一个根目录内。** 解析每个路径，拒绝任何离开 feed 目录的路径。
- **Return errors as results.** Use `is_error: true` so Claude can recover, instead of failing the loop.
  > **把错误作为结果返回。** 使用 `is_error: true`，让 Claude 可以自行恢复，而不是让循环失败。

**Trade-offs.** An allowlist without pipes makes the shell less powerful: no `grep | head`. Add small purpose-built tools for the common jobs, such as "count items with errors in this feed", which are easier to secure and review. If the task needs only computation and not the merchant's local files, Anthropic's server-side code execution tool avoids hosting a sandbox at all.

> **取舍。** 不允许管道的白名单会让 shell 的能力变弱：不能用 `grep | head`。为常见工作添加小型的专用工具，例如「统计这个 feed 中出错的商品数」，它们更容易保障安全，也更容易评审。如果任务只需要计算而不需要商家的本地文件，Anthropic 的服务端代码执行工具可以让你完全不必托管沙箱。

</details>

## 3. Trimming old tool results by hand breaks the cache, and after a model upgrade requests fail with "bound to a different conversation"

**手动裁剪旧的工具结果破坏了缓存，升级模型后请求还报错 "bound to a different conversation"** · `Context & Memory` · `Medium`

### Question · 题目

A catalog-audit agent runs for hundreds of turns per merchant. Each `get_product_page` result is large, so before every request the loop replaces the content of tool results older than 20 turns with `[removed]`. Input cost went up instead of down. After moving to Claude Opus 5.5, some requests also fail with a 400: `Invalid signature in thinking block ... bound to a different conversation`.

> 一个商品目录审核 Agent 对每个商家要运行数百轮。每次 `get_product_page` 的结果都很大，所以循环在每次请求之前，把 20 轮之前的工具结果内容替换成 `[removed]`。输入成本不降反升。迁移到 Claude Opus 5.5 之后，有些请求还会报 400：`Invalid signature in thinking block ... bound to a different conversation`。

Explain both effects and redesign how the agent keeps its context small.

> 解释这两个现象，并重新设计 Agent 保持上下文精简的方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Both the prompt cache and the model's earlier thinking are tied to the exact bytes of the conversation that came before. Rewriting the past, even to shrink it, throws both away. Shrink the context with the tools the API provides, which do not count as rewriting.

> **核心思想。** 提示缓存和模型之前的思考都与之前对话的确切字节绑定。改写过去的内容，哪怕只是为了缩小它，也会让这两者都失效。应该用 API 提供的工具来缩小上下文，这些工具不算作改写。

**Why cost went up.** Caching is a prefix match: any byte change invalidates everything after it. Each request changed a tool result near the start of the window, so almost the whole conversation was written to the cache again at the write premium instead of being read cheaply.

> **为什么成本上升了。** 缓存是前缀匹配：任何字节变化都会让它之后的所有内容失效。每次请求都修改了窗口开头附近的一个工具结果，于是几乎整个对话都要按写入溢价重新写入缓存，而不是被低价读取。

**Why the 400 appeared.** Claude Opus 5.5 runs the history-editing check that the docs call preserved thinking: a thinking block stays valid only while the `system` prompt, the `tools` and every earlier message are byte-identical to when it was produced. It is enforced by default for accounts created on or after August 31, 2026. Replacing old tool results is exactly such an edit, so later thinking blocks no longer match.

> **为什么出现 400。** Claude Opus 5.5 会执行文档中称为 preserved thinking 的历史编辑检查：只有当 `system` 提示、`tools` 以及所有更早的消息与生成某个思考块时逐字节相同，这个思考块才保持有效。对于 2026 年 8 月 31 日及之后创建的账户，这项检查默认强制执行。替换旧的工具结果正是这样一种编辑，所以之后的思考块就对不上了。

**Fix: let the server clear old results.** Server-side context editing clears old tool results before the model sees them. It does not count as an edit, because the check compares the conversation as you sent it.

> **修复：让服务端清理旧结果。** 服务端的上下文编辑会在模型看到对话之前清理旧的工具结果。它不算作编辑，因为检查比较的是你发送出去的对话。

```json
{
  "model": "claude-opus-5-5",
  "context_management": {
    "edits": [{"type": "clear_tool_uses_20250919"}]
  }
}
```

- **It is a beta.** Send it on the beta messages endpoint with the `context-management-2025-06-27` header. `clear_tool_inputs: true` also clears the matching `tool_use` inputs.
  > **它是 beta 功能。** 通过 beta messages 接口发送，并带上 `context-management-2025-06-27` 头。`clear_tool_inputs: true` 还会清理对应的 `tool_use` 输入。
- **Clear rarely, in large batches.** Every clearing pass rewrites the cached conversation. Set the trigger high and use `clear_at_least`, so a clear is skipped unless it removes enough to be worth the cache write.
  > **少清理，且一次清理一大批。** 每次清理都会改写已缓存的对话。把触发阈值设高，并使用 `clear_at_least`，这样只有当一次清理能移除足够多的内容、值得付出缓存写入代价时才会执行。
- **Keep the transcript append-only.** Send the conversation exactly as received, and add new instructions as appended messages instead of editing old ones.
  > **让对话记录只追加不修改。** 完全按收到的样子发送对话，新的指令以追加消息的形式加入，而不是编辑旧消息。
- **Recover once, then stop editing.** For a conversation that already fails, strip the named thinking block and every thinking block after it; text and tool calls stay.
  > **恢复一次，然后停止编辑。** 对于已经失败的对话，去掉报错中指明的思考块及其之后的所有思考块；文本和工具调用保留。

**When clearing is not enough.** Near the window limit, use server-side compaction, or simple client-side compaction: summarize the conversation into one message and start the next request with that summary plus the new user turn, replaying nothing else. For facts the agent must keep across merchants or sessions, use memory, not the transcript.

> **当清理还不够时。** 接近窗口上限时，使用服务端压缩，或者简单的客户端压缩：把对话总结成一条消息，下一次请求以这条总结加上新的用户轮次开始，其他内容一概不重放。对于 Agent 必须在不同商家或会话之间保留的事实，使用记忆，而不是对话记录。

**Trade-offs.** Context editing is a context-window tool, not a savings lever: in the run measured for the platform docs it cost more than it saved. Cleared results are gone, so the agent must fetch a page again if it needs it, and it should note key findings in its own words before they are cleared. Message threads cannot be combined with most context editing, so pick one approach per workload.

> **取舍。** 上下文编辑是一个管理上下文窗口的工具，而不是省钱的手段：在平台文档所做的测量中，它花掉的比省下的还多。被清理的结果就没有了，所以 Agent 如果还需要某个页面，就得重新获取；在结果被清理之前，它应该用自己的话把关键发现记下来。消息线程无法与大多数上下文编辑功能同时使用，所以每类工作负载只选一种方案。

</details>

## 4. Twenty subagents start at the same moment with the same 30K-token brief, and none of them reads the cache

**二十个子 Agent 在同一时刻启动，带着同一份 3 万 token 的说明，却没有一个读到缓存** · `Multi-agent` · `Hard`

### Question · 题目

A lead agent audits a merchant's catalog by splitting it into 20 slices and starting 20 subagent requests at once. Each request begins with the same 30K-token brief: ad-policy rules, the merchant's brand guide and the output format, marked with `cache_control`. Then comes the slice of products and the subagent's instructions, which include the slice number and the current time. The usage logs show `cache_creation_input_tokens` near 30K on all 20 requests and `cache_read_input_tokens` of zero, every night.

> 一个主 Agent 审核商家的商品目录：把目录拆成 20 个切片，同时发起 20 个子 Agent 请求。每个请求都以同一份 3 万 token 的说明开头：广告政策规则、商家的品牌指南和输出格式，并标记了 `cache_control`。后面是这个切片的商品以及子 Agent 的指令，其中包含切片编号和当前时间。使用日志显示，每天晚上这 20 个请求的 `cache_creation_input_tokens` 都接近 3 万，而 `cache_read_input_tokens` 都是零。

Explain why and redesign the fan-out.

> 解释原因，并重新设计这次扇出。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A cache entry is written by one request and can be read only after that request has started answering. Twenty requests sent together all arrive before anything is readable, so each one pays to write the same brief.

> **核心思想。** 缓存条目由一个请求写入，并且只有在这个请求开始作答之后才能被读取。一起发出的二十个请求都在任何内容可读之前就到达了，所以每个请求都要为写入同一份说明付费。

**The mechanism.** An entry becomes readable only after the first response begins streaming. N parallel requests with identical prefixes all pay full price, because none can read what the others are still writing. Cache writes cost more than plain input, 1.25 times the base input price for the 5-minute TTL, so this fan-out pays a premium on the brief 20 times.

> **机制。** 只有在第一个响应开始流式输出之后，缓存条目才可读。N 个前缀相同的并行请求都要付全价，因为谁也读不到其他请求仍在写入的内容。缓存写入比普通输入更贵，5 分钟 TTL 的写入价格是基础输入价格的 1.25 倍，所以这次扇出要为这份说明付 20 次溢价。

**Fix: gate the fan-out on the first token.** Send one request, wait for its first streamed token, not the full response, then start the other 19. They read the entry the first one just wrote. Alternatively, pre-warm before the fan-out with a `max_tokens: 0` request, which writes the cache and returns immediately with no output tokens billed; send it without streaming, because `max_tokens: 0` does not accept `stream: true`, and with the same `thinking` and `effort` settings as the real requests, which are part of the cached prompt.

> **修复：以第一个 token 作为扇出的闸门。** 先发送一个请求，等待它流式返回的第一个 token，而不是完整的响应，然后再启动其余 19 个请求。它们会读取第一个请求刚刚写入的条目。另一种做法是在扇出之前用一个 `max_tokens: 0` 的请求预热，它会写入缓存并立即返回，不计输出 token 费用；发送时不要开启流式，因为 `max_tokens: 0` 不接受 `stream: true`，并且要使用与真实请求相同的 `thinking` 和 `effort` 设置，因为它们是被缓存的提示的一部分。

```go
func fanOut(ctx context.Context, slices []Slice) []Result {
	results := make([]Result, len(slices))
	firstToken := make(chan struct{})
	var once sync.Once
	var wg sync.WaitGroup

	wg.Add(1)
	go func() { // the first request writes the shared brief
		defer wg.Done()
		open := func() { once.Do(func() { close(firstToken) }) }
		defer open() // never leave the gate shut if this request fails early
		results[0] = runSubagent(ctx, slices[0], open)
	}()

	select {
	case <-firstToken: // the entry is readable now
	case <-ctx.Done():
		return nil
	}
	sem := make(chan struct{}, 8) // stay inside rate limits
	for i := 1; i < len(slices); i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			sem <- struct{}{}
			defer func() { <-sem }()
			results[i] = runSubagent(ctx, slices[i], nil)
		}(i)
	}
	wg.Wait()
	return results
}
```

- **Make the shared prefix byte-identical.** Workers that build slightly different prompts over the same context write separate entries and read none of each other's. Put the slice number, the time and the products after the breakpoint.
  > **让共享前缀逐字节相同。** 在同一上下文之上各自拼出略有不同提示的 worker，会写入各自独立的条目，谁也读不到谁的。把切片编号、时间和商品放在断点之后。
- **Same model, same cache.** Caches are model-scoped. A lead on Claude Opus 5.5 and workers on Claude Haiku 5.5 do not share entries, so warm the cache with the workers' model.
  > **同一模型，才有同一缓存。** 缓存按模型隔离。运行在 Claude Opus 5.5 上的主 Agent 和运行在 Claude Haiku 5.5 上的 worker 不共享条目，所以要用 worker 的模型来预热缓存。
- **Check the minimum.** The minimum cacheable prefix depends on the model; a 30K brief is far above it, but a short brief may silently not cache.
  > **检查最小长度。** 可缓存前缀的最小长度取决于模型；3 万 token 的说明远高于这个下限，但一份很短的说明可能会悄无声息地无法缓存。
- **Verify in usage.** After the change, one request should show the write and the others `cache_read_input_tokens` near 30K.
  > **在 usage 中验证。** 改动之后，应该只有一个请求显示写入，其余请求的 `cache_read_input_tokens` 接近 3 万。

**What it saves.** With reads at about 0.1 times the base price, 20 concurrent writes cost about 25 brief-equivalents of input, while one write plus 19 reads cost about 3.2; on Claude Opus 5.5, where reads are 0.05 times, it is about 2.2. The gate costs one time-to-first-token of extra wall-clock time for the whole job.

> **能省多少。** 读取价格约为基础价格的 0.1 倍时，20 次并发写入的输入成本约相当于 25 份说明，而一次写入加 19 次读取只相当于约 3.2 份；在读取价格为 0.05 倍的 Claude Opus 5.5 上，约为 2.2 份。代价是整个任务多出一次首 token 时间的耗时。

**Trade-offs.** Judge the design on the whole job's seconds, quality and cost, not one subagent's. When input cost dominates, fewer lanes over the same prefix, or one worker making several passes, can beat 20 lanes. Concurrency is also bounded by rate limits, so the semaphore matters as much as the gate.

> **取舍。** 评价这个设计时，要看整个任务的耗时、质量和成本，而不是单个子 Agent 的。当输入成本占主导时，在同一前缀上使用更少的并行通道，或者让一个 worker 分多次处理，可能比 20 个通道更划算。并发度还受到限流的约束，所以信号量和闸门同样重要。

</details>

## 5. AI-generated ad creatives: what content provenance marks, why downloaded image checksums changed, and what you can promise merchants

**AI 生成的广告素材：内容来源标记了什么，为什么下载的图片校验和变了，以及可以向商家承诺什么** · `Safety & Security` · `Senior`

### Question · 题目

Your platform lets merchants generate ad copy with Claude Fable 5.1 and produce banner images in the code-execution sandbox, downloaded through the Files API. Three things happen in one week. The asset pipeline flags every banner as tampered, because the SHA-256 the agent logged inside the container does not match the downloaded file. A large merchant asks you to promise that ad platforms will never detect the copy as AI-written. Legal asks what the platform can say about AI-generated creatives.

> 你的平台允许商家用 Claude Fable 5.1 生成广告文案，并在代码执行沙箱中制作横幅图片，再通过 Files API 下载。一周之内发生了三件事。素材流水线把每一张横幅都标记为被篡改，因为 Agent 在容器内记录的 SHA-256 与下载后的文件对不上。一个大商家要求你承诺，广告平台永远不会把这些文案识别为 AI 所写。法务则询问平台对于 AI 生成的素材能说些什么。

As the senior engineer, explain what is happening and set the platform's policy.

> 作为资深工程师，解释发生了什么，并制定平台的政策。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Content Claude produces can carry marks of where it came from: a statistical watermark in text, and signed credentials in some media files. These are features to preserve and explain, not bugs to remove, and your own records must not depend on them.

> **核心思想。** Claude 生成的内容可以带有表明其来源的标记：文本中的统计水印，以及某些媒体文件中的签名凭证。这些是需要保留和说明的特性，而不是需要移除的 bug，同时你自己的记录也不应依赖它们。

**Why the checksums differ.** Supported image, audio and video files that Claude produces in the code-execution sandbox carry signed C2PA Content Credentials when downloaded through the Files API on the Claude API. The manifest adds a few kilobytes, so the downloaded file's size and checksum differ from the file inside the container. Nothing was tampered with. Text, PDF and office files are not signed, and the docs leave platform scope beyond the Claude API open.

> **为什么校验和不同。** Claude 在代码执行沙箱中生成的受支持的图片、音频和视频文件，在 Claude API 上通过 Files API 下载时，会带有签名的 C2PA 内容凭证。这份清单会增加几 KB，所以下载后文件的大小和校验和与容器内的文件不同。并没有发生篡改。文本、PDF 和 Office 文件不会被签名，而文档对 Claude API 之外各平台的适用范围没有给出定论。

**What the text carries.** Text from Claude Fable 5.1 and Claude Mythos 5.1 carries Anthropic's statistical text watermark on every platform. It adds no tokens or hidden characters and contains nothing about your organization. You cannot see it in the string, so stripping characters neither finds nor removes it.

> **文本带有什么。** Claude Fable 5.1 和 Claude Mythos 5.1 生成的文本，在所有平台上都带有 Anthropic 的统计文本水印。它不增加任何 token 或隐藏字符，也不包含任何关于你所在组织的信息。你在字符串中看不到它，所以删除字符既找不到它，也去不掉它。

**Fix the pipeline.** Treat the downloaded file as the artifact of record: compute its checksum after download, keep the container checksum only as a debugging field, and compare like with like.

> **修复流水线。** 把下载后的文件当作正式记录的产物：在下载之后计算它的校验和，容器内的校验和只作为调试字段保留，并且只比较同一类对象。

```go
type Creative struct {
	MerchantID   string
	FileID       string // Files API id
	Model        string
	RequestID    string
	SHA256       string // of the downloaded bytes: the record of truth
	ContainerSHA string // debugging only; differs when credentials are added
	AIGenerated  bool   // our own label, set at creation
}

func record(c *Creative, downloaded []byte) {
	sum := sha256.Sum256(downloaded)
	c.SHA256 = hex.EncodeToString(sum[:])
	c.AIGenerated = true
}
```

- **Keep your own provenance.** Label every creative as AI-generated in your database at creation, with merchant, model and request ID. That label works for every file type and model, which the embedded marks do not.
  > **保留你自己的来源记录。** 在创建时就在数据库中把每个素材标记为 AI 生成，并记录商家、模型和请求 ID。这个标记对所有文件类型和模型都有效，而嵌入的标记做不到这一点。
- **Preserve credentials by default.** Resizing and re-encoding for the CDN can drop embedded metadata; decide deliberately whether derived images keep it, and test that path.
  > **默认保留凭证。** 为 CDN 调整尺寸和重新编码可能会丢失嵌入的元数据；要有意识地决定派生图片是否保留它，并测试这条路径。
- **Do not build removal features.** Offering to strip credentials or launder text so it looks human-written misleads ad platforms and their users.
  > **不要开发去除标记的功能。** 提供剥离凭证或「洗稿」使其看起来像人写的功能，会误导广告平台及其用户。

**What to promise.** Promise neither that AI copy is undetectable nor that it is always detectable. Tell merchants which creatives are AI-generated, that some media carry signed credentials, and that they remain responsible for each ad platform's own disclosure rules. Write the policy, show the label in the creative library, and review it when the provenance docs change.

> **可以承诺什么。** 既不要承诺 AI 文案无法被识别，也不要承诺它总能被识别。告诉商家哪些素材是 AI 生成的、某些媒体文件带有签名凭证，以及他们仍需遵守各广告平台自己的披露规则。把政策写下来，在素材库中显示这个标记，并在来源相关文档变更时重新审视它。

**Trade-offs.** Clear labeling may lower some merchants' willingness to use generated creatives, and preserving credentials through every transform costs engineering time. But a platform that hides provenance takes on the risk when an ad platform or regulator asks, and a checksum policy built on the container file will keep producing false alarms.

> **取舍。** 清晰的标记可能会降低部分商家使用生成素材的意愿，而在每一次转换中保留凭证也要花费工程时间。但一个隐藏来源的平台，在广告平台或监管机构询问时要自己承担风险；而基于容器内文件建立的校验和策略，会不断产生误报。

</details>
