## 1. The support chat sits silent for 40 seconds, then dumps the whole answer

**客服聊天框沉默 40 秒，然后一下子吐出整段回答** · `Production` · `Medium`

### Question · 题目

Your merchant-support assistant lives in the admin dashboard. The Go backend calls the model without streaming, runs a tool loop (usually two to four tool calls), and returns the final text to the browser in one HTTP response.

> 你们的商家客服助手嵌在后台管理页面里。Go 后端以非流式方式调用模型，跑一个工具调用循环（通常两到四次工具调用），然后在一个 HTTP 响应里把最终文本返回给浏览器。

Merchants stare at a spinner for 20 to 40 seconds. Some requests fail because the API gateway closes connections after 30 seconds. Long answers sometimes stop in the middle of a sentence. How would you redesign this so users see progress? What goes over the wire when you stream, and which new failure modes do you have to handle?

> 商家要盯着加载图标等 20 到 40 秒。有些请求会失败，因为 API 网关在 30 秒后会关闭连接。较长的回答有时会在句子中间戛然而止。你会如何重新设计，让用户能看到进度？开启流式之后线路上传输的是什么？你又需要处理哪些新的故障模式？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Streaming does not make the model faster: the total generation time stays roughly the same. It changes when the user sees the first output, and it keeps the connection busy so that proxies do not close it as idle. An agent has two streams to design: the model's token stream into your backend, and your backend's progress stream out to the browser.

> **核心思路。** 流式并不会让模型变快：总的生成时间大致不变。它改变的是用户看到第一段输出的时间，并且让连接一直有数据流动，代理就不会把它当作空闲连接关掉。一个 Agent 要设计两条流：模型流入你后端的 token 流，以及你后端流向浏览器的进度流。

**What goes over the wire.** With streaming on, the Messages API sends server-sent events instead of one JSON body. A response starts with `message_start`. Each content block then arrives as `content_block_start`, a series of `content_block_delta` events and `content_block_stop`. Text comes as `text_delta` fragments; a tool call's input comes as `input_json_delta` fragments of partial JSON. Near the end, `message_delta` carries the `stop_reason` and the final usage, and `message_stop` closes the message. The SDKs accumulate these events for you and offer a helper that returns the assembled final message.

> **线路上传输的是什么。** 开启流式后，Messages API 发送的是 server-sent events（SSE），而不是一个完整的 JSON 响应体。响应以 `message_start` 开头。随后每个内容块依次以 `content_block_start`、一串 `content_block_delta` 事件和 `content_block_stop` 到达。文本以 `text_delta` 片段的形式到达；工具调用的输入以 `input_json_delta` 片段的形式到达，内容是不完整的 JSON。快结束时，`message_delta` 带来 `stop_reason` 和最终的用量统计，`message_stop` 结束这条消息。SDK 会帮你累积这些事件，并提供一个直接返回组装好的最终消息的辅助方法。

**Why the current design fails.**

> **现在的设计为什么会出问题。**

- Spinner: nothing reaches the browser until the last model call finishes, so the user waits through every turn of the loop.
  > 加载图标：最后一次模型调用结束之前，浏览器什么都收不到，所以用户要把循环的每一轮都等完。
- Gateway timeout: one HTTP request holds the whole loop open, and the gateway's 30-second limit kills it even though the work is going fine. Long non-streaming model calls can also hit the SDK's own HTTP timeouts, which is why the SDKs recommend streaming for large outputs.
  > 网关超时：一个 HTTP 请求要撑住整个循环，即使任务进展正常，网关的 30 秒限制也会把它掐断。较长的非流式模型调用还可能触发 SDK 自己的 HTTP 超时，所以 SDK 建议大输出时使用流式。
- Cut-off answers: the response hit `max_tokens`. That is a stop reason, not an error, so the code returned half an answer as if it were complete.
  > 回答被截断：响应触到了 `max_tokens`。这是一个停止原因，而不是错误，所以代码把半截回答当成完整回答返回了。

**Redesign: stream the loop, not just the tokens.** Run the agent as a job with a run ID instead of inside one request. The browser subscribes to that run over SSE or a WebSocket. The backend streams each model call and forwards text deltas as they arrive. Between model calls, the harness sends its own progress events: "Checking your Merchant Center feed..." when a tool call starts, "Found 140 disapproved items" when it returns. People tolerate waiting far better when they can see the agent working. Give every event a sequence number and keep a log, so a browser that reconnects can resume from the last event it saw, and send keepalive comments so idle proxies leave the stream open.

> **重新设计：让整个循环流式化，而不只是 token。** 把 Agent 作为一个带 run ID 的任务来运行，而不是放在一个请求里跑。浏览器通过 SSE 或 WebSocket 订阅这个 run。后端以流式调用模型，并在文本增量到达时立即转发。在两次模型调用之间，harness 发送它自己的进度事件：工具调用开始时发“正在检查你的 Merchant Center feed……”，工具返回时发“发现 140 个被拒登的商品”。看得到 Agent 在干活，人们对等待的容忍度会高得多。给每个事件一个序号并记录日志，这样浏览器重连后可以从它看到的最后一个事件继续；再定期发送 keepalive 注释，让空闲代理不要关闭这条流。

```go
// Events the browser understands. The harness emits them during and between model calls.
type Event struct {
	Seq  int64  `json:"seq"`  // lets a reconnecting browser resume after Last-Event-ID
	Kind string `json:"kind"` // "text", "tool_started", "tool_finished", "done", "error"
	Text string `json:"text,omitempty"`
}

func (r *Run) emit(kind, text string) {
	r.seq++
	ev := Event{Seq: r.seq, Kind: kind, Text: text}
	r.log.Append(ev)       // durable, so a reconnect can replay missed events
	r.subscribers.Send(ev) // fan out to every open SSE connection for this run
}
```

**Tool calls while streaming.** A tool call's input arrives as partial JSON, so never run a tool until its content block has stopped and you have parsed the complete input. The Claude API also lets you turn off server-side buffering of large tool inputs (`eager_input_streaming: true` on the tool), so long inputs start arriving sooner. The trade-off is that the API then no longer validates that input for you, so check it against the tool's schema yourself before running the tool, and treat invalid JSON as an error to report back, not as a crash.

> **流式过程中的工具调用。** 工具调用的输入是以不完整 JSON 的形式到达的，所以在这个内容块结束、你解析出完整输入之前，绝不要执行工具。Claude API 还允许你关闭服务端对大型工具输入的缓冲（在工具上设置 `eager_input_streaming: true`），这样较长的输入会更早开始到达。代价是 API 不再替你校验这个输入，所以在执行工具前要自己按工具的 schema 校验，并把无效 JSON 当作要回报的错误，而不是让程序崩溃。

**Check the stop reason of every call.** `end_turn`: the answer is complete. `tool_use`: run the tools and continue the loop. `max_tokens`: the output was cut off, so do not present it as finished and do not run a tool call from that turn; raise the limit or ask the model to continue. `refusal`: show a clear message and offer a human. Streaming adds one more case: an error event or a dropped connection after the user has already seen half an answer. Mark that message as interrupted in the UI and retry the model call, instead of silently appending a second copy of the same text.

> **检查每次调用的停止原因。** `end_turn`：回答已完成。`tool_use`：执行工具并继续循环。`max_tokens`：输出被截断了，所以不要把它当成完整结果展示，也不要执行这一轮里的工具调用；调高上限，或者让模型接着写。`refusal`：给出清楚的提示，并提供转人工。流式还多了一种情况：用户已经看到半段回答之后，出现错误事件或连接中断。这时在 UI 里把这条消息标记为“已中断”，然后重试这次模型调用，而不是悄悄把同样的文字再追加一遍。

**Trade-offs.** Streaming adds work on both ends: reconnects, partial state, and a UI that may show text that later turns out to be incomplete. Text a user has already seen cannot be taken back, so output checks that must run before display (for example, catching promises the agent is not allowed to make) either hold back a sentence or two at a time or run on the full answer before it is marked final. For short internal calls such as classification, plain non-streaming requests are simpler and perfectly fine.

> **取舍。** 流式会给两端都增加工作量：重连、不完整的中间状态，以及一个可能先显示、后来才发现不完整的文本的 UI。用户已经看到的文字是收不回来的，所以必须在展示之前运行的输出检查（比如拦截 Agent 无权做出的承诺）要么每次先扣住一两句话，要么在回答被标记为最终版本之前对全文运行。对于分类这类简短的内部调用，普通的非流式请求更简单，也完全够用。

</details>

## 2. Merchants are tired of repeating their preferences every session

**商家厌倦了每次会话都重复自己的偏好** · `Context & Memory` · `Medium`

### Question · 题目

Your ads assistant helps merchants manage Google and Meta campaigns. Merchants complain that they repeat the same things in every session: "we never discount below a 20% margin", "our brand voice is formal German", "don't touch the Brand campaigns".

> 你们的广告助手帮助商家管理 Google 和 Meta 的广告系列。商家抱怨每次会话都要重复同样的话：“我们的折扣从不让毛利低于 20%”“我们的品牌语气是正式的德语”“不要动 Brand 系列”。

The PM asks for memory across sessions. Design it: what you store, how memories are written and read back, and how you keep them correct and safe in a multi-tenant SaaS.

> 产品经理希望加上跨会话的记忆。请设计它：存什么，记忆如何写入、如何读回，以及在多租户 SaaS 里如何保证它正确且安全。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The model itself remembers nothing between requests: each request carries everything it knows. Memory is therefore a storage system you build. Something writes facts somewhere durable, and something puts the relevant ones back into the context later. The design questions are the ones you ask for any database: what to store, who may write, how to read, how to keep it correct, and how to delete.

> **核心思路。** 模型本身在请求之间什么都不记得：每个请求都携带了它所知道的全部内容。所以“记忆”是一个由你来构建的存储系统。某个环节把事实写到持久化的地方，另一个环节在之后把相关的内容放回上下文。要回答的设计问题和任何数据库一样：存什么、谁可以写、怎么读、怎么保证正确、怎么删除。

**Keep memory separate from the transcript and from your data.**

> **把记忆与对话记录、业务数据分开。**

- Conversation history belongs to one session; compact or discard it afterwards.
  > 对话历史只属于一次会话；会话结束后压缩或丢弃。
- Business data (campaigns, margins, the catalog) already lives in your systems. Read it with tools and never copy it into memory, or it will go stale.
  > 业务数据（广告系列、毛利、商品目录）本来就存在你们的系统里。用工具去读取，绝不要把它复制进记忆，否则它会过时。
- Memory holds durable preferences, decisions and lessons that exist nowhere else, such as "brand voice: formal German, no emojis" or "merchant said on Oct 3: never pause Brand campaigns".
  > 记忆保存的是在别处都不存在的、长期有效的偏好、决定和经验，例如“品牌语气：正式德语，不用 emoji”或者“商家在 10 月 3 日说过：永远不要暂停 Brand 系列”。

**Two ways to write memories.** In the agent-managed style, the model gets a memory tool and decides what to save. The Claude API's memory tool works this way: it is a client-side tool, the model issues commands such as `view`, `create` and `str_replace` on files under `/memories`, and your code executes them against storage you control. In the application-managed style, a separate extraction step proposes entries after a session, and code or the merchant confirms them. The first is flexible; the second is easier to review. A common hybrid: the agent writes, but entries that change behaviour around money, such as budgets and discounts, need the merchant's confirmation.

> **写入记忆的两种方式。** 在 Agent 管理的方式下，模型拿到一个记忆工具，自己决定存什么。Claude API 的 memory 工具就是这样工作的：它是一个客户端工具，模型对 `/memories` 下的文件发出 `view`、`create`、`str_replace` 等命令，由你的代码在你掌控的存储上执行。在应用管理的方式下，会话结束后由一个单独的提取步骤提出候选条目，再由代码或商家确认。前者灵活，后者更容易审核。常见的折中做法是：由 Agent 写入，但涉及金钱行为的条目（比如预算和折扣）需要商家确认。

**Store entries with structure, not just free text.**

> **以结构化方式存储条目，而不只是一段自由文本。**

```json
{
  "merchant_id": "m_5531",
  "key": "pricing.min_margin",
  "value": "Never suggest discounts that take the margin below 20%",
  "source": {"type": "merchant_statement", "conversation_id": "c_9182", "at": "2026-10-03T09:12:00Z"},
  "confirmed": true,
  "expires_at": null
}
```

A key lets a new statement replace the old one instead of piling up contradictions. The source lets you show the merchant why the agent believes something. An expiry fits temporary facts such as "budget freeze until December 1".

> 有了 key，新的说法可以替换旧的，而不是让互相矛盾的条目越堆越多。有了来源，你就能向商家展示 Agent 为什么会这么认为。过期时间适用于临时性的事实，比如“预算冻结到 12 月 1 日”。

**Reading memories back.** If a merchant has a handful of entries, load them all at the start of a session. Put them after the shared system prompt, for example at the top of the first user message, so the prefix that all merchants share stays identical and keeps hitting the prompt cache. When there are many entries, retrieve the relevant ones by key prefix or similarity, or let the agent browse them with the memory tool. Present them as the merchant's stated preferences with dates, not as system instructions.

> **读回记忆。** 如果一个商家只有少量条目，就在会话开始时全部加载。把它们放在共享的系统提示词之后，比如放在第一条用户消息的开头，这样所有商家共用的前缀保持完全一致，能继续命中 prompt 缓存。条目很多时，按 key 前缀或相似度检索相关条目，或者让 Agent 用 memory 工具自己浏览。展示时要把它们作为“商家陈述过的偏好”并附上日期，而不是作为系统指令。

**Keep it safe.**

> **保证安全。**

- Tenant isolation lives in code: the memory handler takes the merchant from the authenticated session and maps `/memories` to that merchant's storage, so the model never chooses whose memory it opens. Reject paths that try to leave the directory.
  > 租户隔离要写在代码里：记忆处理程序从已认证的会话中获取商家身份，把 `/memories` 映射到该商家的存储，这样模型永远无法选择打开谁的记忆。拒绝任何试图跳出该目录的路径。
- Memory can make a prompt injection permanent: text from a product description or an email that the agent remembers will steer every future session. Save only statements made by the merchant or results of verified actions, record the source, and never save instructions found in tool output.
  > 记忆可能让提示注入变成永久性的：Agent 记住的、来自商品描述或邮件的文字，会影响之后的每一次会话。只保存商家本人说过的话或经过验证的操作结果，记录来源，并且绝不保存在工具输出中发现的指令。
- No secrets and no unnecessary personal data. Tokens belong in your credential store, not in memory files.
  > 不存密钥，也不存不必要的个人数据。token 应该放在凭证存储里，而不是记忆文件里。
- Visibility and deletion: show merchants what is remembered, let them edit or delete entries, and delete everything when the account is closed.
  > 可见与删除：向商家展示记住了哪些内容，允许他们编辑或删除条目，并在账户注销时删除全部内容。

**Trade-offs.** With too little memory, merchants keep repeating themselves. With too much, old or wrong entries steer the agent in surprising ways, which is worse because nobody sees it happen. Start with a small set of explicit, confirmed preferences, measure how often they are used and corrected, and add automatic extraction only once you can review its quality.

> **取舍。** 记忆太少，商家就得不停地重复；记忆太多，过时或错误的条目会以出人意料的方式影响 Agent，而且更糟的是没人看得到它在发生。先从一小组明确的、经过确认的偏好开始，衡量它们被使用和被纠正的频率，等你能审核质量之后，再加入自动提取。

</details>

## 3. "Dresses under $50, not red" returns red dresses at $79

**“50 美元以下、不要红色的连衣裙”却返回了 79 美元的红裙子** · `RAG` · `Hard`

### Question · 题目

A shopping assistant runs on merchants' storefronts. It embeds the shopper's message, runs a nearest-neighbour search over product embeddings (built from title and description), takes the top 10, and lets the model write the reply.

> 一个购物助手运行在商家的店铺前台。它把顾客的消息做 embedding，在商品 embedding（由标题和描述生成）上做最近邻搜索，取前 10 个结果，再让模型写回复。

Shoppers complain:

> 顾客的投诉如下：

- "Dresses under $50, not red" returns red dresses at $79.
  > “50 美元以下、不要红色的连衣裙”返回了 79 美元的红裙子。
- "Nike Air Max 90, size 42" returns other Nike shoes.
  > “Nike Air Max 90，42 码”返回的是别的 Nike 鞋。
- "In stock only" is ignored, and the model sometimes says a product is available when it is sold out.
  > “只要有货的”被忽略了，模型有时还会说一个已经售罄的商品有货。

Explain why this happens and redesign the retrieval.

> 解释为什么会这样，并重新设计检索方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Embedding search answers "which items are about something like this?". It does not evaluate constraints. A price limit, a negation, a size and stock status are filters with exact answers, and the catalog already stores them as structured fields. So let the model translate the shopper's words into a structured query, let the search engine apply the hard constraints exactly, and use semantic similarity only for the fuzzy part.

> **核心思路。** embedding 检索回答的是“哪些商品和这段话说的是类似的东西”，它并不会判断约束条件。价格上限、否定、尺码和库存状态都是有确切答案的过滤条件，而商品目录本来就把它们存成了结构化字段。所以要让模型把顾客的话翻译成结构化查询，让搜索引擎精确地执行硬性约束，语义相似度只用来处理模糊的那部分。

**Why each complaint happens.**

> **每条投诉背后的原因。**

- "Not red": a query containing "not red" lands close to texts about red, because the vector mainly captures the topic. Negation is a well-known weakness of embedding similarity.
  > “不要红色”：包含“不要红色”的查询会落在描述红色的文本附近，因为向量主要捕捉的是主题。否定是 embedding 相似度一个众所周知的弱点。
- "Under $50": embeddings represent numbers poorly, and the price may not be in the embedded text at all.
  > “50 美元以下”：embedding 对数字的表达很差，而且价格可能根本不在被 embedding 的文本里。
- "Air Max 90, size 42": exact model names and sizes are lexical identifiers, and semantic search blurs them into "Nike shoes".
  > “Air Max 90，42 码”：精确的型号和尺码是字面上的标识符，语义检索会把它们模糊成“Nike 的鞋”。
- Wrong stock claims: the model answered from a description written months ago, or from a guess, instead of live inventory.
  > 错误的库存说法：模型依据的是几个月前写的商品描述，或者干脆是猜测，而不是实时库存。

**Step 1: extract a structured query with a strict tool.** Give the model a `search_products` tool whose schema mirrors your filterable fields, with `strict: true` so its arguments always match the schema:

> **第一步：用一个 strict 工具提取结构化查询。** 给模型一个 `search_products` 工具，它的 schema 与可过滤的字段一一对应，并设置 `strict: true`，保证参数始终符合 schema：

```json
{
  "name": "search_products",
  "description": "Search this store's catalog. Put every hard constraint the shopper states into the filter fields and only the descriptive part into text.",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": {
      "text": {"type": "string"},
      "category": {"anyOf": [{"type": "string"}, {"type": "null"}]},
      "max_price": {"anyOf": [{"type": "number"}, {"type": "null"}]},
      "exclude_colors": {"type": "array", "items": {"type": "string"}},
      "size": {"anyOf": [{"type": "string"}, {"type": "null"}]},
      "in_stock_only": {"type": "boolean"}
    },
    "required": ["text", "category", "max_price", "exclude_colors", "size", "in_stock_only"],
    "additionalProperties": false
  }
}
```

"Light summer dress under $50, not red" becomes `text: "light summer dress"`, `max_price: 50` and `exclude_colors: ["red"]`. Normalize the values in code, not with the model: map "crimson" and "burgundy" to the catalog's color facets, convert currencies, and translate size systems (EU 42 versus US sizes) with a lookup table.

> “50 美元以下、不要红色的轻薄夏季连衣裙”会变成 `text: "light summer dress"`、`max_price: 50` 和 `exclude_colors: ["red"]`。数值的规范化要在代码里做，而不是交给模型：把“crimson”“burgundy”映射到商品目录的颜色分面，换算货币，并用对照表转换尺码体系（欧码 42 与美码）。

**Step 2: hybrid search with the filters inside the engine.** Apply the filters as part of the query (price range, color not in the excluded list, size available, stock above zero), then rank what survives with a mix of keyword scoring such as BM25, which catches "Air Max 90", and vector similarity, which catches "light summer dress". Apply the filters inside the search, not to the top 10 afterwards: filtering only the nearest neighbours can leave zero results even when matching products exist.

> **第二步：混合检索，并在搜索引擎内部执行过滤。** 把过滤条件作为查询的一部分（价格区间、颜色不在排除列表中、有该尺码、库存大于零），然后对剩下的商品综合排序：用 BM25 这类关键词打分抓住“Air Max 90”，用向量相似度抓住“轻薄夏季连衣裙”。过滤要在检索内部完成，而不是事后对前 10 个结果过滤：只对最近邻结果做过滤，即使存在符合条件的商品，也可能一个都不剩。

**Step 3: take live facts from the system of record.** Prices, stock and variants change every hour, and the search index can lag behind. After ranking, fetch the current price and availability of the top results from the commerce API, and let the model state only those values. The reply references product IDs, and code checks that every product it mentions came from this search and that every price it states matches.

> **第三步：从权威数据源获取实时事实。** 价格、库存和变体每小时都在变，搜索索引可能跟不上。排序之后，从电商 API 获取排名靠前商品的当前价格和库存，只允许模型陈述这些值。回复中引用商品 ID，并由代码检查：回复提到的每个商品都来自这次检索，陈述的每个价格都与实际一致。

**When nothing matches.** Say so, and offer the closest relaxation: "There are no dresses under $50 in your size except red ones; here are three at $55 to $60." Decide in code which constraint to relax first, usually the softest one, and never "in stock".

> **没有匹配结果时。** 如实说明，并给出最接近的放宽方案：“你的尺码下，50 美元以下的连衣裙只有红色的；这里有三条 55 到 60 美元的。”先放宽哪个条件要在代码里决定，通常是最“软”的那个，而且永远不放宽“有货”。

**How you know it works.** Build a test set of real shopper queries with constraints. Measure constraint violations among returned products (the target is zero, checked by code), recall of known good products, and the rate of "no results" answers. Log the cases where the extracted filters were wrong; they become examples for improving the tool description.

> **如何确认它有效。** 用真实的、带约束条件的顾客查询构建测试集。衡量返回商品中违反约束的情况（目标是零，由代码检查）、已知优质商品的召回率，以及“没有结果”回答的比例。记录提取出的过滤条件出错的案例，它们会成为改进工具描述的示例。

**Trade-offs.** The extraction step adds a model call and latency, so cache popular queries and try a smaller model for extraction if it measures well. Exact filters can be too strict: does "no blue" exclude navy? Keep a facet synonym table and review zero-result queries. Queries that are just a SKU or model number can skip the model and go straight to keyword search.

> **取舍。** 提取步骤多了一次模型调用和相应的延迟，所以要缓存热门查询，如果评测结果可以接受，就用更小的模型来做提取。精确过滤也可能过于严格：“不要蓝色”要不要排除藏青色？维护一张分面同义词表，并定期查看零结果的查询。只有 SKU 或型号的查询可以跳过模型，直接走关键词检索。

</details>

## 4. Two agents keep overwriting each other's catalog edits

**两个 Agent 不断覆盖彼此对商品目录的修改** · `Multi-agent` · `Hard`

### Question · 题目

Your platform runs several agents on the same merchant catalog. A pricing agent adjusts prices every night, a content agent rewrites titles and descriptions for ads, and merchants also edit products by hand in the admin. Both agents use two tools: `get_product(id)` and `update_product(id, product)`, which writes the whole product.

> 你们的平台上有多个 Agent 在操作同一个商家的商品目录。定价 Agent 每晚调整价格，内容 Agent 为广告改写标题和描述，商家也会在后台手动编辑商品。两个 Agent 都使用两个工具：`get_product(id)` 和 `update_product(id, product)`，后者会写入整个商品对象。

In one month you see three incidents:

> 一个月内出现了三起事故：

- Price changes disappear after the content agent updates the same products.
  > 内容 Agent 更新同一批商品之后，价格修改消失了。
- The content agent restores an old price that the merchant had just changed by hand.
  > 内容 Agent 把商家刚刚手动改过的价格又改回了旧值。
- One product's title flips between two versions for a week.
  > 某个商品的标题在两个版本之间来回切换了一周。

Explain what is going on and redesign the system.

> 解释发生了什么，并重新设计这个系统。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** This is the classic lost-update race, and agents make it worse. An agent reads a product, thinks for seconds or minutes, then writes back what it read plus its own change. Anything that changed in between is overwritten. The model's context works like a cache of the data, and a stale one: the agent has no idea the price changed after it looked.

> **核心思路。** 这是经典的丢失更新（lost update）竞态，而 Agent 让它更严重。Agent 读取一个商品，思考几秒甚至几分钟，然后把它读到的内容加上自己的修改一起写回去。中间发生的任何变化都会被覆盖。模型的上下文就像数据的一份缓存，而且是过期的缓存：Agent 根本不知道在它看过之后价格已经变了。

**Why each incident happened.**

> **每起事故的原因。**

- Lost price changes: `update_product` writes the whole object, including the old price that the content agent read before the pricing agent ran.
  > 价格修改丢失：`update_product` 写入整个对象，其中包括内容 Agent 在定价 Agent 运行之前读到的旧价格。
- Restored old price: the same race against a human edit, made more likely because the content agent spends a long time on each product.
  > 旧价格被恢复：同样的竞态，只是对手换成了人工编辑；内容 Agent 在每个商品上花的时间很长，让这种情况更容易发生。
- Flipping title: two goals compete and nobody owns the field. The content agent optimizes titles for clicks, and another job or prompt version rewrites them back. Each sees the other's output as a problem to fix.
  > 标题来回切换：两个目标互相竞争，而这个字段没有归属者。内容 Agent 为点击率优化标题，另一个任务或另一个提示词版本又把它改回去。双方都把对方的输出当成需要修复的问题。

**Fix 1: make writes partial and conditional.** Replace "write the whole product" with a tool that changes only named fields and requires the version the agent read. This is optimistic concurrency control, the same idea as `If-Match` with an ETag in HTTP APIs:

> **修复一：让写入变成局部且有条件的。** 把“写入整个商品”换成一个只修改指定字段、并且要求带上 Agent 读取时版本号的工具。这就是乐观并发控制，和 HTTP API 中用 ETag 配合 `If-Match` 是同一个思路：

```go
// UpdateFields changes only the given fields, and only if nobody wrote since expectVersion.
func (s *Store) UpdateFields(ctx context.Context, id string, expectVersion int64, fields map[string]any) (int64, error) {
	res, err := s.db.ExecContext(ctx,
		`UPDATE products SET doc = doc || $1, version = version + 1
		 WHERE id = $2 AND version = $3`, toJSONB(fields), id, expectVersion)
	if err != nil {
		return 0, err
	}
	if n, _ := res.RowsAffected(); n == 0 {
		return 0, ErrVersionConflict
	}
	return expectVersion + 1, nil
}
```

**Fix 2: turn a conflict into information for the agent.** On a conflict, the tool returns an error result (`is_error: true`) that says what changed, for example "price changed from 59.00 to 54.00 by the merchant at 10:42; read the product again before writing". The agent re-reads and decides again. Cap the retries: two conflicts in a row on one product mean a person or the owning job should look at it.

> **修复二：把冲突变成给 Agent 的信息。** 发生冲突时，工具返回一个错误结果（`is_error: true`），说明发生了什么变化，例如“价格已被商家在 10:42 从 59.00 改为 54.00；写入前请重新读取该商品”。Agent 重新读取后再做决定。要限制重试次数：同一个商品连续冲突两次，就应该交给人或者该字段的归属任务来处理。

**Fix 3: give every field an owner.** Write down who may change what. Prices belong to the pricing agent, within bounds the merchant sets. Ad titles belong to the content agent. Anything the merchant edited by hand is locked against agents for a while unless the merchant opts in. Enforce this in the tool layer by checking the caller's identity, not in the prompts. When two jobs both care about a field, pick one owner and let the other propose changes to it.

> **修复三：给每个字段指定归属者。** 写清楚谁可以改什么。价格归定价 Agent 管，并且要在商家设定的范围内。广告标题归内容 Agent 管。商家手动编辑过的内容，在一段时间内对 Agent 锁定，除非商家主动允许。这些规则要在工具层通过检查调用方身份来强制执行，而不是写在提示词里。如果两个任务都关心同一个字段，就指定一个归属者，另一个只能提出修改建议。

**Fix 4: serialize work on hot products.** For longer multi-step changes, take a short lease on the product (a row with an owner and an expiry, renewed while working), or route all work for one product through one queue partition. Leases must expire, or a crashed agent blocks the product forever. A lease also does not replace the version check: a worker that was paused can still write after its lease has expired, so the version acts as a fencing token on the write.

> **修复四：对热点商品串行处理。** 对于较长的多步修改，给商品加一个短期租约（一条记录持有者和过期时间的数据，工作期间不断续期），或者把同一个商品的所有任务都路由到同一个队列分区。租约必须会过期，否则一个崩溃的 Agent 会永远锁住这个商品。租约也不能取代版本检查：一个被暂停的 worker 在租约过期之后仍可能写入，所以写入时的版本号起到了 fencing token 的作用。

**Fix 5: detect oscillation.** Keep an append-only change log per field with the actor and the reason. Alert when a field changes more than a few times a week or alternates between two values. That is a policy conflict to settle in the ownership table, not something more prompting will fix.

> **修复五：检测来回振荡。** 为每个字段维护一份只追加的变更日志，记录操作者和原因。当某个字段一周内变化超过几次，或者在两个值之间来回切换时发出告警。这属于策略冲突，应该在字段归属表里解决，而不是靠多写几句提示词。

**Trade-offs.** Optimistic locking is cheap when conflicts are rare, which is true for most products. For hot items it causes retries and wasted model calls, so leases or a per-product queue fit better there. Field ownership takes coordination work up front, but it turns mysterious regressions into explicit rules that people can review.

> **取舍。** 冲突很少时，乐观锁的成本很低，大多数商品都属于这种情况。对热点商品，它会导致重试和白白浪费的模型调用，这时租约或按商品分区的队列更合适。字段归属需要事先投入协调工作，但它能把莫名其妙的回退问题变成明确的、可以被审查的规则。

</details>

## 5. Your own loop, an SDK runner, an agent framework or a managed platform for a nightly feed audit?

**夜间 feed 审计 Agent：自己写循环、用 SDK runner、用 Agent 框架，还是用托管平台？** · `Agent Loop` · `Senior`

### Question · 题目

You are asked to build an agent that audits every merchant's product feeds each night. It pulls diagnostics from Google Merchant Center and Meta, reads the merchant's catalog, runs scripts to analyze thousands of items, and writes a report plus a list of proposed fixes that the merchant approves.

> 你需要构建一个 Agent，每晚审计每个商家的商品 feed。它从 Google Merchant Center 和 Meta 拉取诊断信息，读取商家的商品目录，运行脚本分析成千上万个商品，并输出一份报告和一组修复建议，由商家审批。

Four options are on the table: write the loop yourself on the Messages API; use the SDK's tool runner; use the Claude Agent SDK (the Claude Code harness as a library); or use a managed platform where the vendor runs the loop and the sandbox, such as Claude Managed Agents. How do you choose, and what would you pick?

> 摆在面前的有四个选项：直接基于 Messages API 自己写循环；使用 SDK 的 tool runner；使用 Claude Agent SDK（以库的形式提供的 Claude Code harness）；或者使用由厂商运行循环和沙箱的托管平台，例如 Claude Managed Agents。你如何选择？你会选哪个？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Every option needs the same two things: a harness (the loop, context management, tool execution, retries) and a deployment (where it runs, how it is scheduled, where code executes, where state lives). The options differ in how much of each you write and operate yourself. Choose by what the task needs and what your team is good at running, not by which option looks most advanced.

> **核心思路。** 每个选项都需要同样的两样东西：一个 harness（循环、上下文管理、工具执行、重试）和一套部署（在哪里运行、如何调度、代码在哪里执行、状态存在哪里）。这些选项的区别在于，这两部分中有多少需要你自己编写和运维。要根据任务的需要和团队擅长运维什么来选择，而不是看哪个选项看起来最先进。

**The four options, by who owns what.**

> **按“谁负责什么”来看这四个选项。**

- Your own loop on the Messages API: you write all of it (call the model, run the `tool_use` blocks, send back the `tool_result` blocks, repeat until `end_turn`) and host everything. Maximum control and no extra dependency, but the most code to maintain.
  > 基于 Messages API 自己写循环：全部由你编写（调用模型、执行 `tool_use` 块、回传 `tool_result` 块、重复直到 `end_turn`），所有东西也都由你托管。控制力最强，没有额外依赖，但要维护的代码最多。
- SDK tool runner: the SDK drives the loop for tools you define, with per-turn hooks for approvals, logging and retries. Less boilerplate, but still your tools and your hosting, and it is a beta helper.
  > SDK tool runner：SDK 为你定义的工具驱动循环，并在每一轮提供用于审批、日志和重试的钩子。样板代码更少，但工具和托管仍然是你的，而且它是一个 beta 阶段的辅助功能。
- Agent SDK: the Claude Code harness as a library, with built-in file, shell and search tools, subagents, hooks and permissions. You still host it, and you are responsible for containing what its shell can do.
  > Agent SDK：以库的形式提供的 Claude Code harness，内置文件、shell 和搜索工具，以及子 Agent、钩子和权限控制。你仍然要自己托管它，并负责限制它的 shell 能做什么。
- Managed platform: the vendor runs the loop and a sandbox per session; you configure the agent, connect tools and credentials, and consume an event stream. The least infrastructure and the least control over the runtime, and your data and code run on the vendor's infrastructure.
  > 托管平台：由厂商运行循环，并为每个会话提供一个沙箱；你负责配置 Agent、接入工具和凭证，并消费事件流。需要的基础设施最少，对运行时的控制也最少，而且你的数据和代码运行在厂商的基础设施上。

**What this task actually needs.**

> **这个任务真正需要什么。**

- Scheduled, long-running work per merchant: a scheduler, a queue, checkpoints and a cost cap per run.
  > 按商家定时运行的长时间任务：调度器、队列、检查点，以及每次运行的成本上限。
- Code execution over thousands of items: a sandbox with no network or a tight egress allowlist, resource limits, and the merchant's export mounted read-only.
  > 对成千上万个商品执行代码：一个没有网络或者只有严格出站白名单的沙箱、资源限制，以及以只读方式挂载的商家导出数据。
- Google Merchant Center and Meta credentials for every merchant, kept out of the model's context and out of any sandbox where it runs code.
  > 每个商家的 Google Merchant Center 和 Meta 凭证，既不能进入模型的上下文，也不能进入它执行代码的任何沙箱。
- Side effects only through approval: the agent proposes fixes, and applying them is a separate, gated step.
  > 副作用只能经过审批：Agent 只提出修复建议，执行修复是一个单独的、有关卡的步骤。
- Observability and evals: a trace per run, and a regression suite you can run before changing prompts or models.
  > 可观测性与评测：每次运行都有链路追踪，并且在修改提示词或模型之前可以运行一套回归测试。

**First question: is it an agent at all?** Much of the audit is deterministic. Fetching diagnostics, joining them with the catalog and counting error types are ordinary code. The open-ended part is explaining causes and proposing fixes for the unusual cases. A strong design runs a fixed pipeline for the heavy lifting and calls the agent only on the aggregated results and the exceptions. That cuts cost, and most of the run becomes testable without a model.

> **第一个问题：它到底是不是一个 Agent？** 审计中很大一部分是确定性的。拉取诊断信息、把它和商品目录关联起来、统计错误类型，这些都是普通代码。真正开放式的部分，是解释原因并为少见的情况提出修复方案。好的设计是用固定的流水线完成繁重的工作，只在汇总结果和异常情况上调用 Agent。这样能降低成本，而且大部分流程不需要模型也能测试。

**My choice, and why.** For a team of backend engineers who already run queues and workers in Go, I would start with our own loop or the SDK's tool runner inside the existing job system. We already have scheduling, retries, idempotency and tenant isolation; the tools are a few narrow functions over our own APIs; and the heavy analysis runs in our pipeline. If the agent truly needs to write and run arbitrary scripts, I would use a hosted code-execution sandbox for that part rather than build our own isolation, because sandboxing is easy to get wrong. I would choose a managed platform for the whole agent if the team had little appetite for running infrastructure, the data-residency and vendor reviews passed, and the platform's features (some offer scheduled runs, per-session sandboxes and credential vaults) matched this job closely.

> **我的选择及理由。** 对于一个本来就在用 Go 运维队列和 worker 的后端团队，我会先在现有的任务系统里使用自己写的循环或 SDK 的 tool runner。调度、重试、幂等和租户隔离我们都已经有了；工具只是基于我们自己 API 的几个职责单一的函数；繁重的分析则在我们的流水线里完成。如果 Agent 确实需要编写并运行任意脚本，这一部分我会使用托管的代码执行沙箱，而不是自己做隔离，因为沙箱很容易做错。如果团队不太愿意运维基础设施，数据驻留和供应商审查也都通过了，并且平台的功能（有些平台提供定时运行、按会话隔离的沙箱和凭证保管库）与这个任务高度契合，我会把整个 Agent 放到托管平台上。

**Keep the decision reversible.** Whatever you pick, keep the tools behind your own interface or an MCP server, keep prompts and tool definitions versioned in your repository, store run state and results in your own database, and keep the eval suite independent of the harness. Then moving from your own loop to a managed platform, or back, is a migration of the runner, not a rewrite of the product.

> **让这个决定可以反悔。** 不管选哪个，都要把工具放在你自己的接口或 MCP server 后面，把提示词和工具定义纳入代码仓库做版本管理，把运行状态和结果存在你自己的数据库里，并让评测套件独立于 harness。这样，无论是从自己写的循环迁到托管平台，还是反过来，都只是迁移运行器，而不是重写整个产品。

**Trade-offs to say out loud.** Owning the loop means owning its bugs: stop-reason handling, context growth, retries. A framework or platform saves that work but adds a dependency whose behaviour and pricing change on its own schedule, and debugging goes through its abstractions. Beta features move fast, so pin versions and keep an eval suite that tells you when an upgrade changed behaviour.

> **要明确说出来的取舍。** 自己掌控循环，就要自己承担它的 bug：停止原因的处理、上下文的膨胀、重试。框架或平台能省掉这些工作，但会引入一个依赖，它的行为和定价按照它自己的节奏变化，调试也要穿过它的抽象层。beta 功能变化很快，所以要锁定版本，并保留一套评测，在升级改变了行为时能告诉你。
