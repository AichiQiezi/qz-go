## 1. "Do you have AB-1234 in navy?" The assistant finds similar products but never the right SKU

**“AB-1234 有藏青色吗？”助手能找到相似的商品，却从来找不到那个 SKU** · `RAG` · `Medium`

### Question · 题目

A shopping assistant retrieves products with embedding search over titles and descriptions. Questions in natural language work well, but questions with exact identifiers (SKUs, model numbers, brand names, GTINs) often miss: "AB-1234 navy" returns similar jackets, not AB-1234. The team tried adding the SKU to the description text, with little effect.

> 一个导购助手通过对标题和描述做向量检索来查找商品。自然语言的问题效果很好，但带有精确标识符的问题（SKU、型号、品牌名、GTIN）经常检索不到：“AB-1234 藏青色”返回的是相似的夹克，而不是 AB-1234。团队尝试把 SKU 加进描述文本里，效果甚微。

Explain why and design retrieval that handles both kinds of queries.

> 解释原因，并设计一种能同时处理这两类查询的检索方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Embeddings capture meaning, so they are good at "warm jacket for hiking" and weak at exact strings: `AB-1234` and `AB-1243` look almost the same to them, and an identifier carries little meaning to embed. Keyword search is the opposite. Use both, and let exact identifiers bypass search entirely when you can recognize them.

> **核心思路。** 向量表示捕捉的是含义，所以擅长“适合徒步的保暖夹克”这类查询，却不擅长精确字符串：在它们看来，`AB-1234` 和 `AB-1243` 几乎一样，而一个标识符本身也没有多少可供嵌入的含义。关键词检索恰恰相反。两者都要用，并且在能识别出精确标识符时，让它直接绕过检索。

**Design.**

> **设计。**

- **Identifier fast path.** Detect SKU, GTIN and model-number patterns in the query (or let the agent call a `lookup_by_sku` tool) and do an exact database lookup, normalizing case, spaces and dashes. This answers the most valuable queries deterministically.
  > **标识符快速通道。** 在查询中识别 SKU、GTIN 和型号的模式（或者让 Agent 调用 `lookup_by_sku` 工具），并做一次精确的数据库查找，同时对大小写、空格和连字符做归一化。这样能以确定性的方式回答最有价值的那类查询。
- **Hybrid search for everything else.** Run a keyword index (BM25 or similar, with fields for title, brand and attributes) and the vector index in parallel, then merge the two ranked lists.
  > **其余情况用混合检索。** 并行运行关键词索引（BM25 或类似算法，为标题、品牌和属性设置字段）和向量索引，然后合并两份排序结果。
- **Filters from structure.** Turn attributes such as color and size into filters on structured fields ("navy" maps to the color facet), rather than hoping either index ranks them correctly.
  > **用结构化信息过滤。** 把颜色、尺码等属性转换成结构化字段上的过滤条件（“藏青色”对应颜色这个维度），而不是指望某个索引能正确地为它们排序。

Reciprocal rank fusion is a simple, robust way to merge lists whose scores are not comparable: each list contributes `1/(k + rank)` for every document it returned, with a constant such as 60.

> 倒数排名融合（RRF）是一种简单、稳健的方法，用来合并分数彼此不可比的排序列表：每份列表对它返回的每个文档贡献 `1/(k + rank)`，常数 k 取 60 之类的值。

```go
// fuse merges ranked lists of document IDs with reciprocal rank fusion:
// each list contributes 1/(k+rank) for every document it returned.
func fuse(k float64, lists ...[]string) []string {
	score := map[string]float64{}
	for _, list := range lists {
		for rank, id := range list {
			score[id] += 1 / (k + float64(rank+1))
		}
	}
	ids := make([]string, 0, len(score))
	for id := range score {
		ids = append(ids, id)
	}
	sort.Slice(ids, func(i, j int) bool { return score[ids[i]] > score[ids[j]] })
	return ids
}
```

**Then tell the model what it has.** Pass back the matched product with its exact SKU and variant availability as structured fields, and instruct the assistant to say clearly when the exact item was not found instead of offering a similar one as if it were the same.

> **然后告诉模型它拿到的是什么。** 把匹配到的商品连同精确的 SKU 和各个变体的库存情况，以结构化字段的形式传回去，并要求助手在没有找到精确商品时明确说明，而不是把相似商品当作同一件推荐出去。

**Keep both indexes honest.** Feed both from the same product change events, remove deleted or unpublished products from both, and alert when their document counts drift apart. A product that exists in only one index will appear for some queries and vanish for others, which looks to merchants like random search behaviour.

> **让两套索引都保持准确。** 让两者都从同一份商品变更事件中更新数据，把已删除或已下架的商品从两边都移除，并在两边的文档数量出现偏差时告警。只存在于一套索引中的商品，会在某些查询中出现、在另一些查询中消失，在商家看来就像是随机的搜索行为。

**Trade-offs.** Two indexes mean two pipelines to keep in sync and more latency, though they run in parallel. Fusion weights are easy to over-tune; evaluate on a labelled set that mixes identifier queries, attribute queries and vague natural-language queries, and report each group separately so a gain on one does not hide a loss on another.

> **取舍。** 两套索引意味着两条需要保持同步的数据管道，延迟也更高，尽管它们是并行运行的。融合的权重很容易被过度调优；要在一个混合了标识符查询、属性查询和模糊自然语言查询的标注集上评测，并分组报告结果，这样一组的提升就不会掩盖另一组的下降。

</details>

## 2. Nightly agents share one memory store, and merchants' learnings start to mix

**夜间 Agent 共用一个记忆存储，商家之间学到的东西开始混在一起** · `Context & Memory` · `Hard`

### Question · 题目

Your nightly catalog agents run as managed agent sessions. To make them learn, the team attached one memory store to every session with read-write access: "notes about merchants and catalog conventions". After a month, the store holds thousands of files, some notes for merchant A were written under paths for merchant B, one note contains an API key pasted from a tool result, and two sessions running at the same time overwrote each other's edits to the same file.

> 你们的夜间商品目录 Agent 以托管 Agent 会话的形式运行。为了让它们能学习，团队给每个会话都挂载了同一个可读写的记忆存储：“关于商家和目录规范的笔记”。一个月后，这个存储里有了几千个文件；一些属于商家 A 的笔记被写到了商家 B 的路径下；有一条笔记里包含一个从工具结果中粘贴进来的 API key；还有两个同时运行的会话互相覆盖了对同一个文件的修改。

Redesign the memory layout and its governance.

> 重新设计记忆的结构及其管理方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Memory is shared state, so treat it like a database: separate it by owner, give each session only the access it needs, keep it small and reviewable, and handle concurrent writers explicitly. One global read-write store for everyone is the equivalent of one shared table without tenant keys.

> **核心思路。** 记忆是共享状态，所以要像对待数据库一样对待它：按归属方分开，只给每个会话它需要的访问权限，保持它小而可审查，并显式处理并发写入。所有人共用一个全局可读写的存储，就相当于一张没有租户键的共享表。

**How memory stores work.** On Anthropic's Managed Agents, a memory store is a workspace-scoped collection of small text documents that persists across sessions. Stores are attached at session creation in `resources`, with `read_write` or `read_only` access, up to 8 per session, and mounted as a directory the agent uses with its ordinary file tools. Every change creates an immutable memory version, which gives you an audit trail and point-in-time rollback or redaction.

> **记忆存储如何工作。** 在 Anthropic 的 Managed Agents 上，记忆存储是一个作用于整个工作区、跨会话持久保存的小型文本文档集合。存储在创建会话时通过 `resources` 挂载，访问权限为 `read_write` 或 `read_only`，每个会话最多 8 个，并以目录的形式挂载，由 Agent 用它的普通文件工具读写。每次修改都会产生一个不可变的记忆版本，为你提供审计记录，以及按时间点回滚或删改的能力。

- **Split by owner and lifecycle.** One read-only shared store for catalog conventions that your team curates, plus one read-write store per merchant. Each session mounts only its merchant's store, so cross-merchant writes become impossible rather than discouraged.
  > **按归属方和生命周期拆分。** 一个由你们团队维护的、只读的共享存储，存放商品目录规范；再为每个商家各建一个可读写的存储。每个会话只挂载对应商家的存储，这样跨商家写入就从“不鼓励”变成了“不可能”。
- **Describe stores for the model.** The store description and per-session instructions tell the agent what belongs there and when to check it; write them as instructions for the model, not as labels for humans.
  > **为模型描述存储。** 存储的描述和每个会话的说明会告诉 Agent 哪些内容应该放在那里、什么时候该去查看；要把它们写成给模型的指令，而不是给人看的标签。
- **No secrets, ever.** Memories are replayed verbatim into later sessions, so a pasted key spreads to every session that mounts the store. Delete it, redact the affected versions, rotate the key, and keep credentials in vaults instead.
  > **绝不存放机密。** 记忆会被原样带入之后的会话，所以一个被粘贴进去的 key 会扩散到每个挂载该存储的会话。要删除它、删改受影响的版本、轮换这个 key，并改为把凭证放进 vault。
- **Concurrent writers.** Host-side updates can use a `content_sha256` precondition: if the file changed since you read it, the update fails with a conflict and you re-read and retry. Also schedule at most one session per merchant at a time, so agents rarely race on the same files.
  > **并发写入者。** 在宿主侧更新时可以使用 `content_sha256` 前置条件：如果文件在你读取之后被改过，更新会以冲突失败，你需要重新读取再重试。此外，让每个商家同一时间最多只运行一个会话，这样 Agent 之间就很少会争抢同一个文件。

**Keep it small and useful.** Prefer many small files with clear paths (`/conventions/sizing.md`, `/decisions/2026-10-category-mapping.md`) over a few large ones. Run a periodic review job that lists recent versions, flags notes without a source or with stale facts, and lets merchants see and correct what the agent "knows" about them.

> **保持精简和有用。** 宁可使用许多路径清晰的小文件（`/conventions/sizing.md`、`/decisions/2026-10-category-mapping.md`），也不要用少数几个大文件。定期运行一个审查任务，列出最近的版本，标记没有来源或事实已经过时的笔记，并让商家能够查看和纠正 Agent 关于他们“知道”些什么。

**Trade-offs.** Per-merchant stores give isolation and easy deletion when a merchant leaves, but shared learnings no longer spread automatically; promote them deliberately into the shared read-only store after review. Read-only for most sessions reduces risk but slows learning. Measure whether memory actually helps: compare task success and cost with and without the store mounted.

> **取舍。** 按商家拆分的存储提供了隔离，商家离开时也便于删除，但共享的经验不再自动传播；需要在审查之后有意识地把它们提升到共享的只读存储中。大多数会话只读能降低风险，但会减慢学习。要衡量记忆是否真的有帮助：对比挂载与不挂载存储时的任务成功率和成本。

</details>

## 3. The inherited eval says 92%, until you find that timeouts are scored as passes

**接手的评测显示 92%，直到你发现超时被算作了通过** · `Evals & Observability` · `Hard`

### Question · 题目

You inherit an eval suite for the merchant support agent: 120 cases, one run each, a pass rate of 92%, and a plan to make it a release gate. Reading the runner, you notice a timeout returns an empty answer, and the grader checks that the answer "does not contain a wrong refund amount". You also see the runner never checks which model actually served each request.

> 你接手了商家客服 Agent 的一套评测：120 个用例，每个跑一次，通过率 92%，并且计划把它作为发布关卡。读了运行器的代码后，你注意到超时会返回一个空答案，而评分器检查的是答案“不包含错误的退款金额”。你还发现运行器从不检查每个请求实际是由哪个模型处理的。

How do you audit this eval before trusting it?

> 在信任这套评测之前，你会如何审查它？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** An eval can only be trusted if every score reflects the model's behaviour, not the plumbing around it, and if it can actually detect the change you care about. Audit the harness, the grader and the statistics before reading any number it produces.

> **核心思路。** 只有当每个分数反映的都是模型的行为、而不是它周围的管道，并且评测确实能检测出你关心的变化时，这套评测才值得信任。在阅读它产生的任何数字之前，先审查运行框架、评分器和统计方法。

**Harness: separate infrastructure failures from model failures.** Here an empty answer from a timeout passes a check that only looks for wrong amounts, so a broken runner scores well. Timeouts, API errors after retries, responses cut off at `max_tokens`, crashed tools and grader failures must go to an error log with a reason, never into the pass/fail column. Also distinguish "no answer" from a real negative answer.

> **运行框架：把基础设施故障和模型失败分开。** 在这里，超时导致的空答案通过了一个只检查错误金额的校验，于是一个坏掉的运行器反而得了高分。超时、重试后仍失败的 API 错误、在 `max_tokens` 处被截断的响应、崩溃的工具以及评分器自身的失败，都必须连同原因写入错误日志，绝不能进入通过/失败那一栏。还要区分“没有答案”和真正的否定答案。

- **Prove the wiring.** Run an oracle (reference answers, which should score near 100%) and a null baseline (empty output or a constant answer, which should fail) through the whole pipeline. If the null baseline passes, the grader is too lenient.
  > **验证接线是否正确。** 让一个 oracle（参考答案，应当接近 100%）和一个空基线（空输出或固定答案，应当失败）完整地跑一遍流水线。如果空基线能通过，说明评分器过于宽松。
- **Check the served model.** Read `model` from each response and fail the attempt if it is not the model you asked for, for example after a fallback.
  > **检查实际服务的模型。** 从每个响应中读取 `model`，如果不是你请求的模型（例如发生了 fallback），就让这次尝试失败。
- **Match production.** Diff the system prompt, tools, model and scaffolding against what ships, and call the app's real entry point rather than a re-implemented one.
  > **与生产环境保持一致。** 把 system prompt、工具、模型和外围框架与实际上线的版本进行对比，并调用应用真实的入口，而不是重新实现的版本。
- **Save full trajectories** for every case, so a surprising score can be traced without re-running.
  > **为每个用例保存完整的执行轨迹**，这样遇到出乎意料的分数时，不用重跑就能追查原因。

**Grader.** Check that it rewards what the prompt asks for and grades the outcome rather than one specific path; write a deliberately wrong-but-plausible answer and confirm it fails; read a handful of failures and fix the grader if many look like grader errors. If it is an LLM judge, calibrate it against human labels and test it on known negatives such as an empty answer or a confident answer to a different question.

> **评分器。** 检查它奖励的是不是提示所要求的内容，评判的是结果而不是某一条特定路径；写一个故意错误但看似合理的答案，确认它不能通过；读几个失败的用例，如果很多看起来是评分器的错，就先修正评分器。如果评分器是 LLM 评审，要用人工标注来校准它，并用已知的反例来测试，例如空答案，或者对另一个问题的自信回答。

**Statistics: can it see the change?** One run of 120 cases has a wide noise floor; for a pass rate it is roughly `1/sqrt(n x reps)`, about 9 points here. Differences smaller than that are noise, so run several repetitions, report intervals, and compare against the smallest improvement you would actually ship on. For rare, high-stakes behaviours such as wrong refunds, report worst-case or fail-on-any rather than a mean diluted by easy cases.

> **统计：它能看到变化吗？** 120 个用例只跑一次，噪声下限很宽；对于通过率，它大约是 `1/sqrt(n x reps)`，这里约为 9 个百分点。小于这个幅度的差异只是噪声，所以要多跑几次重复，报告置信区间，并与你真正会据此上线的最小改进幅度进行比较。对于错误退款这类少见但高风险的行为，要报告最坏情况或“出现一次即失败”，而不是一个被简单用例稀释的平均值。

**Trade-offs.** A thorough audit takes days and more repetitions cost money, but a release gate that passes broken builds is worse than no gate, because it creates false confidence. Start with the cheap checks (oracle, null baseline, error separation, served model), which catch most wiring bugs in minutes.

> **取舍。** 一次彻底的审查要花好几天，更多的重复运行也要花钱；但一个会放行坏版本的发布关卡比没有关卡更糟，因为它会制造虚假的信心。先从便宜的检查做起（oracle、空基线、错误分离、实际服务的模型），它们能在几分钟内抓住大多数接线错误。

</details>

## 4. Holding 2,000 event streams open every night just to learn when sessions finish

**每晚保持 2,000 条事件流开着，只为了知道会话什么时候结束** · `Production` · `Medium`

### Question · 题目

Your nightly jobs start about 2,000 managed agent sessions. A worker keeps an event stream open for each session to detect when it finishes or needs input. Streams drop during deploys, some sessions are never marked done in your database, and others are processed twice after a reconnect.

> 你们的夜间任务会启动大约 2,000 个托管 Agent 会话。一个 worker 为每个会话保持一条事件流，用来判断会话何时结束或需要输入。发布期间事件流会断开，有些会话在你们的数据库里始终没有被标记为完成，另一些则在重连之后被处理了两次。

How would you track session state reliably?

> 你会如何可靠地跟踪会话状态？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Streams are good for watching a session live; they are a poor way to learn about state changes for thousands of background sessions. Let the platform notify you, and treat each notification as a hint to fetch the current state, not as the state itself.

> **核心思路。** 事件流适合实时观察某一个会话；但对于成千上万个后台会话，用它来获知状态变化并不是好办法。让平台来通知你，并把每次通知当作“去获取当前状态”的提示，而不是状态本身。

**Webhooks.** Managed Agents can POST to your HTTPS endpoint when a session changes state, for example `session.status_idled`, `session.status_terminated`, or `session.outcome_evaluation_ended`. Payloads are thin: an event type and resource IDs. On receipt, fetch the session (and its latest events) for the real state. Endpoints are registered in the Console, and each delivery is signed.

> **Webhook。** 当会话状态发生变化时，Managed Agents 可以向你的 HTTPS 端点发送 POST 请求，例如 `session.status_idled`、`session.status_terminated` 或 `session.outcome_evaluation_ended`。负载很精简：只有事件类型和资源 ID。收到之后，再去获取会话（及其最新事件）来得到真实的状态。端点在 Console 中注册，每次投递都带有签名。

- **Verify first.** Use the SDK's `webhooks.unwrap` with the raw request body; frameworks that re-serialize JSON change the bytes and break the signature check. It also rejects old payloads.
  > **先验证。** 使用 SDK 的 `webhooks.unwrap`，并传入原始请求体；会重新序列化 JSON 的框架会改变字节，导致签名校验失败。它还会拒绝过旧的负载。
- **Deduplicate.** The event ID stays the same across retries, so store processed IDs and return a 2xx for duplicates. Return 2xx quickly and do the work asynchronously.
  > **去重。** 事件 ID 在多次重试中保持不变，所以要保存已处理过的 ID，对重复的事件直接返回 2xx。要尽快返回 2xx，再异步处理具体工作。
- **Read the reason.** `status_idled` covers several cases: waiting for a tool approval, a custom tool result, the next message, or a paused session at its budget. Check the latest idle event's stop reason before acting. `status_terminated` fires on completion and on error, so read the session to tell which.
  > **读取原因。** `status_idled` 涵盖好几种情况：等待工具审批、等待自定义工具结果、等待下一条消息，或者会话因达到预算而暂停。行动之前先检查最近一次 idle 事件的停止原因。`status_terminated` 在完成和出错时都会触发，所以要读取会话来区分是哪一种。

**Make your own records idempotent.** Update your job table with a state machine keyed by session ID (`started`, `waiting`, `done`, `failed`), and only move forward. Then duplicate or out-of-order notifications cannot double-process a session. Keep a reconciliation job that lists sessions still "running" in your table after a deadline and fetches their state, which covers missed deliveries and your own outages.

> **让你自己的记录具备幂等性。** 以会话 ID 为键，用一个状态机（`started`、`waiting`、`done`、`failed`）来更新你的任务表，并且只允许向前推进。这样重复或乱序的通知就不会导致一个会话被处理两次。再保留一个对账任务：在截止时间之后列出你们表中仍处于“运行中”的会话，并获取它们的状态，用以弥补漏掉的投递和你们自身的故障。

**Act on the waiting states.** A session that is idle because it needs a tool approval should create a task for a person, with a deadline, and the approval goes back as a confirmation event. A session paused at its budget accepts only events that settle work already in progress, so a new message is rejected; alert, and decide whether to raise the budget or stop.

> **对等待中的状态采取行动。** 因为需要工具审批而处于 idle 的会话，应该为某个人创建一个带截止时间的任务，审批结果再以确认事件的形式发回去。因达到预算而暂停的会话只接受用于了结进行中工作的事件，所以新消息会被拒绝；要发出告警，并决定是提高预算还是停止。

**Trade-offs.** Webhooks need a public HTTPS endpoint and secret management, and delivery is at-least-once, so idempotency is required. Streams remain the right tool for an interactive UI that shows progress live; for background fleets, webhooks plus reconciliation are simpler and survive deploys.

> **取舍。** Webhook 需要一个公开的 HTTPS 端点和密钥管理，而且投递是至少一次，所以必须做到幂等。对于需要实时展示进度的交互界面，事件流仍然是合适的工具；而对于后台的大批量会话，webhook 加对账更简单，也能扛住发布。

</details>

## 5. An enterprise merchant requires that order data never leave their network: can you still offer the agent?

**一家大企业商家要求订单数据绝不离开他们的网络：你还能提供这个 Agent 吗？** · `Safety & Security` · `Senior`

### Question · 题目

A large merchant wants your catalog and order-analysis agent, but their security team says their order database and files must stay inside their own network, and no inbound connections from outside are allowed. Your agent currently runs on a managed platform with cloud sandboxes that execute bash and file tools.

> 一家大型商家想用你们的商品目录和订单分析 Agent，但他们的安全团队表示，订单数据库和文件必须留在他们自己的网络内部，并且不允许任何来自外部的入站连接。你们的 Agent 目前运行在一个托管平台上，由云端沙箱执行 bash 和文件工具。

Design a deployment that meets the requirement, and be precise about what does and does not leave their network.

> 设计一个满足这个要求的部署方案，并准确说明哪些内容会离开他们的网络、哪些不会。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Separate where the agent thinks from where it acts. The model and the agent loop can run in the provider's cloud while tool execution, and therefore the raw data the tools touch, stays on the merchant's machines. But whatever the model reads must reach the model, so the real design question is what data the tools return.

> **核心思路。** 把 Agent“思考”的地方和它“行动”的地方分开。模型和 Agent 循环可以运行在服务商的云端，而工具的执行，以及工具接触到的原始数据，则留在商家的机器上。但模型要读的内容必须送到模型那里，所以真正需要设计的问题是：工具返回什么数据。

**Self-hosted sandboxes.** On Anthropic's Managed Agents, an environment of type `self_hosted` keeps the agent loop on Anthropic's orchestration layer and moves tool execution into containers the merchant runs. A worker inside their network long-polls a work queue, so connectivity is outbound-only and nothing dials into their network. Bash, file operations and code run there, and the sandbox's filesystem and network egress stay in their environment.

> **自托管沙箱。** 在 Anthropic 的 Managed Agents 上，类型为 `self_hosted` 的运行环境会把 Agent 循环保留在 Anthropic 的编排层，而把工具执行移到商家自己运行的容器中。他们网络内的一个 worker 以长轮询的方式从工作队列中拉取任务，所以连接只有出站方向，没有任何东西会连入他们的网络。bash、文件操作和代码都在那里运行，沙箱的文件系统和网络出口都留在他们的环境中。

**Be precise about what still leaves.**

> **准确说明仍然会离开的内容。**

- Tool inputs and outputs flow to the provider's control plane so the model can see them. A query that returns 50,000 order rows sends those rows out.
  > 工具的输入和输出会流向服务商的控制平面，这样模型才能看到它们。一个返回 50,000 行订单数据的查询，会把这些数据送出去。
- Web search and web fetch run on the provider's servers in both environment types; disable them or restrict their domains.
  > 网页搜索和网页抓取在两种运行环境中都运行在服务商的服务器上；要禁用它们或限制可访问的域名。
- Skills and memory store contents are stored by the provider and copied into the sandbox; memory changes sync back.
  > Skills 和记忆存储的内容由服务商保存，并复制到沙箱中；对记忆的修改会同步回去。

**Design the tools for minimal disclosure.** Give the agent tools that compute inside the network and return aggregates or masked records: "refund rate by category last 30 days" instead of raw orders; customer IDs pseudonymized; free-text fields excluded unless needed. Run the analysis code in the sandbox and return only the summary. Log every tool output that leaves, so the security team can audit exactly what was disclosed.

> **为最小披露而设计工具。** 给 Agent 提供在网络内部完成计算、只返回聚合结果或脱敏记录的工具：返回“最近 30 天各类目的退款率”，而不是原始订单；顾客 ID 做化名处理；除非必要，不返回自由文本字段。让分析代码在沙箱中运行，只返回摘要。记录每一份离开网络的工具输出，让安全团队可以审计到底披露了哪些内容。

**Operations and contract.** The merchant runs and patches the workers, sizes capacity, and owns the sandbox's network policy; you provide the image, the tools and monitoring. Agree on data processing terms, retention and regions with legal, and document the data flow diagram the security team will ask for.

> **运维与合同。** 商家负责运行和修补 worker、规划容量，并负责沙箱的网络策略；你们提供镜像、工具和监控。与法务一起就数据处理条款、保留期限和区域达成一致，并准备好安全团队一定会要的数据流图。

**Test the boundary.** Before go-live, verify that the sandbox can reach only the provider's endpoints and the merchant's internal services it needs, try prompts that ask the agent to dump raw tables, and confirm that the tools refuse or aggregate. Review the outbound tool-output log with the security team after the first week.

> **测试边界。** 上线之前，验证沙箱只能访问服务商的端点以及它需要的商家内部服务；尝试用一些要求 Agent 导出原始数据表的提示，确认工具会拒绝或只返回聚合结果。第一周结束后，和安全团队一起审查出站的工具输出日志。

**Trade-offs.** Self-hosting satisfies "files and databases stay inside" with little change to the agent, but not "nothing leaves", because the model must see tool results. If the requirement is truly that no derived data leaves, the options are a model deployment inside their cloud account through a supported cloud platform, or not using an external model for that data at all. Being exact about this early avoids a failed security review late.

> **取舍。** 自托管能满足“文件和数据库留在内部”，而且对 Agent 的改动很小，但满足不了“什么都不离开”，因为模型必须看到工具结果。如果要求真的是任何派生数据都不能离开，可选方案是通过受支持的云平台在他们自己的云账户内部署模型，或者对这部分数据完全不使用外部模型。尽早把这一点说清楚，可以避免在后期安全评审中失败。

</details>
