## 1. The support agent's hand-written tool loop loses tool calls, answers "Continue." to paused searches, and asks for refund approval after the refund

**客服 agent 手写的工具循环会丢失工具调用、对暂停的搜索回复「Continue.」，还在退款完成之后才请求审批** · `Agent Loop` · `Medium`

### Question · 题目

A merchant-support agent written in Go runs its own loop around the Messages API. The team chose a hand-written loop "for control": a person must approve refunds above $200, and every call must be logged. A code review of the loop and last week's incident log find four problems:

> 一个用 Go 写的商家客服 agent 在 Messages API 外面自己实现了循环。团队选择手写循环是「为了掌控」：超过 200 美元的退款必须由人审批，而且每次调用都要记录日志。对这个循环的代码审查和上周的事故日志发现了四个问题：

- After each response the loop appends only the text blocks to `messages`. The next request fails with a 400 about a `tool_result` that has no matching `tool_use`.
  > 每次响应之后，循环只把文本块追加到 `messages` 里。下一次请求失败，返回一个 400，说某个 `tool_result` 没有对应的 `tool_use`。
- The agent also has web search. When a response comes back with `stop_reason: "pause_turn"`, the loop appends a user message that says "Continue."
  > 这个 agent 还带有网页搜索。当响应以 `stop_reason: "pause_turn"` 返回时，循环会追加一条内容为「Continue.」的用户消息。
- The approval prompt sits in a logging middleware that runs after the tool function returns.
  > 审批提示放在一个日志中间件里，而这个中间件在工具函数返回之后才运行。
- The loop has no limit. One conversation made 140 API calls overnight.
  > 循环没有任何上限。有一个对话在一夜之间发起了 140 次 API 调用。

Fix the problems. Should the team keep the hand-written loop?

> 修复这些问题。团队应该保留手写循环吗？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** For an agent with custom tools, the SDK's tool runner is the recommended default, and "we need control" is rarely a reason to leave it. Approval gates, logging and a limit on the loop all fit inside the runner. Three of the four bugs come from rewriting what the runner already does.

> **核心思想。** 对于带自定义工具的 agent，SDK 的工具运行器（tool runner）是推荐的默认选择，而「我们需要掌控」很少能成为放弃它的理由。审批关口、日志和循环上限都能放进运行器里。四个 bug 中有三个，都来自重写运行器本来就做好的事情。

**Bug 1: lost tool_use blocks.** A manual loop must append the full `response.content` as the assistant turn, not just its text, and each `tool_result` must carry the `tool_use_id` of the call it answers. Keep only the text, and the results point at calls that no longer exist.

> **Bug 1：丢失 tool_use 块。** 手写循环必须把完整的 `response.content` 作为助手轮次追加，而不只是其中的文本；每个 `tool_result` 都必须带上它所回答的那次调用的 `tool_use_id`。只保留文本，结果指向的调用就不存在了。

**Bug 2: "Continue." after pause_turn.** `pause_turn` means the server-side loop that runs server tools such as web search reached its default limit of 10 iterations. To continue, send the user message and the assistant response back as they are and make another request. The API resumes by itself. An extra user message such as "Continue." is exactly what the docs say not to add. Cap continuations, say at 5. The Python and TypeScript runners resume paused turns themselves from `anthropic` 1.1.0 and `@anthropic-ai/sdk` 0.121.0, while older releases return the paused turn as the final message with no error. For Go, check the release you pin; v2.9.0, used for this code, resumes it.

> **Bug 2：pause_turn 之后发送「Continue.」。** `pause_turn` 表示服务端运行网页搜索等服务器工具的循环达到了默认的 10 次迭代上限。要继续，就把用户消息和助手响应原样发回去，再发起一次请求。API 会自己恢复执行。额外添加「Continue.」这样的用户消息，恰恰是文档明确说不要做的。给续接次数设上限，比如 5 次。Python 和 TypeScript 的运行器从 `anthropic` 1.1.0 和 `@anthropic-ai/sdk` 0.121.0 起会自己恢复暂停的轮次，而更早的版本会把暂停的轮次当作最终消息返回，不报任何错误。对于 Go，要检查你锁定的版本；本文代码所用的 v2.9.0 会自动恢复。

**Bug 3: approval after the side effect.** An approval prompt that runs after the tool is a log entry, not a gate. With the runner, put the gate inside the tool's run function: ask for approval, and return a "declined" result instead of running the tool. You can also inspect each yielded message before its tool calls run and change the next request through the runner's `Params` field. When nobody can answer, deny.

> **Bug 3：副作用发生后才审批。** 在工具执行之后才弹出的审批提示只是一条日志，不是关口。使用运行器时，把关口放在工具的执行函数里：先请求审批，拒绝时返回一个「已拒绝」的结果，而不是执行工具。你也可以在每条产出消息里的工具调用执行之前检查它，并通过运行器的 `Params` 字段修改下一次请求。没有人能回应时，就拒绝。

**Bug 4: no limit.** `MaxIterations` caps API calls. When the cap ends the run, the last message still has `stop_reason: "tool_use"` and unanswered calls. Report it as a stopped run, not an answer.

> **Bug 4：没有上限。** `MaxIterations` 限制 API 调用次数。当上限结束运行时，最后一条消息的 `stop_reason` 仍然是 `"tool_use"`，并带着未回答的调用。要把它报告为被中止的运行，而不是答案。

```go
type RefundInput struct {
	OrderID     string `json:"order_id" jsonschema:"required"`
	AmountMinor int64  `json:"amount_minor" jsonschema:"required"`
}

// The gate lives in the tool, so no path can refund without it.
func refundTool(approve func(context.Context, RefundInput) bool,
	issue func(context.Context, RefundInput) error) (anthropic.BetaTool, error) {
	return toolrunner.NewBetaToolFromJSONSchema("issue_refund", "Refund an order; large refunds need the merchant's approval.",
		func(ctx context.Context, in RefundInput) (anthropic.BetaToolResultBlockParamContentUnion, error) {
			msg := "The merchant declined this refund. Do not retry it."
			if approve(ctx, in) {
				if err := issue(ctx, in); err != nil {
					return anthropic.BetaToolResultBlockParamContentUnion{}, err // becomes an error tool_result
				}
				msg = "Refund issued."
			}
			return anthropic.BetaToolResultBlockParamContentUnion{OfText: &anthropic.BetaTextBlockParam{Text: msg}}, nil
		})
}

func run(ctx context.Context, client anthropic.Client, tools []anthropic.BetaTool, q string) (*anthropic.BetaMessage, error) {
	runner := client.Beta.Messages.NewToolRunner(tools, anthropic.BetaToolRunnerParams{
		BetaMessageNewParams: anthropic.BetaMessageNewParams{
			Model: "claude-opus-5-5", MaxTokens: 16000,
			Messages: []anthropic.BetaMessageParam{anthropic.NewBetaUserMessage(anthropic.NewBetaTextBlock(q))},
		},
		MaxIterations: 12, // bounds the number of API calls
	})
	for msg, err := range runner.All(ctx) {
		if err != nil {
			return nil, err
		}
		log.Printf("turn %d stop_reason=%s", runner.IterationCount(), msg.StopReason)
	}
	last := runner.LastMessage()
	if last.StopReason != anthropic.BetaStopReasonEndTurn { // tool_use: limit hit; or refusal, max_tokens
		return last, fmt.Errorf("run stopped with %s", last.StopReason)
	}
	return last, nil
}
```

In the Go runner, a handler error goes back to the model as an error `tool_result`, and the calls of one turn run in parallel, so two refunds can ask for approval at once.

> 在 Go 运行器中，处理函数返回的错误会作为错误的 `tool_result` 发回给模型，而且同一轮的多个调用会并行执行，所以两笔退款可能同时请求审批。

**When a manual loop is right.** Only when you need control the runner does not expose: a custom transport, request shapes the SDK cannot build, per-token streaming where the runner lacks it, avoiding a beta dependency, or unrelated work interleaved inside the loop. None of the team's reasons are on that list, and logging works from the yielded messages.

> **什么时候手写循环才合适。** 只有在需要运行器没有提供的控制能力时才这样做：自定义传输层、SDK 无法构造的请求结构、运行器不支持时的逐 token 流式、不想依赖 beta 功能，或者在循环中穿插不相关的工作。团队给出的理由都不在这个列表里，日志也可以直接基于运行器产出的消息来做。

**Trade-offs.** The runner is beta: pin the SDK version and read the changelog on upgrades, since `pause_turn` handling has changed between releases. Keep the refund rule in the tool, where no prompt can skip it.

> **权衡。** 运行器是 beta 功能：要锁定 SDK 版本，升级时阅读变更日志，因为 `pause_turn` 的处理在不同版本之间已经变过。把退款规则放在工具里，这样任何提示词都无法绕过它。

## 2. To cut latency, the team turned thinking off on the Claude Haiku 5.5 category step, and products now get categories nobody looked up

**为了降低延迟，团队在 Claude Haiku 5.5 的分类步骤上关闭了思考，结果商品被分到了没人查过的类目里** · `Tools & MCP` · `Medium`

### Question · 题目

The catalog import moved from Claude Haiku 4.5 to Claude Haiku 5.5. The category step has one tool, `lookup_category`, which searches the merchant's own category tree, and it asks for the final answer in a JSON output format (`output_config.format`). To keep the step fast, an engineer set `thinking: {type: "disabled"}`.

> 商品目录导入从 Claude Haiku 4.5 迁到了 Claude Haiku 5.5。分类步骤有一个工具 `lookup_category`，用来搜索商家自己的类目树，并要求以 JSON 输出格式（`output_config.format`）给出最终答案。为了让这一步更快，一位工程师设置了 `thinking: {type: "disabled"}`。

Two days later merchants report products filed under categories that do not exist in their tree. The logs show that for about 8% of products the model returned valid JSON without ever calling `lookup_category`. A second engineer tries `effort: "max"` with thinking still off, "to make it more careful", and every request returns a 400.

> 两天后，商家反馈有商品被归到了他们类目树里根本不存在的类目下。日志显示，大约 8% 的商品，模型返回了合法的 JSON，却从未调用过 `lookup_category`。另一位工程师在思考仍然关闭的情况下尝试了 `effort: "max"`，想「让它更仔细」，结果每个请求都返回 400。

Explain both problems and fix the step.

> 解释这两个问题，并修复这一步。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** This is a documented behavior of Claude Haiku 5.5: with thinking turned off, the model may skip a tool call it needs when the same request also asks for structured JSON output. On this model, turning thinking off is not the right speed lever. Effort is.

> **核心思想。** 这是 Claude Haiku 5.5 有文档记载的行为：关闭思考后，如果同一个请求还要求结构化 JSON 输出，模型可能会跳过它本该进行的工具调用。在这个模型上，关闭思考不是正确的提速手段，effort 才是。

**Why the 400.** Claude Haiku 5.5 accepts `thinking: {type: "disabled"}` only at effort `low`, `medium` and `high`. With `xhigh` or `max` it returns a 400. The two settings also pull in opposite directions: one asks for less thought, the other for the most.

> **为什么是 400。** Claude Haiku 5.5 只在 effort 为 `low`、`medium` 和 `high` 时接受 `thinking: {type: "disabled"}`。配合 `xhigh` 或 `max` 时会返回 400。这两个设置本身也是相互矛盾的：一个要求少思考，另一个要求最大程度地思考。

**Three documented fixes for the skipped lookup.**

> **针对跳过查询问题，文档给出了三种修复方式。**

- Leave adaptive thinking on for these requests. This is the simplest fix.
  > 对这些请求保持自适应思考开启。这是最简单的修复。
- Remove the output format from any request where the model must call a tool. For example, do the lookup in one request and ask for the formatted answer in the next.
  > 在模型必须调用工具的请求里去掉输出格式。比如，在一个请求里完成查询，在下一个请求里再要求格式化的答案。
- Force the call with `tool_choice`. Claude Haiku 5.5 accepts a forced `tool_choice` (`any` or a named tool), but the response then starts with the tool call, with no thinking block and no text before it. Use this only if every product really needs exactly one lookup.
  > 用 `tool_choice` 强制调用。Claude Haiku 5.5 接受强制的 `tool_choice`（`any` 或指定某个工具），但响应会直接以工具调用开头，前面没有思考块，也没有文本。只有当每个商品确实都需要恰好一次查询时才这样用。

If thinking has to stay off, add this line to the system prompt: "The JSON output format applies to your final answer only. When you need a tool, call it first, with no text before the call, and write the JSON once you have the results." In Anthropic's testing, with thinking off, it raised the share of complete and correct JSON answers at `low` and `medium` effort.

> 如果思考必须保持关闭，就在系统提示里加上这一句：「The JSON output format applies to your final answer only. When you need a tool, call it first, with no text before the call, and write the JSON once you have the results.」（JSON 输出格式只适用于你的最终答案。需要工具时先调用它，调用前不要写任何文本，拿到结果后再写 JSON。）在 Anthropic 的测试中，在思考关闭时，这句话在 `low` 和 `medium` effort 下提高了完整且正确的 JSON 答案的比例。

**The real speed lever.** To get less thinking, lower the effort level. In Anthropic's testing the model still thought when the prompt told it to answer directly. Effort on Claude Haiku 5.5 runs from `low` to `max` with `medium` as the default, and at lower levels the model thinks less and can skip thinking entirely on simpler requests. Thinking counts toward `max_tokens`, so leave room for it. A response can also begin with `thinking` blocks, so read content blocks by `type`, not by position.

> **真正的提速手段。** 想让模型少思考，就降低 effort 等级。在 Anthropic 的测试中，即使提示要求直接回答，模型仍然会思考。Claude Haiku 5.5 的 effort 从 `low` 到 `max`，默认是 `medium`；等级越低，模型思考越少，在较简单的请求上还可以完全跳过思考。思考会计入 `max_tokens`，所以要给它留出空间。响应也可能以 `thinking` 块开头，所以要按 `type` 读取内容块，而不是按位置。

```go
type Route struct {
	Effort      string // low, medium, high, xhigh, max
	ThinkingOff bool   // thinking: {type: "disabled"}
	JSONFormat  bool   // output_config.format set
	Tools       []string
}

// Checked in CI against every route config before it ships.
func routeProblems(r Route) []string {
	var p []string
	if r.ThinkingOff && (r.Effort == "xhigh" || r.Effort == "max") {
		p = append(p, "400: thinking disabled is accepted only at effort high or lower")
	}
	if r.ThinkingOff && r.JSONFormat && len(r.Tools) > 0 {
		p = append(p, "may skip a needed tool call: keep adaptive thinking, drop the format, or add the final-answer-only line")
	}
	return p
}

type Call struct{ Tool string }

// The eval metric: a category written without a lookup in the same run.
func guessedCategory(calls []Call, answeredCategory bool) bool {
	return answeredCategory && !slices.ContainsFunc(calls, func(c Call) bool { return c.Tool == "lookup_category" })
}
```

**Prove the fix.** Make "a category without a lookup" an eval metric and compare adaptive thinking at `low` and at `medium` against thinking off with the extra line, on the same products. Track latency and output tokens next to the metric. Do not compare token counts with the Claude Haiku 4.5 logs: the newer tokenizer counts the same text as about 30% more tokens.

> **证明修复有效。** 把「没有查询就给出类目」设为评测指标，在同一批商品上对比 `low` 和 `medium` 下的自适应思考，以及关闭思考并加上那句话的配置。在指标旁边同时跟踪延迟和输出 token 数。不要拿 token 数和 Claude Haiku 4.5 的日志比较：新的分词器对同样的文本大约多算 30% 的 token。

**Keep a check in code.** Structured outputs guarantee the shape of the answer, not that the category exists. Validate every returned category against the merchant's tree before writing it, and send failures back for a lookup.

> **在代码里保留校验。** 结构化输出保证的是答案的格式，而不是类目真的存在。在写入之前，把每个返回的类目和商家的类目树核对一遍，校验失败的退回去重新查询。

**Trade-offs.** Adaptive thinking adds some latency on hard items but keeps the model's judgment. A forced `tool_choice` removes that judgment and adds a call even where none is needed. The prompt line helps, but only your eval shows how much.

> **权衡。** 自适应思考会在难的商品上增加一些延迟，但保留了模型的判断。强制 `tool_choice` 去掉了这种判断，即使不需要也会多一次调用。那句提示有帮助，但到底有多大帮助，只有你的评测能说明。

</details>

## 3. Fast mode on Opus 4.8 ends on November 30: moving the live-chat agent's fast traffic on the Claude API, Managed Agents, Foundry and Vertex

**Opus 4.8 的快速模式将于 11 月 30 日下线：迁移实时聊天 agent 在 Claude API、Managed Agents、Foundry 和 Vertex 上的快速流量** · `Production` · `Hard`

### Question · 题目

The merchant live chat runs on Opus 4.8 with fast mode, set up during the research preview: the beta messages endpoint, the `fast-mode-2026-02-01` beta header and `speed: "fast"`. It runs in four places:

> 商家实时聊天运行在启用了快速模式的 Opus 4.8 上，是在研究预览期间配置的：使用 beta messages 端点、`fast-mode-2026-02-01` beta 请求头，以及 `speed: "fast"`。它部署在四个地方：

- the main chat, on the Claude API;
  > 主聊天，运行在 Claude API 上；
- an after-hours agent on Managed Agents, configured with `model: {id: "claude-opus-4-8", speed: "fast"}`;
  > 一个下班时间的 agent，运行在 Managed Agents 上，配置为 `model: {id: "claude-opus-4-8", speed: "fast"}`；

## 4. Moving the research agent's API keys into vault credentials: a Slack webhook, a signed S3 upload, an OAuth token exchange, and a key that only fails when set up in the Console

**把研究 agent 的 API 密钥迁入 vault 凭据：一个 Slack webhook、一次签名的 S3 上传、一次 OAuth 令牌交换，以及一个只在控制台创建时才出错的密钥** · `Safety & Security` · `Hard`

### Question · 题目

A research agent on Managed Agents used to get its secrets as plain environment variables set up inside its environment. It uses five of them:

> 一个运行在 Managed Agents 上的研究 agent，以前是通过在环境内部配置的普通环境变量拿到密钥的。它用到了五个密钥：

- an ads-reporting API key, which the API reads from a JSON field in the request body;
  > 一个广告报表 API 的密钥，该 API 从请求体的一个 JSON 字段中读取它；
- a Slack incoming-webhook URL for alerts;
  > 一个用于告警的 Slack incoming webhook URL；
- AWS keys for uploading reports to S3 with the AWS CLI;
  > 用于通过 AWS CLI 把报表上传到 S3 的 AWS 密钥；
- a client ID and secret for a partner API that uses the OAuth client-credentials flow;
  > 一个合作方 API 的 client ID 和 secret，该 API 使用 OAuth client-credentials 流程；
- a key for a vendor CLI that checks the key starts with `vk_`.
  > 一个供应商 CLI 的密钥，该 CLI 会检查密钥是否以 `vk_` 开头。

Security asks to move all of them into vault `environment_variable` credentials, so the sandbox never holds a secret. After the move, Slack alerts stop, S3 uploads fail with signature errors, the vendor CLI exits at startup with "invalid key format", and the ads API, whose credential was created in the Console, returns 401 although the key is correct. The partner API works, but a review finds its access tokens in the session's tool output. Explain each failure and design the setup.

> 安全团队要求把它们全部迁入 vault 的 `environment_variable` 凭据，这样沙箱里就永远不会有密钥。迁移之后，Slack 告警停了，S3 上传因签名错误失败，供应商 CLI 在启动时以「invalid key format」退出，而广告 API（它的凭据是在控制台里创建的）在密钥正确的情况下返回 401。合作方 API 能用，但审查发现它的访问令牌出现在了会话的工具输出里。解释每一个故障，并设计整体方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Vault credentials never enter the sandbox. The sandbox sees an opaque placeholder, and the real value replaces it at egress, only on requests to the credential's allowed hosts and only in the parts of the request where substitution is enabled. Anything that needs the real secret inside the sandbox breaks, and anything that brings a secret back into the sandbox defeats the design.

> **核心思想。** vault 凭据永远不会进入沙箱。沙箱看到的是一个不透明的占位符，真实的值在出口处（egress）替换它，而且只发生在发往该凭据允许主机的请求上，只发生在请求中启用了替换的部分。任何需要在沙箱内部拿到真实密钥的东西都会失效，而任何把密钥带回沙箱的东西都会破坏这个设计。

**Slack.** Substitution covers request headers and bodies only. A secret in the URL path is never substituted, so incoming-webhook URLs cannot be vaulted. Use header-based auth instead: a bot token in `Authorization`, sent with `chat.postMessage`.

> **Slack。** 替换只覆盖请求头和请求体。URL 路径里的密钥永远不会被替换，所以 incoming webhook URL 无法放进 vault。改用基于请求头的认证：用 `chat.postMessage` 发送，在 `Authorization` 里放 bot token。

**S3.** The AWS CLI computes a SigV4 signature from the secret, so it signs with the placeholder and S3 rejects the request. Use a custom tool: the agent emits `agent.custom_tool_use`, your orchestrator, which holds the credential, makes the upload, and returns `user.custom_tool_result` over the same event stream. The sandbox never sees the key.

> **S3。** AWS CLI 会用密钥计算 SigV4 签名，所以它是用占位符签的名，S3 就拒绝了请求。改用自定义工具：agent 发出 `agent.custom_tool_use`，持有凭据的编排器负责上传，再通过同一个事件流返回 `user.custom_tool_result`。沙箱永远看不到这个密钥。

**The vendor CLI.** Clients that validate the key's format locally, before any network request, see the placeholder and fail at startup. Call the vendor's HTTP API directly with a client that sends the key unchanged in a header.

> **供应商 CLI。** 那些在发出任何网络请求之前就在本地校验密钥格式的客户端，看到的是占位符，于是在启动时就失败了。改为用一个把密钥原样放在请求头里发送的客户端，直接调用供应商的 HTTP API。

**The ads API 401.** Credentials created in the Console are header-only by default, while the API enables both locations when the field is omitted. A placeholder in a disabled location is neither substituted nor stripped, so the ads API received the literal placeholder in the body. Enable body injection in the Console form, or `POST` `{"injection_location": {"body": true}}`. Updates merge field by field. Bodies are often built from content the agent works with, which makes them the broader exposure surface, so enable body only on this credential, with `allowed_hosts` limited to the ads API.

> **广告 API 的 401。** 在控制台创建的凭据默认只在请求头中替换，而通过 API 创建时，省略该字段会同时启用两个位置。处在未启用位置的占位符既不会被替换，也不会被删除，所以广告 API 在请求体里收到的就是字面的占位符。在控制台表单里勾选请求体注入，或者 `POST` `{"injection_location": {"body": true}}`。更新是按字段逐个合并的。请求体往往由 agent 正在处理的内容拼成，暴露面更大，所以只在这一个凭据上启用请求体注入，并把 `allowed_hosts` 限定为广告 API。

**The partner tokens.** Substitution is outbound only. A client that exchanges the secret for a session token receives that token in the sandbox unredacted, and from there it lands in tool output. Do the client-credentials exchange yourself, store the resulting access token in the vault, and update its secret value when you refresh it.

> **合作方的令牌。** 替换只作用于出站请求。用密钥换取会话令牌的客户端，会在沙箱里拿到未经遮盖的令牌，令牌再从那里进入工具输出。由你自己完成 client-credentials 交换，把得到的访问令牌存进 vault，刷新时更新它的密钥值。

**Echo endpoints.** Responses reach the sandbox unredacted, so a host that echoes request headers hands the real secret back. Allow only hosts you trust.

> **回显端点。** 响应会未经遮盖地到达沙箱，所以一个回显请求头的主机会把真实密钥交还回来。只允许你信任的主机。

```go
type Integration struct {
	Name           string
	SecretIn       string // "header", "body" or "url_path"
	SignsRequests  bool   // computes a signature from the secret (SigV4, HMAC)
	ChecksFormat   bool   // client validates the key's format before any request
	ExchangesToken bool   // trades the secret for a session token
	EchoesRequests bool   // some endpoint returns request headers or bodies
}

// Where the secret should live for each integration.
func plan(i Integration) string {
	switch {
	case i.SecretIn == "url_path":
		return "not vaultable: paths are never substituted; move to header auth"
	case i.SignsRequests:
		return "custom tool: the orchestrator signs; a placeholder signature is rejected"
	case i.ExchangesToken:
		return "exchange outside, vault the resulting token, refresh it yourself"
	case i.ChecksFormat:
		return "call the HTTP API directly, or patch the client's local check"
	case i.EchoesRequests:
		return "keep that host out of allowed_hosts: the echo returns the real secret"
	case i.SecretIn == "body":
		return "environment_variable with injection_location {header:false, body:true}"
	default:
		return "environment_variable, header only, allowed_hosts limited"
	}
}
```

**The rest of the setup.** `networking.allowed_hosts` on a credential decides which requests use the secret, not which are allowed. The environment must also be able to reach the host, so both layers must list it. Give each key the narrowest permissions the task needs. Never put a key in the system prompt or a user message, because it persists in the session's event history. Credentials are not validated until runtime, so a wrong one shows up as an authentication error during the session. `vault_ids` can be set only when a session is created. Self-hosted sandboxes do not support `environment_variable` credentials; custom tools are the fallback there.

> **方案的其余部分。** 凭据上的 `networking.allowed_hosts` 决定的是哪些请求会用到密钥，而不是哪些请求被允许。环境也必须能访问该主机，所以两层都要列出它。给每个密钥只授予任务所需的最小权限。永远不要把密钥放进系统提示或用户消息，因为它们会持久保存在会话的事件历史里。凭据要到运行时才会被校验，所以错误的凭据会在会话期间以认证错误的形式出现。`vault_ids` 只能在创建会话时设置。自托管沙箱不支持 `environment_variable` 凭据，在那里要退回到自定义工具。

**Trade-offs.** Custom tools keep secrets out completely, but your orchestrator now carries the load and must stay available. Body injection makes one API work at the cost of a wider surface. Refreshing tokens yourself adds a job that must not fail silently.

> **权衡。** 自定义工具能把密钥完全挡在外面，但编排器就要承担这部分负载，并且必须保持可用。请求体注入让一个 API 能够工作，代价是更大的暴露面。自己刷新令牌会多出一个绝不能静默失败的任务。

</details>

  > 「停止这个工作者」把整个会话都停了，包括协调者。

  > 在长会话的后期，协调者无法启动新的工作者，尽管只有两个在运行。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The session stream is the primary thread. It carries the coordinator's trace plus a condensed view of the workers: thread status changes and cross-thread messages, not every worker tool call. Every per-worker feature needs the thread endpoints, and every event must be read relative to the stream that carries it.

> **核心思想。** 会话事件流就是主线程。它承载协调者的完整轨迹，外加工作者活动的精简视图：线程状态变化和跨线程消息，而不是工作者的每一次工具调用。每个按工作者区分的功能都需要用到线程端点，而且每个事件都必须相对于承载它的那条流来解读。

**"Done" on assignment.** Direction is relative to the stream. On the primary stream, `agent.thread_message_sent` is the coordinator sending a task, and `agent.thread_message_received` is a worker sending a report or a question to the coordinator. On a worker's own stream, the delegated task itself arrives as `_received`. So `_received` never means "finished". Drive status from `session.thread_status_*` events and their `stop_reason`, and treat a report as a claim the coordinator still has to check.

> **一分配就显示「完成」。** 方向是相对于流而言的。在主流上，`agent.thread_message_sent` 表示协调者发出了一个任务，`agent.thread_message_received` 表示某个工作者向协调者发送了报告或问题。在工作者自己的流上，被委派的任务本身就是以 `_received` 到达的。所以 `_received` 从来都不表示「已完成」。用 `session.thread_status_*` 事件及其 `stop_reason` 来驱动状态，并把报告当作协调者仍需核实的说法。

**Empty live panes.** Previews are thread-scoped. A worker's previews arrive only on its own stream, `GET /v1/sessions/{sid}/threads/{tid}/stream` with `event_deltas[]=agent.message`, and are never cross-posted to the session stream. Also, only plain assistant text is previewed. A worker's reply to the coordinator rides `agent.thread_message_sent` and is never previewed, so a worker that only reports back streams nothing. If you want live text, prompt workers to write the answer as a plain assistant message in their own thread first and then report.

> **实时面板为空。** 预览是按线程划分的。工作者的预览只会出现在它自己的流上，即带 `event_deltas[]=agent.message` 的 `GET /v1/sessions/{sid}/threads/{tid}/stream`，而且永远不会被转发到会话流上。另外，只有普通的助手文本才会被预览。工作者给协调者的回复走的是 `agent.thread_message_sent`，永远不会被预览，所以一个只负责回报的工作者什么也不会流出来。如果你想要实时文本，就在提示里让工作者先在自己的线程中以普通助手消息写出答案，然后再回报。

**Costs.** Per-thread `usage.list_cost` figures do not sum to the session total: the session figure also includes session running time, and each figure is rounded on its own. The session-level number is authoritative.

> **成本。** 各线程的 `usage.list_cost` 加起来不等于会话总额：会话的数字还包括会话运行时间，而且每个数字都是单独取整的。会话级别的数字才是权威的。

**The stop button.** A `user.interrupt` without `session_thread_id` interrupts every non-archived thread, the primary included. Send the worker's `session_thread_id`. Against a worker blocked on `requires_action`, the interrupt closes each pending call with an error tool result and the thread goes idle with `end_turn` without sampling the model. Against a thread that is idle with `end_turn` or `budget_reached` it is a no-op, and naming a terminated thread is a 400.

> **停止按钮。** 不带 `session_thread_id` 的 `user.interrupt` 会中断所有未归档的线程，包括主线程。要发送该工作者的 `session_thread_id`。对于阻塞在 `requires_action` 上的工作者，中断会以错误工具结果关闭每个待处理的调用，线程不再调用模型，直接以 `end_turn` 进入空闲。对以 `end_turn` 或 `budget_reached` 进入空闲的线程，中断不起作用；而指定一个已终止的线程会返回 400。

**No new workers.** A session allows at most 25 child threads, and idle threads count until they are archived. Archive each worker once its work is accepted. Archiving needs the thread to be idle, and `requires_action` counts as idle; only a running thread must be interrupted first.

> **无法启动新工作者。** 一个会话最多允许 25 个子线程，空闲线程在归档之前都计入这个数。每个工作者的工作被接受后就把它归档。归档要求线程处于空闲状态，而 `requires_action` 也算空闲；只有正在运行的线程需要先中断。

**Missing approvals.** A worker call that pauses for approval (`always_ask`, or `auto` without a determination) is cross-posted to the primary thread with `session_thread_id`. Answer it with `user.tool_confirmation` and the `tool_use_id`; the server routes by that ID. But a call the server denies under `auto` is not cross-posted: its event and error result appear only on the worker's own stream, and the worker keeps going. To show denials, the console must read worker streams.

> **审批缺失。** 工作者发起的需要暂停等待审批的调用（`always_ask`，或者 `auto` 下没有得出判定），会带着 `session_thread_id` 被转发到主线程。用 `user.tool_confirmation` 加上 `tool_use_id` 回复即可；服务端按这个 ID 路由。但在 `auto` 下被服务端拒绝的调用不会被转发：它的事件和错误结果只出现在该工作者自己的流上，而工作者会继续运行。要显示这些拒绝，控制台必须读取工作者的流。

```go
type Event struct {
	Type       string // as delivered on the session (primary) stream
	ThreadID   string // session_thread_id, or from_session_thread_id on a delivery
	StopReason string // stop_reason.type on *_idle events
}

type Worker struct{ State string }

// apply folds one primary-stream event into the console's view.
func apply(ws map[string]*Worker, e Event) {
	w := ws[e.ThreadID]
	if w == nil {
		w = &Worker{}
		ws[e.ThreadID] = w
	}
	switch e.Type {
	case "session.thread_created", "session.thread_status_running":
		w.State = "working"
	case "session.thread_status_idle":
		switch e.StopReason {
		case "requires_action":
			w.State = "waiting for approval"
		case "budget_reached":
			w.State = "paused: shared budget used up"
		default:
			w.State = "idle" // archive it when its work is accepted
		}
	case "agent.thread_message_received":
		w.State = "reported to coordinator" // a report or a question, not proof of success
	case "session.thread_status_terminated":
		w.State = "terminated"
	}
}

// One worker, not the session: without session_thread_id every thread stops.
func interruptWorker(threadID string) map[string]any {
	return map[string]any{"type": "user.interrupt", "session_thread_id": threadID}
}
```

**Budget.** A session budget is one cap shared by all threads, which pause one by one with `budget_reached`. A thread can report `end_turn` while the session reports `budget_reached`, so key the banner on the session status.

> **预算。** 会话预算是所有线程共享的一个上限，线程会一个接一个地以 `budget_reached` 暂停。某个线程可能报告 `end_turn`，而会话报告的是 `budget_reached`，所以横幅提示要以会话状态为准。

**Trade-offs.** One stream per worker costs connections, so open worker streams only while someone has that pane open, and keep the primary stream as the source of status.

> **权衡。** 每个工作者一条流会消耗连接数，所以只在有人打开某个工作者面板时才打开它的流，并以主流作为状态的来源。
