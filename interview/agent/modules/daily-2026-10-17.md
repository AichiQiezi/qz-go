## 1. The agent gives up after one 429, or retries the same broken call forever

**Agent 遇到一次 429 就放弃，或者无休止地重试同一个错误调用** · `Tools & MCP` · `Medium`

### Question · 题目

Your catalog agent calls tools that wrap the Meta Marketing API and your own product service. When a tool fails, the handler returns the raw exception text, for example `Error: request failed`. In production you see two opposite failures: after a single rate-limit error the agent tells the merchant "Meta is down, please try again later", and in other runs it calls the same tool with the same invalid arguments eight times in a row.

> 你们的商品目录 Agent 调用的工具封装了 Meta Marketing API 和你们自己的商品服务。工具失败时，处理程序直接返回原始异常文本，例如 `Error: request failed`。线上出现了两种截然相反的问题：遇到一次限流错误后，Agent 就告诉商家“Meta 宕机了，请稍后再试”；而在另一些运行中，它用同样的无效参数连续调用同一个工具八次。

How should tool errors be designed so the agent recovers well? What belongs in the harness, and what belongs in the model's hands?

> 工具错误应该如何设计，才能让 Agent 很好地恢复？哪些事情应该由 harness 处理，哪些应该交给模型？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A tool error is a message to the model, and the model can only act on what the message says. `Error: request failed` tells it nothing: it cannot tell a temporary problem from a mistake in its own arguments, so it either gives up or tries the same thing again. Split the work: the harness handles failures that need no judgment (transient errors, backoff, budgets), and the model gets clear, structured errors for the failures it can fix by changing what it does.

> **核心思路。** 工具错误是发给模型的一条消息，而模型只能根据消息里写的内容行动。`Error: request failed` 什么信息都没有：模型分不清这是暂时性问题还是自己参数写错了，于是要么放弃，要么原样再试一次。要分工：不需要判断的失败（暂时性错误、退避、预算）由 harness 处理；模型能通过改变做法来修复的失败，则以清晰、结构化的错误交给它。

**Sort failures into three kinds.**

> **把失败分成三类。**

- Transient: rate limits, timeouts, 5xx responses. Retrying the same call later is the right fix, and the model adds nothing. The harness retries with backoff and jitter inside the tool, honoring any retry-after hint, and the model never sees these unless the retry budget runs out.
  > 暂时性的：限流、超时、5xx 响应。正确的做法是稍后原样重试，模型帮不上什么忙。由 harness 在工具内部用退避加抖动重试，并遵守服务端给出的重试等待时间；除非重试预算用完，否则模型根本看不到这些错误。
- Fixable by the model: invalid arguments, a product ID that does not exist, a field the platform rejects. Retrying unchanged will fail again; the model must change its input or its plan.
  > 模型可以修复的：参数无效、商品 ID 不存在、平台拒绝某个字段。原样重试只会再次失败；模型必须修改输入或者改变计划。
- Not fixable here: an expired OAuth token, missing permissions, a suspended ad account. Neither retrying nor new arguments help; the agent should stop that path and tell the merchant what to do.
  > 在这里无法修复的：OAuth token 过期、权限不足、广告账户被封。重试和改参数都没用；Agent 应该停止这条路径，并告诉商家该怎么做。

**Write errors for the model.** Return the error as a tool result with `is_error: true` (in the Claude API) and content the model can act on: what failed, why, whether retrying could help, and what to do instead. Keep the shape stable so the model learns it:

> **为模型编写错误信息。** 把错误作为工具结果返回，并设置 `is_error: true`（Claude API 中的写法），内容要让模型能据此行动：什么失败了、为什么、重试有没有用、应该改做什么。保持格式稳定，让模型能学会它：

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A",
  "is_error": true,
  "content": "{\"error\": \"invalid_argument\", \"field\": \"product_ids[3]\", \"detail\": \"SKU-88 does not exist in this catalog\", \"retryable\": false, \"hint\": \"Call search_products to find the correct ID\"}"
}
```

**Map errors in one place.** A small classifier in the tool layer turns HTTP statuses and platform error codes into these categories, so every tool behaves the same way:

> **在一个地方统一映射错误。** 在工具层放一个小的分类器，把 HTTP 状态码和平台错误码转换成上面这些类别，这样所有工具的行为都一致：

```go
func classify(status int, platformCode string) (kind string, retryable bool) {
	switch {
	case status == 429 || status >= 500:
		return "transient", true // the harness retries; the model only hears about it if retries run out
	case status == 401 || platformCode == "token_expired":
		return "reauth_required", false // stop and ask the merchant to reconnect
	case status == 403:
		return "permission_denied", false
	case status == 400 || status == 404 || status == 422:
		return "invalid_argument", false // the model must change its input
	default:
		return "unknown", false
	}
}
```

**Stop loops in the harness.** Track a fingerprint of each call (tool name plus normalized arguments). If the same failing call repeats, do not run it again: return an error saying "this exact call already failed twice with the same error; change the arguments or choose another approach". Add a cap on total tool errors per run, after which the harness ends the run and hands the case to a person. These rules are deterministic, so they live in code, not in the prompt.

> **在 harness 中阻止死循环。** 为每次调用记录一个指纹（工具名加上规范化后的参数）。如果同一个失败调用再次出现，就不要再执行，而是返回一个错误：“这个调用已经以同样的错误失败了两次；请修改参数或换一种做法。”再给每次运行的工具错误总数设一个上限，超过后由 harness 结束运行，把问题交给人处理。这些规则是确定性的，所以写在代码里，而不是写在提示词里。

**Tell the model the policy once.** One or two sentences in the system prompt or the tool descriptions help: transient errors are already retried for you; for `invalid_argument`, fix the input; for `reauth_required`, stop and explain to the merchant. Then the model's answer to the merchant matches what actually happened.

> **把处理策略告诉模型一次。** 在系统提示词或工具描述里写一两句就够了：暂时性错误已经替你重试过；遇到 `invalid_argument` 要修正输入；遇到 `reauth_required` 要停下来并向商家说明。这样模型对商家的回答就能和实际发生的情况一致。

**Trade-offs.** Retrying inside the tool hides latency from the model but makes a single tool call slow, so cap the retry time and report the delay in the result. Very detailed errors can leak internals, such as stack traces or other merchants' IDs, into the context; return what the model needs and log the rest. Track error rates per tool and per kind, because a rise in `invalid_argument` usually means a tool description or schema needs fixing.

> **取舍。** 在工具内部重试能对模型隐藏延迟，但会让单次工具调用变慢，所以要限制重试时间，并在结果中注明延迟。过于详细的错误可能把内部信息（比如堆栈或其他商家的 ID）泄露到上下文里；只返回模型需要的内容，其余的写进日志。按工具和错误类别统计错误率，因为 `invalid_argument` 增多通常意味着某个工具描述或 schema 需要修改。

</details>

## 2. Where do the merchants' Google and Meta tokens go when an agent calls their APIs?

**Agent 调用商家的 Google 和 Meta API 时，这些 token 应该放在哪里？** · `Safety & Security` · `Medium`

### Question · 题目

Your agent manages ad campaigns for thousands of merchants, so it needs each merchant's OAuth tokens for Google Ads and Meta. A teammate's prototype puts the merchant's access token into the system prompt, so the model can pass it to a generic `http_request` tool, and logs every prompt for debugging.

> 你们的 Agent 为成千上万的商家管理广告系列，所以需要每个商家的 Google Ads 和 Meta OAuth token。一位同事的原型把商家的 access token 放进系统提示词，让模型把它传给一个通用的 `http_request` 工具，并且为了调试记录了每一条提示词。

What is wrong with this, and how would you handle credentials in an agent system?

> 这样做有什么问题？你会如何在 Agent 系统中处理凭证？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The model should never see a credential. Anything in the context can come back out: in an answer, in a tool argument sent to the wrong place, in logs, in traces, or through a prompt injection that asks for it. Treat the model like an untrusted client: it asks for an action, and trusted code performs that action with credentials the model cannot read.

> **核心思路。** 模型永远不应该看到凭证。上下文里的任何内容都可能被带出去：出现在回答里、作为工具参数被发到错误的地方、出现在日志和链路追踪里，或者被一段要求它交出来的提示注入拿走。把模型当成一个不可信的客户端：它请求执行某个操作，由可信的代码使用模型读不到的凭证去执行。

**What goes wrong in the prototype.**

> **原型里的问题。**

- Tokens in the prompt end up in prompt logs, traces, evaluation sets and any vendor dashboards that store prompts.
  > 放在提示词里的 token 会进入提示词日志、链路追踪、评测集，以及任何会保存提示词的第三方看板。
- A generic HTTP tool plus a token lets an injected instruction send the merchant's token, or their data, to any URL.
  > 通用 HTTP 工具加上 token，就能让一段注入的指令把商家的 token 或数据发到任意 URL。
- The model chooses which token to use, so a confused or manipulated run can act on the wrong merchant's account.
  > 由模型选择使用哪个 token，那么一次出错或被操纵的运行就可能操作到错误商家的账户。

**The pattern: tools hold the credentials.** Give the agent narrow tools such as `get_campaign_stats(campaign_id)` or `set_daily_budget(campaign_id, amount)`. The tool handler takes the merchant ID from the authenticated session, fetches that merchant's token from a secrets store, calls the platform, and returns only the data the model needs. The token never enters a prompt, a tool argument or a tool result.

> **正确的模式：凭证由工具持有。** 给 Agent 提供职责单一的工具，比如 `get_campaign_stats(campaign_id)` 或 `set_daily_budget(campaign_id, amount)`。工具处理程序从已认证的会话中获取商家 ID，从密钥存储中取出该商家的 token，调用平台，只返回模型需要的数据。token 永远不会进入提示词、工具参数或工具结果。

```go
func (t *BudgetTool) Handle(ctx context.Context, in SetBudgetInput) (ToolResult, error) {
	merchant := auth.MerchantID(ctx)                     // from the session, never from the model
	tok, err := t.tokens.Get(ctx, merchant, "meta_ads")  // secrets store, refreshed server-side
	if err != nil {
		return reauthRequired("Meta connection expired; ask the merchant to reconnect"), nil
	}
	if !t.owns(ctx, merchant, in.CampaignID) {
		return denied("campaign does not belong to this merchant"), nil
	}
	return t.meta.SetDailyBudget(ctx, tok, in.CampaignID, in.Amount)
}
```

**Token lifecycle stays in your backend.** Store refresh tokens encrypted, refresh access tokens in the backend before they expire, and request the narrowest scopes each feature needs (read-only reporting should not hold write scopes). When a refresh fails, the tool returns a clear "reconnect required" error, and the agent tells the merchant how to reconnect rather than retrying.

> **token 的生命周期留在你的后端。** 加密存储 refresh token，在 access token 过期前由后端刷新，并且每个功能只申请所需的最小权限范围（只读报表不应该持有写权限）。刷新失败时，工具返回一个清楚的“需要重新连接”的错误，Agent 告诉商家如何重新连接，而不是不断重试。

**If the agent runs code in a sandbox.** Put no credentials inside it. When scripts must call an API, route the calls through a proxy or a harness tool that adds the credential outside the sandbox. Some managed agent platforms offer credential vaults that work this way: the secret is substituted at egress and is never visible inside the sandbox.

> **如果 Agent 在沙箱里运行代码。** 沙箱里不放任何凭证。脚本必须调用 API 时，让调用经过一个代理或 harness 工具，由它在沙箱外部附加凭证。一些托管 Agent 平台提供以这种方式工作的凭证保管库：密钥在出站时才被替换进去，在沙箱内部永远不可见。

**Logs and traces.** Redact authorization headers and token-like strings at the source, before anything is exported, and run a secret scanner over logs as a backstop. Even with tokens out of prompts, tool results can carry secrets from a misbehaving API, so scrub results too.

> **日志与链路追踪。** 在数据导出之前就在源头脱敏授权头和看起来像 token 的字符串，并用密钥扫描工具扫描日志作为兜底。即使提示词里没有 token，表现异常的 API 也可能在工具结果中带出密钥，所以工具结果同样要清洗。

**Trade-offs.** Narrow tools mean more tools to build than one generic HTTP tool, but each one is easier to authorize, audit and test. If you truly need flexibility, offer a constrained request tool with an allowlist of hosts and paths per platform, and keep adding credentials in the handler.

> **取舍。** 职责单一的工具意味着要构建的工具比一个通用 HTTP 工具多，但每个工具都更容易授权、审计和测试。如果确实需要灵活性，可以提供一个受限的请求工具，为每个平台设置主机和路径白名单，凭证仍然在处理程序里附加。

</details>

## 3. The agent read a 200-page supplier contract and missed the clause on page 143

**Agent 读了一份 200 页的供应商合同，却漏掉了第 143 页的条款** · `Context & Memory` · `Hard`

### Question · 题目

Merchants upload supplier contracts and product compliance documents, often 100 to 300 pages of PDF. Your agent answers questions such as "Can I sell these products in Germany, and who pays for returns?" by putting the whole PDF into the context and asking.

> 商家会上传供应商合同和商品合规文件，通常是 100 到 300 页的 PDF。你们的 Agent 回答诸如“这些商品能在德国销售吗？退货费用由谁承担？”这样的问题，做法是把整份 PDF 放进上下文然后直接提问。

Answers are usually fluent but sometimes miss a clause buried deep in the document, mix up two similar clauses, or state something the contract does not say. The context window is far larger than the document. What is going on, and how would you make answers reliable?

> 回答通常很流畅，但有时会漏掉藏在文档深处的条款，把两个相似的条款混为一谈，或者说出合同里根本没写的内容。上下文窗口比文档大得多。这是怎么回事？你会如何让回答变得可靠？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Fitting in the window is not the same as being used well. Models attend unevenly across long inputs: details in the middle of a long context are easier to miss (the "lost in the middle" finding), and quality drops as irrelevant text accumulates. A 200-page contract is mostly irrelevant to any single question, so the fix is to point the model at the parts that matter and make it prove its answer from them.

> **核心思路。** 能装进窗口，不等于能被用好。模型对长输入的注意力并不均匀：位于长上下文中间的细节更容易被忽略（即“lost in the middle”研究的发现），并且随着无关文本的累积，质量会下降。一份 200 页的合同对任何单个问题来说大部分内容都无关，所以解决办法是把模型引向关键部分，并让它用这些部分来证明自己的答案。

**Why each failure happens.**

> **每种问题的原因。**

- Missed clause: page 143 competes with 199 other pages for attention, and the question's wording ("returns") may not match the contract's ("reverse logistics costs").
  > 漏掉条款：第 143 页要和另外 199 页争夺注意力，而且问题的措辞（“退货”）可能和合同的措辞（“逆向物流费用”）对不上。
- Mixed-up clauses: contracts repeat similar structures (one returns clause for the EU, one for the US), and nothing forces the model to say which one it used.
  > 条款混淆：合同中有很多结构相似的内容（一条针对欧盟的退货条款，一条针对美国的），而没有任何机制强制模型说明它用的是哪一条。
- Invented statements: without citations, a plausible general answer about returns looks the same as one taken from the document.
  > 编造内容：没有引用时，一个关于退货的、听起来合理的通用回答，看起来和从文档中摘出来的回答没什么两样。

**Fix 1: require citations.** Ask for every claim to quote or point at its source. The Claude API has a citations feature for documents: with citations enabled on a document block, the answer comes back with cited passages and, for PDFs, page numbers. Code can then check that each claim has a citation and show the merchant the exact clause. (In the Claude API, citations cannot be combined with structured outputs in the same request, so pick one per call.)

> **修复一：要求引用。** 要求每一条结论都引用或指明出处。Claude API 为文档提供了引用功能：在文档块上开启引用后，回答会附带被引用的段落，对 PDF 还会给出页码。这样代码就能检查每条结论是否有引用，并把确切的条款展示给商家。（在 Claude API 中，引用功能不能与结构化输出在同一个请求里同时使用，所以每次调用只能选其一。）

**Fix 2: retrieve before you ask.** Split the document by its own structure (sections and clauses, with page numbers), index it with hybrid search, and for each question pass the relevant sections plus the table of contents and definitions, not all 200 pages. Rewrite the question into the contract's vocabulary first ("returns" also searches "reverse logistics", "RMA"). For a single document this is cheap and dramatically raises precision.

> **修复二：先检索再提问。** 按文档自身的结构（章节和条款，并带上页码）切分，用混合检索建立索引；每个问题只传入相关章节，再加上目录和定义部分，而不是全部 200 页。先把问题改写成合同的用语（搜“退货”时也搜“逆向物流”“RMA”）。对单份文档来说，这样做成本很低，却能大幅提高准确性。

**Fix 3: extract once, query many times.** Most questions about supplier contracts are the same: territories, return terms, liability, payment terms, termination, compliance certificates. Run a one-time extraction pass that reads the document in sections (possibly in parallel subagents, each with one part) and fills a structured record with a page reference for every field. Questions are then answered from the record, and the merchant can review it.

> **修复三：一次提取，多次查询。** 关于供应商合同的问题大多相同：销售地区、退货条款、责任、付款条件、终止条款、合规证书。做一次性的提取：分段阅读文档（可以用并行的子 Agent，每个负责一部分），把结果填进一条结构化记录，每个字段都带上页码引用。之后的问题都基于这条记录回答，商家也可以审核它。

```json
{
  "territories": {"value": ["DE", "AT", "FR"], "source": {"page": 12, "clause": "2.1"}},
  "returns_cost_borne_by": {"value": "supplier, EU orders only", "source": {"page": 143, "clause": "17.4(b)"}},
  "returns_window_days": {"value": 30, "source": {"page": 143, "clause": "17.4(a)"}},
  "ce_certificate_provided": {"value": null, "source": null, "note": "not found in the document"}
}
```

**Fix 4: verify the important answers.** For answers that drive decisions (can I sell this in Germany?), run a second check: give a verifier only the cited passages and the claim, and ask whether the passages support it. Unsupported claims are removed or flagged. Allow "the document does not say" as an answer, and make it the expected answer when nothing relevant is found.

> **修复四：核实关键答案。** 对于会影响决策的回答（这个能在德国卖吗？），再做一次检查：只把被引用的段落和结论交给一个核查步骤，问这些段落是否支持该结论。没有依据的结论会被删除或标记出来。允许“文档中没有说明”作为答案，并且在找不到相关内容时，把它作为预期的回答。

**Practical details.** PDFs have size and page limits per request (in the Claude API, 32 MB per request and up to 600 pages on 1M-context models), so very large documents have to be split anyway. Upload each file once and reference it by ID across calls instead of resending it, and cache the stable document prefix when you ask several questions in a row.

> **实际细节。** PDF 在每个请求中都有大小和页数限制（在 Claude API 中，每个请求最大 32 MB，1M 上下文的模型最多 600 页），所以非常大的文档无论如何都需要拆分。每个文件只上传一次，在多次调用中通过 ID 引用，而不是反复重发；连续问多个问题时，把不变的文档前缀缓存起来。

**Trade-offs.** Retrieval can miss a clause that uses unexpected wording, while full-document reading is slower and costlier but sees everything; a hybrid that retrieves first and falls back to a full read when retrieval finds nothing works well. Extraction adds an up-front cost per document but makes repeated questions cheap, consistent and reviewable.

> **取舍。** 检索可能漏掉措辞出乎意料的条款，而通读全文更慢、更贵，但能看到所有内容；一种效果不错的折中是先检索，检索不到时再退回到通读全文。提取会为每份文档增加一笔前期成本，但能让重复的问题回答得便宜、一致，而且可以审核。

</details>

## 4. Task success fell from 91% to 84% overnight, and nobody deployed anything

**任务成功率一夜之间从 91% 掉到 84%，而没有任何人发布过东西** · `Evals & Observability` · `Hard`

### Question · 题目

Your feed-fixing agent has a dashboard of online success rate (cases resolved without a human). It has been stable around 91% for weeks. On Tuesday it drops to 84% and stays there. The team checks the deploy log: no code, prompt or config changes in a week.

> 你们的 feed 修复 Agent 有一个线上成功率看板（无需人工介入就解决的案例比例）。几周来一直稳定在 91% 左右。周二它掉到了 84%，并且一直没有回升。团队查了发布记录：一周内没有任何代码、提示词或配置变更。

How would you find the cause? List the likely suspects and the order in which you would check them.

> 你会如何找出原因？列出可能的嫌疑点，以及你检查它们的顺序。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** An agent's behaviour depends on much more than your deploys: the inputs it receives, the external APIs its tools call, any third-party tools or servers it loads, and the model and settings behind the API. "Nothing changed" usually means "nothing we deploy changed". Debug it like any production regression: narrow down when, where and for whom, then compare good runs with bad runs.

> **核心思路。** Agent 的行为远不只取决于你们的发布：它收到的输入、工具调用的外部 API、它加载的第三方工具或服务，以及 API 背后的模型和设置，都会影响它。“什么都没变”通常只是“我们发布的东西没变”。像排查任何线上回退一样排查它：先缩小范围，确定是什么时候、在哪里、对谁出的问题，然后对比正常的运行和失败的运行。

**Step 1: slice the drop.** Break the success rate down by hour, merchant segment, platform (Google versus Meta), error category, language and tool. A sharp step at one time points to an external change; a drop concentrated in one platform or one tool points at that dependency; a drop spread evenly across everything points at the model, the prompt path or the grader.

> **第一步：把下降拆开看。** 按小时、商家分群、平台（Google 和 Meta）、错误类别、语言和工具拆分成功率。如果在某个时间点陡然下降，说明是外部发生了变化；如果下降集中在某个平台或某个工具，问题就出在那个依赖上；如果所有维度都均匀下降，就要怀疑模型、提示词链路或评分方式。

**Step 2: check the usual suspects, cheapest first.**

> **第二步：从成本最低的开始，逐个检查常见嫌疑点。**

- The measurement itself: did the success definition, the logging or an LLM grader change? A grader that moved can create a drop that is not real.
  > 度量本身：成功的定义、日志记录方式或 LLM 评分器有没有变化？评分器一变，就可能造出一个并不真实的下降。
- Input mix: a new merchant segment, a seasonal surge, or a new feed source can bring harder cases. Compare the distribution of case types before and after.
  > 输入构成：新的商家群体、季节性高峰或新的 feed 来源，可能带来更难的案例。对比前后案例类型的分布。
- External APIs: platforms change response formats, error codes and policies without telling you. A field renamed in a diagnostics response can make a tool return empty results, and the agent then reasons from nothing.
  > 外部 API：平台会在不通知你的情况下修改响应格式、错误码和政策。诊断接口里某个字段改了名，就可能让工具返回空结果，Agent 随后就在没有信息的情况下推理。
- Third-party tools: an MCP server or plugin you load can update its tool descriptions or behaviour on its own schedule.
  > 第三方工具：你加载的 MCP server 或插件，可能按它自己的节奏更新工具描述或行为。
- Model configuration: record the exact model ID, effort and other settings on every trace, and confirm nothing resolved differently from last week. If the config uses an alias, check which model it actually served.
  > 模型配置：在每条链路追踪上记录确切的模型 ID、effort 和其他设置，确认它们与上周解析出的结果完全一致。如果配置里用的是别名，要查清它实际调用的是哪个模型。

**Step 3: diff good and bad trajectories.** Take a sample of failures from after the drop and successes from before it, with similar case types, and compare the traces: which tools were called, what they returned, where the runs diverged. Often one tool result looks different (an empty list, a new error message) and everything after it goes wrong. Replay a failing case against recorded tool results from before the change to confirm the cause.

> **第三步：对比正常与失败的执行轨迹。** 取下降之后的一批失败案例和下降之前的一批成功案例，案例类型尽量相近，然后对比它们的链路追踪：调用了哪些工具、返回了什么、在哪里开始分叉。常见的情况是某个工具的返回看起来不一样了（空列表、新的错误信息），之后的一切都跟着出错。用变化发生前录制的工具结果重放一个失败案例，以确认原因。

```text
before (success)  get_item_issues -> 3 issues [missing_gtin x2, price_mismatch]
after  (failure)  get_item_issues -> []        agent: "No problems found, nothing to fix"
cause: the platform moved issues to a new response field; our parser read the old one
```

**Step 4: fix, then prevent.** Fix the cause (here, the parser), and add a regression case built from a real failing trace. Then close the blind spot: contract tests that call each external API daily and alert when the response shape changes; alerts on tool-level signals (empty results, new error codes) rather than only on the final success rate; and version pinning for third-party tools where possible.

> **第四步：修复，然后预防。** 修复根因（这个例子里是解析器），并用真实的失败轨迹构建一个回归测试案例。然后补上盲区：每天调用各个外部 API 的契约测试，在响应结构变化时告警；在工具层面的信号（空结果、新错误码）上设置告警，而不只盯着最终成功率；条件允许时锁定第三方工具的版本。

**Trade-offs.** Detailed traces and per-tool dashboards cost storage and effort, but without them a silent regression turns into days of guessing. Pinning everything protects stability but means you have to schedule upgrades deliberately, with your eval suite as the gate.

> **取舍。** 详细的链路追踪和按工具划分的看板需要存储和投入，但没有它们，一次无声的回退就会变成好几天的猜测。把一切都锁定版本能保证稳定，但意味着你必须有计划地安排升级，并以评测套件作为把关。

</details>

## 5. An agent that waits hours for a merchant's approval, then continues safely

**Agent 等待商家审批几个小时后，如何安全地继续执行** · `Agent Loop` · `Senior`

### Question · 题目

Your campaign agent analyzes a merchant's ads, proposes budget changes and must wait for the merchant to approve them, which can take minutes or a whole weekend. Today the agent loop runs inside a worker that blocks while it waits, so workers pile up, and after a deploy restarts them the pending approvals are lost.

> 你们的广告系列 Agent 会分析商家的广告、提出预算调整建议，并且必须等商家批准，这可能需要几分钟，也可能要等整个周末。现在 Agent 循环跑在一个 worker 里，等待时会一直阻塞，于是 worker 越积越多，而一次发布导致 worker 重启后，待审批的请求就全丢了。

Design a human-in-the-loop flow that pauses for as long as needed and resumes correctly. Cover the state you store, how the conversation with the model resumes, and what must be checked when it does.

> 设计一个人机协同的流程，能暂停任意长的时间，并且能正确地恢复。说明你要存储哪些状态、与模型的对话如何恢复，以及恢复时必须检查什么。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** The model API is stateless: each request carries the whole conversation, and nothing is held open between requests. So an agent never has to wait in memory. Pausing means saving the conversation and the pending action to a database and stopping; resuming means loading them and sending the next request, minutes or days later. It is a workflow with a durable wait state, like an order waiting for payment.

> **核心思路。** 模型 API 是无状态的：每个请求都携带完整的对话，请求之间不保持任何连接。所以 Agent 根本不需要在内存里等待。暂停就是把对话和待执行的操作存进数据库然后停下；恢复就是把它们读出来，再发送下一个请求，不管是几分钟后还是几天后。这是一个带持久化等待状态的工作流，就像一个等待付款的订单。

**Where the pause happens.** The model proposes the change by calling a tool such as `propose_budget_changes`. Instead of executing it, the harness stores the proposal and ends the run in a `waiting_approval` state. The assistant message containing that `tool_use` block stays in the saved history exactly as received; when the merchant decides, the next request answers it with a `tool_result` carrying the decision. Every `tool_use` must get its `tool_result` in the next user message, so the decision slots naturally into the protocol.

> **在哪里暂停。** 模型通过调用 `propose_budget_changes` 这样的工具来提出修改。harness 不执行它，而是保存这个提议，并以 `waiting_approval` 状态结束本次运行。包含这个 `tool_use` 块的 assistant 消息原样保存在历史中；商家做出决定后，下一个请求用一个携带该决定的 `tool_result` 来回应它。每个 `tool_use` 都必须在下一条 user 消息中得到对应的 `tool_result`，所以审批结果自然地嵌进了协议里。

```go
type Run struct {
	ID          string
	MerchantID  string
	Status      string          // running | waiting_approval | approved | rejected | expired | done
	Messages    json.RawMessage // full history, assistant content stored exactly as returned
	PendingCall *PendingCall    // the tool_use awaiting a decision
	ExpiresAt   time.Time
	Version     int64           // optimistic lock: approve and expire can race
}

type PendingCall struct {
	ToolUseID string
	Plan      json.RawMessage // exact changes the merchant sees and approves
	PlanHash  string          // approval is bound to this hash
	Snapshot  json.RawMessage // budgets as they were when the plan was made
}
```

**Store the history exactly.** Save the assistant content as returned, including any thinking blocks, and append to it rather than editing earlier turns. Some newer models validate replayed thinking blocks against the conversation they came from, so a resumed request that edits history can be rejected or lose reasoning. Also expect the prompt cache to have expired after a long pause (its lifetime is minutes to an hour), so the first resumed request pays to rebuild it.

> **原样保存历史。** assistant 返回的内容要原样保存，包括其中的 thinking 块，并且只追加、不修改之前的轮次。一些较新的模型会校验回传的 thinking 块是否属于原来的对话，所以一个修改了历史的恢复请求可能会被拒绝，或者丢失推理内容。另外要预期：长时间暂停后 prompt 缓存已经过期（它的有效期是几分钟到一小时），所以恢复后的第一个请求需要付费重建缓存。

**Approval is an authenticated action bound to the exact plan.** The merchant approves in your UI, not by typing "yes" in chat. The approval record stores who approved, when, and the plan hash. If the plan changed, the old approval does not apply. Use the run's version for a conditional update, so an approval and an expiry that arrive at the same moment cannot both win.

> **审批是一个经过身份认证、并绑定到确切计划的操作。** 商家在你们的 UI 里审批，而不是在聊天里输入“同意”。审批记录保存谁批准的、什么时候批准的，以及计划的哈希值。如果计划变了，旧的审批就不再适用。用运行记录的版本号做条件更新，这样同时到达的审批和过期操作不会都生效。

**Re-validate on resume.** Hours later the world has moved: the merchant may have edited budgets by hand, a campaign may have been paused, or spend may already be over the limit. Before executing, compare the current state with the snapshot. If something relevant changed, do not apply the stale plan; return a `tool_result` that explains what changed, and let the model propose again. Apply the approved changes with idempotency keys derived from the run and the change, so a crash in the middle cannot apply them twice.

> **恢复时重新校验。** 几个小时后，情况已经变了：商家可能手动改过预算，某个广告系列可能被暂停了，或者花费可能已经超出上限。执行之前，把当前状态和快照对比。如果相关内容发生了变化，就不要执行过时的计划，而是返回一个说明变化的 `tool_result`，让模型重新提出方案。执行已批准的修改时，使用由运行 ID 和具体修改派生出的幂等键，这样即使中途崩溃也不会重复执行。

**Timeouts and reminders.** Give each pending approval an expiry. A scheduler sends reminders and, at the deadline, resumes the run with a "no decision, expired" result, so the model closes the task cleanly. Decide per action what silence means; for money, it always means "do not apply".

> **超时与提醒。** 给每个待审批请求设置过期时间。由调度器发送提醒，并在截止时用“未作决定，已过期”的结果恢复运行，让模型干净地结束这个任务。每类操作都要明确沉默意味着什么；涉及金钱的操作，沉默永远意味着“不执行”。

**Trade-offs.** A durable workflow engine gives you timers, retries and resumable state, but adds a system to operate; a status table plus a scheduler is often enough at first. Batching several proposals into one approval reduces approval fatigue, but makes partial approval and re-validation more complex, so let the merchant approve items individually within a batch.

> **取舍。** 持久化工作流引擎能提供定时器、重试和可恢复的状态，但也多了一个需要运维的系统；起步阶段，一张状态表加一个调度器往往就够了。把多个提议合并成一次审批可以减少审批疲劳，但会让部分批准和重新校验变得更复杂，所以要允许商家在一批中逐项审批。

</details>
