## 1. The order-status tool returns the shopper's whole profile, and phone numbers and street addresses start showing up in chat replies and traces

**订单状态工具返回了顾客的完整资料，于是电话号码和街道地址开始出现在聊天回复和链路追踪里** · `Safety & Security` · `Medium`

### Question · 题目

The shopper-facing support assistant answers "where is my order?". Its `get_order` tool returns the full order record from the database: name, email, phone, shipping address, payment card's last four digits, and status. Shoppers occasionally see their full address repeated back to them in chat, the observability team finds phone numbers in every trace, and a security review asks why the model ever sees card digits.

> 面向顾客的客服助手负责回答「我的订单到哪了？」。它的 `get_order` 工具会从数据库返回完整的订单记录：姓名、邮箱、电话、收货地址、银行卡后四位以及状态。顾客偶尔会在聊天中看到自己的完整地址被复述出来，可观测性团队在每一条链路追踪里都找到了电话号码，而安全评审则问：为什么模型能看到卡号数字？

Explain the risk and redesign the tool.

> 解释其中的风险，并重新设计这个工具。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Whatever a tool returns becomes part of the conversation: the model can repeat it, it is stored with the transcript, and it flows into logs, traces and eval sets. So the cheapest privacy control is to never hand the model data the task does not need. This is data minimization applied at the tool boundary.

> **核心思想。** 工具返回的任何内容都会成为对话的一部分：模型可能复述它，它会随对话记录一起存储，还会流进日志、链路追踪和评测集。所以最便宜的隐私控制，就是绝不把任务用不到的数据交给模型。这就是在工具边界上落实的数据最小化。

**Why it leaks today.** The tool was written as a thin wrapper over the database row, which is convenient for engineers and wrong for an agent. The model is trying to be helpful, so it confirms details it can see, and every system that records tool results copies the personal data along with it.

> **为什么现在会泄露。** 这个工具写成了数据库行的一层薄包装，对工程师来说很方便，对 Agent 来说却是错的。模型想要帮上忙，所以会确认它能看到的细节；而每一个记录工具结果的系统，都会把这些个人数据一并复制下来。

**The fix: a purpose-built view per tool.**

> **修复方法：为每个工具设计专用的视图。**

```go
// orderStatusView is the only shape the order-status tool returns to the model.
type orderStatusView struct {
	OrderID     string `json:"order_id"`
	Status      string `json:"status"`
	Carrier     string `json:"carrier,omitempty"`
	TrackingURL string `json:"tracking_url,omitempty"`
	ShipsTo     string `json:"ships_to_country,omitempty"` // enough to answer "where is it going?"
}

func toStatusView(o Order, country string) orderStatusView {
	return orderStatusView{OrderID: o.ID, Status: o.Status, Carrier: o.Carrier, TrackingURL: o.TrackingURL, ShipsTo: country}
}
```

- Return only what answers the question: status, carrier, tracking link, and the destination country rather than the street address. In a local run, the projected result was half the size of the full record and contained no contact details.
  > 只返回能回答问题的内容：状态、承运商、追踪链接，以及目的国家而不是街道地址。在本地运行中，投影后的结果只有完整记录的一半大小，而且不含任何联系方式。
- When a task does need personal data, such as changing the shipping address, use a separate tool that writes it without reading it back, and gate it behind a check that the shopper is signed in to the right account.
  > 当任务确实需要个人数据时，比如修改收货地址，就使用一个单独的工具：只写入、不回读，并且要先验证顾客已登录到正确的账户。
- Card digits never belong in a support tool. If shoppers need to know which card was charged, show it in your own UI, outside the conversation.
  > 卡号数字绝不应该出现在客服工具里。如果顾客需要知道扣的是哪张卡，就在你自己的界面上显示，放在对话之外。

**Clean the other paths too.** Redact known patterns such as emails and phone numbers before tool results reach logs and traces, keep full-content tracing off by default in production, and set retention limits for stored transcripts. Redaction is a safety net; the view is the real control, because a pattern list always misses something, such as an address typed in an unusual format.

> **把其他路径也清理干净。** 在工具结果进入日志和链路追踪之前，先对邮箱、电话号码等已知格式做脱敏；生产环境默认关闭全量内容追踪；并为存储的对话记录设置保留期限。脱敏只是安全网；视图才是真正的控制手段，因为模式列表总会漏掉一些东西，比如用不常见格式写的地址。

**Trade-offs.** Narrow tools mean more tools and more code, and sometimes the agent needs a second call where one wide call would have done. That is a fair price: each tool's view is also its documentation of what data the agent is allowed to see, and a reviewer can approve it in minutes.

> **权衡。** 窄工具意味着更多的工具和更多的代码，有时 Agent 还需要多调用一次，而原本一次宽调用就够了。这个代价是值得的：每个工具的视图，同时也是一份文档，说明了 Agent 被允许看到哪些数据，评审人员几分钟就能审完。

</details>

## 2. The help assistant tells a shopper returns are accepted for 30 days, quoting the platform's default, while the merchant's own policy says 14

**帮助助手告诉顾客退货期限是 30 天，引用的是平台默认规则，而商家自己的政策写的是 14 天** · `RAG` · `Medium`

### Question · 题目

Each storefront has a shopper assistant that retrieves from two sources: the platform's general help center and the merchant's own policy pages. A shopper asks about returns, retrieval finds both the platform article ("stores accept returns within 30 days by default") and the merchant's policy ("14 days"), and the answer says 30 days. The merchant now has angry shoppers holding a screenshot.

> 每个店铺都有一个顾客助手，它从两个来源检索：平台的通用帮助中心，以及商家自己的政策页面。一位顾客询问退货规则，检索同时找到了平台文章（「店铺默认接受 30 天内退货」）和商家政策（「14 天」），而回答说的是 30 天。现在商家面对的是拿着截图的愤怒顾客。

Explain why this happens and design the fix.

> 解释为什么会这样，并设计修复方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Retrieval ranks passages by how well they match the question, not by how much authority they have. When two sources disagree, the model sees two plausible passages and no rule saying which one wins. Authority is a property of the source, so the system has to decide it, not the similarity score.

> **核心思想。** 检索是按照段落与问题的匹配程度来排序的，而不是按照它们的权威性。当两个来源互相矛盾时，模型看到的是两段看起来都合理的文字，却没有任何规则说明哪一段优先。权威性是来源本身的属性，所以必须由系统来决定，而不是由相似度分数决定。

**Why the platform text won.** General help articles are written to explain a topic thoroughly, so they often match a question better than a merchant's short policy page. They also use the same wording as the question. The model then preferred the more detailed passage, which was the wrong one for this store.

> **为什么平台文本胜出。** 通用帮助文章的写法是为了把一个主题讲透，所以它们往往比商家简短的政策页面更贴合问题，用词也和提问更一致。于是模型更倾向于那段更详细的文字，而对这家店来说它恰恰是错的。

**The fix: label sources and resolve conflicts before generation.**

> **修复方法：给来源打标签，并在生成之前解决冲突。**

```go
var precedence = map[string]int{"merchant_policy": 0, "platform_help": 1, "community": 2}

// resolve keeps, for each topic, only the passage from the most authoritative source,
// and reports which topics had a conflict so the answer can say so.
func resolve(ps []Passage) (kept []Passage, conflicts []string) {
	best := map[string]Passage{}
	seen := map[string]map[string]bool{}
	for _, p := range ps {
		if seen[p.Topic] == nil {
			seen[p.Topic] = map[string]bool{}
		}
		seen[p.Topic][p.Source] = true
		if b, ok := best[p.Topic]; !ok || precedence[p.Source] < precedence[b.Source] {
			best[p.Topic] = p
		}
	}
	for t, p := range best {
		kept = append(kept, p)
		if len(seen[t]) > 1 {
			conflicts = append(conflicts, t)
		}
	}
	sort.Slice(kept, func(i, j int) bool { return kept[i].Topic < kept[j].Topic })
	sort.Strings(conflicts)
	return kept, conflicts
}
```

- Tag every chunk with its source and a topic key at indexing time, such as `returns.window`. Merchant policy outranks the platform default on the same topic; the platform article still answers topics the merchant never wrote about.
  > 在建索引时给每个块打上来源和主题键，比如 `returns.window`。在同一主题上，商家政策的优先级高于平台默认规则；而商家从未写过的主题，仍然由平台文章来回答。
- In a local run, the 14-day merchant policy was kept for `returns.window`, the platform article was kept for return labels, and the conflict was reported.
  > 在本地运行中，`returns.window` 保留了商家 14 天的政策，退货运单这个主题保留了平台文章，并且报告了冲突。
- Also say it in the prompt: present passages grouped by source with their authority, and instruct the assistant that the store's own policy applies to this store.
  > 也要在提示词里说清楚：按来源分组呈现段落并标明其权威性，并告诉助手：本店自己的政策适用于本店。

**When topics cannot be tagged.** Retrieve from the merchant's sources first and fall back to platform content only when nothing relevant is found, or ask the model to state which source it used and check that the citation is a merchant page for policy questions.

> **当无法给主题打标签时。** 先从商家的来源检索，只有找不到相关内容时才回退到平台内容；或者让模型说明它用了哪个来源，并检查政策类问题的引用是否来自商家页面。

**Measure it.** Add eval cases where the merchant's policy differs from the platform default for returns, shipping and warranties, and score whether the answer follows the merchant. These are exactly the questions where being confidently wrong costs the merchant money.

> **度量它。** 加入一些评测用例：在退货、配送和保修方面，商家政策与平台默认规则不同；然后评分答案是否遵循了商家的规定。正是在这类问题上，自信地答错会让商家损失钱。

**Trade-offs.** Hard precedence rules can be wrong when a merchant's page is outdated. Show the date of the merchant policy in the answer, and give merchants a dashboard that lists topics where their pages contradict platform defaults, so they can fix the source.

> **权衡。** 当商家页面已经过时时，硬性的优先级规则也可能出错。在回答里显示商家政策的日期，并给商家提供一个看板，列出他们页面与平台默认规则相矛盾的主题，让他们能修正源头。

</details>

## 3. Merchants can edit an earlier message or regenerate a reply in the planning chat, and the team's in-place edits break caching and fail on newer models

**商家可以在规划聊天里编辑之前的消息或重新生成回复，而团队采用的原地修改方式破坏了缓存，并在较新的模型上报错** · `Context & Memory` · `Hard`

### Question · 题目

The campaign-planning chat now lets merchants edit an earlier message or regenerate an answer, like popular chat apps. The first implementation overwrites the edited message in the stored history and deletes everything after it. Merchants complain they lost a plan they liked, the cache hit rate dropped, and on a newer model some requests after a regenerate fail with errors about thinking blocks.

> 活动规划聊天现在允许商家编辑之前的消息或重新生成回答，就像流行的聊天应用那样。第一版实现会在存储的历史中覆盖被编辑的消息，并删除它之后的所有内容。商家抱怨丢了一份他们喜欢的方案，缓存命中率下降了，而且在较新的模型上，重新生成之后的一些请求会因 thinking 块相关的错误而失败。

Design how edits and regenerations should work.

> 设计编辑和重新生成应当如何工作。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** An edit does not change the past; it starts a new branch from an earlier point. Model a conversation as a tree: every message is stored once, exactly as sent or received, and each branch is a path from the root to a leaf. Sending a request means sending one path. Nothing that was sent is ever modified.

> **核心思想。** 编辑不是在修改过去，而是从更早的某个点开出一个新分支。把对话建模成一棵树：每条消息只存储一次，并且与当初发送或接收时完全一致；每个分支都是从根到某个叶子的一条路径。发起请求就是发送其中一条路径。已经发送过的内容永远不被修改。

```go
// Node is one message in a conversation tree. Content is stored exactly as sent
// or received, including thinking blocks, and never edited.
type Node struct {
	ID       string
	ParentID string // "" for the first message
	Role     string // "user" or "assistant"
	Content  string // raw blocks as JSON in a real system
}

type Tree struct {
	Nodes  map[string]Node
	Active string // leaf of the branch the user is looking at
}

// Path returns the messages from the root to the active leaf: the exact
// history to send for the next request on this branch.
func (t Tree) Path() []Node {
	var rev []Node
	for id := t.Active; id != ""; id = t.Nodes[id].ParentID {
		rev = append(rev, t.Nodes[id])
	}
	out := make([]Node, len(rev))
	for i := range rev {
		out[i] = rev[len(rev)-1-i]
	}
	return out
}

// Edit adds a new user message as a sibling of an existing one and makes it active.
func (t *Tree) Edit(of, newID, text string) {
	t.Nodes[newID] = Node{ID: newID, ParentID: t.Nodes[of].ParentID, Role: "user", Content: text}
	t.Active = newID
}
```

In a local run, editing the second user message created a sibling, and the active path became the first exchange followed by the edited message, with the old reply kept on its own branch.

> 在本地运行中，编辑第二条用户消息创建了一个兄弟节点，当前路径变成了第一轮对话加上编辑后的消息，而旧的回复保留在它自己的分支上。

**Why the old design broke things.**

> **为什么旧设计会出问题。**

- Lost work: overwriting and deleting removed the branch the merchant wanted to return to. A tree keeps every branch.
  > 丢失工作：覆盖和删除抹掉了商家想要回去的那个分支。树结构会保留每一个分支。
- Caching: prompt caching is a prefix match. A branch that shares the first ten turns with the old one still matches that prefix, so it can read the cache; rewriting stored messages in place changes bytes and loses it.
  > 缓存：提示缓存是前缀匹配。与旧分支共享前十轮的新分支依然能匹配这段前缀，所以可以命中缓存；而原地改写存储的消息会改变字节，导致缓存失效。
- Thinking blocks: on models that run the preserved-thinking check, a replayed thinking block is valid only if the system prompt, tools and every earlier message are byte-identical to when it was produced. Rewriting history in place breaks that. A branch keeps everything before the branch point untouched, so earlier blocks on the path remain valid, and blocks from the abandoned branch are simply not sent.
  > Thinking 块：在执行 preserved thinking 检查的模型上，被重放的 thinking 块只有在系统提示词、工具以及之前的每条消息都与它生成时逐字节一致的情况下才有效。原地改写历史会破坏这一点。分支会让分支点之前的一切保持原样，所以路径上较早的块依然有效，而被放弃分支上的块根本不会被发送。

**Regenerate is a branch too.** Regenerating an answer adds a sibling assistant node under the same user message. Show merchants the alternatives and let them switch; the active leaf decides what the next request sends.

> **重新生成也是一个分支。** 重新生成回答，就是在同一条用户消息下新增一个兄弟助手节点。把这些备选结果展示给商家，让他们可以切换；当前叶子决定了下一次请求发送什么。

**Side effects do not branch.** If the abandoned branch launched a campaign through a tool, editing a message does not undo it. Mark tool calls with side effects in the tree, and when a merchant branches past one, tell them it already happened and offer an explicit undo action.

> **副作用不会随分支分开。** 如果被放弃的分支通过工具发布了一个广告活动，编辑消息并不会撤销它。在树中标记出带副作用的工具调用；当商家从这类调用之前开分支时，告诉他们这件事已经发生了，并提供一个明确的撤销操作。

**Trade-offs.** Trees use more storage than a list, and every feature that reads history, such as search, export and memory extraction, must decide which branch it means, usually the active one. Long branches still need server-side compaction or context editing, applied per branch.

> **权衡。** 树比列表占用更多存储空间，而且每一个读取历史的功能（比如搜索、导出和记忆提取）都必须决定它指的是哪个分支，通常是当前分支。很长的分支仍然需要服务端压缩或上下文编辑，并且要按分支分别处理。

</details>

## 4. After the LLM judge was moved to a newer model, the support-quality dashboard dropped 9 points overnight, and nothing about the agent had changed

**把 LLM 评审换成更新的模型后，客服质量看板一夜之间掉了 9 个点，而 Agent 本身没有任何改动** · `Evals & Observability` · `Hard`

### Question · 题目

A nightly job samples production support conversations and asks an LLM judge to score each one for correctness and tone. The weekly quality number goes to leadership. When the platform team upgraded the judge to a newer model, the score fell by 9 points the next day. The agent, its prompt and its tools were unchanged. Leadership wants to know whether quality really dropped.

> 一个夜间任务会抽样生产环境的客服对话，让一个 LLM 评审从正确性和语气两方面给每段对话打分。每周的质量数字会报给管理层。平台团队把评审升级到一个更新的模型后，第二天分数下降了 9 个点。Agent 本身、它的提示词和工具都没有变化。管理层想知道质量是否真的下降了。

Explain what happened and how the monitoring should be built.

> 解释发生了什么，以及这套监控应当如何构建。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A judged score is a measurement made with an instrument, and the judge is the instrument. Change the judge model, its prompt or its rubric, and you have changed the ruler. Scores from before and after a grader change are not comparable, so a step change on the day of an upgrade is first a question about the judge, not about the agent.

> **核心思想。** 评审给出的分数，是用一件仪器做出的测量，而评审就是那件仪器。换掉评审模型、它的提示词或评分标准，就等于换了一把尺子。评分器变更前后的分数不可比，所以在升级当天出现的跳变，首先是关于评审的问题，而不是关于 Agent 的问题。

**How to tell which one moved.** Keep a fixed anchor set of conversations that humans labeled independently, and run every judge version on it:

> **如何判断是谁变了。** 保留一组固定的锚定对话集，由人工独立标注，并让每个版本的评审都在上面跑一遍：

```go
// JudgeVersion pins everything that defines a score.
type JudgeVersion struct {
	Model    string
	PromptID string
	Rubric   string
}

// agreement compares judge verdicts with human labels on the anchor set.
func agreement(judge, human []bool) float64 {
	same := 0
	for i := range judge {
		if judge[i] == human[i] {
			same++
		}
	}
	return float64(same) / float64(len(judge))
}
```

- If the new judge agrees with the human labels less than the old one did, the drop is the judge's. The snippet's example shows that pattern: the two judges disagree with each other far more than the old judge disagreed with people.
  > 如果新评审与人工标注的一致率低于旧评审，那么下降就是评审造成的。代码片段中的例子展示的正是这种模式：两个评审之间的分歧，远大于旧评审与人工之间的分歧。
- If both judges agree with humans equally well and both score the same recent conversations lower, the agent's quality did drop, and the cause is elsewhere, such as new kinds of questions.
  > 如果两个评审与人工的一致率相当，而且都给同一批近期对话打了更低的分，那么 Agent 的质量确实下降了，原因在别处，比如出现了新类型的问题。
- Also re-score last week's sampled conversations with the new judge. Same conversations, different score, means the ruler moved.
  > 还要用新评审给上周抽样的对话重新打分。同样的对话、不同的分数，说明是尺子变了。

**How to build the monitor.** Version the judge as one unit, model plus prompt plus rubric, and record that version with every score. Upgrade by running old and new judges side by side for a period, publish the new series only once it is calibrated against the anchor set, and mark the change on the dashboard. Prefer atomic checks, such as "cited the right policy" or "promised a refund it could not give", over one holistic score, so a drift shows up in a specific property.

> **如何构建监控。** 把评审作为一个整体做版本管理：模型、提示词和评分标准一起，并在每个分数上记录这个版本。升级时让新旧评审并行运行一段时间，只有在新评审对照锚定集校准之后才发布新的数据序列，并在看板上标注这次变更。优先使用原子化的检查项，比如「引用了正确的政策」或「承诺了无法兑现的退款」，而不是一个整体分数，这样漂移会体现在某个具体属性上。

**Sampling and noise.** A nightly sample has its own variance; report the score with an interval and the sample size, so a few points of movement are not mistaken for a trend. Keep the sampling rule stable too, because a change in which conversations are sampled moves the score as surely as a change in the judge.

> **抽样与噪声。** 每晚的抽样本身就有方差；报告分数时要附上置信区间和样本量，免得几个点的波动被误认为趋势。抽样规则也要保持稳定，因为抽中哪些对话的变化，和评审的变化一样会让分数移动。

**Trade-offs.** Human labeling costs money and time, but a small anchor set of a few dozen clear cases is enough to catch a broken judge. Pinning the judge forever avoids drift but leaves you on an old model, which may itself be retired; a planned, calibrated switch is the middle path.

> **权衡。** 人工标注要花钱也要花时间，但几十个清晰用例组成的小型锚定集，就足以发现一个出了问题的评审。永远固定评审可以避免漂移，却会让你一直停留在旧模型上，而旧模型本身也可能退役；有计划、经过校准的切换才是折中之道。

</details>

## 5. Thirty parallel worker agents hit the Meta Marketing API rate limit together, all retry at once, and the coordinator marks half the ad accounts as failed

**三十个并行的工作 Agent 同时撞上 Meta Marketing API 的限流，一起重试，协调者把一半的广告账户标记为失败** · `Multi-agent` · `Senior`

### Question · 题目

A nightly audit uses a coordinator that starts one worker agent per batch of ad accounts. Each worker calls the Meta Marketing API through its own tools and retries with backoff on rate-limit errors. With 30 workers running, the account-level limit is exceeded within minutes, every worker backs off and retries on a similar schedule, the limit is hit again, and many workers give up and report failure. The coordinator's summary says half the accounts could not be audited.

> 一个夜间审计任务由一个协调者负责，它为每一批广告账户启动一个工作 Agent。每个工作 Agent 通过自己的工具调用 Meta Marketing API，遇到限流错误时带退避地重试。当 30 个工作 Agent 同时运行时，几分钟内就会超出账户级别的限额；每个工作 Agent 都按相似的节奏退避重试，然后又一次撞上限额，许多工作 Agent 放弃并报告失败。协调者的总结说有一半账户无法完成审计。

Redesign how the agents share the external API.

> 重新设计这些 Agent 如何共享这个外部 API。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** A rate limit belongs to the API account, not to any one agent. Thirty agents that each manage their own retries are thirty independent clients competing for one budget, and they cannot see each other. The quota has to be owned by one shared component that every worker goes through, and agents should spend their intelligence on the audit, not on fighting for capacity.

> **核心思想。** 限流额度属于 API 账户，而不属于任何一个 Agent。30 个各自管理重试的 Agent，就是 30 个互相看不见、却在争抢同一份额度的独立客户端。额度必须由一个所有工作 Agent 都要经过的共享组件来掌管；Agent 应该把智能用在审计上，而不是用在争抢容量上。

**Why it collapsed.** Retries multiply load exactly when the API is already saying no. Similar backoff schedules make workers return together, so the limit is hit in waves. And because each worker saw only its own failures, it concluded the task was impossible and stopped, turning a capacity problem into a wrong audit result.

> **为什么会崩溃。** 重试恰恰在 API 已经说「不」的时候成倍放大了负载。相似的退避节奏让工作 Agent 一起回来，于是限额被一波接一波地撞上。而且每个工作 Agent 只看到自己的失败，就断定任务无法完成而停下，把一个容量问题变成了一个错误的审计结果。

**The fix: one quota gate shared by all workers.**

> **修复方法：所有工作 Agent 共享同一个额度关卡。**

```go
// Quota is shared by every worker that calls the same ad account.
type Quota struct {
	mu        sync.Mutex
	slots     chan struct{} // max calls in flight
	pausedTil time.Time     // set from Retry-After; every worker honors it
}

func NewQuota(inFlight int) *Quota { return &Quota{slots: make(chan struct{}, inFlight)} }

// Do waits for a slot and for any account-wide pause, then runs the call.
func (q *Quota) Do(ctx context.Context, call func() (retryAfter time.Duration, err error)) error {
	select {
	case q.slots <- struct{}{}:
	case <-ctx.Done():
		return ctx.Err()
	}
	defer func() { <-q.slots }()
	for {
		q.mu.Lock()
		wait := time.Until(q.pausedTil)
		q.mu.Unlock()
		if wait <= 0 {
			break
		}
		select {
		case <-time.After(wait):
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	ra, err := call()
	if ra > 0 {
		q.mu.Lock()
		if t := time.Now().Add(ra); t.After(q.pausedTil) {
			q.pausedTil = t // one 429 pauses everyone, instead of thirty retries
		}
		q.mu.Unlock()
	}
	return err
}
```

- The tool implementation, not the agent, calls the API through the gate. It caps calls in flight per ad account; in a local run, 30 workers never had more than 5 calls in flight.
  > 通过这个关卡调用 API 的是工具实现，而不是 Agent。它按广告账户限制同时在途的调用数；在本地运行中，30 个工作 Agent 同时在途的调用从未超过 5 个。
- One rate-limit response pauses every worker for the time the API asked for, instead of thirty separate retry storms. Add jitter when the pause ends.
  > 一次限流响应会让所有工作 Agent 按 API 要求的时间暂停，而不是出现 30 场各自为战的重试风暴。暂停结束时加入随机抖动。
- When workers run in separate processes, the gate moves to a shared service or a Redis-backed limiter keyed by ad account.
  > 当工作 Agent 运行在不同进程中时，这个关卡要挪到一个共享服务里，或者使用按广告账户为键、基于 Redis 的限流器。

**Tell agents the truth about waiting.** A worker should see "queued behind the account's rate limit, retrying automatically" rather than an error, so it does not give up or try workarounds. Only a real failure, such as an expired token, should reach the worker as an error, and the coordinator should report "not audited yet, will resume" separately from "audited, found problems".

> **如实告诉 Agent 正在等待。** 工作 Agent 看到的应该是「正在账户限流后排队，会自动重试」，而不是一个错误，这样它就不会放弃或去尝试变通办法。只有真正的失败（比如令牌过期）才应该以错误的形式到达工作 Agent；协调者也应该把「尚未审计、将会继续」与「已审计、发现问题」分开报告。

**Rethink the fan-out.** Thirty agents only help if the bottleneck is thinking, not API calls. When the API limit is the bottleneck, fewer workers, or a plain code loop that fetches data under the quota and hands it to agents for analysis, finishes sooner and costs fewer tokens. Plan the night's work from the quota: accounts times calls per account, divided by the allowed rate, tells you whether the audit fits before morning.

> **重新考虑扇出规模。** 只有当瓶颈在于思考而不在于 API 调用时，30 个 Agent 才有帮助。当 API 限额是瓶颈时，减少工作 Agent 的数量，或者用一段普通的代码循环在额度内抓取数据、再交给 Agent 分析，会更快完成，也更省 token。根据额度来规划当晚的工作量：账户数乘以每个账户的调用次数，再除以允许的速率，就能知道审计能否在早上之前完成。

**Trade-offs.** A shared gate is a component to run and monitor, and a single slow account can hold slots. Per-account fairness, timeouts per call, and a dashboard of queue time versus work time keep it honest.

> **权衡。** 共享关卡是一个需要运行和监控的组件，而且某个慢账户可能长期占用名额。按账户分配的公平性、每次调用的超时，以及一个对比排队时间与工作时间的看板，能让它保持正常运转。

</details>
