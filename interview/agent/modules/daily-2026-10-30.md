## 1. Merchants think the agent has frozen: three minutes of silence, then a wall of text

**商家以为 Agent 卡住了：三分钟毫无动静，然后突然冒出一大段文字** · `Agent Loop` · `Medium`

### Question · 题目

A catalog-repair agent runs for a few minutes per request, calling tools to read products, check ad-platform errors and propose fixes. The chat UI shows a spinner until the final answer. Merchants close the tab or click "retry", which starts a second run. Streaming is already on, but the screen still stays empty for most of the run.

> 一个商品目录修复 Agent 每次请求要运行几分钟，调用工具读取商品、检查广告平台报错并提出修复建议。聊天界面在最终答案出来之前一直显示转圈。商家要么关掉页面，要么点“重试”，结果又启动了第二次运行。流式输出已经开启，但在大部分运行时间里，屏幕仍然是空的。

Why is the screen empty, and how would you design progress for long agent turns?

> 为什么屏幕是空的？你会如何为长时间的 Agent 轮次设计进度展示？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Streaming only helps if there is something visible to stream. During a long turn, most of the work is thinking and tool calls, and on current models that reasoning is not shown by default. So you need to ask for visible progress explicitly, show your own tool activity, and make retries safe in case people still click.

> **核心思路。** 只有存在可见的内容时，流式输出才有帮助。在一个很长的轮次里，大部分工作都是思考和工具调用，而在当前的模型上，这部分推理默认是不展示的。所以你需要显式地请求可见的进度，展示你自己的工具活动，并且让重试是安全的，以防用户还是会去点。

**Why it is empty.** On newer models, thinking `display` defaults to `"omitted"`: thinking blocks stream with empty text, so a client that renders only text sees nothing until the answer. On Claude Opus 5.5, text the model writes between tool calls also comes back as progress-update thinking blocks, which are empty by default too.

> **为什么是空的。** 在较新的模型上，思考的 `display` 默认是 `"omitted"`：思考块会以空文本流式返回，所以只渲染文本的客户端在答案出来之前什么也看不到。在 Claude Opus 5.5 上，模型在工具调用之间写下的文字也会以“进度更新”类型的思考块返回，而它们默认同样是空的。

**Make progress visible.**

> **让进度可见。**

- Set `display: "updates"` (beta `thinking-display-updates-2026-08-18`) to receive the model's short between-tool-call progress notes while the reasoning itself stays hidden, or `"summarized"` to show a readable summary of the reasoning. Display changes visibility only; thinking is billed the same either way.
  > 设置 `display: "updates"`（beta `thinking-display-updates-2026-08-18`），在推理本身保持隐藏的同时，接收模型在工具调用之间写下的简短进度说明；或者设置 `"summarized"`，展示一份可读的推理摘要。display 只改变可见性；无论怎样设置，思考的计费都一样。
- Render your own progress from tool calls: "Reading 120 products", "Checking Google Merchant Center errors (3 of 5 accounts)". You know exactly which tool runs and can show it immediately.
  > 根据工具调用渲染你自己的进度：“正在读取 120 个商品”“正在检查 Google Merchant Center 报错（5 个账户中的第 3 个）”。你清楚地知道正在运行哪个工具，可以立即把它展示出来。
- Guide the updates in the prompt instead of scripting them: describe who reads them and what a useful update looks like, rather than rules like "summarize after every three tool calls", which newer models no longer need.
  > 在提示中引导进度说明，而不是把它写成固定脚本：描述谁会阅读它们、什么样的进度说明有用，而不是写“每三次工具调用后总结一次”这样的规则，较新的模型已经不需要这类规则了。

```go
adaptive := anthropic.ThinkingConfigAdaptiveParam{
	Display: anthropic.ThinkingConfigAdaptiveDisplaySummarized,
}
params.Thinking = anthropic.ThinkingConfigParamUnion{OfAdaptive: &adaptive}
```

**Make retries and leaving safe.** Run long tasks as background jobs with an ID, so closing the tab does not kill the work and reopening shows the same job. A retry click while a job is running attaches to it instead of starting a second one, and tool calls that change data use idempotency keys.

> **让重试和离开都变得安全。** 把长任务作为带 ID 的后台任务运行，这样关闭页面不会终止工作，重新打开时看到的仍是同一个任务。任务运行期间点击重试，应当接入正在运行的任务，而不是启动第二个；会修改数据的工具调用要使用幂等键。

**Measure it.** Track the time until the first visible update, the share of runs abandoned before completion, and how often a second run starts for the same request. These numbers tell you whether the progress design works far better than asking whether the spinner feels faster.

> **加以度量。** 跟踪出现第一条可见更新所需的时间、在完成前被放弃的运行所占比例，以及同一请求启动第二次运行的频率。这些数字比“转圈感觉是不是快了一点”更能告诉你进度设计是否有效。

**Trade-offs.** Summaries of reasoning can confuse non-technical merchants and occasionally reveal internal deliberation you would rather not show; progress notes and your own tool status are usually the better fit for a merchant UI. Too many updates are noise, so measure whether they reduce abandoned runs and duplicate retries.

> **取舍。** 推理摘要可能让不懂技术的商家感到困惑，偶尔还会暴露一些你不想展示的内部斟酌；对商家界面来说，进度说明加上你自己的工具状态通常更合适。更新太多就成了噪音，所以要衡量它们是否真的减少了被放弃的运行和重复的重试。

</details>

## 2. The agent's Excel reports have broken formulas: build a file-writing tool, or use Agent Skills?

**Agent 生成的 Excel 报表公式是坏的：自己做一个写文件工具，还是使用 Agent Skills？** · `Tools & MCP` · `Hard`

### Question · 题目

Merchants ask the reporting agent for a monthly ad performance workbook: a summary sheet with formulas, a sheet per platform and a chart. Today the agent calls your `write_file` tool with CSV text, and a backend job converts it to XLSX. Formulas arrive as text, charts are missing, and non-ASCII product names break in some spreadsheet apps.

> 商家让报表 Agent 生成月度广告效果工作簿：一个带公式的汇总表、每个平台一张表，再加一张图表。现在 Agent 用 CSV 文本调用你们的 `write_file` 工具，再由后端任务把它转换成 XLSX。结果公式变成了文本，图表缺失，非 ASCII 的商品名在某些表格软件里显示乱码。

How would you let the agent produce real Office files, and what are the trade-offs?

> 你会如何让 Agent 生成真正的 Office 文件？其中有哪些取舍？

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Writing a correct XLSX is a programming task, not a text task. Instead of asking the model to emit a file format through a narrow tool, let it write and run code in a sandbox with a library that knows the format, guided by instructions for how to do it well. That is what Agent Skills plus code execution provide.

> **核心思路。** 写出一个正确的 XLSX 是一项编程任务，而不是文本任务。与其让模型通过一个功能狭窄的工具输出某种文件格式，不如让它在沙箱中借助一个了解该格式的库来编写并运行代码，并由一套“怎样做好”的说明来指导它。这正是 Agent Skills 加上代码执行所提供的能力。

**How it works on the Messages API.** A skill packages task-specific instructions and files that Claude loads when relevant; Anthropic provides pre-built skills such as `xlsx`, `pptx`, `docx` and `pdf`. You enable them with the `container` parameter together with the code execution tool and the `code-execution-2025-08-25` beta. Files the model creates are written in the container, the response carries a file ID for each, and you download them through the Files API.

> **它在 Messages API 上如何工作。** 一个 skill 打包了特定任务的说明和文件，Claude 会在相关时加载它们；Anthropic 提供了 `xlsx`、`pptx`、`docx`、`pdf` 等预置的 skill。你通过 `container` 参数，配合代码执行工具和 `code-execution-2025-08-25` beta 来启用它们。模型创建的文件写在容器中，响应会为每个文件附带一个文件 ID，你通过 Files API 下载它们。

```json
{
  "model": "claude-opus-5-5",
  "max_tokens": 16000,
  "container": {"skills": [{"type": "anthropic", "skill_id": "xlsx", "version": "latest"}]},
  "tools": [{"type": "code_execution_20260521", "name": "code_execution"}],
  "messages": [{"role": "user", "content": "Build the October ad report workbook from the attached data."}]
}
```

- **Get data in safely.** Pass the merchant's data as an uploaded file or a structured tool result, so the code reads exact numbers instead of numbers retyped by the model.
  > **安全地导入数据。** 把商家的数据作为上传的文件或结构化的工具结果传进去，这样代码读取的是精确的数字，而不是由模型重新打出来的数字。
- **Custom skills for house style.** If reports must follow your template (sheet names, colours, chart types, number formats), package that as your own skill: a folder with instructions and assets. Only the skill's short description sits in context until the model decides it needs the full instructions.
  > **用自定义 skill 固化公司风格。** 如果报表必须遵循你们的模板（表名、配色、图表类型、数字格式），就把这些打包成你们自己的 skill：一个包含说明和素材的文件夹。在模型判断需要完整说明之前，上下文中只放 skill 的简短描述。
- **Verify the artifact.** After download, open the workbook with a library in your backend and check that formulas exist where expected, totals match your source data, and every platform sheet is present before sending it to the merchant.
  > **校验产出物。** 下载之后，在后端用一个库打开工作簿，检查公式是否出现在预期位置、合计是否与源数据一致、每个平台的表是否都存在，然后再发给商家。

**When a plain tool is better.** For a fixed report layout, a deterministic report service that takes structured data from the agent and renders the workbook in your code is cheaper, faster and fully testable. Skills shine when layouts vary per request, when merchants ask for ad-hoc analysis, or when the file needs judgement such as choosing which chart explains a trend.

> **什么时候普通工具更好。** 对于版式固定的报表，一个确定性的报表服务（接收 Agent 提供的结构化数据，由你们的代码渲染工作簿）更便宜、更快，也完全可以测试。当每次请求的版式都不同、商家提出临时性的分析需求，或者文件需要一些判断（比如选择哪种图表最能说明趋势）时，skill 才真正发挥作用。

**Trade-offs.** Code execution adds latency and container cost, and generated code can still be wrong, which is why you verify the output. Files created in the container live with the provider until you download and delete them, so include them in your data retention rules. Keep the skill set small per request; every enabled skill is something the model may load.

> **取舍。** 代码执行会增加延迟和容器成本，生成的代码也仍然可能出错，这就是为什么要校验输出。在容器中创建的文件会一直保存在服务商那里，直到你下载并删除它们，所以要把它们纳入你们的数据保留规则。每个请求启用的 skill 要尽量少；每个被启用的 skill 都可能被模型加载。

</details>

## 3. "Stop, that's the wrong store!" The lead agent stops, but its workers keep editing

**“停下，店铺选错了！”主 Agent 停了，可它的工作者还在继续改** · `Multi-agent` · `Hard`

### Question · 题目

A merchant starts a bulk catalog cleanup in a managed multi-agent session: a lead agent plans the work and a workflow run fans it out to worker threads. Two minutes in, the merchant realizes the wrong store is selected and clicks "Stop". Your client sends an interrupt, the lead goes idle, but product edits keep appearing for a while, and the next message from your client fails with a 400.

> 一位商家在一个托管的多 Agent 会话中启动了批量商品目录清理：主 Agent 规划工作，再由一次工作流运行把任务分发给多个工作者线程。两分钟后，商家发现选错了店铺，点击了“停止”。你们的客户端发送了一个中断，主 Agent 进入了 idle，但商品修改还在陆续出现一段时间，而且客户端发出的下一条消息以 400 失败。

Explain what happened and design a reliable stop.

> 解释发生了什么，并设计一种可靠的停止方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** In a multi-agent system, "stop" is not one switch. Interrupting the coordinator stops its turn, but work it already handed out can keep running, and pending tool calls still wait for answers. A reliable stop has to reach every running piece, settle what is waiting, and make the side effects that already happened visible and reversible.

> **核心思路。** 在多 Agent 系统中，“停止”不是一个开关。中断协调者会停止它当前的轮次，但它已经分发出去的工作可能仍在运行，而待处理的工具调用仍在等待答复。可靠的停止必须触达每一个正在运行的部分，处理好正在等待的内容，并让已经发生的副作用可见、可撤销。

**What happened.** On Anthropic's Managed Agents, `user.interrupt` stops the agent's turn at a safe boundary, then the session goes idle. An interrupt without a thread ID stops the primary thread's turn, but it ends no workflow run; the run's threads may pause or keep going, and you cannot interrupt a run's thread by its ID. To stop a run, ask the agent to stop it. Meanwhile, a run thread's tool call may still be waiting on your client, and while the session is idle with `requires_action`, a `user.message` returns 400; that is the error you saw.

> **发生了什么。** 在 Anthropic 的 Managed Agents 上，`user.interrupt` 会在一个安全的边界上停止 Agent 的轮次，然后会话进入 idle。不带线程 ID 的中断会停止主线程的轮次，但不会结束任何工作流运行；运行中的线程可能暂停，也可能继续，而且你无法按 ID 中断某次运行中的线程。要停止一次运行，需要让 Agent 去停止它。与此同时，某个运行线程的工具调用可能仍在等待你的客户端；当会话处于带 `requires_action` 的 idle 状态时，`user.message` 会返回 400，这就是你看到的错误。

**A reliable stop sequence.**

> **一套可靠的停止流程。**

- Send the interrupt, then answer every waiting tool call: deny calls that ask for confirmation, and send custom tool results with `is_error` set to true and a short reason ("operation cancelled by merchant").
  > 发送中断，然后答复每一个正在等待的工具调用：拒绝那些需要确认的调用；对自定义工具调用，发送 `is_error` 设为 true 的结果，并附上简短原因（“操作已被商家取消”）。
- Once nothing is waiting, tell the agent to stop its open workflow runs, and watch the run events until each one has ended.
  > 等到没有任何调用在等待时，告诉 Agent 停止它尚未结束的工作流运行，并观察运行事件，直到每一个都已结束。
- Enforce the stop in your own tools too: set a cancelled flag on the job, and make every write tool check it and refuse. This is the part you fully control and it takes effect immediately.
  > 在你们自己的工具中也强制执行停止：给任务设置一个“已取消”标记，让每个写操作工具都检查它并拒绝执行。这是你们完全可控的部分，而且会立即生效。

**Know when it has really stopped.** Events you send appear on the stream with `processed_at` empty while they are queued and filled once processed, so confirm the interrupt was processed rather than assuming it. There is no endpoint that lists runs: after a reconnect, list the session's events filtered to the run created and ended types to find runs still open, and only then report "stopped" to the merchant.

> **确认它真的已经停下了。** 你发送的事件会出现在事件流中，排队时 `processed_at` 为空，处理完成后才会被填上，所以要确认中断已被处理，而不是想当然。没有接口可以列出所有运行：重连之后，按“运行已创建”和“运行已结束”这两类事件筛选会话的事件，找出仍未结束的运行，然后再向商家报告“已停止”。

**Make partial work reversible.** Record every change with the job ID and the previous value, so you can show the merchant exactly what was changed before the stop and offer a one-click revert. Use idempotency keys so a resumed or repeated run does not apply changes twice.

> **让已完成的部分工作可撤销。** 记录每一处修改及其所属的任务 ID 和修改前的值，这样你可以准确地向商家展示停止之前改了什么，并提供一键撤销。使用幂等键，这样恢复或重复的运行不会把修改应用两次。

**Trade-offs.** A tool-level kill switch stops writes instantly but leaves agents running until they notice the errors, which costs some tokens; the agent-level stop is cleaner but slower. Use both. For destructive bulk jobs, confirm the target store and a dry-run summary before fan-out, which prevents most of these incidents in the first place.

> **取舍。** 工具层面的“急停开关”能立刻阻止写入，但 Agent 会一直运行到它们注意到这些错误为止，会多花一些 token；Agent 层面的停止更干净，但更慢。两者都要用。对于破坏性的批量任务，要在分发之前先确认目标店铺并给出一份试运行摘要，这样从一开始就能避免大部分此类事故。

</details>

## 4. A US merchant requires US-only processing, and an EU merchant asks for EU-only: what can you promise?

**一家美国商家要求只在美国处理数据，一家欧盟商家要求只在欧盟处理：你能承诺什么？** · `Safety & Security` · `Senior`

### Question · 题目

Your agent platform serves merchants worldwide. A large US merchant's contract now requires that model inference on their data happen only in the United States. Soon after, an EU merchant asks for the same guarantee within the EU. Sales wants a yes to both by next week.

> 你们的 Agent 平台服务全球的商家。一家大型美国商家的合同现在要求，对其数据的模型推理只能在美国进行。不久之后，一家欧盟商家也要求在欧盟境内获得同样的保证。销售希望下周之前对两者都给出肯定的答复。

Design how you meet these requirements and what you must not promise.

> 设计你如何满足这些要求，以及哪些是你绝不能承诺的。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Separate where data is stored from where inference runs, and promise only what each layer can enforce. Then make the guarantee a property of the tenant's configuration that the system checks on every request, not a setting someone remembers.

> **核心思路。** 把数据存放在哪里和推理在哪里运行区分开，并且只承诺每一层能够强制执行的内容。然后把这项保证变成租户配置的一个属性，由系统在每次请求时检查，而不是一个靠人记住的设置。

**US-only on the Claude API.** The `inference_geo` parameter pins where a request's inference runs; it accepts `"us"` or `"global"`, and the response's usage reports where inference ran. US-only inference is priced with a multiplier over the standard rate, so the merchant's contract should account for it. On Managed Agents, `inference_geo` sits inside the agent's `model` object, is validated against the workspace's `allowed_inference_geos` on every turn, is fixed for a session's lifetime, and must be the same for every agent in a multi-agent roster.

> **在 Claude API 上做到仅限美国。** `inference_geo` 参数可以固定一个请求的推理运行位置；它接受 `"us"` 或 `"global"`，响应中的 usage 会报告推理实际在哪里运行。仅限美国的推理在标准价格之上有一个加价系数，所以商家的合同中应该把它考虑进去。在 Managed Agents 上，`inference_geo` 位于 Agent 的 `model` 对象内部，每一轮都会对照工作区的 `allowed_inference_geos` 进行校验，在会话生命周期内固定不变，并且多 Agent 阵容中的每个 Agent 都必须一致。

- **Enforce by workspace.** Put US-only tenants in a workspace whose allowlist permits only `us`. If the allowlist later narrows, new sessions cannot be created and running sessions refuse further turns; pins are never grandfathered, which is exactly the behaviour a compliance promise needs.
  > **按工作区强制执行。** 把仅限美国的租户放进一个允许列表只包含 `us` 的工作区。如果之后允许列表收窄，就无法再创建新会话，正在运行的会话也会拒绝后续轮次；固定设置从不享受“老规则豁免”，而这正是一项合规承诺所需要的行为。
- **Route per tenant in your code.** Your gateway looks up the tenant's residency policy and picks the client, workspace and parameters; requests without a resolved policy are rejected, not sent with defaults.
  > **在你们的代码中按租户路由。** 你们的网关查找租户的数据驻留策略，并据此选择客户端、工作区和参数；无法确定策略的请求会被拒绝，而不是带着默认值发出去。
- **Log the evidence.** Record the inference location reported in each response per tenant, so you can show auditors that the guarantee held.
  > **记录证据。** 按租户记录每个响应中报告的推理位置，这样你就能向审计人员证明这项保证一直得到了遵守。

**EU-only is a different answer.** `inference_geo` offers `us` and `global`, not an EU option, so you cannot promise EU-only inference on that path. Options are a cloud provider's regional deployment (for example a Vertex AI EU multi-region endpoint, checked against that platform's feature availability), or keeping EU personal data out of model requests through minimization. Confirm current options with the provider before signing anything.

> **仅限欧盟则是另一回事。** `inference_geo` 提供的是 `us` 和 `global`，没有欧盟选项，所以在这条路径上你无法承诺仅在欧盟推理。可选方案是使用云服务商的区域部署（例如 Vertex AI 的欧盟多区域端点，并对照该平台的功能可用性进行核实），或者通过数据最小化让欧盟的个人数据不进入模型请求。在签署任何合同之前，先与服务商确认当前可用的选项。

**What not to promise.** Inference location does not cover everything: your own storage, logs, traces, backups, third-party tools the agent calls, and web tools that run on provider servers all need their own answers. Features differ by platform, so a regional deployment may lack some features. Write the guarantee precisely ("model inference for your requests runs in the US"), get legal review, and test it with an automated check per tenant.

> **不能承诺什么。** 推理位置并不能覆盖一切：你们自己的存储、日志、链路追踪、备份、Agent 调用的第三方工具，以及在服务商服务器上运行的网页工具，都需要各自的答案。不同平台的功能各不相同，所以区域部署可能缺少某些功能。要精确地写出这项保证（“对你们请求的模型推理在美国运行”），经过法务审核，并为每个租户配置自动化检查来验证它。

**Trade-offs.** Pinning costs more and narrows the features and capacity you can use; separate workspaces per residency class add operational work. But a vague promise that fails an audit costs far more than either.

> **取舍。** 固定推理位置成本更高，也会缩小你能使用的功能和容量范围；按驻留等级划分不同的工作区会增加运维工作。但一个含糊、在审计中站不住脚的承诺，代价要比这两者高得多。

</details>

## 5. The policy assistant must return JSON with citations, and the API rejects the request

**政策助手必须返回带引用的 JSON，而 API 拒绝了这个请求** · `RAG` · `Medium`

### Question · 题目

The ad-policy assistant answers merchants' questions from policy documents. The frontend wants a JSON object with `answer`, `verdict` and a list of citations, so the team enabled citations on the documents and set `output_config.format` to a JSON schema. Every request now fails with a 400.

> 广告政策助手根据政策文档回答商家的问题。前端需要一个包含 `answer`、`verdict` 和引用列表的 JSON 对象，所以团队在文档上开启了引用功能，同时把 `output_config.format` 设成了一个 JSON schema。现在每个请求都以 400 失败。

Explain the conflict and design a response format that gives the frontend structure and verifiable sources.

> 解释其中的冲突，并设计一种既能给前端结构化数据、又能提供可验证来源的响应格式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Citations and structured outputs constrain the response in different ways: citations split the answer into text blocks with source locations attached, while structured outputs force the response into a JSON schema. The API does not allow both at once, so choose one mechanism for the answer and get the other property by other means.

> **核心思路。** 引用功能和结构化输出以不同的方式约束响应：引用会把答案拆分成附带来源位置的文本块，而结构化输出会强制响应符合某个 JSON schema。API 不允许同时使用两者，所以要为答案选定一种机制，再通过其他方式获得另一种特性。

**Option 1: keep citations, build the JSON yourself.** With `citations: {enabled: true}` on each document, the response is a list of text blocks, and cited blocks carry a `citations` array with the cited text, the document index and title, and a location (characters for plain text, pages for PDFs). Your backend assembles the JSON: concatenate the text into `answer`, map citations to your document IDs and page numbers, and derive `verdict` with a small, separate classification call if needed. The sources come from the API, so they point to real text.

> **方案一：保留引用，自己组装 JSON。** 在每个文档上设置 `citations: {enabled: true}` 后，响应是一组文本块，带引用的块会附带一个 `citations` 数组，其中包含被引用的文本、文档序号和标题，以及位置（纯文本是字符位置，PDF 是页码）。由你们的后端来组装 JSON：把文本拼接成 `answer`，把引用映射到你们的文档 ID 和页码；如果需要，再用一次单独的小型分类调用得出 `verdict`。来源是由 API 给出的，所以它们指向的是真实存在的文本。

**Option 2: structured output, verified quotes.** Keep `output_config.format` and ask for a schema with `claims`, each holding a document ID and an exact quote. The model now writes the quotes itself, so verify them in code before showing them; checks that call no model are cheap and reliable:

> **方案二：结构化输出，加上引文校验。** 保留 `output_config.format`，要求一个包含 `claims` 的 schema，每条声明都带有文档 ID 和一段精确的引文。此时引文是模型自己写出来的，所以在展示之前要在代码中校验它们；不调用模型的检查既便宜又可靠：

```go
// unsupported returns the claims whose quote does not appear verbatim in the cited document.
func unsupported(claims []Claim, docs map[string]string) []Claim {
	var bad []Claim
	for _, c := range claims {
		doc, ok := docs[c.DocID]
		if !ok || c.Quote == "" || !strings.Contains(normalize(doc), normalize(c.Quote)) {
			bad = append(bad, c)
		}
	}
	return bad
}

func normalize(s string) string {
	return strings.Join(strings.Fields(strings.ToLower(s)), " ")
}
```

- If a quote fails, drop that claim, or send the answer back to the same conversation once with the list of unsupported quotes; do not show an unverified source to a merchant.
  > 如果某段引文校验失败，就删除这条声明，或者把答案连同不被支持的引文列表发回同一段对话一次；绝不要把未经验证的来源展示给商家。
- Return the policy version and effective date with each source, so merchants and support staff can see which version the answer relied on.
  > 为每个来源附上政策的版本和生效日期，这样商家和客服人员都能看到答案依据的是哪个版本。

**Trade-offs.** Option 1 gives the strongest grounding with no extra validation code, but the JSON assembly lives in your backend and fields such as `verdict` need another step. Option 2 gives the frontend exactly the schema it wants in one call, at the cost of verifying quotes and occasionally dropping claims. For compliance-sensitive answers, prefer API citations; for UI convenience on low-risk answers, structured output with verification is fine.

> **取舍。** 方案一的依据最可靠，不需要额外的校验代码，但 JSON 的组装要放在你们的后端，`verdict` 这类字段也需要额外一步。方案二一次调用就能给前端它想要的 schema，代价是要校验引文，偶尔还要删掉一些声明。对于合规敏感的答案，优先使用 API 自带的引用；对于低风险答案，为了界面方便，使用结构化输出加校验就可以了。

</details>
