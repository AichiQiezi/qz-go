## 1. An API client that slowly runs out of ports

**一个慢慢耗尽端口的 API 客户端** · `Go` · `Medium`

### Question · 题目

A Go service calls an ad platform's reporting API about 300 times per second with code like this:

> 一个 Go 服务以每秒约 300 次的频率调用某广告平台的报表 API，代码大致如下：

```go
func fetchReport(ctx context.Context, url string) (int, error) {
    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return 0, err
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return resp.StatusCode, nil // the caller retries later
    }
    var r Report
    if err := json.NewDecoder(resp.Body).Decode(&r); err != nil {
        return 0, err
    }
    return http.StatusOK, nil
}
```

Under load, latency creeps up, `ss` shows tens of thousands of sockets in `TIME_WAIT`, and calls start failing with `dial tcp ...: connect: cannot assign requested address`. Some goroutines also hang for minutes whenever the platform stalls. Explain the causes and fix them.

> 在压力下，延迟逐渐上升，`ss` 显示有数万个处于 `TIME_WAIT` 状态的 socket，调用开始失败，报错 `dial tcp ...: connect: cannot assign requested address`。每当平台卡住时，还有一些 goroutine 会挂起好几分钟。请解释原因并修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Cause 1: response bodies are closed before they are fully read.** Go's `Transport` returns a keep-alive connection to its pool only when the body has been read to EOF and closed. This code misses EOF on both paths:

> **原因 1：响应体在被完整读取之前就关闭了。** 只有当响应体被读到 EOF 并关闭后，Go 的 `Transport` 才会把这个 keep-alive 连接放回连接池。这段代码在两条路径上都没有读到 EOF：

- On a non-200 response it returns without reading the body at all. Error responses usually have a body, so every 429 or 500 throws its connection away.
  > 遇到非 200 响应时，它根本没读响应体就返回了。错误响应通常都带有响应体，所以每个 429 或 500 都会让连接被丢弃。
- On a 200, `json.Decoder` stops after the first JSON value. Servers usually end the body with a newline (`json.Encoder` adds one), so the decoder never reaches EOF either.
  > 遇到 200 时，`json.Decoder` 在解析完第一个 JSON 值后就停下了。服务端通常会在响应体末尾加一个换行符（`json.Encoder` 就会加），所以解码器同样读不到 EOF。

So every call opens a new TCP and TLS connection. Each closed connection then sits in `TIME_WAIT` for about a minute on the side that closed it, the client here. At 300 calls per second the client runs out of ephemeral ports, and `connect` fails with `cannot assign requested address`. The extra handshakes are also where the latency comes from. In a quick test, 100 requests decoded with `json.Decoder` alone opened 100 connections; adding a drain reused one connection for all of them.

> 于是每次调用都会新建一个 TCP 和 TLS 连接。每个被关闭的连接还会在主动关闭的一方（这里是客户端）停留在 `TIME_WAIT` 状态大约一分钟。在每秒 300 次调用的情况下，客户端会耗尽临时端口，`connect` 就会以 `cannot assign requested address` 失败。额外的握手也正是延迟上升的原因。在一次简单测试中，只用 `json.Decoder` 解码的 100 个请求打开了 100 个连接；加上读空之后，所有请求复用了同一个连接。

**Fix: always drain the body, with a cap.**

> **修复：总是读空响应体，并设置上限。**

```go
defer func() {
    io.Copy(io.Discard, io.LimitReader(resp.Body, 64<<10))
    resp.Body.Close()
}()
```

The cap avoids reading a huge body just to save a connection; past it, closing the connection is the cheaper choice.

> 设置上限是为了避免为了省一个连接而读取一个巨大的响应体；超过上限时，直接关闭连接反而更划算。

**Cause 2: the idle pool is too small.** `http.DefaultTransport` keeps at most 2 idle connections per host (`DefaultMaxIdleConnsPerHost`). With dozens of concurrent calls to one host, most connections are closed after each use even when bodies are drained. Create one shared client with its own transport:

> **原因 2：空闲连接池太小。** `http.DefaultTransport` 对每个 host 最多保留 2 个空闲连接（`DefaultMaxIdleConnsPerHost`）。当有几十个并发调用打到同一个 host 时，即使响应体都读空了，大多数连接在用完后仍会被关闭。创建一个共享的 client，并为它配置自己的 transport：

```go
t := http.DefaultTransport.(*http.Transport).Clone()
t.MaxIdleConnsPerHost = 64 // about your steady concurrency to this host
t.MaxConnsPerHost = 128    // a hard cap that protects you and the platform
var apiClient = &http.Client{Transport: t, Timeout: 10 * time.Second}
```

`Clone` keeps the default proxy, dial and TLS handshake timeouts. Create the client once and reuse it: a new client or transport per request has no pool at all.

> `Clone` 会保留默认的代理设置、拨号超时和 TLS 握手超时。client 只创建一次并重复使用：每个请求都新建 client 或 transport，就等于完全没有连接池。

**Cause 3: no timeout.** `http.DefaultClient` has `Timeout: 0`, which means no limit, and the caller's context may have no deadline. When the platform accepts the connection but stops responding, goroutines wait forever. Set `Client.Timeout` as a ceiling, and give each call a context deadline that fits its caller.

> **原因 3：没有超时。** `http.DefaultClient` 的 `Timeout` 为 0，表示不设上限，而调用方的 context 也可能没有截止时间。当平台接受了连接却不再响应时，goroutine 会一直等下去。设置 `Client.Timeout` 作为兜底上限，并为每次调用设置符合调用方需求的 context 截止时间。

**Verifying the fix.** `httptrace.ClientTrace` reports `Reused` in its `GotConn` callback for every request; the reuse rate should be close to 100%. Watch the `TIME_WAIT` count with `ss -s`.

> **验证修复效果。** `httptrace.ClientTrace` 会在每个请求的 `GotConn` 回调中报告 `Reused`；复用率应该接近 100%。用 `ss -s` 观察 `TIME_WAIT` 的数量。

</details>

## 2. Importing a 2 GB product CSV without timeouts or half-done imports

**导入 2 GB 的商品 CSV，不超时，也不留下半成品** · `System Design` · `Medium`

### Question · 题目

Merchants import products by uploading a CSV file of up to 2 GB, several million rows. Today the browser posts the file to an API server, which parses it inside the request handler and inserts each row into the database. Large imports hit the load balancer's 60-second timeout, API pods run out of memory, a failed import leaves some products updated with no way to tell which, and merchants who re-upload the same file end up with duplicate products. Redesign the import flow.

> 商家通过上传 CSV 文件来导入商品，文件最大 2 GB，包含数百万行。目前浏览器把文件直接 POST 到 API 服务器，服务器在请求处理函数里解析文件，并把每一行插入数据库。大文件导入会撞上负载均衡器 60 秒的超时，API pod 会内存溢出；导入失败后，一部分商品被更新了，却无从知道是哪些；商家重新上传同一个文件后，还会出现重复商品。请重新设计导入流程。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Upload straight to object storage.** The API only issues a presigned upload URL. For large files, use a multipart upload: parts are at least 5 MiB (except the last), there can be up to 10,000 of them, and each one can be retried on its own. The browser sends the file directly to storage, so app servers never hold it and the 60-second limit no longer applies. When the upload finishes, the client calls `POST /imports` with the object key; the API creates an `import_jobs` row with status `pending` and returns its id at once.

> **直接上传到对象存储。** API 只负责签发一个预签名上传 URL。大文件使用分片上传：每个分片至少 5 MiB（最后一个除外），最多 10,000 个分片，每个分片都可以单独重试。浏览器把文件直接传到存储，应用服务器根本不经手文件，60 秒的限制也就不再适用。上传完成后，客户端带上对象 key 调用 `POST /imports`；API 创建一条状态为 `pending` 的 `import_jobs` 记录，并立即返回它的 id。

**Process asynchronously, as a stream.** A worker picks up the job and streams the file row by row, never loading it into memory. It validates each row (required fields, price format, image URLs, SKUs repeated within the file) and writes rejected rows, with the reason, to an error report the merchant can download.

> **异步处理，流式读取。** worker 领取任务后逐行流式读取文件，从不把整个文件加载进内存。它校验每一行（必填字段、价格格式、图片 URL、文件内重复的 SKU），并把被拒绝的行连同原因写入一份错误报告，供商家下载。

**Make every write idempotent.** Upsert by `(merchant_id, sku)` instead of inserting. Process rows in chunks of, say, 1,000, and record a checkpoint (`last_row`) on the job in the same transaction as each chunk's writes. A crashed worker resumes from the checkpoint, and replaying a chunk changes nothing.

> **让每次写入都具备幂等性。** 按 `(merchant_id, sku)` 做 upsert，而不是直接插入。按块处理数据，比如每块 1,000 行，并在写入每个块的同一个事务里，在任务上记录检查点（`last_row`）。worker 崩溃后可以从检查点继续，重放某个块也不会改变任何结果。

**Decide what a partial import means.** There are two honest options:

> **想清楚“部分导入”意味着什么。** 有两种坦诚的选择：

- Partial success with a report: apply the valid rows and report the invalid ones. Simple, and usually what merchants want.
  > 部分成功并附带报告：应用有效的行，报告无效的行。简单，通常也是商家想要的。
- All or nothing: load into a staging table keyed by job id, validate everything, then apply it in one switch-over step. Safer for price lists, but slower and it needs more storage.
  > 要么全部成功，要么全部不生效：先加载到按任务 id 区分的暂存表中，全部校验通过后，再一步切换生效。对价目表来说更安全，但更慢，也需要更多存储。

Either way, the job shows counts (processed, created, updated, failed), so nothing is ambiguous.

> 无论哪种方式，任务都会显示各项计数（已处理、新建、更新、失败），这样就不会有任何含糊不清的地方。

**Re-uploads.** Store a hash of each file and warn when the same file was imported recently, and allow only one running import per merchant and catalog.

> **重复上传。** 保存每个文件的哈希值，如果同一个文件最近已经导入过就给出提醒；并且每个商家的每个商品目录同时只允许运行一个导入任务。

**Progress and fairness.** The UI polls the job for progress. Jobs go through a queue with a per-merchant concurrency limit, so one merchant's 5-million-row import cannot starve everyone else, and the downstream syncs an import triggers (for example to ad platforms) are rate-limited too.

> **进度与公平性。** 界面轮询任务的进度。任务经过一个带有按商家并发限制的队列，这样某个商家 500 万行的导入不会饿死其他所有人；导入触发的下游同步（例如同步到广告平台）也要限流。

</details>

## 3. Fast in staging, full table scans in production

**预发环境很快，生产环境却在全表扫描** · `Database` · `Hard`

### Question · 题目

An endpoint runs three MySQL 8.0 queries. All of them are fast in staging, but in production, where the tables are 100 times larger, each one takes seconds:

> 某个接口会执行三条 MySQL 8.0 查询。它们在预发环境都很快，但在表大了 100 倍的生产环境中，每一条都要好几秒：

```sql
-- 1. customers.phone is VARCHAR(20) with an index
SELECT * FROM customers WHERE phone = 13800138000;

-- 2. there is an index on orders(created_at)
SELECT COUNT(*) FROM orders WHERE DATE(created_at) = '2026-10-12';

-- 3. about 0.1% of orders are 'failed'; there is an index on (status, created_at)
SELECT * FROM orders WHERE status = 'failed' ORDER BY id DESC LIMIT 20;
```

Explain why each query cannot use its index efficiently, how you would prove it, and how to fix each one.

> 请解释为什么每条查询都无法高效地使用索引，你会如何证明这一点，以及分别如何修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Query 1: implicit type conversion.** `phone` is a string column, but the literal is a number. When MySQL compares a string column with a number, it converts both sides to floating point, row by row. The index is sorted as strings, so it cannot be used to look up a number, and MySQL scans the table. It can also return wrong rows: `'013800138000'` and `' 13800138000'` convert to the same number, and for strings longer than about 15 digits, double precision makes different values compare equal. Fix: compare with a string (`phone = '13800138000'`), and make sure the driver or ORM binds the parameter as a string. PostgreSQL rejects this comparison outright with `operator does not exist`, which is why this is mostly a MySQL bug.

> **查询 1：隐式类型转换。** `phone` 是字符串列，但字面量是数字。MySQL 在比较字符串列和数字时，会逐行把两边都转换成浮点数。索引是按字符串排序的，无法用来查找一个数字，于是 MySQL 只能扫描全表。它还可能返回错误的行：`'013800138000'` 和 `' 13800138000'` 会转换成同一个数字；而对于超过约 15 位的字符串，双精度浮点数会让不同的值比较结果相等。修复方法：用字符串来比较（`phone = '13800138000'`），并确保驱动或 ORM 把参数绑定为字符串。PostgreSQL 会直接以 `operator does not exist` 拒绝这种比较，所以这主要是 MySQL 上的 bug。

**Query 2: a function on the indexed column.** The index stores `created_at` values, not `DATE(created_at)`, so MySQL has to evaluate the function on every row. Fix: rewrite it as a range on the raw column, `created_at >= '2026-10-12' AND created_at < '2026-10-13'`, which uses the index directly. If you really need the expression, MySQL 8.0.13+ supports functional indexes such as `INDEX ((DATE(created_at)))`. Joins between columns with different character sets, such as a utf8mb3 column joined to a utf8mb4 one, can hit the same wall when the conversion lands on the indexed column.

> **查询 2：在索引列上使用了函数。** 索引存的是 `created_at` 的值，而不是 `DATE(created_at)`，所以 MySQL 必须对每一行计算这个函数。修复方法：改写成对原始列的范围条件 `created_at >= '2026-10-12' AND created_at < '2026-10-13'`，这样就能直接使用索引。如果确实需要这个表达式，MySQL 8.0.13+ 支持函数索引，例如 `INDEX ((DATE(created_at)))`。字符集不同的列做关联时，比如 utf8mb3 列关联 utf8mb4 列，如果转换落在带索引的那一列上，也会撞上同样的问题。

**Query 3: the ORDER BY ... LIMIT trap.** Two plans compete. Using `(status, created_at)` finds every failed order (about 100,000 at this size) and then sorts them by `id`. Scanning the primary key backwards returns rows already in `id` order and can stop after 20 matches. With a small `LIMIT`, MySQL often prefers the backward scan, because it assumes failed orders are spread evenly and expects to read only about 20,000 rows. If most failures are old, for example from an incident last year, it actually reads millions of rows before finding 20. Fix: an index on `(status, id)` serves both the filter and the order, and the query reads exactly 20 entries. In InnoDB every secondary index ends with the primary key, so an index on `(status)` alone would also work, but `(status, created_at)` puts `created_at` before `id`. MySQL 8.0.21+ can also turn off the preference for ordering indexes through the `prefer_ordering_index` optimizer switch, but fixing the index beats steering the optimizer.

> **查询 3：ORDER BY ... LIMIT 陷阱。** 有两个执行计划在竞争。使用 `(status, created_at)` 会找出所有失败的订单（在这个数据量下约 10 万条），再按 `id` 排序。反向扫描主键则直接按 `id` 顺序返回行，找到 20 条匹配就可以停下。在 `LIMIT` 很小时，MySQL 往往会选择反向扫描，因为它假设失败订单是均匀分布的，预计只需读取约 2 万行。如果大部分失败订单都很旧，比如来自去年的一次故障，它实际要读几百万行才能找到 20 条。修复方法：在 `(status, id)` 上建索引，同时满足过滤和排序，查询只需读取恰好 20 个条目。在 InnoDB 中，每个二级索引的末尾都带着主键，所以只在 `(status)` 上建索引也能奏效，但 `(status, created_at)` 把 `created_at` 放在了 `id` 前面。MySQL 8.0.21+ 还可以通过 `prefer_ordering_index` 优化器开关关闭对排序索引的偏好，但修好索引胜过去操控优化器。

**Proving it.**

> **如何证明。**

- `EXPLAIN` shows `type: ALL` or an unexpected `key`, with a huge `rows` estimate. For query 1, `possible_keys` lists the phone index but `key` is NULL, and `SHOW WARNINGS` right after `EXPLAIN` may say the index cannot be used because of a type or collation conversion.
  > `EXPLAIN` 会显示 `type: ALL` 或者一个意料之外的 `key`，`rows` 的估计值很大。对于查询 1，`possible_keys` 里列出了 phone 索引，但 `key` 为 NULL；在 `EXPLAIN` 之后紧接着执行 `SHOW WARNINGS`，可能会提示由于类型或排序规则转换而无法使用索引。
- `EXPLAIN ANALYZE` (MySQL 8.0.18+) runs the query and shows the rows actually read at each step. That exposes query 3: millions of rows read to return 20.
  > `EXPLAIN ANALYZE`（MySQL 8.0.18+）会真正执行查询，并显示每一步实际读取的行数。这能暴露查询 3 的问题：为了返回 20 行读了几百万行。
- In the slow query log, comparing `Rows_examined` with the rows returned finds these queries in production before users complain.
  > 在慢查询日志中，对比 `Rows_examined` 和返回的行数，就能在用户投诉之前于生产环境发现这类查询。

**The real lesson.** A plan depends on data size and distribution. Staging needs production-like volume and skew, or you need to check plans against production statistics before a release.

> **真正的教训。** 执行计划取决于数据量和数据分布。预发环境需要具备与生产相近的数据量和倾斜度，否则就要在发布前用生产环境的统计信息来检查执行计划。

</details>

## 4. Lost and looping messages in a RabbitMQ pipeline

**RabbitMQ 链路中丢失和死循环的消息** · `Middleware` · `Hard`

### Question · 题目

An order service publishes `order.paid` events to RabbitMQ, and a consumer forwards each one to an ad platform's conversion API. For speed, the consumer was written with `autoAck=true` and no prefetch limit. Three problems show up:

> 订单服务把 `order.paid` 事件发布到 RabbitMQ，一个消费者把每条事件转发给广告平台的转化 API。为了追求速度，消费者使用了 `autoAck=true`，并且没有设置预取上限。出现了三个问题：

- After every deploy, a few hundred conversions are missing.
  > 每次发布后，都会有几百条转化丢失。
- A malformed event (a null currency) makes the handler throw. Someone switched to manual acks with `basicNack(tag, false, true)` on any exception. Now the consumer burns CPU, the same message is redelivered thousands of times per second, and the queue backs up behind it.
  > 一条格式错误的事件（currency 为 null）导致处理函数抛出异常。有人改成了手动确认，并在任何异常时调用 `basicNack(tag, false, true)`。现在消费者 CPU 飙高，同一条消息每秒被重新投递几千次，队列在它后面不断积压。
- During a broker restart, the producer logged every publish as successful, but some events never arrived.
  > 在一次 broker 重启期间，生产者把每次发布都记录为成功，但有些事件始终没有到达。

Explain each problem and redesign the pipeline.

> 请解释每个问题，并重新设计这条链路。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Problem 1: auto-ack with unlimited prefetch.** With `autoAck=true`, the broker treats a message as done the moment it sends it. With no prefetch limit (a `basic.qos` prefetch of 0), it pushes as many messages as it can into the consumer's memory. When a deploy stops the process, everything buffered or in progress is gone, and the broker will not deliver it again.

> **问题 1：自动确认加上无上限的预取。** 在 `autoAck=true` 下，broker 一发出消息就认为它已处理完毕。没有预取上限（`basic.qos` 的预取值为 0）时，broker 会尽可能多地把消息推进消费者的内存。发布时进程被停止，所有已缓存或正在处理的消息都会丢失，broker 也不会再投递它们。

Fix: use manual acks, and ack only after the conversion API call succeeds. Set a bounded prefetch, for example 50, which caps both in-flight work and memory. On shutdown, cancel the consumer, finish or nack in-flight messages, and only then exit.

> 修复方法：使用手动确认，只有在转化 API 调用成功后才 ack。设置有界的预取值，例如 50，它同时限制了在途任务数和内存占用。关闭时，先取消消费者，处理完或 nack 掉在途消息，然后再退出。

**Problem 2: a poison message in a requeue loop.** `requeue=true` puts the message back in its original place at the front of the queue, so it is delivered again at once, fails again, and loops as fast as the network allows. Every retry costs CPU, and other messages wait behind it.

> **问题 2：毒消息陷入重新入队的死循环。** `requeue=true` 会把消息放回它在队列前端的原始位置，于是它立刻被再次投递，再次失败，以网络允许的最快速度循环。每次重试都消耗 CPU，其他消息只能在它后面等待。

Fix: classify failures.

> 修复方法：对失败进行分类。

- Transient (timeouts, 5xx, 429): retry after a delay, for example by routing the message to a retry queue whose message TTL dead-letters it back to the main exchange, and count attempts in a header.
  > 暂时性失败（超时、5xx、429）：延迟后重试，例如把消息路由到一个重试队列，利用消息 TTL 让它死信回到主交换机，并在消息头中记录尝试次数。
- Permanent (validation errors), or retries used up: `basicReject(tag, false)` with requeue off, so the queue's dead-letter exchange routes it to a dead-letter queue. Alert on that queue, and provide a replay tool for after the data is fixed.
  > 永久性失败（校验错误），或者重试次数用完：调用 `basicReject(tag, false)` 并关闭重新入队，让队列的死信交换机把它路由到死信队列。对这个队列设置告警，并提供一个在数据修好后重放消息的工具。
- As a safety net, use quorum queues with a `delivery-limit`. Since RabbitMQ 4.0, quorum queues default to a limit of 20 deliveries, after which the message is dead-lettered, or dropped if no dead-letter exchange is configured.
  > 作为兜底，使用带 `delivery-limit` 的 quorum 队列。从 RabbitMQ 4.0 起，quorum 队列默认的投递上限是 20 次，超过后消息会被死信处理；如果没有配置死信交换机，则会被丢弃。

**Problem 3: fire-and-forget publishing.** `basicPublish` returns as soon as the bytes are written to the socket. Without publisher confirms, the producer never learns whether the broker stored the message. Messages also vanish if the queue is not durable, if they are not marked persistent, or if they cannot be routed and are silently dropped.

> **问题 3：发出即不管的发布方式。** `basicPublish` 在字节写入 socket 后就返回了。没有发布确认，生产者永远不知道 broker 是否存储了这条消息。如果队列不是持久化的、消息没有标记为持久化，或者消息无法路由而被悄悄丢弃，消息同样会消失。

Fix: use durable (quorum) queues, persistent messages and publisher confirms: wait for the broker's ack, and retry on a nack or timeout. Set `mandatory` and handle returned messages so unroutable events are noticed. Better still, write the event to an outbox table in the same transaction as the order and let a relay publish it, so an order can never commit without its event.

> 修复方法：使用持久化的（quorum）队列、持久化消息和发布确认：等待 broker 的 ack，在收到 nack 或超时时重试。设置 `mandatory` 并处理被退回的消息，这样无法路由的事件就能被发现。更好的做法是，在写订单的同一个事务里把事件写入 outbox 表，再由一个转发进程负责发布，这样订单提交了就一定会有对应的事件。

**End to end, this is at-least-once.** Publisher retries and consumer redeliveries both create duplicates, so the consumer deduplicates by event id and passes a stable event id to the ad platform where it supports deduplication.

> **端到端来看，这是至少一次的投递。** 发布方的重试和消费方的重新投递都会产生重复，所以消费者要按事件 id 去重；在广告平台支持去重的情况下，还要把稳定的事件 id 传给它。

</details>

## 5. Virtual threads made the service slower

**启用虚拟线程后，服务反而变慢了** · `Java & CS` · `Senior`

### Question · 题目

A Spring Boot 3.3 service on Java 21 turns on virtual threads (`spring.threads.virtual.enabled=true`) to handle more concurrent calls to slow ad-platform APIs. In a load test with 2,000 concurrent requests on an 8-core machine:

> 一个运行在 Java 21 上的 Spring Boot 3.3 服务开启了虚拟线程（`spring.threads.virtual.enabled=true`），以便同时处理更多对慢速广告平台 API 的调用。在一台 8 核机器上用 2,000 个并发请求做压测时：

- Throughput drops below what the old 200-thread Tomcat pool achieved, while the CPU sits mostly idle.
  > 吞吐量反而低于原来 200 个线程的 Tomcat 线程池，而 CPU 大部分时间是空闲的。
- A thread dump shows thousands of virtual threads waiting, and all the carrier threads blocked in a socket read inside a `synchronized` method of a legacy SDK client.
  > 线程 dump 显示有数千个虚拟线程在等待，所有载体线程都阻塞在某个老旧 SDK 客户端的一个 `synchronized` 方法里的 socket 读取上。
- HikariCP starts failing with `Connection is not available, request timed out`.
  > HikariCP 开始报错 `Connection is not available, request timed out`。
- Heap usage is about three times higher than before.
  > 堆内存使用量是以前的三倍左右。

Explain all four effects and how you would fix them.

> 请解释这四个现象，并说明如何修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Effects 1 and 2: pinning.** Virtual threads run on a small pool of carrier threads, by default one per core, so 8 here. When a virtual thread blocks on I/O, it normally unmounts and frees its carrier. On Java 21 to 23, a virtual thread that blocks inside a `synchronized` block or method stays pinned to its carrier. The legacy SDK holds a monitor around its socket read, so 8 slow API calls pin all 8 carriers, and every other virtual thread, even one with only microseconds of work, waits for a carrier. Throughput collapses while the CPU idles. The lock does not even need to be contended. In a quick test with 4 carriers, 100 tasks that each sleep 100 ms inside their own `synchronized` block took about 2.5 s; with `ReentrantLock` they took about 0.1 s.

> **现象 1 和 2：钉住（pinning）。** 虚拟线程运行在一小组载体线程上，默认每个核一个，这里就是 8 个。虚拟线程在 I/O 上阻塞时，通常会卸载并释放它的载体线程。但在 Java 21 到 23 中，在 `synchronized` 代码块或方法里阻塞的虚拟线程会被钉在载体线程上。老旧 SDK 在 socket 读取外面持有一个监视器锁，所以 8 个慢 API 调用就能钉住全部 8 个载体线程，其他所有虚拟线程，哪怕只有几微秒的工作，也只能等待载体线程。于是吞吐量崩溃，CPU 却在空转。这个锁甚至不需要存在竞争。在一次使用 4 个载体线程的简单测试中，100 个任务各自在自己的 `synchronized` 块里 sleep 100 ms，总共耗时约 2.5 s；换成 `ReentrantLock` 后约 0.1 s。

**Finding pinning.** Record with JFR and look for `jdk.VirtualThreadPinned` events, which by default report pins longer than 20 ms. On Java 21 to 23, `-Djdk.tracePinnedThreads=full` prints a stack each time a pinned thread blocks. `jcmd <pid> Thread.dump_to_file -format=json <file>` includes virtual threads, which a classic `jstack` dump leaves out.

> **如何发现钉住。** 用 JFR 录制，查找 `jdk.VirtualThreadPinned` 事件，它默认报告超过 20 ms 的钉住。在 Java 21 到 23 中，`-Djdk.tracePinnedThreads=full` 会在每次被钉住的线程阻塞时打印调用栈。`jcmd <pid> Thread.dump_to_file -format=json <file>` 会包含虚拟线程，而传统的 `jstack` dump 不包含。

**Fixing pinning.**

> **如何修复钉住。**

- Upgrade to Java 24 or later (JEP 491; Java 25 is the current LTS), where `synchronized` no longer pins. Blocking inside native code still does.
  > 升级到 Java 24 或更高版本（JEP 491；Java 25 是当前的 LTS），`synchronized` 不再导致钉住。但在本地代码中阻塞仍然会。
- On Java 21, replace `synchronized` around blocking calls in your own code with `ReentrantLock`, and upgrade libraries that have made the same change.
  > 在 Java 21 上，把自己代码中包住阻塞调用的 `synchronized` 换成 `ReentrantLock`，并升级已经做了同样改动的依赖库。
- Run a library you cannot change on a bounded executor of platform threads, so it cannot occupy the carriers.
  > 无法修改的库，放到一个有界的平台线程 executor 上运行，让它无法占用载体线程。

**Effect 3: the connection pool is now the bottleneck.** The old 200-thread pool quietly limited concurrency. With virtual threads, all 2,000 requests reach HikariCP's 10 connections at once, queue, and time out. Don't raise the pool to 2,000, because the database cannot serve that many connections either. Limit concurrency explicitly: a `Semaphore` per downstream (the database, each external API), sized to what that dependency can handle, so extra requests wait cheaply or are rejected quickly.

> **现象 3：连接池成了瓶颈。** 原来 200 个线程的线程池悄悄地限制了并发。换成虚拟线程后，全部 2,000 个请求同时涌向 HikariCP 的 10 个连接，排队，然后超时。不要把连接池调到 2,000，数据库也承受不了这么多连接。要显式地限制并发：为每个下游（数据库、每个外部 API）配一个 `Semaphore`，大小按该依赖能承受的量来定，多出来的请求以很低的代价等待，或者被快速拒绝。

**Effect 4: memory.** A virtual thread is cheap, but per-thread state is not. Libraries that cache buffers or formatters in a `ThreadLocal` now keep one copy per virtual thread, and 2,000 deep stacks live on the heap. Remove `ThreadLocal` caches or share them, carry request context in parameters or a `ScopedValue` (final in Java 25), and never pool virtual threads: create one per task and bound the work with semaphores.

> **现象 4：内存。** 虚拟线程本身很便宜，但每个线程的状态并不便宜。把缓冲区或格式化器缓存在 `ThreadLocal` 里的库，现在会为每个虚拟线程各保留一份，2,000 个很深的调用栈也都在堆上。去掉 `ThreadLocal` 缓存或改为共享，用参数或 `ScopedValue`（在 Java 25 中正式发布）传递请求上下文，并且绝不池化虚拟线程：每个任务创建一个，用信号量来限制工作量。

**When virtual threads help.** They pay off when many concurrent tasks spend most of their time blocked on I/O. They do nothing for CPU-bound work, and they cannot add capacity to a downstream system that is already saturated.

> **虚拟线程什么时候有用。** 当大量并发任务的大部分时间都阻塞在 I/O 上时，它才有回报。它对 CPU 密集型工作毫无帮助，也无法为一个已经饱和的下游系统增加容量。

</details>
