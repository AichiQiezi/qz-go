## 1. After someone sets Accept-Encoding: gzip on the ad-report client, JSON decoding fails with '\x1f', and the size limit stops working

**有人在广告报表客户端上设置了 Accept-Encoding: gzip 之后，JSON 解码报 '\x1f' 错误，而且大小限制也失效了** · `Go` · `Hard`

### Question · 题目

A Go service downloads daily performance reports from an ad platform. To save bandwidth, a teammate added `req.Header.Set("Accept-Encoding", "gzip")`. Since then, decoding fails with `invalid character '\x1f' looking for beginning of value` on the endpoints that honor gzip, while others still work. Separately, an older code path that never set the header has a size check, `if resp.ContentLength > 200<<20 { reject }`; it never fires, and one 2 GB report ran the pod out of memory.

> 一个 Go 服务从广告平台下载每日效果报表。为了节省带宽，一位同事加上了 `req.Header.Set("Accept-Encoding", "gzip")`。从那以后，在支持 gzip 的端点上，解码报错 `invalid character '\x1f' looking for beginning of value`，而其他端点仍然正常。另外，一条从未设置过这个请求头的旧代码路径里有一个大小检查：`if resp.ContentLength > 200<<20 { reject }`；它从来没有触发过，结果一份 2 GB 的报表把 Pod 的内存耗尽了。

Explain both problems and fix the client.

> 解释这两个问题，并修复这个客户端。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Transparent decompression.** When you do not set `Accept-Encoding` yourself, Go's `http.Transport` asks for gzip on its own and decompresses the response for you. It then removes the `Content-Encoding` and `Content-Length` headers, sets `resp.ContentLength` to -1 and `resp.Uncompressed` to true, as a local test showed.

> **透明解压。** 如果你自己不设置 `Accept-Encoding`，Go 的 `http.Transport` 会自行请求 gzip，并替你把响应解压。随后它会去掉 `Content-Encoding` 和 `Content-Length` 两个响应头，把 `resp.ContentLength` 设为 -1、`resp.Uncompressed` 设为 true，本地测试结果正是如此。

**Why the JSON error.** When you set `Accept-Encoding` yourself, the Transport assumes you will handle the encoding and leaves the body alone. The body is then raw gzip, whose first byte is `0x1f`, hence the JSON error; servers that ignore the header still send plain JSON, which is why only some endpoints broke. In the local test, the same request decoded fine without the header and failed with the `'\x1f'` error with it. Delete the header; if you must set it, decode by `Content-Encoding` yourself.

> **为什么会有 JSON 错误。** 当你自己设置了 `Accept-Encoding` 时，Transport 会认为你要自己处理编码，于是不去碰响应体。这时响应体就是原始的 gzip 数据，第一个字节是 `0x1f`，所以出现了 JSON 错误；而那些忽略这个请求头的服务器仍然发送普通 JSON，这就是为什么只有部分端点出问题。在本地测试中，同一个请求不带这个请求头时能正常解码，带上它就报 `'\x1f'` 错误。删掉这个请求头；如果必须设置它，就自己按 `Content-Encoding` 解码。

**Why the size check never fires.** After transparent decompression, `ContentLength` is -1, so the comparison is always false. Limit what you actually read instead. Wrapped around `resp.Body`, a counting reader sees decompressed bytes, which is what protects memory against a small compressed body that expands enormously.

> **为什么大小检查从不触发。** 经过透明解压后，`ContentLength` 是 -1，所以这个比较永远为假。应该改为限制你实际读取的数据量。把一个计数读取器包在 `resp.Body` 外面，它看到的是解压后的字节，这才能在内存层面防住那种压缩后很小、解压后却极其庞大的响应体。

```go
var errTooLarge = errors.New("report exceeds size limit")

// capReader fails after max bytes. Around resp.Body it counts decompressed
// bytes, because the Transport has already decoded gzip.
type capReader struct {
	r    io.Reader
	left int64
}

func (c *capReader) Read(p []byte) (int, error) {
	if c.left < 0 {
		return 0, errTooLarge
	}
	if int64(len(p)) > c.left+1 {
		p = p[:c.left+1]
	}
	n, err := c.r.Read(p)
	if c.left -= int64(n); c.left < 0 {
		return n, errTooLarge
	}
	return n, err
}

// No Accept-Encoding set by hand; resp.ContentLength is -1 after decompression.
func decodeReport(resp *http.Response, maxBytes int64, v any) error {
	defer resp.Body.Close()
	return json.NewDecoder(&capReader{r: resp.Body, left: maxBytes}).Decode(v)
}
```

Locally, on an 80 KB report, a 1 MB limit decoded all 10,001 rows and a 10 KB limit stopped with `errTooLarge`. If you decode gzip yourself, put the limit around the gzip reader, not the compressed stream.

> 在本地测试中，对于一份 80 KB 的报表，1 MB 的限制完整解码出了全部 10,001 行，而 10 KB 的限制以 `errTooLarge` 停止。如果你自己解码 gzip，要把限制放在 gzip 读取器外面，而不是压缩数据流外面。

**Trade-offs.** Letting the Transport handle gzip is simpler and safer but hides the compressed size. A limited, streamed decode protects memory, but a report that legitimately outgrows the limit now fails loudly, so alert on it.

> **权衡。** 让 Transport 处理 gzip 更简单也更安全，但会隐藏压缩后的大小。带限制的流式解码能保护内存，但一份合理增长到超过限制的报表现在会明确失败，所以要为此设置告警。

</details>

## 2. Search-as-you-type for 100,000 storefronts: suggestions within 100 ms on every keystroke

**为 100,000 个店铺实现边输入边搜索：每次按键都要在 100 毫秒内给出建议** · `System Design` · `Medium`

### Question · 题目

Merchants want search suggestions in their storefront's search box: as a shopper types, show up to eight product names, categories and popular searches. Requirements: under 100 ms at p95 per keystroke, results only from that store and only products that are published and in stock in the shopper's market, new products appearing within minutes, and some tolerance for typos. Stores range from 20 products to 2 million.

> 商家希望在店铺的搜索框里提供搜索建议：顾客输入时，显示最多八个商品名称、分类和热门搜索词。要求：每次按键的 p95 延迟低于 100 毫秒；结果只来自该店铺，并且只包含已上架、在顾客所在市场有库存的商品；新商品在几分钟内就能出现；对输入错误有一定的容错。店铺规模从 20 个商品到 200 万个商品不等。

Design the suggestion service.

> 设计这个搜索建议服务。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why the normal search endpoint is not enough.** Full search ranks a whole catalog and is built for a request every few seconds, not one per keystroke. Most prefixes are short and shared by thousands of shoppers, and a slow answer arrives after the next letter.

> **为什么普通的搜索接口不够用。** 完整搜索要对整个商品目录排序，它是为每隔几秒一次的请求设计的，而不是每次按键一次。大多数前缀都很短，而且被成千上万的顾客共用；而慢一点的回答到达时，顾客已经输入了下一个字母。

**The design.**

> **设计方案。**

- **Client:** start at two characters, debounce keystrokes briefly, and cancel the previous request when a new one starts, so only the latest answer is shown.
  > **客户端：** 从两个字符开始，对按键做短暂的防抖，并在发起新请求时取消上一个请求，这样只显示最新的结果。
- **Precomputed top lists for short prefixes:** per store, a job builds the top suggestions for every prefix up to a few characters from popular searches and product names, ranked by searches and clicks with time decay. These answers are the same for every shopper of that store and market.
  > **为短前缀预先计算的热门列表：** 针对每个店铺，一个任务会根据热门搜索词和商品名称，为每个不超过几个字符的前缀构建最热门的建议，并按搜索和点击次数加上时间衰减进行排序。这些结果对该店铺、该市场的每位顾客都是一样的。
- **A search index for longer prefixes:** an index with edge n-grams or a completion field, filtered by store, market, published and in-stock, with fuzzy matching for typos.
  > **为较长前缀准备的搜索索引：** 一个使用 edge n-gram 或补全字段的索引，按店铺、市场、上架状态和库存进行过滤，并用模糊匹配来容忍输入错误。
- **Freshness:** product events update the index within minutes; the top lists are rebuilt on a schedule, and unpublished or out-of-stock items are filtered again at read time, so a stale list never shows them.
  > **新鲜度：** 商品事件会在几分钟内更新索引；热门列表按计划重建，而已下架或缺货的商品会在读取时再过滤一遍，这样过期的列表也不会把它们显示出来。
- **Caching:** cache short-prefix answers per store and market at the edge with a short lifetime.
  > **缓存：** 在边缘节点按店铺和市场缓存短前缀的结果，设置较短的有效期。

```go
import "sort"

type Term struct {
	Text       string  // normalized, lower-case
	Popularity float64 // searches and clicks with time decay
}

// Top k suggestions for every prefix of 2..maxLen characters, built per store.
// Longer prefixes go to the search index.
func buildPrefixTable(terms []Term, maxLen, k int) map[string][]string {
	sort.Slice(terms, func(i, j int) bool { return terms[i].Popularity > terms[j].Popularity })
	table := map[string][]string{}
	for _, t := range terms {
		r := []rune(t.Text)
		for n := 2; n <= maxLen && n <= len(r); n++ {
			if p := string(r[:n]); len(table[p]) < k {
				table[p] = append(table[p], t.Text)
			}
		}
	}
	return table
}
```

Locally, for five terms, `na` returned the three most popular matches and `nai` only `nail polish`.

> 在本地测试中，对于五个词条，`na` 返回了最热门的三个匹配项，`nai` 只返回了 `nail polish`。

**Trade-offs.** Precomputed lists are fast and cheap but only as fresh as the last build, which is why the read path filters again. Fuzzy matching helps with typos but costs latency and can surface odd results on short prefixes, so apply it only from a few characters up. Small stores can be served entirely from memory; the largest ones need the index.

> **权衡。** 预先计算的列表又快又便宜，但它的新鲜程度只取决于上一次构建，这就是为什么读取路径要再过滤一遍。模糊匹配有助于容忍输入错误，但会增加延迟，并可能在短前缀上给出奇怪的结果，所以只在输入达到几个字符之后才启用。小店铺可以完全从内存里提供服务；最大的那些店铺则需要用索引。

</details>

## 3. Upgrading the orders database with logical replication: at cutover every insert fails with a duplicate key, and the old primary rejected updates during the copy

**用逻辑复制升级订单数据库：切换时每次插入都报主键冲突，而在复制期间，旧主库还拒绝了更新操作** · `Database` · `Senior`

### Question · 题目

To move the orders database to a new major Postgres version with little downtime, the team set up logical replication from the old primary to a new cluster: same schema, `CREATE PUBLICATION ... FOR ALL TABLES` on the old one, a subscription on the new one. Problems:

> 为了以很短的停机时间把订单数据库迁移到新的 Postgres 大版本，团队搭建了从旧主库到新集群的逻辑复制：两边的表结构相同，在旧库上执行 `CREATE PUBLICATION ... FOR ALL TABLES`，在新库上创建订阅。出现了这些问题：

- right after the publication was created, updates to an `order_events` table on the old primary started failing;
  > 发布刚创建好，旧主库上对 `order_events` 表的更新就开始失败；
- a developer added a column on the old primary during the copy, and the new cluster stopped catching up;
  > 复制期间，一位开发人员在旧主库上加了一列，新集群就停止追赶进度了；
- at cutover, every insert into `orders` on the new cluster failed with `duplicate key value violates unique constraint "orders_pkey"`.
  > 切换时，新集群上每一次向 `orders` 插入数据都失败，报错 `duplicate key value violates unique constraint "orders_pkey"`。

Explain each problem and write the cutover plan.

> 解释每个问题，并写出切换方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Logical replication copies row changes for published tables, and nothing else. Sequences and schema changes stay behind, and tables must identify the rows they change. A two-cluster test on Postgres 16 reproduced all three.

> **核心思想。** 逻辑复制只复制已发布表的行变更，其他什么都不复制。序列和表结构变更都会被落下，而且表必须能标识出它所修改的行。在 Postgres 16 上用两个集群做的测试复现了全部三个问题。

**Updates rejected on the old primary.** A table in a publication that publishes updates and deletes needs a replica identity, normally its primary key. `order_events` had none, so the old primary itself refused the update: `cannot update table "order_events" because it does not have a replica identity and publishes updates`. Before creating the publication, give every published table a primary key, or set `REPLICA IDENTITY FULL` where that is impossible.

> **旧主库拒绝更新。** 如果一张表所在的发布要发布更新和删除操作，这张表就需要一个复制标识（replica identity），通常就是它的主键。`order_events` 没有主键，所以旧主库自己拒绝了这次更新：`cannot update table "order_events" because it does not have a replica identity and publishes updates`。在创建发布之前，要给每张要发布的表加上主键；无法加主键的，设置 `REPLICA IDENTITY FULL`。

**Replication stopped after the new column.** Schema changes are not replicated. The new cluster's apply worker kept failing with `logical replication target relation "public.orders" is missing replicated column: "currency"`; adding the column there let it catch up. Freeze schema changes, or apply additive changes to the new cluster first.

> **加了新列之后复制停止了。** 表结构变更是不会被复制的。新集群的应用进程（apply worker）不断报错 `logical replication target relation "public.orders" is missing replicated column: "currency"`；在那里加上这一列之后，它就追上来了。冻结表结构变更，或者把新增类的变更先在新集群上执行。

**Duplicate keys at cutover.** Sequence values are not replicated. After 1,001 rows had arrived, the new cluster's `orders_id_seq` was still at its start (`last_value` 1, `is_called` false), so the first insert after cutover tried `id` 1. At cutover, stop writes, wait until the new cluster has applied everything, then move every sequence past its column's maximum:

> **切换时出现主键冲突。** 序列的值是不会被复制的。在 1,001 行数据已经同步过来之后，新集群的 `orders_id_seq` 仍然停在初始状态（`last_value` 为 1，`is_called` 为 false），所以切换后的第一次插入尝试使用的 `id` 是 1。切换时，先停止写入，等新集群应用完所有变更，然后把每个序列都推进到超过其对应列的最大值：

```sql
-- New primary, writes stopped, replication caught up: one setval per owned sequence.
SELECT format('SELECT setval(%L, (SELECT COALESCE(max(%I), 0) + 1000 FROM %I.%I));',
              seq.oid::regclass, col.attname, ns.nspname, tbl.relname)
FROM pg_class seq
JOIN pg_depend d ON d.objid = seq.oid AND d.classid = 'pg_class'::regclass
                AND d.deptype IN ('a', 'i')
JOIN pg_class tbl ON tbl.oid = d.refobjid
JOIN pg_namespace ns ON ns.oid = tbl.relnamespace
JOIN pg_attribute col ON col.attrelid = tbl.oid AND col.attnum = d.refobjsubid
WHERE seq.relkind = 'S' \gexec
```

Locally, the next inserts after this got 1501 and 1071.

> 在本地测试中，执行之后的插入分别得到了 1501 和 1071。

**The cutover plan.** Check replica identities and freeze DDL first; let the copy finish and watch lag; then stop writes, confirm everything is applied, fix sequences, switch connection strings and run smoke tests. Keep the old cluster as the fallback, and drop its slot when done.

> **切换方案。** 先检查复制标识并冻结 DDL；等待复制完成并监控延迟；然后停止写入，确认所有变更都已应用，修正序列，切换连接字符串并运行冒烟测试。保留旧集群作为回退方案，完成后删除它的复制槽。

**Trade-offs.** Logical replication keeps downtime to the switch itself but needs this preparation. An in-place upgrade is simpler but means a longer outage and a harder rollback.

> **权衡。** 逻辑复制能把停机时间压缩到切换那一刻，但需要上述准备工作。原地升级更简单，但意味着更长的停机时间和更困难的回滚。

</details>

## 4. Catalog sync jobs disappear when a worker pod is killed: a Redis list queue built on BLPOP

**worker Pod 被杀掉时，商品同步任务就凭空消失：一个基于 BLPOP 的 Redis 列表队列** · `Middleware` · `Medium`

### Question · 题目

Catalog sync jobs are pushed onto a Redis list with `RPUSH jobs:sync` and workers take them with `BLPOP`. During deploys and node failures, some merchants' syncs never happen: there is no error, the job is simply gone. The team asks whether they should switch to a full message broker, or whether Redis can do this reliably.

> 商品同步任务通过 `RPUSH jobs:sync` 推送到一个 Redis 列表中，worker 用 `BLPOP` 取出任务。在发布和节点故障期间，有些商家的同步根本没有执行：没有任何报错，任务就这么没了。团队在问：是应该换成一个完整的消息代理，还是 Redis 也能可靠地做到这件事？

Explain the loss and design a reliable queue.

> 解释任务丢失的原因，并设计一个可靠的队列。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why jobs vanish.** `BLPOP` removes the job from Redis the moment it is handed to the worker. From then on the only copy lives in the worker's memory, so a killed pod takes the job with it.

> **为什么任务会消失。** `BLPOP` 在把任务交给 worker 的那一刻，就把它从 Redis 中删除了。从那以后，唯一的副本只存在于 worker 的内存里，所以 Pod 被杀掉时，任务也随之消失。

**Reliable list pattern.** Move the job atomically into a per-worker processing list with `BLMOVE`, and remove it with `LREM` only after the work is done. After a crash, a reaper moves the jobs of workers whose heartbeat expired back to the queue. Locally, a "crashed" worker's job went back to the queue.

> **可靠列表模式。** 用 `BLMOVE` 把任务原子地移到每个 worker 自己的处理中列表里，只有在工作完成之后才用 `LREM` 把它删掉。崩溃之后，回收任务会把心跳已经过期的 worker 的任务移回队列。在本地测试中，一个「崩溃了」的 worker 的任务回到了队列。

```go
// Jobs carry a unique ID, so LREM removes exactly one job.
func work(ctx context.Context, rdb *redis.Client, worker string, handle func(string) error) error {
	processing := "jobs:processing:" + worker
	for ctx.Err() == nil {
		// Atomic move: a crash leaves the job in processing instead of losing it.
		job, err := rdb.BLMove(ctx, "jobs:sync", processing, "LEFT", "RIGHT", 5*time.Second).Result()
		if err == redis.Nil {
			continue
		} else if err != nil {
			return err
		}
		rdb.Set(ctx, "worker:alive:"+worker, "1", 30*time.Second) // heartbeat
		done := context.WithoutCancel(ctx)                        // shutdown must not skip the ack
		if err := handle(job); err != nil {
			rdb.RPush(done, "jobs:failed", job)
		}
		rdb.LRem(done, processing, 1, job) // ack
	}
	return ctx.Err()
}

// Reaper: return the jobs of a worker whose heartbeat expired.
func reap(ctx context.Context, rdb *redis.Client, worker string) error {
	if n, _ := rdb.Exists(ctx, "worker:alive:"+worker).Result(); n > 0 {
		return nil
	}
	for {
		_, err := rdb.LMove(ctx, "jobs:processing:"+worker, "jobs:sync", "RIGHT", "LEFT").Result()
		if err == redis.Nil {
			return nil
		} else if err != nil {
			return err
		}
	}
}
```

The test caught two details. Acknowledge with a context that shutdown cannot cancel: with the cancelled one, the `LREM` for a finished job failed and the job would have run again. And a job that fails in a live worker must leave the processing list explicitly, here into `jobs:failed`, because the reaper only handles dead workers.

> 测试发现了两个细节。确认时要使用一个不会被关闭流程取消的 context：用已取消的 context 时，已完成任务的 `LREM` 失败了，任务会被再执行一次。另外，在仍然存活的 worker 里失败的任务，必须显式地离开处理中列表，这里是放进 `jobs:failed`，因为回收任务只处理已经死掉的 worker。

**Rules that make it work.** Give every payload a unique ID, since `LREM` removes by value, and make handlers idempotent: a crash between work and ack runs a job twice. Redis Streams with consumer groups give the same guarantees with claiming built in.

> **让它能正常工作的规则。** 给每个任务载荷一个唯一的 ID，因为 `LREM` 是按值删除的；并让处理函数具备幂等性：在工作完成和确认之间发生崩溃，任务会被执行两次。带消费者组的 Redis Streams 也能提供同样的保证，并内置了认领机制。

**Trade-offs.** This is at-least-once delivery, so idempotency is not optional. A broker adds dead-letter queues and redelivery delays but is another system to run; for a few sync queues, this pattern is often enough.

> **权衡。** 这是「至少一次」投递，所以幂等性不是可选项。消息代理能提供死信队列和重新投递延迟，但又多了一个要运维的系统；对于少量的同步队列，这种模式通常就够了。

</details>

## 5. Supplier feeds in Windows-1252: one import crashes, another sends broken titles to Google, a third shows 'CafÃ©'

**Windows-1252 编码的供应商 feed：一个导入任务崩溃，另一个把损坏的标题发给了 Google，第三个则显示成「CafÃ©」** · `Java & CS` · `Hard`

### Question · 题目

Several Java services import supplier product feeds. Most suppliers send UTF-8, but some legacy systems still export Windows-1252. Three symptoms appeared after the services moved to a newer JDK:

> 几个 Java 服务负责导入供应商的商品 feed。大多数供应商发送的是 UTF-8，但有些老系统导出的仍然是 Windows-1252。在这些服务迁移到更新的 JDK 之后，出现了三种现象：

- the importer that uses `Files.readAllLines` fails with `MalformedInputException` on those files;
  > 使用 `Files.readAllLines` 的导入程序在这些文件上抛出 `MalformedInputException`；
- the importer that uses `new String(bytes, UTF_8)` succeeds, but titles such as "Café crème – 12€" reach Google Shopping with replacement characters where the accented letters were;
  > 使用 `new String(bytes, UTF_8)` 的导入程序能成功运行，但像「Café crème – 12€」这样的标题到达 Google Shopping 时，带重音的字母都变成了替换字符；
- an export that reads UTF-8 files as Windows-1252 shows "CafÃ©".
  > 一个把 UTF-8 文件当作 Windows-1252 来读的导出功能，显示的是「CafÃ©」。

Explain all three and design the decoding.

> 解释这三种现象，并设计解码方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Bytes have no meaning without a charset, and Java decodes with different error policies in different APIs. Some throw on invalid input, some silently replace it, and a wrong but valid charset produces garbage that no API can detect.

> **核心思想。** 字节在没有字符集的情况下没有任何意义，而 Java 的不同 API 在解码时有不同的错误处理策略。有些遇到无效输入会抛出异常，有些会悄悄替换掉，而一个错误但有效的字符集产生的乱码，任何 API 都检测不出来。

**Why the default changed.** Since JDK 18 the default charset is UTF-8 on every platform. On the test machine (JDK 21), `Charset.defaultCharset()` was UTF-8 even though the operating system's native encoding was ASCII. Code that relied on a Windows server's default charset now decodes as UTF-8.

> **为什么默认值变了。** 从 JDK 18 开始，所有平台上的默认字符集都是 UTF-8。在测试机器上（JDK 21），尽管操作系统的原生编码是 ASCII，`Charset.defaultCharset()` 仍然是 UTF-8。那些依赖 Windows 服务器默认字符集的代码，现在都按 UTF-8 解码了。

**The three symptoms.** In a local test with "Café crème brûlée mug – 12€" saved as Windows-1252:

> **三种现象。** 在本地测试中，把「Café crème brûlée mug – 12€」保存为 Windows-1252：

- `Files.readAllLines`, `Files.readString` and `Files.newBufferedReader` decode as UTF-8 and throw `MalformedInputException`. That crash is the safest of the three outcomes.
  > `Files.readAllLines`、`Files.readString` 和 `Files.newBufferedReader` 按 UTF-8 解码，并抛出 `MalformedInputException`。这次崩溃反而是三种结果里最安全的。
- `new String(bytes, UTF_8)` and `InputStreamReader` replace each invalid byte sequence with U+FFFD, the replacement character: six of them in that title, with no error.
  > `new String(bytes, UTF_8)` 和 `InputStreamReader` 会把每个无效的字节序列替换成 U+FFFD，也就是替换字符：在那个标题里一共替换了六处，没有任何报错。
- UTF-8 bytes decoded as Windows-1252 are valid in that charset, so every API accepts them and `é` becomes `Ã©`.
  > 把 UTF-8 字节按 Windows-1252 解码时，这些字节在该字符集里是有效的，所以每个 API 都会接受它们，`é` 就变成了 `Ã©`。

```java
// Decode strictly: invalid bytes raise an error instead of becoming U+FFFD.
static String decodeFeed(byte[] bytes, Charset supplierCharset) throws CharacterCodingException {
    Charset cs = supplierCharset != null ? supplierCharset : StandardCharsets.UTF_8;
    return cs.newDecoder()
            .onMalformedInput(CodingErrorAction.REPORT)
            .onUnmappableCharacter(CodingErrorAction.REPORT)
            .decode(ByteBuffer.wrap(bytes))
            .toString();
}

// Last line of defence before a title goes to an ad platform.
static void checkTitle(String sku, String title) {
    if (title.indexOf('�') >= 0) {
        throw new IllegalArgumentException("SKU " + sku + ": title contains U+FFFD, decoded with the wrong charset");
    }
}
```

**The design.** Store a charset per supplier and decode with it strictly; locally, strict UTF-8 rejected the Windows-1252 bytes, while the declared charset reproduced the original title exactly. For a new supplier, try strict UTF-8, then only a charset the supplier has confirmed. Keep the original bytes so a wrong guess can be re-decoded, and check titles for U+FFFD before they go to any ad platform.

> **设计方案。** 为每个供应商保存一个字符集，并用它进行严格解码；在本地测试中，严格的 UTF-8 解码拒绝了 Windows-1252 字节，而用声明的字符集解码则完全还原了原始标题。对于新供应商，先尝试严格的 UTF-8 解码，然后只尝试供应商确认过的字符集。保留原始字节，这样猜错时可以重新解码；在标题发往任何广告平台之前，检查其中是否含有 U+FFFD。

**Trade-offs.** Strict decoding turns silent corruption into failed imports that someone has to look at, which is the point but costs support time. Prefer a declared charset over automatic detection, which fails on short texts.

> **权衡。** 严格解码会把悄无声息的数据损坏变成需要有人去处理的导入失败，这正是目的所在，但会耗费客服时间。应优先使用声明的字符集，而不是在短文本上容易出错的自动检测。
