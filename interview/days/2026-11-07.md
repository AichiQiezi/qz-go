## 1. An exchange-rate loader wrapped in sync.Once fails once at startup, and the service never recovers

**用 sync.Once 包装的汇率加载器在启动时失败了一次，服务就再也恢复不了** · `Go` · `Medium`

### Question · 题目

A Go pricing service converts product prices into the shopper's currency. The exchange-rate table is loaded lazily from the database the first time it is needed, guarded by a `sync.Once` so that concurrent requests do not load it twice. After a deploy during a short database failover, every price request kept failing with "connection refused" for hours, although the database was back within a minute. Restarting the pods fixed it.

> 一个 Go 定价服务把商品价格换算成购物者所用的货币。汇率表在第一次需要时才从数据库懒加载，并用 `sync.Once` 保护，这样并发请求就不会重复加载。在一次恰逢数据库短暂故障切换的发布之后，每个价格请求都持续报错 "connection refused" 长达数小时，尽管数据库一分钟内就恢复了。重启 Pod 之后问题才消失。

```go
var (
	once  sync.Once
	rates map[string]float64
	err   error
)

func Rates() (map[string]float64, error) {
	once.Do(func() { rates, err = loadRates() })
	return rates, err
}
```

Explain why it never recovered and how to fix it.

> 解释为什么它再也恢复不了，以及如何修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why it never recovers.** `sync.Once` runs its function exactly once, whatever the outcome. If `loadRates` returns an error, the error is stored in the package variable and every later call returns the same error without trying again. In a local test, three calls after one failed load all returned the original error, and the loader ran only once. `sync.OnceValues` behaves the same way: it caches the error along with the value.

> **为什么它恢复不了。** `sync.Once` 只会执行一次它的函数，不管结果如何。如果 `loadRates` 返回了错误，这个错误就会被存进包级变量，之后的每次调用都直接返回同一个错误，不会重试。在本地测试中，一次加载失败之后的三次调用都返回了最初的错误，而加载函数只运行了一次。`sync.OnceValues` 的行为相同：它会把错误连同值一起缓存起来。

**Panics are no better.** If the function passed to `Do` panics, `Once` still counts it as done: later calls return immediately without running anything, so callers see empty data instead of an error. `sync.OnceFunc` is different: it re-panics with the same value on every call.

> **panic 也好不到哪去。** 如果传给 `Do` 的函数发生了 panic，`Once` 仍然认为它已经执行过：之后的调用会立刻返回，什么都不执行，于是调用方看到的是空数据而不是错误。`sync.OnceFunc` 则不同：每次调用它都会用相同的值再次 panic。

**Fix: remember only success.** Use a mutex and store the result only when loading succeeds. A failed call returns its error, and the next call tries again.

> **修复：只记住成功的结果。** 使用互斥锁，并且只在加载成功时保存结果。失败的调用返回它的错误，下一次调用会重新尝试。

```go
type rateCache struct {
	mu    sync.Mutex
	rates map[string]float64
}

func (c *rateCache) Get(ctx context.Context) (map[string]float64, error) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.rates != nil {
		return c.rates, nil
	}
	r, err := loadRates(ctx)
	if err != nil {
		return nil, err // not cached: the next call retries
	}
	c.rates = r
	return r, nil
}
```

- **Load eagerly at startup** and fail the readiness probe until it succeeds, so traffic never reaches a pod without rates.
  > **在启动时就主动加载**，并且在加载成功之前让就绪探针失败，这样流量就不会打到没有汇率数据的 Pod 上。
- **Bound the retry.** Use a context timeout and a short backoff so a down database is not hit by every request.
  > **限制重试。** 使用带超时的 context 和短暂的退避，这样数据库宕机时不会被每个请求都冲击一遍。
- **Rates change.** A value that is loaded once and kept forever goes stale; refresh it on a schedule and keep the last good table if a refresh fails.
  > **汇率会变化。** 加载一次就永久保留的值会过期；按计划刷新它，并且在刷新失败时保留上一份正确的表。

**Trade-offs.** Holding the mutex during the load means concurrent callers wait for one attempt instead of all hitting the database, which is what you want here, but every caller also waits for the timeout when the database is down. `golang.org/x/sync/singleflight` gives the same deduplication without a long-held lock. Use `sync.Once` only for work that cannot fail, such as building a regexp from a constant.

> **取舍。** 在加载期间持有互斥锁，意味着并发调用方会等待同一次尝试，而不是全都去访问数据库，这正是这里想要的效果；但在数据库宕机时，每个调用方也都要等到超时。`golang.org/x/sync/singleflight` 可以在不长时间持锁的情况下实现同样的去重。只把 `sync.Once` 用在不会失败的工作上，例如用一个常量构建正则表达式。

</details>

## 2. Ad-spend reports that keep changing for days: importing restated numbers from Meta, Google and TikTok

**过了好几天还在变的广告花费报表：从 Meta、Google 和 TikTok 导入会被修正的数据** · `System Design` · `Medium`

### Question · 题目

Merchants connect their Meta, Google and TikTok ad accounts, and the platform shows daily spend, clicks and conversions per campaign next to the store's own sales. A nightly job fetches "yesterday" from each platform and inserts the rows. Merchants complain that the numbers do not match the ad platforms' own dashboards, especially conversions, and that the gap is largest for the last few days. Some days are counted twice after a job retry.

> 商家连接了他们的 Meta、Google 和 TikTok 广告账户，平台按广告系列展示每日花费、点击和转化，并和店铺自己的销售数据放在一起。一个夜间任务从每个平台拉取「昨天」的数据并插入这些行。商家抱怨这些数字和广告平台自己的后台对不上，尤其是转化数，而且最近几天的差距最大。还有一些日子在任务重试之后被计算了两次。

Design the import so the numbers converge on the platforms' figures.

> 设计这个导入流程，让数字最终与各平台的数据一致。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why yesterday is never final.** Ad platforms attribute a conversion to the day of the click or impression, and the conversion can arrive days later within the attribution window. Platforms also remove invalid clicks and correct spend afterwards. A row fetched once the next morning is an early estimate, and importing only yesterday freezes that estimate.

> **为什么昨天的数据永远不是最终的。** 广告平台会把一次转化归因到点击或展示发生的那一天，而这次转化可能在归因窗口内的几天之后才到达。平台之后还会剔除无效点击并修正花费。第二天早上只拉取一次的数据只是一个早期估计，只导入昨天的数据就把这个估计固定住了。

**Re-fetch a sliding window and upsert.** Each run pulls a lookback window per platform, sized from that platform's attribution settings, and writes with an upsert on a natural key. Retries then replace rows instead of adding them.

> **重新拉取一个滑动窗口并执行 upsert。** 每次运行都按平台拉取一个回溯窗口，窗口大小根据该平台的归因设置确定，并基于自然键用 upsert 写入。这样重试就会替换已有的行，而不是新增行。

```sql
INSERT INTO ad_daily (platform, account_id, campaign_id, day,
                      spend_micros, clicks, conversions, fetched_at)
VALUES ($1, $2, $3, $4, $5, $6, $7, now())
ON CONFLICT (platform, account_id, campaign_id, day)
DO UPDATE SET spend_micros = EXCLUDED.spend_micros,
              clicks       = EXCLUDED.clicks,
              conversions  = EXCLUDED.conversions,
              fetched_at   = EXCLUDED.fetched_at;
```

- **Use the ad account's time zone and currency.** "Day" means the account's day as the platform reports it; store the currency with the amount and convert only for display.
  > **使用广告账户的时区和币种。** 「天」指的是平台报告时所用的账户日期；把币种和金额一起存储，只在展示时换算。
- **Handle deletions.** A campaign that disappears from a re-fetched day must be removed or zeroed, so replace the whole (account, day) slice inside one transaction.
  > **处理删除。** 如果某个广告系列在重新拉取的某天数据中消失了，就必须删除它或将其清零，所以要在一个事务中替换整个（账户，日期）切片。
- **Show freshness.** Mark days inside the window as "may still change" and show when each account was last fetched, so merchants know why numbers move.
  > **展示数据新鲜度。** 把窗口内的日期标记为「仍可能变化」，并显示每个账户上次拉取的时间，让商家知道数字为什么会变。
- **Spread the load.** Schedule accounts across the night with per-platform rate limits, and backfill a new connection in small date ranges.
  > **分散负载。** 结合各平台的限流，把各个账户的任务分散在整个夜间执行，并且对新连接按较小的日期范围分批回填历史数据。

**Trade-offs.** A longer window gets closer to the platform's numbers but costs more API quota every night; many teams re-fetch recent days daily and older days weekly. Comparing the platform's conversions with the store's own orders will never match exactly, because each side uses its own attribution, so explain the difference instead of forcing them to agree.

> **取舍。** 窗口越长，数据越接近平台的数字，但每晚消耗的 API 配额也越多；很多团队每天重新拉取最近几天的数据，每周再重新拉取更早的数据。平台的转化数和店铺自己的订单永远不会完全一致，因为双方使用各自的归因方式，所以应该解释差异，而不是强行让它们一致。

</details>

## 3. Moving tenant isolation into Postgres row-level security: the owner sees every row, and pooled connections leak the tenant

**把租户隔离移到 Postgres 行级安全中：表的所有者能看到所有行，连接池中的连接还会泄漏租户** · `Database` · `Senior`

### Question · 题目

A multi-tenant SaaS stores all merchants in shared tables with a `tenant_id` column. After a bug where a missing `WHERE tenant_id = ?` showed one merchant another merchant's orders, the team adds row-level security, so the database enforces the filter. The application sets the tenant with `SET app.tenant_id = '42'` when it borrows a connection from the pool.

> 一个多租户 SaaS 把所有商家存放在带有 `tenant_id` 列的共享表中。在一次因为漏写 `WHERE tenant_id = ?` 而让一个商家看到另一个商家订单的 bug 之后，团队加上了行级安全，让数据库来强制执行这个过滤。应用在从连接池借出连接时，用 `SET app.tenant_id = '42'` 设置租户。

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id', true)::bigint);
```

In testing, the migration user still sees every row. In production, a request that forgot to set the tenant returns another merchant's data, and a later change to `SET LOCAL` makes some queries fail with "invalid input syntax for type bigint". Explain all three and design the rollout.

> 在测试中，执行迁移的用户仍然能看到所有行。在生产环境中，一个忘记设置租户的请求返回了另一个商家的数据；而后来改用 `SET LOCAL` 之后，有些查询又报错 "invalid input syntax for type bigint"。解释这三个现象，并设计上线方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The owner bypasses the policy.** Row-level security does not apply to the table's owner unless the table also has `FORCE ROW LEVEL SECURITY`, and superusers and roles with `BYPASSRLS` skip it always. In a local test, a non-superuser owner saw all rows until `FORCE` was added; a superuser still saw all rows after it. The application must connect as a separate role that owns nothing.

> **表的所有者会绕过策略。** 行级安全不会作用于表的所有者，除非表还设置了 `FORCE ROW LEVEL SECURITY`；而超级用户和拥有 `BYPASSRLS` 的角色则总是会跳过它。在本地测试中，一个非超级用户的所有者在加上 `FORCE` 之前能看到所有行；而超级用户在加上之后仍然能看到所有行。应用必须以一个不拥有任何对象的独立角色连接数据库。

**A session setting outlives the request.** `SET` lasts for the whole connection. When the pool hands that connection to the next request, the old tenant is still set, and a request that forgot to set its own reads the previous merchant's rows. The test reproduced this on one connection.

> **会话级设置比请求活得更久。** `SET` 的效果会持续整个连接。当连接池把这个连接交给下一个请求时，旧的租户仍然有效，一个忘记设置自己租户的请求就会读到上一个商家的行。测试在同一个连接上复现了这个问题。

**`SET LOCAL` leaves an empty string.** `SET LOCAL` resets at the end of the transaction, which is what you want. But afterwards `current_setting('app.tenant_id', true)` returns an empty string, not NULL, and casting it to `bigint` throws. Before the setting was ever used it returns NULL. Wrap it in `NULLIF`, so an unset tenant matches no rows instead of failing.

> **`SET LOCAL` 会留下一个空字符串。** `SET LOCAL` 在事务结束时重置，这正是我们想要的。但之后 `current_setting('app.tenant_id', true)` 返回的是空字符串而不是 NULL，把它转换成 `bigint` 就会报错。在这个设置从未被使用过时，它返回的是 NULL。用 `NULLIF` 包一层，这样未设置租户时就匹配不到任何行，而不是报错。

```sql
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint);

-- per request, inside the transaction:
BEGIN;
SET LOCAL app.tenant_id = '42';
-- queries...
COMMIT;
```

- **Writes are checked too.** Without a `WITH CHECK` clause the `USING` expression also checks new rows, so inserting a row for another tenant fails with a policy violation.
  > **写入也会被检查。** 没有 `WITH CHECK` 子句时，`USING` 表达式也会检查新行，所以插入属于另一个租户的行会因违反策略而失败。
- **Index the tenant column.** The policy becomes part of every query; with an index on `tenant_id` the test plan used it.
  > **为租户列建索引。** 策略会成为每个查询的一部分；在 `tenant_id` 上有索引时，测试中的执行计划使用了它。
- **Roll out per table.** Enable the policy in staging with the application role, compare query results with the old filters, and keep the `WHERE tenant_id` clauses as a second layer.
  > **逐表上线。** 先在预发环境中用应用角色启用策略，把查询结果和原来的过滤结果进行对比，并保留 `WHERE tenant_id` 子句作为第二层保护。

**Trade-offs.** RLS turns a forgotten filter from a data leak into an empty result, but it hides the filter from code review and can surprise people debugging with an admin account. Background jobs that work across tenants need a separate role with `BYPASSRLS`, which must be tightly limited. Every connection must run requests in transactions; poolers in statement mode cannot carry `SET LOCAL` across statements.

> **取舍。** RLS 把一个被遗忘的过滤条件从数据泄漏变成了空结果，但它也让过滤条件在代码评审中不可见，还可能让用管理员账户调试的人感到意外。跨租户工作的后台任务需要一个拥有 `BYPASSRLS` 的独立角色，而这个角色必须受到严格限制。每个连接都必须在事务中执行请求；语句模式的连接池无法让 `SET LOCAL` 跨语句生效。

</details>

## 4. A delayed-job queue on a Redis sorted set runs jobs twice under load and loses them when a worker crashes

**基于 Redis 有序集合的延迟任务队列：高负载时任务执行两次，worker 崩溃时任务丢失** · `Middleware` · `Hard`

### Question · 题目

Delayed jobs, such as "retry the TikTok catalog sync in 10 minutes" or "cancel the unpaid order in 30 minutes", are stored in a Redis sorted set with the due time as the score. Each worker polls once a second:

> 延迟任务，例如「10 分钟后重试 TikTok 商品目录同步」或「30 分钟后取消未支付的订单」，被存储在一个以到期时间为分数的 Redis 有序集合中。每个 worker 每秒轮询一次：

```text
ZRANGEBYSCORE delayed -inf <now> LIMIT 0 100
for each id: run the job, then ZREM delayed id
```

With more workers, some orders are cancelled twice and some syncs run twice. When a worker is killed during a deploy, the jobs it was running are never retried. Explain and redesign.

> worker 增多之后，有些订单被取消了两次，有些同步执行了两次。当某个 worker 在发布时被杀掉，它正在执行的任务就再也不会被重试。请解释原因并重新设计。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why jobs run twice.** Reading and removing are separate commands. Two workers that poll at the same time both read the same due ids and both run them. Moving `ZREM` before the work and running only if `ZREM` returns 1 closes that race: in a local test the first `ZREM` returned 1 and the second 0.

> **为什么任务会执行两次。** 读取和删除是两条独立的命令。两个同时轮询的 worker 会读到相同的到期 id，并且都去执行它们。把 `ZREM` 移到执行之前，并且只在 `ZREM` 返回 1 时才执行，就能消除这个竞态：在本地测试中，第一次 `ZREM` 返回 1，第二次返回 0。

**Why jobs vanish.** But removing first means a crash between `ZREM` and the end of the job loses it, because nothing records that it was taken. Delivery needs a claimed state that expires: a lease.

> **为什么任务会消失。** 但先删除意味着，如果在 `ZREM` 之后、任务完成之前崩溃，任务就丢了，因为没有任何地方记录它已被领取。投递需要一个会过期的「已领取」状态：也就是租约。

**Claim with a lease, atomically.** A Lua script moves due jobs from `delayed` to a `processing` sorted set whose score is the lease deadline. Scripts run atomically, so two workers can never claim the same job. In the test, a second claim at the same moment returned nothing.

> **原子地领取并附带租约。** 一个 Lua 脚本把到期的任务从 `delayed` 移到 `processing` 有序集合中，其分数是租约的截止时间。脚本是原子执行的，所以两个 worker 永远不会领取到同一个任务。在测试中，同一时刻的第二次领取什么也没有返回。

```lua
-- KEYS[1]=delayed KEYS[2]=processing ARGV: now, lease_until, limit
local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[3])
for _, id in ipairs(due) do
  redis.call('ZREM', KEYS[1], id)
  redis.call('ZADD', KEYS[2], ARGV[2], id)
end
return due
```

- **Acknowledge by removing from `processing`.** If that `ZREM` returns 0, the lease had expired and someone else may own the job; log it.
  > **通过从 `processing` 中删除来确认完成。** 如果这次 `ZREM` 返回 0，说明租约已经过期，任务可能已经归别人所有；要记录下来。
- **Reap expired leases.** A second script moves jobs whose lease deadline has passed back to `delayed`; in the test, a crashed worker's job reappeared there.
  > **回收过期的租约。** 第二个脚本把租约截止时间已过的任务移回 `delayed`；在测试中，崩溃 worker 的任务重新出现在了那里。
- **Make jobs idempotent.** A slow worker whose lease expires keeps running while another starts, so delivery is at least once. Cancelling an order must check its state, for example `UPDATE ... WHERE status = 'unpaid'`.
  > **让任务具备幂等性。** 租约过期的慢 worker 会继续运行，而另一个 worker 同时开始执行，所以投递语义是「至少一次」。取消订单时必须检查订单状态，例如 `UPDATE ... WHERE status = 'unpaid'`。
- **Keep payloads in a hash** keyed by id, and pass `now` from one clock, because workers' clocks differ.
  > **把任务内容存放在以 id 为键的哈希中**，并且由同一个时钟传入 `now`，因为各个 worker 的时钟并不一致。

**Trade-offs.** Leases trade lost jobs for duplicates, and the lease length trades fast recovery against duplicates for slow jobs; long jobs should extend their lease. Redis persistence and failover can still lose recent writes, so the order itself must carry the truth, with a periodic database scan as a safety net. If you already run Kafka or a job framework with delays and retries, prefer it over building this yourself.

> **取舍。** 租约用重复执行换来了不丢任务，而租约的长短则是在快速恢复和慢任务被重复执行之间权衡；长任务应该续租。Redis 的持久化和故障转移仍然可能丢失最近的写入，所以订单本身必须承载真实状态，并用定期的数据库扫描作为兜底。如果你已经在用 Kafka 或支持延迟与重试的任务框架，优先使用它们，而不是自己实现。

</details>

## 5. Truncating product titles to an ad platform's limit turns emoji into '?' and some feeds are rejected

**按广告平台的长度限制截断商品标题，表情符号变成了 '?'，部分 feed 还被拒绝** · `Java & CS` · `Hard`

### Question · 题目

Before sending products to ad platforms, a Java service shortens each title to the platform's limit with `title.substring(0, Math.min(title.length(), max))`. Merchants report titles ending in "?", flags and family emoji that split into separate figures, and one platform rejecting feeds because a title is over its limit, although the code checked the length.

> 在把商品发送给广告平台之前，一个 Java 服务用 `title.substring(0, Math.min(title.length(), max))` 把每个标题缩短到平台的限制以内。商家反馈标题末尾出现了 "?"，国旗和家庭表情被拆成了几个单独的图形，还有一个平台因为标题超长拒绝了 feed，尽管代码检查过长度。

Explain each symptom and write a correct truncation.

> 解释每一个现象，并写出一个正确的截断方法。

<details>
<summary><b>Answer · 参考答案</b></summary>

**`length()` counts UTF-16 units.** A Java `String` is a sequence of UTF-16 code units. Characters outside the Basic Multilingual Plane, including most emoji, take two units, a surrogate pair. In a local test, cutting "Wool Scarf 🧣 Winter" at 12 kept only the high surrogate of the scarf emoji.

> **`length()` 计算的是 UTF-16 单元。** Java 的 `String` 是一串 UTF-16 代码单元。基本多文种平面之外的字符，包括大多数表情符号，占用两个单元，即一个代理对。在本地测试中，把 "Wool Scarf 🧣 Winter" 在 12 处截断，只保留了围巾表情的高位代理。

**Where the "?" comes from.** A lone surrogate is not a valid character, so `getBytes(StandardCharsets.UTF_8)` replaces it with `?`; the test showed the last byte as 0x3F. Some JSON encoders and APIs reject the string instead.

> **"?" 是从哪里来的。** 单独的代理项不是有效的字符，所以 `getBytes(StandardCharsets.UTF_8)` 会把它替换成 `?`；测试显示最后一个字节是 0x3F。有些 JSON 编码器和 API 则会直接拒绝这个字符串。

**What users see as one character.** A flag is two code points, a family emoji is several code points joined by zero-width joiners, and "é" can be "e" plus a combining accent. Cutting between code points still splits them. What a user sees as one character is a grapheme cluster: in the test, the family emoji was 8 UTF-16 units but one cluster.

> **用户眼中的一个字符。** 一面国旗是两个码点，一个家庭表情是由零宽连接符连起来的多个码点，而 "é" 可以是 "e" 加上一个组合重音符。在码点之间截断仍然会把它们拆开。用户看到的一个字符是一个字素簇：在测试中，家庭表情占 8 个 UTF-16 单元，却只是一个字素簇。

**Why the platform still rejected it.** Platforms count in different units, often UTF-8 bytes or code points. An emoji is 2 UTF-16 units but 4 UTF-8 bytes, so a title under the limit in `length()` can be over it in bytes.

> **为什么平台还是拒绝了它。** 各平台的计数单位不同，常见的是 UTF-8 字节或码点。一个表情符号占 2 个 UTF-16 单元，却占 4 个 UTF-8 字节，所以按 `length()` 没超限的标题，按字节算可能就超了。

**Fix: cut at grapheme boundaries, measured in the platform's unit.** On Java 21, `BreakIterator.getCharacterInstance()` returned grapheme cluster boundaries for the flag, family and accent cases in the test.

> **修复：在字素簇边界截断，并用平台的单位来计量。** 在 Java 21 上，`BreakIterator.getCharacterInstance()` 在测试中针对国旗、家庭表情和重音字符都返回了字素簇边界。

```java
static String truncateUtf8(String s, int maxBytes) {
    BreakIterator it = BreakIterator.getCharacterInstance();
    it.setText(s);
    int end = 0;
    for (int b = it.next(); b != BreakIterator.DONE; b = it.next()) {
        if (s.substring(0, b).getBytes(StandardCharsets.UTF_8).length > maxBytes) break;
        end = b;
    }
    return s.substring(0, end);
}
```

**Trade-offs.** This loop re-encodes the prefix at each boundary, which is fine for titles and too slow for large texts, where you would count bytes per cluster instead. Grapheme rules follow the Unicode version of the JDK, so older JDKs split some emoji differently. Keep one limit function per platform, test it with emoji, flags and accents, and store the untruncated title.

> **取舍。** 这个循环在每个边界都重新编码前缀，用于标题没有问题，但对于大段文本就太慢了，那时应改为按字素簇累加字节数。字素簇的规则跟随 JDK 所支持的 Unicode 版本，所以较旧的 JDK 对某些表情的拆分方式不同。为每个平台保留一个限制函数，用表情、国旗和重音字符来测试它，并保存未截断的原始标题。

</details>
