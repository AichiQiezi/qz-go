## 1. A webhook middleware checks the HMAC signature, and then every order webhook fails to decode with EOF

**Webhook 中间件校验完 HMAC 签名后，所有订单 webhook 在解码时都报 EOF** · `Go` · `Medium`

### Question · 题目

Order webhooks from a marketplace are signed with HMAC-SHA256 over the raw body. A teammate added a middleware that reads the body with `io.ReadAll`, compares the signature with `hmac.Equal`, and then calls the order handler. Signatures now pass, but the handler's `json.NewDecoder(r.Body).Decode` fails with `EOF` on every request, and the marketplace starts retrying all webhooks.

> 某个电商平台发来的订单 webhook 用 HMAC-SHA256 对原始请求体签名。一位同事加了一个中间件：用 `io.ReadAll` 读取请求体，用 `hmac.Equal` 比对签名，然后调用订单处理函数。现在签名都能通过，但处理函数里的 `json.NewDecoder(r.Body).Decode` 每次都报 `EOF`，平台开始重试所有 webhook。

Explain the bug and fix the middleware.

> 解释这个 bug，并修复中间件。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** `r.Body` is a stream, not a buffer. `io.ReadAll` consumed it, so the handler reads from a stream that is already at its end. Decoding zero bytes gives `EOF`. In a local test, the middleware returned 400 with `decode: EOF` for a correctly signed body.

> **原因。** `r.Body` 是一个流，而不是缓冲区。`io.ReadAll` 已经把它读完了，所以处理函数读的是一个已经到达末尾的流。对零字节解码会得到 `EOF`。在本地测试中，对一个签名正确的请求体，中间件返回了 400 和 `decode: EOF`。

**The fix.** Read the body once, with a size limit, verify the signature over those exact bytes, and give the handler a fresh reader over the same bytes:

> **修复方法。** 只读取一次请求体，并加上大小限制；对这些原始字节校验签名；再给处理函数一个基于同一批字节的新 reader：

```go
const maxWebhookBody = 1 << 20 // 1 MiB

func verify(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, maxWebhookBody))
		if err != nil {
			http.Error(w, "body too large or unreadable", http.StatusRequestEntityTooLarge)
			return
		}
		if !hmac.Equal([]byte(sign(body)), []byte(r.Header.Get("X-Signature"))) {
			http.Error(w, "bad signature", http.StatusUnauthorized)
			return
		}
		r.Body = io.NopCloser(bytes.NewReader(body)) // the handler reads the same bytes
		next.ServeHTTP(w, r)
	})
}
```

- **Sign the raw bytes.** Never verify against re-encoded JSON: in the test, `{"id":"ord_1001"}` and `{"id": "ord_1001"}` produced different signatures, although they parse to the same value.
  > **对原始字节签名。** 绝不要对重新编码后的 JSON 做校验：在测试中，`{"id":"ord_1001"}` 和 `{"id": "ord_1001"}` 生成的签名不同，尽管它们解析出来的值一样。
- **Limit the size before reading.** Without `http.MaxBytesReader`, anyone can make the service buffer an arbitrarily large body before the signature check rejects it; with a 1 MiB limit, a 2 MiB body got a 413.
  > **读取前先限制大小。** 没有 `http.MaxBytesReader` 的话，任何人都能让服务在签名校验拒绝之前，先缓冲一个任意大的请求体；设置 1 MiB 的限制后，一个 2 MiB 的请求体得到了 413。
- **Compare in constant time** with `hmac.Equal`, as the middleware already does, and check the timestamp header if the platform sends one, to reject replays.
  > **用常量时间比较，** 也就是 `hmac.Equal`，中间件已经这么做了；如果平台发送了时间戳头，还要检查它以拒绝重放。

**Trade-offs.** Buffering the whole body costs memory per request, which is why the limit matters; for very large payloads, stream into a hash and a temporary file instead. Return the error status quickly and do the real work asynchronously, so the platform's retries stay rare.

> **权衡。** 缓冲整个请求体会让每个请求都占用内存，所以限制大小很重要；对于非常大的载荷，可以改为边读边计算哈希并写入临时文件。尽快返回状态码，把实际处理放到异步任务中，这样平台的重试会保持很少。

</details>

## 2. Bulk-editing prices for 500,000 products with a preview and an undo button that does not overwrite later changes

**对 50 万个商品批量改价：要有预览，还要有不会覆盖后续修改的撤销按钮** · `System Design` · `Hard`

### Question · 题目

Merchants want to select products by filter, such as a collection or a tag, and apply a change like "raise prices 10%" or "set compare-at price" to up to 500,000 products. They want a preview first and an undo button afterwards. The changes must reach the storefront, the search index and the ad feeds. Today a single synchronous request does the update and times out on large stores.

> 商家希望按条件（比如某个商品分组或标签）选出商品，然后对最多 50 万个商品执行「涨价 10%」或「设置划线价」之类的修改。他们希望先预览，事后还能一键撤销。这些修改必须同步到店铺前台、搜索索引和广告商品源。目前是一个同步请求完成整个更新，大店铺会超时。

Design the bulk-edit feature.

> 设计这个批量编辑功能。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Make it a job, not a request.** The API creates a bulk-edit job and returns its ID. The job freezes the selection at creation time by saving the matching product IDs, so products added later are not swept in by surprise, and processes them in batches of a few hundred, each batch in its own short transaction.

> **把它做成任务，而不是请求。** API 创建一个批量编辑任务并返回任务 ID。任务在创建时就固定选择范围，保存匹配到的商品 ID，这样之后新增的商品不会被意外卷入；然后按每批几百个商品处理，每一批都在自己的短事务中完成。

- **Preview:** compute the count and a sample of before and after values from the frozen selection, and flag values the change would make invalid, such as a negative price or a sale price above the regular price.
  > **预览：** 基于固定下来的选择范围计算数量，并抽样展示修改前后的值；同时标出这次修改会导致无效的值，比如负价格，或者促销价高于原价。
- **Change log:** for every product, write the job ID, the field, the old value and the new value in the same transaction as the update. This log is what makes undo possible and gives support an audit trail.
  > **变更日志：** 对每个商品，把任务 ID、字段、旧值和新值，与更新本身写在同一个事务里。正是这份日志让撤销成为可能，也为客服提供了审计记录。
- **Restartable batches:** record progress per batch, and make each batch idempotent, so a crashed worker resumes without applying a 10% increase twice. Store the computed new value, not the formula.
  > **可恢复的批次：** 按批记录进度，并让每一批都是幂等的，这样崩溃的 worker 恢复后不会把 10% 的涨幅应用两次。存储计算好的新值，而不是公式。

**Undo without clobbering.** Between the job and the undo, the merchant or an inventory app may have edited some products. Undo restores the old value only where the current value still equals what the job wrote, as a compare-and-set in the `UPDATE` itself, and reports the products it skipped. Restoring blindly would silently erase those later edits.

> **撤销时不覆盖他人修改。** 在任务完成到撤销之间，商家或某个库存应用可能已经改过部分商品。撤销时只有当当前值仍然等于任务写入的值时，才恢复旧值；这个比较并设置直接写在 `UPDATE` 语句里；被跳过的商品要报告出来。盲目恢复会悄悄抹掉那些后来的修改。

**Downstream.** Each batch emits change events after commit, through an outbox. The search indexer and the feed builder consume them at their own pace; ad platforms have their own rate limits, so feed updates for a 500,000-product job may take hours, and the job page should say so rather than claim everything is live.

> **下游同步。** 每一批在提交后通过 outbox 发出变更事件。搜索索引器和商品源构建器按各自的节奏消费；广告平台有自己的限流，所以一个 50 万商品的任务，商品源可能要好几个小时才能更新完，任务页面应如实说明，而不是声称一切都已生效。

**Limits and safety.** Allow one running job per store, cap the size per plan, and require confirmation above a threshold. A job can be cancelled between batches, leaving a clear record of which products changed.

> **限制与安全。** 每个店铺同时只允许一个运行中的任务，按套餐限制规模，超过阈值时要求二次确认。任务可以在批次之间取消，并留下清晰的记录，说明哪些商品已被修改。

**Trade-offs.** Batches mean the store is partly updated for a while, which beats one huge transaction that locks rows for minutes. The change log costs storage, so keep it for a fixed period after which undo is no longer offered.

> **权衡。** 分批处理意味着店铺会有一段时间处于部分更新的状态，但这比一个锁住行好几分钟的超大事务要好。变更日志会占用存储空间，所以只保留固定的一段时间，过期之后不再提供撤销。

</details>

## 3. A sync worker calls the Meta API inside a database transaction, and during a Meta slowdown checkouts hang and the connection pool runs dry

**同步 worker 在数据库事务里调用 Meta API，Meta 一变慢，结账就卡住，连接池也被耗尽** · `Database` · `Senior`

### Question · 题目

A catalog sync worker opens a transaction, updates the product's `sync_status` row and the matching stock row, calls the Meta Catalog API, and commits after the response. During a Meta slowdown, checkouts that touch the same stock rows hang, the API's connection pool is exhausted, and `pg_stat_activity` shows many sessions in `idle in transaction` and many more waiting on locks.

> 一个商品目录同步 worker 会打开一个事务，更新商品的 `sync_status` 行和对应的库存行，然后调用 Meta Catalog API，拿到响应后再提交。Meta 变慢期间，涉及同样库存行的结账请求会卡住，API 的连接池被耗尽，`pg_stat_activity` 显示大量会话处于 `idle in transaction` 状态，还有更多会话在等锁。

Explain the failure and redesign the flow.

> 解释这个故障，并重新设计流程。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** Row locks taken by an `UPDATE` are held until the transaction ends. While the worker waits for Meta, its session is idle in transaction and keeps those locks. Every checkout that updates the same stock row waits, and each waiting request holds a pool connection, so a slow third party turns into an outage of your own database.

> **原因。** `UPDATE` 获取的行锁会一直保持到事务结束。worker 等待 Meta 时，它的会话处于事务中空闲状态，并一直持有这些锁。所有更新同一库存行的结账请求都要等待，而每个等待的请求都占着一个连接池连接，于是一个变慢的第三方，就变成了你自己数据库的故障。

**Reproduced locally:** one session held a row lock while idle in transaction, and three more `UPDATE`s on the same row queued behind it. `pg_blocking_pids` showed the first waiter blocked by the idle session and each later waiter blocked by the ones before it, so the queue grows behind a single holder.

> **本地复现：** 一个会话在事务中空闲并持有行锁，另外三条针对同一行的 `UPDATE` 排在它后面。`pg_blocking_pids` 显示：第一个等待者被那个空闲会话阻塞，之后的每个等待者又被排在它前面的会话阻塞，所以队列会在单个持锁者后面不断变长。

```sql
-- Find who is holding everyone up.
SELECT pid, state, wait_event_type, pg_blocking_pids(pid) AS blocked_by,
       now() - xact_start AS xact_age, left(query, 60) AS last_query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_start;

-- Guard rails for the application role.
ALTER ROLE app SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE app SET lock_timeout = '2s';
```

**The redesign: never hold a transaction across a network call.**

> **重新设计：绝不在网络调用期间持有事务。**

- **Transaction 1:** mark the product as pending sync and write a job to an outbox table, then commit. Checkout never waits on this.
  > **事务 1：** 把商品标记为待同步，并向 outbox 表写入一个任务，然后提交。结账永远不必等它。
- **Outside any transaction:** call Meta with a timeout and an idempotency key.
  > **在任何事务之外：** 带着超时和幂等键调用 Meta。
- **Transaction 2:** record the result with a conditional update, so a stale response cannot overwrite a newer sync.
  > **事务 2：** 用条件更新记录结果，这样过期的响应不会覆盖更新的同步结果。
- **Stock is not the sync worker's business.** Keep stock updates in short transactions owned by the order service.
  > **库存不归同步 worker 管。** 库存更新放在由订单服务负责的短事务中。

**Guard rails.** With `idle_in_transaction_session_timeout`, the server ended an idle transaction in the local test with a FATAL error and rolled it back, which released its locks. With `lock_timeout`, a waiting statement failed after its timeout instead of hanging. Set both per role, alert on old transactions, and size pool waits so requests fail fast.

> **防护措施。** 在本地测试中，设置 `idle_in_transaction_session_timeout` 后，服务端以 FATAL 错误结束了一个空闲事务并回滚，从而释放了它持有的锁。设置 `lock_timeout` 后，等待中的语句在超时后失败，而不是一直挂着。两者都按角色设置，对长事务告警，并设定连接池的等待时间，让请求快速失败。

**Trade-offs.** Splitting the transaction means the database and Meta can disagree for a while, so the outbox and a reconciliation job must close the gap. Timeouts turn hangs into errors that callers must handle and retry.

> **权衡。** 拆分事务意味着数据库和 Meta 会有一段时间不一致，所以需要 outbox 和对账任务来弥合差距。超时会把卡住变成报错，调用方必须处理并重试。

</details>

## 4. During flash sales, the WebSocket gateway's Redis Pub/Sub subscription keeps getting disconnected, and shoppers miss price updates

**限时促销期间，WebSocket 网关的 Redis Pub/Sub 订阅不断被断开，顾客错过了价格更新** · `Middleware` · `Hard`

### Question · 题目

A WebSocket gateway subscribes to the Redis channel `price-updates` and pushes each message to connected shoppers. During flash sales, the gateway's logs show the Redis connection dropping every few minutes. While it reconnects, shoppers see stale prices, and the publisher's `PUBLISH` sometimes returns 0.

> 一个 WebSocket 网关订阅 Redis 频道 `price-updates`，并把每条消息推送给已连接的顾客。限时促销期间，网关日志显示与 Redis 的连接每隔几分钟就断一次。在重连期间，顾客看到的是过期的价格，发布方的 `PUBLISH` 有时返回 0。

Explain what is happening and redesign the pipeline.

> 解释发生了什么，并重新设计这条链路。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** Redis buffers outgoing messages per client. When a subscriber reads more slowly than messages are published, its output buffer grows, and Redis closes the connection once the buffer passes the limit for its client class. The pubsub limit has a hard size and a soft size held for a number of seconds; this server's defaults were 32 MB hard and 8 MB for 60 seconds.

> **原因。** Redis 会为每个客户端缓冲待发送的消息。当订阅者读取的速度跟不上发布速度时，它的输出缓冲区就会增长，一旦超过该客户端类别的限制，Redis 就会关闭连接。pubsub 的限制包括一个硬上限，以及一个需要持续若干秒才触发的软上限；这台服务器的默认值是硬上限 32 MB、软上限 8 MB 持续 60 秒。

**Reproduced locally:** with the pubsub limit lowered to 1 MB, a subscriber that stopped reading was closed. The log said the client was "scheduled to be closed ASAP for overcoming of output buffer limits", and later `PUBLISH` calls returned 0 receivers. Pub/Sub stores nothing, so every message published while the gateway was gone was lost.

> **本地复现：** 把 pubsub 限制调低到 1 MB 后，一个停止读取的订阅者被关闭了。日志写着该客户端「scheduled to be closed ASAP for overcoming of output buffer limits」，之后的 `PUBLISH` 返回 0 个接收者。Pub/Sub 不存储任何东西，所以网关断开期间发布的每条消息都丢了。

**Why the gateway is slow.** It pushes to thousands of WebSockets from the same loop that reads Redis, so one slow shopper's connection stalls the read.

> **网关为什么慢。** 它在读取 Redis 的同一个循环里向成千上万个 WebSocket 推送消息，所以一个慢速顾客的连接就会拖住整个读取过程。

- **Decouple reading from fan-out:** one goroutine reads Redis into a bounded queue; per-connection writers have their own small buffers and drop or disconnect slow shoppers, never the Redis subscription.
  > **把读取与扇出解耦：** 一个 goroutine 从 Redis 读取到有界队列；每个连接的写入者有自己的小缓冲区，丢弃或断开慢速顾客，而绝不拖累 Redis 订阅。
- **Send state, not deltas:** a price message carries the full current price, so a missed one is repaired by the next, and on reconnect the gateway reloads current prices for the pages it serves.
  > **发送状态而不是增量：** 价格消息携带完整的当前价格，这样漏掉一条会被下一条修复；网关重连后，重新加载它所服务页面的当前价格。
- **Coalesce:** during a sale, keep only the latest price per product in the queue instead of every intermediate update.
  > **合并更新：** 促销期间，队列里每个商品只保留最新价格，而不是每一次中间更新。
- **Need delivery guarantees?** Use Redis Streams, where a consumer reads from its last ID after a reconnect, instead of raising the buffer limit, which only moves the memory problem into Redis.
  > **需要投递保证？** 改用 Redis Streams，消费者重连后可以从上次的 ID 继续读取，而不是调高缓冲区限制；调高限制只会把内存问题转移到 Redis 身上。

**Trade-offs.** Dropping slow shoppers is harsh but protects everyone else. Streams add storage and trimming decisions; for prices that are always re-sent in full, Pub/Sub plus a reload on reconnect is usually enough.

> **权衡。** 丢弃慢速顾客的连接很粗暴，但能保护其他所有人。Streams 会带来存储和裁剪方面的决策；对于每次都完整重发的价格来说，Pub/Sub 加上重连后的重新加载通常就够了。

</details>

## 5. Removing a sold-out SKU from a list deletes the wrong one, and a set of paused campaign IDs never matches

**从列表中移除售罄的 SKU 时删错了一个，而一个存放已暂停广告活动 ID 的集合永远匹配不上** · `Java & CS` · `Medium`

### Question · 题目

Three small bugs in an ad-sync service: `ids.remove(soldId)` on a `List<Integer>` removes a different product or throws `IndexOutOfBoundsException`; `paused.contains(campaignId)` on a `Set<Long>` is always false although the ID is in the set; and `Arrays.asList(blockedIds).contains(101)` is false for an `int[]` that contains 101.

> 一个广告同步服务里有三个小 bug：对 `List<Integer>` 调用 `ids.remove(soldId)`，结果删掉了另一个商品，或者抛出 `IndexOutOfBoundsException`；对 `Set<Long>` 调用 `paused.contains(campaignId)` 永远返回 false，尽管这个 ID 就在集合里；对一个包含 101 的 `int[]`，`Arrays.asList(blockedIds).contains(101)` 返回 false。

Explain each one and fix them.

> 逐一解释并修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Overloads pick the index.** `List` has `remove(int index)` and `remove(Object o)`. With an `int` argument, Java chooses the exact match, `remove(int)`, before considering boxing. In a local test, removing 3 from `[101, 3, 205, 7]` removed 7, the element at index 3, and `remove(205)` threw `Index 205 out of bounds for length 4`.

> **重载选中了按下标删除。** `List` 有 `remove(int index)` 和 `remove(Object o)` 两个方法。参数是 `int` 时，Java 会先选择精确匹配的 `remove(int)`，然后才考虑装箱。在本地测试中，从 `[101, 3, 205, 7]` 中移除 3，删掉的是下标为 3 的元素 7；而 `remove(205)` 抛出了 `Index 205 out of bounds for length 4`。

**Boxing to the wrong type.** `contains` and `get` take `Object`, so an `int` campaign ID is boxed to `Integer`, and `Integer.valueOf(101)` is never equal to `Long.valueOf(101)`: `equals` checks the class first. The test returned false for `Set<Long>.contains` and null for `Map<Long, String>.get`, with no compiler error.

> **装箱成了错误的类型。** `contains` 和 `get` 的参数是 `Object`，所以 `int` 类型的活动 ID 会被装箱成 `Integer`，而 `Integer.valueOf(101)` 永远不等于 `Long.valueOf(101)`：`equals` 会先比较类型。测试中 `Set<Long>.contains` 返回 false，`Map<Long, String>.get` 返回 null，编译器没有任何报错。

**A primitive array is one object.** `Arrays.asList` takes varargs of objects; an `int[]` cannot be spread into them, so it becomes a list with a single element, the array itself. The test printed size 1 and `contains(101)` false, while the same call on an `Integer[]` returned true.

> **基本类型数组是一个对象。** `Arrays.asList` 接受的是对象类型的可变参数；`int[]` 无法展开成这些参数，所以它变成了只有一个元素的列表，这个元素就是数组本身。测试输出的大小是 1，`contains(101)` 为 false；而对 `Integer[]` 做同样的调用返回 true。

**The fixes:**

> **修复方法：**

```java
List<Integer> ids = new ArrayList<>(List.of(101, 3, 205, 7));
ids.remove(Integer.valueOf(soldId));      // remove by value, not by index

Set<Long> paused = loadPausedCampaigns(); // keys are Long
long campaignId = event.campaignId();     // keep the key type identical
if (paused.contains(campaignId)) { ... }

List<Integer> blocked = Arrays.stream(blockedIds).boxed().toList();
```

- Use one ID type end to end. IDs from ad platforms often exceed the `int` range anyway, so `long` everywhere, or a small value type such as `record CampaignId(long value)`, prevents the mix.
  > 从头到尾使用同一种 ID 类型。广告平台的 ID 往往本来就会超出 `int` 的范围，所以处处使用 `long`，或者一个小的值类型（比如 `record CampaignId(long value)`），就能避免混用。
- Turn on static analysis that flags collection calls with an argument of an unrelated type; most IDEs and linters have such a check.
  > 开启静态分析，标记那些传入不相关类型参数的集合调用；大多数 IDE 和 lint 工具都有这样的检查。

**Trade-offs.** Wrapper types add a little ceremony and allocation, but they turn these silent bugs into compile errors, which is worth it for IDs that cross service boundaries.

> **权衡。** 包装类型会带来一点样板代码和内存分配，但它们能把这些悄无声息的 bug 变成编译错误；对于跨服务边界传递的 ID 来说，这是值得的。

</details>
