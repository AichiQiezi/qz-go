## 1. A feed parser keeps only a few IDs, yet memory grows by hundreds of megabytes

**feed 解析器只保留了几个 ID，内存却增长了几百 MB** · `Go` · `Senior`

### Question · 题目

A Go service downloads merchants' product feeds (often 10 MB to 100 MB each), parses them, and keeps a small index in memory: for each feed, a handful of product IDs and the feed's ETag. The index holds only a few kilobytes of data, but the service's heap grows by hundreds of megabytes over the day and the pods get OOMKilled.

> 一个 Go 服务会下载商家的商品 feed（每个通常 10 MB 到 100 MB），解析之后在内存中保存一个小索引：每个 feed 只保留少量商品 ID 和该 feed 的 ETag。这个索引里的数据只有几 KB，但服务的堆内存一天下来会增长几百 MB，pod 被 OOMKill。

The IDs are taken with `id := line[start:end]` from the downloaded `[]byte`, or with `s[i:j]` from a string built from it. Explain what is happening, how you would prove it, and how you would fix it.

> 这些 ID 是从下载的 `[]byte` 中用 `id := line[start:end]` 取出的，或者是从由它构造的字符串中用 `s[i:j]` 取出的。解释发生了什么，你会如何证明，以及如何修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

**What is happening.** A sub-slice or substring in Go shares the backing array of the original. As long as any small slice taken from a 10 MB buffer is reachable, the garbage collector must keep the whole 10 MB alive, because it cannot free part of an array. The index looks tiny, but each entry pins an entire feed. Twenty 16-byte IDs taken from twenty 10 MB buffers keep about 200 MB alive.

> **发生了什么。** 在 Go 中，子切片或子字符串与原数据共享同一个底层数组。只要从一个 10 MB 缓冲区中取出的任何一个小切片仍然可达，垃圾回收器就必须让整个 10 MB 存活，因为它无法只释放数组的一部分。索引看起来很小，但每个条目都“钉住”了一整个 feed。从二十个 10 MB 的缓冲区里各取一个 16 字节的 ID，大约会让 200 MB 一直存活。

**How to prove it.** Take a heap profile with `net/http/pprof` and look at `inuse_space`: the large allocations will be attributed to the code that downloaded or read the feed, not to the index, even though the feeds should be garbage. Comparing two profiles over time (`-base`) shows the growth coming from feed buffers that are never released.

> **如何证明。** 用 `net/http/pprof` 抓取堆 profile，查看 `inuse_space`：那些大块内存会被记在下载或读取 feed 的代码头上，而不是索引上，尽管这些 feed 本应早已成为垃圾。对比不同时间点的两份 profile（使用 `-base`），可以看到增长来自从未被释放的 feed 缓冲区。

```go
// Before: id shares the 10 MB buffer, so the buffer can never be freed.
id := string(line[start:end]) // a string conversion copies: this one is fine
key := line[start:end]        // a sub-slice: pins the whole buffer

// After: copy what you keep.
key = bytes.Clone(line[start:end])
name := strings.Clone(s[i:j]) // substrings share memory too
```

**The fix.** Copy small values you want to keep beyond the life of the big buffer: `bytes.Clone` for byte slices, `strings.Clone` for substrings. Converting `[]byte` to `string` already copies, so the bug usually comes from storing byte sub-slices or substrings of a large string. Also stream large feeds (`bufio.Scanner` or a streaming decoder) instead of reading them whole, which caps memory per feed, and reuse buffers carefully: a `sync.Pool` of large buffers only helps if nothing retains slices of them.

> **修复。** 对于需要在大缓冲区生命周期之外继续保留的小值，要复制一份：字节切片用 `bytes.Clone`，子字符串用 `strings.Clone`。把 `[]byte` 转换成 `string` 本身就会复制，所以这个 bug 通常来自保存了字节子切片，或者大字符串的子字符串。另外，对大型 feed 要流式读取（`bufio.Scanner` 或流式解码器），而不是整个读入内存，这样能限制每个 feed 的内存占用；复用缓冲区时也要小心：大缓冲区的 `sync.Pool` 只有在没有任何地方保留其切片时才有帮助。

**Guard rails.** Set `GOMEMLIMIT` somewhat below the container limit so the GC works harder before the kernel kills the pod, and alert on heap growth per hour. A soft limit helps with real peaks, but it cannot fix a leak: retained memory is still live, so the right fix is to stop retaining it.

> **防护措施。** 把 `GOMEMLIMIT` 设置得略低于容器内存上限，让 GC 在内核杀掉 pod 之前更积极地工作，并对每小时的堆增长设置告警。软限制有助于应对真实的峰值，却解决不了泄漏：被保留的内存仍然是存活的，所以正确的修复是停止保留它。

</details>

## 2. Sending webhooks to thousands of merchant endpoints that are often down

**向成千上万个经常宕机的商家端点发送 webhook** · `System Design` · `Medium`

### Question · 题目

Your platform notifies merchants' own systems about events such as `order.paid` and `product.disapproved` by POSTing to a URL each merchant configures. Some endpoints are slow, some are down for hours, and one merchant reported a forged webhook that looked like it came from you.

> 你们的平台会向每个商家配置的 URL 发送 POST 请求，通知商家自己的系统发生了 `order.paid`、`product.disapproved` 等事件。有些端点响应很慢，有些会宕机好几个小时，还有一个商家反馈说收到了一个伪造的、看起来像是你们发出的 webhook。

Design the outgoing webhook system.

> 请设计这套外发 webhook 系统。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Delivery is asynchronous and per endpoint.** The business transaction writes the event to an outbox; a dispatcher puts a delivery job per subscribed endpoint on a queue. Workers send with a short timeout. Keep each endpoint's work isolated (its own queue or a fair scheduler with per-endpoint concurrency limits), so one slow merchant cannot hold up deliveries to everyone else.

> **投递是异步的，并且按端点隔离。** 业务事务把事件写入 outbox；分发器为每个订阅了该事件的端点向队列放入一个投递任务。worker 以较短的超时时间发送请求。让每个端点的工作彼此隔离（各自的队列，或者带有按端点并发上限的公平调度器），这样一个响应慢的商家就不会拖住对其他所有人的投递。

**Retries and giving up.** Treat any 2xx as success; retry timeouts, connection errors and 5xx with exponential backoff and jitter over many hours; do not retry most 4xx. After repeated failures over a long period, mark the endpoint as failing, pause it, and email the merchant. Keep undelivered events so they can be replayed from the dashboard once the endpoint is fixed.

> **重试与放弃。** 任何 2xx 都视为成功；对超时、连接错误和 5xx 使用带抖动的指数退避，在许多个小时内持续重试；大多数 4xx 不重试。如果在很长一段时间内反复失败，就把这个端点标记为故障、暂停投递，并发邮件通知商家。保留未投递的事件，端点修好之后可以从后台重放。

**Signatures against forgery.** Sign every request with HMAC-SHA256 using a per-endpoint secret, over the timestamp and the raw body, and send both in headers. The merchant recomputes the signature, compares it in constant time, and rejects requests whose timestamp is too old, which stops replays. Support two active secrets during rotation.

> **用签名防伪造。** 用每个端点各自的密钥，对时间戳和原始请求体计算 HMAC-SHA256 签名，并把两者都放在请求头里发送。商家重新计算签名，用恒定时间的方式比较，并拒绝时间戳过旧的请求，从而阻止重放攻击。轮换密钥期间要支持两个同时有效的密钥。

```go
func sign(secret []byte, ts int64, body []byte) string {
	mac := hmac.New(sha256.New, secret)
	fmt.Fprintf(mac, "%d.", ts)
	mac.Write(body)
	return hex.EncodeToString(mac.Sum(nil))
}
// headers: X-Webhook-Timestamp: <ts>, X-Webhook-Signature: v1=<sign(...)>
```

- Duplicates and order: retries mean a merchant can receive an event more than once and out of order. Include a unique event ID and the resource's version or timestamp, and tell merchants to deduplicate by ID and ignore older versions.
  > 重复与乱序：由于重试，商家可能会多次收到同一个事件，而且顺序可能是乱的。在事件中带上唯一的事件 ID，以及资源的版本号或时间戳，并告诉商家按 ID 去重、忽略更旧的版本。
- Safety of the sender: merchants choose the URL, so block internal IP ranges and cloud metadata addresses to prevent server-side request forgery, and do not follow redirects to them.
  > 发送方自身的安全：URL 是由商家选择的，所以要屏蔽内网 IP 段和云元数据地址，防止服务端请求伪造（SSRF），也不要跟随重定向跳转到这些地址。
- Thin payloads are an option: send the event type and resource ID, and let the merchant fetch current state from the API, which avoids ordering problems and leaking data to a stale URL.
  > 轻量负载也是一种选择：只发送事件类型和资源 ID，让商家通过 API 获取当前状态，这样既避免了顺序问题，也不会把数据泄露给一个过时的 URL。

**Trade-offs.** Long retry windows improve delivery but build up backlogs during outages, so cap the backlog per endpoint. Thin payloads cost merchants an extra API call but make their handlers simpler and safer.

> **取舍。** 更长的重试窗口能提高投递成功率，但在故障期间会积压大量任务，所以要限制每个端点的积压量。轻量负载会让商家多一次 API 调用，但能让他们的处理逻辑更简单、更安全。

</details>

## 3. The dashboard's order count takes seconds on large merchants

**大商家的后台订单总数要好几秒才能显示出来** · `Database` · `Medium`

### Question · 题目

The merchant dashboard shows "Orders: 1,284,551" using `SELECT count(*) FROM orders WHERE merchant_id = $1`. For large merchants it takes several seconds and runs on every dashboard load. A teammate suggests adding an index on `merchant_id`. Will that be enough, and what are the better options?

> 商家后台用 `SELECT count(*) FROM orders WHERE merchant_id = $1` 显示“订单数：1,284,551”。对大商家来说，这条查询要好几秒，而且每次打开后台都会执行。一位同事建议在 `merchant_id` 上加索引。这样够吗？还有哪些更好的选择？

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why count is expensive in Postgres.** Because of MVCC, each transaction may see a different set of rows, so Postgres cannot keep one stored row count; it has to count visible rows. Without a suitable index that means scanning the table. With an index on `merchant_id`, it can use an index-only scan, but that only stays cheap if the visibility map is up to date (VACUUM has run recently); otherwise it still visits table pages to check visibility. Either way the work grows with the number of rows counted.

> **为什么在 Postgres 中计数很昂贵。** 由于 MVCC，每个事务可能看到不同的行集合，所以 Postgres 无法保存一个统一的行数；它必须去数可见的行。如果没有合适的索引，就意味着要扫描整张表。有了 `merchant_id` 上的索引后，它可以使用仅索引扫描，但只有在可见性映射是最新的（最近执行过 VACUUM）时才会便宜；否则它仍然要访问表页面来检查可见性。无论哪种情况，工作量都随着要数的行数增长。

**So the index helps but does not solve it.** For a merchant with a million orders, counting a million index entries on every page load is still wasteful. Decide what the number is for, then choose:

> **所以索引有帮助，但解决不了根本问题。** 对一个有一百万个订单的商家，每次加载页面都去数一百万个索引项，仍然是一种浪费。先想清楚这个数字是干什么用的，再做选择：

- Exact and real-time is rarely needed for a dashboard. A counter table updated in the same transaction as the order insert gives an exact number cheaply, but a single hot row per merchant can become a lock bottleneck under heavy write load; spread it over several rows per merchant and sum them.
  > 后台的数字很少需要既精确又实时。在插入订单的同一个事务里更新一张计数表，可以低成本地得到精确数字；但在写入量很大时，每个商家一行的热点数据可能成为锁瓶颈，可以把它分散到每个商家的若干行上，读取时再求和。
- Slightly stale is usually fine: precompute counts per merchant in a summary table or materialized view refreshed every few minutes, and show "updated 2 minutes ago".
  > 稍微过时通常也没关系：在汇总表或物化视图中预先计算每个商家的数量，每隔几分钟刷新一次，并显示“2 分钟前更新”。
- For a whole-table total, the planner's estimate in `pg_class.reltuples` is free and good enough for "about 2 million".
  > 如果只是全表的总数，`pg_class.reltuples` 中优化器的估算值是免费的，用来显示“大约 200 万”已经足够。

```sql
-- exact, cheap to read: maintained in the same transaction as the insert
UPDATE merchant_order_counts
SET n = n + 1
WHERE merchant_id = $1 AND shard = $2;   -- shard = random 0..7 to avoid one hot row

SELECT sum(n) FROM merchant_order_counts WHERE merchant_id = $1;
```

**Also fix the access pattern.** Cache the dashboard numbers briefly, and do not run expensive aggregates on every page load against the primary; send them to a replica or the analytics store.

> **同时修正访问模式。** 对后台数字做短时缓存，不要在每次加载页面时都在主库上执行昂贵的聚合；把它们放到只读副本或分析库上去。

**Trade-offs.** Counter tables add a write to every order and can drift if a code path forgets to update them, so reconcile them periodically with a real count. Summary tables are simpler but stale; choose based on whether merchants actually need the exact number right now.

> **取舍。** 计数表会让每笔订单多一次写入，而且如果某条代码路径忘了更新它，数字就会产生偏差，所以要定期用真实的计数来对账。汇总表更简单，但数据有延迟；要根据商家是否真的需要此刻的精确数字来选择。

</details>

## 4. Streaming responses arrive all at once, and connections drop after a minute

**流式响应一下子全部到达，而且连接在一分钟后断开** · `Middleware` · `Hard`

### Question · 题目

Your AI assistant streams answers to the browser with server-sent events. Locally it works: text appears word by word. Behind the production Nginx reverse proxy, the browser receives the whole answer at the end, and long-running streams (a slow agent run) are cut off after about a minute. The same proxy also serves a WebSocket endpoint for live order notifications, which fails to connect at all.

> 你们的 AI 助手通过 server-sent events 把回答以流的形式发送给浏览器。在本地一切正常：文字一个词一个词地出现。但在生产环境的 Nginx 反向代理后面，浏览器要等到最后才一次性收到整个回答，而长时间运行的流（一次很慢的 Agent 运行）大约一分钟后就被切断了。同一个代理还承载着一个用于实时订单通知的 WebSocket 端点，它则根本连不上。

Explain each problem and the configuration and application changes that fix them.

> 解释每个问题，以及能解决它们的配置和应用改动。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Everything arrives at once: proxy buffering.** By default Nginx buffers responses from the upstream and sends them to the client in larger chunks, which is good for normal pages and fatal for streaming. Turn buffering off for the streaming location (`proxy_buffering off;`), or have the application send the `X-Accel-Buffering: no` response header on streaming responses. Also check every other hop: a CDN, a load balancer or compression middleware can buffer too.

> **所有内容一次性到达：代理缓冲。** 默认情况下，Nginx 会缓冲来自上游的响应，再以较大的块发送给客户端，这对普通页面很好，对流式传输却是致命的。为流式接口所在的 location 关闭缓冲（`proxy_buffering off;`），或者让应用在流式响应中带上 `X-Accel-Buffering: no` 响应头。还要检查链路上的每一跳：CDN、负载均衡器或压缩中间件也可能做缓冲。

**Streams cut off after a minute: read timeout.** Nginx closes an upstream connection when it receives nothing for `proxy_read_timeout`, which defaults to 60 seconds. A slow agent may think for longer than that between tokens. Raise the timeout for the streaming route only, and, more importantly, have the server send a heartbeat (an SSE comment line such as `: ping`) every 15 to 30 seconds, so every proxy on the path sees traffic.

> **流在一分钟后被切断：读超时。** 当 Nginx 在 `proxy_read_timeout` 时间内没有收到上游的任何数据时，就会关闭这个上游连接，而它的默认值是 60 秒。一个很慢的 Agent 在两个 token 之间思考的时间可能会更长。只为流式路由调大这个超时，更重要的是让服务端每 15 到 30 秒发送一次心跳（比如一行 SSE 注释 `: ping`），让链路上的每个代理都能看到有流量。

```nginx
location /api/stream/ {
    proxy_pass http://app;
    proxy_http_version 1.1;
    proxy_buffering off;          # or send X-Accel-Buffering: no from the app
    proxy_read_timeout 300s;      # still send heartbeats every ~20s
}

location /ws/ {
    proxy_pass http://app;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 300s;
}
```

**WebSocket fails to connect: missing upgrade headers.** A WebSocket starts as an HTTP/1.1 request with `Upgrade: websocket` and `Connection: Upgrade`. These are hop-by-hop headers, so Nginx does not pass them to the upstream unless you set them explicitly and use HTTP/1.1 to the upstream, as above. Without them the backend sees a plain HTTP request and the handshake fails.

> **WebSocket 连不上：缺少升级相关的请求头。** WebSocket 一开始是一个带有 `Upgrade: websocket` 和 `Connection: Upgrade` 的 HTTP/1.1 请求。这些是逐跳请求头，所以除非像上面那样显式设置，并且对上游使用 HTTP/1.1，否则 Nginx 不会把它们转发给上游。缺少这些请求头，后端看到的只是一个普通的 HTTP 请求，握手就会失败。

- Clients must reconnect: SSE has built-in reconnection with `Last-Event-ID`, so give events IDs and let the server resume from them.
  > 客户端必须能重连：SSE 自带基于 `Last-Event-ID` 的重连机制，所以要给事件编号，让服务端能从那里继续。
- Deploys close long-lived connections: drain them gracefully and expect clients to reconnect to another instance.
  > 发布会关闭长连接：要优雅地排空这些连接，并预期客户端会重连到另一个实例。
- Capacity: each open stream holds a connection on every hop, so size worker connection limits for the number of concurrent streams.
  > 容量：每个打开的流都会在每一跳上占用一个连接，所以要按并发流的数量来设置 worker 的连接数上限。

**Trade-offs.** Disabling buffering and raising timeouts globally hurts normal traffic and lets stuck connections pile up, so scope these settings to streaming routes and rely on heartbeats rather than very long timeouts.

> **取舍。** 全局关闭缓冲、调大超时会损害普通流量，还会让卡住的连接越积越多，所以只对流式路由做这些设置，并依靠心跳，而不是非常长的超时。

</details>

## 5. One merchant's request runs with another merchant's ID

**某个商家的请求却带着另一个商家的 ID 在运行** · `Java & CS` · `Hard`

### Question · 题目

A Java service stores the current merchant in a `ThreadLocal` set by a request filter, so that the data layer adds the right tenant filter automatically. After a change that moved report generation onto a shared `ExecutorService`, a merchant saw rows from another merchant's report. Tests pass, and the bug is rare in production.

> 一个 Java 服务把当前商家保存在一个由请求过滤器设置的 `ThreadLocal` 里，这样数据层就能自动加上正确的租户过滤条件。在一次把报表生成迁移到共享 `ExecutorService` 上的改动之后，有个商家在报表里看到了另一个商家的数据行。测试都能通过，这个 bug 在线上也很少出现。

Explain how this happens and how to make tenant context safe.

> 解释这是怎么发生的，以及如何让租户上下文变得安全。

<details>
<summary><b>Answer · 参考答案</b></summary>

**How it happens.** A `ThreadLocal` value belongs to a thread, not to a request. Pool threads are reused, so a value set by one task is still there when the next task runs on the same thread, unless someone removes it. A report task that runs on a pool thread either sees nothing (the filter ran on the request thread, not on the pool thread) or sees whatever the previous task on that thread left behind, which can be another merchant.

> **发生的过程。** `ThreadLocal` 的值属于某个线程，而不属于某个请求。线程池里的线程会被复用，所以一个任务设置的值，在下一个任务运行在同一个线程上时依然存在，除非有人把它移除。一个运行在线程池线程上的报表任务，要么什么都看不到（过滤器是在请求线程上运行的，而不是在线程池线程上），要么看到的是这个线程上前一个任务遗留下来的值，而那可能是另一个商家的。

```java
static final ThreadLocal<String> MERCHANT = new ThreadLocal<>();
ExecutorService pool = Executors.newFixedThreadPool(1);
pool.submit(() -> MERCHANT.set("m_A")).get();
pool.submit(() -> System.out.println(MERCHANT.get())).get(); // prints m_A
```

**Fixes, from the most important.**

> **修复方法，按重要性排列。**

- Pass the tenant explicitly to work that runs elsewhere: capture it when the task is created and set it inside the task in a try/finally that always calls `remove()`. Wrap the executor so every submitted task does this automatically.
  > 对于在别处运行的工作，显式传递租户：在创建任务时捕获它，在任务内部用 try/finally 设置它，并且一定要调用 `remove()`。对执行器做一层包装，让每个提交的任务都自动这样做。
- Fail closed: if the data layer finds no tenant, it throws instead of running a query without a tenant filter.
  > 默认拒绝：如果数据层找不到租户，就抛出异常，而不是执行一条没有租户过滤条件的查询。
- Defense in depth: enforce tenancy in the database as well, for example with row-level security keyed on a session setting, so a missing or wrong filter in Java cannot return another merchant's rows.
  > 纵深防御：在数据库层也强制执行租户隔离，比如使用基于会话设置的行级安全策略，这样即使 Java 里漏掉或写错了过滤条件，也不会返回其他商家的数据行。
- Always `remove()` in the request filter's finally block too, so request threads do not leak values between requests either.
  > 在请求过滤器的 finally 块里也总是调用 `remove()`，这样请求线程之间也不会互相泄漏值。

```java
Runnable withTenant(String merchant, Runnable task) {
    return () -> {
        MERCHANT.set(merchant);
        try { task.run(); } finally { MERCHANT.remove(); }
    };
}
```

**Beyond ThreadLocal.** The same problem appears with `CompletableFuture` async stages, reactive pipelines and virtual threads created per task. Recent JDKs add scoped values, which bind a value for a well-defined block of code and are safer for this pattern; frameworks that propagate context across threads are another option. The deeper lesson is that implicit context must never be the only thing standing between a tenant and another tenant's data.

> **ThreadLocal 之外。** 同样的问题也会出现在 `CompletableFuture` 的异步阶段、响应式流水线，以及按任务创建的虚拟线程中。较新的 JDK 增加了 scoped values（作用域值），它把一个值绑定到一段界限分明的代码上，用于这种模式更安全；能够跨线程传递上下文的框架也是一种选择。更深层的教训是：隐式上下文绝不能成为隔开一个租户与另一个租户数据的唯一屏障。

**Trade-offs.** Explicit parameters are more verbose but impossible to forget silently; implicit context is convenient but needs wrappers, fail-closed checks and database-level enforcement to be safe in a multi-tenant system.

> **取舍。** 显式传参更啰嗦，但不可能悄无声息地被遗忘；隐式上下文很方便，但在多租户系统里，需要包装器、默认拒绝的检查和数据库层的强制隔离才能保证安全。

</details>
