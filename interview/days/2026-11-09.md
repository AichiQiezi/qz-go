## 1. Calls to an ad platform start failing with 401 after the platform moves its API to a new host behind a redirect

**广告平台把 API 迁到一个新主机并加上重定向之后，调用开始返回 401** · `Go` · `Medium`

### Question · 题目

A Go service syncs catalogs to an ad platform with `http.DefaultClient`, setting `Authorization: Bearer <token>` on each request. The platform announces a new API host and redirects the old one with `301 Moved Permanently`. Overnight every call returns 401, although the token is valid. Engineers also notice that `POST /v1/catalog` requests show up on the new host as `GET` with no body.

> 一个 Go 服务使用 `http.DefaultClient` 向广告平台同步商品目录，每个请求都设置 `Authorization: Bearer <token>`。平台宣布启用新的 API 主机，并用 `301 Moved Permanently` 把旧主机重定向过去。一夜之间所有调用都返回 401，尽管令牌是有效的。工程师还发现，`POST /v1/catalog` 请求到了新主机上变成了不带请求体的 `GET`。

Explain both symptoms and fix the client.

> 解释这两个现象，并修复这个客户端。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why the token disappears.** Go's `http.Client` follows redirects automatically, but it does not forward sensitive headers such as `Authorization` and `Cookie` to a host that is not the same domain or a subdomain of the original. This protects credentials from being sent wherever a server points them. In a local test, a redirect to a different hostname dropped the header and the new host answered 401; a redirect on the same host kept it.

> **为什么令牌丢了。** Go 的 `http.Client` 会自动跟随重定向，但不会把 `Authorization`、`Cookie` 这类敏感头转发给一个与原主机不同、也不是其子域名的主机。这样可以防止凭证被发送到服务器指向的任意地方。在本地测试中，重定向到不同的主机名时这个头被丢弃，新主机返回了 401；而在同一主机内重定向时，这个头被保留了。

**Why POST became GET.** For `301`, `302` and `303`, the client follows a `POST` with a `GET` and no body, as browsers historically did. Only `307` and `308` keep the method and body. The test showed a `POST` arriving as `GET` after a 301, and staying `POST` after a 308.

> **为什么 POST 变成了 GET。** 对于 `301`、`302` 和 `303`，客户端会像浏览器一直以来那样，用不带请求体的 `GET` 去跟随一个 `POST`。只有 `307` 和 `308` 会保留方法和请求体。测试显示，经过 301 之后 `POST` 变成了 `GET`，而经过 308 之后仍然是 `POST`。

**Fix.** Configure the new base URL explicitly instead of relying on redirects, and make unexpected redirects visible rather than silently followed.

> **修复。** 显式配置新的基础 URL，而不是依赖重定向，并让意外的重定向可见，而不是被悄悄跟随。

```go
var adClient = &http.Client{
	Timeout: 30 * time.Second,
	CheckRedirect: func(req *http.Request, via []*http.Request) error {
		// Surface the 3xx to the caller instead of following it.
		return http.ErrUseLastResponse
	},
}

func checkStatus(resp *http.Response) error {
	if resp.StatusCode >= 300 && resp.StatusCode < 400 {
		return fmt.Errorf("unexpected redirect to %s: update the base URL",
			resp.Header.Get("Location"))
	}
	return nil
}
```

- **Alert on redirects.** A 3xx from an API you call is a configuration change; log the `Location` and page someone instead of retrying.
  > **对重定向发出告警。** 你调用的 API 返回 3xx 意味着配置发生了变化；记录 `Location` 并通知相关人员，而不是重试。
- **Do not copy the token back yourself** in `CheckRedirect` for any host; if you must follow, allow only an explicit list of trusted hosts.
  > **不要自己在 `CheckRedirect` 里把令牌重新加回去**，不论是哪个主机；如果必须跟随重定向，只允许一份明确的可信主机列表。
- **Do not use `http.DefaultClient` in production.** It has no timeout, and it is shared by every library in the process.
  > **不要在生产环境中使用 `http.DefaultClient`。** 它没有超时，并且被进程中的所有库共享。

**Trade-offs.** Refusing redirects means a platform migration needs a config change on your side, but it turns a silent 401 storm or a lost write into one clear error. Following redirects is convenient for downloading files from CDNs, so use a separate client with different rules for that.

> **取舍。** 拒绝重定向意味着平台迁移时你这边需要改配置，但它把一场悄无声息的 401 风暴或一次丢失的写入，变成了一个清晰的错误。跟随重定向在从 CDN 下载文件时很方便，所以为那种场景使用另一个规则不同的客户端。

</details>

## 2. Merchants want custom reports over two years of orders and ad spend: designing analytics that never touch the OLTP database

**商家想基于两年的订单和广告花费自定义报表：设计一套完全不碰 OLTP 数据库的分析系统** · `System Design` · `Hard`

### Question · 题目

Merchants ask for a report builder: pick dimensions such as day, country, product and ad campaign, pick metrics such as revenue, orders, ad spend and ROAS, filter, and export. Today the few built-in reports run SQL against the Postgres primary, and a large merchant's "last 24 months by product" report has slowed checkout for everyone.

> 商家希望有一个报表构建器：可以选择日期、国家、商品和广告系列等维度，选择收入、订单数、广告花费和 ROAS 等指标，进行筛选并导出。目前少数几个内置报表直接对 Postgres 主库执行 SQL，而一个大商家的「过去 24 个月按商品统计」报表已经拖慢了所有人的结账流程。

Design the analytics system.

> 设计这个分析系统。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Separate the workloads.** Checkout needs short transactions on a few rows; reports scan millions of rows and aggregate. Run them on different systems: stream changes out of Postgres with change data capture, and load them into a columnar analytics store that is built for scans and aggregations.

> **把两类负载分开。** 结账需要针对少量行的短事务；报表则要扫描数百万行并做聚合。让它们运行在不同的系统上：用变更数据捕获把变化从 Postgres 流式导出，并加载到一个专为扫描和聚合设计的列式分析存储中。

- **Model facts and dimensions.** Fact tables for order lines and daily ad spend, keyed by tenant, date and IDs; dimension tables for products, campaigns and countries. Store money in the order's currency plus a converted reporting currency with the rate used.
  > **建模事实表和维度表。** 订单行和每日广告花费作为事实表，以租户、日期和各类 ID 作为键；商品、广告系列和国家作为维度表。金额既存订单的原始币种，也存换算后的报表币种，并记录所用的汇率。
- **Partition by tenant and date.** Every query is for one merchant and a time range, so the store must prune everything else before reading.
  > **按租户和日期分区。** 每个查询都只针对一个商家和一个时间范围，所以存储系统必须在读取之前就把其他数据全部剪掉。
- **Pre-aggregate the common shapes.** Daily rollups by product and by campaign answer most reports cheaply; fall back to raw facts only for unusual combinations.
  > **对常见形态进行预聚合。** 按商品和按广告系列的每日汇总能以很低的成本回答大部分报表；只有不常见的组合才回退到原始事实表。
- **Join orders to ad spend carefully.** Spend comes from the platforms at campaign and day level and keeps changing for days; attribute revenue with your own rules and label the attribution model in the report.
  > **谨慎地把订单与广告花费关联起来。** 花费数据来自各平台，粒度是广告系列和天，并且在之后几天内还会不断变化；用你自己的规则归因收入，并在报表中标明所用的归因模型。

```text
Postgres --CDC--> stream --> loader --> columnar store (facts, rollups)
ad platforms --nightly re-fetch--> spend facts --^
report API --> query builder (tenant filter always added) --> store
          \-> async export job --> file in object storage --> link
```

**Protect the system.** The query builder generates SQL from a whitelist of dimensions and metrics and always adds the tenant filter, so merchants never write SQL. Each tenant gets limits on concurrency, scanned rows and query time; large exports run as background jobs that write a file and send a link.

> **保护系统。** 查询构建器从一份维度和指标白名单生成 SQL，并始终加上租户过滤条件，所以商家永远不会自己写 SQL。每个租户在并发数、扫描行数和查询时间上都有限制；大型导出以后台任务的形式运行，生成文件后发送链接。

**Freshness and correctness.** Show when the data was last updated. Handle late updates such as refunds and restated ad spend by upserting facts keyed on their natural keys, and reconcile daily totals against the source to catch a broken pipeline.

> **新鲜度与正确性。** 显示数据的最后更新时间。对退款、广告花费被修正之类的延迟更新，按自然键对事实表执行 upsert；并每天把汇总值与数据源对账，以发现损坏的流水线。

**Trade-offs.** A separate store adds a pipeline to operate and minutes of lag, but it removes reports from the checkout path entirely. Read replicas are a cheaper first step but still row-oriented and can lag under heavy scans. Rollups make reports fast but must be rebuilt when definitions change, so version metric definitions and keep raw facts.

> **取舍。** 独立的存储增加了一条需要运维的流水线和几分钟的延迟，但它把报表彻底移出了结账路径。只读副本是更便宜的第一步，但它仍然是行式存储，而且在大量扫描下可能出现延迟。汇总表让报表变快，但在指标定义变化时必须重建，所以要对指标定义做版本管理，并保留原始事实数据。

</details>

## 3. Two accounts for the same email, and login lookups scan the whole table: case-insensitive emails in Postgres

**同一个邮箱出现了两个账户，登录查询还在扫全表：Postgres 中不区分大小写的邮箱** · `Database` · `Medium`

### Question · 题目

The `merchant_users` table has `email text UNIQUE`. Support finds merchants with two accounts, `Alice@Example.com` and `alice@example.com`, created by different sign-up flows. To fix login, a developer changes the lookup to `WHERE lower(email) = lower($1)`, and login latency jumps under load.

> `merchant_users` 表上有 `email text UNIQUE`。客服发现有些商家拥有两个账户，`Alice@Example.com` 和 `alice@example.com`，分别由不同的注册流程创建。为了修复登录，一位开发者把查询改成了 `WHERE lower(email) = lower($1)`，结果在高负载下登录延迟大幅上升。

Explain both problems and fix them properly.

> 解释这两个问题，并正确地修复它们。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why duplicates got in.** A unique constraint on `text` compares exact values, and `Alice@Example.com` and `alice@example.com` are different strings. In a local test both inserts succeeded under the plain unique constraint.

> **为什么会出现重复。** `text` 上的唯一约束比较的是精确值，而 `Alice@Example.com` 和 `alice@example.com` 是不同的字符串。在本地测试中，在普通唯一约束下这两条插入都成功了。

**Why the new lookup is slow.** The index is on `email`, but the query filters on `lower(email)`, an expression the index does not contain. With 500,000 rows the test plan was a parallel sequential scan taking about 78 ms; `ILIKE` also scanned the table.

> **为什么新的查询很慢。** 索引建在 `email` 上，而查询过滤的是 `lower(email)`，这个表达式并不在索引中。在 50 万行数据下，测试的执行计划是并行顺序扫描，耗时约 78 ms；`ILIKE` 同样会扫描整张表。

**Fix: one unique expression index.** It enforces case-insensitive uniqueness and serves the lookup. In the test, the same query became an index scan of well under a millisecond, and inserting `ALICE@example.com` failed with a duplicate-key error.

> **修复：一个唯一的表达式索引。** 它既能强制不区分大小写的唯一性，又能支撑查询。在测试中，同样的查询变成了耗时远低于一毫秒的索引扫描，而插入 `ALICE@example.com` 则因重复键错误而失败。

```sql
-- clean up existing duplicates first, or the index build fails
CREATE UNIQUE INDEX CONCURRENTLY merchant_users_email_lower
    ON merchant_users (lower(email));

SELECT id FROM merchant_users WHERE lower(email) = lower($1);
```

- **Merge duplicates before building.** The test showed the unique index build fails while duplicates exist; decide which account survives and move its stores, sessions and tokens.
  > **建索引之前先合并重复账户。** 测试表明，存在重复时唯一索引会创建失败；要决定保留哪个账户，并迁移它的店铺、会话和令牌。
- **Query with the same expression.** The index is used only when the query says `lower(email)` exactly as indexed; normalize in one repository function.
  > **查询时使用相同的表达式。** 只有当查询写的是与索引完全相同的 `lower(email)` 时，索引才会被使用；把规范化集中在一个数据访问函数中。
- **Consider `citext`.** The `citext` extension makes comparisons case-insensitive by type; in the test its unique constraint rejected `bob@x.com` after `Bob@X.com`, and equality matched any case.
  > **考虑 `citext`。** `citext` 扩展通过类型让比较不区分大小写；在测试中，插入 `Bob@X.com` 之后，它的唯一约束拒绝了 `bob@x.com`，而相等比较能匹配任意大小写。

**Trade-offs.** Lower-casing is simple and covers most cases, but it is not full Unicode case folding, and the local part of an email is technically case-sensitive, although almost no provider treats it that way. Keep the address as the user typed it for display and sending, and use the normalized form only for identity and uniqueness.

> **取舍。** 转成小写很简单，能覆盖大多数情况，但它并不是完整的 Unicode 大小写折叠；而且严格来说，邮箱地址的本地部分是区分大小写的，尽管几乎没有邮件服务商这样处理。保留用户输入的原始地址用于显示和发信，只把规范化后的形式用于身份识别和唯一性约束。

</details>

## 4. A Redis cleanup job stops after the first empty SCAN page and leaves most expired sessions behind

**Redis 清理任务在 SCAN 第一次返回空页后就停了，留下了大部分过期会话** · `Middleware` · `Hard`

### Question · 题目

Old storefront sessions were written without a TTL, so a nightly job deletes them. It replaced `KEYS sess:old:*` with `SCAN` to avoid blocking Redis, but it stops as soon as a call returns no keys. Each night it deletes a handful, memory keeps growing, and on some nights the job logs that it deleted the same key twice.

> 旧的店铺会话在写入时没有设置 TTL，所以由一个夜间任务来删除它们。为了避免阻塞 Redis，它用 `SCAN` 替换了 `KEYS sess:old:*`，但只要某次调用没有返回任何键，它就停止。每天晚上它只删掉寥寥几个，内存持续增长，而且有些晚上任务日志显示同一个键被删除了两次。

```text
cursor = 0
loop:
    cursor, keys = SCAN cursor MATCH sess:old:* COUNT 100
    if keys is empty: break        # bug
    UNLINK keys...
```

Explain how SCAN works and fix the job.

> 解释 SCAN 的工作方式，并修复这个任务。

<details>
<summary><b>Answer · 参考答案</b></summary>

**SCAN walks the keyspace, not the matches.** Each call looks at roughly `COUNT` slots of the whole keyspace and then applies `MATCH` to what it found. When matching keys are rare, most calls return nothing even though many remain. The iteration is finished only when the server returns cursor `0`.

> **SCAN 遍历的是整个键空间，而不是匹配项。** 每次调用大约查看整个键空间中 `COUNT` 个槽位，然后对找到的内容应用 `MATCH`。当匹配的键很少时，即使还剩很多，大部分调用也会什么都不返回。只有当服务器返回游标 `0` 时，迭代才算结束。

**What the test showed.** With 200,000 cache keys and 300 matching sessions, the first five calls each returned zero keys with a non-zero cursor. A full iteration took 1,996 calls, 1,725 of them empty, and found all 300.

> **测试的结果。** 在 20 万个缓存键、300 个匹配的会话键的情况下，前五次调用都返回零个键，游标却不为零。一次完整的迭代用了 1,996 次调用，其中 1,725 次为空，最终找到了全部 300 个键。

**What SCAN guarantees.** A key present for the whole iteration is returned at least once, but it may be returned more than once, for example when the hash table resizes. Keys added or removed during the scan may or may not appear. So deletion must be idempotent: `UNLINK` of a missing key simply does nothing.

> **SCAN 保证什么。** 在整个迭代期间一直存在的键至少会被返回一次，但可能被返回不止一次，例如在哈希表扩缩容时。迭代过程中新增或删除的键可能出现，也可能不出现。所以删除必须是幂等的：对不存在的键执行 `UNLINK` 什么也不会发生。

```go
var cursor uint64
for {
	keys, next, err := rdb.Scan(ctx, cursor, "sess:old:*", 1000).Result()
	if err != nil {
		return err
	}
	if len(keys) > 0 {
		if err := rdb.Unlink(ctx, keys...).Err(); err != nil { // idempotent
			return err
		}
	}
	cursor = next
	if cursor == 0 { // the only end condition
		return nil
	}
}
```

- **Pace it.** Use a larger `COUNT` to cut round trips and a short sleep between batches so the scan does not dominate Redis CPU at night.
  > **控制节奏。** 使用更大的 `COUNT` 来减少往返次数，并在批次之间短暂休眠，这样扫描就不会在夜里占满 Redis 的 CPU。
- **In a cluster, scan every primary.** A cursor belongs to one node; iterate each master separately.
  > **在集群中，要扫描每一个主节点。** 一个游标只属于一个节点；要分别遍历每个主节点。
- **Fix the cause.** Write sessions with `EX` so they expire on their own; then the job only drains the backlog once.
  > **修复根因。** 写入会话时带上 `EX`，让它们自行过期；这样清理任务只需要把积压的数据清理一次。

**Trade-offs.** SCAN never blocks the way `KEYS` does, but a full pass over a large keyspace takes many calls and gives only weak guarantees. If you often need "all keys of a kind", keep them in a set or sorted set as an index, at the cost of keeping that index in sync, or give each kind its own logical database or instance.

> **取舍。** SCAN 永远不会像 `KEYS` 那样阻塞，但对大型键空间的一次完整遍历需要大量调用，而且只提供很弱的保证。如果你经常需要「某一类的所有键」，就用一个集合或有序集合作为索引来保存它们，代价是要保持这个索引同步；或者为每一类键使用单独的逻辑数据库或实例。

</details>

## 5. A Bloom filter deduplicates conversion events, and some real purchases are silently dropped

**用布隆过滤器给转化事件去重，结果有些真实的购买被悄悄丢掉了** · `Java & CS` · `Senior`

### Question · 题目

To avoid sending the same conversion to ad platforms twice, a Java service checks each `event_id` against an in-memory Bloom filter sized for one million events at a 1% false-positive rate, and skips events the filter says it has seen. The filter is never reset. Months later, marketing finds that reported conversions are well below orders, and the gap keeps growing.

> 为了避免把同一次转化重复发送给广告平台，一个 Java 服务用一个内存中的布隆过滤器检查每个 `event_id`，过滤器按一百万个事件、1% 的误判率来设计，凡是过滤器认为见过的事件都会被跳过。这个过滤器从不重置。几个月后，市场团队发现上报的转化数远低于订单数，而且差距还在不断扩大。

As the senior engineer, explain what happened, size the structure correctly and redesign deduplication.

> 作为资深工程师，解释发生了什么，正确地估算这个数据结构的大小，并重新设计去重方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**What a Bloom filter promises.** It answers "definitely not seen" or "maybe seen". It never gives false negatives, but it gives false positives, and here a false positive means a real purchase is skipped. Using it as the only gate turns its error rate into lost revenue data.

> **布隆过滤器承诺了什么。** 它的回答要么是「肯定没见过」，要么是「可能见过」。它从不出现漏判，但会出现误判，而在这里，一次误判就意味着一笔真实的购买被跳过。把它当作唯一的关卡，就是把它的误判率变成了丢失的收入数据。

**Why it got worse.** The false-positive rate depends on how full the filter is. For n items, m bits and k hash functions it is about `(1 - e^(-kn/m))^k`. Sized for one million items at 1%, the optimum is about 9.6 million bits (1.1 MB) and k = 7. In a local Java test the measured rate was 0.99% at one million inserts, 15.6% at two million, 43% at three million and 68% at four million, matching the formula.

> **为什么情况越来越糟。** 误判率取决于过滤器被填满的程度。对于 n 个元素、m 个比特和 k 个哈希函数，误判率约为 `(1 - e^(-kn/m))^k`。按一百万个元素、1% 误判率来设计，最优值约为 960 万比特（1.1 MB），k = 7。在本地 Java 测试中，测得的误判率在插入一百万个时为 0.99%，两百万个时为 15.6%，三百万个时为 43%，四百万个时为 68%，与公式一致。

```java
static long bitsFor(long n, double p) {         // m = -n ln p / (ln 2)^2
    return (long) Math.ceil(-n * Math.log(p) / (Math.log(2) * Math.log(2)));
}
static int hashesFor(long m, long n) {          // k = (m / n) ln 2
    return Math.max(1, (int) Math.round((double) m / n * Math.log(2)));
}
```

**Redesign: Bloom as a pre-check, exact store as the decision.** Only "definitely not seen" is trustworthy, so use the filter to skip the expensive check in that case, and confirm every "maybe" against an exact record, such as a unique key on `event_id` in the database or a `SET NX` with a TTL equal to the deduplication window.

> **重新设计：布隆过滤器做预检查，精确存储做决定。** 只有「肯定没见过」是可信的，所以在这种情况下用过滤器跳过昂贵的检查；对每一个「可能见过」，都要用精确记录来确认，例如数据库中 `event_id` 上的唯一键，或者一个 TTL 等于去重窗口的 `SET NX`。

- **Bound the population.** Duplicates arrive within hours or days, not forever. Rotate time-windowed filters, for example one per day, check the last few, and drop old ones, so n stays within the sized capacity.
  > **限定元素的总量。** 重复事件会在几小时或几天内到达，而不是永远。轮换按时间窗口划分的过滤器，例如每天一个，检查最近几个并丢弃旧的，这样 n 就始终在设计容量之内。
- **Monitor fill ratio.** Export the share of bits set and the measured "maybe" rate; alert before they pass the design point.
  > **监控填充率。** 导出已置位比特的比例和实测的「可能见过」比例；在它们超过设计值之前发出告警。
- **Use stable IDs downstream too.** Ad platforms can deduplicate by event ID, so sending a rare duplicate is far cheaper than dropping a purchase.
  > **在下游也使用稳定的 ID。** 广告平台可以按事件 ID 去重，所以偶尔发送一次重复，远比丢掉一笔购买的代价小。
- **Make it survive restarts.** An in-memory filter is empty after a deploy; that is safe only because the exact store still decides.
  > **让它在重启后依然可用。** 内存中的过滤器在部署之后就是空的；之所以安全，只是因为最终仍由精确存储来做决定。

**Trade-offs.** The exact store costs a lookup per "maybe" and storage for the window, but it removes silent data loss. The filter saves memory and lookups only when most events are new; if traffic is small, the exact store alone is simpler. Choose the error direction deliberately: for revenue signals, an occasional duplicate the platform can absorb is better than a dropped event nobody sees.

> **取舍。** 精确存储需要为每个「可能见过」付出一次查询，并为去重窗口付出存储空间，但它消除了悄无声息的数据丢失。只有当大部分事件都是新事件时，过滤器才能节省内存和查询；如果流量不大，只用精确存储会更简单。要有意识地选择错误的方向：对于收入信号，偶尔出现一次平台能够消化的重复，要好过一个没人察觉的丢失事件。

</details>
