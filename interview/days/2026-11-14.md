## 1. The product API hangs under load while the database is almost idle, and only some endpoints recover on their own

**商品 API 在负载下卡死，而数据库几乎是空闲的，只有部分接口能自己恢复** · `Go` · `Hard`

### Question · 题目

A Go product service uses `database/sql` with the pgx driver and `SetMaxOpenConns(20)`. A new helper returns a product's first active variant:

> 一个 Go 商品服务使用 `database/sql` 和 pgx 驱动，设置了 `SetMaxOpenConns(20)`。一个新的辅助函数用来返回某个商品的第一个有效变体：

```go
func firstActiveVariant(ctx context.Context, db *sql.DB, productID int64) (string, error) {
	rows, err := db.QueryContext(ctx,
		`SELECT sku, active FROM variants WHERE product_id = $1 ORDER BY position`, productID)
	if err != nil {
		return "", err
	}
	for rows.Next() {
		var sku string
		var active bool
		if err := rows.Scan(&sku, &active); err != nil {
			return "", err
		}
		if active {
			return sku, nil
		}
	}
	return "", ErrNoActiveVariant
}
```

After the deploy, requests start to hang under load while the database server itself is almost idle. Request handlers have a 2-second deadline; they fail with `context deadline exceeded` for a while and then recover. A nightly feed job that calls the same helper with `context.Background()` hangs until the pod is restarted. Explain both behaviors and fix the code.

> 上线之后，请求在负载下开始卡住，而数据库服务器本身几乎是空闲的。请求处理函数都有 2 秒的截止时间；它们会有一段时间以 `context deadline exceeded` 失败，然后又恢复正常。一个夜间生成商品 feed 的任务用 `context.Background()` 调用同一个函数，结果一直卡住，直到 Pod 被重启。解释这两种现象，并修复代码。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why it hangs.** A `*sql.Rows` keeps its connection checked out until `Close` is called or `Next` has returned false. Returning early on the first active variant does neither, so every call that finds a match leaks one connection. After 20 such calls the pool is empty and every other query in the service waits for a connection that never comes back. The database is idle because the queries never reach it. In a local test with a pool of 3, the fourth call waited until its deadline while `db.Stats()` showed 3 connections in use and a growing wait count.

> **为什么会卡住。** `*sql.Rows` 会一直占用它的连接，直到调用了 `Close`，或者 `Next` 返回了 false。在找到第一个有效变体时提前返回，这两件事都没有发生，所以每一次找到匹配的调用都会泄漏一个连接。这样的调用发生 20 次之后，连接池就空了，服务里其他所有查询都在等一个永远不会回来的连接。数据库之所以空闲，是因为这些查询根本到不了它那里。在本地用大小为 3 的连接池测试时，第四次调用一直等到截止时间，而 `db.Stats()` 显示有 3 个连接在使用中，等待次数还在不断增加。

**Why some endpoints recover.** `database/sql` closes a `Rows` when the context of its query ends. Leaks from requests with a deadline are released when that deadline passes, so the pool drains and refills in waves. Leaks from `context.Background()` are never released. In the local test, calls with one-second deadlines got their connections back after about a second, while background calls held them for good.

> **为什么有些接口能恢复。** 当查询的 context 结束时，`database/sql` 会关闭对应的 `Rows`。来自带截止时间的请求的泄漏，会在截止时间过去后被释放，所以连接池会一阵阵地被耗尽、又被补满。而来自 `context.Background()` 的泄漏永远不会被释放。在本地测试中，带 1 秒截止时间的调用大约一秒后就拿回了连接，而后台调用则会一直占着连接不放。

**The fix.** Close the rows on every path, and check `rows.Err()` after the loop, because an error can end iteration early and look like "no rows". For a single row, `QueryRowContext` closes itself, and adding `LIMIT 1` with the `active` filter to the SQL is simpler still.

> **修复方法。** 在每条返回路径上都关闭 rows，并在循环结束后检查 `rows.Err()`，因为错误可能提前结束迭代，看起来就像「没有数据」。如果只需要一行，`QueryRowContext` 会自己关闭；把 `active` 条件和 `LIMIT 1` 直接写进 SQL 还要更简单。

```go
	rows, err := db.QueryContext(ctx, query, productID)
	if err != nil {
		return "", err
	}
	defer rows.Close() // every return path gives the connection back
	for rows.Next() {
		// ... scan, return early on a match ...
	}
	if err := rows.Err(); err != nil { // an error that ended the loop early
		return "", err
	}
	return "", ErrNoActiveVariant
```

**Catch it next time.** Export `db.Stats()` (connections in use, wait count, wait duration) as metrics and alert when waits grow while the database is quiet. Linters can flag unclosed rows in review. Give every database call a deadline, so a leak degrades service instead of freezing it.

> **下次及早发现。** 把 `db.Stats()`（使用中的连接数、等待次数、等待时长）导出为监控指标，在数据库很安静而等待却在增长时告警。静态检查工具可以在代码审查时发现未关闭的 rows。给每次数据库调用都加上截止时间，这样泄漏只会让服务变差，而不会让它彻底卡死。

**Trade-offs.** A bigger pool only delays the hang and can overload the database when the leak is fixed elsewhere. Deadlines everywhere mean choosing a timeout for batch jobs too, but an explicit long timeout is still better than none.

> **权衡。** 加大连接池只会推迟卡死的时间，而且在别处的泄漏修好之后，过大的连接池可能会压垮数据库。到处加截止时间意味着连批处理任务也要选一个超时值，但明确的长超时也总比没有超时好。

</details>

## 2. One app's bulk sync slows the Admin API for everyone: rate limiting third-party apps on your own platform

**一个应用的批量同步拖慢了所有人的 Admin API：为自己平台上的第三方应用做限流** · `System Design` · `Senior`

### Question · 题目

The platform opened its Admin API to third-party apps: about 1,500 apps installed across 200,000 stores. Today there is one global limit per app. Problems: a large app syncing a huge store slows the API for every store on the same database shard; an app that is fine on 50,000 small stores gets throttled because of one large store; apps retry 429s immediately; and the new GraphQL endpoint lets one query read 250 products with all their variants, so request counts say little about load.

> 平台向第三方应用开放了 Admin API：大约 1,500 个应用，安装在 200,000 家店铺上。目前每个应用只有一个全局限额。存在的问题：一个大应用在同步一家超大店铺时，会拖慢同一数据库分片上所有店铺的 API；一个在 50,000 家小店上都运行正常的应用，会因为某一家大店而被限流；应用遇到 429 会立即重试；而新的 GraphQL 端点允许一次查询读取 250 个商品及其全部变体，所以请求次数几乎反映不了真实负载。

Design the rate limiting.

> 设计这套限流方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why one global limit per app fails.** Load lands on a store's shard, not on an app, so a per-app limit lets one heavy store hurt its neighbours while punishing the app everywhere else. Counting requests ignores that one query can cost a thousand times more than another.

> **为什么每个应用一个全局限额行不通。** 负载落在店铺所在的分片上，而不是落在应用上，所以按应用限额既放任一家重负载店铺拖累它的邻居，又在其他所有地方惩罚这个应用。按请求次数计数，也忽略了一次查询的开销可能是另一次的上千倍。

**The design.**

> **设计方案。**

- **Bucket per app and store.** The main limit is a token bucket per (app, store): a capacity for bursts and a steady refill rate. An app's traffic on one store no longer affects its other installations.
  > **按「应用 + 店铺」划分的桶。** 主要的限额是每个（应用，店铺）组合一个令牌桶：有一个应对突发的容量，以及一个稳定的补充速率。应用在某一家店铺上的流量，不再影响它在其他店铺上的安装。
- **Ceilings above it.** Add a total per store across all apps, sized to what one shard can take, and a platform-wide load-shedding switch.
  > **更上层的上限。** 再加一个跨所有应用的单店铺总上限（按一个分片的承受能力来定），以及一个全平台的降载开关。
- **Charge by cost, not by request.** For REST, weight endpoints by the work they do. For GraphQL, compute a query's cost before running it from the fields and page sizes it asks for, reject queries above a maximum, and refund the difference when the actual cost is lower.
  > **按开销计费，而不是按请求计费。** 对于 REST，按端点实际做的工作给它们加权。对于 GraphQL，在执行之前根据请求的字段和分页大小计算查询的开销，拒绝超过上限的查询，并在实际开销更低时退还差额。
- **Tell clients the rules.** Return the remaining budget in response headers, send 429 with `Retry-After`, and ship SDKs that back off with jitter.
  > **把规则告诉客户端。** 在响应头里返回剩余额度，返回 429 时带上 `Retry-After`，并提供会带抖动退避的 SDK。
- **A separate path for bulk work.** Full syncs go through asynchronous bulk export and import jobs that run at the platform's pace, and webhooks replace polling, so interactive limits stay small.
  > **批量工作走单独的通道。** 全量同步通过异步的批量导出和导入任务完成，按平台自己的节奏运行；用 webhook 取代轮询，这样交互式请求的限额就可以保持较小。

**Enforcement.** Check limits at the gateway with an atomic script in Redis, so concurrent requests cannot both spend the last tokens. Locally, with a capacity of 40 and a refill of 2 per second, it allowed four requests of cost 10, then returned a 5-second wait:

> **执行方式。** 在网关上用 Redis 里的原子脚本检查限额，这样并发请求就不可能同时花掉最后的那些令牌。在本地测试中，容量为 40、每秒补充 2 个令牌时，它允许了四次开销为 10 的请求，随后返回了 5 秒的等待时间：

```lua
-- KEYS[1]: bucket for one app on one store
-- ARGV: capacity, refill per second, cost of this request
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t = redis.call('TIME')
local now = tonumber(t[1]) + tonumber(t[2]) / 1e6
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = math.min(cap, (tonumber(b[1]) or cap) + (now - (tonumber(b[2]) or now)) * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) + 1)
if allowed then return {1, 0} end
return {0, math.ceil((cost - tokens) / rate)} -- seconds for Retry-After
```

**Trade-offs.** Per-(app, store) buckets mean many keys, but each one is tiny and expires when idle. If Redis is down, failing open protects merchants' apps but not the shards, so fail open with a conservative local limit per gateway.

> **权衡。** 按（应用，店铺）划分的桶意味着键的数量很多，但每个键都很小，空闲时就会过期。如果 Redis 宕机，放行（fail open）能保护商家使用的应用，却保护不了分片，所以放行时要配合每个网关本地的保守限额。

</details>

## 3. A SKU prefix search uses the index in staging and scans 30 million rows in production

**SKU 前缀搜索在预发环境走索引，在生产环境却扫描了 3000 万行** · `Database` · `Medium`

### Question · 题目

The merchant admin has a SKU search box that runs `SELECT id FROM products WHERE sku LIKE $1 || '%'` against a btree index on `sku`. In staging the plan is an index scan. In production, on 30 million products, it is a sequential scan, and the request times out. The staging database was created with the `C` locale; production was created with `en_US.UTF-8`. A newer version of the box uses `ILIKE` so merchants can type lowercase, and it is slow everywhere.

> 商家后台有一个 SKU 搜索框，执行的是 `SELECT id FROM products WHERE sku LIKE $1 || '%'`，`sku` 上有一个 btree 索引。在预发环境中，执行计划是索引扫描。在生产环境的 3000 万个商品上，它却是全表顺序扫描，请求超时。预发数据库是用 `C` locale 创建的；生产数据库是用 `en_US.UTF-8` 创建的。新版的搜索框改用了 `ILIKE`，方便商家输入小写，结果在哪里都很慢。

Explain the difference and fix the search.

> 解释这种差异，并修复这个搜索。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why the plans differ.** Postgres can turn `LIKE 'AB12%'` into an index range only when the index sorts by plain byte order: the column's collation is `C` or `POSIX`, or the index uses the `text_pattern_ops` operator class. A linguistic collation such as `en_US.UTF-8` sorts by language rules, so a prefix is not one contiguous range in the index. In a local test on Postgres 16, a column with an ICU English collation got a sequential scan, and so did the database's default `C.UTF-8` collation; only a `C` column or a `text_pattern_ops` index produced the range condition. The same test showed the two orders really differ: `SKU_1` sorts before `sku-1` in English order and after it in byte order.

> **为什么执行计划不同。** 只有当索引按纯字节顺序排序时，Postgres 才能把 `LIKE 'AB12%'` 转换成索引范围：列的排序规则是 `C` 或 `POSIX`，或者索引使用了 `text_pattern_ops` 运算符类。像 `en_US.UTF-8` 这样的语言排序规则按语言规则排序，所以一个前缀在索引里并不是一段连续的范围。在 Postgres 16 上的本地测试中，使用 ICU 英语排序规则的列走的是全表扫描，使用数据库默认 `C.UTF-8` 排序规则的列也是如此；只有 `C` 列或 `text_pattern_ops` 索引才生成了范围条件。同一个测试还显示两种顺序确实不同：`SKU_1` 在英语顺序里排在 `sku-1` 之前，在字节顺序里则排在它之后。

**Why ILIKE is slow everywhere.** A btree index cannot serve a case-insensitive pattern at all. Index the lowercased value with `text_pattern_ops` and compare lowercased input; locally that turned the scan into an index range.

> **为什么 ILIKE 在哪里都慢。** btree 索引根本无法支持大小写不敏感的模式匹配。对转成小写后的值建立带 `text_pattern_ops` 的索引，并用转成小写的输入去比较；在本地测试中，这样就把全表扫描变成了索引范围扫描。

```sql
-- Option 1: an index for prefix search, next to the normal one
CREATE INDEX CONCURRENTLY products_sku_prefix ON products (sku text_pattern_ops);

-- Option 2: SKUs are identifiers, so byte order is fine
ALTER TABLE products ALTER COLUMN sku TYPE text COLLATE "C";

-- Case-insensitive prefix search
CREATE INDEX CONCURRENTLY products_sku_lower ON products (lower(sku) text_pattern_ops);
SELECT id FROM products WHERE lower(sku) LIKE lower($1) || '%';
```

**Which option.** A `text_pattern_ops` index serves prefix `LIKE` and equality but not `ORDER BY sku` under the column's own collation; locally, sorting still used a sequential scan and a sort. Changing the column to `COLLATE "C"` lets one ordinary index serve equality, prefixes and sorting, and for identifiers like SKUs byte order is fine. In the local test the change rebuilt the index without rewriting the table, but it still takes a strong lock, so run it in a quiet window. Escape `%` and `_` in the merchant's input, or a SKU containing an underscore matches too much.

> **选哪种方案。** `text_pattern_ops` 索引可以支持前缀 `LIKE` 和等值查询，但不能支持按列自身排序规则进行的 `ORDER BY sku`；在本地测试中，排序仍然用了全表扫描加排序。把列改成 `COLLATE "C"` 之后，一个普通索引就能同时支持等值、前缀和排序，而对于 SKU 这类标识符，字节顺序完全没问题。在本地测试中，这个修改重建了索引但没有重写表，不过它仍然会持有一个很强的锁，所以要在业务低峰期执行。还要转义商家输入中的 `%` 和 `_`，否则包含下划线的 SKU 会匹配到过多结果。

**Trade-offs.** An extra index costs write time and disk. A `C` collation sorts uppercase before lowercase, which is wrong for product titles but right for codes. Keep staging on the same locale as production, or plans will keep surprising you.

> **权衡。** 额外的索引会增加写入耗时和磁盘占用。`C` 排序规则会把大写字母排在小写字母前面，这对商品标题来说不对，但对编码来说正好。让预发环境和生产环境使用相同的 locale，否则执行计划还会不断给你「惊喜」。

</details>

## 4. A Redis bitmap of products viewed today: one new product ID made Redis allocate 500 MB and stall

**用 Redis 位图记录今天被浏览过的商品：一个新的商品 ID 让 Redis 分配了 500 MB 内存并卡顿** · `Middleware` · `Medium`

### Question · 题目

To show "viewed today" badges and count viewed products per day, the team runs `SETBIT viewed:{day} {productID} 1` on every product view and `BITCOUNT viewed:{day}` for the dashboard. It works in staging, where IDs are below two million. In production, a new ID service starts issuing product IDs around 4,000,000,000. Redis memory jumps by about 500 MB, latency spikes for every client, and the replica falls behind. A week later, IDs above 2^32 fail with `bit offset is not an integer or out of range`.

> 为了显示「今日已浏览」标记并统计每天被浏览的商品数，团队在每次商品浏览时执行 `SETBIT viewed:{day} {productID} 1`，并在仪表盘上用 `BITCOUNT viewed:{day}` 统计。在 ID 都小于两百万的预发环境里一切正常。在生产环境中，一个新的 ID 服务开始发放大约 4,000,000,000 左右的商品 ID。Redis 内存一下子涨了大约 500 MB，所有客户端的延迟飙升，从库也落后了。一周之后，大于 2^32 的 ID 开始报错：`bit offset is not an integer or out of range`。

Explain what happened and redesign the tracking.

> 解释发生了什么，并重新设计这个统计方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why one SETBIT costs 500 MB.** A Redis bitmap is an ordinary string. Setting bit N grows the string to about N/8 bytes and fills the gap with zeros, so offset 4,000,000,000 creates a 500 MB value, every day, for one product. Redis does this on its single command thread: in a local test, that one `SETBIT` took about 200 ms and memory went from under 1 MB to 513 MB. `BITCOUNT` over the whole string took about 330 ms, blocking every other client while it ran. The replica must receive the large value too, and persistence has to write it.

> **为什么一次 SETBIT 要花 500 MB。** Redis 位图就是一个普通的字符串。设置第 N 位会把字符串扩展到大约 N/8 字节，并用零填满中间的空隙，所以偏移量 4,000,000,000 每天都会为一个商品创建一个 500 MB 的值。Redis 在它唯一的命令线程上做这件事：在本地测试中，这一次 `SETBIT` 花了大约 200 毫秒，内存从不到 1 MB 涨到了 513 MB。对整个字符串执行 `BITCOUNT` 花了大约 330 毫秒，运行期间阻塞了所有其他客户端。从库也必须接收这个大值，持久化也要把它写下来。

**Why IDs above 2^32 fail.** Bit offsets are limited to 2^32 - 1, the 512 MB maximum string size. Larger IDs cannot be stored in one bitmap at all; locally, offset 2^32 returned exactly that error.

> **为什么大于 2^32 的 ID 会失败。** 位偏移量的上限是 2^32 - 1，对应字符串最大 512 MB 的大小。更大的 ID 根本无法存进一个位图；在本地测试中，偏移量 2^32 正是返回了这个错误。

**Redesign.** Pick by the question you need to answer:

> **重新设计。** 根据你需要回答的问题来选择：

- **Bucketed bitmaps** for "was product X viewed today" and exact counts: split IDs into ranges, one key per range. Only ranges that see traffic exist, and each is at most 128 KB.
  > **分桶位图**，适用于「商品 X 今天是否被浏览过」以及精确计数：把 ID 按范围切分，每个范围一个键。只有有流量的范围才会存在，而且每个最多 128 KB。
- **Dense IDs**: map product IDs to a compact per-store sequence and use that as the offset, if such a mapping already exists.
  > **稠密 ID**：如果已经有这样的映射，就把商品 ID 映射到每个店铺内紧凑的序号，并把它作为偏移量。
- **A set** when few products are viewed: exact, with more memory per member than a bit.
  > **集合（Set）**，适用于被浏览的商品很少时：结果精确，但每个成员占用的内存比一个比特多。
- **HyperLogLog** when only an approximate count is needed; it cannot tell you whether a given product was viewed.
  > **HyperLogLog**，适用于只需要近似计数的情况；它无法告诉你某个具体商品是否被浏览过。

```go
const bucketBits = 20 // 1,048,576 products per bucket, at most 128 KB each

func markViewed(ctx context.Context, rdb *redis.Client, day string, productID uint64) error {
	key := fmt.Sprintf("viewed:%s:%d", day, productID>>bucketBits)
	offset := int64(productID & (1<<bucketBits - 1))
	pipe := rdb.Pipeline()
	pipe.SetBit(ctx, key, offset, 1)
	pipe.Expire(ctx, key, 48*time.Hour)
	_, err := pipe.Exec(ctx)
	return err
}
```

Count with `BITCOUNT` per bucket in a pipeline and sum. Delete the oversized keys with `UNLINK`, which frees memory in the background, not `DEL`.

> 计数时，在一个 pipeline 里对每个桶执行 `BITCOUNT` 然后求和。删除那些过大的键时要用 `UNLINK`，它在后台释放内存，而不要用 `DEL`。

**Trade-offs.** Buckets add a little bookkeeping for counts. Bitmaps are great for dense IDs and terrible for sparse ones, so the ID scheme is part of the design. Test with production-like IDs, not staging's small ones.

> **权衡。** 分桶会给计数增加一点额外的管理工作。位图非常适合稠密的 ID，对稀疏的 ID 则糟糕透顶，所以 ID 方案本身就是设计的一部分。要用和生产环境类似的 ID 来测试，而不是预发环境里那些很小的 ID。

</details>

## 5. Campaigns created in late December get end dates a year too late on US servers and in the past on EU servers

**在 12 月底创建的广告活动，在美国服务器上结束日期晚了一年，在欧洲服务器上则变成了过去的日期** · `Java & CS` · `Hard`

### Question · 题目

The campaign scheduler sends start and end dates to ad platforms using `DateTimeFormatter.ofPattern("YYYY-MM-dd")`. In the last days of December, a campaign created on a US server with end date 2026-12-31 appears on the platform ending on 2027-12-31 and keeps spending. On EU servers, a campaign ending on 2027-01-02 is rejected because its end date is in the past. Meanwhile, a report file named with `yyyy-MM-DD` was called `2026-02-36` on February 5, and the CSV import accepted `2026-02-30` as a date.

> 广告活动调度器使用 `DateTimeFormatter.ofPattern("YYYY-MM-dd")` 把开始和结束日期发送给广告平台。在 12 月的最后几天，一个在美国服务器上创建、结束日期为 2026-12-31 的活动，在平台上显示的结束日期却是 2027-12-31，并且一直在花钱。在欧洲服务器上，一个结束日期为 2027-01-02 的活动被拒绝，原因是结束日期已经过去了。与此同时，一个用 `yyyy-MM-DD` 命名的报表文件在 2 月 5 日被命名成了 `2026-02-36`，而 CSV 导入还接受了 `2026-02-30` 这样的日期。

Explain each bug and fix the date handling.

> 解释每个 bug，并修复日期的处理方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why the year is wrong.** In `DateTimeFormatter` patterns, `Y` is the week-based year, not the calendar year (`y` or `u`). Near New Year, days belong to week 1 of the next year or the last week of the previous one, and the week rules depend on the locale. In a local test, with the US locale, every date from December 27, 2026 printed as 2027. With the German and UK locales, January 1 to 3, 2027 printed as 2026, and December 29, 2025 printed as 2026. That is the same code giving different answers on servers with different default locales. `SimpleDateFormat` has the same `Y`.

> **为什么年份不对。** 在 `DateTimeFormatter` 的模式中，`Y` 表示基于周的年份，而不是日历年（`y` 或 `u`）。在新年前后，有些日子属于下一年的第 1 周，或者上一年的最后一周，而周的规则取决于 locale。在本地测试中，使用美国 locale 时，从 2026 年 12 月 27 日起的每一天都被打印成 2027 年。使用德国和英国 locale 时，2027 年 1 月 1 日到 3 日被打印成 2026 年，2025 年 12 月 29 日也被打印成了 2026 年。同一段代码，在默认 locale 不同的服务器上给出了不同的答案。`SimpleDateFormat` 里的 `Y` 也是同样的含义。

**The other two bugs.** `D` is the day of the year, so February 5 is day 36. And `LocalDate.parse` with a `yyyy-MM-dd` pattern uses the default SMART resolver, which locally turned `2026-02-30` into February 28 without an error.

> **另外两个 bug。** `D` 是一年中的第几天，所以 2 月 5 日是第 36 天。而使用 `yyyy-MM-dd` 模式的 `LocalDate.parse` 采用默认的 SMART 解析模式，在本地测试中它把 `2026-02-30` 悄悄变成了 2 月 28 日，没有任何报错。

```java
// Wrong: week-based year (Y) and day of year (D), and a lenient parser.
DateTimeFormatter bad = DateTimeFormatter.ofPattern("YYYY-MM-DD");

// Right for wire formats: the ISO formatter, no locale involved.
String end = DateTimeFormatter.ISO_LOCAL_DATE.format(campaign.endDate());

// Right for parsing merchant input: uuuu with STRICT, so 2026-02-30 is rejected.
DateTimeFormatter in = DateTimeFormatter.ofPattern("uuuu-MM-dd", Locale.ROOT)
        .withResolverStyle(ResolverStyle.STRICT);
LocalDate d = LocalDate.parse(text, in);
```

**Why uuuu with STRICT.** Under STRICT, `yyyy` means year-of-era and needs an era to build a date, so locally even a valid `2026-02-28` failed to parse. `uuuu` is the plain proleptic year and works. `Locale.ROOT` keeps formatting independent of the server's default locale.

> **为什么要用 uuuu 加 STRICT。** 在 STRICT 模式下，`yyyy` 表示纪元内的年份，需要有纪元才能构成日期，所以在本地测试中，连合法的 `2026-02-28` 都解析失败了。`uuuu` 是普通的前推公历年份（proleptic year），可以正常工作。`Locale.ROOT` 让格式化不受服务器默认 locale 的影响。

**Prevent the next one.** Add tests that format and parse every date from December 26 to January 4 under several locales, plus February 29 and 30. Ban `Y` and `D` in pattern strings with a lint rule, and use the ISO formatters for anything another system reads.

> **预防下一次。** 增加测试，在多个 locale 下对 12 月 26 日到 1 月 4 日之间的每一天进行格式化和解析，再加上 2 月 29 日和 2 月 30 日。用 lint 规则禁止在模式字符串中使用 `Y` 和 `D`，并且凡是要给其他系统读取的日期，都使用 ISO 格式化器。

**Trade-offs.** STRICT parsing rejects input that used to "work", so merchants with bad files will see new errors; show them the row and the reason. That is still better than silently moving a campaign's end date.

> **权衡。** STRICT 解析会拒绝那些以前「能用」的输入，所以文件有问题的商家会看到新的错误；要把出错的行和原因展示给他们。即便如此，也比悄悄地挪动广告活动的结束日期要好。

</details>
