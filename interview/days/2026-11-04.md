## 1. One malformed webhook takes down the whole webhook service, although net/http recovers handler panics

**一个格式错误的 webhook 让整个 webhook 服务崩溃，尽管 net/http 会恢复 handler 中的 panic** · `Go` · `Senior`

### Question · 题目

A Go service receives order webhooks from many shops. The handler validates the request, replies `202 Accepted`, and starts a goroutine to parse and store the payload. One shop's app started sending a payload with a missing nested object; the parser dereferences a nil pointer, and every instance of the service restarts in a loop. A teammate says this cannot be the cause, because `net/http` recovers panics. Another proposes adding `recover()` to `main`.

> 一个 Go 服务接收来自许多店铺的订单 webhook。handler 校验请求、回复 `202 Accepted`，然后启动一个 goroutine 去解析并存储负载。某个店铺的应用开始发送一个缺少嵌套对象的负载；解析器对一个 nil 指针解引用，于是服务的每一个实例都陷入循环重启。一位同事说这不可能是原因，因为 `net/http` 会恢复 panic。另一位提议在 `main` 里加上 `recover()`。

Explain what happens and design the service so one bad payload cannot take it down.

> 解释发生了什么，并设计这个服务，让一个有问题的负载无法让它崩溃。

<details>
<summary><b>Answer · 参考答案</b></summary>

**What happens.** `recover` only works in a deferred function on the same goroutine that panicked. The `net/http` server does recover panics in the handler's own goroutine: in a local test, a handler panic was logged as "http: panic serving ...", the client's request failed, and the server kept serving the next request. But a panic in a goroutine the handler started is outside that protection. In the same test, it killed the whole process with exit status 2. A `recover()` in `main` cannot catch it either, because `main` runs on a different goroutine.

> **发生了什么。** `recover` 只有在发生 panic 的同一个 goroutine 中、并且在被 defer 的函数里调用才有效。`net/http` 服务器确实会恢复 handler 自己所在 goroutine 中的 panic：在本地测试中，handler 的 panic 被记录为 “http: panic serving ...”，客户端的请求失败了，而服务器继续处理下一个请求。但 handler 启动的 goroutine 中发生的 panic 不在这层保护之内。在同一个测试中，它以退出码 2 杀死了整个进程。在 `main` 里加 `recover()` 也抓不住它，因为 `main` 运行在另一个 goroutine 上。

**Why every instance dies.** The shop's app retries the webhook because processing failed, so the poison payload reaches the next instance, which also crashes. The fleet goes down one instance after another.

> **为什么每个实例都会挂掉。** 由于处理失败，店铺的应用会重试这个 webhook，于是这个“毒”负载到达下一个实例，下一个实例也随之崩溃。整组实例就这样一个接一个地倒下。

**Design.**

> **设计。**

- **Validate, then return errors, not panics.** Parse into structs that tolerate missing fields, check them, and return an error. A nil dereference is a bug to fix, not a control flow.
  > **先校验，再返回错误，而不是 panic。** 解析到能容忍缺失字段的结构体中，进行检查，然后返回错误。nil 解引用是需要修复的 bug，而不是一种控制流程。
- **Every goroutine you start owns its own recovery.** Start background work through one helper that defers a `recover`, logs the panic with the stack and the payload ID, and reports it.
  > **你启动的每个 goroutine 都要自己负责恢复。** 通过一个统一的辅助函数启动后台工作，它在 defer 中调用 `recover`，记录 panic 的堆栈和负载 ID，并上报它。
- **Persist before processing.** Store the raw payload durably, reply 202, and process it from a queue. A payload that keeps failing goes to a dead-letter table after a few attempts instead of crashing the fleet or being lost.
  > **先持久化，再处理。** 先把原始负载可靠地存储起来，回复 202，然后从队列中处理它。一个反复失败的负载在尝试几次之后会被放进死信表，而不是让整组实例崩溃或者丢失。

```go
// safeGo runs f in a new goroutine; a panic is logged and reported instead of
// killing the process.
func safeGo(name string, f func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("%s panicked: %v\n%s", name, r, debug.Stack())
				panicsTotal.Inc()
			}
		}()
		f()
	}()
}
```

**Senior judgement.** Recovering everywhere can hide corrupted state: a panic in the middle of updating shared data may leave it inconsistent. Recover at boundaries where the unit of work is isolated, such as one webhook, one job or one request, and let truly unexpected panics in shared state crash and restart. Alert on the panic counter, and add fuzz tests on the parser with real malformed payloads.

> **资深工程师的判断。** 到处恢复可能会掩盖被破坏的状态：在更新共享数据的过程中发生的 panic，可能会让数据处于不一致的状态。在工作单元相互隔离的边界处恢复，比如一个 webhook、一个作业或一个请求；而对于共享状态中真正意外的 panic，就让进程崩溃并重启。对 panic 计数器设置告警，并用真实的格式错误负载对解析器做模糊测试。

**Trade-offs.** Persisting first adds a write and a queue to every webhook, but it turns a crash loop into a backlog and makes every payload replayable. A recover helper is cheap, but it must be the only way to start goroutines, or the next `go func()` reopens the hole.

> **取舍。** 先持久化会给每个 webhook 增加一次写入和一个队列，但它把循环崩溃变成了积压，并让每个负载都可以重放。recover 辅助函数的成本很低，但它必须是启动 goroutine 的唯一方式，否则下一个 `go func()` 就会重新打开这个漏洞。

</details>

## 2. Order alerts to merchants by email, SMS and app push: no duplicates, quiet hours, and per-channel failures

**通过邮件、短信和应用推送向商家发送订单提醒：不重复、免打扰时段，以及单个渠道的故障** · `System Design` · `Medium`

### Question · 题目

Merchants get notified about new orders, low stock and failed ad payments by email, SMS and mobile push. Today each feature calls the providers directly. Merchants complain about duplicate SMS, alerts at 3 a.m. in their own time zone, and missing alerts when the SMS provider is down. Costs for SMS are also growing. Design a notification system.

> 商家会通过邮件、短信和手机推送收到新订单、库存不足和广告付款失败的通知。目前每个功能都直接调用这些服务商。商家抱怨收到重复短信、在自己时区的凌晨 3 点收到提醒，以及在短信服务商故障时漏掉提醒。短信的费用也在不断增长。请设计一个通知系统。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Separate "something happened" from "how we tell the merchant". Features publish events; one notification service decides who gets what, on which channel and when, sends it once, and records the result.

> **核心思路。** 把“发生了某件事”和“我们如何告诉商家”分开。各个功能只发布事件；由一个通知服务决定谁收到什么、走哪个渠道、在什么时间发送，只发送一次，并记录结果。

**Design.**

> **设计。**

- **Events in, with an idempotency key.** Each event has an ID such as `order_created:<order_id>`. The service stores a notification row per recipient and channel with a unique key, so a retried event never creates a second SMS.
  > **输入事件带有幂等键。** 每个事件都有一个 ID，例如 `order_created:<order_id>`。服务按接收人和渠道为每条通知存一行，并带有唯一键，这样重试的事件永远不会产生第二条短信。
- **Preferences and rules.** Merchants choose channels per alert type. Quiet hours are evaluated in the merchant's time zone; urgent alerts like payment failures can bypass them, while others are held and sent in the morning.
  > **偏好与规则。** 商家按提醒类型选择渠道。免打扰时段按商家所在的时区计算；像付款失败这样的紧急提醒可以绕过它，而其他提醒则会被暂缓到早上再发送。
- **Digest and rate limits.** A burst of 200 orders becomes one summary, not 200 SMS. Per-merchant limits per channel control cost and stop runaway loops.
  > **汇总与限流。** 一次集中出现的 200 个订单会变成一条汇总，而不是 200 条短信。按商家、按渠道的限额可以控制成本，并阻止失控的循环。
- **Per-channel workers with fallback.** Each channel has its own queue and retries with backoff. If SMS fails for an urgent alert after retries, fall back to push or email; an outage of one provider does not block the others.
  > **按渠道划分的 worker 及降级。** 每个渠道都有自己的队列，并带退避地重试。如果紧急提醒的短信在重试后仍然失败，就降级为推送或邮件；一个服务商的故障不会阻塞其他渠道。
- **Delivery status.** Store sent, delivered, failed and opened, using provider callbacks where available, and show merchants a notification history.
  > **投递状态。** 记录已发送、已送达、失败和已打开等状态，在服务商支持时使用其回调，并向商家展示通知历史。

**Trade-offs.** A central service adds a hop and a component to run, but it is the only place where deduplication, quiet hours and cost limits can be enforced consistently. Digests reduce noise but delay information; let merchants choose for each alert type. Falling back between channels improves reach but can surprise merchants, so make it visible in their settings.

> **取舍。** 集中式服务增加了一跳和一个需要运维的组件，但它是唯一能一致地执行去重、免打扰时段和成本限额的地方。汇总能减少干扰，但会延迟信息；让商家按提醒类型自行选择。渠道之间的降级可以提高触达率，但可能会让商家感到意外，所以要在他们的设置中明确展示出来。

</details>

### Follow-ups · 追问

  > 如果在提醒被暂缓期间，商家修改了时区或免打扰时段，你会如何处理？
- Where exactly would you enforce the idempotency key?
  > 你具体会在哪里强制执行幂等键？

## 3. A Postgres-backed job table: workers process the same sync job twice, or all wait behind one slow job

**基于 Postgres 的作业表：worker 把同一个同步作业处理了两次，或者全都排在一个慢作业后面等待** · `Database` · `Hard`

### Question · 题目

Catalog sync jobs live in a PostgreSQL table `jobs(id, merchant_id, status, ...)`. Each worker runs `SELECT id FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 1`, then `UPDATE jobs SET status = 'running'`. Some jobs run twice. A developer adds `FOR UPDATE` to the select; now duplicates stop, but with 20 workers throughput barely changes from one worker. Also, when a worker pod is killed, its jobs stay `running` forever.

> 商品目录同步作业保存在 PostgreSQL 表 `jobs(id, merchant_id, status, ...)` 中。每个 worker 先执行 `SELECT id FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 1`，再执行 `UPDATE jobs SET status = 'running'`。有些作业被执行了两次。一位开发者在 select 上加了 `FOR UPDATE`；现在重复没有了，但 20 个 worker 的吞吐量和一个 worker 差不多。此外，当某个 worker 的 pod 被杀掉时，它手上的作业会永远停留在 `running` 状态。

Explain each problem and write a correct claim.

> 解释每个问题，并写出一个正确的作业领取方式。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Duplicates.** The select and the update are separate steps, so two workers can both read the same pending row before either marks it. In a local PostgreSQL 16 test, two concurrent workers both selected job 1.

> **重复执行。** select 和 update 是两个独立的步骤，所以两个 worker 可能在任何一方标记之前都读到同一个待处理的行。在本地 PostgreSQL 16 的测试中，两个并发的 worker 都选中了作业 1。

**No throughput.** `FOR UPDATE` locks the row, so the second worker waits for the first one's transaction instead of moving on; every worker queues behind the same first row. In the test, the second worker waited about 1.7 seconds for the first one's transaction. `FOR UPDATE SKIP LOCKED` instead skips rows other transactions have locked: the second worker got job 2 in a few milliseconds.

> **吞吐量上不去。** `FOR UPDATE` 会锁住这一行，所以第二个 worker 会等待第一个 worker 的事务结束，而不是继续往下走；每个 worker 都排在同一个第一行后面。在测试中，第二个 worker 等了大约 1.7 秒，直到第一个的事务结束。而 `FOR UPDATE SKIP LOCKED` 会跳过已被其他事务锁住的行：第二个 worker 在几毫秒内就拿到了作业 2。

**Stuck jobs.** A status of `running` with no expiry means nobody ever picks the job up again. Use a lease: `locked_until`, and let the claim also take jobs whose lease has expired.

> **卡住的作业。** 没有过期时间的 `running` 状态，意味着再也没有人会去领取这个作业。使用租约：`locked_until`，并让领取操作同时接管租约已过期的作业。

```sql
UPDATE jobs
SET status = 'running', locked_until = now() + interval '5 minutes',
    attempts = attempts + 1
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'pending'
     OR (status = 'running' AND locked_until < now())
  ORDER BY id
  LIMIT 1
  FOR UPDATE SKIP LOCKED)
RETURNING id, attempts;
```

In the test, two claims returned jobs 1 and 2; after job 1's lease was moved into the past, the next claim took job 1 again with `attempts` = 2.

> 在测试中，两次领取分别返回了作业 1 和作业 2；在把作业 1 的租约改到过去的时间之后，下一次领取再次拿到了作业 1，且 `attempts` 为 2。

- **Commit the claim, then work.** Do not hold the row lock while calling TikTok or Meta; a long transaction blocks vacuum and holds a connection. Claim in a short transaction, do the work, then mark the job done in another.
  > **先提交领取，再开始工作。** 不要在调用 TikTok 或 Meta 期间持有行锁；长事务会阻塞 vacuum，并占用一个连接。在一个短事务中完成领取，然后去做工作，再在另一个事务中把作业标记为完成。
- **Extend long leases.** A worker that needs more time renews `locked_until` periodically; the work itself must be idempotent, because an expired lease can still be taken over while the first worker is alive.
  > **为长任务续租。** 需要更多时间的 worker 会定期更新 `locked_until`；而工作本身必须是幂等的，因为即使第一个 worker 还活着，过期的租约仍然可能被接管。
- **Cap attempts.** After too many attempts, move the job to `failed` for review instead of retrying forever, and index the columns used by the claim query.
  > **限制尝试次数。** 尝试次数过多后，把作业移到 `failed` 状态等待复核，而不是无限重试，并为领取查询用到的列建立索引。

**Trade-offs.** A Postgres queue is simple, transactional with your data and fine for moderate volumes; at high throughput the row churn and polling become costly, and a dedicated queue fits better. Strict per-merchant ordering is harder with `SKIP LOCKED`, because jobs for one merchant can run in parallel unless you also lock per merchant.

> **取舍。** Postgres 队列简单，能与你们的数据处于同一事务中，适合中等规模；在高吞吐量下，行的频繁变更和轮询会变得昂贵，此时专用队列更合适。使用 `SKIP LOCKED` 时更难保证按商家严格有序，因为除非你还按商家加锁，同一个商家的作业可能会并行执行。

</details>

## 4. Merchants cannot page past result 10,000 in product search, and the "export results" button times out

**商家在商品搜索中无法翻到第 10,000 条之后，而“导出结果”按钮会超时** · `Middleware` · `Hard`

### Question · 题目

The merchant admin uses Elasticsearch for product search with `from` and `size` pagination. Large merchants with hundreds of thousands of products get an error when they jump to deep pages, and an "export all matching products" feature, which pages through the same search, fails or produces duplicates and gaps while products are being updated. Someone proposes raising `index.max_result_window` to 10 million.

> 商家后台使用 Elasticsearch 做商品搜索，采用 `from` 和 `size` 分页。拥有几十万个商品的大商家在跳到很深的页码时会得到一个错误，而“导出所有匹配商品”功能也是通过翻页同一个搜索来实现的，它会失败，或者在商品被更新期间产生重复和遗漏。有人提议把 `index.max_result_window` 提高到 1000 万。

Explain the limit and design deep pagination and export.

> 解释这个限制，并设计深度分页和导出。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why the limit exists.** With `from` and `size`, every shard must collect and sort `from + size` hits, and the coordinating node merges all of them, just to return the last `size`. Cost grows with depth on every shard. Elasticsearch caps `from + size` with `index.max_result_window`, which defaults to 10,000, so deep pages fail. Raising it to millions moves the problem into heap usage and slow queries that can hurt the whole cluster.

> **为什么存在这个限制。** 使用 `from` 和 `size` 时，每个分片都必须收集并排序 `from + size` 条结果，协调节点再把它们全部合并，只为了返回最后的 `size` 条。成本在每个分片上都随深度增长。Elasticsearch 用 `index.max_result_window` 限制 `from + size`，默认值是 10,000，所以很深的页会失败。把它提高到几百万，只会把问题转移成堆内存占用和慢查询，可能会拖累整个集群。

**Why export breaks.** Paging an index that changes underneath you shifts results between pages: an updated product can move, appearing twice or not at all.

> **为什么导出会出问题。** 对一个在底下不断变化的索引进行翻页，结果会在页之间移动：一个被更新的商品可能会移位，从而出现两次，或者一次都不出现。

**Design.**

> **设计。**

- **UI: no deep jumping.** Few people go to page 2,000. Offer next and previous with `search_after`, which continues from the sort values of the last hit, plus better filters and sorting. Always include a unique tiebreaker such as the product ID in the sort.
  > **界面：不支持深度跳页。** 很少有人会去第 2,000 页。用 `search_after` 提供上一页和下一页，它会从上一条结果的排序值处继续，同时提供更好的筛选和排序。排序中始终要包含一个唯一的决胜字段，例如商品 ID。
- **Consistent export: point in time plus `search_after`.** Open a point in time (PIT) to page a fixed view of the index, page through with `search_after`, then close it. Elastic recommends this over the older scroll API for deep pagination.
  > **一致的导出：时间点加 `search_after`。** 打开一个时间点（PIT），对索引的一个固定视图进行翻页，用 `search_after` 逐页读取，然后关闭它。对于深度分页，Elastic 推荐这种方式，而不是较旧的 scroll API。
- **Better still, export from the source of truth.** Search finds IDs; the export job reads full product data from the database in keyset pages, which avoids stale index data and keeps exports off the search cluster.
  > **更好的做法是从事实来源导出。** 搜索负责找出 ID；导出作业以键集分页的方式从数据库读取完整的商品数据，这样既避免了索引数据过时，也让导出不占用搜索集群。

```json
{"size": 500,
 "query": {"term": {"merchant_id": 42}},
 "pit": {"id": "<pit id>", "keep_alive": "2m"},
 "sort": [{"updated_at": "desc"}, {"product_id": "asc"}],
 "search_after": ["2026-11-01T08:00:00Z", 98231]}
```

**Operational notes.** Each open PIT keeps old segments around, so keep `keep_alive` short and renew it per page, close it when done, and limit concurrent exports per merchant. Run exports as background jobs, as with any large export.

> **运维要点。** 每个打开的 PIT 都会让旧的段继续保留，所以要把 `keep_alive` 设得短一些并在每一页续期，用完就关闭，并限制每个商家同时进行的导出数量。和任何大型导出一样，把导出作为后台作业来运行。

**Trade-offs.** `search_after` cannot jump to an arbitrary page, which is a product change merchants may notice; most accept it with good filters. PIT gives a consistent snapshot at the cost of cluster resources while it is open. Exporting from the database is the most correct and the most work, since it needs a second query path.

> **取舍。** `search_after` 无法跳到任意页，这是商家可能会注意到的产品变化；但在有良好筛选的情况下，大多数人都能接受。PIT 提供一致的快照，代价是在它打开期间占用集群资源。从数据库导出是最正确的方式，也是工作量最大的，因为它需要第二条查询路径。

</details>

## 5. Sorting products by price into a TreeSet silently drops products that share a price

**把商品按价格放进 TreeSet 排序时，价格相同的商品被悄悄丢掉了** · `Java & CS` · `Medium`

### Question · 题目

A Java feed builder keeps products sorted by price with `new TreeSet<>(Comparator.comparing(Product::price))`, then writes them to a Google Shopping feed. Merchants report missing products in the feed, always ones with the same price as another product. A similar `TreeMap` keyed by product with the same comparator shows wrong stock numbers.

> 一个 Java feed 生成程序用 `new TreeSet<>(Comparator.comparing(Product::price))` 让商品按价格保持有序，然后把它们写入 Google Shopping feed。商家反馈 feed 中缺少商品，而缺少的总是那些和其他商品价格相同的商品。另一个使用相同比较器、以商品为键的 `TreeMap` 则显示了错误的库存数字。

Explain why and fix it.

> 解释原因并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** A `TreeSet` or `TreeMap` decides whether two elements are the same with the comparator, not with `equals`. If the comparator says two products compare as 0, the set treats them as one element and keeps only the first. In a local test on Java 21, four products, three of them at 19.90, became a set of two. The `TreeMap` kept a single entry for two products, and the second `put` overwrote the first one's stock.

> **原因。** `TreeSet` 或 `TreeMap` 用比较器而不是 `equals` 来判断两个元素是否相同。如果比较器认为两个商品比较结果为 0，集合就会把它们当作同一个元素，只保留第一个。在 Java 21 上的本地测试中，四个商品（其中三个价格是 19.90）变成了只有两个元素的集合。`TreeMap` 为两个商品只保留了一个条目，第二次 `put` 覆盖了第一个商品的库存。

**A subtle variant.** `BigDecimal` makes this worse: `19.90` and `19.9` are not `equals`, but `compareTo` returns 0. In the test a `HashSet` kept both, while a `TreeSet` kept one, so the same data behaved differently in two collections.

> **一个微妙的变体。** `BigDecimal` 让问题更严重：`19.90` 和 `19.9` 不 `equals`，但 `compareTo` 返回 0。在测试中，`HashSet` 保留了两个，而 `TreeSet` 只保留了一个，所以同样的数据在两种集合中表现不同。

**Fix.** Make the comparator consistent with equality by adding a unique tiebreaker, or do not use a sorted set for sorting at all.

> **修复方法。** 通过添加唯一的决胜字段，让比较器与相等性保持一致；或者干脆不要用有序集合来排序。

```java
// unique tiebreaker: two products never compare as equal unless they are the same SKU
TreeSet<Product> byPrice = new TreeSet<>(
    Comparator.comparing(Product::price).thenComparing(Product::sku));

// or keep a list and sort it when needed
List<Product> sorted = new ArrayList<>(products);
sorted.sort(Comparator.comparing(Product::price));
```

In the test, both versions kept all four products in price order.

> 在测试中，两种写法都按价格顺序保留了全部四个商品。

- **Key maps by identity.** A stock map should be keyed by SKU in a `HashMap`, not by a product sorted by price.
  > **按身份作为 map 的键。** 库存 map 应该在 `HashMap` 中以 SKU 为键，而不是以按价格排序的商品为键。
- **Test with ties.** Unit tests for anything sorted should include equal keys, because data without ties hides the bug completely.
  > **用相等的值来测试。** 任何排序相关的单元测试都应该包含相等的键，因为没有相等值的数据会把这个 bug 完全掩盖。
- **Count in and out.** A feed builder should log input and output counts, so a silent drop shows up as a mismatch.
  > **统计输入和输出数量。** feed 生成程序应该记录输入和输出的数量，这样悄无声息的丢失就会表现为数量不一致。

**Trade-offs.** A sorted set keeps order on every insert, which helps only when you need the order continuously, for example a live top-N. For building a file once, sorting a list is simpler and has no equality trap. Adding a tiebreaker fixes the set but makes the comparator part of your data model, so document it.

> **取舍。** 有序集合在每次插入时都维持顺序，只有在你需要持续保持顺序时才有用，例如实时的前 N 名。对于一次性生成一个文件来说，对列表排序更简单，也没有相等性陷阱。添加决胜字段能修复集合的问题，但会让比较器成为数据模型的一部分，所以要写进文档。

</details>
