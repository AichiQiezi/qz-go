## 1. After a request-signing wrapper was added, retried conversion uploads reach the ad platform with an empty body, and the retry helper reports success

**加了请求签名包装器之后，重试的转化回传以空请求体到达广告平台，而重试辅助函数还报告成功** · `Go` · `Hard`

### Question · 题目

The conversion service posts purchase events to an ad platform. A retry helper builds the `*http.Request` once and calls `client.Do(req)` up to three times on 5xx. It worked for months. Then a signing middleware was added that wraps `req.Body` in its own `io.ReadCloser` to hash the bytes as they stream. Since then, some retried events are missing on the platform's side. Its logs show requests with an empty body, and on a test endpoint the second attempt even returned 200.

> 转化服务把购买事件 POST 到一个广告平台。重试辅助函数只构建一次 `*http.Request`，遇到 5xx 时最多调用三次 `client.Do(req)`。它正常运行了好几个月。后来加了一个签名中间件，它把 `req.Body` 包进自己的 `io.ReadCloser`，在数据流过时计算哈希。从那以后，一些被重试的事件在平台那边丢失了。平台日志里出现了请求体为空的请求；在一个测试端点上，第二次尝试甚至返回了 200。

Explain why it used to work, why it broke, and fix it.

> 解释为什么它以前能正常工作、为什么坏了，并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** A request body is a stream, and the first `Do` reads it to the end. Reusing the same request only works when the client can get a fresh copy of the body, which is what `Request.GetBody` is for. `http.NewRequest` sets `GetBody` automatically for in-memory bodies such as `*bytes.Reader`, `*bytes.Buffer` and `*strings.Reader`, so the old code was quietly relying on it. The signing wrapper replaced the body with a type `NewRequest` does not know, so `GetBody` was nil and nothing could rewind the stream.

> **原因。** 请求体是一个流，第一次 `Do` 会把它读到末尾。只有当客户端能拿到请求体的新副本时，复用同一个请求才行得通，而 `Request.GetBody` 正是为此存在的。`http.NewRequest` 会为 `*bytes.Reader`、`*bytes.Buffer` 和 `*strings.Reader` 这样的内存请求体自动设置 `GetBody`，所以旧代码其实一直在悄悄依赖它。签名包装器把请求体换成了一个 `NewRequest` 不认识的类型，于是 `GetBody` 为 nil，再也没有东西能把流倒回去。

**What the local tests showed** (Go 1.24, a test server that fails the first attempt with 503):

> **本地测试的结果**（Go 1.24，测试服务器让第一次尝试返回 503）：

- A request built from `bytes.NewReader` sent the full 34 bytes on both attempts.
  > 用 `bytes.NewReader` 构建的请求，两次尝试都发送了完整的 34 字节。
- The same request with `GetBody` cleared failed the retry with `http: ContentLength=34 with Body length 0`.
  > 同一个请求清掉 `GetBody` 后，重试失败，报错 `http: ContentLength=34 with Body length 0`。
- A body wrapped in an unknown reader type, so the length was unknown and the request was sent chunked, reached the server with 0 bytes on the retry, and the server answered 200. That is the silent case: no error anywhere.
  > 被包进未知 reader 类型的请求体，由于长度未知，请求以分块方式发送；重试时到达服务器的是 0 字节，而服务器回了 200。这就是静默失败的情况：任何地方都没有报错。
- A body streamed through `io.Pipe` and gzip failed the retry with `io: read/write on closed pipe`, after an empty request had already reached the server.
  > 通过 `io.Pipe` 和 gzip 流式发送的请求体，重试时报错 `io: read/write on closed pipe`，而在此之前一个空请求已经到达了服务器。

**The fix: never reuse a request; build one per attempt.**

> **修复方法：绝不复用请求，每次尝试都构建一个新的。**

```go
// Build a fresh request for every attempt from bytes you own.
func sendWithRetry(ctx context.Context, c *http.Client, url string, payload []byte) error {
	for attempt := 0; attempt < 3; attempt++ {
		req, err := http.NewRequestWithContext(ctx, "POST", url, bytes.NewReader(payload))
		if err != nil {
			return err
		}
		req.Header.Set("Content-Type", "application/json")
		resp, err := c.Do(req)
		if err == nil {
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			if resp.StatusCode < 500 {
				return checkStatus(resp)
			}
		}
		time.Sleep(backoff(attempt))
	}
	return errors.New("conversion upload failed after retries")
}
```

- Keep the payload as bytes and create a new body each time, so wrappers such as signing run fresh on every attempt.
  > 把负载保存为字节，每次都创建新的请求体，这样签名之类的包装器在每次尝试时都会重新运行。
- If a wrapper must replace the body, it must also set `GetBody` and `ContentLength`, or redirects with 307 and 308 break the same way.
  > 如果包装器必须替换请求体，它也必须同时设置 `GetBody` 和 `ContentLength`，否则 307 和 308 重定向也会以同样的方式出错。

**Make the server side safe too.** Send an event ID with every conversion so the platform can deduplicate retries. A test that fails the first attempt and checks the second request's body would have caught this in CI.

> **服务端也要做到安全。** 每个转化都带上事件 ID，让平台能对重试去重。一个让第一次尝试失败、再检查第二次请求体的测试，本可以在 CI 中发现这个问题。

**Trade-offs.** Buffering costs one copy per event, which is small here; for very large uploads, set `GetBody` to reopen a file.

> **权衡。** 缓存负载意味着每个事件多一份拷贝，在这里很小；对于非常大的上传，设置 `GetBody` 来重新打开一个文件。

</details>

## 2. Fraud screening at checkout for 100,000 stores: decide within 300 ms, avoid blocking good shoppers, and learn from chargebacks that arrive weeks later

**为 10 万家店铺做结账反欺诈：300 毫秒内给出结论，避免误拦正常顾客，并从几周后才到来的拒付中学习** · `System Design` · `Senior`

### Question · 题目

Merchants lose money to stolen cards: the order ships, and weeks later the card owner disputes the charge. Some merchants also complain that legitimate customers are declined. You are asked to design a fraud check that runs at checkout for every store on the platform, adds no more than 300 ms, and gets better over time.

> 商家因盗刷信用卡而蒙受损失：订单发货了，几周后持卡人对这笔扣款提出争议。也有商家抱怨正常顾客被拒绝。你需要设计一个对平台上每家店铺都在结账时运行的反欺诈检查，增加的延迟不超过 300 毫秒，并且会随着时间推移变得更准。

Design the decision path, the data, and the feedback loop.

> 设计决策链路、所需数据和反馈闭环。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Shape of the system.** A fast synchronous decision at checkout, slower checks after payment, and a slow loop that learns from outcomes:

> **系统的形态。** 结账时做一个快速的同步决策，支付后做较慢的检查，再加一个从结果中学习的慢循环：

```text
checkout ──> score(order) within the budget ──> approve | step-up (3DS) | review | decline
                 │                                  │
                 ├─ velocity counters (Redis)       └─ timeout: merchant policy decides
                 ├─ rules (merchant + platform)
                 └─ model score
after capture ──> async enrichment ──> hold fulfillment if risk rises
weeks later   ──> chargebacks / refunds ──> labels ──> retrain, re-tune thresholds
```

**The synchronous path.** Everything must come from data that is already precomputed or cheap to read:

> **同步链路。** 所有东西都必须来自已经预先计算好、或者读取成本很低的数据：

- Velocity counters in Redis, keyed by hashed card fingerprint, email, device and IP: orders and declined attempts in the last minutes and hours, across all stores. Many cards tried from one device is a strong signal no single merchant can see.
  > Redis 里的频率计数器，按哈希后的卡指纹、邮箱、设备和 IP 作为键：跨所有店铺统计最近几分钟、几小时内的订单数和被拒尝试次数。一个设备上试了很多张卡是强烈的信号，而任何单个商家都看不到。
- Order features: value compared with the store's usual basket, billing and shipping mismatch, card country against IP country, new account, rushed shipping on high-resale items.
  > 订单特征：与店铺平常客单价相比的金额、账单地址与收货地址不一致、发卡国家与 IP 所在国家不一致、新账户、高转售价值商品选择加急配送。
- Rules for hard limits and merchant preferences, plus a model score for everything else. Rules are explainable; the model catches patterns rules miss.
  > 用规则处理硬性限制和商家偏好，其他情况交给模型打分。规则可解释；模型能抓住规则漏掉的模式。

**More than approve and decline.** A middle outcome cuts both losses and false declines: step-up authentication with 3-D Secure for medium risk, which can also move fraud liability to the card issuer, or manual review for high-value orders. Decline only when the risk is clear.

> **不止批准和拒绝两种结果。** 一个中间选项能同时减少损失和误拒：中等风险时用 3-D Secure 做加强验证，这还可能把欺诈责任转移给发卡行；高价值订单则转人工审核。只有风险明确时才拒绝。

**Failure policy.** If scoring times out, checkout must not hang. Let each merchant choose fail-open (approve and review later) or fail-closed for high-risk categories, and alert when the timeout rate rises. After payment, asynchronous enrichment can still hold fulfillment, which is cheaper than refusing the sale.

> **故障策略。** 如果打分超时，结账不能卡住。让每个商家选择放行（先批准、事后审核），或者对高风险品类选择拦截，并在超时比例上升时告警。支付之后，异步补充分析仍然可以暂缓发货，这比拒绝这笔销售代价更小。

**Learning from late labels.** Chargebacks arrive weeks after the order, so today's model is trained on last month's fraud. Join outcomes back to the decision record, which stores the features exactly as they were at decision time. Keep a small random holdout of orders that skip declines, or you can never measure how many good customers you turned away.

> **从迟到的标签中学习。** 拒付在下单几周后才到来，所以今天的模型是用上个月的欺诈数据训练的。把结果关联回决策记录，决策记录要原样保存决策当时的特征。保留一小部分随机抽取、跳过拒绝环节的订单作为对照组，否则你永远无法衡量自己拒掉了多少正常顾客。

**Trade-offs.** Cross-store signals are powerful but need care with privacy: hash identifiers and explain the data use in merchant terms. Every point of fraud caught is paid for in false declines, so report both to merchants.

> **权衡。** 跨店铺信号很有力，但在隐私方面需要谨慎：对标识符做哈希，并在商家条款中说明数据用途。每多拦住一分欺诈，都要用误拒来买单，所以两者都要报告给商家。

</details>

## 3. A bulk SKU lookup and a batch upsert fail only for the largest merchants with "number of parameters must be between 0 and 65535"

**批量 SKU 查询和批量 upsert 只对最大的商家失败，报错「number of parameters must be between 0 and 65535」** · `Database` · `Medium`

### Question · 题目

The catalog sync builds `WHERE store_id = $1 AND sku IN ($2, $3, ...)` with one placeholder per SKU, and saves products with a multi-row `INSERT ... VALUES` of 12 columns per row. Small stores work. A merchant with 80,000 SKUs gets `number of parameters must be between 0 and 65535` on the lookup, and the upsert fails once a batch passes about 5,400 rows.

> 商品目录同步会构造 `WHERE store_id = $1 AND sku IN ($2, $3, ...)`，每个 SKU 一个占位符；保存商品时用多行 `INSERT ... VALUES`，每行 12 列。小店铺都正常。一个有 8 万个 SKU 的商家，查询时报错 `number of parameters must be between 0 and 65535`；而 upsert 在一个批次超过约 5,400 行后就失败了。

Explain the limit and fix both queries.

> 解释这个限制，并修复这两个查询。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** In the PostgreSQL extended query protocol, the Bind message carries the number of parameters in a 16-bit field, so one statement can have at most 65,535 bound parameters. Drivers check this before sending. In a local test with psql's `\bind`, 65,535 parameters worked, and 65,536 failed with exactly this message. The upsert hits the same wall sooner: 12 columns times 5,462 rows is already 65,544 parameters.

> **原因。** 在 PostgreSQL 的扩展查询协议里，Bind 消息用一个 16 位的字段表示参数个数，所以一条语句最多只能绑定 65,535 个参数。驱动会在发送前检查这一点。在本地用 psql 的 `\bind` 测试，65,535 个参数可以执行，65,536 个就报出了这条错误。upsert 会更早撞上同一堵墙：12 列乘以 5,462 行就已经是 65,544 个参数了。

**The fix: pass arrays, not one parameter per value.**

> **修复方法：传数组，而不是每个值一个参数。**

```sql
-- One parameter, any number of SKUs.
SELECT sku, price_minor FROM products
WHERE store_id = $1 AND sku = ANY($2::text[]);

-- Bulk upsert with one array per column instead of one parameter per value.
INSERT INTO products (store_id, sku, price_minor)
SELECT $1, s, p FROM unnest($2::text[], $3::bigint[]) AS t(s, p)
ON CONFLICT (store_id, sku) DO UPDATE SET price_minor = EXCLUDED.price_minor;
```

- In the same test, `sku = ANY($2::text[])` with a 70,000-element array returned all 70,000 rows, and the `unnest` upsert wrote 70,000 rows in one statement.
  > 在同一个测试中，带 70,000 个元素数组的 `sku = ANY($2::text[])` 返回了全部 70,000 行，`unnest` 方式的 upsert 也在一条语句中写入了 70,000 行。
- The statement text stays the same for every batch size, so the driver can prepare it once, instead of building a new query string with a different number of placeholders each time.
  > 无论批次大小如何，语句文本都保持不变，所以驱动可以只准备一次，而不必每次都构建一个占位符数量不同的新查询字符串。
- For very large loads, `COPY` into a temporary table and then one `INSERT ... SELECT ... ON CONFLICT` is faster still.
  > 对于非常大的数据量，先用 `COPY` 导入临时表，再执行一条 `INSERT ... SELECT ... ON CONFLICT`，速度会更快。

**Still batch, for other reasons.** Removing the parameter limit does not make a 2-million-row upsert a good idea. One huge statement holds locks and generates WAL as a single transaction, and one bad row fails all of it. Batches of a few thousand rows keep transactions short and let you retry a failed batch.

> **仍然要分批，但理由不同。** 去掉参数限制，并不意味着一次 upsert 200 万行是个好主意。一条巨大的语句会作为单个事务持有锁并产生 WAL，而且一行出错就会让整条语句失败。几千行一批，可以让事务保持短小，也能单独重试失败的批次。

**Trade-offs.** Arrays need care with types and `NULL` values, and an `ON CONFLICT` upsert rejects input that contains the same key twice, so deduplicate SKUs in the batch first. Chunking the original `IN` list would also have worked, but it hides the real limit behind a magic number in the code.

> **权衡。** 使用数组时需要注意类型和 `NULL` 值；而且 `ON CONFLICT` upsert 会拒绝同一个键出现两次的输入，所以要先在批次内对 SKU 去重。把原来的 `IN` 列表切块也能解决问题，但那样会把真正的限制藏在代码里的一个魔法数字后面。

</details>

## 4. Stock reservations with Redis WATCH work in tests, and during a flash sale they burn CPU on retries while checkout latency explodes

**用 Redis WATCH 实现的库存预留在测试中正常，到了闪购时却在重试上耗尽 CPU，结账延迟暴涨** · `Middleware` · `Hard`

### Question · 题目

Checkout reserves stock with optimistic locking: `WATCH stock:<sku>`, `GET`, check the count, then `MULTI`, `SET`, `EXEC`, and retry from the start when `EXEC` returns nil because someone else changed the key. Load tests with a few workers were fine. During a flash sale with hundreds of checkout workers on one product, Redis CPU rises, the service spends most of its time retrying, and checkout latency climbs from milliseconds to seconds. Oversold orders did not occur.

> 结账用乐观锁来预留库存：`WATCH stock:<sku>`、`GET`、检查数量，然后 `MULTI`、`SET`、`EXEC`；如果因为别人改了这个 key 而导致 `EXEC` 返回 nil，就从头重试。少量工作线程的压测没有问题。在一次闪购中，几百个结账工作线程同时抢同一个商品，Redis CPU 飙升，服务大部分时间都在重试，结账延迟从毫秒级涨到了秒级。没有出现超卖。

Explain the behavior and redesign the reservation.

> 解释这种现象，并重新设计库存预留。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** `WATCH` is optimistic: it assumes conflicts are rare. Every successful `EXEC` invalidates every other client watching the same key, so with N clients racing for one key, one wins each round and the rest throw their work away and start again. The work per successful reservation grows with contention. Correctness held, which is why no orders were oversold, but the throughput collapsed.

> **原因。** `WATCH` 是乐观的：它假设冲突很少发生。每一次成功的 `EXEC`，都会让所有正在监视同一个 key 的其他客户端失效；所以当 N 个客户端争抢一个 key 时，每一轮只有一个赢家，其余的都把已做的工作丢掉，从头再来。每次成功预留所需的工作量会随争抢程度一起增长。正确性保住了，所以没有出现超卖，但吞吐量崩溃了。

**Measured locally** (Redis 7.0, go-redis, 20 reservations per worker against a stock of 1,000, all on one machine):

> **本地实测**（Redis 7.0、go-redis，每个工作线程预留 20 次，库存 1,000，全部在一台机器上）：

- 10 workers: 200 reservations needed 739 retries. 50 workers: 1,000 reservations needed 15,612 retries and took 512 ms.
  > 10 个工作线程：200 次预留需要 739 次重试。50 个工作线程：1,000 次预留需要 15,612 次重试，耗时 512 毫秒。
- 200 workers: 61,760 retries and 1.57 s to sell 1,000 units.
  > 200 个工作线程：卖出 1,000 件需要 61,760 次重试，耗时 1.57 秒。
- The same work as a Lua script took 9 ms and 34 ms, with no retries, and the same final stock.
  > 用 Lua 脚本完成同样的工作，分别耗时 9 毫秒和 34 毫秒，没有任何重试，最终库存也相同。

Over a real network, each failed round also costs several round trips, so production is worse than these numbers.

> 在真实网络环境下，每一轮失败还要额外付出好几次网络往返，所以线上情况会比这些数字更糟。

**The fix: do the check and the write in one atomic step on the server.**

> **修复方法：在服务器上用一个原子步骤完成检查和写入。**

```go
// Check and decrement in one atomic step: no retries, no lost updates.
var reserve = redis.NewScript(`
local n = tonumber(redis.call('GET', KEYS[1]) or '0')
if n <= 0 then return -1 end
return redis.call('DECR', KEYS[1])
`)

left, err := reserve.Run(ctx, rdb, []string{"stock:" + sku}).Int()
if err == nil && left < 0 {
	return ErrSoldOut
}
```

- Redis runs a script without interleaving other commands, so there is nothing to retry. Keep it short, because a long script blocks every client.
  > Redis 执行脚本时不会穿插执行其他命令，所以不需要任何重试。脚本要保持简短，因为一个长脚本会阻塞所有客户端。
- For a plain counter, `DECR` followed by an `INCR` to undo when the result goes below zero also works without a script.
  > 对于简单的计数器，先 `DECR`，结果小于零时再 `INCR` 撤销，也可以不用脚本实现。
- Reserve with an expiry and confirm on payment, so abandoned checkouts give stock back.
  > 预留时设置过期时间、支付时再确认，这样放弃结账的订单会把库存还回来。

**Where WATCH still fits.** Optimistic locking is right when conflicts are rare and the logic is hard to express in a script, such as editing a document many fields at a time. For a hot counter during a sale, conflicts are the normal case, which is exactly where optimistic locking does worst.

> **WATCH 仍然适用的场景。** 当冲突很少、逻辑又难以用脚本表达时，乐观锁是合适的选择，比如一次编辑一个文档的很多字段。而对于促销期间的热点计数器，冲突才是常态，这恰恰是乐观锁表现最差的地方。

**Trade-offs.** A single hot key still lives on one Redis thread. For very large sales, split stock into several keys and pick one at random, accepting a little complexity when some sub-counters run out first.

> **权衡。** 单个热点 key 仍然只落在一个 Redis 线程上。对于超大型促销，可以把库存拆到多个 key 上并随机选择一个，代价是当某些子计数器先卖完时会多一点复杂度。

</details>

## 5. A wholesale order of 12,000 units shows a negative total, although the total is stored in a long

**一笔 12,000 件的批发订单显示总额为负数，尽管总额是存在 long 里的** · `Java & CS` · `Medium`

### Question · 题目

A B2B merchant places an order for 12,000 units of a product priced at 2,499.00. The order page shows a total of -12,961,672.96, and the payment provider rejects the charge. The order line stores `int unitPriceMinor` and `int quantity`, and the total is computed as `long total = line.unitPriceMinor() * line.quantity();`. The developer points out that the result is a `long`.

> 一位 B2B 商家下了一笔订单，购买 12,000 件单价 2,499.00 的商品。订单页显示总额为 -12,961,672.96，支付服务商拒绝了这笔扣款。订单行保存的是 `int unitPriceMinor` 和 `int quantity`，总额的计算方式是 `long total = line.unitPriceMinor() * line.quantity();`。开发者指出，结果明明是 `long`。

Explain the bug and fix it.

> 解释这个 bug，并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** Java evaluates the right-hand side first, using the types of its operands. Both are `int`, so the multiplication is done in 32-bit arithmetic, overflows silently and wraps around, and only then is the wrong result widened to `long`. 249,900 times 12,000 is 2,998,800,000, which is above `Integer.MAX_VALUE` (2,147,483,647). In a local test the expression produced -1,296,167,296; at this price, any quantity from 8,594 up overflows.

> **原因。** Java 会先按操作数的类型计算右边的表达式。两个操作数都是 `int`，所以乘法以 32 位运算进行，悄无声息地溢出并回绕，然后这个错误的结果才被扩展成 `long`。249,900 乘以 12,000 等于 2,998,800,000，超过了 `Integer.MAX_VALUE`（2,147,483,647）。在本地测试中，这个表达式得到 -1,296,167,296；在这个单价下，数量从 8,594 起都会溢出。

**The fix: widen before multiplying, and fail loudly where wrong money is worse than an error.**

> **修复方法：先扩展再相乘；在金额算错比报错更糟糕的地方，要明确地失败。**

```java
long wrong = line.unitPriceMinor() * line.quantity();        // int * int wraps, then widens
long right = (long) line.unitPriceMinor() * line.quantity(); // widen first

// Or fail loudly instead of wrapping:
long exact = Math.multiplyExact((long) line.unitPriceMinor(), line.quantity());
long total = lines.stream()
    .mapToLong(l -> Math.multiplyExact((long) l.unitPriceMinor(), l.quantity()))
    .reduce(0L, Math::addExact);
```

- Casting one operand to `long` makes the whole multiplication 64-bit; the test then gave 2,998,800,000.
  > 把其中一个操作数转成 `long`，整个乘法就会以 64 位进行；测试中结果变成了 2,998,800,000。
- `Math.multiplyExact` and `addExact` throw `ArithmeticException` on overflow instead of wrapping. With two `int` arguments, the test threw `integer overflow`.
  > `Math.multiplyExact` 和 `addExact` 在溢出时会抛出 `ArithmeticException`，而不是回绕。传入两个 `int` 参数时，测试抛出了 `integer overflow`。
- Watch compound assignment: `int total += someLong` compiles because `+=` hides a narrowing cast. In the test, adding 3,000,000,000L to an `int` gave -1,294,967,296.
  > 注意复合赋值：`int total += someLong` 能够编译通过，因为 `+=` 隐藏了一次窄化转换。在测试中，把 3,000,000,000L 加到一个 `int` 上，得到了 -1,294,967,296。
- Sum with a `long` accumulator, for example `mapToLong(...).sum()`; an `int` running total wrapped in the test as well.
  > 用 `long` 累加器求和，比如 `mapToLong(...).sum()`；测试中用 `int` 累加的总和同样发生了回绕。

**Validate at the edges.** Store money as `long` minor units end to end, cap quantity and line totals at limits that make business sense, and reject negative totals before they reach the payment provider. A property test with large quantities would have caught this.

> **在边界处做校验。** 从头到尾都用 `long` 类型的最小货币单位存储金额，按业务上合理的上限限制数量和行金额，并在负数总额到达支付服务商之前就拒绝它。一个用大数量做的性质测试本可以发现这个问题。

**Trade-offs.** `long` covers any realistic order total in minor units. `BigDecimal` is needed for prices with sub-cent precision, tax rounding rules and currency conversion, at the cost of slower and more verbose code.

> **权衡。** `long` 足以覆盖以最小货币单位表示的任何现实订单总额。对于需要分以下精度的价格、税费舍入规则和货币换算，则需要 `BigDecimal`，代价是代码更慢、更啰嗦。

</details>
