## 1. Merchants' flash sales end hours early: promotion times parsed without a time zone

**商家的限时促销提前几个小时结束：促销时间在解析时没有带时区** · `Go` · `Medium`

### Question · 题目

Merchants enter a promotion's end time in the admin as `2026-11-11 23:59`, meaning their store's local time. The Go service stores it with `time.Parse("2006-01-02 15:04", s)` and ends the sale when `time.Now()` passes it. Merchants in Europe report sales ending an hour or more early, and merchants in the Americas report sales still running after they should have ended. A developer tries adding the zone name, `2026-11-11 23:59 CET`, and the problem does not go away.

> 商家在后台把促销的结束时间输入为 `2026-11-11 23:59`，意思是店铺所在地的本地时间。Go 服务用 `time.Parse("2006-01-02 15:04", s)` 保存它，并在 `time.Now()` 超过这个时间时结束促销。欧洲的商家反馈促销提前了一个小时甚至更久就结束了，而美洲的商家反馈促销到了该结束的时候还在继续。一位开发者尝试加上时区名称 `2026-11-11 23:59 CET`，问题仍然没有消失。

Explain the bug and fix it.

> 解释这个 bug 并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why it happens.** `time.Parse` interprets a value with no zone information as UTC. A local wall-clock time is therefore treated as if it were UTC: for a store east of UTC the sale ends early, and for one west of UTC it ends late. In a local test, `23:59` parsed with `time.Parse` was one hour later than the same text parsed in `Europe/Berlin`, so a Berlin sale would end an hour early.

> **原因。** `time.Parse` 会把不带时区信息的值当作 UTC 来解释。于是一个本地的挂钟时间被当作 UTC 时间来处理：对于位于 UTC 以东的店铺，促销会提前结束；对于位于 UTC 以西的店铺，促销会推迟结束。在本地测试中，用 `time.Parse` 解析的 `23:59`，比在 `Europe/Berlin` 中解析同样的文本晚了一个小时，所以柏林的促销会提前一个小时结束。

**Why the abbreviation did not help.** A zone abbreviation such as `CET` is ambiguous across the world. When Go parses an abbreviation that the current location does not define, it records the name with a zero offset. In the test, `23:59 CET` came back with offset 0, still the wrong instant.

> **为什么时区缩写没有用。** 像 `CET` 这样的时区缩写在全世界范围内是有歧义的。当 Go 解析一个当前时区中没有定义的缩写时，它会记下这个名称，但偏移量为零。在测试中，`23:59 CET` 返回的偏移量是 0，仍然是错误的时间点。

**Fix: parse in the store's time zone, store UTC.** Keep each store's IANA zone name, parse with `time.ParseInLocation`, and convert to UTC for storage and comparisons.

> **修复：在店铺所在时区解析，以 UTC 存储。** 为每个店铺保存其 IANA 时区名称，用 `time.ParseInLocation` 解析，再转换成 UTC 用于存储和比较。

```go
func parsePromoEnd(s, storeTZ string) (time.Time, error) {
	loc, err := time.LoadLocation(storeTZ) // e.g. "Europe/Berlin"
	if err != nil {
		return time.Time{}, err
	}
	t, err := time.ParseInLocation("2006-01-02 15:04", s, loc)
	if err != nil {
		return time.Time{}, err
	}
	return t.UTC(), nil
}
```

- **Accept offsets from APIs.** For machine input, require RFC 3339 with an explicit offset, such as `2026-11-11T23:59:00+01:00`; the test showed it keeps the offset.
  > **API 输入要带偏移量。** 对于机器输入，要求使用带显式偏移量的 RFC 3339 格式，例如 `2026-11-11T23:59:00+01:00`；测试表明它会保留偏移量。
- **Handle daylight-saving gaps.** A local time that does not exist, such as 02:30 on the night clocks spring forward, is moved forward by Go; the test turned 02:30 into 03:30. Warn the merchant instead of silently shifting it.
  > **处理夏令时的空档。** 对于不存在的本地时间，例如时钟拨快那一晚的 02:30，Go 会把它往后顺延；测试中 02:30 变成了 03:30。应该提醒商家，而不是悄悄地挪动它。
- **Ship time zone data.** `time.LoadLocation` needs the zone database; minimal container images may lack it, so embed `time/tzdata` or install it.
  > **附带时区数据。** `time.LoadLocation` 需要时区数据库；精简的容器镜像里可能没有，所以要嵌入 `time/tzdata` 或者安装它。

**Trade-offs.** Storing UTC plus the store's zone makes comparisons simple and correct, but every display must convert back, and a store that changes its zone changes how its future promotions should be read; decide whether existing promotions keep their instant or their wall-clock time, and tell the merchant.

> **取舍。** 存储 UTC 加上店铺时区，让比较变得简单而正确，但每次展示都必须转换回去；而店铺更改时区后，会影响其未来促销该如何理解。要决定已有的促销是保持原来的时间点还是保持原来的挂钟时间，并告知商家。

</details>

## 2. Billing merchants for a subscription plus a share of sales: mid-month plan changes, failed card payments and invoices that must never change

**向商家收取订阅费加销售抽成：月中更换套餐、信用卡扣款失败，以及永远不能更改的发票** · `System Design` · `Senior`

### Question · 题目

The platform charges each merchant a monthly plan fee plus a percentage of sales, and some add-ons are billed by usage, such as SMS sent or AI-generated descriptions. Merchants upgrade and downgrade mid-month, cards fail, refunds of orders should reduce the sales fee, and finance needs invoices that match the ledger exactly. Today a nightly script computes charges from the orders table and sometimes bills twice after a rerun.

> 平台每月向每个商家收取套餐费，再加上销售额的一定比例；一些增值服务按用量计费，例如发送的短信条数或 AI 生成的商品描述数。商家会在月中升级或降级，信用卡扣款会失败，订单退款应该减少销售抽成，而财务需要与账本完全一致的发票。目前由一个夜间脚本从订单表计算费用，重跑时有时会重复收费。

As the senior engineer, design the billing system.

> 作为资深工程师，设计这个计费系统。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Principle: billing is an append-only ledger.** Record every billable fact as an immutable usage event with an idempotency key, rate events into line items, and close them into invoices that are never edited. Corrections are new entries, such as credit notes, never updates to old ones. This makes reruns safe and lets finance reconcile every number.

> **原则：计费是一个只追加的账本。** 把每一个计费事实都记录为带幂等键的不可变用量事件，把事件计价为明细项，再结账生成永不修改的发票。更正以新条目的形式出现，例如贷项通知单，而绝不是修改旧条目。这样重跑是安全的，财务也能核对每一个数字。

- **Usage events.** Order paid, order refunded, SMS sent: each with merchant, amount in the order currency, occurred-at time and a unique event ID from its source, so duplicates are ignored on insert.
  > **用量事件。** 订单已支付、订单已退款、短信已发送：每条事件都包含商家、以订单币种计的金额、发生时间，以及来自其源头的唯一事件 ID，这样重复事件在插入时就会被忽略。
- **Rating.** A rating step applies the plan in force at the event time: the sales percentage, included quotas and overage prices. Plans are versioned, so a price change never rewrites past charges.
  > **计价。** 计价步骤采用事件发生时生效的套餐：销售抽成比例、包含的额度以及超额单价。套餐有版本管理，所以价格变动永远不会改写过去的费用。
- **Plan changes.** Model each change as an effective-dated subscription period; upgrades charge the prorated difference at once, downgrades take effect at the next period. Write the proration rule down and show it on the invoice.
  > **更换套餐。** 把每次更换建模为一个带生效日期的订阅周期；升级立即按比例收取差价，降级从下一个周期开始生效。把按比例计费的规则写下来，并在发票上展示。
- **Refunds.** A refunded order creates a negative event in the period it happens, not an edit to the closed invoice where the sale was billed.
  > **退款。** 一笔退款订单在退款发生的那个周期产生一个负向事件，而不是去修改当初计费那笔销售时已经结账的发票。

```text
usage_events (idempotent) -> rating (plan version at event time) -> line_items
period close -> invoice (immutable, numbered) -> payment attempt (idempotency key)
failed payment -> dunning schedule -> retries, emails, grace period -> restrict features
corrections -> credit note / adjustment entry (never edit an issued invoice)
```

**Payments and dunning.** Charge each invoice with an idempotency key at the payment provider, so a retried request cannot charge twice. On failure, follow a dunning schedule of retries and emails with a grace period before features are restricted, and record each attempt. Reconcile daily against the provider's settlement reports.

> **支付与催缴。** 用幂等键在支付服务商处为每张发票扣款，这样重试的请求就不会重复扣款。扣款失败时，按照催缴计划进行重试和发送邮件，在限制功能之前给予一段宽限期，并记录每一次尝试。每天与支付服务商的结算报告进行对账。

**Money and time details.** Store amounts as integers in minor units with their currency, convert to the billing currency with a recorded rate, and define periods in one time zone per merchant. Tax depends on the merchant's country and must be computed per invoice line with the rule version recorded.

> **金额与时间的细节。** 以最小货币单位的整数连同币种来存储金额，用记录下来的汇率换算成计费币种，并为每个商家在一个时区内定义计费周期。税费取决于商家所在国家，必须针对每一行发票明细计算，并记录所用规则的版本。

**Trade-offs.** An event-sourced ledger costs more storage and engineering than a nightly sum, but it makes reruns, audits and disputes tractable. Building on a billing provider saves much of this work but limits custom pricing such as percentage fees with caps; many platforms keep rating in-house and delegate invoicing and payment collection. Whatever you choose, never let a rerun or a plan change alter an invoice already sent.

> **取舍。** 基于事件溯源的账本比每晚做一次汇总需要更多的存储和工程投入，但它让重跑、审计和争议处理变得可控。基于计费服务商来构建能省掉大部分工作，但会限制自定义定价，例如带封顶的比例抽成；很多平台把计价留在自己系统内，而把开票和收款交给服务商。无论你选择哪种方式，都绝不能让一次重跑或一次套餐变更改动已经发出的发票。

</details>

## 3. "Highest price first" shows products without a price at the top, and the fix makes the query slow

**「价格从高到低」把没有价格的商品排在了最前面，而修复之后查询又变慢了** · `Database` · `Medium`

### Question · 题目

The storefront sorts a category by `ORDER BY price DESC LIMIT 20`. Products that have no price yet, stored as `NULL`, appear at the top. A developer changes the query to `ORDER BY price DESC NULLS LAST`, which fixes the order, but the page becomes slow for large stores. Pagination uses "`WHERE price < :last_price`" and some products never appear on any page.

> 店铺前台用 `ORDER BY price DESC LIMIT 20` 对一个类目进行排序。还没有价格、以 `NULL` 存储的商品出现在了最前面。一位开发者把查询改成了 `ORDER BY price DESC NULLS LAST`，排序问题解决了，但对大店铺来说页面变慢了。分页使用的是「`WHERE price < :last_price`」，而有些商品在任何一页上都不会出现。

Explain all three problems and fix them.

> 解释这三个问题，并修复它们。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why NULLs come first.** In Postgres, NULL sorts as larger than any value by default, so ascending order puts NULLs last and descending order puts them first. In a local test with 200,000 products, 10% without a price, the top three of `ORDER BY price DESC` were all NULL.

> **为什么 NULL 排在最前。** 在 Postgres 中，NULL 默认被当作比任何值都大来排序，所以升序时 NULL 排在最后，降序时排在最前。在一个有 20 万个商品、其中 10% 没有价格的本地测试中，`ORDER BY price DESC` 的前三名全都是 NULL。

**Why the fix got slow.** The index is on `(store_id, price)` in ascending order with the default NULL placement. Read backwards, it delivers `price DESC NULLS FIRST`, which matched the old query. `DESC NULLS LAST` matches neither direction, so in the test the plan switched from a backward index scan to a sequential scan plus sort. Create an index whose order matches the query.

> **为什么修复之后变慢了。** 索引建在 `(store_id, price)` 上，按升序排列，NULL 的位置是默认的。反向读取时，它提供的是 `price DESC NULLS FIRST`，正好与旧查询相匹配。而 `DESC NULLS LAST` 与哪个方向都不匹配，所以在测试中，执行计划从反向索引扫描变成了顺序扫描加排序。应该创建一个顺序与查询匹配的索引。

```sql
CREATE INDEX CONCURRENTLY products_store_price_desc
    ON products (store_id, price DESC NULLS LAST, id DESC);

SELECT id, price FROM products
WHERE store_id = $1
ORDER BY price DESC NULLS LAST, id DESC
LIMIT 20;
```

**Why products went missing.** `price < :last_price` is never true for NULL, so unpriced products can never appear on a later page. In the test, the condition `price < 5` matched 904 rows, and adding `OR price IS NULL` matched 20,904. Keyset pagination also needs a unique tie-breaker, because many products share a price and a comparison on price alone skips or repeats them at page boundaries.

> **为什么有商品不见了。** `price < :last_price` 对 NULL 永远不成立，所以没有价格的商品永远不会出现在后续页面上。在测试中，条件 `price < 5` 匹配了 904 行，而加上 `OR price IS NULL` 后匹配了 20,904 行。键集分页还需要一个唯一的决胜字段，因为很多商品价格相同，只按价格比较会在页面边界处跳过或重复它们。

- **Use the same order everywhere.** The `ORDER BY`, the index and the cursor condition must all use `price DESC NULLS LAST, id DESC`; with the matching index the test plan became an index-only scan.
  > **处处使用相同的顺序。** `ORDER BY`、索引和游标条件都必须使用 `price DESC NULLS LAST, id DESC`；有了匹配的索引后，测试中的执行计划变成了仅索引扫描。
- **Handle the NULL section explicitly.** Paginate priced products by `(price, id)`, then continue into unpriced ones by `id`; the cursor records which section it is in.
  > **显式处理 NULL 部分。** 先按 `(price, id)` 对有价格的商品分页，再按 `id` 继续翻到没有价格的商品；游标中记录当前处于哪一部分。
- **Question the NULLs.** If unpriced products should not be sold, filter them out of the storefront entirely instead of sorting them.
  > **审视这些 NULL。** 如果没有价格的商品本就不该出售，就干脆把它们从前台过滤掉，而不是去排序它们。

**Trade-offs.** An extra index for each sort order speeds reads but slows writes and uses disk, so add only the orders the storefront offers. Replacing NULL with a sentinel price simplifies sorting but lies in the data and leaks into reports; an explicit NULL with clear rules is usually better.

> **取舍。** 为每种排序方式额外建一个索引能加快读取，但会拖慢写入并占用磁盘，所以只为前台实际提供的排序方式建立索引。用一个哨兵价格来代替 NULL 能简化排序，但会让数据失真，并渗透到报表中；一个规则清晰的显式 NULL 通常更好。

</details>

## 4. A Lua script that recalculates stock for a large merchant makes Redis answer BUSY to every service, and SCRIPT KILL refuses to stop it

**一个为大商家重新计算库存的 Lua 脚本让 Redis 对所有服务都返回 BUSY，而 SCRIPT KILL 也拒绝终止它** · `Middleware` · `Hard`

### Question · 题目

To keep stock counters consistent, a developer wrote a Lua script that loops over every variant key of a merchant and rewrites its available quantity. It is fast for small stores. For a merchant with hundreds of thousands of variants, every service using the same Redis starts failing with `BUSY Redis is busy running a script`, checkout stops, and an operator's `SCRIPT KILL` returns `UNKILLABLE`.

> 为了让库存计数器保持一致，一位开发者写了一个 Lua 脚本，遍历某个商家的每一个规格键并重写其可用数量。对小店铺来说它很快。但对于一个有几十万个规格的商家，所有使用同一个 Redis 的服务都开始报错 `BUSY Redis is busy running a script`，结账停止了，而运维执行的 `SCRIPT KILL` 返回了 `UNKILLABLE`。

Explain what happened, how to recover, and how to redesign the job.

> 解释发生了什么、如何恢复，以及如何重新设计这个任务。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why everything stops.** Redis runs a Lua script atomically: no other command runs until it finishes. That atomicity is why scripts are useful, but it also means one long script blocks every client. After a configured threshold the server starts answering other clients with `BUSY`, accepting only `SCRIPT KILL` or `SHUTDOWN NOSAVE`. In a local test, a script looping for several seconds made `PING` and `GET` from another client return `BUSY`.

> **为什么一切都停了。** Redis 以原子方式执行 Lua 脚本：在它完成之前，不会运行任何其他命令。这种原子性正是脚本有用的原因，但也意味着一个长时间运行的脚本会阻塞所有客户端。超过所配置的阈值后，服务器开始对其他客户端返回 `BUSY`，只接受 `SCRIPT KILL` 或 `SHUTDOWN NOSAVE`。在本地测试中，一个循环了好几秒的脚本，让另一个客户端的 `PING` 和 `GET` 都返回了 `BUSY`。

**Why it could not be killed.** `SCRIPT KILL` works only on a script that has not written anything yet; killing it then leaves the data unchanged. Once a script has written, stopping it halfway would break the all-or-nothing promise, so Redis refuses. The test showed exactly this: a read-only script was killed, and a script that had written one key returned `UNKILLABLE`.

> **为什么无法终止它。** `SCRIPT KILL` 只对尚未写入任何内容的脚本有效；此时终止它，数据保持不变。一旦脚本已经写入，中途停止就会破坏「要么全做要么全不做」的承诺，所以 Redis 会拒绝。测试正好显示了这一点：一个只读脚本被终止了，而一个已经写入了一个键的脚本返回了 `UNKILLABLE`。

**Recovery options are both bad.** Wait for the script to finish, with Redis unavailable meanwhile, or `SHUTDOWN NOSAVE`, which stops the server and loses writes since the last persistence point; with replicas, failing over to one is often the faster path. Decide this in a runbook before it happens.

> **两种恢复方式都不好。** 要么等脚本执行完，期间 Redis 一直不可用；要么执行 `SHUTDOWN NOSAVE`，它会停止服务器，并丢失自上次持久化以来的写入；如果有副本，切换到副本往往更快。要在事情发生之前就在运维手册中定好如何处理。

```text
for each batch of 500 variant keys (from SCAN or an index set):
    EVALSHA recompute_batch 500 key1..key500 merchant_id
    sleep briefly; record progress (cursor) in the job state
```

- **Keep scripts short and bounded.** A script should touch a small, known set of keys passed in `KEYS`, so its run time does not grow with merchant size.
  > **让脚本短小且有界。** 一个脚本应该只处理通过 `KEYS` 传入的一小组已知的键，这样它的运行时间就不会随商家规模增长。
- **Batch the job outside Redis.** Iterate in the application, run one bounded script per batch, and store progress so the job can resume.
  > **在 Redis 之外对任务分批。** 在应用中迭代，每一批运行一个有界的脚本，并保存进度，让任务可以断点续传。
- **Isolate workloads.** Do not run bulk maintenance on the same Redis that serves checkout; use a separate instance or run it off-peak.
  > **隔离不同的负载。** 不要在为结账服务的同一个 Redis 上运行批量维护任务；使用单独的实例，或在低峰期运行。
- **Alert on script time.** Watch slow logs and latency, and test scripts against the largest merchant's data before release.
  > **对脚本耗时发出告警。** 关注慢日志和延迟，并在发布之前用最大商家的数据来测试脚本。

**Trade-offs.** Batching gives up atomicity across the whole merchant: during the job, some variants are recalculated and others are not. That is usually acceptable if each batch is atomic and readers tolerate a short mix; if not, build the new values under new keys and switch a pointer at the end.

> **取舍。** 分批会放弃对整个商家的原子性：在任务执行期间，一部分规格已重新计算，另一部分还没有。如果每一批本身是原子的，并且读取方能容忍短时间的新旧混合，这通常是可以接受的；如果不能容忍，就把新值写到新的键下，最后再切换一个指针。

</details>

## 5. Deploys hang until the pod is killed because a sync worker swallows InterruptedException

**部署一直卡住直到 Pod 被强制杀掉，原因是一个同步 worker 吞掉了 InterruptedException** · `Java & CS` · `Hard`

### Question · 题目

A Java service runs catalog-sync workers on an `ExecutorService`. Each worker loops: fetch a batch, push it to an ad platform, then `Thread.sleep` to respect the rate limit. On shutdown the service calls `shutdownNow()` and `awaitTermination(30, SECONDS)`. Every deploy, pods sit in "Terminating" until Kubernetes kills them, and the last batch is sometimes half-sent.

> 一个 Java 服务在 `ExecutorService` 上运行商品目录同步 worker。每个 worker 循环执行：获取一批数据，推送到广告平台，然后调用 `Thread.sleep` 以遵守限流。关闭时，服务调用 `shutdownNow()` 和 `awaitTermination(30, SECONDS)`。每次部署，Pod 都一直停在「Terminating」状态，直到被 Kubernetes 强制杀掉，而最后一批数据有时只发送了一半。

```java
while (!Thread.currentThread().isInterrupted()) {
    pushBatch(nextBatch());
    try {
        Thread.sleep(200);
    } catch (InterruptedException e) {
        log.warn("sleep interrupted", e); // and keep looping
    }
}
```

Explain why shutdown hangs and fix it.

> 解释为什么关闭会卡住，并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**How interruption works.** Java has no way to force a thread to stop; `shutdownNow()` only sets each worker's interrupt flag. Blocking methods such as `sleep` respond by throwing `InterruptedException` and clearing the flag. If the catch block logs and continues, the flag is gone, the loop condition is true again, and the worker runs forever.

> **中断是如何工作的。** Java 没有办法强制让一个线程停止；`shutdownNow()` 只是设置每个 worker 的中断标志。像 `sleep` 这样的阻塞方法会通过抛出 `InterruptedException` 并清除这个标志来响应。如果 catch 块只是记录日志然后继续，标志就没了，循环条件再次为真，worker 就会永远运行下去。

**What the test showed.** With the swallowing worker, `awaitTermination` waited out its full timeout and reported the pool still running; the worker never stopped. With the flag restored in the catch block, the pool terminated within milliseconds. In production, the shutdown waits until the grace period ends and Kubernetes kills the process, cutting off whatever batch is in flight.

> **测试的结果。** 使用吞掉异常的 worker 时，`awaitTermination` 等满了整个超时时间，报告线程池仍在运行；worker 始终没有停止。在 catch 块中恢复中断标志后，线程池在几毫秒内就终止了。在生产环境中，关闭会一直等到宽限期结束，然后 Kubernetes 杀掉进程，切断正在发送的那一批数据。

```java
while (!Thread.currentThread().isInterrupted()) {
    Batch b = nextBatch();
    pushBatch(b);                       // idempotent: safe to resend after a restart
    markDone(b);
    try {
        Thread.sleep(200);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // restore the flag
        break;                              // and leave the loop
    }
}
```

- **Restore or rethrow.** Either call `Thread.currentThread().interrupt()` and exit, or let `InterruptedException` propagate; never swallow it silently, including in libraries and helpers.
  > **恢复或重新抛出。** 要么调用 `Thread.currentThread().interrupt()` 然后退出，要么让 `InterruptedException` 向上传播；绝不要悄悄吞掉它，在库和工具方法中也一样。
- **Stop between batches, not inside one.** Check for shutdown at safe points, and make pushes idempotent so a batch cut off by a kill can be resent after restart.
  > **在批次之间停止，而不是在批次内部。** 在安全点检查是否需要关闭，并让推送具备幂等性，这样被强制终止切断的那一批可以在重启后重新发送。
- **Make blocking calls interruptible or time-bounded.** Network calls do not always respond to interrupts; give HTTP clients timeouts so a stuck call cannot outlive the grace period.
  > **让阻塞调用可以被中断或有时间上限。** 网络调用并不总是会响应中断；给 HTTP 客户端设置超时，这样一个卡住的调用就不会拖过宽限期。
- **Align the timeouts.** The executor's `awaitTermination` plus any other shutdown work must fit inside the Kubernetes grace period.
  > **让各个超时相互匹配。** 执行器的 `awaitTermination` 加上其他关闭工作所需的时间，必须控制在 Kubernetes 的宽限期之内。

**Trade-offs.** Stopping only at batch boundaries makes shutdown slower by up to one batch, so keep batches small or allow cancellation of the push itself. A longer grace period hides the problem and slows every rollout; fixing interrupt handling and idempotency is what makes deploys fast and safe.

> **取舍。** 只在批次边界停止，会让关闭最多慢上一个批次的时间，所以要让批次保持小巧，或者允许取消推送本身。更长的宽限期只会掩盖问题，并拖慢每一次发布；修好中断处理和幂等性，才能让部署既快又安全。

</details>
