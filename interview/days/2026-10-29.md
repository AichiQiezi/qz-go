## 1. Merchants cannot un-pause a campaign or set a budget to zero through the API

**商家无法通过 API 恢复暂停的广告活动，也无法把预算设为零** · `Go` · `Medium`

### Question · 题目

A Go service exposes `PATCH /campaigns/{id}` and forwards changes to an ad platform. The request struct has `Paused bool` and `DailyBudgetMicros int64`, both tagged `omitempty`. Pausing works, but un-pausing does nothing, and setting the budget to 0 to stop spending leaves the old budget in place. Logs show the outgoing body is `{}`.

> 一个 Go 服务提供 `PATCH /campaigns/{id}` 接口，并把修改转发给广告平台。请求结构体里有 `Paused bool` 和 `DailyBudgetMicros int64`，都带有 `omitempty` 标签。暂停是有效的，但恢复投放没有任何效果；把预算设为 0 来停止花费时，原来的预算也依然生效。日志显示发出去的请求体是 `{}`。

Explain why and how to model partial updates in Go.

> 解释原因，以及在 Go 中应如何建模部分更新。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** `omitempty` drops fields that hold their zero value: `false`, `0`, `""`, nil. For a partial update, "set to false" and "not provided" are different instructions, but with plain `bool` and `int64` both are the zero value and both disappear. A local test printed `{}` for `Paused: false, DailyBudgetMicros: 0`. The newer `omitzero` option (Go 1.24) does not help here either: it also omits `false`.

> **原因。** `omitempty` 会丢弃取零值的字段：`false`、`0`、`""`、nil。对于部分更新来说，“设为 false”和“没有提供”是两种不同的指令，但用普通的 `bool` 和 `int64` 时，两者都是零值，也都会消失。本地测试中，`Paused: false, DailyBudgetMicros: 0` 输出的是 `{}`。较新的 `omitzero` 选项（Go 1.24）在这里同样没用：它也会省略 `false`。

**Fix: make "absent" representable.** Use pointer fields: nil means "not provided", and a non-nil pointer carries the value, including `false` and `0`. Decoding works the same way, so the handler can tell which fields the client sent:

> **修复：让“缺失”可以被表示出来。** 使用指针字段：nil 表示“没有提供”，非 nil 的指针则携带值，包括 `false` 和 `0`。解码时也是同样的道理，所以处理函数能分辨客户端发送了哪些字段：

```go
type CampaignPatch struct {
	Paused            *bool  `json:"paused,omitempty"`
	DailyBudgetMicros *int64 `json:"daily_budget_micros,omitempty"`
}

var p CampaignPatch
if err := json.NewDecoder(r.Body).Decode(&p); err != nil { /* 400 */ }
if p.Paused != nil {
	campaign.Paused = *p.Paused // false is applied, not ignored
}
```

- In the test, a patch with `Paused` pointing to `false` and a zero budget encoded as `{"paused":false,"daily_budget_micros":0}`, and decoding `{"paused":false}` set only `Paused`.
  > 在测试中，`Paused` 指向 `false`、预算为零的补丁被编码为 `{"paused":false,"daily_budget_micros":0}`，而解码 `{"paused":false}` 时只设置了 `Paused`。
- If you also need "set to null" (for example clearing an end date), a pointer is not enough; use a small optional type that records presence and null separately, or decode into `map[string]json.RawMessage`.
  > 如果还需要表达“设为 null”（例如清空结束日期），指针就不够用了；可以用一个分别记录“是否出现”和“是否为 null”的小型可选类型，或者解码到 `map[string]json.RawMessage`。
- Validate values explicitly: a zero budget should be a deliberate, allowed state, not an accident of defaults.
  > 显式校验取值：零预算应该是一个有意为之、被允许的状态，而不是默认值造成的意外。

**Trade-offs.** Pointers make code noisier and need nil checks everywhere; a dedicated `Optional[T]` generic type keeps intent clearer. For full replacements (PUT), plain values without `omitempty` are simpler and safer. Write a test for every field that can legitimately be zero, because the happy path with non-zero values hides this bug.

> **取舍。** 指针会让代码更啰嗦，到处都需要判空；一个专门的 `Optional[T]` 泛型类型能让意图更清楚。对于整体替换（PUT），不带 `omitempty` 的普通值更简单、更安全。要为每个可能合法为零的字段写测试，因为只用非零值的正常路径会把这个 bug 掩盖掉。

</details>

## 2. Order numbers collide after the order service scales to many instances

**订单服务扩展到多个实例之后，订单号开始冲突** · `System Design` · `Hard`

### Question · 题目

Order numbers were generated as `merchant prefix + yyyyMMddHHmmss + 3 random digits`. After scaling the order service to 20 instances for a sale, inserts started failing on the unique index, and some customers saw each other's order numbers in confirmation emails that were sent before the insert failed. You need IDs that are unique across instances and regions, roughly time-ordered, and not guessable from outside.

> 订单号的生成方式是“商家前缀 + yyyyMMddHHmmss + 3 位随机数”。为了大促把订单服务扩到 20 个实例之后，插入开始在唯一索引上失败，而且有些顾客在确认邮件中看到了别人的订单号，因为这些邮件是在插入失败之前就发出去的。你需要的 ID 要在多个实例和区域之间唯一、大致按时间排序，并且从外部无法猜测。

Design ID generation for orders.

> 设计订单的 ID 生成方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why it failed.** Three random digits per second give only a thousand values; with many instances creating orders in the same second, collisions are a matter of time (the birthday problem). And sending the email before the database confirmed the insert leaked a number that later belonged to someone else.

> **为什么会失败。** 每秒 3 位随机数只能提供一千个取值；在许多实例同一秒内创建订单的情况下，冲突只是时间问题（生日问题）。而且在数据库确认插入之前就发邮件，会把一个后来属于别人的号码泄露出去。

**Separate two identifiers.** An internal ID used as the primary key and in APIs, and a human-friendly order number shown to shoppers. They have different requirements and should not be the same field.

> **把两种标识分开。** 一个是作为主键并在 API 中使用的内部 ID，另一个是展示给顾客的、便于人阅读的订单号。它们的要求不同，不应该是同一个字段。

- **Internal ID options.** A UUIDv7 or ULID combines a millisecond timestamp with random bits: no coordination, time-ordered, good for B-tree indexes. A Snowflake-style 64-bit ID (timestamp, worker ID, per-millisecond sequence) is smaller and strictly ordered per worker but needs unique worker IDs and protection against clock moving backwards.
  > **内部 ID 的选择。** UUIDv7 或 ULID 把毫秒级时间戳和随机位结合在一起：无需协调、按时间排序、对 B 树索引友好。Snowflake 风格的 64 位 ID（时间戳、worker ID、每毫秒内的序列号）更小，在每个 worker 内严格有序，但需要唯一的 worker ID，并且要防范时钟回拨。
- **Worker IDs.** Lease them from a coordination store with expiry, or derive them from a stable pod ordinal; never from random numbers, which collide like the original scheme.
  > **worker ID。** 从带过期机制的协调存储中租用，或者从稳定的 pod 序号推导；绝不要用随机数，它会像原来的方案一样发生冲突。
- **Clock skew.** If the clock goes backwards, a Snowflake generator must wait or refuse rather than reuse timestamps. UUIDv7 tolerates small skew because of its random bits, at the cost of looser ordering.
  > **时钟偏差。** 如果时钟回拨，Snowflake 生成器必须等待或拒绝，而不能重复使用时间戳。UUIDv7 因为有随机位，可以容忍较小的偏差，代价是排序没那么严格。
- **Shopper-facing number.** Per merchant, a short readable number such as `SHOP-104233`, allocated from a per-merchant counter in the database inside the order transaction, or derived from the internal ID with an encoding that is not sequential across merchants, so competitors cannot read order volume from it.
  > **面向顾客的订单号。** 按商家生成一个简短易读的编号，例如 `SHOP-104233`，在订单事务中从数据库里每个商家的计数器分配；或者用一种在不同商家之间不连续的编码从内部 ID 推导出来，这样竞争对手就无法从中读出订单量。

**Process order.** Send emails and webhooks only after the order transaction commits, ideally from an outbox, so nothing external ever refers to an order that does not exist.

> **处理顺序。** 只在订单事务提交之后才发送邮件和 webhook，最好通过 outbox 发送，这样外部就永远不会引用一个并不存在的订单。

**Trade-offs.** UUIDs are 128 bits and need no infrastructure; Snowflake IDs are compact but add worker-ID management and clock handling. Per-merchant counters give nice numbers but serialize order creation per merchant on one row, which is fine for most merchants and a hotspot for the very largest; those can use preallocated ranges. Time-ordered IDs also reveal creation time, which is usually acceptable for internal IDs.

> **取舍。** UUID 有 128 位，不需要任何基础设施；Snowflake ID 很紧凑，但增加了 worker ID 管理和时钟处理的负担。每个商家一个计数器能得到好看的编号，但会让同一商家的下单在一行上串行化，这对大多数商家没问题，对体量最大的商家则会成为热点；这些商家可以使用预分配的号段。按时间排序的 ID 也会暴露创建时间，对内部 ID 来说这通常可以接受。

</details>

## 3. Invoice numbers must have no gaps, but the sequence skips numbers

**发票号必须连续无间隔，但序列会跳号** · `Database` · `Hard`

### Question · 题目

Merchants in some markets must issue invoices with consecutive numbers per merchant, and auditors flagged gaps. Invoice numbers come from a PostgreSQL sequence, `nextval('invoice_seq')`, inside the order transaction. When payment capture fails, the transaction rolls back, and the number is never used.

> 某些市场的商家必须按商家开具编号连续的发票，审计人员发现了编号中的间隔。发票号来自一个 PostgreSQL 序列 `nextval('invoice_seq')`，在订单事务中调用。当支付扣款失败时，事务回滚，这个号码就再也不会被使用。

Explain why sequences leave gaps and how to issue gapless numbers safely.

> 解释为什么序列会留下间隔，以及如何安全地发放连续无间隔的编号。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** Sequences are designed for speed, not for gaplessness: `nextval` is not rolled back when the transaction aborts, so other transactions never wait for it. In a PostgreSQL 16 test, inserting with `nextval`, then doing the same in a rolled-back transaction, then inserting again produced invoice numbers 1 and 3. Caching and crashes can also skip values. Sequences are also global unless you create one per merchant, which does not scale well.

> **原因。** 序列是为速度设计的，而不是为了不留间隔：事务中止时 `nextval` 不会回滚，因此其他事务永远不必等待它。在 PostgreSQL 16 的测试中，先用 `nextval` 插入一行，再在一个被回滚的事务中做同样的操作，然后再插入一次，得到的发票号是 1 和 3。缓存和崩溃也可能导致跳号。另外，除非为每个商家单独建一个序列，否则序列是全局的，而按商家建序列的扩展性并不好。

**Fix: a counter row updated in the same transaction.** Keep one row per merchant and increment it in the transaction that creates the invoice. If the transaction rolls back, the increment rolls back too, so no number is lost. The row lock serializes invoice creation per merchant: a second transaction waits until the first commits or rolls back.

> **修复：在同一事务中更新计数器行。** 每个商家保留一行，在创建发票的那个事务中把它加一。如果事务回滚，这次加一也会一并回滚，所以不会丢失任何号码。行锁会让同一商家的发票创建串行化：第二个事务要等到第一个提交或回滚之后才能继续。

```sql
WITH c AS (
  UPDATE invoice_counter
     SET next_no = next_no + 1
   WHERE merchant_id = $1
  RETURNING next_no - 1 AS no
)
INSERT INTO invoice (merchant_id, no, order_id, ...)
SELECT $1, no, $2, ... FROM c;
```

In the same test, a rolled-back allocation followed by two committed ones gave 1 and 2, and a concurrent second transaction blocked on the counter row until the first committed.

> 在同一个测试中，一次被回滚的分配之后再进行两次已提交的分配，得到的是 1 和 2；而一个并发的第二个事务会在计数器行上阻塞，直到第一个事务提交。

- **Keep the locked section short.** Allocate the invoice number at the very end, after slow work such as calling the payment provider has succeeded, so the lock is held for milliseconds, not seconds.
  > **让持锁的区间尽量短。** 在最后一步才分配发票号，也就是在调用支付服务商等慢操作成功之后，这样锁只会被持有几毫秒，而不是几秒。
- **Separate the order from the invoice.** Orders can use any unique ID; only the legally numbered invoice needs the counter, and it is created once payment is final.
  > **把订单和发票分开。** 订单可以使用任意唯一 ID；只有需要按法规编号的发票才需要计数器，而且它在支付最终确认后才创建。
- **Never reuse or delete numbers.** Corrections are made with credit notes that get their own numbers, so the series stays complete and auditable.
  > **绝不重用或删除编号。** 更正通过贷项通知单（credit note）完成，它有自己的编号，这样整个序列保持完整、可审计。

**Trade-offs.** Gapless numbering limits invoice throughput per merchant to one at a time on the counter row, which is fine for most merchants but needs care for very large ones (for example separate series per store or channel, if the local rules allow it). Check the actual legal requirement per market: some require gapless series, others only unique and sequential ones, and the cheaper design is enough there.

> **取舍。** 连续无间隔的编号让每个商家在计数器行上一次只能开一张发票，这对大多数商家没问题，但对体量很大的商家需要小心处理（例如在当地规则允许的情况下，按店铺或渠道分别使用不同的编号序列）。要按市场核实真正的法律要求：有些要求连续无间隔，有些只要求唯一且递增，后一种情况用更便宜的设计就够了。

</details>

## 4. Migrating the order event pipeline from RabbitMQ to Kafka without losing or duplicating events

**把订单事件管道从 RabbitMQ 迁移到 Kafka，同时不丢失、不重复事件** · `Middleware` · `Senior`

### Question · 题目

Order events (created, paid, refunded) flow through RabbitMQ to six consumers: email, inventory, analytics, ad-conversion upload, fraud checks and a webhook dispatcher. The team wants Kafka for replay, longer retention and higher throughput. The pipeline cannot stop, and the conversion uploader and inventory must not double-count events.

> 订单事件（已创建、已支付、已退款）通过 RabbitMQ 流向六个消费者：邮件、库存、分析、广告转化回传、风控检查和 webhook 分发器。团队希望迁到 Kafka，以获得重放能力、更长的保留期和更高的吞吐量。管道不能停，而且转化回传和库存不能重复计算事件。

Plan the migration.

> 规划这次迁移。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Migrate one direction at a time and make duplicates harmless before you start, because during any migration some events will be seen twice. Producers move first and publish to both systems; consumers then move one by one; RabbitMQ is retired only when nothing reads from it.

> **核心思路。** 一次只迁移一个方向，并且在开始之前就让重复变得无害，因为任何迁移过程中都会有一些事件被看到两次。生产者先迁移，同时向两个系统发布；然后消费者逐个迁移；只有当没有任何东西再从 RabbitMQ 读取时，才把它下线。

**Step 0: idempotent consumers.** Every event gets a stable `event_id` assigned once at the source, plus the order ID and a version. Each consumer records processed event IDs (or applies changes conditionally on version) so a replayed or doubly delivered event has no effect. The conversion uploader also passes the event ID to the ad platforms for their deduplication.

> **第 0 步：幂等的消费者。** 每个事件在源头就分配一个稳定的 `event_id`，并带上订单 ID 和版本号。每个消费者记录已处理过的事件 ID（或者根据版本号有条件地应用变更），这样重放的或被投递两次的事件就不会产生影响。转化回传服务还会把事件 ID 传给广告平台，供它们去重。

**Step 1: publish from an outbox to both.** Write events to an outbox table in the same transaction as the order change, and have a relay publish each outbox row to both RabbitMQ and Kafka. Publishing directly to two brokers from application code cannot be atomic, so one would eventually miss events the other has. Key Kafka messages by order ID so each order's events stay in order within a partition.

> **第 1 步：从 outbox 向两边发布。** 在修改订单的同一个事务中把事件写入 outbox 表，由一个中继进程把每一行 outbox 记录同时发布到 RabbitMQ 和 Kafka。在应用代码里直接向两个 broker 发布不可能是原子的，所以迟早会有一边漏掉另一边收到的事件。Kafka 消息以订单 ID 为键，这样每个订单的事件在分区内保持有序。

- **Step 2: shadow consumers.** Run each new Kafka consumer in shadow mode, computing results without side effects, and compare with the RabbitMQ consumer's results for a few days.
  > **第 2 步：影子消费者。** 让每个新的 Kafka 消费者以影子模式运行，只计算结果、不产生副作用，并与 RabbitMQ 消费者的结果对比几天。
- **Step 3: cut over one consumer at a time.** Stop the RabbitMQ consumer, note the time, and start the Kafka consumer from an offset safely before that point; idempotency absorbs the overlap. Start with low-risk consumers (analytics), finish with inventory and conversions.
  > **第 3 步：逐个切换消费者。** 停掉 RabbitMQ 消费者，记下时间点，然后让 Kafka 消费者从这个时间点之前、足够安全的 offset 开始消费；重叠的部分由幂等性吸收。先切换低风险的消费者（分析），最后再切换库存和转化回传。
- **Step 4: retire RabbitMQ.** When every consumer reads from Kafka and the RabbitMQ queues are empty, stop publishing there, then remove the exchanges.
  > **第 4 步：下线 RabbitMQ。** 当所有消费者都从 Kafka 读取、并且 RabbitMQ 的队列已经清空时，停止向它发布，然后删除相关的 exchange。

**Semantics that change.** RabbitMQ features such as per-message TTL, dead-letter exchanges, priorities and routing keys have no direct Kafka equivalent; plan retry topics and dead-letter topics explicitly. Ordering in Kafka is per partition only, and a slow message blocks its partition, so give slow consumers their own consumer groups and handle poison messages by parking them rather than retrying forever.

> **会发生变化的语义。** RabbitMQ 的单条消息 TTL、死信交换机、优先级和路由键等特性，在 Kafka 中没有直接对应的功能；要显式规划重试主题和死信主题。Kafka 只在分区内保证顺序，一条慢消息会阻塞它所在的分区，所以要给慢消费者单独的消费者组，并把毒消息转存起来，而不是无限重试。

**Trade-offs.** Dual publishing doubles broker load and operational work for weeks; a big-bang switch is shorter but risks losing events during the cutover window. Rollback must stay possible until the end: keep RabbitMQ publishing until the last consumer has run stably on Kafka. Measure end-to-end lag and per-consumer error rates before and after each cutover.

> **取舍。** 双写发布会在好几周内让 broker 负载和运维工作量翻倍；一次性切换耗时更短，但在切换窗口内有丢失事件的风险。直到最后都必须保留回滚的可能：在最后一个消费者在 Kafka 上稳定运行之前，保持向 RabbitMQ 发布。每次切换前后都要测量端到端延迟和各消费者的错误率。

</details>

## 5. Adding to a list of SKUs throws UnsupportedOperationException after a refactor

**重构之后，向一个 SKU 列表添加元素时抛出 UnsupportedOperationException** · `Java & CS` · `Medium`

### Question · 题目

A refactor replaced `.collect(Collectors.toList())` with the shorter `.toList()` in a service that builds the SKU list for a feed export. A later step adds bundle SKUs to that list, and now every export fails with `UnsupportedOperationException`. In another place, `Arrays.asList(...)` lets you change elements but not add them.

> 一次重构把一个为 feed 导出构建 SKU 列表的服务中的 `.collect(Collectors.toList())` 换成了更短的 `.toList()`。后续步骤会往这个列表中添加组合商品的 SKU，现在每次导出都以 `UnsupportedOperationException` 失败。另一处的 `Arrays.asList(...)` 则允许修改元素，但不允许添加元素。

Explain the different kinds of lists and how to avoid this class of bug.

> 解释这几种不同的列表，以及如何避免这一类 bug。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** `Stream.toList()` (Java 16+) returns an unmodifiable list, while `Collectors.toList()` makes no guarantee about mutability and in practice returns an `ArrayList`. Code that silently relied on mutability breaks when the collector changes. A local Java 21 test confirmed it: adding to `Stream.toList()` throws `UnsupportedOperationException`, while the `Collectors.toList()` result accepted the add.

> **原因。** `Stream.toList()`（Java 16+）返回的是不可修改的列表，而 `Collectors.toList()` 对可变性不作任何保证，实际上返回的是 `ArrayList`。那些悄悄依赖可变性的代码，在换了收集方式之后就会出错。本地 Java 21 测试证实了这一点：向 `Stream.toList()` 添加元素会抛出 `UnsupportedOperationException`，而 `Collectors.toList()` 的结果可以正常添加。

**The family of lists.**

> **几种列表。**

- `List.of(...)` and `Collectors.toUnmodifiableList()`: unmodifiable, and they reject `null` elements (`List.of("A", null)` throws `NullPointerException`).
  > `List.of(...)` 和 `Collectors.toUnmodifiableList()`：不可修改，并且拒绝 `null` 元素（`List.of("A", null)` 会抛出 `NullPointerException`）。
- `Stream.toList()`: unmodifiable, but it allows `null` elements, a subtle difference from `toUnmodifiableList()`.
  > `Stream.toList()`：不可修改，但允许 `null` 元素，这是它与 `toUnmodifiableList()` 之间一个细微的差别。
- `Arrays.asList(...)`: fixed-size and backed by the array; `set` works, `add` and `remove` throw.
  > `Arrays.asList(...)`：大小固定，并以数组作为底层存储；`set` 可以使用，`add` 和 `remove` 会抛出异常。
- `Collections.unmodifiableList(list)`: a read-only view; changes to the underlying list are still visible through it, so it is not a copy.
  > `Collections.unmodifiableList(list)`：一个只读视图；对底层列表的修改仍然会通过它反映出来，所以它不是副本。

**Fix.** Do not mutate a list you received; build what you need explicitly:

> **修复。** 不要修改你拿到的列表；显式地构建你需要的东西：

```java
List<String> skus = products.stream().map(Product::sku).toList();

// need to add more? make your own mutable copy
List<String> exportSkus = new ArrayList<>(skus);
exportSkus.addAll(bundleSkus);

// or build it in one pass
List<String> all = Stream.concat(skus.stream(), bundleSkus.stream()).toList();
```

**Trade-offs.** Unmodifiable collections make sharing safe and intentions clear, at the cost of an explicit copy when you do need to change something. A good team convention: methods return unmodifiable lists, and callers copy before mutating. Note that unmodifiable does not mean deeply immutable: the elements themselves can still change if they are mutable objects.

> **取舍。** 不可修改的集合让共享变得安全、意图也更清晰，代价是在确实需要修改时要显式复制一份。一个好的团队约定是：方法返回不可修改的列表，调用方在修改前先复制。注意，不可修改并不意味着深度不可变：如果元素本身是可变对象，它们仍然可以被改变。

</details>
