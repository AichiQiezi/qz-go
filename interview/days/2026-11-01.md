## 1. Conversions sent to Meta after the response is written fail with "context canceled"

**在响应写出之后再发往 Meta 的转化事件，以 "context canceled" 失败** · `Go` · `Senior`

### Question · 题目

A checkout service handles `POST /orders`. To keep checkout fast, the handler saves the order, writes the response, and starts a goroutine that sends a Purchase conversion to Meta's Conversions API using `r.Context()`. In production almost every conversion call fails with `context canceled`, and every deploy also loses whatever conversions were still in flight.

> 一个结账服务处理 `POST /orders`。为了让结账保持快速，handler 保存订单、写出响应，然后启动一个 goroutine，用 `r.Context()` 把一个 Purchase 转化事件发送到 Meta 的 Conversions API。在生产环境中，几乎每一次转化调用都以 `context canceled` 失败，而且每次部署还会丢掉所有仍在发送途中的转化事件。

Explain the failure and design a reliable way to do work after the response.

> 解释这个失败的原因，并设计一种可靠的方式来完成响应之后的工作。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why it fails.** The request context belongs to the request. The server cancels it when `ServeHTTP` returns (or when the client goes away), so a goroutine that outlives the handler inherits a context that is about to be cancelled. In a local test, a goroutine holding the request context saw `context canceled` 50 ms after the handler returned. Any call still waiting on the network at that moment is aborted.

> **为什么会失败。** 请求的 context 属于这个请求。当 `ServeHTTP` 返回时（或者客户端断开时），服务器会取消它，所以一个比 handler 活得更久的 goroutine 继承的是一个即将被取消的 context。在本地测试中，一个持有请求 context 的 goroutine 在 handler 返回 50 ms 后看到了 `context canceled`。此时任何仍在等待网络的调用都会被中止。

**The quick fix and its limits.** `context.WithoutCancel(ctx)` (Go 1.21+) returns a context that keeps the parent's values, such as trace IDs and the merchant ID, but is never cancelled and has no deadline. In the same test it kept the value and reported no error. Give it your own timeout:

> **快速修复及其局限。** `context.WithoutCancel(ctx)`（Go 1.21+）返回的 context 保留父 context 的值，比如 trace ID 和商家 ID，但它永远不会被取消，也没有截止时间。在同一个测试中，它保留了这个值，并且没有报告错误。要给它设置你们自己的超时：

```go
bg, cancel := context.WithTimeout(context.WithoutCancel(r.Context()), 10*time.Second)
go func() {
	defer cancel()
	if err := capi.Send(bg, purchase); err != nil {
		log.Printf("conversion %s: %v", purchase.EventID, err)
	}
}()
```

This fixes the error but not the reliability problem. The goroutine is untracked: a deploy kills it, a Meta outage drops events, and a traffic spike can start thousands of goroutines at once.

> 这修复了错误，但没有解决可靠性问题。这个 goroutine 没有被跟踪：一次部署就会杀掉它，一次 Meta 故障就会丢掉事件，一次流量高峰可能同时启动成千上万个 goroutine。

**The reliable design.**

> **可靠的设计。**

- **Outbox.** Write the conversion into an outbox table in the same transaction as the order. If the order exists, the event exists.
  > **发件箱（outbox）。** 在保存订单的同一个事务里，把转化事件写入一张 outbox 表。只要订单存在，事件就一定存在。
- **Bounded workers.** A fixed set of workers reads the outbox, sends with retries and backoff, and marks rows as sent. Concurrency is capped, so a spike becomes a backlog, not a goroutine explosion.
  > **有界的 worker。** 一组固定数量的 worker 读取 outbox，带重试和退避地发送，并把行标记为已发送。并发数是有上限的，所以流量高峰只会变成积压，而不会变成 goroutine 爆炸。
- **Idempotency.** Send the order ID as Meta's `event_id`, so a retry after a timeout is deduplicated instead of counted twice.
  > **幂等。** 把订单 ID 作为 Meta 的 `event_id` 发送，这样超时后的重试会被去重，而不会被重复计数。
- **Graceful shutdown.** Workers stop taking new rows on SIGTERM and finish or release current ones; anything unsent stays in the table for the next instance.
  > **优雅关闭。** 收到 SIGTERM 时，worker 停止领取新的行，并完成或释放手上的行；任何未发送的内容都留在表里，交给下一个实例处理。

**Trade-offs.** The outbox adds a table, a worker and a few seconds of delay, and conversions can arrive late during outages. For conversions, which drive ad optimization and billing reports, that is far better than silently losing them. A detached goroutine with `WithoutCancel` is acceptable only for work you can afford to lose, such as warming a cache.

> **取舍。** outbox 增加了一张表、一个 worker 和几秒的延迟，并且在故障期间转化事件可能会晚到。对于驱动广告优化和计费报表的转化事件来说，这远比悄无声息地丢失它们要好。用 `WithoutCancel` 启动一个脱离请求的 goroutine，只适用于丢了也无妨的工作，比如预热缓存。

</details>

## 2. Deleting a shopper's personal data across a dozen services within 30 days

**在 30 天内删除一位顾客分散在十几个服务中的个人数据** · `System Design` · `Hard`

### Question · 题目

A shopper in the EU asks a merchant to delete their personal data. Their email, name and address live in the order service, the customer service, the email marketing service, search indexes, the analytics warehouse, logs, backups, and audiences already uploaded to Meta and Google. The merchant must also keep invoices for tax purposes. Today support deletes rows by hand, and nobody can prove anything was removed.

> 一位欧盟的顾客要求商家删除他们的个人数据。他们的邮箱、姓名和地址分布在订单服务、客户服务、邮件营销服务、搜索索引、分析数据仓库、日志、备份，以及已经上传到 Meta 和 Google 的受众中。商家还必须出于税务目的保留发票。目前由客服手工删除数据行，没有人能证明任何东西真的被删掉了。

Design an erasure system.

> 设计一个数据删除系统。

<details>
<summary><b>Answer · 参考答案</b></summary>

**The core idea.** Erasure is a distributed workflow, not a `DELETE`. You need to know where personal data lives, ask every owner to remove it, track each step until it is confirmed, and keep proof without keeping the data.

> **核心思路。** 删除是一个分布式工作流，而不是一条 `DELETE`。你需要知道个人数据存在哪里，要求每个数据所有者把它删掉，跟踪每一步直到得到确认，并且在不保留数据本身的前提下保留证据。

**Design.**

> **设计。**

- **Data map.** Each service registers which personal fields it stores and how it handles erasure: delete, anonymize, or retain for a legal reason. A new table with personal data is not allowed without an entry.
  > **数据地图。** 每个服务登记它存储了哪些个人字段，以及它如何处理删除：删除、匿名化，或者出于法律原因保留。没有登记的话，不允许新建含有个人数据的表。
- **Erasure coordinator.** A request becomes a job with one task per service. The coordinator publishes an erasure event; each service handles it idempotently and reports done or failed. Tasks are retried, and anything stuck past a deadline pages the owning team, well before the 30-day limit.
  > **删除协调器。** 一个请求变成一个作业，每个服务对应一个任务。协调器发布一个删除事件；每个服务以幂等的方式处理它，并报告完成或失败。任务会被重试，任何超过期限仍未完成的任务都会通知负责的团队，并且远早于 30 天的上限。
- **Keep what the law requires, minimized.** Invoices stay, but the order record keeps only what tax rules need; marketing profiles, browsing history and search entries go. The decision per field lives in the data map, reviewed by legal.
  > **保留法律要求的内容，并最小化。** 发票要保留，但订单记录只保留税务规则需要的内容；营销画像、浏览历史和搜索条目则要删除。每个字段的处理决定记录在数据地图中，并由法务审核。
- **Third parties.** Remove the shopper from uploaded audiences through each platform's API and record the response. Stop future uploads by adding them to a suppression list keyed by a hash, so the next sync does not re-add them.
  > **第三方。** 通过各平台的 API 把这位顾客从已上传的受众中移除，并记录响应。把他们加入一个以哈希为键的屏蔽名单来阻止以后的上传，这样下一次同步不会把他们重新加回去。
- **Warehouse, logs and backups.** Delete or anonymize warehouse rows in a scheduled job. Keep personal data out of logs in the first place. Backups usually cannot be edited; keep their retention short and re-apply the erasure list after any restore.
  > **数据仓库、日志和备份。** 用定时作业删除或匿名化数据仓库中的行。从一开始就不让个人数据进入日志。备份通常无法修改；要让它们的保留期限保持较短，并在任何一次恢复之后重新执行删除名单。

**Proof.** The job keeps an audit trail: request time, each service's confirmation and time, and what was retained and why, identified by a request ID rather than the shopper's email.

> **证据。** 作业保留一条审计记录：请求时间、每个服务的确认及其时间，以及保留了什么、为什么保留；这些记录用请求 ID 标识，而不是用顾客的邮箱。

**Trade-offs.** A coordinator and a data map cost real engineering effort and slow down teams adding new data stores. Crypto-shredding, encrypting each shopper's data with their own key and deleting the key, makes erasure fast even in backups, but adds key management to every read. Many teams use it only for the most sensitive stores.

> **取舍。** 协调器和数据地图需要实打实的工程投入，并且会让新增数据存储的团队放慢速度。加密粉碎（crypto-shredding），即用每位顾客自己的密钥加密其数据、删除时只删除密钥，可以让删除即使在备份中也很快完成，但会给每一次读取增加密钥管理的负担。很多团队只在最敏感的存储上使用它。

</details>

  > 你如何防止一次备份恢复把已经删除的顾客数据带回来？

## 3. A unique constraint should stop duplicate ad connections, but duplicates still appear when one column is NULL

**唯一约束本应阻止重复的广告连接，但当某一列为 NULL 时仍然出现了重复** · `Database` · `Medium`

### Question · 题目

In PostgreSQL, a table of ad-platform connections has `UNIQUE (merchant_id, platform, ad_account_id)`. While a merchant is still choosing an ad account, `ad_account_id` is `NULL`. Double clicks on "Connect Meta" create several pending rows for the same merchant, even though the insert uses `ON CONFLICT DO NOTHING`. The OAuth callback then updates one of them at random.

> 在 PostgreSQL 中，一张广告平台连接表上有 `UNIQUE (merchant_id, platform, ad_account_id)`。当商家还在选择广告账户时，`ad_account_id` 为 `NULL`。即使插入语句使用了 `ON CONFLICT DO NOTHING`，双击“连接 Meta”仍然会为同一个商家创建多条待处理的行。随后 OAuth 回调会随机更新其中一行。

Why does the constraint not help, and how do you fix it?

> 为什么这个约束没有起作用？你会如何修复？

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** In SQL, `NULL` means unknown, so `NULL = NULL` is not true. A standard unique constraint treats NULLs as distinct from each other: rows with a `NULL` in any constrained column never conflict. In a local PostgreSQL 16 test, two inserts of `(1, 'meta', NULL)` both succeeded, and a third with `ON CONFLICT DO NOTHING` was inserted too, because there was no conflict to detect.

> **原因。** 在 SQL 中，`NULL` 表示未知，所以 `NULL = NULL` 不为真。标准的唯一约束把 NULL 视为彼此不同：只要约束的任意一列为 `NULL`，这些行就永远不会冲突。在本地 PostgreSQL 16 的测试中，两次插入 `(1, 'meta', NULL)` 都成功了，而第三次带 `ON CONFLICT DO NOTHING` 的插入也被插入了，因为根本没有可以检测到的冲突。

**Fix options.**

> **修复方案。**

- **`NULLS NOT DISTINCT` (PostgreSQL 15+).** `UNIQUE NULLS NOT DISTINCT (merchant_id, platform, ad_account_id)` treats NULLs as equal. In the test, the second insert failed with a duplicate key error and `ON CONFLICT DO NOTHING` skipped it.
  > **`NULLS NOT DISTINCT`（PostgreSQL 15+）。** `UNIQUE NULLS NOT DISTINCT (merchant_id, platform, ad_account_id)` 会把 NULL 视为相等。在测试中，第二次插入以重复键错误失败，而 `ON CONFLICT DO NOTHING` 则跳过了它。
- **A partial unique index.** `CREATE UNIQUE INDEX ... ON connections (merchant_id, platform) WHERE ad_account_id IS NULL` allows one pending connection per merchant and platform. To use it with `ON CONFLICT`, repeat the predicate: `ON CONFLICT (merchant_id, platform) WHERE ad_account_id IS NULL DO NOTHING`.
  > **部分唯一索引。** `CREATE UNIQUE INDEX ... ON connections (merchant_id, platform) WHERE ad_account_id IS NULL` 允许每个商家和平台只有一条待处理的连接。要让它与 `ON CONFLICT` 配合使用，需要重复这个条件：`ON CONFLICT (merchant_id, platform) WHERE ad_account_id IS NULL DO NOTHING`。
- **Avoid the NULL.** Model the pending state explicitly, for example a separate pending-connections table, or a status column plus a non-null placeholder.
  > **避免出现 NULL。** 显式地建模待处理状态，例如单独建一张待处理连接表，或者使用状态列加一个非空的占位值。

**Cleaning up first.** Both new constraints fail to build while duplicates exist; in the test, creating them reported the duplicated key. Remove duplicates first, comparing with `IS NOT DISTINCT FROM`, which treats two NULLs as equal:

> **先清理数据。** 只要还存在重复数据，这两种新约束都无法建立；在测试中，创建它们时报告了重复的键。先删除重复数据，比较时使用 `IS NOT DISTINCT FROM`，它会把两个 NULL 视为相等：

```sql
DELETE FROM connections a
USING connections b
WHERE a.merchant_id = b.merchant_id
  AND a.platform = b.platform
  AND a.ad_account_id IS NOT DISTINCT FROM b.ad_account_id
  AND a.id > b.id;
```

**Trade-offs.** `NULLS NOT DISTINCT` is the smallest change but needs PostgreSQL 15 or later and changes the meaning for every NULL column in the constraint. The partial index states the rule exactly, but every `ON CONFLICT` must repeat its predicate. Removing the NULL makes the model clearer but costs a migration.

> **取舍。** `NULLS NOT DISTINCT` 是改动最小的方案，但需要 PostgreSQL 15 或更高版本，并且会改变约束中每一个可为 NULL 的列的语义。部分索引能精确地表达这条规则，但每一个 `ON CONFLICT` 都必须重复它的条件。去掉 NULL 能让模型更清晰，但需要做一次迁移。

</details>

## 4. Redis memory keeps growing because keys that were supposed to expire have no TTL

**Redis 内存持续增长，因为本该过期的键没有 TTL** · `Middleware` · `Medium`

### Question · 题目

A gateway stores each merchant's daily API quota in Redis: `SET quota:{merchant}:{day} 0 EX 86400` when the day starts, `INCR` on each call. A nightly job resets some counters with a plain `SET`. Months later Redis is close to `maxmemory`, and `INFO keyspace` shows millions of keys but far fewer with an expiry. An engineer suggests switching the eviction policy to `volatile-lru`.

> 一个网关把每个商家的每日 API 配额存放在 Redis 中：每天开始时执行 `SET quota:{merchant}:{day} 0 EX 86400`，每次调用时执行 `INCR`。一个夜间任务会用普通的 `SET` 重置部分计数器。几个月后，Redis 已经接近 `maxmemory`，而 `INFO keyspace` 显示有数百万个键，但设置了过期时间的却少得多。一位工程师建议把淘汰策略改成 `volatile-lru`。

What happened, and what would you do?

> 发生了什么？你会怎么做？

<details>
<summary><b>Answer · 参考答案</b></summary>

**What happened.** A plain `SET` replaces the value and removes the existing TTL. On Redis 7, a key set with `EX 3600` kept its TTL after `INCR`, but after `SET quota 0` its `TTL` returned `-1`, meaning no expiry. Every counter touched by the reset job became permanent. Other ways to lose a TTL include `GETSET`, which behaved the same in the test, and creating a key with `INCR` without ever calling `EXPIRE`.

> **发生了什么。** 普通的 `SET` 会替换值，并移除已有的 TTL。在 Redis 7 上，一个用 `EX 3600` 设置的键在 `INCR` 之后仍保留其 TTL，但在 `SET quota 0` 之后它的 `TTL` 返回了 `-1`，表示没有过期时间。被重置任务碰过的每一个计数器都变成了永久的。丢失 TTL 的其他方式还包括 `GETSET`（在测试中表现相同），以及用 `INCR` 创建键却从未调用 `EXPIRE`。

**Why `volatile-lru` does not help.** The `volatile-*` policies only evict keys that have an expiry, and the leak is exactly the keys without one. They would evict the healthy keys and leave the leak. `allkeys-lru` would evict leaked keys, but could also evict data you need, such as job queues; a cache and durable data should not share an instance that evicts.

> **为什么 `volatile-lru` 没有帮助。** `volatile-*` 系列策略只淘汰设置了过期时间的键，而泄漏的恰恰是没有过期时间的键。它们会淘汰正常的键，而留下泄漏的键。`allkeys-lru` 会淘汰泄漏的键，但也可能淘汰你需要的数据，比如任务队列；缓存和需要持久保存的数据不应该放在同一个会淘汰数据的实例上。

**Fix.**

> **修复方法。**

- Use `SET key value KEEPTTL` (Redis 6.0+) when you overwrite a value but want to keep its expiry; in the test the TTL stayed at 3600.
  > 当你要覆盖一个值但想保留其过期时间时，使用 `SET key value KEEPTTL`（Redis 6.0+）；在测试中，TTL 保持在 3600。
- When a counter is created by `INCR`, set the expiry in the same step: run `INCR` and `EXPIRE key ttl NX` in a pipeline or a Lua script. `NX` (Redis 7.0+) only sets an expiry if none exists, so later calls do not push it back.
  > 当计数器由 `INCR` 创建时，在同一步里设置过期时间：在 pipeline 或 Lua 脚本中执行 `INCR` 和 `EXPIRE key ttl NX`。`NX`（Redis 7.0+）只在键没有过期时间时才设置，所以后续的调用不会把过期时间往后推。
- Put the date in the key, as here, so yesterday's key is never written again and can simply expire.
  > 像这里一样把日期放进键名里，这样昨天的键永远不会再被写入，可以直接过期。

```text
SET quota:m42:2026-11-01 7 KEEPTTL
INCR quota:m42:2026-11-01
EXPIRE quota:m42:2026-11-01 86400 NX
```

**Clean up and prevent.** Use `SCAN` with a match pattern, never `KEYS`, to find quota keys whose `TTL` is `-1`, and delete or expire them in small batches. Monitor the ratio of keys to keys with an expiry from `INFO keyspace`, and alert when keys without a TTL grow in a namespace that should not have any.

> **清理与预防。** 用带匹配模式的 `SCAN`（绝不要用 `KEYS`）找出 `TTL` 为 `-1` 的配额键，并分小批删除它们或为它们设置过期时间。从 `INFO keyspace` 中监控键总数与带过期时间键数的比例，当某个本不应有无 TTL 键的命名空间中这类键增长时发出告警。

**Trade-offs.** Raising `maxmemory` only buys time. Eviction policies are a safety net, not a fix for a leak. Wrapping all quota access in one small library costs a little flexibility but keeps every caller from repeating the same mistake.

> **取舍。** 调高 `maxmemory` 只能争取时间。淘汰策略是一张安全网，而不是修复泄漏的办法。把所有对配额的访问封装进一个小型库会损失一点灵活性，但能避免每个调用方重复犯同样的错误。

</details>

## 5. A product-sync service runs out of memory during a Meta API slowdown, even though it uses a fixed pool of 20 threads

**一个商品同步服务在 Meta API 变慢时内存耗尽，尽管它只用了一个固定 20 个线程的线程池** · `Java & CS` · `Hard`

### Question · 题目

A Java service syncs product updates to Meta. Each update is submitted to `Executors.newFixedThreadPool(20)`, and each task makes one HTTP call. When Meta's API slows from 200 ms to several seconds, heap usage climbs for an hour and the service dies with `OutOfMemoryError`. The team thought a fixed pool limited the load.

> 一个 Java 服务把商品更新同步到 Meta。每条更新都被提交给 `Executors.newFixedThreadPool(20)`，每个任务发起一次 HTTP 调用。当 Meta 的 API 从 200 ms 变慢到好几秒时，堆内存在一个小时内持续上涨，最后服务以 `OutOfMemoryError` 崩溃。团队原以为固定大小的线程池能限制负载。

Explain the cause and how to design the pool.

> 解释原因，以及应该如何设计这个线程池。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** A fixed pool limits threads, not work. `newFixedThreadPool` uses a `LinkedBlockingQueue` with no bound; in a local test its remaining capacity was `Integer.MAX_VALUE`. When tasks finish more slowly than they arrive, the queue grows without limit, and each queued task holds its product payload. Submitting 100,000 slow tasks left 20 running and 99,980 waiting in the queue. The `newCachedThreadPool` alternative is worse in the other direction: its maximum pool size is also `Integer.MAX_VALUE`, so a slowdown creates threads without limit.

> **原因。** 固定大小的线程池限制的是线程，而不是工作量。`newFixedThreadPool` 使用一个没有上限的 `LinkedBlockingQueue`；在本地测试中，它的剩余容量是 `Integer.MAX_VALUE`。当任务完成的速度比到达的速度慢时，队列会无限增长，而每个排队的任务都持有它的商品数据。提交 100,000 个慢任务后，有 20 个在运行，99,980 个在队列里等待。换成 `newCachedThreadPool` 会在另一个方向上更糟：它的最大线程数同样是 `Integer.MAX_VALUE`，所以一次变慢就会无限制地创建线程。

**Fix: bound the queue and choose what happens when it is full.**

> **修复：给队列设上限，并选择队列满了之后怎么办。**

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    20, 20, 0, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),
    new ThreadPoolExecutor.CallerRunsPolicy());
```

- **`AbortPolicy`** (the default) throws `RejectedExecutionException`. In the test, 1,000 submissions to 20 threads with a queue of 500 gave 500 queued and 480 rejected. Use it when the caller can store the work elsewhere, for example leave it in Kafka or a database and retry later.
  > **`AbortPolicy`**（默认策略）会抛出 `RejectedExecutionException`。在测试中，向 20 个线程、队列为 500 的线程池提交 1,000 个任务，结果是 500 个排队、480 个被拒绝。当调用方能把工作存到别处时使用它，例如留在 Kafka 或数据库中，稍后重试。
- **`CallerRunsPolicy`** runs the task on the submitting thread, which slows the producer down. In the test, two of eight tasks ran on the caller and the submit loop took about 200 ms instead of returning at once. This is natural backpressure for a consumer reading from a queue.
  > **`CallerRunsPolicy`** 在提交任务的线程上执行这个任务，从而让生产者慢下来。在测试中，8 个任务中有 2 个在调用方线程上执行，提交循环花了大约 200 ms，而不是立即返回。对于从队列中读取数据的消费者来说，这是一种天然的背压。
- **Avoid silent drops.** `DiscardPolicy` loses product updates without a trace; if you drop, count and log it.
  > **避免悄无声息地丢弃。** `DiscardPolicy` 会不留痕迹地丢掉商品更新；如果要丢弃，就要计数并记录日志。

**Also fix the cause of the slowness.** Set connect and read timeouts on the HTTP client so a slow Meta cannot hold a thread for minutes, and add a circuit breaker so calls fail fast during an outage. Monitor queue size, active threads and rejections, and alert on a growing queue long before memory runs out.

> **同时修复变慢的根源。** 为 HTTP 客户端设置连接超时和读取超时，这样变慢的 Meta 就不能把一个线程占用好几分钟；再加上熔断器，让调用在故障期间快速失败。监控队列长度、活跃线程数和拒绝次数，在内存耗尽之前很久就对不断增长的队列发出告警。

**Trade-offs.** A bounded queue turns an outage into rejections or slower producers instead of a crash, which is the point, but the work must go somewhere: a durable source like Kafka is the right buffer, not the heap. Virtual threads remove the thread limit but not this problem; an unbounded number of waiting tasks still needs memory, so you still need a limit, such as a semaphore.

> **取舍。** 有界队列会把一次故障变成拒绝或更慢的生产者，而不是一次崩溃，这正是目的所在；但工作总得有个去处：像 Kafka 这样的持久化数据源才是合适的缓冲区，而不是堆内存。虚拟线程消除了线程数的限制，却解决不了这个问题；数量不受限制的等待任务仍然需要内存，所以你仍然需要一个上限，比如信号量。

</details>
