## 1. Batches that silently overwrite each other

**批次之间悄悄互相覆盖** · `Go` · `Medium`

### Question

A helper splits a slice into batches for a bulk API. Before sending, the caller appends a required marker item to each batch:

```go
func splitBatches(items []Product, size int) [][]Product {
    var batches [][]Product
    for len(items) > size {
        batches = append(batches, items[:size])
        items = items[size:]
    }
    if len(items) > 0 {
        batches = append(batches, items)
    }
    return batches
}

for _, b := range splitBatches(products, 100) {
    b = append(b, marker)
    send(b)
}
```

In production, the first product of every batch except the first never reaches the platform, and those batches contain the marker twice. Explain why, and fix it.

### 题目

一个辅助函数把切片拆成多个批次，用来调用批量接口。发送之前，调用方还要给每个批次追加一个必需的标记项：

```go
func splitBatches(items []Product, size int) [][]Product {
    var batches [][]Product
    for len(items) > size {
        batches = append(batches, items[:size])
        items = items[size:]
    }
    if len(items) > 0 {
        batches = append(batches, items)
    }
    return batches
}

for _, b := range splitBatches(products, 100) {
    b = append(b, marker)
    send(b)
}
```

线上出现了问题：除第一个批次外，每个批次的第一个商品都没有到达平台，而且这些批次里标记项出现了两次。请解释原因并修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Root cause.** `items[:size]` shares the backing array with the original slice and keeps all of the remaining capacity. For batch i, `cap(b)` is larger than `len(b)`, so `append` does not allocate. It writes `marker` into the next slot of the shared array, which is element 0 of batch i+1. The next batch is then sent with `marker` in place of its first product, plus its own appended `marker`. Only the last batch's own append is safe, because its length equals its capacity and `append` has to allocate a new array. The caller's `products` slice is modified too, so anything that reads it later sees the wrong data.

**Fix 1: cap each batch with a full slice expression.** `items[:size:size]` sets the capacity equal to the length, so any `append` must copy to a new array. `slices.Clip(b)` from Go 1.21 does the same thing.

**Fix 2: use `slices.Chunk` (Go 1.23+).** It yields sub-slices whose capacity is already clipped to their length:

```go
for b := range slices.Chunk(products, 100) {
    send(append(b, marker))
}
```

**Fix 3: copy when the callee keeps the data.** If `send` holds on to the slice (for example, it queues it for a retry goroutine), copy it with `slices.Clone` so later writes to the original cannot reach it.

**General rule.** A sub-slice is a view, not a copy. Whenever a function returns sub-slices of its input, either clip them or document that callers must not append. If the sends ran concurrently, this bug would also be a data race, and `go test -race` would report it.

#### 参考答案

**根本原因。** `items[:size]` 与原切片共享底层数组，并且保留了剩余的全部容量。对第 i 个批次来说，`cap(b)` 大于 `len(b)`，所以 `append` 不会分配新数组，而是把 `marker` 写进共享数组的下一个位置，也就是第 i+1 个批次的第 0 个元素。于是下一个批次发送时，第一个商品被替换成了 `marker`，再加上它自己追加的 `marker`。只有最后一个批次自己的追加是安全的，因为它的长度等于容量，`append` 必须分配新数组。调用方的 `products` 切片同样被改写了，之后任何读取它的代码都会拿到错误数据。

**修复 1：用完整切片表达式限制容量。** `items[:size:size]` 把容量设为与长度相同，之后任何 `append` 都必须复制到新数组。Go 1.21 的 `slices.Clip(b)` 效果相同。

**修复 2：使用 `slices.Chunk`（Go 1.23+）。** 它产出的子切片已经把容量裁剪到与长度相同：

```go
for b := range slices.Chunk(products, 100) {
    send(append(b, marker))
}
```

**修复 3：被调用方持有数据时就复制。** 如果 `send` 会保留这个切片（例如交给重试 goroutine 排队），就用 `slices.Clone` 复制一份，这样原切片后续的写入就影响不到它。

**通用规则。** 子切片是视图，不是副本。只要函数返回的是输入的子切片，要么裁剪容量，要么在文档里写明调用方不能 `append`。如果这些发送是并发执行的，这个 bug 还会构成数据竞争，`go test -race` 会把它报告出来。

</details>

## 2. Refreshing OAuth tokens from many pods without logging merchants out

**多个 pod 并发刷新 OAuth token，又不让商家掉线** · `System Design` · `Hard`

### Question

Your service holds OAuth tokens for 20,000 merchants on an ad platform. Access tokens expire after one hour. The platform rotates refresh tokens: every refresh returns a new refresh token and invalidates the old one. Twenty pods call the platform's API, and each pod refreshes a token as soon as it sees a 401. A few times a day, a merchant gets `invalid_grant` and has to reconnect their account by hand. Explain why, and design token management that stops this from happening.

### 题目

你的服务在某个广告平台上为 20,000 个商家保存 OAuth token。access token 一小时后过期。该平台会轮换 refresh token：每次刷新都会返回一个新的 refresh token，并使旧的失效。共有 20 个 pod 调用平台 API，每个 pod 一遇到 401 就会自己刷新 token。每天都会有几次，某个商家收到 `invalid_grant`，只能手动重新授权账号。请解释原因，并设计一套 token 管理方案，杜绝这种情况。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Why it breaks.** Two pods see a 401 for the same merchant at about the same time. Both read refresh token R1 and both call the token endpoint. The first call succeeds and returns R2, which invalidates R1. The second call presents R1, gets `invalid_grant`, and the code treats that as "the merchant revoked access" and marks the connection broken. A quieter variant: a pod refreshes successfully but crashes or times out before saving R2, so the only valid refresh token is lost. Some providers also treat reuse of an old refresh token as possible theft and revoke the whole token family, as the OAuth 2.0 Security Best Current Practice (RFC 9700) describes.

**One refresher per merchant.** Make refresh a single-flight operation keyed by merchant:
- Inside a pod, use `golang.org/x/sync/singleflight` so concurrent requests share one refresh call.
- Across pods, take a short lease, for example Redis `SET lock:token:{merchant} {owner} NX PX 15000`, or `SELECT ... FOR UPDATE` on the token row. Make the lease longer than the token call's HTTP timeout. Pods that lose the race wait briefly and re-read the token from storage instead of calling the platform.

**Compare-and-set on storage.** Keep a version column on the token row. Save a refresh with `UPDATE tokens SET access_token=?, refresh_token=?, expires_at=?, version=version+1 WHERE merchant_id=? AND version=?`. If 0 rows change, another worker already refreshed: drop your result and re-read. Persist the new refresh token before you use the new access token, and encrypt tokens at rest.

**Refresh proactively, not on 401.** A scheduler refreshes each token when about 10 minutes of lifetime remain, with random jitter so thousands of tokens do not come due in the same minute. Request-path code then only reads tokens. On a 401 it re-reads storage first and refreshes only if the stored token is still the one that failed.

**Handle `invalid_grant` carefully.** Before marking a merchant disconnected, re-read storage. If a newer token exists, retry with it. Only when a fresh token also fails do you mark the connection as needing re-authorization and notify the merchant. Network errors and 5xx responses from the token endpoint are retryable. They say nothing about the token itself.

**Observability.** Count refreshes, CAS conflicts and `invalid_grant` per platform, and alert on tokens that are close to expiry without a recent successful refresh.

#### 参考答案

**为什么会出问题。** 两个 pod 几乎同时遇到同一个商家的 401。它们都读到 refresh token R1，并且都去调用 token 接口。第一个调用成功，拿到 R2，同时 R1 失效。第二个调用拿着 R1 去刷新，收到 `invalid_grant`，代码把它理解为“商家撤销了授权”，于是把连接标记为断开。还有一种更隐蔽的情况：某个 pod 刷新成功了，但在保存 R2 之前崩溃或超时，唯一有效的 refresh token 就这样丢了。有些平台还会把重复使用旧 refresh token 视为可能的盗用，直接吊销整个 token 家族，OAuth 2.0 安全最佳实践（RFC 9700）中描述的正是这种做法。

**每个商家只有一个刷新者。** 把刷新做成按商家维度的 single-flight 操作：
- 在单个 pod 内，用 `golang.org/x/sync/singleflight` 让并发请求共享同一次刷新调用。
- 跨 pod 时，获取一个短租约，例如 Redis 的 `SET lock:token:{merchant} {owner} NX PX 15000`，或者对 token 行执行 `SELECT ... FOR UPDATE`。租约时长要大于 token 调用的 HTTP 超时时间。没抢到的 pod 稍等片刻，从存储里重新读取 token，而不是自己去调用平台。

**存储层用比较并设置（CAS）。** 在 token 行上加一个 version 列。保存刷新结果时执行 `UPDATE tokens SET access_token=?, refresh_token=?, expires_at=?, version=version+1 WHERE merchant_id=? AND version=?`。如果影响行数为 0，说明别的 worker 已经刷新过了：丢弃你的结果，重新读取。先持久化新的 refresh token，再使用新的 access token，并且对存储的 token 做静态加密。

**主动刷新，而不是等到 401。** 由调度器在每个 token 剩余约 10 分钟有效期时刷新，并加入随机抖动，避免成千上万个 token 在同一分钟到期。这样请求路径上的代码只需要读取 token。遇到 401 时，先重新读取存储，只有当存储里的 token 仍然是失败的那一个时才刷新。

**谨慎处理 `invalid_grant`。** 在把商家标记为断开之前，先重新读取存储。如果已经有更新的 token，就用它重试。只有当最新的 token 也失败时，才把连接标记为需要重新授权，并通知商家。token 接口返回的网络错误和 5xx 都可以重试，它们并不能说明 token 本身有问题。

**可观测性。** 按平台统计刷新次数、CAS 冲突次数和 `invalid_grant` 次数，并对即将过期却迟迟没有成功刷新的 token 告警。

</details>

## 3. Why an "online" ALTER TABLE took the site down

**为什么一个“在线” ALTER TABLE 让整个网站宕机** · `Database` · `Senior`

### Question

`products` is a 500-million-row InnoDB table on MySQL 8.0 serving about 5,000 QPS. A teammate ran the following during the day, because the docs say adding a column is instant and adding an index is online:

```sql
ALTER TABLE products ADD COLUMN ad_status TINYINT NULL;
ALTER TABLE products ADD INDEX idx_shop_updated (shop_id, updated_at);
```

Within seconds, every query on `products` hung, connection pools were exhausted, and the site went down. Later that day the replica also fell more than an hour behind. Explain both problems, and describe how you would run this change safely.

### 题目

`products` 是 MySQL 8.0 上一张有 5 亿行的 InnoDB 表，承载约 5,000 QPS。一位同事在白天执行了下面的语句，因为文档上说加列是 instant 的，加索引是 online 的：

```sql
ALTER TABLE products ADD COLUMN ad_status TINYINT NULL;
ALTER TABLE products ADD INDEX idx_shop_updated (shop_id, updated_at);
```

几秒之内，所有访问 `products` 的查询都卡住了，连接池被耗尽，网站宕机。当天晚些时候，从库也落后了一个多小时。请解释这两个问题，并说明你会如何安全地完成这次变更。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**The metadata lock queue.** Every DDL statement, even `ALGORITHM=INSTANT`, needs an exclusive metadata lock (MDL) on the table for a moment. Every query holds a shared MDL until its transaction ends. Here some long-running transaction still held a shared MDL on `products`, for example a session that ran a `SELECT` inside a transaction and never committed, or a 10-minute report. The `ALTER` waited in `Waiting for table metadata lock`. A pending exclusive MDL request blocks new shared requests, so every new query on the table queued behind it. The table was effectively locked for as long as the old transaction stayed open, and the app ran out of connections. The DDL itself was cheap. The wait was the outage.

**Why the replica lagged.** The index build ran online on the primary, but it is written to the binlog only after it finishes. The replica then runs the same long build. A DDL statement is a barrier for the applier, even with multi-threaded replication, so nothing after it applies until it completes. The lag is roughly the build time.

**How to run it safely.**
- **Check first.** Look for old transactions in `information_schema.innodb_trx` and for lock holders in `performance_schema.metadata_locks`. Wait them out or kill them.
- **Fail fast.** In the DDL session, run `SET SESSION lock_wait_timeout = 5` (the default is one year), so a blocked `ALTER` gives up after a few seconds instead of building a queue. Retry in a loop.
- **Be explicit about the algorithm.** Write `ALGORITHM=INSTANT` for the column and `ALGORITHM=INPLACE, LOCK=NONE` for the index. If MySQL cannot honor them, it returns an error instead of silently falling back to a blocking table copy.
- **Know the limits of native online DDL.** During an `INPLACE` index build, concurrent writes are buffered in a temporary log capped by `innodb_online_alter_log_max_size` (128 MB by default). On a busy table it can overflow, and then the whole build fails at the very end.
- **Use an online schema change tool for the big build.** `gh-ost` copies rows into a shadow table, follows the row-based binlog for ongoing changes, throttles on replica lag and load, and lets you choose when to run the short cut-over. `pt-online-schema-change` does the same with triggers. Replicas then see ordinary row changes instead of one huge DDL, so lag stays bounded.
- **Plan the rollback.** A new index can change query plans for the worse. In MySQL 8.0 you can hide it from the optimizer instantly with `ALTER TABLE products ALTER INDEX idx_shop_updated INVISIBLE`, and drop it later off-peak.

**One more detail.** Since MySQL 8.0.29, `INSTANT` can add a column at any position, but each table allows a limited number of instant row versions (64 in 8.0) before a rebuild is required.

#### 参考答案

**元数据锁排队。** 每条 DDL 语句，即便是 `ALGORITHM=INSTANT`，也需要短暂获取表上的排他元数据锁（MDL）。每个查询在其事务结束前都持有共享 MDL。这次的情况是：某个长事务仍持有 `products` 的共享 MDL，比如某个会话在事务里执行了 `SELECT` 后一直没有提交，或者一个跑了 10 分钟的报表。`ALTER` 于是停在 `Waiting for table metadata lock` 状态。等待中的排他 MDL 请求会阻塞新的共享请求，所以此后所有访问这张表的新查询都排在它后面。只要那个老事务不结束，这张表实际上就被锁住了，应用的连接随之耗尽。DDL 本身很轻，真正造成故障的是等待。

**从库为什么延迟。** 索引是在主库上在线构建的，但它只有在执行完成后才会写入 binlog。随后从库要把同样漫长的构建再跑一遍。对于应用线程来说，DDL 是一道屏障，即使开启了多线程复制，它之后的事务也必须等它完成才能应用。所以延迟大约就等于构建耗时。

**如何安全地执行。**
- **先检查。** 在 `information_schema.innodb_trx` 中查找老事务，在 `performance_schema.metadata_locks` 中查找锁的持有者。等它们结束，或者直接 kill。
- **快速失败。** 在执行 DDL 的会话里运行 `SET SESSION lock_wait_timeout = 5`（默认值是一年），让被阻塞的 `ALTER` 几秒后就放弃，而不是制造排队。然后循环重试。
- **明确指定算法。** 加列写 `ALGORITHM=INSTANT`，加索引写 `ALGORITHM=INPLACE, LOCK=NONE`。如果 MySQL 无法满足，它会直接报错，而不是悄悄退回到会阻塞的整表复制。
- **了解原生 online DDL 的限制。** `INPLACE` 构建索引期间，并发写入会缓存在一个临时日志里，其大小受 `innodb_online_alter_log_max_size` 限制（默认 128 MB）。在写入繁忙的表上它可能溢出，整个构建会在最后一步失败。
- **大表构建使用在线变更工具。** `gh-ost` 把数据行复制到影子表，通过行格式 binlog 追踪增量变更，根据从库延迟和负载自动限速，并且让你自己决定何时执行短暂的切换。`pt-online-schema-change` 用触发器实现同样的目标。这样从库看到的是普通的行变更，而不是一条巨大的 DDL，延迟就能保持在可控范围内。
- **规划回滚。** 新索引可能让某些查询的执行计划变差。在 MySQL 8.0 中，可以用 `ALTER TABLE products ALTER INDEX idx_shop_updated INVISIBLE` 立即让它对优化器不可见，之后在低峰期再删除。

**还有一个细节。** 从 MySQL 8.0.29 起，`INSTANT` 可以在任意位置加列，但每张表允许的 instant 行版本数是有限的（8.0 中为 64 个），超过后就必须重建表。

</details>

## 4. A slow downstream API turns into a Kafka rebalance storm

**下游 API 变慢演变成 Kafka 重平衡风暴** · `Middleware` · `Hard`

### Question

A Kafka consumer group reads conversion events and posts each one to an ad platform's HTTP API, one record at a time. It uses the Java client defaults `max.poll.records=500` and `max.poll.interval.ms=300000`, and commits offsets after each batch. One afternoon the platform's p99 latency rises from 200 ms to 8 s. Within minutes the group is rebalancing constantly, lag keeps growing, the logs show `CommitFailedException`, and the platform reports duplicate conversions. Walk through the chain of events and fix it.

### 题目

一个 Kafka 消费者组读取转化事件，并把它们逐条发送到某广告平台的 HTTP API。它使用 Java 客户端的默认值 `max.poll.records=500` 和 `max.poll.interval.ms=300000`，每处理完一批就提交一次 offset。某天下午，平台的 p99 延迟从 200 ms 涨到了 8 s。几分钟之内，消费者组开始不停地重平衡，lag 持续上涨，日志里出现 `CommitFailedException`，平台还反馈收到了重复的转化。请梳理事件的连锁过程，并给出修复方案。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**The chain of events.**
- One `poll()` returns up to 500 records. At 8 s per call, the batch can take 500 × 8 s = 4,000 s, far beyond the 300 s `max.poll.interval.ms`.
- The consumer does not call `poll()` again in time, so its background thread leaves the group and the coordinator reassigns its partitions.
- The new owner starts from the last committed offset, which is before the batch the first consumer was still sending. It sends those events again: duplicates.
- When the first consumer finishes and tries to commit, it no longer owns the partitions, so the commit fails with `CommitFailedException`.
- The new owner gets the same 500 records, hits the same slow API, misses the same deadline, and the cycle repeats. With the default eager protocol, every rebalance also stops consumption on all partitions in the group. Lag grows while almost nothing gets committed.

Heartbeats run on a background thread, so `session.timeout.ms` is not what fails here. The poll-interval check exists precisely to catch a consumer that is alive but stuck in its processing loop.

**Fixes, in order of impact.**
- **Bound the work per poll.** Pick `max.poll.records` so that records × worst-case latency stays well under `max.poll.interval.ms`, and set a hard per-request HTTP timeout so the worst case is actually known. For example, 50 records × 3 s timeout = 150 s.
- **Process concurrently, commit carefully.** Send through a bounded worker pool, and commit only the highest offset below which every record is done. Move failures to a retry topic and then a dead-letter topic instead of blocking the partition.
- **Decouple liveness from slow work.** If a batch can still be slow, `pause()` the partitions, process asynchronously, keep calling `poll()` (it returns nothing for paused partitions but keeps the consumer in the group), then `resume()`.
- **Make sends idempotent.** Rebalances always cause some redelivery. Send a stable event id that the platform uses for deduplication where it supports one, and keep your own record of sent ids as a guard.
- **Shrink the blast radius of rebalances.** Use `CooperativeStickyAssignor` so only the partitions that move are paused, and static membership (`group.instance.id`) so rolling restarts do not trigger rebalances. From Kafka 4.0, the new consumer group protocol (`group.protocol=consumer`, KIP-848) is generally available and replaces stop-the-world rebalances with incremental, broker-driven assignment.
- **Protect the downstream.** A circuit breaker and a rate limiter keep you from hammering a struggling API, and lag alerts tell you early.

#### 参考答案

**事件的连锁过程。**
- 一次 `poll()` 最多返回 500 条记录。每次调用 8 s，这一批最多可能耗时 500 × 8 s = 4,000 s，远远超过 300 s 的 `max.poll.interval.ms`。
- 消费者没能及时再次调用 `poll()`，于是它的后台线程主动离开消费者组，协调者把它的分区重新分配出去。
- 新的分区持有者从最后一次提交的 offset 开始消费，而这个位置在第一个消费者仍在发送的那一批之前。它把这些事件又发了一遍：重复由此产生。
- 第一个消费者处理完后尝试提交 offset，但它已经不再拥有这些分区，于是提交失败，抛出 `CommitFailedException`。
- 新的持有者拿到同样的 500 条记录，碰上同样慢的 API，错过同样的期限，循环就此重复。在默认的 eager 协议下，每次重平衡还会让组内所有分区停止消费。lag 不断增长，几乎什么都提交不了。

心跳是在后台线程中发送的，所以失效的并不是 `session.timeout.ms`。poll 间隔检查存在的目的，正是为了发现“消费者还活着，但处理循环卡住了”的情况。

**修复方案，按影响从大到小排列。**
- **限制每次 poll 的工作量。** 选择合适的 `max.poll.records`，使记录数 × 最坏延迟远小于 `max.poll.interval.ms`；同时为每个 HTTP 请求设置硬超时，让最坏情况真正可知。例如 50 条记录 × 3 s 超时 = 150 s。
- **并发处理，谨慎提交。** 通过有界的 worker 池发送，只提交“其之前所有记录都已完成”的最大 offset。失败的记录先转入重试 topic，再转入死信 topic，而不是阻塞整个分区。
- **把存活检测与慢处理解耦。** 如果一批数据仍可能很慢，就先 `pause()` 这些分区，异步处理，同时继续调用 `poll()`（对暂停的分区它不会返回数据，但能让消费者留在组内），处理完再 `resume()`。
- **让发送具备幂等性。** 重平衡总会带来一些重复投递。在平台支持去重的情况下，发送稳定的事件 id 供其去重，同时在自己这边记录已发送的 id 作为兜底。
- **缩小重平衡的影响范围。** 使用 `CooperativeStickyAssignor`，只有被迁移的分区才会暂停；使用静态成员（`group.instance.id`），滚动重启时不会触发重平衡。从 Kafka 4.0 起，新的消费者组协议（`group.protocol=consumer`，KIP-848）正式可用，它用由 broker 驱动的增量分配取代了 stop-the-world 式的重平衡。
- **保护下游。** 熔断器和限流器可以避免你持续冲击一个已经吃力的 API，lag 告警则能让你尽早发现问题。

</details>

## 5. One merchant sees another merchant's report

**一个商家看到了另一个商家的报表** · `Java & CS` · `Medium`

### Question

A Spring Boot service keeps the current tenant in a `ThreadLocal`, set by a servlet filter:

```java
public class TenantFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        String shopId = resolveShopId((HttpServletRequest) req); // null if the session expired
        if (shopId != null) {
            TenantContext.set(shopId);
        }
        chain.doFilter(req, res);
    }
}
```

Controllers call `TenantContext.get()` and return 401 when it is null. A few times a week, a merchant briefly sees another merchant's ad report. Separately, a CSV export started with `CompletableFuture.supplyAsync(() -> export(TenantContext.get()))` sometimes runs with no tenant at all. Explain both bugs and fix them.

### 题目

一个 Spring Boot 服务把当前租户保存在 `ThreadLocal` 里，由一个 servlet 过滤器负责设置：

```java
public class TenantFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        String shopId = resolveShopId((HttpServletRequest) req); // null if the session expired
        if (shopId != null) {
            TenantContext.set(shopId);
        }
        chain.doFilter(req, res);
    }
}
```

控制器调用 `TenantContext.get()`，为 null 时返回 401。每周有几次，某个商家会短暂地看到另一个商家的广告报表。另外，用 `CompletableFuture.supplyAsync(() -> export(TenantContext.get()))` 启动的 CSV 导出任务，有时会在完全没有租户的情况下运行。请解释这两个 bug 并修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Bug 1: a stale tenant on a reused thread.** Tomcat serves requests from a thread pool, and nothing ever clears the `ThreadLocal`. When a session has expired, `resolveShopId` returns null, the filter skips `set`, and the thread still holds whichever merchant it served last. The null check in the controller never fires, so the request runs as that other merchant. It is rare only because expired sessions on that page are rare. Fix: never leave the old value in place, fail closed, and always clear in `finally`:

```java
String shopId = resolveShopId((HttpServletRequest) req);
if (shopId == null) {
    ((HttpServletResponse) res).sendError(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
TenantContext.set(shopId);
try {
    chain.doFilter(req, res);
} finally {
    TenantContext.clear(); // calls threadLocal.remove()
}
```

Prefer `remove()` over `set(null)`, because it deletes the entry instead of keeping it in the thread's map. Leftover entries also leak memory: pool threads live as long as the process, and in app servers that hot-redeploy, a stale value can keep a whole class loader alive.

**Bug 2: thread locals do not follow work to other threads.** `supplyAsync` without an executor runs the lambda on the default async pool, usually `ForkJoinPool.commonPool()`. Those threads never passed through the filter, so `TenantContext.get()` returns null there, or a stale value if other code once set one on that thread. `InheritableThreadLocal` does not help either: it copies values only when a thread is created, and pool threads are created long before the request.

**Fixes for async work.**
- Read the tenant on the request thread and pass it in: `String shop = TenantContext.get(); CompletableFuture.supplyAsync(() -> export(shop), exportExecutor);`
- Or wrap tasks so they set and clear the context around each run, for example with a Spring `TaskDecorator` on a `ThreadPoolTaskExecutor`.
- Pass your own executor rather than relying on the common pool, so slow exports cannot starve unrelated work.

**Defense in depth.** Make the tenant id a required argument of every repository method and reject null, so a missing context fails loudly instead of running an unscoped query. Log the tenant with each request (for example through MDC, which is itself a thread local and needs the same cleanup) so leaks can be traced. On Java 25, `ScopedValue` (JEP 506) gives an immutable binding that exists only inside a scope and disappears when it ends, which removes this whole class of bug.

#### 参考答案

**Bug 1：复用线程上残留的旧租户。** Tomcat 用线程池处理请求，而代码里从来没有清理这个 `ThreadLocal`。当会话过期时，`resolveShopId` 返回 null，过滤器跳过了 `set`，线程里仍然保存着它上一次服务的那个商家。控制器里的 null 检查永远不会触发，于是这个请求就以另一个商家的身份执行了。它之所以少见，只是因为那个页面上会话过期的情况本来就少。修复方法：绝不保留旧值，失败即拒绝，并且始终在 `finally` 中清理：

```java
String shopId = resolveShopId((HttpServletRequest) req);
if (shopId == null) {
    ((HttpServletResponse) res).sendError(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
TenantContext.set(shopId);
try {
    chain.doFilter(req, res);
} finally {
    TenantContext.clear(); // calls threadLocal.remove()
}
```

优先使用 `remove()` 而不是 `set(null)`，因为前者会删除条目，而不是把它留在线程的 map 里。残留的条目还会造成内存泄漏：线程池中的线程与进程同寿；在支持热部署的应用服务器里，一个残留的值甚至能让整个类加载器无法被回收。

**Bug 2：ThreadLocal 不会跟着任务跑到别的线程。** 不指定 executor 的 `supplyAsync` 会在默认的异步线程池上执行 lambda，通常是 `ForkJoinPool.commonPool()`。这些线程从未经过过滤器，所以在那里 `TenantContext.get()` 返回 null；如果别的代码曾在该线程上设置过值，拿到的则是残留的旧值。`InheritableThreadLocal` 也帮不上忙：它只在线程创建时复制值，而线程池里的线程早在请求到来之前就已经创建好了。

**异步任务的修复方法。**
- 在请求线程上读取租户，再显式传进去：`String shop = TenantContext.get(); CompletableFuture.supplyAsync(() -> export(shop), exportExecutor);`
- 或者包装任务，在每次执行前后设置并清理上下文，例如在 `ThreadPoolTaskExecutor` 上配置 Spring 的 `TaskDecorator`。
- 传入你自己的 executor，而不是依赖公共线程池，这样缓慢的导出任务就不会饿死其他无关的工作。

**纵深防御。** 让租户 id 成为每个 repository 方法的必填参数，并拒绝 null，这样上下文缺失时会明确报错，而不是执行一条没有租户限定的查询。在每个请求的日志里带上租户（例如通过 MDC，它本身也是 ThreadLocal，同样需要清理），让串数据的问题可以追溯。在 Java 25 上，`ScopedValue`（JEP 506）提供一种不可变的绑定，它只在某个作用域内存在，作用域结束后自动消失，从根本上消除了这一类 bug。
