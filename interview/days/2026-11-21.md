## 1. A range-over-func iterator over the paged orders API panics in production when a caller breaks out of the loop

**一个遍历分页订单 API 的 range-over-func 迭代器，在调用方中途 break 时于线上 panic** · `Go` · `Senior`

### Question · 题目

The order sync library exposes `Orders()` as a Go 1.23-style iterator so callers can write `for o := range Orders()`. The iterator fetches pages from the order API and calls `yield(o)` for each order. Callers that read everything work fine. A new caller stops at the first matching order with `break`, and the service crashes with `range function continued iteration after function for loop body returned false`.

> 订单同步库把 `Orders()` 暴露成 Go 1.23 风格的迭代器，调用方可以写 `for o := range Orders()`。迭代器从订单 API 拉取分页，对每个订单调用 `yield(o)`。读完全部数据的调用方都正常。一个新的调用方在找到第一个匹配的订单时用 `break` 退出，服务随即崩溃，报错 `range function continued iteration after function for loop body returned false`。

Explain what happened, fix the iterator, and say how errors should reach the caller.

> 解释发生了什么，修复这个迭代器，并说明错误应该如何传给调用方。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** The loop body is compiled into the `yield` function. When the body runs `break`, `return` or `goto` out of the loop, `yield` returns `false`, and the iterator must stop calling it. The buggy iterator ignored the result and kept yielding the rest of the page, so the runtime panicked. In a local test, breaking after the first order raised exactly that runtime error.

> **原因。** 循环体被编译成了 `yield` 函数。当循环体执行 `break`、`return` 或 `goto` 跳出循环时，`yield` 返回 `false`，迭代器必须停止调用它。有 bug 的迭代器忽略了这个返回值，继续 yield 本页剩下的订单，于是运行时 panic 了。在本地测试中，读到第一个订单就 break，触发的正是这个运行时错误。

**The fix: check every `yield`, and return errors as the second value.**

> **修复方法：检查每一次 `yield` 的返回值，并把错误作为第二个值返回。**

```go
func Orders(ctx context.Context, c *Client) iter.Seq2[Order, error] {
	return func(yield func(Order, error) bool) {
		for cursor := ""; ; {
			page, next, err := c.ListOrders(ctx, cursor)
			if err != nil {
				yield(Order{}, err) // report once, then stop
				return
			}
			for _, o := range page {
				if !yield(o, nil) { // caller broke out or returned
					return
				}
			}
			if next == "" {
				return
			}
			cursor = next
		}
	}
}

for o, err := range Orders(ctx, c) {
	if err != nil {
		return err
	}
	if o.ID == target {
		break // no more pages are fetched
	}
}
```

- Stopping early also saves work. In the test, breaking at the third order fetched 2 pages instead of 3.
  > 提前停止还能省下工作。在测试中，在第三个订单处 break，只拉取了 2 页而不是 3 页。
- `defer` inside the iterator runs on every exit: normal end, `break`, an early `return` from the caller's function, and a panic in the loop body. All four ran the cleanup in the test, so closing a cursor or releasing a lease belongs in a `defer`.
  > 迭代器内部的 `defer` 在每一种退出路径上都会执行：正常结束、`break`、调用方函数提前 `return`，以及循环体里的 panic。测试中这四种情况都执行了清理，所以关闭游标或释放租约应该放在 `defer` 里。
- `iter.Seq2[Order, error]` makes the caller look at the error on every step. Yield it once and stop; do not keep going after a failed page, or the caller may see a gap that looks like a complete result.
  > `iter.Seq2[Order, error]` 让调用方在每一步都要看一下错误。错误只 yield 一次然后停止；某一页失败后不要继续，否则调用方可能看到一段缺口，却以为结果是完整的。
- Do not recover the body's panic inside the iterator. It is the caller's panic and should keep going up.
  > 不要在迭代器里 recover 循环体的 panic。那是调用方的 panic，应该继续往上传。

**Trade-offs.** An iterator hides paging, rate limits and retries behind a plain `for` loop, which is convenient but can make one innocent loop cost hundreds of API calls. Take a `context.Context`, document whether the sequence can be ranged over twice, and keep a page-level API for callers that need cursors or progress.

> **权衡。** 迭代器把分页、限流和重试都藏在一个普通的 `for` 循环后面，很方便，但也可能让一个看似无害的循环花掉几百次 API 调用。接收 `context.Context`，在文档里写明这个序列能否被遍历两次，并为需要游标或进度的调用方保留按页访问的 API。

</details>

## 2. Dynamic customer segments for email marketing: "spent over $200 but no order in 30 days"

**邮件营销的动态客户分群：「消费超过 200 美元，但 30 天没有下单」** · `System Design` · `Medium`

### Question · 题目

Merchants want to build customer segments from rules such as "total spent over $200, no order in the last 30 days, subscribed to email". The editor should show the segment size while they type, and a campaign sent to the segment on Friday must go to the right people exactly once. The largest stores have a few million customers.

> 商家想用规则来创建客户分群，比如「累计消费超过 200 美元、最近 30 天没有下单、订阅了邮件」。编辑器要在商家输入时显示分群人数；周五发给这个分群的营销活动必须准确送达对的人，而且每人只发一次。最大的店铺有几百万客户。

Design the rule model, the data it runs on, and the send path.

> 设计规则模型、规则所依赖的数据，以及发送链路。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Rules are data, compiled to queries.** Store each segment as a small tree of conditions over a fixed list of fields, never as SQL text from the browser:

> **规则是数据，编译成查询。** 每个分群存成一棵小的条件树，条件只能引用一组固定的字段，绝不存储来自浏览器的 SQL 文本：

```json
{"all": [
  {"field": "total_spent", "op": ">=", "value": 20000},
  {"field": "last_order_at", "op": "older_than", "days": 30},
  {"field": "email_consent", "op": "=", "value": "subscribed"}
]}
```

The server checks each field and operator against an allow-list and compiles the tree to a parameterized query:

> 服务端按白名单校验每个字段和操作符，再把这棵树编译成参数化查询：

```sql
SELECT customer_id FROM customer_profiles
WHERE merchant_id = $1
  AND total_spent >= 20000
  AND last_order_at < now() - interval '30 days'
  AND email_consent = 'subscribed';
```

**Precompute per-customer facts, not memberships.** A `customer_profiles` row holds totals such as `total_spent`, `orders_count` and `last_order_at`, updated from order and refund events. Store timestamps, not flags like "inactive_30d": a customer drifts into "no order in 30 days" without any event happening, so the time condition has to be checked at query time against `now()`.

> **预先计算每个客户的事实，而不是分群成员关系。** `customer_profiles` 的每一行保存 `total_spent`、`orders_count`、`last_order_at` 等汇总值，由订单和退款事件更新。存时间戳，而不是存「30 天未活跃」这样的标记：客户会在没有任何事件发生的情况下变成「30 天没有下单」，所以时间条件必须在查询时对照 `now()` 来判断。

- Counts in the editor run against the same table with a short timeout and an index on `(merchant_id, ...)` for the common fields. For the few huge stores, a columnar copy of the profiles answers counts faster; the number is labeled approximate if it comes from a delayed copy.
  > 编辑器里的人数统计在同一张表上执行，设置较短的超时，并为常用字段建立 `(merchant_id, ...)` 索引。对于少数超大店铺，用一份列式存储的画像副本来更快地统计人数；如果数字来自有延迟的副本，就标注为近似值。
- Money is stored in minor units and one currency per store, so `>= 20000` means $200.00 and comparisons are exact.
  > 金额以最小货币单位存储，每个店铺一种币种，所以 `>= 20000` 表示 200.00 美元，比较是精确的。

**Sending freezes the list.** At send time, run the query once and insert the result into `campaign_recipients(campaign_id, customer_id)` with that pair as the primary key. Workers send from this table and mark each row sent, so a retry or a second worker never mails anyone twice. Check consent again right before each email goes out, because someone may unsubscribe between the snapshot and the send.

> **发送时冻结名单。** 在发送时执行一次查询，把结果写入 `campaign_recipients(campaign_id, customer_id)`，以这两列作为主键。发送程序从这张表读取并把每一行标记为已发送，这样重试或多一个发送程序都不会给任何人发两次。每封邮件发出前再检查一次订阅状态，因为有人可能在快照之后、发送之前退订了。

**Trade-offs.** Live evaluation keeps segments correct without background jobs, at the cost of query time on large stores. Automations such as "email people when they enter the segment" need membership changes, which means re-evaluating customers touched by events plus a daily sweep for time-based rules.

> **权衡。** 实时计算让分群始终正确，不需要后台任务，代价是大店铺上的查询时间。像「客户进入分群时发邮件」这样的自动化需要知道成员变化，这意味着要对被事件影响的客户重新计算，再加上每天一次针对时间类规则的全量扫描。

</details>

## 3. An index on updated_at for the sync job doubles the size of every index on the busy inventory table

**为同步任务在 updated_at 上加了一个索引，繁忙的库存表上所有索引的体积都翻倍了** · `Database` · `Hard`

### Question · 题目

The `inventory` table gets thousands of stock updates per second, each one `SET qty = qty - 1, updated_at = now()`. A new job syncs changed rows to the search service, so someone added `CREATE INDEX ON inventory (updated_at)`. Since then, update latency and WAL volume have gone up, and the primary key and `store_id` indexes keep growing although the row count is flat.

> `inventory` 表每秒有几千次库存更新，每次都是 `SET qty = qty - 1, updated_at = now()`。一个新任务要把变化的行同步到搜索服务，于是有人加了 `CREATE INDEX ON inventory (updated_at)`。从那以后，更新延迟和 WAL 量都上升了，而且尽管行数没变，主键和 `store_id` 索引却一直在变大。

Explain why the other indexes grow, and fix it.

> 解释为什么其他索引会变大，并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** A PostgreSQL update writes a new row version. If no indexed column changed and the new version fits on the same page, it is a HOT (heap-only tuple) update: the new version is chained from the old one and no index gets a new entry. Once `updated_at` is indexed, every update changes an indexed column, so every update adds a new entry to every index on the table, including the primary key and `store_id`.

> **原因。** PostgreSQL 的更新会写入一个新的行版本。如果没有被索引的列发生变化，并且新版本能放进同一个页面，这就是一次 HOT（heap-only tuple）更新：新版本挂在旧版本的链上，任何索引都不需要新增条目。一旦 `updated_at` 被索引，每次更新都会改变一个被索引的列，于是每次更新都要在表上的每个索引里新增一个条目，包括主键和 `store_id`。

**Measured on PostgreSQL 16** with 200,000 rows, fillfactor 90 and five rounds of updating 10% of the rows:

> **在 PostgreSQL 16 上实测**：20 万行，fillfactor 为 90，分五轮每轮更新 10% 的行：

- Without the `updated_at` index: 100,000 updates, all of them HOT, and index size unchanged at 6.2 MB.
  > 没有 `updated_at` 索引：10 万次更新全部是 HOT，索引体积保持 6.2 MB 不变。
- With it: zero HOT updates, and total index size went from 7.5 MB to 14 MB; the primary key alone grew from 4.4 MB to 7.8 MB.
  > 有这个索引：HOT 更新为零，索引总体积从 7.5 MB 涨到 14 MB；仅主键就从 4.4 MB 涨到了 7.8 MB。
- Fillfactor matters too. With the default of 100, pages had no room at first, and only 79.6% of the same updates were HOT.
  > fillfactor 也有影响。使用默认值 100 时，页面一开始没有空位，同样的更新只有 79.6% 是 HOT。

```sql
-- How many updates were HOT?
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'inventory';

-- Leave free space on each page for new row versions.
ALTER TABLE inventory SET (fillfactor = 90);  -- applies to pages written from now on
```

**The fix: do not index a column that every update changes.** Give the sync job its own change feed instead: write `(variant_id, changed_at)` to a small append-only `inventory_changes` table in the same transaction, or read the changes from logical decoding. The job reads and deletes from that table, and `inventory` goes back to HOT updates.

> **修复方法：不要给每次更新都会改变的列建索引。** 改为给同步任务一个单独的变更流：在同一个事务里把 `(variant_id, changed_at)` 写入一张小的、只追加的 `inventory_changes` 表，或者从逻辑解码中读取变更。同步任务从这张表读取并删除，`inventory` 就能恢复 HOT 更新。

**Trade-offs.** In the PostgreSQL 16 test, a BRIN index on `updated_at` did not block HOT updates, but rows updated in place keep their old page, so the BRIN ranges would be too wide to help. Lower fillfactor costs disk space for room to update, and a change table adds a write, which is far cheaper than an entry in every index.

> **权衡。** 在 PostgreSQL 16 的测试中，`updated_at` 上的 BRIN 索引不会阻止 HOT 更新，但原地更新的行留在原来的页面上，所以 BRIN 的范围会太宽，起不到作用。更低的 fillfactor 用磁盘空间换来更新的余地；变更表会多一次写入，但这比在每个索引里都加一个条目便宜得多。

</details>

## 4. Redis memory for product hashes quadruples after adding one short description field

**给商品哈希加了一个简短的描述字段之后，Redis 内存翻了四倍** · `Middleware` · `Hard`

### Question · 题目

Product data is cached in Redis as one hash per product with about 30 small fields. A release added a `note` field holding an 80-character description to each hash. Within an hour, `used_memory` went from about 5 GB to about 20 GB and the instance started evicting keys. Rolling back and deleting the `note` field did not bring memory back down.

> 商品数据以每个商品一个哈希的形式缓存在 Redis 里，每个哈希大约 30 个很小的字段。一次发布给每个哈希加了一个 `note` 字段，存 80 个字符的描述。一小时之内，`used_memory` 从大约 5 GB 涨到了大约 20 GB，实例开始驱逐 key。回滚并删除 `note` 字段之后，内存并没有降下来。

Explain both effects and fix them.

> 解释这两个现象，并修复它们。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why it grew.** Small hashes are stored as a listpack, one compact block of bytes. Redis converts a hash to a real hash table when it has more fields than `hash-max-listpack-entries`, or when any field name or value is longer than `hash-max-listpack-value`. On the local Redis 7.0.15, those were 512 and 64 bytes. The 80-character note crossed the value limit, so every product hash was converted.

> **为什么会变大。** 小哈希以 listpack 存储，即一整块紧凑的字节。当哈希的字段数超过 `hash-max-listpack-entries`，或任何字段名或值的长度超过 `hash-max-listpack-value` 时，Redis 会把它转换成真正的哈希表。在本地的 Redis 7.0.15 上，这两个值分别是 512 和 64 字节。80 个字符的描述超过了值的长度上限，所以每个商品哈希都被转换了。

```text
127.0.0.1:6411> OBJECT ENCODING p:1
"listpack"
127.0.0.1:6411> MEMORY USAGE p:1
(integer) 1072
127.0.0.1:6411> HSET p:1 desc "xxxx...65 bytes...x"
127.0.0.1:6411> OBJECT ENCODING p:1
"hashtable"
127.0.0.1:6411> MEMORY USAGE p:1
(integer) 5168
```

- A 64-byte value kept the listpack; 65 bytes converted it.
  > 64 字节的值仍保持 listpack；65 字节就触发了转换。
- On 10,000 hashes of 30 fields, `used_memory` went from 5.1 MB to 20.9 MB after adding one 80-byte field to each, the same factor of four seen in production.
  > 在 1 万个 30 字段的哈希上，给每个哈希加一个 80 字节的字段后，`used_memory` 从 5.1 MB 涨到了 20.9 MB，与线上看到的四倍一致。

**Why it stayed.** The conversion is one way. After `HDEL` of the note, the hashes were still `hashtable` and memory only dropped to 19.5 MB. Changing the config afterwards does not convert existing keys either. A key returns to a listpack only when it is rewritten: deleting it and setting it again brought a test key back to 1,072 bytes.

> **为什么降不下来。** 这个转换是单向的。用 `HDEL` 删除描述之后，这些哈希仍然是 `hashtable`，内存只降到了 19.5 MB。之后再修改配置，也不会转换已有的 key。只有重写 key，它才会回到 listpack：在测试中，删除后重新写入，一个 key 回到了 1,072 字节。

**The fix.**

> **修复方法。**

- Keep long text out of the hot hash: store it under its own string key, or fetch it from the database when the product page needs it.
  > 把长文本放在热点哈希之外：用单独的字符串 key 存储，或者在商品页需要时从数据库读取。
- Repair existing keys by rewriting them, for example letting the cache expire or a background job that deletes and refills keys in small batches.
  > 通过重写来修复已有的 key，比如让缓存自然过期，或者用后台任务小批量删除并重新填充。
- Add a check before release: run `OBJECT ENCODING` and `MEMORY USAGE` on sample keys in staging, and alert when the encoding or the average size changes.
  > 发布前加一项检查：在预发环境对样本 key 执行 `OBJECT ENCODING` 和 `MEMORY USAGE`，编码或平均大小变化时告警。

**Trade-offs.** Raising `hash-max-listpack-value` keeps hashes compact, but listpack lookups are linear scans, so bigger listpacks make `HGET` slower and cost CPU on every read. Measure both before changing it.

> **权衡。** 调大 `hash-max-listpack-value` 能让哈希保持紧凑，但 listpack 的查找是线性扫描，listpack 越大，`HGET` 越慢，每次读取都要多花 CPU。修改之前两方面都要测量。

</details>

## 5. Order-ID batches built with subList all fail with ConcurrentModificationException after the buffer is cleared

**用 subList 切出来的订单 ID 批次，在缓冲区被清空后全部抛出 ConcurrentModificationException** · `Java & CS` · `Medium`

### Question · 题目

A sync job collects order IDs into an `ArrayList`, splits it into batches of 500 with `subList`, and submits each batch to an executor that calls a partner API. To reuse the buffer for the next poll, the job calls `ids.clear()` right after submitting. Since that change, every batch fails with `ConcurrentModificationException`, and nothing reaches the partner.

> 一个同步任务把订单 ID 收集到 `ArrayList` 里，用 `subList` 切成每批 500 个，再把每一批提交给线程池去调用合作方的 API。为了在下一次轮询时复用缓冲区，任务在提交之后立刻调用 `ids.clear()`。从这次改动开始，每一批都抛出 `ConcurrentModificationException`，没有任何数据到达合作方。

Explain why, and fix it.

> 解释原因，并修复它。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** `subList` returns a view of the parent list, not a copy. It has no elements of its own; it reads the parent's array through an offset. It also records the parent's modification count when created. When `clear()` changes the parent's size, every view's recorded count is out of date, and the next `size()`, `get()` or iteration on a view throws. In the local test on Java 21, all four batches failed this way.

> **原因。** `subList` 返回的是父列表的一个视图，而不是副本。它自己没有元素，而是通过偏移量读取父列表的数组。它在创建时还会记下父列表的修改计数。当 `clear()` 改变了父列表的大小，每个视图记下的计数都过期了，视图上接下来的 `size()`、`get()` 或遍历都会抛异常。在 Java 21 的本地测试中，四个批次全部这样失败了。

```java
for (int i = 0; i < ids.size(); i += 500) {
    List<Long> batch = ids.subList(i, Math.min(i + 500, ids.size()));
    pool.submit(() -> send(batch));     // a view of ids, not a copy
}
ids.clear();                            // every queued batch now fails

// Fixed: each task gets its own immutable copy.
List<Long> batch = List.copyOf(ids.subList(i, Math.min(i + 500, ids.size())));
```

After copying with `List.copyOf`, all four batches sent 500 IDs each even though the buffer was cleared.

> 用 `List.copyOf` 复制之后，即使缓冲区被清空，四个批次也各自发送了 500 个 ID。

**Other effects of the view, all seen in the same test:**

> **视图带来的其他影响，都在同一个测试中观察到：**

- Writes go through. `set` on a view changes the parent, and `subList(1, 3).clear()` removes that range from the parent, which is a handy idiom when meant.
  > 写操作会穿透。在视图上 `set` 会改变父列表；`subList(1, 3).clear()` 会从父列表中删除这一段，有意这样用时是个方便的写法。
- A non-structural change to the parent, such as `set`, does not invalidate views; adding or removing does.
  > 父列表的非结构性修改（比如 `set`）不会让视图失效；添加或删除才会。
- A view keeps the whole parent reachable. Holding a 10-element view of a 5-million-element list kept about 100 MB in use until the view was dropped.
  > 视图会让整个父列表保持可达。持有一个 500 万元素列表的 10 元素视图，在视图被释放之前一直占用约 100 MB。

**Not a reliable guard.** The exception is a best-effort check, and here the views are read on other threads without synchronization. If the parent were appended to instead of cleared, a worker could read changed data without any exception. Copy before handing a slice to another thread.

> **这不是可靠的保护。** 这个异常只是尽力而为的检查，而这里的视图是在其他线程上无同步地读取的。如果父列表是被追加而不是被清空，工作线程可能读到已改变的数据却不抛任何异常。把一段数据交给其他线程之前，先复制。

**Trade-offs.** A copy costs one array per batch, which is small next to an API call. Views remain useful inside one method for range operations on a list you own.

> **权衡。** 复制意味着每个批次多一个数组，与一次 API 调用相比微不足道。在单个方法内部，对自己拥有的列表做区间操作时，视图依然很有用。

</details>
