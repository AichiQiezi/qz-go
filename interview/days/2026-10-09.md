## 1. Goroutine leak behind a timed-out downstream call

**下游调用超时后产生的 goroutine 泄漏** · `Go` · `Hard`

### Question

A Go service's memory grows steadily. A goroutine profile shows 50k goroutines parked in `chan send`. The handler looks like this:

```go
func handle(w http.ResponseWriter, r *http.Request) {
    ch := make(chan Result)
    go func() { ch <- callDownstream() }()
    select {
    case res := <-ch:
        write(w, res)
    case <-time.After(2 * time.Second):
        http.Error(w, "timeout", 504)
    }
}
```

Explain the root cause, give two different fixes, and describe how you would catch this class of bug before production.

### 题目

一个 Go 服务的内存持续增长。goroutine profile 显示有 5 万个 goroutine 阻塞在 `chan send` 上。处理函数如下：

```go
func handle(w http.ResponseWriter, r *http.Request) {
    ch := make(chan Result)
    go func() { ch <- callDownstream() }()
    select {
    case res := <-ch:
        write(w, res)
    case <-time.After(2 * time.Second):
        http.Error(w, "timeout", 504)
    }
}
```

请解释根本原因，给出两种不同的修复方式，并说明如何在上线前发现这类问题。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Root cause.** The channel is unbuffered. When the timeout branch wins, the handler returns and nobody ever receives from `ch`. The worker goroutine blocks forever on the send. A blocked goroutine is never garbage collected, and it keeps its stack and everything it references alive, so memory grows with every timed-out request.

**Fix 1: make the send non-blocking for the loser.** Use `make(chan Result, 1)`. The single send always succeeds, the goroutine exits, and the buffered value is collected with the channel. This only works because there is exactly one sender.

**Fix 2: propagate cancellation.** Create `ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)`, pass `ctx` into the downstream call (`http.NewRequestWithContext`), and in the goroutine `select` on `ctx.Done()` when sending. This also stops wasted work downstream, which Fix 1 alone does not.

**Catching it early.**
- `go.uber.org/goleak` in `TestMain` fails tests that leave goroutines behind.
- Export `runtime.NumGoroutine()` as a metric and alert on a sustained upward slope.
- In an incident, `/debug/pprof/goroutine?debug=2` groups goroutines by stack and shows the blocking line directly.

#### 参考答案

**根本原因。** channel 是无缓冲的。超时分支先触发后，handler 直接返回，再没有人从 `ch` 接收数据，于是工作 goroutine 永远阻塞在发送语句上。被阻塞的 goroutine 不会被垃圾回收，它的栈以及引用的所有对象都会一直存活，所以每发生一次超时请求，内存就多涨一点。

**修复 1：让落败的一方发送不阻塞。** 使用 `make(chan Result, 1)`。唯一的一次发送一定成功，goroutine 随即退出，缓冲里的值随 channel 一起被回收。这个办法只在恰好只有一个发送方时成立。

**修复 2：传播取消信号。** 创建 `ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)`，把 `ctx` 传给下游调用（`http.NewRequestWithContext`），并在 goroutine 里发送结果时对 `ctx.Done()` 做 `select`。这样还能让下游停止无用的工作，而修复 1 做不到这一点。

**如何提前发现。**
- 在 `TestMain` 中使用 `go.uber.org/goleak`，测试结束后仍有 goroutine 残留就判定失败。
- 把 `runtime.NumGoroutine()` 作为指标导出，对持续上升的趋势告警。
- 线上排查时用 `/debug/pprof/goroutine?debug=2`，它按调用栈聚合 goroutine，可以直接定位阻塞的那一行。

</details>

## 2. Syncing a product catalog to four ad platforms reliably

**把商品目录可靠地同步到四个广告平台** · `System Design` · `Senior`

### Question

Merchants edit products constantly. You must keep their catalogs in sync with Google Merchant Center, Meta, Pinterest and TikTok. Each platform has different rate limits, batch APIs and outage patterns. Design the pipeline. Cover ordering, idempotency, rate limiting, failure isolation and how you detect drift.

### 题目

商家会频繁编辑商品。你需要让他们的商品目录与 Google Merchant Center、Meta、Pinterest 和 TikTok 保持同步。每个平台的限流、批量接口和故障模式各不相同。请设计这条流水线，需要涵盖：顺序性、幂等性、限流、故障隔离，以及如何发现数据漂移。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Source of truth and capture.** Write product changes and an outbox row in the same DB transaction (or read the binlog via CDC). That gives at-least-once delivery without dual-write races.

**Ordering.** Publish to a queue keyed by `(merchant_id, product_id)` so changes to one product are processed in order. Every event carries a monotonically increasing `version`.

**Per-platform isolation.** Fan out to one consumer group, queue and worker pool per platform. A Pinterest outage then backs up only the Pinterest lane. Each lane has its own retry policy, circuit breaker and dead-letter queue.

**Idempotency.** Keep a `sync_state(platform, merchant, product)` row with `last_synced_version` and a content hash. Skip events whose version is not newer, and skip when the payload hash is unchanged. A redelivered or reordered event then becomes a no-op. Use the platform's own item id or offer id as the upsert key.

**Rate limiting.** A token bucket per platform and per merchant account, sized from the documented quota. Coalesce bursts: wait a short window and send only the latest version of each product, using batch endpoints where they exist. Retry on 429 and 5xx with exponential backoff plus jitter.

**Drift detection.** Events can still be lost, so run a periodic reconciliation. Pull platform-side status or a hash listing, diff against `sync_state`, and enqueue repairs. Also surface platform-side disapprovals (for example crawl or policy errors) as first-class data for merchants.

**Observability.** Track lag per lane, success rate per error code, DLQ depth and reconciliation diff size.

#### 参考答案

**数据源与变更捕获。** 在同一个数据库事务中写入商品变更和一条 outbox 记录（或通过 CDC 读取 binlog）。这样可以做到至少一次投递，并避免双写竞争。

**顺序性。** 以 `(merchant_id, product_id)` 为 key 发布到队列，让同一个商品的变更按顺序处理。每个事件都携带单调递增的 `version`。

**按平台隔离。** 为每个平台提供独立的消费者组、队列和 worker 池。这样 Pinterest 故障时，只会让 Pinterest 这条通道积压。每条通道有自己的重试策略、熔断器和死信队列。

**幂等性。** 维护一张 `sync_state(platform, merchant, product)` 表，记录 `last_synced_version` 和内容哈希。版本不更新的事件直接跳过，内容哈希未变也跳过。这样重复投递或乱序的事件都会变成空操作。使用平台自己的 item id 或 offer id 作为 upsert 的键。

**限流。** 对每个平台、每个商家账号使用令牌桶，容量依据文档中的配额设定。合并突发流量：等待一个短窗口，只发送每个商品的最新版本，有批量接口时优先使用。遇到 429 和 5xx 时用指数退避加抖动重试。

**漂移检测。** 事件仍然可能丢失，所以要定期对账。拉取平台侧的状态或哈希清单，与 `sync_state` 比对，再把需要修复的项重新入队。同时把平台侧的拒审信息（例如抓取或政策错误）作为一等数据展示给商家。

**可观测性。** 监控每条通道的延迟、按错误码统计的成功率、死信队列深度，以及对账差异的大小。

</details>

## 3. Deadlocks from locking a row that does not exist

**锁定一行不存在的数据导致的死锁** · `Database` · `Hard`

### Question

Under InnoDB's default `REPEATABLE READ`, two concurrent transactions run:

```sql
BEGIN;
SELECT * FROM coupons WHERE code = 'SAVE10' FOR UPDATE;  -- no such row yet
INSERT INTO coupons (code, ...) VALUES ('SAVE10', ...);
COMMIT;
```

`code` has a regular (non-unique) secondary index. Production logs show error 1213 (deadlock). Explain exactly why, and how you would fix it.

### 题目

在 InnoDB 默认的 `REPEATABLE READ` 隔离级别下，两个并发事务执行：

```sql
BEGIN;
SELECT * FROM coupons WHERE code = 'SAVE10' FOR UPDATE;  -- 这行数据还不存在
INSERT INTO coupons (code, ...) VALUES ('SAVE10', ...);
COMMIT;
```

`code` 上是普通（非唯一）二级索引。线上日志出现了错误 1213（死锁）。请准确解释原因，并说明如何修复。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Why.** Locking a missing key under `REPEATABLE READ` takes a **gap lock** (part of a next-key lock) on the index range where the key would live. Gap locks are compatible with each other, so both transactions acquire one without blocking. Each then tries to `INSERT`, which needs an insert-intention lock in that same gap. Each insert waits on the other's gap lock, which forms a cycle. InnoDB detects it and rolls one transaction back with error 1213.

**Fixes, roughly in order of preference.**
- Add a **unique index** on `code` and use `INSERT ... ON DUPLICATE KEY UPDATE` or `INSERT IGNORE`, then read the result. The unique check is atomic and needs no preliminary `SELECT ... FOR UPDATE`.
- Run the transaction under `READ COMMITTED`, which does not take gap locks for plain index scans (foreign key and duplicate-key checks still do).
- Keep the transaction short, and **retry** on 1213 and 1205. Deadlocks are normal under concurrency, so handle them in code.
- If you must pre-lock, lock a parent row that exists, so all writers serialize on the same record.

**Diagnosis.** `SHOW ENGINE INNODB STATUS` prints the latest deadlock with both transactions, the locks held and the locks waited for. Enable `innodb_print_all_deadlocks` to log every one.

#### 参考答案

**原因。** 在 `REPEATABLE READ` 下锁定一个不存在的键，会在该键应当所在的索引区间上加**间隙锁**（next-key 锁的一部分）。间隙锁之间是兼容的，所以两个事务都能加锁成功而不会互相阻塞。随后各自执行 `INSERT`，需要在同一个间隙上获取插入意向锁。两边的插入都在等待对方持有的间隙锁，形成环路。InnoDB 检测到后回滚其中一个事务，并返回错误 1213。

**修复方式，大致按推荐顺序：**
- 给 `code` 加**唯一索引**，使用 `INSERT ... ON DUPLICATE KEY UPDATE` 或 `INSERT IGNORE`，再读取结果。唯一性检查是原子的，不需要事先的 `SELECT ... FOR UPDATE`。
- 改用 `READ COMMITTED` 隔离级别。对普通索引扫描它不会加间隙锁（外键和重复键检查仍会加）。
- 保持事务简短，并对 1213 和 1205 **重试**。并发下死锁是正常现象，应当在代码里处理。
- 如果必须预先加锁，就锁住一个已存在的父行，让所有写入者都在同一条记录上串行化。

**排查方法。** `SHOW ENGINE INNODB STATUS` 会打印最近一次死锁，包括两个事务、各自持有的锁和等待的锁。开启 `innodb_print_all_deadlocks` 可以把每一次死锁都记录到日志。

</details>

## 4. ConcurrentHashMap and the check-then-act trap

**ConcurrentHashMap 与先检查后执行的陷阱** · `Java & CS` · `Medium`

### Question

Since Java 8, how does `ConcurrentHashMap` stay thread-safe without segment locks? Then explain why this code is still buggy even though the map is thread-safe:

```java
if (!map.containsKey(key)) {
    map.put(key, expensiveCreate());
}
```

### 题目

自 Java 8 起，`ConcurrentHashMap` 在没有分段锁的情况下是如何保证线程安全的？接着请解释：即使 map 本身线程安全，下面这段代码为什么仍然有 bug：

```java
if (!map.containsKey(key)) {
    map.put(key, expensiveCreate());
}
```

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**Mechanism.** The table is an array of bins. Writing to an empty bin uses a **CAS** with no lock. Writing to a non-empty bin takes `synchronized` on that bin's head node, so contention is per bin rather than per segment. Reads are lock-free through `volatile` table and node fields. Long chains (8 or more nodes, with table size at least 64) are converted to red-black trees. The size is tracked with striped counters that are summed on demand, so `size()` is an estimate under concurrency. During resize, threads help migrate bins.

**Why the snippet is wrong.** Each call is individually atomic, but the sequence is not. Two threads can both see the key absent, and both create and put the value, so one result is silently overwritten and `expensiveCreate()` runs twice. This is a classic check-then-act race.

**Fix.** Use an atomic compound operation:

```java
map.computeIfAbsent(key, k -> expensiveCreate());
```

The function runs at most once per key and runs while the bin is locked. Keep it short and never modify the same map inside it, because that can deadlock or throw `IllegalStateException: Recursive update`. If creation is slow and you want to avoid holding the bin lock, store a `FutureTask` or `CompletableFuture` with `putIfAbsent`, then wait on it outside the lock.

#### 参考答案

**实现机制。** 底层是一个桶数组。向空桶写入使用 **CAS**，无需加锁。向非空桶写入则对该桶的头节点加 `synchronized`，所以竞争发生在单个桶上，而不是整个分段。读操作通过 `volatile` 的表和节点字段实现无锁读取。链过长（节点数达到 8，且表容量至少为 64）时会转换为红黑树。元素数量用分散的计数器记录，调用时再求和，因此并发下 `size()` 只是一个估计值。扩容时，多个线程会协助迁移桶。

**为什么这段代码是错的。** 每个调用单独看都是原子的，但它们组合起来不是。两个线程可能同时看到 key 不存在，都去创建并 put，其中一个结果被悄悄覆盖，`expensiveCreate()` 也被执行了两次。这是典型的“先检查后执行”竞态。

**修复。** 使用原子的复合操作：

```java
map.computeIfAbsent(key, k -> expensiveCreate());
```

对每个 key，这个函数最多执行一次，并且是在持有桶锁的情况下执行。函数体要尽量短，并且绝不能在其中修改同一个 map，否则可能死锁或抛出 `IllegalStateException: Recursive update`。如果创建很慢，又不想长时间占用桶锁，可以用 `putIfAbsent` 存入一个 `FutureTask` 或 `CompletableFuture`，然后在锁外等待它完成。

</details>

## 5. How cache-aside still serves stale data

**旁路缓存（cache-aside）为什么仍会读到脏数据** · `Middleware` · `Medium`

### Question

You use cache-aside with Redis: read from cache, on a miss read the DB and fill the cache, and on update write the DB then delete the cache key. Users still occasionally see stale values for a long time. Describe a concrete interleaving that causes it, and list mitigations with their trade-offs.

### 题目

你使用 Redis 的旁路缓存模式：先读缓存，未命中则读数据库并回填缓存；更新时先写数据库，再删除缓存 key。但用户偶尔仍会长时间看到过期的值。请描述一个会导致这种情况的具体时序，并列出各种缓解方案及其取舍。

<details>
<summary><b>Answer · 参考答案</b></summary>

#### Answer

**The race.** Thread A reads the key, misses, and reads the old value from the DB. Thread B then updates the DB and deletes the cache key. Thread A finally writes its old value into the cache. The cache now holds stale data until the TTL expires, and no later write will fix it because the delete already happened.

**Mitigations.**
- **TTL as a backstop.** Always set one. It bounds staleness but does not remove it.
- **Delayed double delete.** Delete again a few hundred milliseconds after the DB write. It narrows the window but the delay is a guess.
- **Invalidate from the binlog** (for example with Canal or Debezium). A single ordered stream deletes the key after the commit is visible, and it also catches writers that forgot to touch the cache. It adds infrastructure and some lag.
- **Versioned cache values.** Store `(value, version)` and fill with a Lua script that only writes when the version is newer. This is strict, but every write path must carry versions.
- **Single flight on miss** (a per-key mutex or `singleflight` in Go) to avoid stampedes. It reduces concurrent fills but does not remove this race on its own.

Also mention that deleting the cache after the DB write is preferred over updating the cache, because concurrent updates can land out of order.

#### 参考答案

**竞态过程。** 线程 A 读缓存未命中，从数据库读到旧值。接着线程 B 更新数据库并删除缓存 key。最后线程 A 才把它读到的旧值写入缓存。此后缓存里一直是脏数据，直到 TTL 过期；后续的写操作也无法修复，因为删除操作已经发生过了。

**缓解方案。**
- **用 TTL 兜底。** 一定要设置。它只能限制脏数据的持续时间，不能彻底消除。
- **延迟双删。** 在写库后过几百毫秒再删一次。它缩小了窗口，但延迟时间只能靠经验估计。
- **基于 binlog 失效缓存**（例如 Canal 或 Debezium）。单一有序的数据流在事务提交后删除 key，也能覆盖忘记操作缓存的其他写入方。代价是增加基础设施和一定延迟。
- **带版本的缓存值。** 存储 `(value, version)`，用 Lua 脚本回填，只有版本更新时才写入。这种方式最严格，但每条写路径都要携带版本。
- **未命中时的 single flight**（按 key 的互斥锁，或 Go 的 `singleflight`），避免缓存击穿造成的并发回填。它减少并发回填，但本身并不能消除这个竞态。

另外要提到：写库后“删除”缓存比“更新”缓存更好，因为并发的更新可能乱序落地。

</details>
