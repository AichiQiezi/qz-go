## 1. Exchange-rate lookups share one upstream call through singleflight, and when one shopper closes the tab, hundreds of checkouts fail with "context canceled"

**汇率查询通过 singleflight 共用一次上游调用，结果一个顾客关掉页面，几百个结账请求都以 "context canceled" 失败** · `Go` · `Senior`

### Question · 题目

The checkout service converts prices with exchange rates from a paid API. To avoid a stampede when the cache entry expires, a teammate wrapped the fetch in `singleflight.Group.Do`, keyed by currency, and passed the request's `ctx` into the fetch. Since then, two things happen: bursts of checkouts fail with `context canceled` or `context deadline exceeded` at the same moment, and during an API slowdown checkouts with a 2-second budget wait much longer than 2 seconds.

> 结账服务用付费 API 提供的汇率来换算价格。为了在缓存过期时避免击穿，一位同事用 `singleflight.Group.Do` 包住了获取逻辑，以币种为 key，并把请求的 `ctx` 传进了获取函数。从那以后出现了两种现象：一批结账请求会在同一时刻以 `context canceled` 或 `context deadline exceeded` 失败；而在 API 变慢期间，预算只有 2 秒的结账请求等待的时间远远超过 2 秒。

Explain both symptoms and fix the code.

> 解释这两种现象，并修复代码。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why the bursts fail.** `Do` runs the function once, for the first caller, and gives every waiting caller the same result. The function closes over the first caller's `ctx`. When that shopper closes the tab, or that request's deadline passes, the shared fetch is cancelled and every caller waiting on the same key gets the first caller's error. In a local test, one caller with a 50 ms deadline made three callers with 2-second deadlines fail after about 40 ms.

> **为什么会成批失败。** `Do` 只为第一个调用方执行一次函数，然后把同一个结果交给所有等待的调用方。这个函数捕获的是第一个调用方的 `ctx`。当那位顾客关掉页面，或者那个请求的截止时间到了，共享的获取就被取消，同一个 key 上所有等待的调用方都会拿到第一个调用方的错误。在本地测试中，一个截止时间为 50 毫秒的调用方，让另外三个截止时间为 2 秒的调用方在约 40 毫秒后一起失败了。

**Why waits ignore the budget.** `Do` blocks until the shared call returns; it never looks at the waiting caller's own `ctx`. If the first caller had no deadline, everyone waits for the slow upstream. In the test, a caller with a 100 ms deadline waited the full 3 seconds of the upstream call.

> **为什么等待会无视预算。** `Do` 会一直阻塞到共享调用返回，它从不查看等待者自己的 `ctx`。如果第一个调用方没有截止时间，所有人都要等慢速的上游。在测试中，一个截止时间为 100 毫秒的调用方，等满了上游调用的整整 3 秒。

**The fix.** Give the shared call its own lifetime, and let each caller wait only as long as its own context allows:

> **修复方法。** 给共享调用一个独立的生命周期，并让每个调用方只等待它自己的 context 允许的时长：

```go
// get shares one upstream call per key, but each caller waits only as long as its own ctx allows.
func get(ctx context.Context, key string, delay time.Duration) (string, error) {
	ch := group.DoChan(key, func() (any, error) {
		// Detach from the caller that happened to start the call, and bound it on its own.
		cctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)
		defer cancel()
		return fetchUpstream(cctx, key, delay)
	})
	select {
	case r := <-ch:
		if r.Err != nil {
			return "", r.Err
		}
		return r.Val.(string), nil
	case <-ctx.Done():
		return "", ctx.Err() // the shared call keeps running for the others
	}
}
```

- `context.WithoutCancel` keeps the first caller's values, such as the trace ID, but not its cancellation; the explicit timeout bounds the upstream call for everyone.
  > `context.WithoutCancel` 保留了第一个调用方的值（比如 trace ID），但不继承它的取消；显式的超时为所有人限定了上游调用的时长。
- `DoChan` plus `select` lets a caller leave on its own deadline while the call keeps running for the others. In the test, the shopper who left failed alone and the other three got the rate.
  > `DoChan` 加上 `select`，让调用方可以按自己的截止时间离开，而调用继续为其他人运行。在测试中，离开的那位顾客单独失败，其余三个拿到了汇率。
- Errors are shared too. When the upstream fails, every waiter fails at once, so serve the last good rate for a bounded time instead of failing checkout.
  > 错误同样是共享的。上游失败时，所有等待者会同时失败，所以应在有限时间内继续使用上一次成功的汇率，而不是让结账失败。

**Trade-offs.** The shared call can now outlive every caller and spend a paid request nobody reads; the timeout caps that. A stale rate is a business decision: agree with finance how old a rate checkout may use.

> **权衡。** 现在共享调用可能比所有调用方活得都久，花掉一次没人读取的付费请求；超时限制了这种浪费。使用过期汇率是业务决策：要和财务约定结账最多能用多旧的汇率。

</details>

## 2. Designing the shopping cart for 100,000 storefronts: guest carts, merging carts at login, and prices that changed since an item was added

**为 10 万个店铺设计购物车：访客购物车、登录时合并购物车，以及加购之后价格发生变化** · `System Design` · `Hard`

### Question · 题目

Shoppers add items as guests, log in on another device, and expect one cart. Merchants run flash sales that change prices and stock while items sit in carts. Today the cart is a JSON blob in a cookie, so it is lost across devices, and checkout sometimes charges a price different from the one the cart showed.

> 顾客以访客身份加购商品，然后在另一台设备上登录，并期望看到同一个购物车。商家会做限时促销，在商品还躺在购物车里时改变价格和库存。目前购物车是存放在 cookie 里的一段 JSON，所以换设备就丢了，而且结账时有时收取的价格和购物车显示的不一样。

Design the cart service: data model, merging, pricing and stock, and how it scales.

> 设计购物车服务：数据模型、合并、定价与库存，以及如何扩展。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Store lines, not prices.** A cart belongs to a store and to either a guest token or a customer ID. Each line holds the variant ID, quantity and the time it was added. The price shown is computed when the cart is read, from the current catalog, promotions and the shopper's currency. A stored price only records what the shopper saw, so the service can tell them when it changed.

> **存商品行，不存价格。** 购物车属于某个店铺，并属于一个访客令牌或一个顾客 ID。每一行保存变体 ID、数量和加购时间。显示的价格在读取购物车时根据当前的商品目录、促销和顾客的币种计算得出。保存下来的价格只用来记录顾客当时看到的价格，以便在价格变化时提醒他们。

- **Guest carts:** a random token in a cookie points to a server-side cart with a TTL of a few weeks; the cookie holds no data.
  > **访客购物车：** cookie 中的随机令牌指向服务端的购物车，TTL 为几周；cookie 本身不存数据。
- **Merging at login:** one function, run once per guest token. For a variant in both carts, take the larger quantity rather than the sum, so a shopper who added the same item twice does not get two. Cap by the stock and per-order limits, then delete the guest cart in the same transaction so a retried login cannot merge twice.
  > **登录时合并：** 用一个函数完成，每个访客令牌只执行一次。对两个购物车里都有的变体，取较大的数量而不是相加，免得把同一商品加购了两次的顾客变成买两件。再按库存和单笔订单限制封顶，并在同一个事务里删除访客购物车，这样重试登录不会合并两次。
- **Concurrent edits:** two tabs update the same cart. Give the cart a version and make every write a compare-and-set on it, retrying on conflict.
  > **并发编辑：** 两个标签页会同时修改同一个购物车。给购物车一个版本号，每次写入都对它做比较并设置（compare-and-set），冲突时重试。

**Price and stock.** Adding to cart does not reserve stock; during a flash sale that would lock inventory in carts nobody buys. Checkout re-prices every line and reserves stock for a short window. If the total differs from what the cart last showed, checkout shows the new total and asks for confirmation rather than charging silently. The payment amount always comes from that final pricing, never from the client.

> **价格与库存。** 加购不预留库存；在限时促销期间，那样会把库存锁在没人买的购物车里。结账时对每一行重新定价，并在一个短时间窗口内预留库存。如果总价与购物车上次显示的不同，结账页面展示新的总价并请顾客确认，而不是悄悄扣款。支付金额永远来自这次最终定价，绝不来自客户端。

**Scale.** Carts are small, read often and keyed by store plus owner, so a key-value store or a partitioned table works; reads hit the price service, which should be cached per store and variant. Expire abandoned carts, but emit an event first so abandoned-cart emails still work.

> **扩展。** 购物车数据量小、读取频繁，并以店铺加所有者作为键，所以键值存储或分区表都可以；读取会访问价格服务，而价格服务应按店铺和变体做缓存。过期清理被放弃的购物车，但要先发出一个事件，让弃购提醒邮件仍然能工作。

**Trade-offs.** Not reserving at add-to-cart means some shoppers learn at checkout that an item sold out; reserving means unsold stock during the busiest hour. Merging by maximum can surprise a shopper who really wanted both; show the merged cart after login.

> **权衡。** 加购时不预留库存，意味着有些顾客到结账时才发现商品已售罄；预留库存则意味着在最忙的时段里有库存卖不出去。按较大值合并可能会让真心想要两件的顾客感到意外；登录后要把合并后的购物车展示出来。

</details>

## 3. The "current price" query shows an old price for some products, and the result changes after an update that changes nothing

**「当前价格」查询对某些商品显示旧价格，而且在一次什么都没改的更新之后结果就变了** · `Database` · `Medium`

### Question · 题目

Price history lives in `price_changes(id bigserial, product_id, price_cents, changed_at timestamptz)`. The storefront reads the current price with `SELECT DISTINCT ON (product_id) product_id, price_cents FROM price_changes ORDER BY product_id, changed_at DESC`. A bulk repricing job writes all of a product's changes in one transaction with `changed_at = now()`. Some products now show an old price, and after an unrelated maintenance `UPDATE` the same products show a different one.

> 价格历史存放在 `price_changes(id bigserial, product_id, price_cents, changed_at timestamptz)` 中。店铺前台用 `SELECT DISTINCT ON (product_id) product_id, price_cents FROM price_changes ORDER BY product_id, changed_at DESC` 读取当前价格。一个批量改价任务在一个事务里写入某个商品的所有变更，并设置 `changed_at = now()`。现在有些商品显示的是旧价格，而在一次无关的维护性 `UPDATE` 之后，同一批商品又显示出了另一个价格。

Explain what is happening and fix the query and the data.

> 解释发生了什么，并修复查询和数据。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Why.** `DISTINCT ON` keeps the first row of each group in the `ORDER BY` order. When two rows of a product have the same `changed_at`, the order between them is not defined, so Postgres returns whichever it reads first. `now()` is the transaction's start time and stays the same for every statement in the transaction, so the repricing job writes ties on purpose.

> **原因。** `DISTINCT ON` 按 `ORDER BY` 的顺序保留每组的第一行。当某个商品有两行的 `changed_at` 相同时，它们之间的顺序没有定义，所以 Postgres 会返回它先读到的那一行。`now()` 是事务的开始时间，在同一事务的每条语句中都保持不变，所以改价任务必然写出并列的时间。

**Reproduced locally:** with two changes at the same time, the query returned the first one inserted. A no-op `UPDATE` on that row moved its new version to the end of the table, and the same query then returned the other row. Nothing about the data changed, only the physical order.

> **本地复现：** 有两条变更时间相同时，查询返回了先插入的那一条。对那一行做一次不改任何值的 `UPDATE`，会把它的新版本移到表的末尾，于是同一个查询返回了另一行。数据本身什么都没变，变的只是物理顺序。

**Fix the query** with a unique tiebreaker, and give it an index that matches the order:

> **修复查询：** 加一个唯一的决胜字段，并建立一个与排序一致的索引：

```sql
-- Ties on changed_at are broken by id, so the answer no longer depends on row order.
SELECT DISTINCT ON (product_id) product_id, price_cents
FROM price_changes
WHERE product_id = ANY($1)
ORDER BY product_id, changed_at DESC, id DESC;

CREATE INDEX ON price_changes (product_id, changed_at DESC, id DESC);
```

- `id` follows insertion order within the job, so it picks the last change the job wrote. Across concurrent writers, sequence order is not commit order, so decide which writer should win and record it explicitly, for example with a version number.
  > 在同一个任务内，`id` 遵循插入顺序，所以会选出任务最后写入的那条变更。但在并发写入者之间，序列顺序并不等于提交顺序，所以要决定哪个写入者应该胜出，并显式记录下来，比如用版本号。
- If a row needs its own time, `clock_timestamp()` changes during a transaction, while `now()` does not; ties are still possible, so keep the tiebreaker.
  > 如果每一行需要自己的时间，`clock_timestamp()` 在事务中会变化，而 `now()` 不会；但仍然可能出现并列，所以决胜字段要保留。
- For the storefront, store the current price on the product row, updated in the same transaction as the history. Reading one row is cheaper than sorting history on every page view.
  > 对店铺前台来说，把当前价格存在商品行上，并与历史记录在同一个事务中更新。读一行比每次浏览页面都对历史排序要便宜。

**Trade-offs.** The extra column must be kept in sync, which the shared transaction handles; the history table stays the record of how a price got there.

> **权衡。** 额外的列必须保持同步，同一个事务可以保证这一点；历史表依然是价格如何变成现在这样的记录。

</details>

## 4. A Redis sorted-set leaderboard of best-selling products: revenue shows 0.99999999999999989, tied products swap places, and page 2 repeats a product from page 1

**用 Redis 有序集合做的商品销量排行榜：销售额显示为 0.99999999999999989、并列的商品互换位置，第 2 页还重复了第 1 页的商品** · `Middleware` · `Hard`

### Question · 题目

The merchant dashboard shows top-selling products from a sorted set per month: every paid order line runs `ZINCRBY revenue:<month> <amount> <sku>` with the amount in dollars, such as 12.99. Merchants report three problems: revenues like 0.99999999999999989, products with the same revenue changing order between refreshes, and page 2 (`ZREVRANGE ... 20 39`) showing a product that was already on page 1.

> 商家后台按月用一个有序集合展示最畅销的商品：每一条已支付的订单行都执行 `ZINCRBY revenue:<month> <amount> <sku>`，金额以美元计，比如 12.99。商家反馈了三个问题：销售额出现 0.99999999999999989 这样的值；销售额相同的商品在刷新之间顺序会变；第 2 页（`ZREVRANGE ... 20 39`）出现了第 1 页已经展示过的商品。

Explain each problem and redesign the leaderboard.

> 解释每一个问题，并重新设计这个排行榜。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Scores are doubles.** A sorted-set score is a 64-bit floating-point number. Adding 0.1 ten times in a local test gave 0.99999999999999989, because 0.1 has no exact binary form. Store integer cents: integers are exact up to 2^53, and beyond that they are rounded too, which the test also showed.

> **分数是 double。** 有序集合的分数是 64 位浮点数。在本地测试中把 0.1 累加十次，得到 0.99999999999999989，因为 0.1 没有精确的二进制表示。改为存整数的分：整数在 2^53 以内是精确的，超过之后同样会被舍入，测试也证实了这一点。

**Ties are ordered by member name.** Members with equal scores are sorted by name in byte order, and `ZREVRANGE` reverses that, so `sku:zebra` came before `sku:apple`. The order changes whenever one tied product sells again. If ties need a business rule, such as more units first, encode it in the score or sort the page in the application.

> **并列按成员名称排序。** 分数相同的成员按名称的字节顺序排列，`ZREVRANGE` 会把它反过来，所以 `sku:zebra` 排在了 `sku:apple` 前面。只要并列的商品中有一个又卖出了，顺序就会变化。如果并列需要业务规则（比如销量件数多的在前），就把它编码进分数，或者在应用里对这一页排序。

**Offsets move under writes.** Page 2 is computed from the live set. In the test, a product that jumped up between two page requests pushed another product down, so it appeared on both pages. A cursor by score does not fully help, because ties make the boundary ambiguous.

> **偏移量会随写入移动。** 第 2 页是根据实时集合计算的。在测试中，一个商品在两次分页请求之间排名上升，把另一个商品挤了下去，于是那个商品在两页上都出现了。按分数做游标也不能完全解决，因为并列会让分页边界变得不明确。

**The redesign: page from a snapshot.**

> **重新设计：从快照分页。**

```text
ZINCRBY revenue:2026-11 1299 sku:A            # integer cents, not 12.99
ZRANGESTORE top:2026-11:1042 revenue:2026-11 0 999 REV
EXPIRE top:2026-11:1042 600
ZRANGE top:2026-11:1042 20 39 REV WITHSCORES   # page 2, always from the same snapshot
```

- A job copies the top entries into a versioned key every minute with `ZRANGESTORE` (Redis 6.2 or later) and sets a TTL. The first page returns the snapshot ID, and later pages read the same snapshot, so they cannot overlap.
  > 一个任务每分钟用 `ZRANGESTORE`（Redis 6.2 及以上）把排名靠前的条目复制到一个带版本号的 key 中，并设置 TTL。第一页返回快照 ID，后续页面读取同一个快照，所以不会重叠。
- Retried order events must not count twice: make the increment idempotent per order line, for example with a Lua script that checks a set of processed line IDs.
  > 重试的订单事件不能重复计数：让每一条订单行的累加是幂等的，比如用一个 Lua 脚本先检查已处理订单行 ID 的集合。
- Redis is a view, not the record. Rebuild the month from the orders database when it drifts.
  > Redis 只是一个视图，不是记录。出现偏差时，从订单数据库重建这个月的数据。

**Trade-offs.** Snapshots are up to a minute old and cost memory per version; that is fine for a dashboard, not for checkout logic.

> **权衡。** 快照最多落后一分钟，并且每个版本都占内存；这对后台看板没问题，但不适用于结账逻辑。

</details>

## 5. A supplier's variant feed crashes on rows with empty trailing columns, and every product gets one-letter tags

**供应商的变体文件在末尾列为空的行上崩溃，而且每个商品都被打上了单个字母的标签** · `Java & CS` · `Medium`

### Question · 题目

The importer reads lines like `SKU-1,red|wool|winter,M,blue` with `line.split(",")` and then `line.split(",")[1].split("|")` for tags. Rows such as `SKU-2,wool,,` throw `ArrayIndexOutOfBoundsException` at index 2, and the tags that do import come out as `r`, `e`, `d`, `|` and so on.

> 导入程序用 `line.split(",")` 读取 `SKU-1,red|wool|winter,M,blue` 这样的行，再用 `line.split(",")[1].split("|")` 拆分标签。像 `SKU-2,wool,,` 这样的行会在下标 2 处抛出 `ArrayIndexOutOfBoundsException`，而成功导入的标签变成了 `r`、`e`、`d`、`|` 等等。

Explain both bugs and fix the parser.

> 解释这两个 bug，并修复解析器。

<details>
<summary><b>Answer · 参考答案</b></summary>

**Trailing empty strings are removed.** `split(regex)` is `split(regex, 0)`, and a limit of 0 drops trailing empty strings. In a local test `"SKU-1,Wool scarf,,".split(",")` returned 2 elements, while `split(",", -1)` returned 4. Empty fields in the middle stay; only the trailing ones vanish, which is why only some rows fail.

> **末尾的空字符串会被移除。** `split(regex)` 就是 `split(regex, 0)`，而 limit 为 0 时会丢弃末尾的空字符串。在本地测试中，`"SKU-1,Wool scarf,,".split(",")` 返回 2 个元素，而 `split(",", -1)` 返回 4 个。中间的空字段会保留，只有末尾的会消失，所以只有部分行出错。

**The argument is a regex.** `|` means "empty or empty", which matches between every character, so `"red|wool|winter".split("|")` splits into single characters. The same trap hits `.`: `"1.5.2".split(".")` returned an empty array, because every character is a separator and all the resulting empty strings are trailing.

> **参数是正则表达式。** `|` 的意思是「空或空」，它会在每两个字符之间匹配，所以 `"red|wool|winter".split("|")` 被拆成了单个字符。`.` 也有同样的陷阱：`"1.5.2".split(".")` 返回了空数组，因为每个字符都是分隔符，产生的空字符串全都位于末尾。

**The fix:**

> **修复方法：**

```java
String[] cols = line.split(",", -1);          // keep trailing empty fields
if (cols.length != 4) {
    throw new FeedRowException(lineNo, "expected 4 columns, got " + cols.length);
}
String[] tags = cols[1].isEmpty()
        ? new String[0]
        : cols[1].split(Pattern.quote("|"));  // a literal |, not a regex
```

- `Pattern.quote` or `"\\|"` makes the separator literal; a precompiled `Pattern` is also faster in a hot loop.
  > `Pattern.quote` 或 `"\\|"` 能让分隔符按字面匹配；在高频循环中，预编译的 `Pattern` 也更快。
- Validate the column count and report the line number, instead of indexing blindly.
  > 校验列数并报告行号，而不是盲目地按下标取值。
- Note that `"".split(",")` returns one empty string, not an empty array, so handle empty input explicitly.
  > 注意 `"".split(",")` 返回的是一个空字符串，而不是空数组，所以要显式处理空输入。

**Trade-offs.** `split` cannot handle quoted fields: `"Scarf, wool",12` splits inside the quotes. Once a feed can contain quotes or commas in titles, use a real CSV parser and keep `split` for simple internal formats.

> **权衡。** `split` 无法处理带引号的字段：`"Scarf, wool",12` 会在引号内部被拆开。一旦文件中可能出现引号或标题里带逗号，就要使用真正的 CSV 解析器，`split` 只留给简单的内部格式。

</details>
